59.1Why Python, and three ways to run it

Python is a programming language designed to be readable. It uses plain English words (if, for, in, not) and indentation instead of lots of brackets. For AI work it has the biggest set of ready-made libraries: Anthropic's own anthropic SDK, HTTP clients, data analysis, and test tools such as pytest.

In everyday life

A Python script is a recipe written for a very literal cook. The cook follows each line exactly, top to bottom, and never guesses what you meant. If a step says "add the sugar" and there's no sugar, the cook stops and tells you precisely which line failed and why. That's a traceback, and by the end of this chapter you'll read them calmly.

59.2Values, variables and strings

A variable is a name that points to a value. You create one with =, which means "make this name refer to this value", not "is equal to". Python works out the type of value for you.

TypeExampleWhat it holds
str (string)"Login fails on Safari"Text, in single or double quotes
int (integer)47Whole numbers
float94.7Numbers with a decimal point
bool (Boolean)True, FalseYes or no; note the capital letters
NoneNone"No value"; JSON's null becomes None
list["chromium", "firefox"]An ordered collection
dict (dictionary){"id": "QA-7", "severity": "high"}Named fields: key → value

The most useful string feature is the f-string: put f before the opening quote, and anything in {braces} is replaced with its value. {rate:.1f} means "show this number with one decimal place". Other string tools you'll use constantly: .strip() removes spaces at both ends, .lower() makes text lower-case for comparisons, .split(",") breaks text into a list, .startswith("ERR") checks the beginning, and "x" in text checks whether one string contains another.

Under the hood: names point to values

In Python a variable isn't a box that holds a value; it's a label stuck on a value. a = [1, 2] then b = a sticks a second label on the same list, so b.append(3) changes what a shows too. Numbers and strings can't be changed in place (they're immutable), so this surprise only appears with lists and dictionaries, which can (mutable). If you need an independent copy, use b = a.copy(). This matters when you pass a list into a function and the function modifies it.

Read the script again with these four ideas in mind:

  • Indentation is part of the language. The lines indented under for, if and def belong to them. Use four spaces, consistently. A line ending in a colon : always starts an indented block.
  • if / elif / else choose between paths. Comparisons are == (equal), !=, <, >= and so on, combined with and, or, not.
  • for name in browsers: repeats the indented block once per item. for i in range(3): repeats with i = 0, 1, 2. A while loop repeats as long as a condition is true; you'll use one for pagination in Chapter 60.
  • def defines a function: a named, reusable step. Values go in as parameters, and return sends a result back. The text in triple quotes is a docstring, a short description of what the function does. Calling with a name, as in open_blockers=0, makes the call easier to read.
Real-world example

A release gate is just a function: "go" when the pass rate is at least 95% and there are no open blockers. Writing it as a function means the rule lives in one place. When the team changes the threshold to 98%, you change one number, and every script that calls the function follows. (The thresholds here are illustrative.)

59.5Modules and the standard library

A module is simply a .py file whose functions other files can import. Split your helpers into one file and reuse them everywhere. Save these two files side by side:

qa_utils.py
# qa_utils.py - helpers we want to reuse in several scripts
def pass_rate(passed, total):
    """Percentage of tests that passed, rounded to one decimal place."""
    if total == 0:
        return 0.0
    return round(passed / total * 100, 1)


def is_release_ready(rate, open_blockers, threshold=95):
    return rate >= threshold and open_blockers == 0


if __name__ == "__main__":
    # Runs only when you execute this file directly, not when it is imported
    print(pass_rate(47, 50), is_release_ready(94.0, 0))
gate.py
# gate.py - uses the functions from qa_utils.py
import sys

from qa_utils import is_release_ready, pass_rate

rate = pass_rate(passed=196, total=200)
blockers = 0
print(f"Pass rate {rate}% with {blockers} open blockers")

if is_release_ready(rate, blockers):
    print("GO")
    sys.exit(0)
else:
    print("NO GO")
    sys.exit(1)

sys.exit(1) ends the program with a non-zero exit code, which tells a shell script or CI pipeline that the check failed (Chapter 55). The if __name__ == "__main__": line in qa_utils.py means "only run this part when the file is executed directly": it lets a module contain a quick self-test without that test running every time someone imports it.

59.6Reading and writing files

Testers live in files: logs, CSV exports, reports. The pattern is always the same: with open(...) as f:. The with block closes the file for you, even if an error happens. Open mode "r" (the default) reads, "w" writes (replacing what was there) and "a" appends. Always say encoding="utf-8", so accented names and symbols behave the same on every operating system.

Save this sample log as app.log:

# log_scan.py - count log levels and list the errors
from collections import Counter

levels = Counter()
errors = []

with open("app.log", encoding="utf-8") as log:
    for line in log:
        parts = line.split()
        if len(parts) < 3:
            continue                    # skip blank or odd lines
        level = parts[2]
        levels[level] += 1
        if level == "ERROR":
            errors.append(line.strip())

print("Lines per level:", dict(levels))
print(f"{len(errors)} errors:")
for e in errors:
    print("  " + e)

with open("errors.txt", "w", encoding="utf-8") as out:
    out.write("\n".join(errors) + "\n")
print("Saved errors.txt")

Looping over an open file gives you one line at a time, which works even for logs far too big to load at once. line.split() with no argument splits on any run of spaces, so parts[2] is the third word: the level. Counter counts without you having to set each total to zero first.

59.7JSON: the format AI tools speak

APIs, Claude's structured outputs, Playwright's JSON reporter and most configuration files use JSON. Python's json module converts in both directions:

DirectionFrom text / stringFrom / to a file
JSON → Pythonjson.loads(text)json.load(f)
Python → JSONjson.dumps(data)json.dump(data, f, indent=2)

The "s" in loads and dumps stands for "string". JSON objects become dictionaries, arrays become lists, true/false become True/False, and null becomes None.

json_demo.py
import json

text = '{"id": "QA-101", "labels": ["checkout", "regression"], "estimate": null, "blocker": true}'
bug = json.loads(text)          # JSON text -> Python dict
print(type(bug).__name__, bug["labels"][0], bug["estimate"], bug["blocker"])

bug["labels"].append("ai-triaged")
print(json.dumps(bug))          # Python dict -> JSON text
print(bug.get("assignee", "unassigned"))

AI output isn't guaranteed JSON

When you ask a model to "reply in JSON", it usually does, but it may add a sentence before it or wrap it in a code fence, and json.loads will raise json.JSONDecodeError. Always wrap the parse in try/except and treat a failure as a test result, not a crash. For guaranteed shapes, use the API's structured-output features (Chapter 89).

59.8Errors, exceptions and reading tracebacks

When something goes wrong while Python runs, it raises an exception. If nothing catches it, the program stops and prints a traceback. Save this deliberately broken script as broken.py and run it:

Catching exceptions

try runs code that might fail; except SomeError runs only if that error happens. Catch specific errors you can do something useful about, such as a missing file, and let everything else surface:

Pattern
try:
    with open(path, encoding="utf-8") as f:
        data = json.load(f)
except FileNotFoundError:
    print(f"No such file: {path}")
    sys.exit(2)
except json.JSONDecodeError as err:
    print(f"{path} is not valid JSON: {err}")
    sys.exit(2)
Never write a bare except

except: or except Exception: pass swallows every error, including your own typos, and the script carries on with wrong data. In test tooling that's the worst outcome: a report that says "all passed" because the parser silently failed. AI-written code sometimes does this to "make it work". Ask Claude to catch only specific exceptions.

59.9Working with Claude on Python

Claude writes Python well, and with this chapter you can now review what it produces. A practical routine:

  • Give it a sample of the real input (a few anonymised rows of the CSV, a trimmed JUnit file) and the exact output you want. Inputs and outputs specify a script better than prose does.
  • Ask for standard-library only unless you need a package, so the script runs anywhere without installs.
  • Run it yourself, then feed it awkward input: an empty file, a missing column, an unexpected status such as "error". Those are the cases AI-written scripts most often get wrong.
  • When it fails, paste the full traceback, not "it doesn't work". The last line plus the deepest frame is usually enough for Claude to fix it in one step. Chapter 62 covers asking for help with errors effectively.

    # parse_junit.py - read a JUnit XML report and write a JSON summary
import json
import sys
import xml.etree.ElementTree as ET


def summarise(path):
    root = ET.parse(path).getroot()
    summary = {"passed": 0, "failed": 0, "skipped": 0, "failures": []}
    for case in root.iter("testcase"):
        problem = case.find("failure")
        if problem is None:
            problem = case.find("error")
        if problem is not None:
            summary["failed"] += 1
            summary["failures"].append({
                "test": f"{case.get('classname')}.{case.get('name')}",
                "message": problem.get("message", "").strip(),
            })
        elif case.find("skipped") is not None:
            summary["skipped"] += 1
        else:
            summary["passed"] += 1
    return summary


if __name__ == "__main__":
    report = sys.argv[1] if len(sys.argv) > 1 else "junit.xml"
    try:
        result = summarise(report)
    except FileNotFoundError:
        print(f"No such file: {report}. Check the path and try again.")
        sys.exit(2)
    except ET.ParseError as err:
        print(f"{report} is not valid XML: {err}")
        sys.exit(2)

    print(f"passed={result['passed']} failed={result['failed']} skipped={result['skipped']}")
    for f in result["failures"]:
        print(f"  FAIL {f['test']}: {f['message']}")

    with open("summary.json", "w", encoding="utf-8") as out:
        json.dump(result, out, indent=2)
    print("Wrote summary.json")
    sys.exit(1 if result["failed"] else 0)

Troubleshooting

  • python3: can't open file '…/parse_junit.py': [Errno 2] No such file or directory: you're in a different folder. Run cd ~/qa-python, then ls to check the file is there.
  • IndentationError or TabError after copying: your editor mixed tabs and spaces. In VS Code, use "Convert Indentation to Spaces" from the Command Palette.
  • Output differs slightly: check that you saved the sample files exactly; one changed status changes every count.
  • SyntaxError on an f-string: very old Python. Check python3 --version is 3.11 or newer.
  • Windows: use py parse_junit.py, and echo $LASTEXITCODE in PowerShell instead of echo $?.
Common misunderstandings
"= means equals."
= assigns a value to a name; == compares two values.
"The first item is items[1]."
Positions start at 0. items[0] is the first, and items[-1] the last.
"Indentation is just style."
In Python it defines which lines belong to an if, loop or function. Wrong indentation changes what the program does.
"The top of a traceback shows the problem."
Start at the bottom: the last line names the error, and the frame just above it shows where it happened.
"Catching every exception makes a script robust."
It makes failures silent. Catch the specific errors you can handle and let the rest stop the script loudly.

  • Indentation defines blocks; if, for and def lines end in a colon.
  • Functions package one rule in one place; modules let several scripts share them; the standard library covers files, CSV, XML, JSON and more with no installs.
  • Open files with with open(..., encoding="utf-8").
  • Read tracebacks bottom up, catch only specific exceptions, and use exit codes so CI can act on your scripts.
Check yourself

What does bug.get("owner", "nobody") return when bug has no "owner" key?

.get() returns the default you supply when the key is missing; bug["owner"] would raise KeyError.

A traceback ends with ModuleNotFoundError: No module named 'httpx'. What is the most likely fix?

The package isn't installed in the Python that's running. Naming your own file httpx.py would make things worse, because it would hide the real package.

Which is the right way to turn a JSON file into Python data?

load reads from a file; loads parses a string (passing a filename would try to parse the name itself); dump(s) goes the other way.

Where in a traceback should you look first?

The last line names the error and its message; the frame just above it is where it actually happened.

Why does parse_junit.py call sys.exit(1) when there are failures?

A non-zero exit code is the universal "this step failed" signal for shells and CI systems.
