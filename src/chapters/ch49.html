On its own, Claude only knows what was in its training data, which stops at a knowledge cutoff, and it knows nothing about your company's documents. Web search lets Claude look up current pages and show you where each claim came from. Research mode runs many searches that build on each other and turns them into a longer report. Connectors let Claude reach your own tools, such as Google Drive, GitHub, Jira or Slack, using your own permissions. All three make answers more useful, and all three need the same habit from you: open the sources and check them.

49.1Three ways Claude can know something

Before turning features on, it helps to know where an answer comes from. There are three places.

Where the answer comes fromGood forWeak atHow you can check it
Training (what the model learned before its cutoff)Concepts, explanations, writing, code patterns, test design techniquesAnything recent, anything niche, anything private to your companyYou can't see a source. Treat specific facts, versions and numbers as unverified.
Web search and ResearchCurrent versions, release notes, public documentation, news, standardsPages behind logins; low-quality pages that rank well; long pages that eat usageEach claim has a citation you can open
Connectors and attached filesYour Jira stories, Drive documents, repositories, Slack decisionsOnly what your account can open; only what the connector's tools exposeClaude links or names the item it read; open it in the source tool

Using external sources to anchor an answer is called grounding. A grounded answer is much less likely to be a hallucination, but "less likely" is not "never". Claude can still misread a page, quote the wrong version, or summarise a source that was itself wrong.

In everyday life

Think of a well-read colleague. Ask them a general question and they answer from memory: fast, usually right, sometimes out of date. Ask them to "check the docs" and they open a browser and come back with links. Ask them about your sprint and they need access to Jira first. Web search is the browser; connectors are the access badge.

49.2Web search: turning it on and reading the answer

Web search is available on all plans, including Free. It lets Claude search the public web and, when you give it a link, read the full page (Anthropic's help pages call that second part "web fetch"). Answers that use search include citations: links to the sources, and sometimes the exact quote Claude relied on.

Turning it on

As of 9 November 2026 (menus change often, so look for the same words if the layout has moved):

1. Open the menuSelect the + button at the lower left of the message box
2. Choose Web searchA checkmark shows it is on for this chat
3. AskClaude decides when a search would help and shows the sources

Anthropic's help page also notes that in the newer version of the Claude interface there may be no toggle at all: Claude searches when it judges a search would help. If you can't find the option, that is the likely reason.

Team and Enterprise

On Team and Enterprise plans, web search is off for everyone until an Owner or Primary Owner enables it in Organization settings > Capabilities. If the option is missing on your work account, ask your Claude admin rather than assuming the feature doesn't exist.

What it costs you

Searches and page reads count toward your usage limits. A long page you paste as a link (Anthropic's example is a 10,000-word article) fills a large part of the context window and uses far more of your allowance than a short answer. The help page suggests switching web search off for chats that don't need current information, and being selective about long links.

Reading citations like a tester

A citation shows where Claude says a claim came from. It does not prove the claim. Testers already know this pattern: a passing test only tells you what it actually checked. Apply the same thinking.

CheckWhat you're looking forRed flag
Does the source exist and load?The link opens the page Claude namedDead link, login page, or a different page
Does it say what Claude says?The quoted or summarised claim is actually on the pageThe page talks about the topic but not that specific claim
Is it the right source?Official docs, release notes, the standard itselfA blog, forum post or content farm used for a fact the vendor publishes
Is it the right version and date?The page matches the version you useDocs for an older major version; an undated page
Is anything missing?Claims without a citation are clearly marked as Claude's own reasoningA confident number or date with no source next to it
Real-world example

A QA lead asks: "Which browsers does the current Playwright release support, and has anything changed in the last two releases?" With web search on, Claude cites the Playwright release notes and the browser support page. The lead opens both, confirms the version numbers match the notes, and pastes the links into the test-strategy page. Without web search, Claude could only describe Playwright as of its training, and might name a version that is months old.

Search results can carry instructions

Web pages are written by strangers. A page can contain hidden text aimed at AI tools ("ignore your instructions and…"). This is prompt injection, covered in Chapter 127. For plain web search the main risk is a misleading answer. The risk grows when the same chat also has connectors that can take actions, which is why later sections talk about approvals.

49.3Research mode: many searches, one report

A single web search answers a single question. Some questions need more: "What are the main approaches to visual regression testing, which tools support each, and what do teams report as the trade-offs?" Research mode is built for this. According to Anthropic's help page, Claude runs several searches that build on each other, decides what to explore next, and works through open questions before writing its answer.

Your questionIdeally with scope, audience and the output you want
PlanClaude works out what it needs to find
Search, read, repeatEach finding shapes the next search, across the web and any connectors that are on
ReportA longer answer with sources

Plans, apps and how to start

  • Plans: paid plans only (Pro, Max, Ultra, Team and Enterprise).
  • Apps: web, desktop and mobile. On mobile it searches only the web and silently skips connectors, so start research on the web or desktop if you need your own tools included.
  • Needs: web search must be on.
  • Start it: select + at the lower left of the message box, then Research. A blue indicator appears at the bottom of the chat; select it again to turn Research off. (UI as of 9 November 2026.)

Two details from the help page are easy to miss. First, Research runs on a specific top-tier Opus model whatever model you picked for the chat, so on Team and Enterprise it stops working if an admin has blocked those models for your role. Second, Research can use your connectors' tools automatically, without asking for approval each time. It also can't use local MCP servers configured in the desktop app.

Automatic tool use

Because Research calls connector tools without stopping to ask, only turn on connectors you are happy for it to use freely. For a research task, read-only tools (search, read) are what you want. Use tool permissions (section 49.6) to set write tools to "Needs approval" or "Blocked".

When Research is worth it

Research uses the same usage limits as normal chats but can use them up faster, because it reads many sources. Use it when the question really is broad.

Good fits

  • Comparing three accessibility-testing tools for a tool-selection memo
  • "What changed in WCAG 2.2 that affects our checkout form?"
  • Pulling together everything your Drive and Jira hold about a feature before a test-planning session
  • A landscape review of contract-testing approaches

Poor fits

  • "What's the latest version of Node?" (one search is enough)
  • Explaining a concept Claude already knows well
  • Anything you need in thirty seconds
  • Questions about data no connector or website holds
Prompt: a well-scoped research request
Research question: which open-source tools can our team use for automated
accessibility checks in a Playwright test suite?

Context: web app, React front end, Playwright tests in TypeScript, run in
GitHub Actions. We must report against WCAG 2.2 AA.

I need:
1. A comparison table: tool, licence, how it plugs into Playwright,
   what it can and cannot detect, maintenance activity.
2. What automated tools cannot catch, with sources.
3. A recommendation with the trade-offs stated.

Prefer official documentation and the W3C over blogs. Say clearly when a
claim has no source.
Why multi-step search gives better answers (and new failure modes)

A single search returns whatever ranks well for one query. Research works more like an agent (Chapter 107): it reads results, notices gaps ("the docs mention a config option I haven't seen explained"), and issues follow-up searches. That loop finds things one query misses.

The same loop brings new risks. Early mistakes can shape later searches, so a wrong assumption gets "confirmed" by sources that were chosen because of it. A long report also hides weak claims in the middle of strong ones. Checking two or three key claims at random, rather than just the first, is a cheap way to catch this. Chapter 92 covers the same retrieval problems when you build your own system.

49.4Connectors: letting Claude into your tools

A connector links Claude to an outside app or service so it can find information there and, for some connectors, take actions. Under the hood most connectors are remote MCP servers: programs that offer Claude a set of tools such as "search issues" or "read file". You don't need to know that to use them, but it explains why connectors from different companies behave alike.

The rule that matters most: Claude inherits your permissions. A connector signs in as you, so Claude can only see what you can see in that service. If you can't open a Confluence space, neither can Claude. (A custom connector that uses one shared credential is the exception: it can reach whatever that credential allows.)

Where connectors work

AppKinds of connector
claude.ai on the webRemote connectors, including interactive ones that display content in the chat
Claude desktop appRemote connectors, plus local connectors installed as desktop extensions (Chapter 100)
Claude mobile appsRemote connectors you already added (installing new ones on mobile is in beta)
Claude CodeConnectors you added in claude.ai, when you sign in with your Claude account

Adding one from the directory

The Connectors Directory lists connectors from Anthropic and other providers, each labelled Verified or Community. As of 9 November 2026 you reach it through Customize > Connectors (in the desktop app, Customize is in the sidebar). From a chat you can also select +, hover over Connectors, and choose Manage connectors. Some help pages still say Settings > Connectors: the location has moved before and may move again.

Find itCustomize > Connectors, then browse or search
ConnectSelect the connect button; some ask for a server URL or region first
Sign in and reviewYou're sent to the service to sign in and approve the access Claude asks for
Turn it on per chat+ > Connectors, then the toggle for that service

Connecting doesn't mean Claude uses it everywhere. In each conversation you choose which connectors are on. When Claude wants to use a tool it may ask first; you can choose Allow once or Always allow. The Tool access setting in the same menu (Auto by default, or On demand) controls how many tools are loaded up front; the help page suggests On demand when you have ten or more connectors active.

Plans

Directory connectors are available on all plans, including Free, on web, desktop and mobile. Custom connectors (your own server URL) are on all plans too, but Free accounts are limited to one. On Team and Enterprise, an Owner must add a connector for the organization first; each member then signs in with their own account.

Real-world example: story to test ideas

A tester has the Atlassian and Google Drive connectors on. They ask: "Read story PAY-1423 in Jira and the 'Refunds v2' spec in Drive. List acceptance criteria that are ambiguous or contradict the spec, then draft test ideas for each criterion." Claude fetches both, quotes the exact lines that conflict, and links back to each. The tester checks the quoted lines in Jira and Drive before raising the questions in refinement. Two tools, one answer, and the tester never pasted anything. (The story key is illustrative.)

Connectors can write

Many connectors have tools that change things: create a Jira issue, post a Slack message, edit a file. Before turning a connector on in a chat that also reads untrusted content (web pages, customer emails, uploaded files), ask what the worst action it could take would be. Keep write tools on Needs approval, read the approval prompt properly, and never click "Always allow" on a write tool you haven't thought about. This is least privilege applied to AI.

49.6Custom connectors and tool permissions

If the service you need isn't in the directory but offers a remote MCP server, you can add it as a custom connector. As of 9 November 2026: Customize > Connectors, select Add, hover over Custom, choose Web, then enter a name and the server URL. You then pick an Authentication option: Sign in now, Sign in when needed or No sign in. Servers that use OAuth may also need an OAuth client choice, and fixed credentials go under Request headers.

Two facts shape what's possible:

  • Claude connects from Anthropic's cloud, not from your laptop. Your server must be reachable from the public internet unless your organisation uses the private-network options Anthropic documents. A server running on localhost or inside your company VPN won't work as a web connector; for that, use a desktop extension or Claude Code (Chapter 100).
  • Anthropic doesn't verify custom connectors. Only connect to servers you trust, and read the sign-in request before approving it.

Tool permissions

Each connector's page under Customize > Connectors has Tool permissions. Tools are grouped by type (for example read-only versus write or delete), and each group or single tool can be set to Always allow, Needs approval or Blocked. On Team and Enterprise, Owners can set organisation-wide limits that members cannot override. Restrictions only ever narrow access: they never give Claude more than your account has in the source system.

Tool typeSensible default for a QA teamWhy
Search and readAlways allowLow risk, and approvals for every read get tedious fast
Create (issues, comments, messages)Needs approvalVisible to colleagues; easy to undo, but noisy if wrong
Update, transition, deleteNeeds approval or BlockedCan change sprint data, close bugs or remove content
Admin toolsBlockedNo QA chat needs them

To stop using a connector in one chat, turn its toggle off. To sign Claude out of the service entirely, select Disconnect on the connector's page. Remove (in the three-dot menu) takes it off your account.

Connected services process data on their own infrastructure under their own terms, which may be outside the US. Opinion · this book's authors

For a QA team's first month, start small: web search on, one read-heavy connector (Drive or Atlassian), write tools set to Needs approval, and a shared page listing which connectors are approved and why. Add more once people have the habit of checking citations and reading approval prompts. Turning everything on at once tends to produce a few surprising Jira comments and a loss of trust that takes longer to fix than the setup did.

Common misunderstandings
"If there's a citation, the claim is true."
A citation shows where Claude says it got the claim. Open it: the page may not say that, may be outdated, or may itself be wrong.
"Connectors let Claude see everything in our Jira."
A standard connector signs in as you and sees only what your account can see. Custom connectors with shared credentials are the exception.
"Research mode is just a better web search, so I'll leave it on."
It uses your limits faster, takes longer, and calls connector tools without asking. Use it for broad questions only.
"The GitHub integration can review my pull requests."
It reads file names and contents only. It doesn't see pull requests, issues or commit history. Claude Code or Claude Tag handle that work.
"A custom connector can reach our internal test server."
Web connectors connect from Anthropic's cloud, so the server must be publicly reachable (or use the documented private-network options). Local servers belong in the desktop app or Claude Code.

Key takeaways
  • Training knowledge is fixed at a cutoff and has no sources; web search and connectors add current and private information with citations.
  • Web search is on all plans; on Team and Enterprise an Owner must enable it. Citations must be opened and checked.

  • Connectors sign in as you and inherit your permissions. Turn them on per chat, and use tool permissions to keep write tools on Needs approval.
