An error message is not the computer being rude. It's a short, precise report written by a program that knows exactly what went wrong and is trying to tell you. Most say three things: which program is speaking, what failed, and which file, line or address was involved. A small number of errors cause most of the trouble, and each has a usual cause and a usual fix. If you read the message slowly, check one assumption at a time, and only then search or ask Claude (with the exact text and your context), most problems take minutes rather than hours. Every output in this chapter was produced by really running the commands.

62.1How to read an error message

Here is one of the most common errors you'll ever see, from asking cat to show a file with a typo in its name:

Terminal
cat reprot.txt
Output
cat: reprot.txt: No such file or directory

Most terminal errors follow this pattern, separated by colons:

PartIn this exampleWhat it tells you
Who is speakingcatWhich program failed. If it says zsh or bash, the shell itself couldn't even start your command.
What it was working onreprot.txtThe file, command, URL or line involved. Read it letter by letter: here, the typo is right there.
What went wrongNo such file or directoryThe reason. These phrases are standard and searchable.

Two more clues are always available. The exit code (echo $? straight after the command, from Chapter 55) is 0 for success and anything else for failure. And errors are usually written to standard error, a separate output channel from normal results, which is why redirecting output with > doesn't hide them.

In everyday life

A warning light on a car dashboard. Panicking doesn't help, and nor does ignoring it. You read which light it is, look it up in the manual, and check the obvious thing first (is the petrol cap loose?) before calling the garage. When you do call, you say exactly which light came on and what you were doing, not "the car's broken".

Read errors in the right order

  • Read the whole message, slowly, once. Most people's eyes slide over red text. The answer is often in it, including suggested commands (Git and npm are very good at this).
  • For long outputs, find the first real error. One early failure often causes a cascade of later ones. Fix the first and the rest may disappear.
  • For a traceback (a list of function calls, section 62.4), start at the last line. That's the actual error; the lines above show how the program got there.
  • Separate warnings from errors. A WARN or deprecated line usually means "this still works, but change it eventually". It's rarely why your command failed.

62.2A method instead of guessing

Under pressure (a broken CI build, a demo in ten minutes), people change three things at once and can't tell which one helped. Debugging is the same skill as testing: form a hypothesis, check it, record the result.

1. ReadThe full message. What, where, which program?
2. ReproduceRun it again. Same error every time?
3. Check assumptionsRight folder? Right file name? Right version? Is the service running?
4. Change one thingThen run again
5. Confirm and noteWhat fixed it, and why

Step 3 solves most problems. The quick checks that cover most assumptions:

QuestionCommand
Where am I?pwd
What's actually here (including hidden files)?ls -la
Which copy of this program runs, if any?which python3 (or command -v python3)
Which version?python3 --version, node --version, git --version
Did the last command succeed?echo $?
Is something listening on this port?lsof -nP -iTCP:8080 -sTCP:LISTEN
Is a variable set?echo "$API_BASE_URL" (never echo a secret on a shared screen)
Real-world example

A colleague says "the Playwright tests don't run on my machine". Rather than reinstalling everything, you ask three questions: what exact message do you see, what does pwd say, and what does node --version say? The answer: they're one folder above the project, so npx playwright test can't find the config. One cd fixes it. Reading and checking took two minutes; reinstalling would have taken an hour and fixed nothing.

62.3The five errors you'll meet most

1. Command not found

Output (zsh on macOS; bash says "bash: pyhton3: command not found")
zsh: command not found: pyhton3

The speaker is the shell (zsh), not the program: the shell looked in every folder on your PATH and found nothing with that name. The exit code is 127. Causes, in order of likelihood:

  1. A typo, as here (pyhton3 instead of python3).
  2. Not installed. Install it (Chapter 58), for example brew install jq on macOS.
  3. Installed, but not on PATH. Common straight after installing a tool: open a new terminal window, or follow the installer's instruction to add a line to ~/.zshrc (Chapter 56). echo $PATH shows where the shell is looking.
  4. It's a project tool, not a global one. Tools installed with npm install live in the project's node_modules; run them with npx playwright, not playwright.

2. No such file or directory

Output
cat: reprot.txt: No such file or directory
cd: no such file or directory: nowhere

The path doesn't exist from where you are. Check spelling and capital letters (Linux treats Report.txt and report.txt as different files), run pwd and ls, and remember that a relative path like reports/run1.html is relative to the current folder (Chapter 53). Spaces in names need quotes: cat "test results.txt".

A confusing variant

Running a script can say "No such file or directory" even when the script plainly exists. Then it's usually the program named on the script's first line (the shebang, Chapter 57) that's missing, or the script was saved with Windows line endings. head -1 script.sh shows the first line.

3. Permission denied

Terminal and output
./run-tests.sh
zsh: permission denied: ./run-tests.sh

ls -l run-tests.sh
-rw-r--r--@ 1 asha  staff  31 Nov  9 14:48 run-tests.sh

The file exists, but you aren't allowed to do what you asked. Here the permissions -rw-r--r-- contain no x, so the file isn't executable (exit code 126). The fix is chmod +x run-tests.sh, after which it prints running tests. The other common form is writing where you have no rights:

Output
touch: /etc/qa.txt: Permission denied

Here the right fix is almost always to write somewhere you own (your home folder or the project), not to reach for sudo. Chapter 56 explains permissions and when sudo is appropriate.

Two "fixes" to refuse

sudo in front of npm install or pip install creates files owned by the administrator, which causes worse permission errors later. chmod 777 makes a file writable and runnable by everyone on the machine. Both make the message go away by removing a safety rail. Find out why permission was refused instead.

4. Port already in use

A port is a numbered door on your computer that a server listens on, like 3000 for a front-end dev server or 8080 for an API. Only one program can listen on a port at a time. Start a second server on a busy port and it fails. Python's version ends like this:

Last line of the output (python3 -m http.server 8765, run twice)
OSError: [Errno 48] Address already in use

Node.js reports the same thing as EADDRINUSE; on Linux the Python number is Errno 98. Usually the "other program" is your own server from earlier, still running in another tab or left behind by a crashed test run. Find it:

Terminal
lsof -nP -iTCP:8765 -sTCP:LISTEN
Output
COMMAND   PID       USER   FD   TYPE             DEVICE SIZE/OFF NODE NAME
Python  80051       asha    4u  IPv6 0x889326a7ace7adc6      0t0  TCP *:8765 (LISTEN)

lsof lists open files and network connections; -nP shows plain numbers instead of names (without it, the port may appear as a service name such as ultraseek-http), and the rest means "TCP port 8765, listening only". The PID column is the process ID. If it's yours and safe to stop, go to its terminal and press Ctrl+C, or run kill 80051. Otherwise just use a different port. On Windows, netstat -ano | findstr :8765 in PowerShell gives the PID.

5. Network errors

curl (Chapter 56) is the quickest way to test a connection, and its errors pinpoint which stage failed:

Output of three failing curl commands
curl: (6) Could not resolve host: no-such-host.invalid
curl: (7) Failed to connect to localhost port 8765 after 0 ms: Couldn't connect to server
curl: (28) Connection timed out after 2008 milliseconds
MessageStage that failedUsual causes
Could not resolve host (6)Turning the name into an address (DNS)Typo in the host name; no internet; an internal host that needs the company VPN
Failed to connect / Connection refused (7)Reaching the address, but nothing answered on that portThe server isn't running; wrong port; it listens on a different address
Timed out (28)No reply at allFirewall or proxy silently dropping traffic; VPN off; server overloaded
SSL certificate problemThe secure connectionCorporate proxy inspecting traffic, or a test server with a self-signed certificate. Ask IT; don't switch checks off globally

An HTTP status code is not a network error. If the server replies 404 (not found), 401 (not signed in), 403 (not allowed) or 500 (server crashed), the network worked fine and the server answered. Plain curl even exits with 0 in that case; add -f to make it fail on HTTP errors. To see the status, use curl -i or:

Terminal and output
curl -sS -o /dev/null -w '%{http_code}\n' https://example.com/no-such-page
404

For a tester this distinction matters in a bug report: "DNS fails for staging-api" goes to the network team; "staging-api returns 500 on POST /orders" goes to the developers.

62.4Reading tracebacks and tool errors

When a Python program crashes, it prints a traceback (other languages call it a stack trace): the chain of function calls that led to the error. Here is a small script that calculates a pass rate from a JSON results file, run on data where one result uses the field state instead of status:

Output (paths shortened)
Traceback (most recent call last):
  File "/Users/asha/qa/summarise.py", line 9, in <module>
    print(pass_rate("results.json"))
          ^^^^^^^^^^^^^^^^^^^^^^^^^
  File "/Users/asha/qa/summarise.py", line 6, in pass_rate
    passed = sum(1 for r in results if r["status"] == "PASS")
             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "/Users/asha/qa/summarise.py", line 6, in <genexpr>
    passed = sum(1 for r in results if r["status"] == "PASS")
                                       ~^^^^^^^^^^
KeyError: 'status'

Read it from the bottom up:

  1. Last line: the error. KeyError: 'status': some item has no status key.
  2. Just above: where. Line 6 of summarise.py, in pass_rate, and the ^^^ marks point at r["status"].
  3. Further up: how we got there. Line 9 called pass_rate. "Most recent call last" means the top is where the program started.

The bug may be in the data, not the code: a test reporter that writes state for some results. That's exactly the kind of finding worth putting in a bug report. In real projects, many traceback lines come from libraries you didn't write; look for the lowest line that points at your files. Chapter 59 covers Python errors in more depth.

Tool errors that tell you the fix

Modern tools often suggest the answer. Read before searching:

Output of npm run tset
npm error Missing script: "tset"
npm error
npm error Did you mean this?
npm error   npm set # Set a value in the npm configuration
npm error
npm error To see a list of scripts, run:
npm error   npm run
npm error A complete log of this run can be found in: /Users/asha/.npm/_logs/2026-11-09T09_18_58_908Z-debug-0.log

Its guess (npm set) is wrong, but its second suggestion is right: npm run lists the real scripts, and you'll see test. Note the log path on the last line too: tools often save a full log with more detail than the screen shows.

62.5Finding answers yourself: --help and man

Before searching the web, ask the tool. Almost every command has built-in help:

FormExampleGives
--helpcurl --help, npx playwright test --helpA summary of options, printed straight away
-hgit commit -hA short usage summary (Git's long help is git help commit)
manman lsThe full manual page (man page) for system commands
Output of git commit -h (first lines)
usage: git commit [-a | --interactive | --patch] [-s] [-v] [-u[<mode>]] [--amend]
                  [--dry-run] [(-c | -C | --squash) <commit> | --fixup [(amend|reword):]<commit>]
                  [-F <file> | -m <msg>] [--reset-author] [--allow-empty]

How to read a usage line: square brackets [ ] mean optional; | means "one or the other"; words in angle brackets <msg> are placeholders you replace; ... means "you can repeat this".

Inside man, you are in a pager: arrow keys or space to move, / then a word to search (n for the next match), and q to quit. Help is too long for the screen? Pipe it: curl --help all | less or curl --help all | grep -i proxy. Windows PowerShell commands use Get-Help instead of man.

Help matches your version

Built-in help describes the version you actually have installed. A blog post may describe a newer or older one, or the Linux version of a tool when you're on a Mac. When they disagree, believe --help.

62.6Searching for errors safely

Searching the exact message is often the fastest route, because someone has almost certainly hit it before. Do it well:

  • Search the stable part. Copy the error text but remove things unique to you: file paths, user names, IDs, timestamps, port numbers. "OSError: [Errno 48] Address already in use" finds answers; your full path won't.
  • Add the tool and platform. "npm error Missing script macOS" is better than the message alone.
  • Prefer primary sources. Official documentation, the tool's GitHub issues and its changelog beat a random blog post. Check the date: an answer from years ago may describe an old version.
Never paste these into a search box, forum or chatbot

API keys, tokens and passwords (they often appear in logs and in env output); internal host names and URLs; customer or personal data from test environments; proprietary code your company hasn't approved for sharing. Read the error before pasting it, and replace anything sensitive with a placeholder such as <TOKEN>. If a secret has been pasted somewhere public, revoke it (Chapter 98). Check your company's policy on which AI tools may see work data (Chapter 132).

Distrust "fixes" that remove safety

Be suspicious of any answer that tells you to run sudo, chmod 777, rm -rf, git push --force, to turn off SSL verification, or to pipe a downloaded script straight into the shell (curl … | sh) from a site you don't recognise. Some of these are sometimes right, but understand what each does before running it, and never as a guess.

62.7Asking Claude for help effectively

Claude is excellent at explaining error messages, but it only knows what you tell it. "It doesn't work" gets a guess. A good request gets a diagnosis. Include:

IncludeWhy
The exact command you ranOne character can matter
The full error text, copied, not retyped or summarisedRetyping introduces typos and drops the useful lines
What you expected to happenSo Claude knows what "working" means
Your setup: operating system, tool versions, where you areMany fixes differ on macOS, Linux and Windows
What you already tried, and what happenedAvoids answers you've ruled out
What you want: explanation, fix, or bothAnd ask it to explain the cause, so you learn

Weak request

"npm test is broken, help"

Strong request

"On macOS 15, Node v25, in my Playwright project folder, I ran npm run tset and got npm error Missing script: "tset" (full output below). I expected the test suite to run. npm run lists test and test:e2e. Explain what the error means and which command I should use."

In the Claude apps you paste all this into the chat. In Claude Code it's easier, because Claude can run the checks itself: ask it to run the failing command and read the output, approving each command as it asks (Chapter 65). You can also type ! followed by a command, such as ! npm test, to run it in shell mode: the output goes into the conversation and Claude responds to it. And you can pipe a saved log in from the terminal: cat build-error.log | claude -p "Explain the first real error in this log" (Chapter 75).

Prompt for Claude Code
Run npx playwright test tests/checkout.spec.ts and read the full output.

and propose a fix. Don't change any files until I've agreed.
Check before you run

Claude can be confidently wrong, especially about flags that vary between versions. Before running a command it suggests, read it. If it includes any of the risky patterns from 62.6, ask why. Verify a suggested flag with --help. And after a fix, confirm it worked by re-running the original command, not by taking anyone's word for it.

Opinion · many engineering teams

A common view among senior engineers is that people who read an error themselves for a minute before asking an AI learn faster and ask better questions. A reasonable habit: read the message, run one or two checks from 62.2, then ask Claude, including what your checks showed.

Under the hood: where errors and exit codes come from

Many low-level messages ("No such file or directory", "Permission denied", "Address already in use", "Connection refused") are standard descriptions of operating-system error numbers, often named ENOENT, EACCES, EADDRINUSE and ECONNREFUSED. That's why so many different programs use exactly the same wording, and why Python shows a number such as [Errno 2]. The numbers themselves differ between macOS and Linux (48 versus 98 for "address in use"), but the names and messages match.

Exit codes have some conventions. 0 is success, 1 is a general failure, the shell uses 126 for "found but can't run" and 127 for "command not found", and a process stopped by a signal reports 128 plus the signal number (130 after Ctrl+C). Tools define their own as well: curl's numbers in brackets, such as 6, 7 and 28, are documented in man curl, and Git uses 128 for fatal errors. CI systems only look at the exit code to decide pass or fail, which is why a script that prints "ERROR" but exits with 0 shows as green.

Common misunderstandings
"The error message is gibberish; just search it."
Most messages say exactly what's wrong and where. Read it first; search the stable part second.
"The last line of a long log is the problem."
For tracebacks, yes. For build and test logs, the first real error usually caused the rest.
"Permission denied means I need sudo."
Usually it means a missing execute bit or writing in the wrong place. sudo is rarely the right fix.
"A 404 or 500 is a network problem."
The network worked: the server replied. Network failures are "could not resolve", "connection refused" and "timed out".
"Claude's fix worked because the error went away."
Check it fixed the cause, not the symptom: re-run the original command and read what changed.

62.8Review

Key takeaways
  • Errors say who failed, what with, and why. Read the whole message slowly; tools often include the fix.
  • Use a method: read, reproduce, check assumptions (pwd, ls, which, versions), change one thing, confirm.
  • Command not found: spelling, install, PATH, or use npx. No such file: wrong folder or name. Permission denied: chmod +x or write somewhere you own.
  • Port in use: find the owner with lsof -nP -iTCP:<port> -sTCP:LISTEN. Network: resolve (DNS), connect, timeout; HTTP status codes are server replies, not network failures.
  • Read tracebacks bottom-up; read build logs from the first error.
  • --help, -h and man describe the version you actually have.
  • Search the stable part of a message, never paste secrets, and distrust fixes that remove safety. Give Claude the exact command, full error, expected result, setup and what you tried.
Check yourself

You see zsh: command not found: playwright in a project where Playwright is installed with npm. What's the most likely fix?

Project tools live in node_modules, not on your PATH; npx finds and runs them.

A Python traceback is 40 lines long. Where do you look first?

The last line is the error itself; the frames above show the path the program took to get there.

curl prints curl: (6) Could not resolve host: staging-api.internal. What failed?

Error 6 happens before any connection is attempted. "Connection refused" (7) would mean the address was found but nothing answered.

Your dev server fails with EADDRINUSE on port 3000. What should you do first?

Usually an earlier copy of your own server is still running. lsof shows its PID; stop it or use another port.

Which is the best thing to send when asking Claude about an error?

Claude only knows what you tell it. Complete, exact context gets a diagnosis instead of a guess.

Assignment

Start an "error diary" for two weeks. Each time you meet an error at work (terminal, CI, test run), write down the exact message (with sensitive parts replaced), what it meant, how you found out, and what fixed it. At the end, group them: which kinds came up most? Turn your three most common into a one-page "first checks" guide for your team, in the style of the quick-reference table in 62.3, and share it.
