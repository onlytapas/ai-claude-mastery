Every Claude API call costs money and uses up a share of your organisation's limits, and both are measured in tokens. Four levers keep them under control: prompt caching (pay about a twentieth of the price for input you've already sent recently), batching (half price if you can wait for results), model choice, and sending less. When you do hit a limit or a temporary fault, the API tells you with a status code and headers. Good code retries the right errors, waits sensibly between tries, and never retries the ones that can't succeed. Measure everything from the usage field rather than guessing.

90.1Where the money and the limits go

Chapter 86 showed that you pay for input tokens (everything you send) and output tokens (everything Claude writes, including its thinking). A production AI feature usually sends the same large block of text again and again: a long system prompt, tool definitions, a test-strategy document, a style guide. Then it adds a small new part each time: one user story, one failing test log.

That pattern is where most savings come from. If 20,000 tokens of every request are identical and only 500 are new, you are paying full price to have the model re-read the same 20,000 tokens on every call. Prompt caching fixes exactly that.

In everyday life

90.2Prompt caching: how it works

Prompt caching stores the processed form of the beginning of your prompt (the prefix) for a short time. If the next request starts with exactly the same prefix, Claude reads it from the cache instead of processing it again. That is cheaper and faster. Verified 9 Nov 2026

Three rules explain almost everything:

  1. Order matters. The prompt is cached in the order tools → system → messages. Put stable things first and changing things last.
  2. The prefix must be identical. A cache hit needs the content up to the cache point to be 100% the same. One changed character, such as a timestamp in the system prompt, means a miss.
  3. It expires. The default lifetime is 5 minutes, refreshed free every time the cache is used. A 1-hour lifetime is available at a higher write price.

Turning it on

The simplest way is automatic caching: add one top-level cache_control field. The API places the cache point on the last cacheable block and moves it forward as a conversation grows.

Automatic caching (curl)
curl https://api.anthropic.com/v1/messages \
  -H "content-type: application/json" \
  -H "Authorization: Bearer $ANTHROPIC_API_KEY" \
  -H "anthropic-version: 2026-10-21" \
  -d '{
    "model": "claude-opus-5-5",
    "max_tokens": 2000,
    "cache_control": {"type": "ephemeral"},
    "system": "You are a senior QA engineer. <team test strategy, 20,000 tokens>",
    "messages": [
      {"role": "user", "content": "Write test cases for story QA-1432: password reset by SMS."}
    ]
  }'

For finer control, put cache_control on individual content blocks. These are called cache breakpoints, and a request may have at most four (automatic caching uses one of the four).

Python: an explicit breakpoint after a long system document, with a 1-hour lifetime
import anthropic

client = anthropic.Anthropic()

        {"type": "text", "text": "You are a senior QA engineer. Use the team's test strategy below."},
        {"type": "text", "text": strategy,
         "cache_control": {"type": "ephemeral", "ttl": "1h"}},     # cache up to here

Under the hood: what breaks a cache

Because the prefix is cached in layers (tools, then system, then messages), a change invalidates its own layer and everything after it:

  • Changing tool definitions (names, descriptions, parameters) invalidates tools, system and messages: everything.
  • Changing the system prompt, or switching web search or citations on or off, invalidates system and messages.
  • Changing tool_choice, adding or removing images, the thinking configuration or the effort setting invalidates the messages layer (and on some models more).
  • Switching between fast mode and standard speed invalidates system and messages.

The API also looks back a limited distance for an earlier cache entry: at most 20 positions (content blocks) per breakpoint. In a very long conversation that only has a breakpoint at the end, an entry further back than that won't be found, which is one reason to add breakpoints at stable points.

The cache stores the model's internal processed state for those tokens (related to the KV cache), not a saved answer. Caching never changes what Claude says; it only changes cost and speed.

Real-world example: the timestamp that cost a fortune

A team's triage bot started its system prompt with Current time: 2026-11-09 14:03:27. Every request had a different first line, so nothing after it was ever cached. Moving the time into the user message, after the stable instructions, raised their cache hit rate from almost zero to most of their input. A tester can catch this kind of thing: check cache_read_input_tokens on the second of two identical calls. If it's 0, something in the prefix is changing.

The classic misreading

input_tokens is not your total input once caching is on. Total input = cache_read_input_tokens + cache_creation_input_tokens + input_tokens. Dashboards that only add up input_tokens will show a suspiciously tiny number.

When does caching pay off?

Anthropic's pricing page puts it simply: with a 5-minute cache (write at 1.25×), caching pays off after one cache read; with a 1-hour cache (write at 2×), after two. On Opus 5.5 and Sonnet 5.5, where reads are 0.05×, the gap is even bigger.

Worked example (illustrative): 1,000 calls/month, Opus 5.5, 20,000-token shared prefix, 500 new input tokens, 1,500 output tokens
Without caching:   1,000 × (20,500 × $4 + 1,500 × $20) / 1M        = $112.00
With caching, 90% of calls hit the cache:
   100 misses × (500 × $4 + 20,000 × $5   + 1,500 × $20) / 1M     =  $13.20
   900 hits   × (500 × $4 + 20,000 × $0.20 + 1,500 × $20) / 1M    =  $32.40
                                                                    ───────
                                                                     $45.60  (about 59% less)

Notice that output is now the biggest cost. After caching, the next saving usually comes from asking for shorter answers or a lower effort level.

Discounts stack

Caching multipliers combine with the Batch API discount and with data-residency pricing. For example, using inference_geo: "us" (US-only processing) applies a 1.1× multiplier to all token prices on Claude 4.6 and later models. Fast mode on Opus 5.5 costs $8 input / $40 output per million tokens, and caching multipliers apply on top of that. Fast mode can't be used with the Batch API.

Python: classify 300 overnight test failures in one batch
import json, time
import anthropic

client = anthropic.Anthropic()
failures = [json.loads(line) for line in open("failures.jsonl", encoding="utf-8")]
# each line: {"test_id": "checkout_spec_14", "log": "..."}

batch = client.messages.batches.create(requests=[
    {"custom_id": f["test_id"],
     "params": {"model": "claude-haiku-5-5", "max_tokens": 300,
                "messages": [{"role": "user", "content":
                    "Classify this test failure as PRODUCT_BUG, TEST_BUG, ENVIRONMENT or FLAKY, "
                    "then give one sentence of reasoning.\n\n" + f["log"]}]}}
    for f in failures])
print("Submitted", batch.id)

while client.messages.batches.retrieve(batch.id).processing_status != "ended":
    time.sleep(60)                                     # poll once a minute

for result in client.messages.batches.results(batch.id):
    if result.result.type == "succeeded":
        text = "".join(b.text for b in result.result.message.content if b.type == "text")
        print(result.custom_id, "→", text)
    else:
        print(result.custom_id, "→", result.result.type)  # errored / canceled / expired

Good fits for batching

  • Nightly classification of test failures
  • Generating draft test cases for a whole backlog
  • Running an eval set of hundreds of prompts (Chapter 125)
  • Back-filling summaries for old bug reports

Poor fits

  • Anything a person is waiting for on screen
  • Agent loops where each step depends on the previous answer
  • Fast mode (not available with batches)
Batches and caching together

Batch requests that share a long prefix can use prompt caching too, and the discounts combine. Because a batch can take longer than 5 minutes, Anthropic suggests the 1-hour cache lifetime for shared context in batches. Results come back in any order, so always match them up by custom_id, never by position.

90.5Rate limits and usage tiers

A rate limit caps how much your organisation can send in a period of time. On the Messages API, each model has three separate limits. Exceed any one and you get a 429. Verified 9 Nov 2026

Under the hood: the token bucket

Anthropic uses the token bucket algorithm. Picture a bucket that holds your per-minute allowance and refills continuously, not all at once at the top of each minute. Each request takes some out. You can burst until the bucket is empty, then you must wait for it to refill.

Two practical consequences: a limit of 60 RPM may be enforced as about 1 request per second, so a burst of 60 requests in the same second can fail even though you're "under 60 a minute"; and sudden large jumps in traffic can trigger separate acceleration limits, so ramp traffic up gradually.

Caching raises your effective limits. Anthropic's own example: with a 2,000,000 ITPM limit and an 80% cache hit rate, you can process about 10,000,000 total input tokens a minute, because the 8 million cached tokens don't count.

Protect one team from another

An organisation can set lower rate and spend limits per workspace. Give your experimental QA scripts their own workspace with a modest limit, so a runaway loop can't starve the production chatbot. (You can't set spend limits on the default workspace.)

90.6Errors and retries done properly

Chapter 86 listed the error codes. The production question is: which ones should my code retry? A retry only makes sense if trying again could succeed.

ResponseRetry?Why
429 rate_limit_error with retry-afterYes, after the stated waitThe bucket will refill
429 with error.details.error_code = enforced_spend_limit_reachedNoMonthly tier spend cap reached. It has no retry-after and keeps failing until the next month (00:00 UTC on the 1st) or a tier increase.
500 api_error, 529 overloaded_error, connection errorsYes, with backoffTemporary trouble on Anthropic's side
504 or other timeout_errorMaybe; better to streamLong non-streaming requests are fragile. Use streaming (Chapter 87) or batches for anything long.
400 invalid_request_errorNoThe request is wrong (or a spend limit you set was reached). Fix it.
401, 402, 403, 404, 413NoKey, billing, permission, path or size problems won't fix themselves

The official SDKs already retry connection errors, 408, 409, 429 and 5xx responses twice by default, with exponential backoff, honouring retry-after. You can change that with max_retries. For many scripts, that's enough.

Python: configure SDK retries and catch typed errors
import anthropic

client = anthropic.Anthropic(max_retries=4, timeout=120.0)

try:
    message = client.messages.create(
        model="claude-opus-5-5", max_tokens=1000,
        messages=[{"role": "user", "content": "Summarise this test run: ..."}])
except anthropic.RateLimitError as e:          # 429 after all retries
    print("Still rate limited. Request ID:", e.response.headers.get("request-id"))
    raise
except anthropic.BadRequestError as e:         # 400: fix the request, don't retry
    print("Bad request:", e.message)
    raise
except anthropic.APIStatusError as e:          # any other non-2xx status
    print("API error", e.status_code)
    raise

Writing your own backoff (and why jitter matters)

Exponential backoff doubles the wait after each failure: about 1 second, then 2, 4, 8. Jitter randomises the wait. Without it, a hundred CI jobs that all hit a 529 at 02:00:00 all retry at 02:00:01, then 02:00:03, and keep colliding. With "full jitter" each one waits a random time between zero and the backoff ceiling, so they spread out.

Callsend the request
Error?check status and type
Retryable?429 (not spend cap), 5xx, 529, connection
Waitretry-after if given, otherwise random(0, base × 2n)
Give upafter N attempts; log the request ID

The script below is the logic on its own, with a fake API, so you can test it with no key. It's in the lab.

retry_sim.py (standard library only; tested offline)
"""retry_sim.py - retry with exponential backoff and full jitter, tested offline.
Runs with the Python standard library only. No API key needed."""
import random

RETRYABLE = {408, 409, 429, 500, 502, 503, 504, 529}

class APIError(Exception):
    def __init__(self, status, retry_after=None, spend_cap=False):
        super().__init__(f"HTTP {status}")
        self.status, self.retry_after, self.spend_cap = status, retry_after, spend_cap

def backoff_delay(attempt, retry_after=None, base=1.0, cap=60.0):
    """Seconds to wait before retry number `attempt` (1, 2, 3...)."""
    if retry_after is not None:          # the server told us: obey it
        return float(retry_after)
    return random.uniform(0, min(cap, base * 2 ** (attempt - 1)))   # full jitter

def call_with_retries(fn, max_attempts=5, sleep=lambda s: None, log=print):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except APIError as e:
            if e.spend_cap or e.status not in RETRYABLE or attempt == max_attempts:
                log(f"  attempt {attempt}: HTTP {e.status} -> giving up")
                raise
            wait = backoff_delay(attempt, e.retry_after)
            log(f"  attempt {attempt}: HTTP {e.status} -> waiting {wait:.1f}s")
            sleep(wait)

def fake_api(script):
    """Returns a function that fails according to `script`, then succeeds."""
    events = iter(script)
    def fn():
        ev = next(events, None)
        if ev is None:
            return "200 OK: test cases generated"
        raise ev
    return fn

if __name__ == "__main__":
    random.seed(7)
    print("Case 1: two overloads, then success")
    print(" ", call_with_retries(fake_api([APIError(529), APIError(529)])))
    print("Case 2: rate limited, server sends retry-after: 12")
    print(" ", call_with_retries(fake_api([APIError(429, retry_after=12)])))
    print("Case 3: bad request (400) is never retried")
    try:
        call_with_retries(fake_api([APIError(400)]))
    except APIError as e:
        print("  raised", e)
    print("Case 4: monthly spend cap (429, no retry-after) is not retried")
    try:
        call_with_retries(fake_api([APIError(429, spend_cap=True)]))
    except APIError as e:
        print("  raised", e)

In real code, pass sleep=time.sleep and map the SDK's exceptions onto the same decision (the SDK error has status_code and the response headers). The sleep parameter is a QA habit worth copying: injecting the clock makes retry logic testable in milliseconds.

Under the hood: retries, duplicates and streaming errors
  • Duplicates. If a connection drops after Claude finished but before you got the reply, a retry runs (and bills) the request again. For a pure "generate text" call that's harmless. If your code then acts on the result (files a Jira bug, posts to Slack), make that action idempotent: check whether the bug already exists before creating it.
  • Errors after a 200. When streaming over server-sent events, an error can arrive mid-stream after the HTTP status was already 200. Your status-code handling won't see it; handle the stream's error event (Chapter 87).
  • Long requests. Anthropic recommends streaming or batches for requests that may run over 10 minutes. The SDK refuses non-streaming requests it expects to exceed a 10-minute timeout, and some networks silently drop idle connections.
  • Retry budgets. In a big system, cap the total share of traffic that may be retries, so an outage doesn't turn into a self-inflicted flood.

Step 1: count tokens before you send

The token counting endpoint, POST /v1/messages/count_tokens, takes the same body as a Messages request (without max_tokens) and returns {"input_tokens": N}. It is free, has its own rate limit, and gives an estimate (the real count can differ slightly). It doesn't use caching. Step 2: a cost calculator

This script compares a month's bill with and without caching, and with batching. It uses only the standard library. Prices are written into the script, so re-check them against the pricing page before you rely on the numbers.

cost_calc.py (tested with Python 3.11)
"""cost_calc.py - estimate Claude API cost from token counts.
Prices: USD per million tokens, Claude API, verified 9 Nov 2026
(platform.claude.com/docs/en/about-claude/pricing). Re-check before use."""
import argparse

PRICES = {
    # model: (base input, 5m cache write, 1h cache write, cache read, output)
    "claude-fable-5-1":  (10.00, 12.50, 20.00, 0.25, 50.00),
    "claude-opus-5-5":   (4.00,  5.00,  8.00,  0.20, 20.00),
    "claude-sonnet-5-5": (2.00,  2.50,  4.00,  0.10, 10.00),
    "claude-haiku-5-5":  (0.10,  0.125, 0.20,  0.01, 0.50),   # prompts up to 100K tokens
}
HAIKU_LONG = (0.50, 0.625, 1.00, 0.05, 2.50)                  # Haiku 5.5 prompts over 100K

def call_cost(model, uncached_in, cache_write, cache_read, out,
              ttl="5m", batch=False):
    p = PRICES[model]
    prompt_len = uncached_in + cache_write + cache_read
    if model == "claude-haiku-5-5" and prompt_len > 100_000:
        p = HAIKU_LONG
    base, w5, w1, read, outp = p
    write = w5 if ttl == "5m" else w1
    dollars = (uncached_in * base + cache_write * write
               + cache_read * read + out * outp) / 1_000_000
    return dollars * (0.5 if batch else 1.0)

def main():
    ap = argparse.ArgumentParser(description="Estimate a monthly Claude API bill")
    ap.add_argument("--model", default="claude-opus-5-5", choices=PRICES)
    ap.add_argument("--calls", type=int, default=1000, help="calls per month")
    ap.add_argument("--prefix", type=int, default=20000, help="shared prompt prefix tokens (cacheable)")
    ap.add_argument("--unique", type=int, default=500, help="unique input tokens per call")
    ap.add_argument("--out", type=int, default=1500, help="output tokens per call (incl. thinking)")
    ap.add_argument("--hit-rate", type=float, default=0.9, help="share of calls that hit the cache")
    ap.add_argument("--batch", action="store_true", help="use the Message Batches API (50%% off)")
    a = ap.parse_args()

    no_cache = a.calls * call_cost(a.model, a.prefix + a.unique, 0, 0, a.out, batch=a.batch)
    hits = round(a.calls * a.hit_rate)
    misses = a.calls - hits
    cached = (misses * call_cost(a.model, a.unique, a.prefix, 0, a.out, batch=a.batch)
              + hits * call_cost(a.model, a.unique, 0, a.prefix, a.out, batch=a.batch))
    print(f"Model: {a.model}   calls: {a.calls:,}   batch: {a.batch}")
    print(f"Without caching : ${no_cache:,.2f}")
    print(f"With caching    : ${cached:,.2f}   (hit rate {a.hit_rate:.0%})")
    print(f"Saving          : ${no_cache - cached:,.2f} ({1 - cached / no_cache:.0%})")

if __name__ == "__main__":
    main()

Step 3: measure real calls

Estimates are a start; real usage numbers are the truth. Add this function to cost_calc.py and call it with message.usage.model_dump() after every request, then log the result with the feature name and request ID.

Cost of one real call, from its usage object
def cost_from_usage(model, usage, batch=False):
    """usage: the 'usage' object from a Messages API response, as a dict."""
    base, w5, w1, read, outp = PRICES[model]
    cc = usage.get("cache_creation") or {}
    w5_tok = cc.get("ephemeral_5m_input_tokens", usage.get("cache_creation_input_tokens", 0))
    w1_tok = cc.get("ephemeral_1h_input_tokens", 0)
    dollars = (usage.get("input_tokens", 0) * base + w5_tok * w5 + w1_tok * w1
               + usage.get("cache_read_input_tokens", 0) * read
               + usage.get("output_tokens", 0) * outp) / 1_000_000
    return dollars * (0.5 if batch else 1.0)

# the cached call from 90.3: 50 uncached, 20,000 read from cache, 1,200 out
print(f"${cost_from_usage('claude-opus-5-5', {'input_tokens': 50, 'cache_read_input_tokens': 20000, 'output_tokens': 1200}):.4f}")
# → $0.0282

(For simplicity this ignores the Haiku long-prompt price and other multipliers. Extend it if you use them.)

Step 4: monitor and cap

  • The Console's Usage page shows token and request charts, including your cache rate and how close you run to your input- and output-token limits.
  • Set a spend limit under Settings → Billing below your tier's cap, and per-workspace limits for risky tools. When your limit is reached, requests return 400 with a message starting "You have reached your specified API usage limits".
  • In your own logs, record per call: feature, model, all four token counts, cost, latency, request ID. That turns "the AI bill doubled" into "the release-notes feature started sending the full changelog on every call on 3 November". Chapter 95 builds this into proper monitoring.
Opinion · common engineering practice

Many teams treat a sudden fall in cache hit rate as a defect, not a cost curiosity, and alert on it. It almost always means someone changed a prompt prefix (a date, a reordered tool list, a per-user detail in the system prompt). It's cheap to monitor and catches regressions that functional tests miss.

Common misunderstandings
"Caching stores Claude's answers, so I'll get the same reply."
It stores the processed prompt prefix only. Replies are generated fresh every time.
"input_tokens in usage is my total input."
With caching, it's only the part after the last cache point. Add the cache read and write fields to get the total.
"A 429 always means slow down and retry."
A 429 caused by the monthly tier spend cap has no retry-after and won't succeed until access resumes. Check error.details.error_code.
"Setting a big max_tokens uses up my output rate limit."
OTPM counts tokens actually produced, not max_tokens.
"Retrying more is always safer."
Retrying 400s wastes time, retrying without jitter makes outages worse, and retrying actions with side effects can create duplicates.
"Batches are only for huge jobs."
Any job nobody is waiting for qualifies, even 50 requests. The discount is the same.

Key takeaways
  • Prompt caching reuses an identical prompt prefix (tools → system → messages). Turn it on with a top-level cache_control or up to four block-level breakpoints; minimum 512 tokens on current models; 5-minute default lifetime, 1-hour option.
  • Cache writes cost 1.25× (5 min) or 2× (1 hour); reads cost 0.025×–0.1× depending on model. Cache reads don't count toward ITPM.
  • With caching, total input = cache_read_input_tokens + cache_creation_input_tokens + input_tokens.
  • The Message Batches API is 50% off, up to 100,000 requests per batch, results within 24 hours; match results by custom_id.
  • Rate limits are RPM, ITPM and OTPM per model, set by usage tier (Start, Build, Scale, Custom), enforced with a token bucket; watch the anthropic-ratelimit-* and retry-after headers.
  • Retry 429 (except spend cap), 5xx, 529 and connection errors with backoff and jitter; never retry 400/401/403/404; the SDK retries twice by default.
  • Estimate with the free token-counting endpoint, measure with usage, monitor in the Console, and cap with spend limits.
Check yourself

Your second identical request shows cache_read_input_tokens: 0. What is the most likely cause?

A hit needs the prefix up to the cache point to be identical. A changing value near the start invalidates everything after it. (Other causes: the prefix is under 512 tokens, or more than 5 minutes passed.)

A response's usage shows input_tokens: 40, cache_creation_input_tokens: 0, cache_read_input_tokens: 30000. How many input tokens did the request contain in total?

Total input is the sum of the three fields. input_tokens alone counts only what came after the last cache point.

You get a 429 whose body includes "error_code": "enforced_spend_limit_reached" and no retry-after header. What should your code do?

The monthly tier spend cap won't clear on its own until 00:00 UTC on the first of next month, unless the tier is raised. Retrying just fails again.

Which job is the best fit for the Message Batches API?

Batches suit independent requests nobody is waiting on. You get 50% off and results within 24 hours (usually under one).

Why add random jitter to retry waits?

Synchronised retries create waves of load. Randomised waits spread them out.

Teach it

"You pay Claude per token, and most AI features resend the same big chunk of text every call.
