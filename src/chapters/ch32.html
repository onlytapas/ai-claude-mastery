A trained model is, at heart, a very large file of numbers called weights. A proprietary model keeps that file private: you can only use it through the company's app or API. An open-weight model lets you download the file and run it yourself, under the terms of a licence. "Open weights" is not the same as "open source": true open-source AI also shares the code and enough information about the training data to rebuild it. Neither approach is simply better. Proprietary models usually lead on capability and are easier to start with; open-weight models give control, privacy and independence, at the cost of running them yourself.

32.1Three words that get mixed up

When people argue about "open" AI they often mean different things. Start with what a model actually is: a program (the architecture and code that runs it) plus a huge set of learned numbers, the weights. The weights are where the knowledge lives. Whoever holds them can run the model.

TermWhat you getExamples (Nov 2026)
Proprietary (closed)Access through an app or API only. The weights never leave the company (or its cloud partners).Claude, GPT-6 Astra, Gemini 4 Argon, Grok 4.7, Muse Spark

In everyday life

Think of a famous restaurant dish. Proprietary is eating at the restaurant: you get the meal, but never see the kitchen. Open weights is buying the dish frozen: you can heat it at home, serve it to guests, maybe add your own sauce, but you don't know the recipe or where the ingredients came from. Open source is getting the full recipe, the ingredient list with suppliers, and the cooking method, so a skilled cook could make it from scratch and change it.

32.2Open weights is not open source

In software, "open source" has had a precise meaning for decades, maintained by the Open Source Initiative (OSI). For AI, OSI published the Open Source AI Definition 1.0 on 28 October 2024. It says an open-source AI system must grant four freedoms:

Use and study

Use the system for any purpose without asking permission. Study how it works and inspect its components.

Modify and share

Modify it for any purpose, including changing its output. Share it, changed or not, for any purpose.

To make those freedoms real, the definition requires three things to be available:

Data informationEnough detail about the training data (sources, selection, processing) that a skilled person could build a substantially equivalent system
CodeThe complete code to process data, train, validate and run the model, under OSI-approved licences
ParametersThe weights (and things like key training checkpoints) under OSI-approved terms

Most "open" models today publish only the last box. That is valuable, but it's open weights. You can run and adapt them; you can't fully inspect or reproduce how they were made.

A live debate

The definition was contested from the start. Some critics argued that "data information" is too weak and that only fully released training data counts; others argued it is too demanding for models trained on data that can't legally be redistributed. OSI itself describes 1.0 as a starting point. When a vendor calls its model "open source", check which of the three boxes it actually provides.

Real-world example

A test manager reads that a vendor's assistant is "built on open-source AI" and assumes the company could audit its training data for licensing problems. In fact the base model is open-weight only: the weights are downloadable, but there is no information about what data it learned from. The audit question has to go to the model's maker, and the answer may be "not disclosed". Knowing the difference stops a wrong assumption reaching a risk register.

32.3Reading a model licence

Downloading weights doesn't mean you can do anything with them. The licence sets the rules. Three broad kinds are common:

Licence typeWhat it generally allowsExamples
Permissive (Apache 2.0, MIT)Commercial use, modification and redistribution with few conditions (mainly keeping copyright and licence notices)DeepSeek R1, V3.1, V3.2 and V4 (MIT); gpt-oss-120b and gpt-oss-20b (Apache 2.0); Qwen3.8-27B and Muse Glimmer (Apache 2.0); Cohere Command A+ (Apache 2.0)
Custom "community" licenceCommercial use allowed, but with extra conditions written by the vendorLlama 3.1 Community License; Mistral Ecosystem Open-Weight License (Large 4)
Custom with commercial stringsUse allowed, with revenue-sharing or size thresholdsMoonshot's Kimi K3 (reported revenue-share licence)

Custom licences need careful reading. The Llama 3.1 Community License is a good example of the kinds of clauses to look for:

  • A size threshold. If your products had "greater than 700 million monthly active users" in the month before the release date, "you must request a license from Meta", which Meta may grant at its discretion.
  • An acceptable use policy. Your use must "adhere to the Acceptable Use Policy", a separate document listing forbidden uses.
  • Attribution. If you distribute the model or a product containing it, you must "prominently display 'Built with Llama'". If you use its outputs to build another distributed model, that model's name must begin with "Llama".
Not legal advice

This chapter teaches you what to look for, not how to interpret a licence for your company. Before using an open-weight model in a product, involve your legal or procurement team. Licences also change between versions: the terms for one release may not match the next.

Why companies release weights at all

Releasing weights gives away something that cost a lot to make. Companies do it for several business reasons (described here as observed strategies, not endorsements):

  • Ecosystem. Developers who build on your models, tools and formats become your community. Alibaba's Qwen strategy pairs many open-weight models with proprietary "Max" cloud models.
  • Selling something else. NVIDIA releases open Nemotron models while selling the GPUs they run on. Mistral pairs open weights with paid enterprise and sovereign deployments.
  • Talent and reputation. Strong open releases attract researchers and attention. DeepSeek-R1 (January 2025) showed a research-first lab could compete at the frontier with open weights.
  • Strategy can change. Meta built its reputation on open Llama weights (2023–2025), then in April 2026 launched Muse Spark as a proprietary model while releasing a smaller open-weight Muse Glimmer in August 2026. Meta said it "hope[s] to open-source future versions". Don't assume a vendor's openness is permanent.

32.4Running a model yourself

The practical benefit of open weights is that you can self-host: run the model on your own laptop, server or cloud account. Tools such as Ollama and llama.cpp make this approachable; Chapter 137 walks through it step by step. Here we cover what it takes.

The main constraint is memory. The weights must fit in the memory of your GPU (or, more slowly, your computer's main memory). A rough rule: each parameter takes 2 bytes at 16-bit precision. So one billion parameters needs about 2 GB just to hold the weights. Quantisation stores each number with fewer bits (8-bit or 4-bit), shrinking the file by two or four times, usually with a small loss of quality.

mem.py · rough memory needed for the weights alone
# mem.py - rough memory needed just to hold a model's weights
# Rule of thumb only: real use needs extra room for the context (KV cache) and the runtime.
BYTES_PER_PARAM = {"16-bit": 2.0, "8-bit": 1.0, "4-bit": 0.5}

models = {                       # parameters, in billions (total, not active)
    "small 8B model":     8,
    "Qwen3.8-27B":        27,
    "Muse Glimmer 30B":   30,
    "~1T MoE model":      1000,
}

print(f"{'model':<20}" + "".join(f"{p:>10}" for p in BYTES_PER_PARAM))
for name, billions in models.items():
    row = ""
    for precision, size in BYTES_PER_PARAM.items():
        gb = billions * size          # 1 billion params x 1 byte = about 1 GB
        row += f"{gb:>8.0f}GB"
    print(f"{name:<20}{row}")
Expected output
model                   16-bit     8-bit     4-bit
small 8B model            16GB       8GB       4GB
Qwen3.8-27B               54GB      27GB      14GB
Muse Glimmer 30B          60GB      30GB      15GB
~1T MoE model           2000GB    1000GB     500GB

The lesson: models of a few billion to a few tens of billions of parameters can run on a well-equipped workstation once quantised. The largest open-weight models (DeepSeek-V4-Pro is reported at 1.6 trillion total parameters; Mistral Large 4 at about 1 trillion) need data-centre hardware, even though their active parameters per token are far fewer, because all the experts still have to sit in memory.

In everyday life

Quantisation is like saving a photo as a smaller JPEG. A 4-bit model is a heavily compressed photo: perfectly recognisable, much smaller, but with some fine detail lost. For a quick look it's fine; for printing a poster you might want the full file.

The hidden costs

Self-hosting moves work onto you: buying or renting GPUs, keeping the serving software patched, monitoring, scaling for peak load, applying your own safety filters, and swapping in new versions. For a small team, an API is usually cheaper until volumes are large or a hard requirement (like no data leaving the building) forces the issue.

Real-world example

A bank's QA team wants AI help analysing production logs that contain customer data. Policy forbids sending that data outside the bank's network. Option one: an open-weight model self-hosted inside the bank, after masking. Option two: a proprietary model through the bank's existing cloud provider, if the security team approves that provider's data terms. A third team in the same bank, generating test ideas from public product documentation, has no such constraint and simply uses Claude through the company plan. Same company, different answers per use case.

"Open weights" doesn't mean "transparent"

Having the weights lets you run, measure and fine-tune a model, and researchers can probe its internals in ways an API doesn't allow. But billions of numbers are not readable like source code. You still can't easily tell what data a model saw, whether it memorised copyrighted text, or what behaviours its training encouraged. Interpretability research (Chapter 38) is trying to change that, for open and closed models alike.

Conversely, closed vendors often publish detailed system cards about testing and safety (Chapter 33), which can tell you more about known risks than a bare weights download does. Transparency is about documentation and evidence, not only about file access.

32.6The safety debate

Whether powerful model weights should be released openly is one of the most argued questions in AI. Both sides include serious researchers and companies. The positions below are summaries of commonly made arguments, not settled facts.

Opinion · advocates of open release

Supporters argue that open weights let independent researchers study and stress-test models, spread benefits beyond a handful of large companies, reduce dependence on any one vendor, support privacy (data never leaves your machine) and let countries and smaller firms build their own systems. They often add that many risks come from how models are used, not whether weights are public, and that openness has historically made software more secure through scrutiny.

Opinion · advocates of caution

Critics argue that once weights are released they can't be recalled, and that anyone can strip out safety training through fine-tuning. For the most capable models, they worry this could give real help with cyberattacks or biological and chemical harm. Many in this camp support open release for smaller models but want testing and thresholds before releasing frontier-level weights. Anthropic, for example, keeps its models closed and makes Claude Mythos (the same underlying model as Fable, with some safeguards lifted) available only to organisations verified through programmes such as its Cyber Verification Program.

Notice that the camps overlap: several labs (OpenAI with gpt-oss, Google with Gemma, Meta with Muse Glimmer) keep frontier models closed while releasing smaller open-weight ones. The debate is mostly about where the line should be, not whether any open release is acceptable.

Common misunderstandings
"Open weights means open source."
Open-source AI (OSI definition) also needs the full code and enough training-data information to rebuild the model. Most open-weight releases provide only weights and inference code.
"If I can download it, I can use it however I like."
The licence decides. Some are permissive (Apache 2.0, MIT); others add usage policies, attribution or size thresholds.
"Self-hosting is free."
The weights may be free; GPUs, electricity, engineering time, monitoring and safety work are not.
"Proprietary means my data is used for training."
It depends on the product and plan. Commercial API and enterprise terms often differ from consumer apps. Check the terms (Chapter 132).
"Open models are always behind."
The top closed models usually lead on the hardest tasks, but strong open-weight models are competitive for many everyday jobs. Test on your own task.

32.8Review

Key takeaways
  • Proprietary models are used through an app or API; open-weight models can be downloaded and run under a licence.
  • OSI's Open Source AI Definition 1.0 (28 Oct 2024) requires data information, complete code and parameters, granting freedoms to use, study, modify and share.
  • Licences range from permissive (Apache 2.0, MIT) to custom terms with usage policies, attribution and thresholds, as in Llama 3.1's 700-million-user clause.
  • Self-hosting is limited mainly by memory; quantisation shrinks models at some cost in quality.
  • Open weights give control, privacy and version stability; proprietary APIs give frontier capability, speed to start and vendor support.
  • The safety debate is mainly about where to draw the line for releasing the most capable weights; present it as debate, not fact.
Check yourself

A vendor releases a model's weights under Apache 2.0 but publishes nothing about its training data or training code. How is it best described?

The OSI definition also requires training code and data information. Weights alone make it open-weight.

Which of these is a typical clause in a custom model licence like Llama 3.1's?

Llama 3.1 allows commercial use but adds an acceptable use policy, "Built with Llama" attribution and a 700-million-MAU threshold.

Roughly how much memory do the weights of a 30-billion-parameter model need at 4-bit precision?

4-bit is half a byte per parameter: 30 billion × 0.5 bytes ≈ 15 GB, before the extra room for the context and runtime. 60 GB would be 16-bit.

Policy says customer data must never leave the company network. Which approach does that most directly point to?

Only self-hosting keeps data entirely on your infrastructure. A cloud-hosted proprietary model may still be acceptable if security approves, but that's a different requirement.

How should a textbook present the arguments about releasing powerful model weights?

Serious researchers disagree, and many labs take a middle path of closed frontier models plus smaller open ones.

Teach it

"A model is basically a giant file of numbers called weights. Proprietary models, like Claude, keep that file private and you use them through an app or API. Open-weight models let you download the file and run it yourself, but the licence still sets rules, and you usually don't get the training data or training code, so it's not truly open source. Proprietary is quicker to start and usually more capable at the top end; open weights give you privacy, control and a version that never changes. Plenty of companies use both."
