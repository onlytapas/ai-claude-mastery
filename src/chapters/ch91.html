Before you start: Chapter 86 (the Claude request format). Chapter 89 (tool use and structured outputs on Claude) and Chapter 90 (caching and cost) give the Claude side in depth. Chapter 26 covers the AI companies themselves; this chapter is only about their developer APIs.

Claude, OpenAI's GPT models and Google's Gemini models are all reached the same basic way: an HTTPS POST with an API key, a model name, some instructions and the user's input, and a JSON reply with text and token counts. The details differ: field names, where the system prompt goes, how tool calls and results are shaped, whether the server remembers the conversation, and how caching is priced. Knowing those differences lets you compare models fairly, read anyone's sample code, and keep your own code from being locked to one vendor. All facts here were checked against each vendor's documentation in November 2026, and all three change often.

91.1Why a QA team should know all three

You may work only with Claude, and still meet the others:

  • Testing someone else's product. The chatbot you're testing may call OpenAI or Gemini. To read its logs, reproduce bugs and write mocks, you need to recognise their request and response shapes.
  • Fair comparisons. Managers ask "would another model be cheaper or better?" Answering that honestly means running the same eval set (Chapter 125) through each API.
  • Resilience and vendor lock-in. If all your tooling is written against one SDK's shapes, switching or adding a fallback is a rewrite. A thin adapter keeps that cost small.
In everyday life

Three courier companies all deliver parcels, but each has its own form: one puts the recipient's name at the top, another at the bottom, a third asks you to tick a box for "signature required". The parcel and the job are the same. Once you've filled in all three forms you stop thinking "these are different services" and start thinking "these are different forms for the same service".

What this chapter isn't

It isn't a ranking. Which model is "best" depends on your task and changes with every release; measure it with your own evals. This chapter is about the interfaces, which is what your code depends on.

Under the hood: stateless versus stored conversations

Claude's Messages API keeps nothing between calls: to continue a conversation you send all earlier turns again (Chapter 87). That's simple to reason about and easy to log and replay in tests.

OpenAI's Responses API and Google's Interactions API both store each exchange by default and let you continue by passing the previous ID, so you don't resend history yourself. Two details from their docs catch people out:

  • On OpenAI, top-level instructions are not carried over by previous_response_id; you resend them each turn. Earlier turns in the chain are still billed as input tokens.
  • On Gemini, tools, system_instruction and generation_config apply to one interaction only and must be sent again each turn. Setting store=false means you can't use previous_interaction_id.

Stored state also matters for data handling: check with your security team before relying on server-side storage for anything sensitive.

Older tutorials will mislead you

Most blog posts online use OpenAI's Chat Completions (messages, choices[0].message.content) or Gemini's generateContent (contents, parts). Both still work, but each vendor now recommends the newer API for new projects. OpenAI's Assistants API was shut down on 26 August 2026. And as Chapter 86 explained, Claude rejects temperature, top_p and top_k on API version 2026-10-21; Google's docs say Gemini 4 and Gemini 3.6+ ignore them and return deprecation warnings. Old "set temperature to 0 for consistency" advice no longer transfers.

Real-world example: the string that wasn't an object

A team ported a "look up test results" tool from Claude to OpenAI. On Claude, block.input["suite"] worked. On OpenAI the same line failed, because arguments arrives as a JSON-encoded string that needs json.loads() first. A contract test that feeds a recorded tool call from each provider into your handler catches this in seconds.

Why per-token prices can't be compared directly

Each vendor uses its own tokenizer, so the same user story can be a different number of tokens on each. Anthropic itself notes that Claude Opus 4.7 and later produce about 30% more tokens for the same text than earlier Claude models. Reasoning models also vary widely in how many thinking tokens they spend (billed as output) for the same task.

So the only fair comparison is cost per completed task at acceptable quality: run the same eval set through each model, record the real usage from every response, multiply by that vendor's prices, and compare alongside the pass rate. A model that is cheaper per token but needs twice the output, or fails twice as often, isn't cheaper.

91.7Compatibility layers

A compatibility layer lets you point one vendor's SDK at another vendor's models by changing the base URL, key and model name.

Python: calling Claude through the OpenAI SDK (Chat Completions format)
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ.get("ANTHROPIC_API_KEY"),   # a Claude key, not an OpenAI key
    base_url="https://api.anthropic.com/v1/",
)
response = client.chat.completions.create(
    model="claude-sonnet-5-5",
    messages=[
        {"role": "system", "content": "You are a senior QA engineer."},
        {"role": "user", "content": "Boundary values for age 18 to 65?"},
    ],
)
print(response.choices[0].message.content)

Google offers the same idea for Gemini at https://generativelanguage.googleapis.com/v1beta/openai/ (chat completions, embeddings, batch and more), which its docs describe as still in beta.

For testing, not for production

Anthropic says its OpenAI SDK compatibility is "primarily intended to test and compare model capabilities" and is not "a long-term or production-ready solution for most use cases". Documented limits include: prompt caching isn't supported; the strict flag on functions is ignored; system and developer messages are all hoisted into one system prompt; Claude's thinking isn't returned; most unsupported fields are silently ignored rather than rejected. That last point matters to testers: a request can "work" while quietly dropping a setting you rely on.

91.8Portability: a thin adapter you can test

The cheapest protection against lock-in isn't a big framework; it's keeping vendor-specific code in one small, tested place. Your application calls ask(...); only the adapter knows field names.

adapter.py
"""adapter.py - one function, three providers. Clients are passed in, so the
logic can be tested offline with fakes (see test_adapter.py)."""

def ask(provider, client, model, system, user, max_tokens=1000):
    if provider == "claude":
        msg = client.messages.create(
            model=model, max_tokens=max_tokens, system=system,
            messages=[{"role": "user", "content": user}])
        if msg.stop_reason == "max_tokens":
            raise RuntimeError("Claude reply was cut off at max_tokens")
        return "".join(b.text for b in msg.content if b.type == "text")
    if provider == "openai":
        resp = client.responses.create(
            model=model, instructions=system, input=user,
            max_output_tokens=max_tokens)
        return resp.output_text
    if provider == "gemini":
        inter = client.interactions.create(
            model=model, system_instruction=system, input=user)
        return inter.output_text
    raise ValueError(f"unknown provider: {provider}")
test_adapter.py (runs offline: fake clients, no keys, no network)
"""test_adapter.py - offline tests for adapter.py using fake clients."""
from types import SimpleNamespace as NS
from adapter import ask

class Recorder:
    """Records the keyword arguments a fake SDK method was called with."""
    def __init__(self, reply):
        self.reply, self.kwargs = reply, None
    def create(self, **kwargs):
        self.kwargs = kwargs
        return self.reply

def test_claude_joins_text_blocks_and_skips_thinking():
    rec = Recorder(NS(stop_reason="end_turn", content=[
        NS(type="thinking", thinking="..."), NS(type="text", text="17, 18, 65, 66")]))
    out = ask("claude", NS(messages=rec), "claude-opus-5-5", "QA", "Boundaries?")
    assert out == "17, 18, 65, 66"
    assert rec.kwargs["system"] == "QA" and rec.kwargs["max_tokens"] == 1000

def test_claude_truncation_is_an_error():
    rec = Recorder(NS(stop_reason="max_tokens", content=[NS(type="text", text="17, 1")]))
    try:
        ask("claude", NS(messages=rec), "claude-opus-5-5", "QA", "Boundaries?")
        assert False, "expected RuntimeError"
    except RuntimeError:
        pass

def test_openai_uses_instructions_and_input():
    rec = Recorder(NS(output_text="17, 18, 65, 66"))
    out = ask("openai", NS(responses=rec), "gpt-6.1-sol", "QA", "Boundaries?")
    assert out == "17, 18, 65, 66"
    assert rec.kwargs["instructions"] == "QA" and rec.kwargs["input"] == "Boundaries?"

def test_gemini_uses_system_instruction():
    rec = Recorder(NS(output_text="17, 18, 65, 66"))
    out = ask("gemini", NS(interactions=rec), "gemini-3.8-flash", "QA", "Boundaries?")
    assert out == "17, 18, 65, 66"
    assert rec.kwargs["system_instruction"] == "QA"

Portability habits that pay off

  • Keep prompts in files, not code, with a version number (Chapter 88). Expect to tune them per model: Anthropic's own docs warn that a prompt tuned for OpenAI is probably not ideal for Claude, and the reverse is true too.
  • Normalise usage and cost into your own record (provider, model, input, cached input, output, cost) so dashboards don't care which vendor answered.
  • Use the lowest common denominator only where you need portability. Citations, Claude's cache breakpoints, OpenAI's stored responses and Gemini's built-in tools are genuinely useful. Use them inside the adapter, behind a clear option, not scattered through the app.
  • Pin model IDs and record which model produced each result. Every vendor retires models on its own schedule (Chapter 95).
Opinion · widely held among practitioners

Many engineers prefer a small home-made adapter like this over a large multi-provider framework for internal tools: it's easier to debug, and new vendor features arrive the day they ship. Others prefer an established open-source abstraction library to avoid maintaining their own. Both are defensible; what matters is that vendor-specific code isn't spread across your whole codebase.

Common misunderstandings
"All LLM APIs are OpenAI-compatible now, so the format doesn't matter."
Compatibility layers exist but are partial: they silently ignore fields and drop features like caching and thinking. Native APIs are the reference.
"Cheaper per token means cheaper."
Tokenizers and thinking budgets differ. Compare cost per completed task at the quality you need.
"Tool call arguments are always an object."
Claude gives an object (input); OpenAI gives a JSON string (arguments) that you must parse.
"The server remembers my chat."
True by default on OpenAI Responses and Gemini Interactions (stored state), false on Claude Messages (you resend history).
"A prompt that works on one model will work the same on another."
Prompts usually need tuning per model. Re-run your evals after switching.

91.9Review

Key takeaways
  • Claude: POST /v1/messages with system, messages and required max_tokens; stateless.
  • OpenAI: POST /v1/responses with instructions and input; output_text helper; stored by default; Chat Completions still supported.
  • Gemini: POST /v1beta/interactions with system_instruction and input, key in x-goog-api-key; stored by default; generateContent still supported.
  • Tool calls and structured output follow the same idea everywhere but with different field names; OpenAI's tool arguments arrive as a JSON string.
  • All three price per million tokens with cached-input discounts and 50% batch discounts, but caching rules and minimums differ, and token counts aren't comparable across vendors.
  • Compatibility layers are for quick comparisons; keep vendor-specific code in a small adapter with contract tests.
Check yourself

On OpenAI's Responses API, where does the equivalent of Claude's system prompt go?

The Responses API uses instructions for high-level guidance, and developer messages rank above user messages.

Which header carries the API key for the Gemini API in Google's REST examples?

Gemini uses x-goog-api-key. Claude and OpenAI use Authorization: Bearer.

Your tool handler works with Claude but crashes with OpenAI when reading the tool's arguments. What is the likely reason?

Claude's tool_use block has input as an object; OpenAI's function_call item has arguments as a string.

Why is Anthropic's OpenAI SDK compatibility layer a poor choice for a production feature?

Anthropic describes it as primarily for testing and comparing capabilities; use the native API for production.

Model A costs half as much per million tokens as model B. What's the fair way to decide which is cheaper for your test-case generator?

Different tokenizers, thinking budgets and failure rates mean per-token price alone doesn't predict cost per useful result.
