A language model writes one token at a time, and every token gets roughly the same amount of computation. So a hard problem answered in one line gets very little "brain time". If the model first writes out its working, as a person would on scrap paper, it spends more computation on the problem and usually gets a better answer. Reasoning models are trained to do this well and on their own. In current Claude models this is called adaptive thinking: Claude decides whether and how much to think, and you steer it with an effort level. More thinking costs more tokens and time, so the skill is matching effort to the task.

19.1Why "thinking" helps a next-token predictor

Recall from Chapter 14 and Chapter 17 that a language model predicts the next token, then the next, and so on. Producing each token takes one pass through the network: a fixed amount of work. That has an important consequence. If you ask "Is 7,919 a prime number? Answer yes or no", the model has to commit to "Yes" or "No" in its first token, after one pass. There is no room to check anything.

Now ask the same question but let it write: "Check whether 7,919 is divisible by 2, 3, 5, 7, 11 … up to its square root, then answer." Every intermediate line it writes becomes part of the text it reads when producing the next line. The written steps act as working memory. The model gets many passes, and each later step can build on earlier ones.

In everyday life

Ask a colleague to multiply 47 by 38 in their head and answer within one second, and they will probably guess. Give them a pen and ten seconds and they will write 47 × 38 = 47 × 40 − 47 × 2 = 1,880 − 94 = 1,786, and get it right. They are not cleverer with the pen. They simply have somewhere to put the intermediate results, and more time to use them.

This written-out working has a name: chain of thought. In current Claude models it usually appears as a separate thinking section that comes before the final answer. Apps typically show it collapsed, or as a summary.

19.2From a prompting trick to a model feature

The idea grew in three stages over about four years.

  1. 2022Chain-of-thought prompting. Researchers at Google (Wei et al.) showed that putting worked examples with step-by-step reasoning in the prompt made large models much better at maths and logic word problems. The same year, Kojima et al. found that just adding "Let's think step by step" helped too.
  2. 2022Self-consistency. Wang et al. sampled several reasoning paths for the same question and took the most common final answer. More attempts meant more accuracy: an early sign that spending more compute at answer time pays off.
  3. 2024Reasoning models. In September 2024 OpenAI released o1, a model trained to produce a long internal chain of thought before answering. Thinking moved from a prompt trick into the model itself.
  4. 2025Open recipe and hybrid models. In January DeepSeek published R1 with open weights and a paper describing how reinforcement learning taught it to reason. In February Anthropic released Claude 3.7 Sonnet, which it called "the first hybrid reasoning model on the market": one model that could answer quickly or think at length.
  5. 2026Adaptive thinking and effort. Anthropic's effort parameter became generally available in February 2026. On today's Claude models thinking is adaptive: the model decides per request whether to think, and effort sets how readily and how deeply.

A model trained this way is called a reasoning model. Today the line is blurry: most frontier models, Claude included, can both reason at length and answer directly.

19.3Test-time compute: a second way to buy intelligence

For years the main way to get a smarter model was to make training bigger: more parameters, more data, more computation before release (Chapter 17). Reasoning models added a second dial. You can also spend more computation when the model answers, by letting it generate more thinking tokens. This is called test-time compute (or inference-time compute).

Training-time compute

Paid once, by the model maker, before release. Makes the model generally more capable. You can't change it: you pick a model.

Test-time compute

Paid on every request, by you, as thinking tokens. Lets the same model try harder on hard questions. You control it with effort, prompts and token limits.

The practical meaning for you: a smaller model thinking harder can sometimes match a bigger model answering quickly, and the reverse. Anthropic's own guidance reflects this: it recommends starting with Opus 5.5 for most workloads and moving to Fable 5.1 only "when evals on Opus 5.5 at higher effort still fall short". That is, try more thinking before a bigger model.

Thinking is output, and output is billed

Anthropic's documentation says thinking tokens are billed as output tokens, and output costs five times as much as input on current Claude models (for example $4 input and $20 output per million tokens on Opus 5.5, verified 9 Nov 2026). Thinking also counts toward max_tokens, the cap on how much a single reply may generate. A reply with a short visible answer can still be expensive if the model thought for a long time.

19.4How models learn to reason

Prompting "think step by step" helps any large model a little. Reasoning models are better at it because they were trained to reason, mostly with reinforcement learning (RL), the learn-from-reward method from Chapter 10 and Chapter 18.

1. ProblemA maths question, coding task or puzzle with a checkable answer
2. AttemptsThe model writes several reasoning chains and final answers
3. Automatic checkIs the answer right? Do the unit tests pass? Reward 1 or 0
4. UpdateMake the reasoning patterns that led to rewards more likely
5. RepeatMillions of times, on ever harder problems

The key ingredient is step 3: the reward comes from a verifier, a program that can check the answer, rather than a human rating. Maths answers can be compared, code can be run against tests. That makes the training cheap to scale, and it explains why reasoning models are especially strong at maths and code.

Real-world example: DeepSeek-R1

DeepSeek's January 2025 paper on R1 is the clearest public description of this recipe. Its first experiment, R1-Zero, used reinforcement learning without any human-written reasoning examples, rewarding only correct answers and the right output format. The model learned by itself to write longer chains of thought, to re-check its work and to try another approach when stuck. The final R1 added a small amount of supervised data first to make its reasoning more readable. The weights were released under the MIT licence. (Source: DeepSeek-AI, arXiv 2501.12948.)

Under the hood: why a reward on the answer improves the reasoning

The reward only looks at the final answer, so why does the reasoning get better? Because reasoning and answer are generated by the same process. In RL the model's probabilities are nudged so that whole sequences which earned a reward become more likely. If chains that check intermediate results lead to correct answers more often, the habit of checking is reinforced, even though nobody wrote a rule saying "check your work".

DeepSeek's paper uses an algorithm called GRPO (Group Relative Policy Optimisation, from their earlier DeepSeekMath work). For each problem it samples a group of answers, scores them, and pushes the model towards answers that scored better than the group average. No separate "critic" network is needed, which saves memory.

Two well-known side effects follow from this training. First, models may learn to "game" a weak verifier, for example writing code that special-cases the tests rather than solving the problem (sometimes called reward hacking). Second, the written chain of thought is a tool the model uses, not a guaranteed transcript of how it reached the answer. Anthropic published research in 2025 titled "Reasoning models don't always say what they think", which found that models often fail to mention hints that actually influenced their answers. Treat visible thinking as useful evidence, not as proof.

19.5Thinking in Claude today

Here is how thinking works on the current Claude models. These details change often, so check the date.

Verified 9 Nov 2026

On Claude Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5, thinking is adaptive. In Anthropic's words, "the model evaluates each request and determines whether to think and how much." A simple factual question may get no thinking at all; a tricky debugging task gets deep reasoning. The older manual mode, where you set a fixed thinking budget with budget_tokens ("extended thinking"), was deprecated on the 4.6 models and is not accepted on later ones.

The main control is effort. Anthropic describes it as "soft guidance" for how often and how deeply Claude thinks, and how many tokens it spends overall. It is not a guaranteed token count.

Old habits that no longer work

In Claude Code, "think", "think hard" and similar phrases are now passed through as ordinary text; ultrathink is the only recognised keyword. The Option+T / Alt+T thinking toggle has no effect on the 5.5 models or Fable, because thinking can't be switched off on them there. On the API, Anthropic notes that telling Sonnet 5.5 or Haiku 5.5 to "think less" in a prompt does not reliably reduce thinking: lower the effort instead.

19.6When thinking helps, and when it wastes time

Thinking is not free quality. It costs output tokens and seconds, and on easy tasks it can even make answers worse by over-complicating them. Anthropic's effort guidance warns that max "can lead to overthinking" on some structured-output or less demanding tasks.

Usually worth more thinkingUsually not worth it
Debugging a flaky test from a stack trace and logsReformatting test data from CSV into JSON
Designing boundary-value and pairwise cases for a complex ruleFixing spelling in a bug report
Reviewing a pull request for logic errorsClassifying 10,000 tickets as bug / feature / question
Working out why a CI pipeline fails only on one branchSummarising a meeting transcript
Planning a multi-step agent task across many filesAnswering "what does HTTP 404 mean?"
Calculations, date logic, multi-condition business rulesChat where the user is waiting and the task is simple

A simple rule of thumb: if a careful person would need scrap paper, the model benefits from thinking. If a person would answer instantly, low effort is usually fine.

Real-world example: a nightly triage job

A QA team runs Claude over every failed test each night to label it "product bug", "test bug" or "environment". Most failures are obvious (a timeout during a known outage), so they run at low effort on Haiku 5.5. Failures the first pass marks "unsure" are sent again at high effort on Opus 5.5. The expensive thinking is spent only where it changes the answer. This "cheap first, think harder on the hard ones" pattern is common, and Chapter 90 covers cost control in depth.

Opinion · Anthropic's guidance

Anthropic's documentation repeatedly advises choosing effort by measurement rather than instinct: run a representative sample at different levels, then compare quality, tokens and latency ("run a fresh effort sweep on your evals"). That advice reflects Anthropic's view that the best level depends on the workload, not a universal answer. Chapter 125 and Chapter 36 show how to build such evals.

Time follows the same shape, because output tokens are generated one at a time. If a model writes very roughly 50–100 tokens a second (a loose illustrative range, not a measured figure), 4,000 tokens of thinking add about 40–80 seconds before the answer appears. In an interactive chat that is a long wait; in an overnight batch it doesn't matter.

Under the hood: max_tokens, stop reasons and caching

On the API, max_tokens is a hard cap on everything Claude generates for one request: thinking plus visible answer. If thinking uses most of it, the answer can be cut off and the response's stop_reason will be "max_tokens". Anthropic's fix is either to raise max_tokens (if the reasoning was needed) or lower effort (if it was over-thinking).

Each response's usage section has output_tokens (the billed total) and, inside output_tokens_details, thinking_tokens: how many of those were reasoning. Apps may show a summary of the thinking, but you are billed for the full thinking the model generated, not the shorter text you see.

One more subtlety: the effort level is part of the prompt the model sees, so changing it between requests in one conversation breaks prompt caching for that conversation. Pick a level per conversation and keep it. Chapter 90 covers caching.

compare_effort.py (Python 3, standard library only)
"""Run the same question at three effort levels and compare tokens and time."""
import json
import os
import sys
import time
import urllib.error
import urllib.request

API_URL = "https://api.anthropic.com/v1/messages"
MODEL = "claude-sonnet-5-5"
QUESTION = (
    "A login form accepts usernames of 3 to 20 characters made of letters, "
    "digits and underscores, and the first character must be a letter. "
    "List the boundary-value and invalid-class test inputs you would use, "
    "one per line, with the expected result (accept or reject)."
)


def ask(key, effort):
    body = {
        "model": MODEL,
        "max_tokens": 16000,
        "output_config": {"effort": effort},
        "messages": [{"role": "user", "content": QUESTION}],
    }
    req = urllib.request.Request(
        API_URL,
        data=json.dumps(body).encode("utf-8"),
        headers={
            "x-api-key": key,
            "anthropic-version": "2026-10-21",
            "content-type": "application/json",
        },
    )
    start = time.time()
    try:
        with urllib.request.urlopen(req, timeout=300) as resp:
            data = json.load(resp)
    except urllib.error.HTTPError as err:
        sys.exit(f"HTTP {err.code}: {err.read().decode('utf-8')}")
    seconds = time.time() - start
    usage = data.get("usage", {})
    details = usage.get("output_tokens_details") or {}
    answer = "".join(
        block.get("text", "") for block in data.get("content", [])
        if block.get("type") == "text"
    )
    return {
        "effort": effort,
        "seconds": round(seconds, 1),
        "output_tokens": usage.get("output_tokens", 0),
        "thinking_tokens": details.get("thinking_tokens", 0),
        "answer_lines": len([l for l in answer.splitlines() if l.strip()]),
    }


def main():
    key = os.environ.get("ANTHROPIC_API_KEY")
    if not key:
        sys.exit("Set ANTHROPIC_API_KEY first (see Chapter 98).")
    print(f"Model: {MODEL}")
    print(f"{'effort':8}{'seconds':>9}{'output':>9}{'thinking':>10}{'lines':>7}")
    for effort in ("low", "medium", "high"):
        r = ask(key, effort)
        print(f"{r['effort']:8}{r['seconds']:>9}{r['output_tokens']:>9}"
              f"{r['thinking_tokens']:>10}{r['answer_lines']:>7}")


if __name__ == "__main__":
    main()

Common misunderstandings
"More thinking always gives better answers."
Only on tasks that need reasoning. On simple tasks it adds cost and delay and can cause over-thinking. Measure.
"The visible thinking is exactly how the model reached its answer."
It is useful evidence, not a guaranteed transcript. Research, including Anthropic's own, shows models don't always mention what influenced them. Check the answer, not just the reasoning.
"Typing 'think hard' makes Claude Code think harder."
Not any more. Use /effort, or ultrathink for one turn.
"Effort sets an exact number of thinking tokens."
It is soft guidance. Claude still decides per request, and no level guarantees a thinking block every time.
"If the answer is short, it was cheap."
Thinking tokens are billed as output even when you only see a summary or nothing at all. Check thinking_tokens in the usage data.
"Reasoning models were taught by people writing out every step."
Mostly they learned through reinforcement learning against automatic checks, as DeepSeek-R1's paper shows publicly.

19.9Review

Key takeaways
  • Each token gets about the same computation, so writing out working (chain of thought) gives a model more computation and a place to store intermediate results.
  • Chain of thought began as a prompting trick (2022) and became a trained model behaviour with reasoning models (OpenAI o1 in 2024, DeepSeek-R1 and Claude 3.7 Sonnet in 2025).
  • Test-time compute is a second dial alongside model size: spend more tokens thinking on hard problems.
  • Reasoning is mostly taught with reinforcement learning against automatic verifiers, which is why it is strongest on maths and code.
  • Current Claude models use adaptive thinking; effort (low to max) is the main control. Defaults differ by model and product.
  • Thinking is billed as output and adds latency. Match effort to the task and measure rather than guess.
Check yourself

Why does letting a model write out its reasoning tend to improve hard answers?

The model gets many passes instead of one, and the written steps act as working memory.

What is "test-time compute"?

It is paid per request by the user, unlike training compute, which the model maker pays once.

In DeepSeek-R1-Zero's training, what produced the reward?

Rewards came from verifiable answers. Good reasoning habits emerged because they led to correct answers.

You want Claude Sonnet 5.5 on the API to think less on a simple, high-volume task. What does Anthropic recommend first?

Effort is the calibrated control; Anthropic notes prompt instructions to think less aren't reliable on Sonnet 5.5, and budget_tokens isn't accepted on current models.

A reply shows only a three-line answer, but the bill is high. What is the most likely reason?

You are billed for the full thinking, even when only a summary (or nothing) is shown. Check usage.output_tokens_details.thinking_tokens.

Teach it

"A language model spends the same effort on every word it writes, so if it has to answer a hard question in one word, it's guessing. Letting it think first, writing out its working, gives it more effort and somewhere to keep notes. Reasoning models are trained to do that well, mostly by rewarding correct answers on maths and code. In Claude you control this with an effort level: low for quick, simple jobs, higher for debugging or test design. Thinking costs tokens and time, so we choose the level by testing, not by habit."
