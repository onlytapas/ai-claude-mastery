An API is how one program asks another program to do something. On the web, that conversation happens over HTTP: your program sends a request (where to go, what to do, who you are, and any data), and the other side sends back a response (a status code saying how it went, plus data, usually written in JSON). Every time you talk to Claude through code, connect a tool to Jira, or run an automated test against a backend, this is what's happening underneath. Once you can read a request and a response, nothing in the later chapters will feel like magic.

85.1What an API is

API stands for application programming interface. That sounds technical, but the idea is simple: it's a menu of things a program offers to other programs, plus rules for how to ask.

In everyday life: the restaurant

You sit in a restaurant. You don't walk into the kitchen and cook; you read the menu, tell the waiter what you want, and the waiter brings back your food, or comes back to say "sorry, we're out of fish". The kitchen is the other program. The menu is the API's documentation: the list of things you're allowed to ask for. The waiter is the API: the go-between that takes your request in a set format and returns a result. You never need to know how the kitchen works inside.

APIs are everywhere, often invisibly:

When you…An API call that happens
Check the weather on your phoneThe app asks a weather service's API for the forecast at your location
Pay online with a cardThe shop's website calls a payment provider's API to charge the card
Log in with "Sign in with Google"The site calls Google's API to confirm who you are
Move a Jira ticket to "Done"The Jira web page calls Jira's own API to update the ticket
Ask Claude something in claude.aiThe app calls Anthropic's API, which runs the model and returns the reply

Two words you'll see constantly: the client is the program asking (your browser, your test script, Claude Code); the server is the program answering (Jira, a payment service, Anthropic's API).

85.2The shape of a conversation: request and response

1 · Client builds a requestWhere (URL), what (method), who and how (headers), and any data (body)
2 · Request travelsOver the internet using HTTP, normally encrypted (HTTPS)
3 · Server does the workChecks who you are, does the job, prepares a result
4 · Response comes backA status code (how it went), headers, and usually a JSON body

Every API call, however complex, follows this pattern. A web API never "calls you" in the middle; it waits for a request and answers it. (Webhooks, in 82.10, are the one twist on this.)

85.3Reading a URL

The URL says where the request goes. A single address packs in several parts:

Anatomy of a URL
https://api.example.com/v2/orders/1042/items?status=shipped&limit=20
└─┬──┘   └──────┬──────┘ └───────┬───────────┘ └─────────┬──────────┘
scheme        host          path                    query string
(protocol)  (which server) (which resource)       (extra options)
PartExampleMeaning
SchemehttpsHow to talk. HTTPS is HTTP with encryption, so nobody in between can read it. Always expect HTTPS for real APIs.
Hostapi.example.comWhich server to contact
Path/v2/orders/1042/itemsWhich thing on that server. Here: version 2 of the API, order number 1042, its items.
Query string?status=shipped&limit=20Options as name=value pairs after a ?, joined with &: "only shipped items, at most 20"

The combination of a method and a path, such as POST /v1/messages, is called an endpoint. API documentation is mostly a list of endpoints and what each one expects.

85.4Methods: what you want done

The method (also called the HTTP verb) tells the server what kind of action you want.

MethodPlain meaningExampleChanges data?
GETGive me somethingGet order 1042No
POSTCreate something, or run an actionCreate a new order; send a message to ClaudeYes
PUTReplace something entirelyReplace order 1042 with this new versionYes
PATCHChange part of somethingChange only the delivery address of order 1042Yes
DELETERemove somethingCancel order 1042Yes
Real-world example: a QA view

Two properties of methods matter a lot in testing. A GET should be safe: calling it should never change anything, so you can call it a thousand times. PUT and DELETE should be idempotent: doing the same call twice has the same effect as doing it once (deleting an already-deleted order shouldn't delete a different one). POST usually isn't: sending "create order" twice may create two orders. That's exactly the "user double-clicks Pay" bug from Chapter 1, at the API level.

85.5Headers: the envelope

If the body is the letter, headers are what's written on the envelope: short Name: value lines that describe the request or response. You'll meet these all the time:

HeaderDirectionWhat it says
Content-Type: application/jsonBoth"The body is JSON." Without it, many servers can't read your data.
Accept: application/jsonRequest"Please answer in JSON."
Authorization: Bearer <token>Request"Here's my proof of who I am." (82.8)
User-AgentRequestWhich program is calling (for example, curl or a browser)
Retry-AfterResponse"Try again after this many seconds", often sent with a 429 or 503
request-id (name varies)ResponseA unique ID for this call. Put it in bug reports so the API team can find the exact request in their logs.

Header names aren't case-sensitive: content-type and Content-Type are the same. Many APIs also define their own headers. Anthropic's API, for instance, requires anthropic-version (Chapter 86).

85.6Status codes: how it went

Every response starts with a three-digit status code. The first digit tells you the family:

2xx · SuccessIt worked
3xx · RedirectLook somewhere else
4xx · Your mistakeSomething about the request is wrong
5xx · Their problemThe server failed
CodeNamePlain meaningWhat a tester checks
200OKWorked; here's the resultBody matches what was asked
201CreatedA new thing was createdIt really exists afterwards (GET it back)
204No ContentWorked; nothing to returnCommon after DELETE
301/302MovedThe resource is at another URLRedirect points somewhere sensible
400Bad RequestThe request is malformed or invalidError message says what was wrong
401Unauthorized"I don't know who you are": missing or bad credentialsNo data leaks without a valid key
403Forbidden"I know who you are, but you're not allowed"Users can't reach other users' data
404Not FoundThat resource doesn't existAsking for order 99999 fails cleanly
409ConflictClashes with the current state (for example, a duplicate)Creating the same user twice
422UnprocessableWell-formed but fails validation (used by some APIs instead of 400)Field-level error messages
429Too Many RequestsYou've hit a rate limit (82.9)A Retry-After header, and recovery later
500Internal Server ErrorThe server crashed handling thisAlways worth a bug report with the request ID
502/503/504Gateway / unavailable / timeoutA server in the chain is down or too slowRetries and timeouts in the client
In everyday life: 401 versus 403

At an office building, 401 is the security guard saying "I need to see your badge"; 403 is the guard saying "I see your badge, but it doesn't open this floor." Mixing these up is a very common bug, and a common interview question.

85.7JSON: the language of the body

JSON (JavaScript Object Notation, said "jay-son") is a plain-text way to write structured data. Despite the name, every programming language reads it. Here's a real-shaped example: a support ticket.

A JSON object
{
  "id": "QA-1042",
  "title": "Coupon total ignores discount",
  "priority": 2,
  "reproducible": true,
  "assignee": null,
  "labels": ["checkout", "regression"],
  "reporter": {
    "name": "Priya",
    "team": "QA"
  }
}
JSON pieceLooks likeIn the example
Object{ "key": value, … }The whole ticket; also reporter
Array (list)[ value, value ]labels
String (text)In double quotes"QA-1042"
NumberNo quotes2
Booleantrue or falsereproducible
Nullnull means "no value"assignee

Objects and arrays can be nested inside each other as deeply as needed. People describe positions with a path: reporter.name is "Priya"; labels[0] is "checkout" (counting starts at 0).

JSON mistakes that break requests
Single quotes
{'id': 'QA-1'} is invalid. JSON needs double quotes.
Trailing commas
["a", "b",]: the last comma is an error.
Comments
JSON has no comments. // like this breaks it.
Numbers as text
"priority": "2" is a string, not a number. The API may reject it or, worse, accept it and behave oddly.
Unquoted keys
{id: 1} is JavaScript, not JSON.

85.8Proving who you are: keys and tokens

Most APIs need to know who is calling, both to protect data and to bill for usage. The common methods:

MethodHow it's sentTypical use
API keyA long secret string in a header, such as x-api-key: sk-… or Authorization: Bearer sk-…Server-to-server calls; the Claude API
Bearer tokenAuthorization: Bearer <token>. "Bearer" means "whoever holds this token gets access".Most modern APIs
Personal access token (PAT)Like an API key, but tied to your user account and its permissionsGitHub, Jira/Atlassian, GitLab
OAuthYou sign in on the provider's page, and the app receives a short-lived token on your behalf"Sign in with…", MCP connectors to Jira or Google
Basic authUsername and password (or email and token) encoded in a headerOlder APIs; some Jira setups
Treat keys like passwords

Anyone who has your API key can act as you and spend your money. Never paste keys into chat messages, tickets, screenshots or code that gets committed to git. Store them in environment variables or a secrets manager. Chapter 98 covers keys, tokens and secrets in depth, including the confusing fact that "token" means two different things in AI.

85.9Rate limits

A rate limit caps how much you can use an API in a period of time, such as 50 requests a minute or a number of tokens per minute. Limits protect the service from overload and stop one customer crowding out others. When you exceed one, you get 429 Too Many Requests, often with a Retry-After header saying how long to wait.

Well-behaved clients slow down and retry after a short, growing wait. This is called exponential backoff: wait 1 second, then 2, then 4, and so on. Official SDKs, like Anthropic's (Chapter 86), do this for you.

85.10Webhooks: when the server calls you

Normally the client asks and the server answers. But what if you want to know when something happens, such as a build finishing or a ticket changing? Asking every ten seconds ("polling") is wasteful. A webhook flips the direction: you give the service a URL of yours, and it sends a request to that URL when the event happens.

Real-world example

GitHub can send a webhook to your CI server whenever someone opens a pull request; the CI server then starts the test run. Jira can send a webhook to a Slack integration whenever a P1 bug is created.

85.11curl, flag by flag

curl is a command-line program that sends HTTP requests. It's installed on macOS, Linux and modern Windows, and nearly every API's documentation shows examples in it. If you can read a curl command, you can read any API example.

A typical POST request in curl
curl https://api.example.com/v2/tickets \
  -X POST \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $EXAMPLE_TOKEN" \
  -d '{"title": "Coupon total ignores discount", "priority": 2}'
PieceMeaning
curl URLSend a request to this URL. With no other options, it's a GET.
\ at line end"The command continues on the next line." Just for readability.
-X POSTUse this method. (curl switches to POST automatically when you use -d, so -X POST is often left out.)
-H "Name: value"Add a header. Repeat for each header.
-d '…'Send this body (data). Single quotes stop the terminal from changing what's inside.
$EXAMPLE_TOKENAn environment variable: the terminal swaps in its value, so the secret never appears in the command (Chapter 56).
-iShow the response status line and headers as well as the body
-sSilent: hide the progress meter
-vVerbose: show everything sent and received. Great for debugging (careful: it prints your auth header).
-o fileSave the response body to a file
-w "%{http_code}"Print just the status code after the response: handy in scripts
What actually travels over the wire

Underneath, an HTTP request is just structured text (HTTP/2 and HTTP/3 pack it more efficiently, but the content is the same). Running curl with -v shows a version of it:

POST /v2/tickets HTTP/1.1          ← method, path, protocol version
Host: api.example.com              ← headers, one per line
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Content-Length: 58
                                   ← a blank line ends the headers
{"title": "Coupon total ignores discount", "priority": 2}

HTTP/1.1 201 Created               ← the response: status line
Content-Type: application/json
Location: /v2/tickets/QA-1043

{"id": "QA-1043", "title": "Coupon total ignores discount", ...}

HTTPS wraps this whole exchange in encryption (TLS), so anyone watching the network sees only that you contacted api.example.com, not the path, headers or body. That's why sending an API key over HTTPS is reasonable, but over plain HTTP it isn't.

85.12Postman, Bruno and friends

Graphical API clients such as Postman, Insomnia and Bruno do exactly what curl does, with forms instead of flags: choose a method, type a URL, add headers and a body, press Send, and read the response. They add collections, environments (for keeping keys out of requests) and test scripts. Most can import and export curl commands, so you can paste an example from documentation straight in. Which you use is a team choice; the concepts are identical.

Why curl still matters

Claude Code runs commands in a terminal. When it tests an API for you, it will usually use curl or a small script. Being able to read its curl commands is how you check what it's actually sending before you approve it (Chapter 67).

Common misunderstandings
"An API is a website."
A website is for people; an API is for programs. Many websites are themselves built on top of APIs.
"200 means the test passed."
Only that the server didn't report an error. Check the body: some APIs return 200 with an error message inside.
"401 and 403 are the same."
401 means "who are you?"; 403 means "you're not allowed".
"JSON and JavaScript objects are the same."
Close, but JSON is stricter: double quotes, no comments, no trailing commas.
"It's fine to share an API key with a colleague in chat."
Keys are passwords. Each person or system should have its own, stored securely, so it can be revoked without breaking everyone.

85.14Review

Key takeaways
  • An API is a defined way for programs to ask each other for things; the client asks, the server answers.
  • An HTTP request has a URL, a method, headers and an optional body; a response has a status code, headers and usually a JSON body.
  • Status code families: 2xx success, 3xx redirect, 4xx your request's problem, 5xx the server's problem. 401 = not identified, 403 = not allowed, 429 = slow down.
  • JSON uses objects, arrays, strings, numbers, booleans and null, with strict rules (double quotes, no trailing commas or comments).
  • APIs identify callers with API keys, bearer tokens, personal access tokens or OAuth; all are secrets.
  • curl and tools like Postman build the same requests; reading curl lets you check what an AI agent is about to send.
Check yourself

Which HTTP method should be used to fetch an order without changing anything?

GET is for reading. It should be safe to repeat with no side effects.

Your test calls an endpoint with a valid token, but for a resource that belongs to another user. What's the correct status?

The server knows who you are (the token is valid) but you aren't allowed. Some APIs deliberately return 404 instead to avoid revealing that the resource exists; either way, it must not be 200.

Which of these is valid JSON?

JSON needs double-quoted keys and strings, and no trailing commas.

In curl -H "Authorization: Bearer $TOKEN" …, what is $TOKEN?

Using a variable keeps the secret out of the command history and out of screenshots.

What does a 429 response tell your client to do?

429 is a rate limit. Back off and retry; don't hammer the API.

Teach it

"An API is a waiter between programs. You send a request with a URL for where, a method for what, headers for who and how, and a JSON body for data. You get back a status code: 2xx is fine, 4xx is your mistake, 5xx is theirs. You prove who you are with a key or token, which is a secret. curl and Postman build the same requests, and reading curl lets you check exactly what an AI agent is about to send."
