Every prompt is a small data transfer. Whatever you paste, attach or let an agent read leaves your machine, reaches a provider, may be logged, and may be kept for a period that depends on your plan and settings. Privacy in practice comes down to four habits: know which route your data takes, put only the data the task needs on that route, mask what's personal or secret before it leaves, and use the commercial controls your organisation has paid for. The law (Chapter 133) tells you why; this chapter tells you how.

132.1What data goes where

When a tester pastes a failing API response into an AI chat, it feels like a private conversation. Technically, it's a journey with several stops:

Your deviceclipboard, files, terminal history, local logs
The appClaude.ai, Claude Code, an IDE plug-in, or your company's tool
The providerAnthropic, or a cloud platform such as Amazon Bedrock
Storagechat history, logs, safety review, feedback
Onwardconnected tools: MCP servers, Jira, Slack, web fetches

At each stop, ask three questions: who can see it, how long is it kept, and what else may it be used for? The answers differ by product and plan, so "Is Claude safe for our data?" has no single answer. The right question is "Is this route, on this plan, with these settings, appropriate for this data?"

In everyday life

Sending data to an AI service is like sending a parcel. A personal courier and a corporate logistics contract may use the same vans, but the contract sets who may open the parcel, how long the depot keeps a copy, and what happens if it's lost. You'd check what's in the box, and which contract you're using, before you hand it over.

Agents widen the journey

A chat sends what you paste. An agent sends what it reads. When Claude Code opens a file, runs a command or calls an MCP tool, the result enters the conversation and travels to the model. An agent working in a repository with a production database dump in it can send rows from that dump without you ever pasting them. Scope what agents can read (Chapter 131 and Chapter 134).

132.2Consumer versus commercial terms

Anthropic offers Claude under two families of terms. Consumer terms cover individual plans (Free, Pro, Max and other personal plans) and Claude Code used from those accounts. Commercial terms cover Team and Enterprise, the Claude API (including through Amazon Bedrock, Google Cloud and Microsoft Foundry), and government and education offerings. The difference matters more than any feature.

Real-world example

A tester uses a personal Pro account at home to "quickly" ask Claude why a customer's payment failed, pasting the request log with the customer's name, email and card prefix. Even with training off, that personal data now sits in a consumer account outside the company's contract, audit logs and deletion controls. The same question asked through the company's Team workspace, with the log first passed through a redactor (lab below), is a very different risk.

Under the hood: why commercial terms usually satisfy security teams

Commercial agreements change three things a security review cares about. Contract: a business agreement and usually a data processing addendum set out the provider's duties as a processor of your data. Control: admins, not individuals, decide settings; Enterprise adds audit logs, SCIM, role-based access, a Compliance API and custom data retention. Visibility: usage is tied to company identities through single sign-on, so access can be removed when someone leaves. None of this stops a person pasting the wrong thing, which is why the remaining sections focus on habits and tooling.

132.4Handling personal data (PII)

Personally identifiable information (PII) is any information that identifies a person directly (name, email, phone, PAN, Aadhaar number) or indirectly when combined (date of birth plus PIN code plus employer). Laws use slightly different terms: "personal data" in the EU's GDPR and in India's DPDP Act. QA teams meet PII constantly: in production bug reports, logs, screenshots, test data copied from live systems and support tickets.

Work down this ladder, stopping at the first step that still lets you do the job:

1. Don't include itMost debugging needs the shape of the data, not the person
2. Synthetic dataGenerate realistic fake records (Chapter 122)
3. MaskReplace values with placeholders such as [EMAIL]
4. PseudonymiseReplace with consistent tokens (user_17) and keep the key elsewhere
5. Approved routeIf real data is unavoidable: commercial workspace, minimum fields, documented reason

Masking

Data masking replaces sensitive values with placeholders. "priya@example.com" becomes "[EMAIL]". Simple and safe, but you lose the ability to tell two customers apart.

Pseudonymisation

Pseudonymisation replaces values with consistent stand-ins ("customer_A" everywhere), so patterns survive. Under GDPR, pseudonymised data is still personal data because someone holds the key to reverse it.

Anonymisation is harder than it looks

Truly anonymous data can't be linked back to a person by any reasonable means. Removing names isn't enough: a rare combination of age, town and job title can identify someone. Treat "we anonymised it" claims sceptically, and prefer synthetic data for testing.

Screenshots and images

Images carry PII too: names in a page header, an email in the corner of a screenshot, a customer's address in a PDF. Crop or blur before attaching, and check the browser's tab bar and bookmarks bar.

132.5Secrets never belong in prompts

A secret is anything that grants access: API keys, passwords, access tokens, private keys, connection strings, session cookies. Secrets leak into AI conversations in predictable ways: a pasted curl command with an Authorization header, a stack trace that prints environment variables, an agent reading .env, or a HAR file exported from browser developer tools, which contains cookies.

In Claude Code, block the obvious paths with deny rules (they win over every allow rule, Chapter 78):

.claude/settings.json (project) or managed settings
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}

Deny rules govern Claude's file tools. Shell commands are a separate path, so pair them with the sandbox and its read restrictions for stronger protection (Chapter 134). If a secret does get into a conversation, treat it as leaked: revoke and rotate it straight away, following Chapter 98. Deleting the chat doesn't un-send it.

132.6Data loss prevention (DLP)

Data loss prevention (DLP) means tools and rules that spot sensitive data and stop it leaving approved places. Security teams apply DLP at several points; each sees different things.

Where DLP sitsWhat it can do for AI useBlind spots
Endpoint (agent on the laptop)Warn or block when sensitive data is copied, uploaded or pasted into unapproved appsPersonal devices; command-line tools
Browser / secure web gatewayAllow the company AI workspace, block consumer AI sites, inspect uploadsDesktop apps and APIs that bypass the browser
API gateway / proxyScan or redact prompts your own applications send to a model APIOnly covers traffic routed through it
Provider admin controlsRestrict connectors, turn off feedback, audit usage, export logs for review (Enterprise)Can't see what users do in other tools
Before you paste (you)A redaction script or checklist, as in the labDepends on people using it

DLP pattern matching is good at structured data (card numbers, PAN, Aadhaar numbers, keys) and poor at meaning (a paragraph describing a customer's medical condition). Expect both misses and false alarms, and keep the human habit even where the tooling exists.

Opinion · common among security practitioners

Many security leaders argue that blocking all AI tools backfires: people move to personal accounts the company can't see ("shadow AI"). Their usual preference is to provide one approved, well-configured route, make it easy, and block or warn on the rest. This is practitioner judgement rather than a published standard.

132.7Data residency

Data residency means controlling which country or region your data is processed and stored in. Organisations care because of law (some data may not leave a jurisdiction), contracts (customers may require it) and risk appetite.

Anthropic's API offers two independent controls (verified 9 November 2026):

ControlWhat it governsOptions today
Inference geo (inference_geo per request, or a workspace default)Where the model runs"global" (default, any available region) or "us" (US-only, priced at 1.1x on Claude 4.6 and later models)
Workspace geo (set when a workspace is created; can't be changed)Where data is stored at rest and where some processing (for example code execution) happens"us" only

Administrators can restrict a workspace with allowed_inference_geos and set default_inference_geo. On Amazon Bedrock and Google Cloud's Google-managed offering, the region comes from the endpoint you choose instead; your cloud team configures it.

For readers in India

At the time of writing, Anthropic's own controls don't offer an India region. If your organisation needs processing in a specific region, check what each cloud platform offers for Claude in that region at the time you decide, and get the answer in writing. India's DPDP Act (Chapter 133) does not ban sending personal data abroad in general: the government may restrict transfers to countries it notifies, and some sector regulators (banking, for example) have their own stricter localisation rules. Your compliance team will know which apply.

It masks secrets first (so later rules don't split them), then emails, PAN and Aadhaar-style numbers, card numbers (checked with the Luhn checksum to reduce false alarms), Indian mobile numbers and IP addresses.one file, about 60 lines.
redact.py
"""redact.py - mask common personal data and secrets before text goes to an AI tool.
Usage: python3 redact.py bug_report.txt > bug_report.redacted.txt
A safety net, not a guarantee: always read the output before you paste it.
"""
import re
import sys


def luhn_ok(number):
    digits = [int(d) for d in re.sub(r"\D", "", number)][::-1]
    total = 0
    for i, d in enumerate(digits):
        if i % 2 == 1:
            d *= 2
            if d > 9:
                d -= 9
        total += d
    return total % 10 == 0


RULES = [
    # secrets first, so later rules don't split them
    ("ANTHROPIC_KEY", re.compile(r"sk-ant-[A-Za-z0-9_\-]{10,}")),
    ("JWT", re.compile(r"eyJ[A-Za-z0-9_\-]+\.[A-Za-z0-9_\-]+\.[A-Za-z0-9_\-]+")),
    ("BEARER", re.compile(r"(?i)(authorization:\s*bearer\s+)[A-Za-z0-9._\-]+")),
    ("PASSWORD", re.compile(r"(?i)(password\s*[=:]\s*)\S+")),
    ("EMAIL", re.compile(r"[A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Za-z]{2,}")),
    ("PAN", re.compile(r"\b[A-Z]{5}[0-9]{4}[A-Z]\b")),
    ("CARD", re.compile(r"\b(?:\d[ -]?){12,18}\d\b")),
    ("AADHAAR", re.compile(r"\b[2-9][0-9]{3}\s?[0-9]{4}\s?[0-9]{4}\b")),
    ("PHONE_IN", re.compile(r"(?<!\d)(?:\+91[\s-]?|0)?[6-9]\d{4}\s?\d{5}(?!\d)")),
    ("IPV4", re.compile(r"\b(?:\d{1,3}\.){3}\d{1,3}\b")),
]


def redact(text):
    counts = {}
    for label, pattern in RULES:
        def replace(match, label=label):
            if label == "CARD" and not luhn_ok(match.group(0)):
                return match.group(0)            # not a real card number shape
            counts[label] = counts.get(label, 0) + 1
            if label in ("BEARER", "PASSWORD"):
                return match.group(1) + f"[{label}]"
            return f"[{label}]"
        text = pattern.sub(replace, text)
    return text, counts


if __name__ == "__main__":
    source = open(sys.argv[1], encoding="utf-8").read() if len(sys.argv) > 1 else sys.stdin.read()
    cleaned, counts = redact(source)
    print(cleaned)
    summary = ", ".join(f"{k}={v}" for k, v in sorted(counts.items())) or "nothing found"
    print(f"Redacted: {summary}", file=sys.stderr)

Common misunderstandings
"If I turn training off, my data is never kept."
Training and retention are different. Data is still stored for the retention period, longer if flagged or sent as feedback.
"My personal Pro account is fine for work if training is off."
Consumer terms sit outside your company's contract, admin controls and audit trail. Use the approved commercial route for work data.
"Pseudonymised data isn't personal data."
Under GDPR it still is, because it can be re-linked. Only truly anonymous data falls outside, and that's hard to achieve.
"The DLP tool will catch it."
DLP catches patterns, not meaning, and only on the routes it watches. Keep the habit of checking before you paste.
"Deleting the chat fixes a leaked key."
Once sent, assume it's exposed. Revoke and rotate the key.

132.9Review

Key takeaways
  • Every prompt, file and agent read is a data transfer: know the route, the plan and the settings.
  • Anthropic's consumer plans train only if the user opts in; commercial products don't train on your data by default. Feedback and flagged content have longer retention.
  • Classify data and map each class to allowed AI routes.
  • For PII: leave it out, use synthetic data, mask or pseudonymise, and only then consider an approved route for real data.
  • Secrets never go in prompts; deny agent access to secret files; rotate anything that leaks.
  • DLP and residency controls help, but they complement careful habits rather than replacing them.
Check yourself

Under Anthropic's terms as of November 2026, are a company's Claude API inputs used for model training by default?

The commercial privacy page says inputs and outputs from commercial products aren't used for training by default. Feedback such as thumbs up/down is the main exception.

A consumer user turned on model improvement. How long may Anthropic keep de-identified data from new chats in training pipelines?

The consumer retention page says up to 5 years with the setting on. With it off, deleted chats leave back-end storage within 30 days.

Because the lookup table can re-identify people, the data remains personal data. It's a good safeguard, not an exemption.

Deny rules are checked first and can't be overridden by allow rules. Instructions in CLAUDE.md are guidance, not enforcement.
