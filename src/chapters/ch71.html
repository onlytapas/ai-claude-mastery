Almost all software lives in git, and almost every change reaches the main code through a pull request on GitHub. Claude Code is fluent in both. It can create branches, write clear commit messages, explain a confusing diff, untangle a merge conflict, open a pull request and review someone else's. Your job is to decide what should happen and to check the result, especially before anything is pushed where other people will see it. This chapter shows how to make that partnership fast and safe.

71.1Why git and Claude work so well together

Git is a time machine for files. Every commit is a saved snapshot you can return to. That makes it the perfect safety net for an AI that edits files: if Claude makes a mess, git can undo it exactly.

What Claude does well with git

  • Explaining what changed and why, in plain words
  • Writing clear, consistent commit messages
  • Resolving routine merge conflicts
  • Finding which commit introduced a bug
  • Remembering exact command syntax so you don't have to

What stays your decision

  • What goes into each commit
  • When to push, and to which branch
  • Whether a conflict resolution is actually correct
  • Anything that rewrites shared history
  • Merging into the main branch
In everyday life

Think of git as the "track changes" feature in a shared document, plus a stack of dated backup copies, plus a formal sign-off process before changes go into the final version. Claude is a fast, careful assistant who can operate all of it, but you still hold the pen for the final signature.

71.2Branches and commits, the Claude way

A branch is a separate line of work, so your changes don't disturb the main version until they're ready. You can ask Claude for each step in plain language. It runs the git commands, and you approve them (or they run automatically if your permission rules allow it).

Prompts you can type in Claude Code
Create a branch called test/coupon-expiry from the latest main.

Show me what I've changed so far, grouped by file, in plain words.

Commit only the test files, not the config change, with a clear message.

What changed on this branch compared with main? Summarise it for a tester.

Behind the scenes Claude uses ordinary git commands. Knowing them lets you read the permission prompts with confidence:

Good commit messages

A commit message is a note to your future self and your team. Claude writes good ones if you tell it your team's style once, ideally in your project's CLAUDE.md (Chapter 77):

A CLAUDE.md section for commits
## Commits
- Format: "<area>: <what changed>", e.g. "checkout tests: cover expired coupons"
- First line under 72 characters; add a short body if the reason isn't obvious
- One logical change per commit; never mix test changes with app changes
- Reference the Jira key at the end of the body, e.g. "Refs CHK-412"
Real-world example

A tester finished a morning of work with eleven changed files: new tests, a fixed helper, and an accidental change to a config file. They asked: "Split my changes into sensible commits and leave the config change uncommitted." Claude proposed three commits with messages, showed which files went in each, and waited for approval. The config file stayed out. Ten minutes of fiddly work took one prompt and a careful read.

71.3Reading diffs with Claude

A diff shows lines removed (often marked -) and lines added (+). Diffs are where you check Claude's work, and where you check developers' work too. Claude can explain any diff in the words you need:

Useful diff prompts for testers
Explain the diff on this branch as if I'm a tester who doesn't read code well.
Which user-visible behaviours could this change affect?

List every condition (if/else, validation rule, limit) that changed, with the
old value and the new value.

Does this diff change any test assertions? Flag any that got weaker.

That last prompt is a QA superpower. A weakened assertion, such as toBe(90) becoming toBeGreaterThan(0), can hide a real bug while every test stays green.

71.4Merge conflicts and rebasing

A merge conflict happens when two people changed the same lines differently, and git can't decide which version wins. Git marks the clash inside the file:

What a conflict looks like
<<<<<<< HEAD
const MAX_COUPONS = 1;
=======
const MAX_COUPONS = 2;
>>>>>>> feature/multi-coupon

Claude is good at untangling these, but the decision about which behaviour is correct is a product decision. A safe prompt:

Prompt
I have merge conflicts after merging main into my branch.
For each conflict: show both sides, explain what each side intended,
and propose a resolution. Don't apply anything until I approve each one.
Afterwards, run the tests.

Rebasing replays your commits on top of the latest main, giving a tidier history. It also rewrites those commits. That's fine on your own branch, and dangerous on a branch other people use.

Golden rule

Never rewrite history that other people have already pulled. That means: no rebasing shared branches, and no force push to main or any team branch. If Claude suggests git push --force, stop and ask why.

Finding the commit that broke something: git bisect

git bisect finds the commit that introduced a bug by binary search: you mark one commit "good" and one "bad", and git checks out the commit halfway between. You test, mark it good or bad, and repeat. A thousand commits take about ten steps.

git bisect start
git bisect bad                 # the current commit has the bug
git bisect good v4.1.0         # this release didn't
# git checks out a middle commit; test it, then:
git bisect good                # or: git bisect bad
# …repeat until git names the first bad commit
git bisect reset               # return to where you started

Claude can drive this for you if there's a test or command that detects the bug: "Use git bisect between v4.1.0 and HEAD; the bug is present when npx playwright test coupon fails." Watch the first few steps to make sure the test really detects the bug.

71.5Pull requests and issues with the GitHub CLI

The GitHub CLI, gh, lets you (and Claude) work with GitHub from the terminal. Install it from cli.github.com, then sign in once with gh auth login. Claude Code uses gh when you ask for anything on GitHub, if it's installed.

An alternative to gh is the GitHub MCP server (Chapter 103), which gives Claude GitHub tools directly. Both work; many teams use gh in the terminal and MCP in the chat apps.

Sessions linked to pull requests

Claude Code remembers which sessions were linked to which pull request. claude --from-pr 123 (or a PR URL) resumes the session linked to that PR; on its own, --from-pr opens a picker. Handy when a reviewer asks for changes days later.

71.6AI code review: /code-review and ultrareview

Claude Code includes a code-review skill. In a session:

Syntax (verified in Claude Code 2.1.319)
/code-review [low|medium|high|xhigh|max|ultra] [--fix] [--comment] [--max-findings n|all|default] [pr#|branch|path]
PartMeaning
Effort levelHow hard to look: low gives few, high-confidence findings; higher levels find more, including uncertain ones. ultra runs a deep review in the cloud.
--fixApply the fixes to your files after the review
--commentPost the findings as comments on the pull request
--max-findingsHow many findings to report
TargetA PR number, branch or path; without one, it reviews your current changes

/review still works, but it's now simply another name for /code-review. The old /pr-comments command was removed.

For a deeper, slower review there's ultrareview, a multi-agent review that runs in Anthropic's cloud. In a session use /code-review ultra (or /ultrareview); from the shell or a script:

claude ultrareview 123            # review PR 123 and print the findings
claude ultrareview 123 --post     # also post one comment on the PR, as you
claude ultrareview --json         # raw findings for scripts

By default ultrareview only prints its findings; it posts to the PR only with --post. The docs note a small number of free runs on Pro, Max and Ultra plans, after which it uses usage credits.

Real-world example: review for testability

Before testing a developer's PR, a tester ran /code-review high 482, then asked: "Given this diff and the review, what should I test manually, and which existing automated tests cover it?" The answer pointed out a new rounding rule with no test at all, which became the first bug of the sprint, found before the code was merged.

71.7Claude inside GitHub: the GitHub App and Action

Claude can also work directly on GitHub, triggered by a comment. The quickest setup is to run, inside Claude Code:

/install-github-app

This works for repositories on github.com. It installs the Claude GitHub App, adds the needed secret to the repository, and opens a pull request containing a workflow file. After it's merged, anyone can write @claude in an issue or PR comment, for example "@claude add tests for the expired-coupon case", and Claude does the work in GitHub's cloud runners and replies.

The workflow uses the official action anthropics/claude-code-action@v1. A minimal version from Anthropic's documentation:

.github/workflows/claude.yml (from the Claude Code docs)
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
PartPlain meaning
on: issue_comment …Run whenever someone comments on an issue or a PR review
if: contains(…'@claude')…but only if the comment mentions @claude
permissionsWhat the job may do in the repository: write code, comment on PRs and issues
secrets.ANTHROPIC_API_KEYThe API key, stored as an encrypted GitHub secret, never in the file (Chapter 98)

Other documented inputs include prompt (run with a fixed instruction, for example on every new PR), claude_args (pass Claude Code flags), claude_code_oauth_token (use a subscription token from claude setup-token instead of an API key), trigger_phrase (change @claude), and options for Bedrock, Vertex and Foundry. GitLab has a similar integration, documented by Anthropic as beta and maintained by GitLab.

Review bots need rules too

A bot that can write to your repository is a powerful team member. Decide who may trigger it, keep it from merging on its own (protect your main branch so merges need a human approval), and read what it changes like any other pull request.

71.8Safety rules for git

Claude asks before running commands unless your rules allow them. Two layers make git work safe:

1. Permission rules (Chapter 78). Deny rules always win over allow rules, at every settings level:

.claude/settings.json — let Claude commit, but never push
{
  "permissions": {
    "allow": [
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(git log *)",
      "Bash(git add *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)",
      "Bash(git reset --hard *)"
    ]
  }
}

With this, Claude can stage, commit and inspect history freely, while pushing and destructive resets are blocked. You push yourself after reviewing.

2. Branch protection on GitHub. Protect main so it requires a pull request, passing checks and a human approval. Then even a mistaken push can't change the main code directly.

Risky actionWhy it's riskySafe habit
git push --forceOverwrites others' commits on the remoteDeny it; never on shared branches
git reset --hardThrows away uncommitted work with no undoCommit or stash first; deny in settings
Rebasing a shared branchRewrites history others depend onRebase only your own branches
Committing secretsKeys in git history are hard to remove and get leakedKeep secrets in environment variables; check diffs
Huge "fix everything" commitsImpossible to review or undoOne logical change per commit

Workflow B: write tests on a feature branch

In plan mode: plan Playwright tests for the expired-coupon story.
[approve the plan]
Implement, run the tests, and prove one assertion can fail by breaking the rule.
Commit with our commit style. Don't push.

Workflow C: open a PR with a test report

Push is blocked for you, so I'll push. Then:
Draft a pull request description with: what was tested, how to run the tests,
results (pass/fail counts), anything not covered, and the Jira key.
Use gh pr create with that description once I confirm.
A safe git round trip40 min · a practice repository
  1. In a practice repo, add the "commit but never push" rules from 68.8 to .claude/settings.json. Start claude.
  2. Ask: "Create a branch called practice/git-lab and add a small README section about how to run the tests."a branch created and a file edited, with permission prompts for anything not in your allow list.
  3. Ask: "Commit this with a clear message, then push it."the commit succeeds; the push is blocked by your deny rule, and Claude tells you so.
  4. Create a conflict on purpose: change the same line on main and on your branch, then ask Claude to merge main into your branch and resolve conflicts one by one with your approval.conflict markers explained, a proposed resolution, and nothing applied without your OK.
  5. If you have gh and a GitHub practice repo, push yourself, then ask: "Open a draft pull request with a test-report style description."a draft PR on GitHub with a structured description.
  6. Run /code-review on the branch.a list of findings (possibly none on such a small change), with confidence levels.
Common misunderstandings
"Claude pushed my code, so it must be fine."
Pushing only moves code. Review the diff, run the tests, and prefer blocking push so you do it yourself.
"An AI review means no human review is needed."
AI review catches different things from human review. Use both, and keep a human approval on merges.
"Merge conflicts are a technical problem."
Often they're a product question: which behaviour is right? Claude can explain both sides; a person decides.
"/review and /code-review are different tools."
In current versions /review is just another name for /code-review.

71.10Review

Key takeaways
  • Git is Claude's safety net: every commit can be inspected and undone.
  • Ask in plain language for branches, commits and diffs; know the underlying commands so you can read the prompts.
  • Put your commit style in CLAUDE.md; use diff prompts to spot weakened assertions.
  • Resolve conflicts with Claude's explanations, but decide behaviour yourself; never rewrite shared history.
  • gh brings PRs, issues and CI logs into the terminal; --from-pr resumes PR-linked sessions.
  • /code-review (alias /review) and claude ultrareview give AI reviews; /install-github-app puts Claude into GitHub via anthropics/claude-code-action@v1.
  • Deny git push and destructive commands in settings, and protect main with required human approval.
Check yourself

You want Claude to commit freely but never push. What's the most reliable way?

Deny rules are enforced by Claude Code itself and beat allow rules at every level.

What does /review do in Claude Code 2.1.319?

/pr-comments was removed; /review became an alias of /code-review.

By default, what does claude ultrareview 123 do with its findings?

--no-post is the default; --post adds one plain comment as you.

When is rebasing risky?

Rebasing your own branch is fine; rewriting shared history breaks other people's copies.

What triggers the Claude GitHub Action in the documented example workflow?

The if: line checks the comment body for @claude; the trigger phrase can be changed.
