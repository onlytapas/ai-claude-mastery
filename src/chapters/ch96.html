96.4Database and storage

The prototype wrote a CSV and forgot about it. A shared service needs to remember things: who the users are, what each person generated (so they can download it again), how much each person used today (for limits and cost reports), and switches such as "AI on or off". That's a database.

We use SQLite, a database stored in one file and built into Python, so there's nothing extra to install or run. It's a sound choice for an internal tool with a single server and a modest number of users. Move to a database server such as PostgreSQL when you need several app servers sharing one database, or a hosting platform with no persistent disk (96.10). The functions in store.py are the only place SQL lives, so that move touches one file.

store.py
"""store: SQLite storage for users, runs and settings. Standard library only."""
import hashlib
import json
import os
import secrets
import sqlite3
from contextlib import closing
from datetime import datetime, timezone

ROLES = ("viewer", "tester", "admin")

TABLES = """
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY,
    name TEXT UNIQUE NOT NULL,
    role TEXT NOT NULL,
    token_hash TEXT UNIQUE NOT NULL,
    active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS runs (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    created_at TEXT NOT NULL,
    day TEXT NOT NULL,
    mode TEXT NOT NULL,
    story_chars INTEGER NOT NULL,
    input_tokens INTEGER NOT NULL,
    output_tokens INTEGER NOT NULL,
    cases INTEGER NOT NULL,
    status TEXT NOT NULL,
    result_json TEXT
);
CREATE TABLE IF NOT EXISTS settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
"""


def db_path():
    return os.path.join(os.environ.get("DATA_DIR", "data"), "qa-helper.db")


def connect():
    os.makedirs(os.path.dirname(db_path()), exist_ok=True)
    conn = sqlite3.connect(db_path(), timeout=10)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode=WAL")
    conn.executescript(TABLES)
    return conn


def now():
    return datetime.now(timezone.utc)


def hash_token(token):
    # Tokens are long random strings, so a plain SHA-256 is enough.
    # Human-chosen passwords would need a slow hash such as argon2 or bcrypt.
    return hashlib.sha256(token.encode()).hexdigest()


def ping():
    with closing(connect()) as conn:
        conn.execute("SELECT 1").fetchone()


def add_user(name, role):
    if role not in ROLES:
        raise ValueError(f"role must be one of {ROLES}")
    token = "qah_" + secrets.token_urlsafe(32)
    with closing(connect()) as conn, conn:
        conn.execute("INSERT INTO users (name, role, token_hash, created_at) VALUES (?, ?, ?, ?)",
                     (name, role, hash_token(token), now().isoformat()))
    return token


def revoke_user(name):
    with closing(connect()) as conn, conn:
        return conn.execute("UPDATE users SET active = 0 WHERE name = ?", (name,)).rowcount == 1


def list_users():
    with closing(connect()) as conn:
        return [dict(r) for r in conn.execute(
            "SELECT name, role, active, created_at FROM users ORDER BY name")]


def user_for_token(token):
    with closing(connect()) as conn:
        row = conn.execute("SELECT * FROM users WHERE token_hash = ? AND active = 1",
                           (hash_token(token),)).fetchone()
        return dict(row) if row else None


def record_run(user_id, mode, story_chars, usage, cases, status, result=None):
    t = now()
    with closing(connect()) as conn, conn:
        cur = conn.execute(
            "INSERT INTO runs (user_id, created_at, day, mode, story_chars, input_tokens,"
            " output_tokens, cases, status, result_json) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)",
            (user_id, t.isoformat(), t.date().isoformat(), mode, story_chars,
             usage.get("input_tokens", 0), usage.get("output_tokens", 0), cases, status,
             json.dumps(result) if result is not None else None))
        return cur.lastrowid


def usage_today(user_id=None):
    sql = ("SELECT COUNT(*) AS requests, COALESCE(SUM(input_tokens), 0) AS input_tokens,"
           " COALESCE(SUM(output_tokens), 0) AS output_tokens FROM runs WHERE day = ?")
    args = [now().date().isoformat()]
    if user_id is not None:
        sql += " AND user_id = ?"
        args.append(user_id)
    with closing(connect()) as conn:
        return dict(conn.execute(sql, args).fetchone())


def usage_by_user_today():
    with closing(connect()) as conn:
        return [dict(r) for r in conn.execute(
            "SELECT u.name, COUNT(*) AS requests, SUM(r.input_tokens) AS input_tokens,"
            " SUM(r.output_tokens) AS output_tokens FROM runs r JOIN users u ON u.id = r.user_id"
            " WHERE r.day = ? GROUP BY u.name ORDER BY u.name", (now().date().isoformat(),))]


def recent_runs(user_id=None, limit=20):
    sql = ("SELECT r.id, u.name AS user, r.created_at, r.mode, r.cases, r.status,"
           " r.input_tokens, r.output_tokens FROM runs r JOIN users u ON u.id = r.user_id")
    args = []
    if user_id is not None:
        sql += " WHERE r.user_id = ?"
        args.append(user_id)
    sql += " ORDER BY r.id DESC LIMIT ?"
    args.append(limit)
    with closing(connect()) as conn:
        return [dict(r) for r in conn.execute(sql, args)]


def purge_results(days):
    """Delete stored results (not the usage numbers) older than `days` days."""
    cutoff = (now().date().toordinal() - days)
    cutoff_day = datetime.fromordinal(cutoff).date().isoformat()
    with closing(connect()) as conn, conn:
        return conn.execute("UPDATE runs SET result_json = NULL WHERE day < ? AND result_json"
                            " IS NOT NULL", (cutoff_day,)).rowcount


def get_setting(key, default):
    with closing(connect()) as conn:
        row = conn.execute("SELECT value FROM settings WHERE key = ?", (key,)).fetchone()
        return row["value"] if row else default


def set_setting(key, value):
    with closing(connect()) as conn, conn:
        conn.execute("INSERT INTO settings (key, value) VALUES (?, ?) ON CONFLICT(key)"
                     " DO UPDATE SET value = excluded.value", (key, value))


def get_run(run_id):
    with closing(connect()) as conn:
        row = conn.execute("SELECT id, user_id, result_json FROM runs WHERE id = ?", (run_id,)).fetchone()
        return dict(row) if row else None

Three design decisions are worth copying:

  • Tokens are stored as hashes. The database keeps a SHA-256 fingerprint of each token, not the token. If someone steals a backup, they can't sign in with what's in it. A long random token makes a fast hash acceptable; passwords that people choose would need a deliberately slow hash such as argon2 or bcrypt.
  • Usage numbers and results are separate. purge_results deletes stored test cases after a retention period but keeps the token counts, so cost reports still work. Stories can contain customer details or unreleased features; agree the retention period with whoever owns data protection (Chapter 132).
  • Write-ahead logging (PRAGMA journal_mode=WAL) lets readers and a writer work at the same time, which suits a web app with a few users.
Where the file lives matters

A container's own filesystem is thrown away when the container is replaced, which happens on every deploy. The database must live on a persistent volume: storage that outlives containers. That's why DATA_DIR is a setting, and why compose.yaml mounts a volume at /data. Forgetting this is the classic "all our users disappeared after the release" incident.

96.5Authentication and permissions

Two different questions, often confused:

  • Authentication: who are you? The app answers it by checking a token. No token, or a wrong one, gives status code 401 Unauthorized.
  • Authorisation (permissions): are you allowed to do this? The app answers it by checking the user's role. A valid user without the right role gets 403 Forbidden.

We use role-based access control: permissions belong to roles, and each user has one role. It's easy to explain to an auditor and easy to test.

# ---------- Authentication and permissions ----------
def current_user(authorization: str = Header(default="")):
    scheme, _, token = authorization.partition(" ")
    if scheme.lower() != "bearer" or not token:
        raise HTTPException(401, "Missing token. Send 'Authorization: Bearer <token>'.",
                            headers={"WWW-Authenticate": "Bearer"})
    user = store.user_for_token(token.strip())
    if user is None:
        raise HTTPException(401, "Invalid or revoked token.", headers={"WWW-Authenticate": "Bearer"})
    return user


def require(*roles):
    def check(user: dict = Depends(current_user)):
        if user["role"] not in roles:
            raise HTTPException(403, f"Your role ({user['role']}) can't do this.")
        return user
    return check

class StoryIn(BaseModel):
    story: str


def generate_for(user, body: StoryIn):
    story = body.story
    if not story.strip():
        raise HTTPException(422, "story is empty")
    limit = env_int("MAX_STORY_CHARS", 8000)
    if len(story) > limit:
        raise HTTPException(413, f"Story is {len(story)} characters; the limit is {limit}.")
    if store.get_setting("ai_enabled", "1") != "1":
        raise HTTPException(503, "AI generation is switched off by an admin. Try again later.")
    per_user = env_int("DAILY_REQUESTS_PER_USER", 40)
    if store.usage_today(user["id"])["requests"] >= per_user:
        raise HTTPException(429, f"You've used today's {per_user} generations. Limits reset at 00:00 UTC.")
    team = store.usage_today()
    if team["input_tokens"] + team["output_tokens"] >= env_int("DAILY_TOKEN_BUDGET", 2_000_000):
        raise HTTPException(503, "The team's daily AI budget is used up. Limits reset at 00:00 UTC.")

    mode = "fake" if fake_mode() else "live"
    started = time.monotonic()
    try:
        result, usage = (qahelper.fake_generate if mode == "fake" else qahelper.generate)(story)
    except Exception as exc:  # noqa: BLE001
        log.error("generate failed user=%s mode=%s error=%s", user["name"], mode, type(exc).__name__)
        store.record_run(user["id"], mode, len(story), {}, 0, "error")
        raise HTTPException(502, "The AI service didn't return a usable answer. Try again in a minute.")
    problems = qahelper.validate(result)
    status = "ok" if not problems else "invalid"
    run_id = store.record_run(user["id"], mode, len(story), usage, len(result.get("test_cases", [])),
                              status, result)
    ms = int((time.monotonic() - started) * 1000)
    # Log numbers, never the story text: stories can be confidential.
    log.info("generate user=%s mode=%s status=%s ms=%d in=%d out=%d run=%d", user["name"], mode,
             status, ms, usage["input_tokens"], usage["output_tokens"], run_id)
    if problems:
        raise HTTPException(502, {"message": "Output failed validation", "problems": problems})
    return run_id, mode, usage, result

How it works

  • current_user is a FastAPI dependency: any endpoint that lists it can't run until it has returned a user. It reads the bearer token from the Authorization header, the same pattern as most APIs (Chapter 98).
  • require("tester", "admin") builds a dependency that also checks the role. Permission rules sit next to each endpoint, where a reviewer can see them.
  • Asking for someone else's run returns 404, not 403. A 403 would confirm the run exists, letting a curious user count everyone's activity by trying numbers.
  • generate_for checks the cheapest things first (empty story, size, kill switch, quotas) and only then calls the model. Every refusal happens before any money is spent.
  • The log line records who, which mode, how long and how many tokens, but never the story. Logs are copied to many places and kept for a long time; they're the wrong home for confidential text (Chapter 95 covers logging in depth).

In a real company: use single sign-on

Hand-issued tokens are fine for learning and for a small team. In most companies the better answer is single sign-on (SSO): people sign in with their normal work account through your identity provider, and leavers lose access automatically when HR closes their account. Your platform or security team will tell you which method to use (often OpenID Connect, an identity layer built on OAuth). The role checks in server.py stay the same; only current_user changes to read the identity SSO provides. If you later add document retrieval, permissions must also apply to documents: a user must never get an answer built from a page they couldn't open themselves (Chapter 92).

The key never goes in these places

Not in the code, not in compose.yaml, not in app.env, not in the image (that's why .dockerignore excludes secrets and .env), not in CI logs, not in the frontend, and never pasted into a chat with an AI. An image pushed to a registry is a file anyone with pull access can unpack layer by layer.

Three more habits for the Anthropic key specifically:

  • A dedicated key in a dedicated workspace. In the Claude Console, create a workspace for this app and a key inside it. Workspaces group keys, members and limits, so you can give this app its own spend and rate limits without affecting anything else (Chapter 90).
  • Rotate on a schedule and on any doubt. To rotate: create a new key, write it to the secret file, restart the app (docker compose up -d --force-recreate app), check /readyz, then delete the old key in the Console.
  • Least privilege everywhere. The registry token can only read packages; the deploy SSH key belongs to a user that can only run Docker in one folder (least privilege).

96.8Cost and rate-limit protection

Every generation costs money, and the provider limits how fast you can call it (rate limits). One person pasting a 200-page specification, a browser tab stuck in a retry loop, or a script someone writes against your API can each burn a month's budget or starve everyone else. The defence is layers, each cheap, from the request inwards:

LayerWhereWhat it stopsWhat the user sees
Story size limit (MAX_STORY_CHARS)server.pyHuge inputs that cost a lot and rarely help413 "Story is N characters; the limit is 8000."
Per-user daily quota (DAILY_REQUESTS_PER_USER)server.pyOne person or script dominating429 "You've used today's 40 generations."
Team daily token budget (DAILY_TOKEN_BUDGET)server.pySlow, steady overspend across everyone503 "The team's daily AI budget is used up."
Kill switchAdmin, POST /admin/aiAnything unexpected, instantly, without a deploy503 "AI generation is switched off by an admin."
Output cap (max_tokens) and stop_reason checkqahelper.py (Chapter 94)Runaway answers502, logged
Workspace spend limit and rate limitsClaude ConsoleEverything above failing at once: the last line of defenceErrors from the API, logged as 502

A worked example, illustrative: Chapter 94 estimated about $0.084 per story with Opus 5.5 at $4 / $20 per million input / output tokens. A team budget of 2,000,000 tokens a day costs at most $40 even if every token were billed at the output price, and in practice about $34 at roughly 400 stories. Set the Console spend limit a little above your app's own monthly ceiling, so the app's friendly limits normally trigger first and the Console limit only catches bugs in them. Prices change, so check the pricing page before you set the numbers.

Make limits visible

GET /api/me returns today's usage and the limit, and the page shows "3/40 today". People ration what they can see. GET /admin/usage gives the admin a per-person view, which is usually the first thing a manager asks for.

Under the hood: why these limits live in the database, not in memory

A counter in a Python variable resets every time the app restarts, and every deploy restarts it, so a user could reset their quota by waiting for a release. It also breaks as soon as you run two copies of the app. Counting rows in the runs table survives restarts and works for every copy that shares the database. The cost is one small query per request, which is nothing next to a model call. For a high-traffic public API you'd use a dedicated rate limiter (often a token bucket in a shared cache, Chapter 90); for an internal tool the database is enough.

Failed calls count towards the user's quota on purpose. Otherwise a broken client retrying in a loop would hit the provider without ever being slowed down.

import argparse
import sqlite3
from contextlib import closing
from datetime import datetime, timezone
from pathlib import Path

import store


def check(path):
    with closing(sqlite3.connect(path)) as conn:
        if conn.execute("PRAGMA integrity_check").fetchone()[0] != "ok":
            raise SystemExit(f"{path} failed the integrity check")
        return {t: conn.execute(f"SELECT COUNT(*) FROM {t}").fetchone()[0] for t in ("users", "runs")}


def make_backup(keep=14):
    folder = Path(store.db_path()).parent / "backups"
    folder.mkdir(parents=True, exist_ok=True)
    dest = folder / f"qa-helper-{datetime.now(timezone.utc):%Y%m%d-%H%M%S}.db"
    with closing(store.connect()) as src, closing(sqlite3.connect(dest)) as out:
        src.backup(out)                      # safe while the app is running
    counts = check(dest)
    for old in sorted(folder.glob("qa-helper-*.db"))[:-keep]:
        old.unlink()
    return dest, counts


def restore(path):
    counts = check(path)                     # never restore a broken file
    with closing(sqlite3.connect(path)) as src, closing(store.connect()) as live:
        src.backup(live)
    return counts


if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("--keep", type=int, default=14)
    p.add_argument("--restore")
    a = p.parse_args()
    if a.restore:
        print(f"Restored {a.restore}: {restore(a.restore)}")
    else:
        dest, counts = make_backup(a.keep)
        print(f"Backup OK: {dest} ({dest.stat().st_size} bytes) {counts}")

Python's sqlite3 backup function copies a live database safely while the app keeps running; copying the file with cp while it's being written can produce a corrupt copy. Every backup is checked with PRAGMA integrity_check and its row counts printed, and --restore refuses a file that fails the check.

96.10Packaging with Docker

"It works on my machine" is the oldest excuse in software. A container fixes it by packaging the app with its exact Python version and libraries. You describe the package in a Dockerfile; Docker builds it into a container image, a read-only snapshot you can run anywhere Docker runs. The same image goes to the test run, the registry and the server, so what you tested is what you ship.

In everyday life

An image is a sealed meal kit: recipe, ingredients and quantities, identical every time. A container is one meal cooked from the kit. You can cook ten from the same kit, and throwing one away doesn't change the kit. Anything you want to keep, like the database, goes in the fridge (a volume), not on the plate.

Dockerfile
# One small image that runs the QA helper web service.
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    DATA_DIR=/data

WORKDIR /app

# Dependencies first: this layer is cached until requirements.txt changes.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Then the application code.
COPY qahelper.py store.py server.py manage.py backup.py ./
COPY static ./static

# Run as an ordinary user, not root, and give it a folder for the database.
RUN useradd --create-home --uid 10001 appuser \
    && mkdir -p /data \
    && chown appuser /data
USER appuser

EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
    CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=2)"]
CMD ["uvicorn", "server:app", "--host", "0.0.0.0", "--port", "8000"]

Line by line, the decisions that matter:

  • python:3.12-slim: an official Python image based on a small Debian. It's smaller than the full image, so faster to pull and with fewer packages to patch.
  • Copying requirements.txt and installing before copying the code means Docker reuses the dependency layer when only your code changes. Rebuilds take seconds, not minutes.
  • The container runs as appuser, not root, so a bug in the app can't change the system inside the container.
  • HEALTHCHECK asks /healthz every 30 seconds; after 3 failures in a row Docker marks the container unhealthy. The command uses Python's standard library because the slim image has no curl.
  • --host 0.0.0.0: inside a container the app must listen on all network interfaces, or nothing outside the container can reach it.

For an internal QA tool, the best host is usually the one your company already supports, because sign-in, networking and security review come with it. If there isn't one, a single small VM with Compose is the easiest option to understand and debug, and it's what this chapter builds. Move to a managed service with a managed database when you need more than one copy of the app or nobody wants to patch a server. Keep the tool on the company network or VPN unless there's a real reason to put it on the public internet: the safest public exposure is none.

HTTPS on a VM: a reverse proxy

Passwords and tokens must never cross a network in plain text, so the app needs HTTPS. Managed platforms provide it. On a VM, a reverse proxy sits in front of the app, holds the certificate and forwards requests. Caddy is one such proxy that obtains and renews certificates automatically when it knows the domain name; nginx and others work too, with more setup.

96.12CI/CD with GitHub Actions: tests → image → deploy

Continuous integration runs the tests on every change. Continuous deployment goes further: a change that passes is built and shipped by the pipeline, not by someone typing commands on a server. Nobody "forgets a step" at 6 p.m. on a Friday, and every release is traceable to a commit.

testEvery pull request and push: pytest and the dry-run eval
buildmain only: build image, start it, check /readyz, push to the registry
approveA named reviewer approves the production environment
deploySSH to the server: back up, start, wait for ready, or roll back
verifyCheck the public URL reports the new version
.github/workflows/deploy.yml
name: test-build-deploy

on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    env:
      QA_FAKE_MODEL: "1"            # tests never call Claude and need no key
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt -r requirements-dev.txt
      - run: python -m pytest -q
      - run: python eval_qahelper.py --dry-run

  build:
    needs: test
    if: github.event_name != 'pull_request' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write               # lets GITHUB_TOKEN push to ghcr.io
    steps:
      - uses: actions/checkout@v7
      - name: Image name (registry names must be lower case)
        run: echo "IMAGE=ghcr.io/${GITHUB_REPOSITORY,,}" >> "$GITHUB_ENV"
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build
        run: docker build -t "$IMAGE:$GITHUB_SHA" .
      - name: Smoke-test the image before publishing it
        run: |
          docker run -d --name smoke -p 8000:8000 \
            -e QA_FAKE_MODEL=1 -e APP_VERSION="$GITHUB_SHA" "$IMAGE:$GITHUB_SHA"
          for i in $(seq 1 20); do
            curl -fsS http://127.0.0.1:8000/readyz && break
            sleep 1
          done
          curl -fsS http://127.0.0.1:8000/readyz | grep "\"version\":\"$GITHUB_SHA\""
      - name: Show container logs if the smoke test failed
        if: failure()
        run: docker logs smoke
      - name: Push
        run: docker push "$IMAGE:$GITHUB_SHA"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production          # add required reviewers to this environment
    concurrency:
      group: production
      cancel-in-progress: false      # never stop a deploy half-way
    steps:
      - name: Deploy over SSH
        env:
          SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
          KNOWN_HOSTS: ${{ secrets.DEPLOY_KNOWN_HOSTS }}
          DEPLOY_HOST: ${{ vars.DEPLOY_HOST }}
        run: |
          mkdir -p ~/.ssh
          printf '%s\n' "$SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          printf '%s\n' "$KNOWN_HOSTS" > ~/.ssh/known_hosts
          ssh -i ~/.ssh/deploy_key "deploy@$DEPLOY_HOST" "/opt/qa-helper/deploy.sh $GITHUB_SHA"
      - name: Check it from the outside
        env:
          PUBLIC_URL: ${{ vars.PUBLIC_URL }}
        run: curl -fsS "$PUBLIC_URL/readyz" | grep "\"version\":\"$GITHUB_SHA\""

How it works

  • The test job needs no API key. QA_FAKE_MODEL=1 means the pipeline never calls Claude, costs nothing and can't leak a key. If you want a live quality check, add Chapter 95's eval gate as a separate, manually triggered job with its own key in an environment secret.
  • The image is tagged with the commit SHA ($GITHUB_SHA), never just latest. A tag that names one exact commit is what makes rollback possible: "go back to a1b2c3d" is precise; "go back to the previous latest" isn't.
  • The image is smoke-tested before it's pushed. A broken image never reaches the registry.
  • Permissions are minimal. The workflow can only read the repository; only the build job may write packages. GitHub's container registry, ghcr.io, accepts the automatic GITHUB_TOKEN for this, so there's no long-lived registry password to manage.
  • The deploy job uses an environment called production. Environments can require approval from named reviewers before the job runs, and environment secrets are only released to jobs that pass those rules. concurrency stops two deploys from running at once.

# Usage (on the server, in /opt/qa-helper):  ./deploy.sh IMAGE_TAG
# Backs up, starts the new version, waits until it reports ready, or rolls back.
set -euo pipefail
cd "$(dirname "$0")"
NEW_TAG="${1:?usage: ./deploy.sh IMAGE_TAG}"
HEALTH_URL="${HEALTH_URL:-http://127.0.0.1:8000/readyz}"
TRIES="${TRIES:-30}"
PREV_TAG="$(cat .current-tag 2>/dev/null || true)"

start() {
  IMAGE_TAG="$1" docker compose pull app
  IMAGE_TAG="$1" docker compose up -d
}

ready() {   # ready TAG: true when /readyz answers with that exact version
  for _ in $(seq 1 "$TRIES"); do
    if curl -fsS "$HEALTH_URL" 2>/dev/null | grep -q "\"version\":\"$1\""; then
      return 0
    fi
    sleep 2
  done
  return 1
}

echo "== Backing up the database before deploying $NEW_TAG"
docker compose exec -T app python backup.py || echo "WARNING: no backup (first deploy, or app down)"

echo "== Starting $NEW_TAG (currently live: ${PREV_TAG:-nothing})"
start "$NEW_TAG"
if ready "$NEW_TAG"; then
  if [ -n "$PREV_TAG" ] && [ "$PREV_TAG" != "$NEW_TAG" ]; then
    echo "$PREV_TAG" > .previous-tag
  fi
  echo "$NEW_TAG" > .current-tag
  echo "== OK: $NEW_TAG is live"
  exit 0
fi

echo "== FAILED: $NEW_TAG did not become ready"
docker compose logs --tail 30 app || true
if [ -n "$PREV_TAG" ]; then
  echo "== Rolling back to $PREV_TAG"
  start "$PREV_TAG"
  if ready "$PREV_TAG"; then
    echo "== Rolled back: $PREV_TAG is live again"
  else
    echo "== Rollback is ALSO unhealthy: call a human now"
  fi
fi
exit 1
deploy/rollback.sh
#!/usr/bin/env bash
# Usage: ./rollback.sh   puts the previous version back (it swaps the last two versions)
set -euo pipefail
cd "$(dirname "$0")"
PREV="$(cat .previous-tag 2>/dev/null || true)"
if [ -z "$PREV" ]; then
  echo "No previous version recorded. Run ./deploy.sh with a known-good tag instead."
  exit 1
fi
echo "Rolling back from $(cat .current-tag) to $PREV"
exec ./deploy.sh "$PREV"

A push to main now runs: test (about a minute), build and smoke test, then waits in the Actions tab with "Waiting for review" on the deploy job. A reviewer clicks Approve; the deploy job signs in, runs deploy.sh with the commit SHA, and the final step checks the public URL reports that SHA.

96.13Health checks and rollbacks

A health check is a small, cheap request that tells a machine whether the app is OK. There are two kinds, and mixing them up causes real outages:

Liveness: /healthzReadiness: /readyz
QuestionIs the process alive?Can it serve real requests right now?
ChecksNothing; just answersDatabase reachable; API key present (or fake mode); reports version
Used byDocker's HEALTHCHECK: restart if deaddeploy.sh, the pipeline, load balancers: send traffic only when ready
If it failsRestart the containerDon't switch to this version; roll back
Never call the model in a health check

Health checks run every few seconds, forever. A check that called Claude would cost money on every probe, use up rate limits, and, worse, mark your app "down" whenever the provider is slow, causing restarts that make things worse. /readyz checks that a key is configured, not that it's valid. After a key change, make one manual live generation as a smoke test.

deploy.sh uses readiness to decide. It doesn't just wait for "ready": it waits for "ready and reporting the new version", so it can't be fooled by the old container still answering. The bad deploy exits with status 1, so the GitHub Actions job goes red and the team is told, while users keep using the good version. Users may see errors for up to a minute while the bad version is tried; avoiding even that needs two copies running side by side (blue-green deployment) or a canary release, which most managed platforms offer and which is overkill for a dozen internal users.

Under the hood: what a rollback does not undo

Rolling back the image puts the old code back. It doesn't undo changes to data. If version B adds a database column and writes to it, version A must still work with that column present. The safe habit is "expand, then contract": first release a version that adds new things without removing old ones, and only remove the old ones in a later release once nobody will roll back past it. store.py uses CREATE TABLE IF NOT EXISTS, which is enough for this small app; bigger apps use a migration tool. This is also why deploy.sh takes a backup before starting the new version: if a release damages data, you have a copy from the minute before.

96.14Backups and production incidents

A backup you haven't restored is a hope, not a backup. Three rules:

  1. Automatic and frequent. deploy.sh backs up before every release; add a nightly one with cron on the server: 15 2 * * * cd /opt/qa-helper && docker compose exec -T app python backup.py.
  2. Off the machine. Backups on the same volume die with the server. Copy them out with docker compose cp app:/data/backups ./backups-copy and send that folder to storage your company backs up (an object storage bucket, a backed-up file share). Provider snapshots of disks (as on Render and Fly.io) help, but their own documentation says to keep your own backups too.
  3. Restore drill, monthly. Restore the latest backup into a scratch copy and check the counts. Write down how long it took: that's your real recovery time.

docker compose stop app
docker compose run --rm app python backup.py --restore /data/backups/qa-helper-20261109-105121.db

Common misunderstandings
"Deploying an AI app means hosting a model."
Most teams call a hosted model through an API. Deploying the application is about users, data, secrets, releases and recovery; model serving is a different job (Chapter 139).
"The API key is safe in the frontend if we minify the code."
Anything sent to the browser can be read. The key stays on the server; the browser only ever holds the user's own token.
"Environment variables in the Dockerfile are a fine place for the key."
They're baked into the image, which anyone with pull access can unpack. Secrets are supplied at run time, never at build time.
"The health check should test that Claude answers."
That costs money every few seconds and marks your app down whenever the provider is slow. Health checks test your app; a manual smoke test checks the model after changes.
"We have backups, so we're safe."
Only if they're off the machine and you've restored one. Test the restore and time it.
"Rollback undoes everything."
It restores the code, not the data. Design changes so the old version still works with the new data, and back up before each release.
"The Console spend limit is all the cost control we need."
It's the last line. When it triggers, everyone is blocked at once. Per-user and team limits in the app fail gently and fairly first.

96.16Review

Key takeaways
  • Deploying an AI application is mostly ordinary engineering around a model API: users, permissions, data, secrets, releases, recovery and cost.
  • Wrap the prototype's core instead of rewriting it; its tests keep protecting it.
  • Check identity (401) and role (403) on the server, for every endpoint; show model output as text, never as HTML.
  • Keep the API key in a mounted secret file on the server, in a dedicated workspace with Console limits; never in code, images, CI or logs.
  • Layer cost protection: input size, per-user quota, team budget, kill switch, then the Console spend limit.
  • Package with a Dockerfile and Compose, keep data on a volume, tag images with the commit SHA, and deploy through a pipeline with approval.
  • Separate liveness from readiness, never call the model in a health check, and let the deploy script roll back automatically.
  • Back up before every release and nightly, copy off the machine, and rehearse the restore.
Check yourself

A tester with a valid token calls POST /admin/ai. What should the server return?

401 means "I don't know who you are". The tester is authenticated; they lack permission, which is 403. (404 is used for other people's runs, so their existence isn't revealed.)

Where should the Anthropic API key live for the deployed app?

Compose files and images get shared and pushed. A secret supplied at run time, readable only by the app's user, never enters git or the registry.

Why doesn't /readyz make a small call to Claude to prove the key works?

Readiness checks your app's own dependencies cheaply. Check the model with a manual smoke test after key or model changes.

Why are images tagged with the commit SHA instead of latest?

latest moves with every push. deploy.sh records the current and previous SHAs, which is what makes rollback precise.

You plan to host on a managed container service whose container filesystem is temporary. What happens to the SQLite file?

Cloud Run's filesystem is in memory, and Azure Container Apps' container storage is temporary. Check each platform's storage model before choosing it.
