Your computer has a manager, the operating system, that runs every program and looks after every file. Normally you talk to it by clicking icons and menus. A terminal is a window where you talk to it by typing instead. Inside that window a program called the shell reads each line you type, works out what you mean, runs it, and prints the answer. Learning a handful of typed commands lets you understand exactly what tools like Claude Code are doing on your machine, and lets you do repetitive work faster and more reliably than clicking.

52.1What an operating system does

An operating system (OS) is the software that runs your computer. When you switch the machine on, the OS starts first, and everything else runs on top of it. It has four main jobs:

  • Run programs. It starts and stops apps, and shares the processor between them so that your browser, Slack and Excel can all run at once.
  • Look after files. It stores your documents on the disk, organised into folders, and remembers where everything is (Chapter 53).
  • Talk to hardware. Keyboard, screen, Wi-Fi, camera and printer all go through it. Apps ask the OS; they don't drive the hardware directly.
  • Keep users apart and safe. It knows who you are, which files you may read or change, and which actions need an administrator password (Chapter 56).

The core of an OS, the part that does this low-level managing, is called the kernel. Around the kernel sit the parts you see: the desktop, the file browser, the settings app, and the terminal.

In everyday life

Think of a large office building. The operating system is the building management: it runs the lifts, the power, the keycards and the post room. The tenants (your apps) get on with their work and ask building management whenever they need something. You can reach building management in two ways: through the friendly reception desk with signs and buttons (the graphical desktop), or by phoning the facilities line and saying exactly what you need (the terminal).

Three operating systems cover almost every computer you will meet at work:

macOS and Linux are cousins. Commands you learn on a Mac work almost the same on Linux, which matters because the machines that run your team's tests in CI are very often Linux. Windows is different, but it can run Linux inside it through WSL (52.5).

52.2Clicking versus typing: GUI and CLI

A GUI (graphical user interface, said "gooey") is what you use every day: windows, icons, menus and a mouse pointer. A CLI (command-line interface) is the older, text-only way: you type an instruction, press Enter, and read the reply as text.

GUI: good for

Discovering what's possible (the menus show you the options), visual work such as images and layouts, and one-off tasks. Easy to learn; hard to repeat exactly or to automate.

CLI: good for

Repeating work exactly, doing things to hundreds of files at once, working on remote servers that have no screen, and automation. Harder to start; every command can be saved, shared, scripted and reviewed.

Why should a tester or analyst care about the CLI in 2026? Four reasons:

  1. AI coding tools live there. Claude Code runs in a terminal and runs shell commands on your behalf (Chapter 63). When it asks "Allow rm -rf build?", you need to know what that means before you say yes.
  2. Test tools are command-line tools. npx playwright test, pytest, mvn test, git and curl are all typed commands.
  3. CI is a terminal with no human. A CI pipeline is just a list of shell commands run on a Linux machine. Reading its log is reading terminal output.
  4. Repeatability. "Run these three commands" is a reproducible bug report step. "Click around until it breaks" isn't.
Real-world example

A release checklist says "collect the last 200 lines of the server log and attach them to the Jira ticket". In a GUI you open the file, scroll to the end, select and copy. In a terminal it is one line, tail -n 200 app.log (Chapter 54), and the same line works on every server, every time, and can be put in a script.

52.3Terminal, shell, prompt, command: four words people mix up

These four words are used loosely, even by experienced engineers. Here is what each one precisely means.

Terminal (also "terminal emulator", "console")The window: an app that shows text and sends your key presses on. It doesn't understand commands itself.Terminal (macOS), Windows Terminal, GNOME Terminal, iTerm2, the terminal panel in VS Code
ShellThe interpreter: a program running inside the terminal that reads each line you type, works out what it means, runs it and returns the result.zsh, bash, PowerShell, cmd.exe

In everyday life

The terminal is a telephone handset. The shell is the operator on the other end of the line: it listens, understands your request and connects you to the right department (the program). The prompt is the operator saying "Go ahead". The command is what you say. You can swap handsets (a different terminal app) and keep the same operator, or keep the handset and talk to a different operator (a different shell).

Under the hood: why it's called a "terminal"

In the 1960s and 1970s, one large computer served many people. Each person sat at a terminal: a keyboard and a printer (later a screen) connected by cable to the distant computer. The terminal had no brain of its own; it only sent keystrokes and displayed replies. Today's terminal apps imitate, or "emulate", those devices in software, which is why they are formally called terminal emulators, and why some terminal settings still mention models like "xterm" or "VT100".

The "shell" got its name because it is the outer layer around the kernel: the part you touch. The first Unix shell was written in 1971; bash ("Bourne Again SHell", a pun on the earlier Bourne shell) arrived in 1989. On a Mac you can see which shells are installed by reading the file /etc/shells:

Terminal (macOS, real output)

# one of these shells.

/bin/csh
/bin/dash

/bin/tcsh

Lines starting with # are comments for humans. The rest are the full locations of each shell program on disk (paths are explained in Chapter 53).

52.4The shells you'll meet

There are many shells, but four cover nearly everything at work.

ShellWhere it's the defaultNotes for beginners
zsh ("zee-shell" or "zed-shell")macOS since macOS 10.15 Catalina (2019)Very close to bash for everyday commands. This book's examples are typed in zsh.
bashMost Linux systems; inside WSL; Git Bash on Windows; most CI runnersThe most common shell in documentation and scripts. macOS still includes an old version (3.2).
PowerShellWindowsA different design: commands are named Verb-Noun (Get-ChildItem) and pass structured objects rather than plain text. It accepts some familiar short names, such as cd and dir, as aliases.
Command Prompt (cmd.exe)Windows (older)The DOS-style shell. Still present, still used by some install instructions. Different commands again (dir, copy, del).

zsh and bash belong to the same family (both follow a standard called POSIX for their basic behaviour), so almost every command in Chapters 53–57 works the same in both. PowerShell and Command Prompt are different languages, and this book gives Windows notes where they differ.

To find out which shell you're using, type this and press Enter:

Terminal (macOS, real output)
echo $SHELL      # print the value of the SHELL variable
/bin/zsh
zsh --version    # ask zsh itself for its version
zsh 5.9 (arm64-apple-darwin25.0)
bash --version
GNU bash, version 3.2.57(1)-release (arm64-apple-darwin25)
...

echo prints whatever follows it. $SHELL is a variable, a named value the system keeps; the $ means "the value of" (Chapter 56). /bin/zsh is the location of your login shell. --version is an option that most programs understand; options are explained fully in Chapter 54. (The ... here stands for further licence lines that bash prints; it isn't part of a command.)

Windows: which one am I in?

If the prompt starts with PS, you're in PowerShell. If it looks like C:\Users\alex> with no PS, it's Command Prompt. Installation instructions often have separate lines for each, and using the wrong one gives telling errors. Claude Code's own troubleshooting notes that irm is not recognized means you're in Command Prompt rather than PowerShell, and The token '&&' is not a valid statement separator means you're in PowerShell rather than Command Prompt.

Don't change your shell yet

Apple documents how to change the default shell (chsh -s /bin/bash, or System Settings → Users & Groups → right-click your name → Advanced Options). Beginners have no reason to. Stay on the default until you know why you'd want something else.

52.5Opening a terminal on each system

macOS

  • Fastest: press Cmd+Space to open Spotlight, type Terminal, press Enter.
  • From Finder: Applications → Utilities → Terminal.
  • Keep it handy: while it's open, right-click its Dock icon → Options → Keep in Dock.

A window opens with a line of text ending in % and a blinking cursor. That's the prompt; the shell is waiting. Cmd+T opens a new tab, Cmd+N a new window, and Cmd++ / Cmd+- make the text bigger or smaller.

Linux

  • On Ubuntu and many other desktops, Ctrl+Alt+T opens a terminal.
  • Or open the app launcher (Activities on Ubuntu) and type Terminal.

The prompt usually ends in $. Copy and paste are Ctrl+Shift+C and Ctrl+Shift+V, because plain Ctrl+C means "cancel" in a terminal (52.7).

Windows

  • Press the Windows key, type Terminal, press Enter. On current Windows 11 this opens Windows Terminal, which can host PowerShell, Command Prompt and Linux shells in tabs.
  • Or right-click the Start button and choose Terminal.
  • If you only find "Windows PowerShell" or "Command Prompt", those work too.

Windows Terminal's default copy shortcut is Ctrl+Shift+C; new tab is Ctrl+Shift+T.

Windows: follow along with WSL or Git Bash

The commands in this Part are Unix-style. To type them exactly as shown on Windows, use either WSL (Windows Subsystem for Linux, which runs a real Linux such as Ubuntu inside Windows and appears as a tab in Windows Terminal) or Git Bash (a bash shell installed with Git for Windows). Claude Code's documentation recommends Git for Windows on native Windows so its Bash tool can be used. PowerShell notes are given where a beginner is likely to try a command there.

Other terminal apps

You don't have to use the built-in app. iTerm2, Ghostty, Warp and others are popular on macOS, and VS Code has its own terminal panel (Ctrl+`, the backtick key, on every system). They're all just different windows around the same shell. Claude Code works in all of these.

Don't type the prompt

Documentation often shows commands as $ npm install or % ls. The $ or % is the prompt, shown to say "this is a command". Type only what comes after it. Copying the $ gives an error such as command not found: $. In this book, code boxes show only what you type, and output appears on the lines underneath without a prompt.

Your prompt may look fancier

Colleagues often customise their prompts with colours, the current Git branch, or the time. Tools such as Oh My Zsh and Oh My Posh do this. The parts underneath are the same. If your prompt shows something odd, don't worry: it's decoration.

52.7Talking to the shell: typing, Enter, output and getting unstuck

Type a command, press Enter, read the output. Here are four harmless first commands with real output (the user name has been changed to alex; yours will show your own):

Terminal (macOS, real output)
whoami                 # who am I logged in as?
alex
date                   # current date, time and time zone
Mon Nov  9 14:43:23 IST 2026
echo Hello, terminal   # print the words back
Hello, terminal
hostname               # this computer's network name
Alexs-MacBook-Air

Notice the pattern: the command on one line, its output underneath, then a fresh prompt (not shown) waiting for the next one. IST is the time zone the computer is set to; yours will show your own.

The golden rules of reading output

  • No news is good news. Many commands print nothing when they succeed. A new prompt with no message usually means "done, no problems".
  • Errors name the culprit. Mistype whoami and zsh says exactly what went wrong:
Terminal (zsh)
whoam
zsh: command not found: whoam

Read it left to right: who is complaining (zsh), what went wrong (command not found) and which word caused it (whoam). bash puts it the other way round: bash: whoam: command not found. PowerShell prints a longer red message starting The term 'whoam' is not recognized. Chapter 62 is entirely about reading errors.

Keys that save you

KeyWhat it does
Ctrl+CCancel the running command and get your prompt back. On a Mac this is the Control key, not Cmd. Your first rescue move when something seems stuck.
↑ / ↓Step back and forward through commands you typed before, so you can rerun or edit them.
TabComplete a command or file name. Type Docu and press Tab; the shell fills in Documents/. Fewer typos.
Ctrl+A / Ctrl+EJump to the start / end of the line (zsh and bash).
Ctrl+L or clearClear the screen. Nothing is undone; it only tidies the window. On macOS Terminal, Cmd+K also clears.
Ctrl+D or exitClose the shell (and usually the tab).
qQuit a full-screen viewer such as man or less (Chapter 54).
In everyday life

Ctrl+C is the "stop" button on a lift. If you got in by mistake or it's taking far too long, you press it. It's always safe to try, and it's the first thing to try when a terminal "freezes".

Under the hood: what "running a program" means

When you type whoami, the shell doesn't know the answer itself. It searches a list of folders (the PATH, Chapter 56) for a program file called whoami, asks the kernel to start it as a new process, connects that process's output to your terminal, and waits for it to finish. When the program ends it hands back a number called an exit code: 0 means success, anything else means some kind of failure (Chapter 55). Only then does the shell print a new prompt.

A few commands, such as cd and echo, are built into the shell instead of being separate programs. You can ask which is which with type:

Terminal (zsh, real output)
type cd pwd
cd is a shell builtin
pwd is a shell builtin

52.8Safety: the terminal does exactly what you say

The terminal is powerful because it doesn't second-guess you, and that is also its risk.

  • There's usually no undo and no Bin. A file deleted with rm doesn't go to the Trash or Recycle Bin (Chapter 54).
  • No "Are you sure?". Most commands just act.
  • Pasted commands run with your permissions. A command copied from a web page can read, change or delete anything you can. Read before you paste, and never paste one you don't understand from an untrusted source.
  • Watch for sudo and #. sudo runs a command as the administrator, and a # prompt means you already are one. Both remove most safety nets (Chapter 56).
Real-world example

Claude Code runs shell commands for you, but by default it asks permission first, showing the exact command. A tester who can read rm -rf test-results ("delete the test-results folder and everything in it, without asking") can approve it with confidence. One who can't is either blocking all useful work or approving blindly. That gap is why this Part exists. Permission settings are covered in Chapter 78.

Learning the terminal used to be optional for testers who didn't write automation. With AI agents now proposing and running commands, we think basic terminal literacy is becoming as important as reading a bug report: not to type everything yourself, but to supervise what is typed on your behalf.

Common misunderstandings
"The terminal and the shell are the same thing."
The terminal is the window; the shell is the program inside that understands commands. You can run different shells in the same terminal.
"The terminal is for programmers only."
It is a different way of using the same computer. Testers, analysts and support staff use it to read logs, run test suites, and check servers.
"No output means it didn't work."
Usually the opposite. Many commands are silent on success and only speak when something goes wrong.
"Ctrl+C copies text in the terminal."
In a terminal, Ctrl+C cancels the running command. On macOS copy is Cmd+C; on Linux and in Windows Terminal it's Ctrl+Shift+C.
"I can break my computer by typing a wrong command."
A mistyped command almost always just gives "command not found". Real damage needs a real, destructive command (like deleting files), which is why you learn to read commands before running them.

52.9Review

Key takeaways
  • The operating system runs programs, manages files, talks to hardware and keeps users apart. macOS and Linux are Unix-like cousins; Windows is different.
  • A GUI is for clicking; a CLI is for typing. The CLI is repeatable, scriptable and where AI coding tools, test runners and CI live.
  • Terminal = the window. Shell = the interpreter inside it. Prompt = "ready". Command = what you type.
  • zsh is the macOS default, bash is common on Linux and CI, PowerShell and Command Prompt are on Windows.
  • The prompt shows user, computer and current folder; don't copy the $ or % from documentation.
  • Ctrl+C cancels, ↑ recalls, Tab completes. Read every command before you run it.
Check yourself

What is the shell?

The window is the terminal; the hardware-controlling core is the kernel. The shell is the interpreter in between.

Your prompt reads alex@build-server:~#. What should catch your attention?

A # at the end of a Unix prompt signals root. ~ just means the home folder.
