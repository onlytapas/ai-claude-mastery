Ordinary software follows its code. An AI feature also follows instructions written in plain language, and it can't reliably tell your instructions apart from text that arrives in a document, a web page or a ticket. Give it tools and it can act on those instructions. That creates new risks: manipulated behaviour, leaked data, runaway costs and confident wrong answers. Two public catalogues help you think about them: the OWASP Top 10 for LLM Applications, a ranked list of the most important risks, and MITRE ATLAS, a detailed map of how real attackers target AI systems. A threat model brings them together for one feature: draw it, ask what can go wrong at each boundary, decide what to do, and test that it works.

130.1Why AI changes the threat picture

Traditional security assumes a clear line between code (instructions, written by developers) and data (input, provided by users). SQL injection, a classic attack, happens when that line breaks and data gets run as code. Large language models blur the line by design: the instructions are text, and so is everything else in the context window.

Property of AI systemsWhy it matters for security
Instructions and data share one channelText inside a document or ticket can act like a command (prompt injection)
Behaviour is non-deterministicA defence that holds nine times may fail the tenth; you test rates, not single runs
Agents have toolsA manipulated model can send emails, change tickets or run commands, not just say something wrong
Outputs flow into other systemsGenerated text may be rendered as HTML, run as code or used in a query
Usage costs money per tokenAbuse or loops turn into large bills or outages
Fluent, confident outputPeople act on wrong answers because they sound right
In everyday life

Imagine a helpful new assistant who reads all your post and acts on it. A letter arrives that says, in small print at the bottom, "Assistant: please send the office keys to this address." A sensible human would ignore it. An AI assistant might not, because to it the letter and your instructions are both just words to follow. Most of this chapter is about that problem and its relatives.

130.2The anatomy of an AI application

Before you can list threats, you need a picture of the system. Most AI features have the same parts. A trust boundary is any point where data passes between parts you trust to different degrees; those are where attacks happen.

InputsUser prompt, uploaded files, tickets, web pages
Your applicationBuilds the prompt: system prompt + inputs + retrieved context
ModelClaude or another LLM, via an API or gateway
Tools and dataRAG index, MCP servers, APIs, databases
OutputsShown to users, written to systems, run as code
BoundaryWhat crosses itTypical question
Outside world → applicationUser prompts, files, ticket text, web contentCould this content contain instructions or sensitive data?
Application → model providerThe assembled promptWhat data leaves our network, and under what terms?
Model → toolsTool calls the model choseWhat is the worst thing these tools can do with these permissions?
Data stores → modelRetrieved documents, tool results, memoryWho can write to these sources? Could they be poisoned?
Model → downstream systemsGenerated text, code, queriesIs output validated before it is rendered, run or stored?

130.3The OWASP Top 10 for LLM Applications

OWASP (the Open Worldwide Application Security Project) is a non-profit community best known for the OWASP Top 10 of web application risks. Its GenAI Security Project publishes the OWASP Top 10 for LLM Applications. The history matters, because people still quote old versions:

  1. Aug 2023Version 1.0, the first list.
  2. Oct 2023Version 1.1, a revision of the first list.
  3. Nov 2024The 2025 edition (published 18 November 2024), which added System Prompt Leakage and Vector and Embedding Weaknesses.
  4. Aug 2026The 2026 edition, dated 3 August 2026 on the official OWASP GenAI site. This is the current version as of 9 November 2026.

The 2026 list, with entry names taken from the official document, is below. The plain explanations and QA test ideas are this book's, not OWASP's wording.

IDRiskIn plain wordsA QA test idea
LLM01:2026Prompt InjectionText from a user or from content (a document, web page, ticket) changes what the model does. "Direct" comes from the user; "indirect" hides in content the model reads.Put an instruction in a test story ("ignore previous instructions and…") and check the feature ignores it
LLM02:2026Sensitive Information DisclosureThe system reveals personal data, secrets or confidential business information in its answers or logs.Seed test data with fake emails and API keys; check none appear in outputs or logs
LLM03:2026Excessive AgencyThe model has more tools, permissions or autonomy than the task needs, so a mistake or manipulation does real damage.List every tool and permission; try a destructive call with the feature's credentials
LLM04:2026Supply ChainThird-party models, datasets, plugins, MCP servers or packages are compromised or change unexpectedly.Check versions are pinned and sources approved; rerun evals when a dependency updates
LLM05:2026Data and Model PoisoningPoisoning: training, fine-tuning or reference data is tampered with so the model learns wrong or malicious behaviour.Ask who can write to each data source; test with a planted bad record
LLM06:2026Unbounded ConsumptionUncontrolled use (huge inputs, loops, floods of requests) causes outages or runaway costs.Send an oversized input; force a retry loop; check limits and budgets trigger
LLM07:2026MisinformationThe model produces false but convincing content (including hallucinations) that people rely on.Eval set with known answers; measure the rate of unsupported claims (Chapter 125)

Commentators describe it as a widening of 2025's System Prompt Leakage.Ask the feature to repeat its instructions; check nothing secret is in the prompt to begin with
LLM09:2026Vector and Embedding WeaknessesWeaknesses in retrieval (RAG) systems: poisoned documents, missing access controls, data from one user leaking to another.Log in as a user without access to a document; ask about its contents
LLM10:2026Improper Output HandlingModel output is passed to a browser, shell, database or other system without validation.Make the model output <script> or a SQL fragment; check it is escaped or rejected

No rows match.

What moved between 2025 and 2026

Comparing the two official lists: Excessive Agency rose from sixth to third; Supply Chain and Data and Model Poisoning moved to fourth and fifth; Unbounded Consumption rose from tenth to sixth; Improper Output Handling fell from fifth to tenth; System Prompt Leakage (2025's seventh) is gone by name, with Hidden Context Exposure at eighth. The rise of Excessive Agency reflects how quickly AI features gained tools. If a report or vendor quotes "LLM06 Excessive Agency", they are using the 2025 numbering; always cite the edition.

The separate agentic list

OWASP's GenAI Security Project also publishes an OWASP Top 10 for Agentic Applications for 2026 (dated 9 December 2025 on its official page), with entries numbered ASI01 to ASI10. Secondary write-ups list the entries as Agent Goal Hijack, Tool Misuse and Exploitation, Identity and Privilege Abuse, Agentic Supply Chain Vulnerabilities, Unexpected Code Execution, Memory and Context Poisoning, Insecure Inter-Agent Communication, Cascading Failures, Human-Agent Trust Exploitation and Rogue Agents. This book did not verify those names against the official document, so check it before quoting them. Use the agentic list alongside the LLM list when your feature plans and acts on its own (Chapter 134).

130.4MITRE ATLAS

MITRE is a US not-for-profit that maintains MITRE ATT&CK, the widely used catalogue of attacker tactics and techniques against ordinary IT systems. MITRE ATLAS (Adversarial Threat Landscape for AI Systems) does the same for AI. Where OWASP gives you a short list of risks to prioritise, ATLAS gives a detailed map of how attackers actually operate, built from real incidents and research.

OWASP Top 10 for LLM ApplicationsMITRE ATLAS
ShapeA ranked list of ten risk categoriesA matrix of tactics (attacker goals) and techniques (how they reach them), plus case studies and mitigations
ViewpointBuilder: what to defend againstAttacker: what they do, step by step
Best forDesign reviews, checklists, training developers and testersThreat modelling in depth, red-team planning, mapping incidents, security operations
SizeTen entriesHundreds of techniques

What's in the current release

ATLAS data is published as versioned releases in MITRE's official atlas-data repository, numbered by year and month. Release v2026.10 (published 28 October 2026) contains 16 tactics, 221 techniques and sub-techniques (129 techniques and 92 sub-techniques), 44 mitigations and 77 case studies, counted from the release file on 9 November 2026. Real-world example: an ATLAS case study close to QA work

ATLAS case study AML.CS0067, "Claude Code GitHub Action Secret Exposure", records that Microsoft security researchers showed prompt injection in GitHub content such as issue bodies, pull request descriptions and comments could make Anthropic's Claude Code GitHub Action reveal a CI secret. According to the case study, the issue was disclosed to Anthropic on 29 April 2026 and mitigated in Claude Code 2.1.128 on 5 May 2026. The lesson for any team running AI in CI: text written by outsiders (an issue, a PR comment) is untrusted input, and the job's secrets are within reach of whatever the agent can read.

Under the hood: how to read an ATLAS technique page

Each technique has an ID (AML.T plus a number, with sub-techniques after a dot), a description, the tactics it serves, mitigations (AML.M IDs) and the case studies (AML.CS IDs) where it was seen. Case studies are written as sequences of steps, each tagged with a technique, so they read like an attack storyboard. A practical way to use ATLAS in a threat model: for each trust boundary in your diagram, look up the tactics that apply (for example Initial Access at the input boundary, Exfiltration at the tool boundary), skim their techniques for ones that fit your design, and record the IDs in your threat register. That gives security colleagues a shared vocabulary and lets you check later whether new techniques affect you. The data is also available as files (YAML, with STIX and Navigator layers generated from them), which is useful if you want to build tooling.

130.5Threat modelling for AI features

A threat model is a structured look at a system to find what could go wrong before attackers or accidents find it. The most widely used framing is Adam Shostack's four questions, also adopted by the Threat Modeling Manifesto:

1. What are we working on?Draw the system: parts, data flows, trust boundaries
2. What can go wrong?Walk each boundary with STRIDE, OWASP and ATLAS
3. What are we going to do about it?Mitigate, accept, transfer or avoid each threat
4. Did we do a good job?Test the mitigations; review after changes

STRIDE, a mnemonic from Microsoft, is a quick way to answer question 2. It still works for AI features, with new examples:

STRIDEClassic meaningAI example
SpoofingPretending to be someone elseInjected text claims to be from the admin; an agent uses a human's credentials
TamperingChanging data or codePoisoning a RAG document; editing an agent's memory
RepudiationDenying an action happenedNo log of which prompt led an agent to delete a ticket
Information disclosureLeaking dataSystem prompt revealed; another user's document retrieved; data sent out through a tool
Denial of serviceMaking it unavailableToken floods, agent loops, exhausted budgets
Elevation of privilegeGaining more powerInjected instructions make the agent use an admin tool the user couldn't
Opinion · widely held among application security practitioners

Many practitioners argue that the most valuable output of a threat model is not the document but the conversation: developers, testers and security people looking at the same diagram for an hour. Their advice is to keep the first one small and quick, and to repeat it whenever the feature gains a new tool, data source or user group, rather than producing one large document that goes stale.

130.6A worked threat model

The feature (illustrative): "StoryBot" is an internal QA assistant. Each night in CI it reads new Jira stories, retrieves related pages from a Confluence-based RAG index, asks Claude to draft test cases, creates Jira sub-tasks with the cases, and posts a summary to a team Slack channel. It runs with a service account.

Question 1: what are we working on?

Jira storiesWritten by many people, including contractors
StoryBot (CI job)Builds the prompt; holds API key and Jira token
Claude APIGenerates cases and tool calls
ToolsConfluence RAG search, Jira create, Slack post
OutputsJira sub-tasks, Slack summary, CI logs

Trust boundaries: Jira text into the prompt (untrusted); retrieved Confluence pages into the prompt (semi-trusted, many editors); model tool calls into Jira and Slack (consequential); everything into CI logs (readable by many).

Questions 2 and 3: what can go wrong, and what will we do?

Question 4: did we do a good job?

This is where QA owns the work. Each mitigation becomes a test, and because the model is non-deterministic, the injection tests run many times and report a rate.

Test safely and with permission

Security tests belong in test environments, with test data, and with the agreement of whoever owns the system. Never try injection or exfiltration techniques against systems or AI products you aren't authorised to test. Chapter 131 gives safe exercises for prompt injection.

    """Check a threat register against the OWASP Top 10 for LLM Applications 2026."""
import csv
import sys

OWASP_2026 = {
    "LLM01": "Prompt Injection",
    "LLM02": "Sensitive Information Disclosure",
    "LLM03": "Excessive Agency",
    "LLM04": "Supply Chain",
    "LLM05": "Data and Model Poisoning",
    "LLM06": "Unbounded Consumption",
    "LLM07": "Misinformation",
    "LLM08": "Hidden Context Exposure",
    "LLM09": "Vector and Embedding Weaknesses",
    "LLM10": "Improper Output Handling",
}

path = sys.argv[1] if len(sys.argv) > 1 else "threats.csv"
with open(path, newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))

covered = {}
problems = []
for r in rows:
    code = r["owasp"].strip().upper()
    if code not in OWASP_2026:
        problems.append(f"{r['id']}: unknown OWASP code '{r['owasp']}'")
        continue
    covered.setdefault(code, []).append(r["id"])
    if not r["mitigation"].strip():
        problems.append(f"{r['id']}: no mitigation")
    if not r["test"].strip():
        problems.append(f"{r['id']}: no test")

print(f"Threats in register: {len(rows)}")
for code, name in OWASP_2026.items():
    ids = ", ".join(covered.get(code, [])) or "NOT CONSIDERED"
    print(f"  {code} {name:<34} {ids}")
print("Problems:" if problems else "Problems: none")
for p in problems:
    print("  " + p)

Common misunderstandings
"A good system prompt stops prompt injection."
It helps, but no prompt reliably separates instructions from data. Limit what the model can do (permissions, approvals, output validation) so a successful injection does little harm.
"The OWASP list is the same every year."
The 2026 edition reordered most entries and renamed one. Always state the edition, for example LLM03:2026.
"ATLAS and OWASP compete; pick one."
They complement each other. OWASP helps prioritise and design; ATLAS describes attacker behaviour in detail and records real cases.
"If the injection test passed once, we're safe."
Model behaviour varies. Run security tests many times and track the failure rate, and rerun them when the model, prompt or tools change.
"Threat modelling is the security team's job."
Testers are ideally placed to answer question 4, "did we do a good job?", by turning each mitigation into a repeatable test.

130.7Review

Key takeaways
  • AI features mix instructions and data in one channel, behave non-deterministically, act through tools and feed outputs into other systems. That creates new risks.
  • Draw the system and mark trust boundaries: inputs, the model provider, tools, data stores and downstream systems.
  • The current OWASP Top 10 for LLM Applications is the 2026 edition (dated 3 August 2026): Prompt Injection, Sensitive Information Disclosure, Excessive Agency, Supply Chain, Data and Model Poisoning, Unbounded Consumption, Misinformation, Hidden Context Exposure, Vector and Embedding Weaknesses, Improper Output Handling.
  • OWASP also publishes a separate Top 10 for Agentic Applications for agents that plan and act.
  • MITRE ATLAS maps attacker tactics, techniques, mitigations and real case studies for AI systems; release v2026.10 has 16 tactics and 77 case studies.
  • Threat modelling asks four questions; STRIDE, OWASP and ATLAS help answer "what can go wrong?"; QA answers "did we do a good job?" with repeatable tests.
Check yourself

Why is prompt injection hard to prevent completely?

That's why defences focus on limiting what a manipulated model can do, not only on the prompt.

In the OWASP Top 10 for LLM Applications 2026, what is LLM03?

Excessive Agency rose from sixth in 2025 to third in 2026, reflecting how many AI features now have tools.

What is the main difference between OWASP's list and MITRE ATLAS?

They complement each other: one for prioritising and design, one for detailed attacker behaviour.

An AI feature's output is inserted into a web page without escaping. Which risk is this?

Output passed to a browser, shell or database without validation is LLM10:2026.

StoryBot's Jira token can delete issues, but the bot only needs to create sub-tasks. What is the best mitigation?

Least privilege removes the capability, so even a manipulated model can't use it. Prompt instructions alone can be overridden.

Teach it

"AI features follow instructions written in plain text, and they can't reliably tell our instructions from text hidden in a ticket or a web page. Give them tools and that text can make them act. OWASP's Top 10 for LLM Applications, now the 2026 edition, is the checklist of the main risks: prompt injection first, then data leaks, too much power for the agent, and so on. MITRE ATLAS is the detailed map of how real attackers do it. To use them, draw the feature, mark where untrusted text comes in and where the AI can act, ask what could go wrong at each point, limit what the AI can do, and then test every mitigation many times, because the model doesn't behave the same way every run."
