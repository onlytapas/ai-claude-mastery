61.1What version control is

Most people have a folder somewhere that looks like this: test-plan.docx, test-plan-v2.docx, test-plan-v2-FINAL.docx, test-plan-v2-FINAL-really.docx. That is version control done by hand. It works badly: nobody knows which file is current, what changed between versions, or who changed it.

A version control system does the same job properly. It keeps one copy of each file in your folder, plus a hidden history of every saved version. Git is by far the most widely used one. It was written by Linus Torvalds in 2005 to manage the Linux kernel, and it is free and open source.

In everyday life

Think of a video game with save points. You play, reach a safe spot, and save. If things go badly later, you load the save and try again. A commit is a save point for a folder, with a label you write yourself ("Add login test cases"). Unlike most games, Git keeps every save forever, and you can open two save files side by side to see exactly what changed.

Git and GitHub are different things

GitGitHub
What it isA program on your computerA website and service (owned by Microsoft)
What it doesRecords history, branches and merges, entirely offlineHosts copies of repositories online, plus pull requests, issues, code review and automation (GitHub Actions)
Do you need an account?NoYes
AlternativesFew in practice; Git dominatesGitLab, Bitbucket, Azure DevOps and others host Git repositories too

You can use Git without GitHub (the lab in this chapter does). You can't really use GitHub without Git, because the repositories it stores are Git repositories.

Real-world example

Your team's Playwright tests live in a Git repository on GitHub. When a test starts failing on Tuesday, you can ask Git "what changed in the tests folder since Monday, and who changed it?" and get an exact answer in seconds. Without version control, you would be comparing folders by eye.

61.2Install Git and set it up once

First check whether Git is already installed:

Terminal
git --version
Output (macOS)
git version 2.54.0 (Apple Git-157)

Any recent version is fine; your number will differ. If you see command not found instead (Chapter 62 explains that message), install it:

  • macOS: run xcode-select --install to get Apple's command-line tools, which include Git. On some Macs, typing git alone pops up the same installer. If you use Homebrew (Chapter 58), brew install git also works.
  • Linux (Debian or Ubuntu): sudo apt install git. Other distributions use their own package manager.
  • Windows: install "Git for Windows" from git-scm.com. It includes Git Bash, a terminal where every command in this chapter works. Inside WSL, use the Linux instructions.

Tell Git who you are

Every commit records an author name and email. Set them once per computer. The --global option means "for every repository for this user":

Terminal (once per computer)
git config --global user.name "Asha Tester"
git config --global user.email "asha@example.com"
git config --global init.defaultBranch main   # call the first branch "main"

These commands print nothing when they succeed. That's normal for many terminal commands: silence means success. Check what you set with git config user.name, which prints the name back. Use the same email as your GitHub account if you plan to use GitHub, so your commits are linked to your profile.

Where this is stored

Global settings go into a text file in your home folder, ~/.gitconfig. You can read it with cat ~/.gitconfig. Settings made without --global, inside a repository, apply to that repository only.

61.3Repositories and the three areas

A repository (or "repo") is a folder whose history Git is tracking. You turn an ordinary folder into one with git init:

Terminal
mkdir -p ~/git-practice/qa-notes
cd ~/git-practice/qa-notes
git init -b main
Output
Initialized empty Git repository in /Users/asha/git-practice/qa-notes/.git/

-b main names the first branch main. The message tells you Git created a hidden folder called .git. That folder is the repository: the whole history lives there. Never edit it by hand, and never delete it unless you want to throw the history away. (ls -a shows it; Chapter 53 explains hidden files.)

The command you will run most is git status. It answers "what's going on here?"

Output of git status in a brand-new repository
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

The three areas

A change moves through three places before it is part of the history. This is the single most important idea in Git:

Working folderThe files you see and edit. Changes here are not saved in Git yet.
Staging areagit add puts chosen changes here: "these go in the next snapshot".
Repositorygit commit saves everything staged as one permanent snapshot.

The middle step, the staging area, exists so you can choose. If you fixed a test and also changed a config file for your own experiments, you can stage only the test and commit it, leaving the config change out.

In everyday life

Packing a parcel. Your desk is the working folder: things everywhere. The open box is the staging area: you put in only what belongs in this delivery. Taping the box shut and writing the label is the commit. Once sent, that parcel and its label are on record for good.

61.4Your first commits

Create a file and ask Git what it thinks:

Terminal
printf '# QA notes\n\nTest notes for the login page.\n' > README.md
git status
Output
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md

nothing added to commit but untracked files present (use "git add" to track)

Untracked means Git can see the file but has never saved it. Git's messages usually tell you the next command to run, in brackets. Stage the file, then check again:

Terminal
git add README.md
git status
Output
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md

"Changes to be committed" is the staging area. Now take the snapshot. -m gives the commit message:

Terminal
git commit -m "Add README with project purpose"
Output
[main (root-commit) 4194538] Add README with project purpose
 1 file changed, 3 insertions(+)
 create mode 100644 README.md

Reading that output piece by piece: main is the branch; root-commit means it's the very first commit; 4194538 is the start of the commit's ID (a unique code Git calculates from the contents, so yours will differ); then a summary: one file, three lines added, and a new file created (100644 just means "an ordinary, non-executable file").

Looking at history

Terminal
git log
Output
commit 4194538e5bd53d8031cc6305f5ed1c533aac4c36
Author: Asha Tester <asha@example.com>
Date:   Mon Nov 9 14:48:01 2026 +0530

    Add README with project purpose

The full ID is 40 characters; Git accepts the first seven or so when you refer to a commit. For a compact view, use git log --oneline, which prints 4194538 Add README with project purpose. If git log fills the screen and shows a : at the bottom, you are in a pager: press q to get back to the prompt.

Seeing what changed with git diff

Now edit the file and ask Git what is different from the last commit:

Terminal
printf '# QA notes\n\nTest notes for the login page and the checkout page.\n' > README.md
git diff
Output
diff --git a/README.md b/README.md
index 3c01ebf..aa77bb8 100644
--- a/README.md
+++ b/README.md
@@ -1,3 +1,3 @@
 # QA notes

-Test notes for the login page.
+Test notes for the login page and the checkout page.

This is a diff. Lines starting with - were removed, lines with + were added, and lines with a space are unchanged context. @@ -1,3 +1,3 @@ means "this piece covers lines 1 to 3 in both versions". A changed line shows as one removal plus one addition. Learning to read diffs is the most useful Git skill for a tester: it's how you review what a developer, or Claude, actually changed.

Terminal
git commit -am "Mention checkout page in README"
Output
[main 761ccc2] Mention checkout page in README
 1 file changed, 1 insertion(+), 1 deletion(-)

-a stages every change to files Git already tracks, then commits, in one step. It does not include brand-new (untracked) files; those always need git add first.

Undoing things before they're committed

You want to…CommandWhat happens
Throw away edits to a file and go back to the last commitgit restore README.mdThe file returns to its committed version. The edits are gone for good, so be sure.
Take a file out of the staging area but keep your editsgit restore --staged draft.txtThe file goes back to "not staged" (or "untracked" if it's new). Nothing is lost.
See what you have stagedgit diff --stagedLike git diff, but for the staging area
See one commit in detailgit show 761ccc2The message plus its diff
Writing good commit messages

Write the first line as a short instruction of what the commit does: "Add boundary tests for coupon expiry", not "changes" or "fixed stuff". Keep it under about 50 characters. If it needs explaining, leave a blank line and add a paragraph about why. Your future self, hunting for the commit that broke a test, will thank you. Small commits that each do one thing are far easier to review and undo than one giant commit at the end of the week.

61.5Branches and merges

A branch is a separate line of commits. You create one to work on something without disturbing main, then bring the work back by merging. Technically a branch is only a movable label pointing at a commit, which is why creating one is instant.

Terminal
git switch -c add-login-cases          # create the branch and move onto it
printf 'TC-01 Valid login shows dashboard\nTC-02 Wrong password shows error\n' > login-cases.txt
git add login-cases.txt
git commit -m "Add first login test cases"
git branch                             # list branches; * marks the current one
Output
Switched to a new branch 'add-login-cases'
[add-login-cases 769903f] Add first login test cases
 1 file changed, 2 insertions(+)
 create mode 100644 login-cases.txt
* add-login-cases
  main

Now switch back to main and look at the folder. login-cases.txt has disappeared, because that file only exists on the other branch. Git changes the files in your folder to match whichever branch you are on. (Older tutorials use git checkout for this; git switch is the newer, clearer command for changing branches.)

Terminal
git switch main
ls
git merge add-login-cases
ls
Output
Switched to branch 'main'
README.md
Updating 761ccc2..769903f
Fast-forward
 login-cases.txt | 2 ++
 1 file changed, 2 insertions(+)
 create mode 100644 login-cases.txt
README.md
login-cases.txt

Fast-forward means main had not moved since the branch started, so Git simply slid the main label forward to the branch's latest commit. No new commit was needed. Once merged, delete the branch label with git branch -d add-login-cases (output: Deleted branch add-login-cases (was 769903f).). The commits stay in history.

When two branches change the same line: a merge conflict

If both branches changed the same line in different ways, Git can't guess which version you want. It stops and asks you. This is a merge conflict. It sounds alarming, but it's routine. Here, one branch changed TC-02 to quote the exact error text while main changed it to describe the banner:

Output of git merge wording
Auto-merging login-cases.txt
CONFLICT (content): Merge conflict in login-cases.txt
Automatic merge failed; fix conflicts and then commit the result.
cat login-cases.txt
TC-01 Valid login shows dashboard
<<<<<<< HEAD
TC-02 Wrong password shows red error banner
=======
TC-02 Wrong password shows "Invalid password"
>>>>>>> wording

Git has written both versions into the file between conflict markers. The part between <<<<<<< HEAD and ======= is your current branch (HEAD means "where you are now"); the part down to >>>>>>> wording is the incoming branch. To resolve it:

1. Open the fileFind every block of markers (search for <<<<)
2. DecideKeep one side, the other, or write a combination. Delete all three marker lines
3. Stagegit add login-cases.txt
4. Commitgit commit -m "Merge wording: keep banner and exact text"

Changed your mind? git merge --abort puts everything back as it was before the merge. After resolving, git log --oneline --graph draws the history, showing the two lines of work joining:

Output
*   76bd7dc Merge wording: keep banner and exact text
|\
| * edbe4f7 Exact error text in TC-02
* | c625ac0 Describe error banner in TC-02
|/
* 769903f Add first login test cases
* 761ccc2 Mention checkout page in README
* 4194538 Add README with project purpose
The decision is yours

Resolving a conflict is a judgement about what the code or document should say. Git can't make it, and an AI tool can only propose it. Read the result before committing, and run the tests afterwards. Chapter 71 shows how to let Claude Code propose resolutions safely.

61.6Keeping files out: .gitignore

Some files must never go into a repository: secrets such as .env files with API tokens, generated test reports, downloaded dependencies like node_modules/, and logs. A file called .gitignore in the top folder lists patterns Git should pretend not to see.

git status --short (before .gitignore)
?? .env
?? reports/

--short gives one line per file; ?? means untracked. Create the ignore file:

Terminal
printf '.env\nreports/\n*.log\nnode_modules/\n' > .gitignore
git status --short
Output
?? .gitignore

.env and reports/ have vanished from Git's view; only the new .gitignore shows, and you commit that like any file. A trailing / means "a folder"; *.log means "any file ending in .log".

Ignoring is not un-committing

.gitignore only affects files Git isn't already tracking. If a secret was committed even once, it's in the history, and anyone with a copy of the repository can find it. Removing it in a new commit doesn't erase the old snapshot. Treat the secret as leaked: revoke it and create a new one (Chapter 98). To stop tracking a file while keeping it on disk, use git rm --cached .env, then commit.

61.7Remotes: clone, push and pull

So far everything has happened in one folder on one computer. To share work you need a remote repository: another copy of the repository, usually on GitHub, that everyone sends their commits to and fetches others' commits from. By convention the main remote is called origin.

CommandWhat it doesEveryday meaning
git clone <url>Copies a whole remote repository, with full history, into a new folder"Get me my own copy of the project"
git remote -vLists the remotes this repository knows about"Where do I push to?"
git pushSends your new commits to the remote"Upload my work"
git fetchDownloads others' new commits but doesn't change your files"What's new? Don't touch my work yet"
git pullFetch, then merge the remote's commits into your current branch"Bring me up to date"

A remote doesn't have to be on the internet. In the lab you will make one in a local folder, which behaves exactly like GitHub for these commands. Connecting and pushing for the first time looks like this:

Terminal
git remote add origin ../remote.git
git push -u origin main
Output
To ../remote.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

-u (short for --set-upstream) links your local main to origin/main, so from now on plain git push and git pull know where to go.

"Rejected": when someone pushed first

If a colleague pushed commits you don't have yet, Git refuses your push rather than overwrite their work:

Output of git push
To ../remote.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '../remote.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.

This is Git protecting the team, not an error in your work. The fix is in the hint: git pull, resolve any conflict as in 61.5, then git push again.

Never "force" your way past it

You will see advice online to use git push --force. On a shared branch that deletes your colleagues' commits from the remote. Don't use it unless you fully understand it and the branch is yours alone.

Real-world example

A developer opens a PR titled "Fix session timeout on checkout" linked to Jira story SHOP-412. The GitHub Actions check shows two Playwright tests failing. You open the "Files changed" tab, read the diff, and spot that the timeout moved from 30 to 3 minutes rather than to 30 minutes. You leave a review comment on that exact line. The bug is caught before it is merged, which is the cheapest possible moment to catch it.

Signing in from the terminal: HTTPS or SSH

When you push to GitHub, Git has to prove who you are. GitHub does not accept your account password for this. There are two common ways:

HTTPS with a token

URLs look like https://github.com/your-name/qa-notes.git. When Git asks for a password, you give a personal access token instead, or let a credential helper handle it. The easiest route is the GitHub CLI: run gh auth login and follow the prompts, which sign you in through the browser and set Git up to use it. Works through most corporate firewalls.

SSH with a key pair

URLs look like git@github.com:your-name/qa-notes.git. You create an SSH key pair on your computer: a private key that never leaves it, and a public key you paste into GitHub (Settings → SSH and GPG keys). No passwords or tokens to type afterwards. Some company networks block the SSH port.

Terminal (SSH setup, if you choose it)
ssh-keygen -t ed25519 -C "asha@example.com"   # press Enter to accept the default file; set a passphrase
cat ~/.ssh/id_ed25519.pub                     # the PUBLIC key: this is what you paste into GitHub
ssh -T git@github.com                         # test the connection

The first time, SSH shows GitHub's key fingerprint and asks Are you sure you want to continue connecting (yes/no)?; check the fingerprint against GitHub's published one, then type yes. When the key is set up, the test prints Hi your-name! You've successfully authenticated, but GitHub does not provide shell access. That's success: the "no shell access" part is normal. Never share or paste the file without .pub: that is the private key. Tokens and keys are both secrets; Chapter 98 covers how to create, scope and store them safely.

Under the hood: what a commit really is

Git stores snapshots, not lists of changes. Each commit records the full state of every tracked file (efficiently: unchanged files are shared between commits), plus the author, date, message and the ID of its parent commit. A merge commit has two parents, which is why --graph draws a join.

The commit ID is a hash: a fingerprint calculated from all of that content. Change one character anywhere in the history and every later ID changes. That's what makes Git history trustworthy, and why "rewriting history" (with commands such as rebase or commit --amend) is a big deal on shared branches: it creates new commits with new IDs, and everyone else's copy disagrees.

A diff isn't stored; Git calculates it on demand by comparing two snapshots. A branch is a tiny file holding one commit ID. HEAD records which branch you are on.

Common misunderstandings
"Git and GitHub are the same thing."
Git is the program on your computer; GitHub is one website that hosts Git repositories and adds pull requests, issues and Actions.
"Saving the file saves it in Git."
Saving only changes the working folder. Nothing is in Git's history until you git add and git commit.
"Commit means upload."
A commit is local. Nobody else sees it until you git push.
"A merge conflict means I broke something."
It means two people changed the same lines and Git needs a human decision. It's normal and fixable, and git merge --abort is always an escape hatch.
"I deleted the secret in a later commit, so it's gone."
It's still in history. Revoke and replace it.
"git push --force fixes a rejected push."
It can delete teammates' work. Pull first instead.

61.9Review

Key takeaways
  • Git records a folder's history as commits; GitHub hosts repositories online and adds pull requests, issues and Actions.
  • A change goes working folder → staging area (git add) → repository (git commit). git status always tells you where things are.
  • git diff shows changes line by line: - removed, + added. Reading diffs is a core review skill.
  • Branches let work happen in parallel; git merge joins it. A conflict shows both versions between markers; you choose, remove the markers, add and commit.
  • .gitignore keeps secrets and generated files out, but can't remove something already committed.
  • clone, push, fetch and pull move commits between copies. A rejected push means "pull first", never "force".
  • GitHub sign-in from the terminal uses a token over HTTPS (easiest via gh auth login) or an SSH key pair, never your password.
Check yourself

You edited tests/login.spec.ts and ran git commit -m "Fix login test", but Git says "no changes added to commit". Why?

Commits contain only staged changes. Run git add tests/login.spec.ts (or use git commit -am for already-tracked files).

In a diff, what does a line starting with + mean?

- is removed, + is added, and a leading space marks unchanged context.

Your push is rejected with "(fetch first)". What should you do?

Someone pushed commits you don't have. Pulling merges them into your work; forcing would delete theirs.

You accidentally committed a .env file containing an API token, then added .env to .gitignore. Is the token safe?

Ignoring affects only untracked files. Anything ever committed stays in history; a pushed secret must be treated as leaked.

Which statement about Git and GitHub is true?

Git runs locally with no account. GitHub is one of several hosts, alongside GitLab, Bitbucket and others.

Assignment

Clone a repository your team uses (or any public one, such as a small open-source project). Using only the terminal, answer: Who made the last five commits, and what did they change (git log --oneline -5, git show)? Which branches exist (git branch -a)? Is there a .gitignore, and does it cover secrets and test reports? Then pick one recent pull request on GitHub, read its "Files changed" diff, and write one review comment a tester would add (a missing test, an unclear assertion, an untested edge case).

Teach it

"Git is save points for a folder. You edit files, choose which changes go in with git add, and save a snapshot with git commit and a clear message. git status tells you where everything is and git diff shows exactly what changed. Branches let you work without disturbing main, and a merge brings the work back; if two people changed the same line, Git asks you to choose. GitHub is the shared copy online: you push your commits there, open a pull request, and the team reviews the diff and the test results before it's merged. Never commit secrets, and never force-push a shared branch."
