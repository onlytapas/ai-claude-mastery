Every Claude Code session starts with a fresh, empty memory of the conversation. Two mechanisms carry knowledge from one session to the next. CLAUDE.md files are plain Markdown instructions that you (and your team) write: build commands, conventions, "always do this" rules. Auto memory is a set of notes Claude writes for itself as it learns your preferences and corrections. Both are loaded at the start of every session as context, which means Claude reads them and tries to follow them, but nothing forces it to. Short, specific, consistent instructions get followed; long, vague or contradictory ones don't. Anything that must be enforced belongs in settings or hooks instead.

77.1Why Claude Code needs memory files

Claude doesn't remember yesterday's session unless you resume it (Chapter 68). Without memory files you would start every session the same way: "We use Playwright with TypeScript. Tests go in tests/e2e. Use data-testid selectors. Run npm run test:smoke before you finish." A CLAUDE.md file is where you write that down once.

CLAUDE.md filesAuto memory
Who writes itYou and your teamClaude
What it containsInstructions and rulesLearnings: your preferences, corrections, project context it can't work out from the code
ScopeOrganisation, user, project or localOne per git repository, on your machine only
How much loadsThe whole file (files over 4 MiB are skipped)The first 200 lines or 25KB of its index, MEMORY.md

In everyday life

A new contractor joins your QA team for a day at a time, and every morning they've forgotten everything. CLAUDE.md is the one-page briefing sheet you hand them at the door: how to run the tests, where things live, the house rules. Auto memory is the contractor's own notebook, where they jot down "Asha prefers bullet-point bug reports" and "staging is down on Fridays". The briefing sheet is yours to write and the whole team uses it. The notebook belongs to the contractor, but you're allowed to read it and cross things out.

Not the same as memory in the Claude apps

The Claude apps on the web, desktop and mobile have their own memory and personalisation features, covered in Chapter 50. This chapter is about Claude Code's files on your computer. They're separate systems.

Context, not enforcement

CLAUDE.md is delivered to Claude as context, not as configuration. Writing "never edit files in src/" makes that unlikely, not impossible. To block an action whatever Claude decides, use a permission deny rule (Chapter 78) or a hook (Chapter 82). Permissions are enforced by Claude Code itself, and CLAUDE.md text can't grant or remove access.

77.2Where CLAUDE.md files live, and the order they load

There are four scopes, listed here from broadest to most specific. This is also the order they're loaded, so a project instruction appears in context after a user instruction:

ScopeLocationWho it's forCommit to Git?
Managed policymacOS /Library/Application Support/ClaudeCode/CLAUDE.md
Linux and WSL /etc/claude-code/CLAUDE.md
Windows C:\Program Files\ClaudeCode\CLAUDE.md		Everyone in an organisation; deployed by ITNo: IT installs it
User~/.claude/CLAUDE.mdYou, in every projectNo
Project./CLAUDE.md or ./.claude/CLAUDE.mdEveryone working on the projectYes
Local./CLAUDE.local.mdYou, in this project onlyNo: add it to .gitignore

Walking up and down the folder tree

When you start claude in a folder, Claude Code looks in that folder and every folder above it, and loads every CLAUDE.md and CLAUDE.local.md it finds. Start it in shop/tests/ and it loads shop/CLAUDE.md and shop/tests/CLAUDE.md.

CLAUDE.md files in folders below where you started aren't loaded at launch. Each one loads on demand, the first time Claude reads or edits a file in that folder.

ManagedOrganisation policy, if any
User~/.claude/CLAUDE.md
Project, top downEach folder from the root down to where you started: CLAUDE.md, then CLAUDE.local.md
Launch completeAll of the above are in context together
On demandSubfolder CLAUDE.md files, as Claude works there

"Precedence": they add up, they don't override

This surprises people used to settings files. CLAUDE.md files are concatenated: joined end to end, with nothing replaced. All of them go into the context, ordered from the top of the folder tree down to your working folder, with CLAUDE.local.md added after CLAUDE.md at each level. So instructions closer to where you started, and your personal notes, are the last things Claude reads.

Being read last is not the same as winning. If two files contradict each other ("use npm" in one, "use pnpm" in another), Claude may pick either one. The fix is not to rely on order, but to remove the contradiction.

Real-world example

Your company's managed CLAUDE.md says "Never paste customer data into prompts or files." Your user file says "Answer in British English, keep summaries short." The checkout team's project CLAUDE.md lists the Playwright commands and selector conventions. Your CLAUDE.local.md says "My test environment is https://qa3.shop.internal and my test user is qa.asha." When you start Claude Code in the checkout repository, all four are loaded together, and none of them cancels another.

Under the hood: how CLAUDE.md reaches the model

According to the Claude Code documentation, CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. That's one reason it guides rather than commands. If you really need text at system-prompt level, for example in a script, the documented route is the --append-system-prompt flag at launch (Chapter 75).

A few details that matter in practice:

  • Block-level HTML comments (<!-- note for maintainers -->) are stripped before the content reaches Claude, so you can leave notes for humans without spending tokens.
  • After /compact, the project-root CLAUDE.md is re-read from disk and injected again. Subfolder CLAUDE.md files and path-scoped rules load again on demand. Anything you said only in conversation may be lost in the summary, which is a good reason to move it into CLAUDE.md.
  • claude --bare skips CLAUDE.md discovery and auto memory altogether, which is useful in CI where you want a predictable run.
  • In a monorepo where another team's CLAUDE.md gets picked up, the claudeMdExcludes setting skips specific files by path or glob. It can't exclude the managed file.
  • The InstructionsLoaded hook event (Chapter 82) can log which files loaded and why, which helps when debugging rules that load on demand.

77.3Imports and the rules folder

Imports with @

A CLAUDE.md can pull in other files by writing @ followed by a path, anywhere in the text:

CLAUDE.md
See @README.md for the project overview and @package.json for the npm scripts.

# Additional instructions
- Bug report format: @docs/bug-report-template.md

The rules:

  • Relative paths resolve from the file that contains the import, not from where you started Claude.
  • Absolute paths and ~/ (home) paths are allowed.
  • Imported files can import others, up to a maximum depth of four hops.
  • Imports inside code spans and code blocks are ignored, so writing `@README.md` in backticks mentions the file without importing it.
  • Escape spaces in a path with a backslash: @Design\ Docs/api.md.
  • The first time a project file imports something outside the working folder (such as @~/.claude/my-notes.md), Claude Code shows a one-time approval dialog. That protects you from files someone else committed.
Imports organise; they don't shrink

An imported file loads together with the CLAUDE.md that imports it. Splitting a long file into imports makes it easier to maintain, but costs exactly the same context. To load something only when it's needed, use a path-scoped rule (below) or a skill (Chapter 80).

The .claude/rules/ folder

For bigger projects, put one topic per file in .claude/rules/. Every .md file in it (including subfolders) loads like .claude/CLAUDE.md. Personal rules for all your projects can go in ~/.claude/rules/.

Project layout
checkout-tests/
├── CLAUDE.md
├── CLAUDE.local.md          # personal, gitignored
└── .claude/
    └── rules/
        ├── test-style.md
        ├── bug-reports.md
        └── api-tests.md     # path-scoped, see below

Path-scoped rules: only when relevant

A rule file can start with paths frontmatter: a short block between --- lines listing file patterns. Then it loads only when Claude works with matching files, which keeps it out of the context the rest of the time. This is a path-scoped rule.

.claude/rules/api-tests.md
---
paths:
  - "tests/api/**/*.ts"
---
# API test rules
- Assert on the status code AND the response body schema, never status alone
- Read the base URL from process.env.API_BASE_URL; never hard-code hosts
- Every negative test names the error code it expects (e.g. 422 VALIDATION_ERROR)

** means "any number of folders", so this rule loads when Claude reads or edits any .ts file anywhere under tests/api/, and not when it's working on UI tests.

77.4CLAUDE.local.md and AGENTS.md

CLAUDE.local.md: personal, per project

CLAUDE.local.md sits at the project root next to CLAUDE.md, loads with it, and is treated the same way. It's for things that are true for you but not for the team: your sandbox URL, your preferred test data, "explain Git commands before running them, I'm still learning". It's still documented and supported. Add it to .gitignore so it's never committed. (With the environment variable CLAUDE_CODE_NEW_INIT=1 set, /init's personal option creates the file and gitignores it for you.)

Personal doesn't mean secret

Don't put passwords, tokens or API keys in CLAUDE.local.md either. It's a plain text file that goes into the model's context. Point to an environment variable instead: "the test user's password is in $QA_USER_PASSWORD" (Chapter 98).

AGENTS.md: the file other coding tools use

Many repositories already contain an AGENTS.md, an instructions file read by several other AI coding agents. From version 2.1.277, Claude Code reads it directly when there's no CLAUDE.md:

Your repository hasClaude Code reads (by default)
An AGENTS.md, and no CLAUDE.md or CLAUDE.local.md in your folder or above itThe AGENTS.md
Both an AGENTS.md and a CLAUDE.md (or CLAUDE.local.md)Only the CLAUDE.md files
A CLAUDE.md that imports AGENTS.md with @AGENTS.mdBoth, through the import

Your ~/.claude/CLAUDE.md, the managed file and .claude/rules/ don't count for this check; they load alongside AGENTS.md. The default can be changed in /config under Project instructions. If you want one shared file for every tool plus some Claude-only extras, the import pattern keeps both:

CLAUDE.md
@AGENTS.md

## Claude Code only
Use plan mode before changing anything under tests/fixtures/.
A trap

Because CLAUDE.local.md counts as "a CLAUDE.md" for this check, creating one in a project that relies on AGENTS.md stops Claude from reading the AGENTS.md. Either import AGENTS.md from a CLAUDE.md, or change the Project instructions setting to read both.

77.6Auto memory: notes Claude keeps for itself

As it works, Claude saves notes that will be useful in future sessions. It doesn't save something every session; it decides what's worth keeping. Each note has one of four types:

TypeWhat it recordsQA example
userYour role, expertise and working preferences"Asha is a QA engineer, new to TypeScript; explain type errors"
feedbackCorrections you give and approaches you confirm"Don't use waitForTimeout; use web-first assertions"
projectOngoing work, deadlines and decisions it can't learn from the code"Release 4.2 code freeze is Thursday; only P1 fixes"
referenceWhere to find information outside the project"Flaky-test dashboard is the CI 'Insights' tab"

Where it lives and how it loads:

  • Folder: ~/.claude/projects/<project>/memory/. There's one per Git repository, shared across its worktrees, and it stays on your machine (it isn't shared with colleagues or other computers).
  • It contains MEMORY.md, an index with one line per memory, plus a topic file for each memory.
  • The first 200 lines or 25KB of MEMORY.md (whichever comes first) load at the start of each session. Topic files are read only when needed.
  • When you say "remember that…", Claude saves it to auto memory. To put it in CLAUDE.md instead, say so explicitly ("add this to CLAUDE.md") or edit the file via /memory.

Auto memory is on by default in local sessions. To turn it off: use the toggle in /memory, set "autoMemoryEnabled": false in a settings file, or set the environment variable CLAUDE_CODE_DISABLE_AUTO_MEMORY=1. To store it somewhere else, set autoMemoryDirectory to an absolute or ~/ path (Chapter 78 covers settings files).

Real-world example

Twice in one week you tell Claude "our staging login needs the VPN, so check the VPN before blaming the app". The next week, when a login test fails with a timeout, Claude's first suggestion is to check the VPN. It saved a feedback memory. If the whole team needs to know this, move it into the project CLAUDE.md, because auto memory is yours alone.

Audit what it saved

Memory files are plain Markdown you can read, edit and delete. Open the folder from /memory every few weeks. Remove anything wrong or out of date, and anything sensitive that slipped in (a customer name from a bug report, an internal URL you'd rather not keep).

77.7Writing a CLAUDE.md that works

The official guidance comes down to three words: specific, short, consistent.

  • Specific enough to check. "Run npm run test:smoke before saying you're done" beats "test your changes". "Selectors: getByTestId only" beats "write good selectors".
  • Short. Aim for under 200 lines per file. Longer files use more context and are followed less reliably. Move rarely needed detail into path-scoped rules or skills.
  • Consistent. If two instructions contradict each other, Claude may pick either. Review all your files together now and then.
  • Structured. Markdown headings and bullet points are easier to follow than dense paragraphs.
  • Only what Claude can't work out. It can read your folder structure and package.json itself. Spend lines on commands, conventions, gotchas and the reasons behind them.

When to add a line: Claude makes the same mistake twice; a code review catches something Claude should have known; you type the same correction you typed last session; a new team member would need the same explanation.

A complete project CLAUDE.md for a QA repository

CLAUDE.md (checkout-tests repository)
# Checkout test suite

Playwright + TypeScript end-to-end and API tests for the web shop checkout.
<!-- Owner: QA guild. Review this file at each sprint retro. -->

## Commands
- Install: `npm ci`
- Smoke tests (about 2 minutes): `npm run test:smoke`
- One file: `npx playwright test tests/e2e/coupon.spec.ts`
- Lint: `npm run lint`
- Before saying a task is done, run lint and the smoke tests and report the result.

## Layout
- UI tests: `tests/e2e/`  · API tests: `tests/api/`  · Page objects: `tests/pages/`
- Test data builders: `tests/data/` (never hard-code users or card numbers in tests)

## Conventions
- Selectors: `getByTestId` first, then `getByRole`. Never CSS classes or XPath.
- Assertions: web-first (`await expect(...)`). No `waitForTimeout`.
- Name tests after behaviour: "rejects an expired coupon", not "coupon test 3".
- Each new test links its Jira key in a comment, e.g. `// SHOP-412`.

## Environments
- Base URL comes from `BASE_URL`; secrets come from environment variables only.
- Never run tests against production.

## Gotchas
- Staging needs the VPN; a login timeout is usually the VPN, not the app.
- The payment sandbox rejects amounts over 5000.00; use `tests/data/cards.ts`.

@.claude/rules/bug-reports.md

And a personal file to go with it, which stays out of Git:

CLAUDE.local.md
# Asha's preferences for this repo
- My environment: BASE_URL=https://qa3.shop.example
- I'm learning TypeScript: explain any type error before fixing it.
- Ask before running the full suite; it takes 25 minutes on my laptop.

Opinion · common team practice

Many teams treat the project CLAUDE.md like any other code: changes go through pull requests, and someone owns it. A reasonable rule of thumb is that each line should earn its place by preventing a mistake that has actually happened. If nobody can remember why a line is there, delete it and see whether the mistake comes back.

Which tool for which job

CLAUDE.md is for facts Claude needs in every session. Multi-step procedures belong in skills (Chapter 80); things that must happen at a fixed moment, like linting after every edit, belong in hooks (Chapter 82); allowed and blocked actions belong in permission settings (Chapter 78). 77.8Review

Key takeaways
  • CLAUDE.md files (written by you) and auto memory (written by Claude) carry knowledge between sessions. Both are context, not enforcement.
  • Scopes: managed, user (~/.claude/CLAUDE.md), project (./CLAUDE.md or ./.claude/CLAUDE.md) and local (./CLAUDE.local.md, gitignored).
  • Files in the working folder and every parent load at launch and are concatenated, root first, with CLAUDE.local.md after CLAUDE.md at each level. Subfolder files load on demand.
  • @path imports (relative to the importing file, up to four hops) organise but don't save context; .claude/rules/ with paths frontmatter loads only for matching files.
  • AGENTS.md is read directly (2.1.277+) when no CLAUDE.md or CLAUDE.local.md exists; otherwise use @AGENTS.md.
  • Auto memory lives in ~/.claude/projects/<project>/memory/; the first 200 lines or 25KB of MEMORY.md load each session. Manage it with /memory.
  • Good files are specific, under 200 lines, consistent, and free of secrets.
