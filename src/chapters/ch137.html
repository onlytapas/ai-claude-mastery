An open-weight model is a file of numbers you can download and run yourself. Two free tools make that easy: Ollama, which feels like an app store plus a local server, and llama.cpp, the lower-level engine for people who want control. Because a full model is too big for most laptops, people run quantised versions that store each number with fewer bits. The result is an AI that works offline and keeps your prompts on your machine, but which is smaller, slower and less capable than a frontier model such as Claude.

137.1Why run a model yourself?

Most of this book uses Claude through the app, Claude Code or the API. The model runs in a data centre and you send it your text. Running a model locally flips that: the model runs on your laptop or a server you control, and your text never leaves it.

ReasonWhat it means in practiceQA example
PrivacyPrompts and answers stay on your machineSummarising production logs that contain customer data your policy forbids sending out
Offline useNo internet needed once the model is downloadedWorking on a train, or in a secure lab with no outbound network
Predictable costNo per-token bill; you pay for hardware and electricityRunning thousands of cheap classification calls in a nightly CI job
Version controlThe exact same weights forever; no surprise retirementsA regression suite for an AI feature that must not change behaviour between releases
LearningYou can see memory use, speed and settings directlyUnderstanding why your vendor's prices and latency look the way they do

And the honest limits:

  • Capability. A model that fits on a laptop is much smaller than a frontier model. It will make more mistakes on hard reasoning, long documents and multi-step agent work.
  • Speed. Your laptop has a tiny fraction of a data centre's memory bandwidth (Chapter 25), so answers stream more slowly, especially for bigger models.
  • Your job now. Updates, safety filters, security and support become your responsibility.
In everyday life

Using Claude through the API is like eating at a top restaurant: excellent food, but you go to them and they see your order. Running a local model is cooking at home: nobody sees what you eat and it's cheap per meal, but your kitchen is smaller than theirs, and some dishes are simply out of reach.

137.2What you actually download

Three pieces work together whenever you run a model locally:

WeightsThe model itself: billions of numbers, published by a lab such as Alibaba (Qwen) or Google (Gemma), often on Hugging Face
A packaged fileThe weights converted and usually quantised into a single file, typically GGUF
An engineSoftware that loads the file, uses your CPU or GPU, and turns your prompt into tokens and back (llama.cpp, Ollama)
An interfaceA chat in the terminal, a local web page, or an HTTP API that your scripts call

GGUF is the file format used by llama.cpp. One .gguf file holds the weights plus the information needed to run them: the tokenizer, the model's shape, and the chat template that formats conversations the way the model was trained to expect. That's why you can download a single file and run it. On Hugging Face, repositories whose names end in -GGUF usually contain several versions of the same model at different quantisation levels.

Ollama hides most of this. You ask for a model by name, such as qwen3.5:0.8b, and it downloads the right file and runs it. llama.cpp exposes more: you can choose the exact file and quantisation, and tune how it uses your hardware.

Model name versus model tag

In Ollama, the part after the colon is a tag: qwen3.5 is the family, qwen3.5:0.8b is the 0.8-billion-parameter version. Leaving the tag off gives you the family's latest tag, which may be much bigger than you expected. Always check the size on the model's library page before you pull.

137.3Quantisation, in plain words

Chapter 32 introduced the idea: a model's numbers are normally stored with 16 bits each, and quantisation stores them with fewer bits, such as 8 or 4. The file shrinks by two or four times, needs less memory, and runs faster because there's less to move from memory to the processor. The price is a small loss of precision, which may or may not show up in answers.

In everyday life

Imagine recording temperatures. Writing "21.3847 °C" is precise. Writing "21 °C" is close enough for almost every purpose and takes half the ink. Writing "about 20" is cheaper still, but now you'd struggle to notice a fever. Quantisation chooses how many digits to keep for billions of numbers at once.

llama.cpp's README lists support for 1.5-bit, 2-bit, 3-bit, 4-bit, 5-bit, 6-bit and 8-bit integer quantisation. In GGUF files, the level appears in the file name:

Name patternRoughlyWhen people pick it
F16 / BF1616 bits per weight, no quantisationReference quality; needs the most memory
Q8_0About 8 bits per weightNear-original quality when you have the memory
Q5_K_M, Q6_KAbout 5–6 bitsA cautious middle ground
Q4_K_MAbout 4–5 bitsThe common default; llama.cpp picks it when you don't specify one
Q3_K, Q2_K and below3 bits or fewerSqueezing a big model onto small hardware; quality loss becomes noticeable
Under the hood: how 4 bits can stand in for 16

A 4-bit number can only take 16 different values. On its own that would be hopeless for weights that range over many sizes. The trick is block quantisation: the weights are split into small blocks (dozens of numbers), and each block gets its own scale factor stored at higher precision. Within a block, each weight is stored as one of 16 steps between that block's minimum and maximum. Because neighbouring weights tend to have similar sizes, the error per block stays small.

The "K" families in GGUF names use blocks within larger super-blocks, so even the scale factors are stored compactly, and the "S / M / L" suffix (small, medium, large) says how many of the more sensitive tensors are kept at a higher bit width. That's why a Q4_K_M file is a little larger than a pure 4-bit calculation predicts: some parts are deliberately kept more precise.

Quantisation for running models on your laptop is mostly about the weights. Data-centre serving also quantises activations and the KV cache; Chapter 139 covers that.

Quality loss is task-specific

"4-bit is nearly as good" is an average across benchmarks. Your task may be the exception: exact numbers, code, rare languages and long instructions often suffer first. If a local model will do real work, test the quantisation you'll actually use on your own examples (Chapter 36).

137.4Hardware: memory is everything

To run a model, its weights must fit in memory, plus room for the conversation (the KV cache) and the engine itself. Where that memory lives decides the speed:

GPU memory (VRAM)

An NVIDIA or AMD graphics card has its own fast memory. If the whole model fits there, answers are quick. If not, the engine splits the model between GPU and main memory, and speed drops sharply.

Apple Silicon (unified memory)

Macs with M-series chips share one pool of memory between CPU and GPU, so a 32 GB Mac can give most of that to a model. llama.cpp's README calls Apple silicon "a first-class citizen", using Apple's Metal framework.

A plain CPU with ordinary memory also works, just more slowly. Small models (around 1–4 billion parameters) are usable on CPU-only laptops; larger ones become painfully slow.

Memory available to the modelWhat is realistic (4-bit, rule of thumb)
8 GBModels up to roughly 4 billion parameters, short conversations
16 GBModels around 7–9 billion parameters comfortably
24–32 GBModels in the 20–30 billion range, such as the 27B and 31B tags below
64 GB and upLarger mixture-of-experts models; very large ones still need data-centre hardware

This table is a rule of thumb derived from the "about half a gigabyte per billion parameters at 4 bits" rule in Chapter 32, with headroom for the system and context. It is not a vendor specification. The download sizes on Ollama's library pages are the most reliable guide to the weights; add a few gigabytes for everything else.

Under the hood: why the context costs memory too

Every token in the conversation leaves behind attention "keys" and "values" for every layer of the model, stored in the KV cache (Chapter 25). A model that advertises a 256K-token context could need many gigabytes for the cache alone at full length. That's why local tools start with a much smaller context by default and let you raise it: in Ollama with the num_ctx parameter or the OLLAMA_CONTEXT_LENGTH environment variable; in llama.cpp with -c. Ollama's FAQ gives the current default. Raising it uses more memory, and if the total no longer fits on the GPU, part of the model moves to the CPU and slows down.

To see what's happening, Ollama's ollama ps command shows a PROCESSOR column. According to Ollama's FAQ, "100% GPU" means the model sits entirely on the GPU, "100% CPU" means it's in main memory, and a split such as "48%/52% CPU/GPU" means it's shared, which is usually the cause of disappointing speed.

137.5Choosing an open-weight model

New open-weight models appear every few weeks, so treat any list as a snapshot. Here are the families named in this chapter's scope, with facts checked on 9 November 2026. Company background is in Chapter 28 and Chapter 30.

FamilyFromLocal-friendly options (examples)Notes
QwenAlibabaOllama's qwen3.5 family has tags from 0.8b (about 1.2 GB download) through 2b, 4b, 9b, 27b and largerMany open releases; Qwen3.8-27B (Aug 2026) is Apache 2.0. The top "Max" models are cloud-only
GemmaGoogle DeepMindOllama's gemma4 family: e2b, e4b, 12b, 26b (a mixture-of-experts model with about 3.8B active parameters) and 31b; text and image inputGoogle's open family alongside its proprietary Gemini models

A sensible way to choose:

  1. Start from your memory budget. Pick the largest size that fits comfortably, not the largest that barely loads.
  2. Read the licence before any work use (Chapter 32). "Open weights" does not always mean "free for any commercial purpose".
  3. Test two or three candidates on 10–20 of your own real examples, not on a leaderboard.
  4. Check the tag. Tags ending in -cloud (for example gemma4:cloud) run on Ollama's servers, not your machine. More on that in 136.9.

137.6Ollama: the easy route

Ollama is a free tool that downloads models, runs them, and offers a local HTTP API on your computer. Install it from ollama.com/download, or with the commands from its README:

Terminal · install
curl -fsSL https://ollama.com/install.sh | sh     # macOS or Linux
irm https://ollama.com/install.ps1 | iex          # Windows PowerShell

On macOS and Windows you can also download a normal installer (a .dmg or .exe) from the same page. As always with "pipe this script into your shell" commands, only run them from the official site.

The commands you'll use

CommandWhat it does
ollama run qwen3.5:0.8bDownload the model if needed, then start an interactive chat. Add a quoted prompt at the end for a one-off answer
ollama pull qwen3.5:0.8bDownload a model without starting a chat
ollama lsList models on your computer, with sizes
ollama psList models currently loaded in memory, and whether they're on GPU or CPU
ollama stop qwen3.5:0.8bUnload a running model and free its memory
ollama rm qwen3.5:0.8bDelete a downloaded model from disk
ollama create name -f ModelfileBuild your own variant with a fixed system prompt and settings
ollama serveStart the background server manually (the desktop app normally does this for you)
ollama launch claudeSet up and start a supported external tool, here Claude Code, to use Ollama models

In an interactive chat, type /bye to leave. You can also pipe a file in, which is handy for logs or bug reports:

Terminal
ollama run qwen3.5:0.8b "Summarise this bug report in one sentence:" < bug-1234.txt

Downloaded models live in ~/.ollama/models on macOS, /usr/share/ollama/.ollama/models on Linux and C:\Users\%username%\.ollama\models on Windows (the OLLAMA_MODELS variable moves them). Models stay loaded for five minutes after use by default, then unload to free memory.

The local API

While Ollama is running, it listens on http://localhost:11434. Ollama's FAQ states that it binds to 127.0.0.1 by default, meaning only programs on your own computer can reach it. Any language that can send HTTP can use it:

Terminal · native chat API
curl http://localhost:11434/api/chat -d '{
  "model": "qwen3.5:0.8b",
  "messages": [{"role": "user", "content": "Give one boundary-value test for an age field that accepts 18-65."}],
  "stream": false
}'

The reply is JSON. The answer is in message.content, and it also reports eval_count (tokens generated) and eval_duration (in nanoseconds), so you can calculate the speed yourself. Ollama also offers two compatibility layers, so existing code can switch to a local model by changing a base URL:

StyleEndpointUse it with
Native/api/chat, /api/generateOllama's own Python (pip install ollama) and JavaScript libraries, or raw HTTP
OpenAI-compatible/v1/chat/completions and others under /v1/Code written for the OpenAI SDK; the API key is required by the SDK but ignored locally
Anthropic-compatible/v1/messagesCode written for the Anthropic Messages API, and Claude Code (see 136.8)

The compatibility layers cover the basics (messages, streaming, system prompts, tool calling), not everything. Ollama's Anthropic compatibility page lists, for example, no prompt caching, no Batches API and no citations.

A Modelfile: your own preset

A Modelfile is a small text file that builds a named variant of a model with a fixed system prompt and settings, much like a Dockerfile builds an image.

Modelfile
FROM qwen3.5:0.8b
PARAMETER temperature 0
PARAMETER num_ctx 8192
SYSTEM You are a QA assistant. Turn rough notes into bug reports with: Title, Steps to reproduce, Expected, Actual, Severity. Never invent steps that are not in the notes.
Terminal
ollama create bugwriter -f Modelfile
ollama run bugwriter "login page: typed wrong password 5 times, no lockout, can keep trying"

137.7llama.cpp: the engine room

llama.cpp is an open-source (MIT-licensed) engine written in C and C++ with no heavy dependencies. Its stated goal is to run models "with minimal setup and state-of-the-art performance on a wide range of hardware". It supports Apple's Metal, NVIDIA's CUDA, AMD through HIP, Vulkan and many other back-ends, and it can split a model between CPU and GPU when it doesn't fit in graphics memory. Choose it when you want to pick exact files, squeeze the most out of your hardware, or embed a model server in your own tooling.

Terminal · install (pick one)
curl -LsSf https://llama.app/install.sh | sh     # macOS or Linux, from the README
irm https://llama.app/install.ps1 | iex          # Windows PowerShell
brew install llama.cpp                           # Homebrew (macOS or Linux)
winget install llama.cpp                         # Windows Package Manager

Prebuilt downloads are also on the project's GitHub releases page. The README's quick start then uses a single llama command with sub-commands:

Terminal
llama cli -hf ggml-org/Qwen3.5-0.8B-GGUF      # download from Hugging Face and chat in the terminal
llama serve -hf ggml-org/Qwen3.5-0.8B-GGUF    # start an OpenAI-compatible server with a web UI

You'll also see the separate programs llama-cli and llama-server in older guides and in the project's own tool documentation. They are still shipped (Homebrew's package lists llama, llama-cli and llama-server among its binaries), so either style works with a current install.

OptionMeaning
-hf user/repo[:quant]Download a GGUF from Hugging Face. The optional quant picks the file, for example :Q8_0; the default is Q4_K_M
-m path/to/model.ggufUse a GGUF file you already have
-c NContext size in tokens; 0 means "use the model's own setting"
-ngl NHow many layers to put in GPU memory: a number, auto (default) or all
--port NFor the server: which port to listen on

The server's documentation says it listens on 127.0.0.1:9931 by default (some examples, including the project's own Docker ones, set port 8080 explicitly; check the address your terminal prints). It offers OpenAI-style endpoints such as /v1/chat/completions, an Anthropic-style /v1/messages, a /health check, and a built-in chat page you can open in your browser at the same address.

Real-world example

A test-automation team keeps a llama-server running on a spare workstation with a mid-sized model. Their nightly job sends each failed test's error message and last 50 log lines to /v1/chat/completions and asks for a one-line suspected cause. Because the logs contain customer email addresses, a local model is the only option their security team approved. Engineers treat the output as a hint for triage, never as the verdict.

137.8Connecting your tools to a local model

Because both tools speak the common API styles, most software that talks to a cloud model can be pointed at a local one. Ollama's documentation shows two ways to use it with Claude Code: the ollama launch claude command, or setting the environment variables yourself:

Terminal · from Ollama's Anthropic-compatibility docs
export ANTHROPIC_AUTH_TOKEN=ollama     # required but ignored by the local server
export ANTHROPIC_BASE_URL=http://localhost:11434
Expect a big drop in agent quality

Claude Code is designed around Claude models. A small local model behind it will follow multi-step instructions far less reliably, may call tools wrongly, and can make destructive mistakes look confident. Use this only for experiments in a throwaway folder, keep permission prompts on (Chapter 67), and don't judge Claude Code by what a 1-billion-parameter model does with it. Unset the variables afterwards so your normal sessions go back to Claude.

For your own scripts, the simplest path is plain HTTP to the native API, which the lab below uses. It needs nothing beyond Python's standard library.

137.9Privacy: real benefits and overlooked gaps

Ollama's FAQ states: "We don't see your prompts or data when you run locally." llama.cpp is code you run yourself with no service behind it. That is a real, strong benefit. But "local" only protects you if everything around the model is local too.

GapWhat can go wrongWhat to do
Cloud models in a local toolOllama also offers cloud-hosted models (tags such as gemma4:cloud). Those prompts go to Ollama's serversFor sensitive work, use only tags you have downloaded; check with ollama ls
Opening the server to the networkChanging OLLAMA_HOST or llama.cpp's --host to 0.0.0.0 lets anyone on the network use it. The local Ollama server does not check API keysKeep the default 127.0.0.1, or put proper authentication in front
The front-end appA third-party chat UI or IDE plug-in may log, sync or send telemetryCheck every tool in the chain, not just the model runner
Where outputs goAnswers pasted into Jira, Slack or a cloud document leave your machine anywayApply the same data rules to outputs as to inputs
Untrusted model filesA model from an unknown uploader may be altered, mislabelled or behave badlyPrefer official or well-known publishers; keep tools updated
Local diskConversation history and logs sit on your laptopFollow your device encryption and retention rules
Opinion · many security teams

A common position in company security policies is that a local model is acceptable for sensitive data only on a managed, encrypted device, with models from an approved list and the server bound to localhost. Check what your own organisation says before relying on "it's local" as your justification.

Run a private bug-triage model45 min · your computer · about 1.5 GB download
  1. Install Ollama for your system (136.6), then open a new terminal and run ollama --version.A version number. If you see "command not found", close and reopen the terminal, or start the Ollama desktop app once.
  2. Run ollama run qwen3.5:0.8b "In one sentence, what is regression testing?"A download progress bar the first time (about 1.2 GB), then a one-sentence answer. Later runs start in seconds.
  3. While it is still loaded, run ollama ps.A row for qwen3.5:0.8b with its size and a PROCESSOR value such as "100% GPU" on most Macs, or "100% CPU" on a laptop without a supported GPU.
  4. Save the script below as local_triage.py and run python3 local_triage.py.Three lines, each with a severity, a speed in tokens per second and the start of the bug text, followed by a one-line reason. The exact wording and speed will differ from the sample.
  5. Check the classifications. The data-exposure bug should be "critical"; the typo "trivial" or "minor".A small model may get one wrong. That is the point: write down which, because it's your first evidence about this model's fitness for triage.
  6. Privacy test: turn off Wi-Fi (or unplug the network) and run the script again.It still works, proving the model runs entirely on your machine.
  7. Optional: build the bugwriter preset from the Modelfile in 136.6 and try it on your own rough notes.A structured bug report. Check whether it invented any steps.

local_triage.py
# local_triage.py - ask a local Ollama model to triage bug reports. Standard library only.
import json
import os
import urllib.request

HOST = os.environ.get("OLLAMA_HOST_URL", "http://localhost:11434")
MODEL = os.environ.get("OLLAMA_MODEL", "qwen3.5:0.8b")

BUGS = [
    "Checkout button does nothing on Safari 18 when the basket has 3+ items.",
    "Typo on the About page: 'Teh team'.",
    "Users can see other customers' order history by changing the ID in the URL.",
]

SCHEMA = {  # structured output: the reply must match this JSON shape
    "type": "object",
    "properties": {
        "severity": {"type": "string", "enum": ["critical", "major", "minor", "trivial"]},
        "reason": {"type": "string"},
    },
    "required": ["severity", "reason"],
}

def ask(text):
    body = {
        "model": MODEL,
        "stream": False,
        "format": SCHEMA,
        "options": {"temperature": 0},
        "messages": [
            {"role": "system", "content": "You are a QA lead. Classify the bug's severity. Reply in JSON."},
            {"role": "user", "content": text},
        ],
    }
    req = urllib.request.Request(
        HOST + "/api/chat",
        data=json.dumps(body).encode("utf-8"),
        headers={"Content-Type": "application/json"},
    )
    with urllib.request.urlopen(req, timeout=300) as resp:
        return json.load(resp)

for bug in BUGS:
    r = ask(bug)
    verdict = json.loads(r["message"]["content"])
    tok_per_s = r["eval_count"] / (r["eval_duration"] / 1e9)  # durations are nanoseconds
    print(f"{verdict['severity']:<9} {tok_per_s:6.1f} tok/s  {bug[:48]}")
    print(f"          reason: {verdict['reason']}")
Sample output (yours will differ; speeds are illustrative)

          reason: Blocks purchase for a subset of users on one browser.
trivial     44.8 tok/s  Typo on the About page: 'Teh team'.
          reason: Cosmetic text error with no functional impact.
critical    43.5 tok/s  Users can see other customers' order history by
          reason: Exposes personal data to unauthorised users.
Troubleshooting
  • Connection refused: Ollama isn't running. Start the desktop app or run ollama serve in another terminal.
  • HTTP Error 404: the model isn't downloaded or the name is misspelt. Run ollama ls, then ollama pull qwen3.5:0.8b.
  • JSONDecodeError: the model returned something that isn't JSON. Re-run; if it persists, try a larger tag such as qwen3.5:4b with OLLAMA_MODEL=qwen3.5:4b python3 local_triage.py.
  • Very slow: ollama ps probably shows CPU. Close other apps, use a smaller model, or accept the speed for batch jobs.
  • The reply contains reasoning text before the JSON: some models "think" first. Ollama's chat API accepts "think": false in the request body for models that support switching it off.
Common misunderstandings
"A local model is the same as Claude, just free."
Models small enough for a laptop are far less capable than frontier models. They are useful for narrow, well-tested tasks, not as drop-in replacements.
"If it runs in Ollama, nothing leaves my computer."
Only for models you've downloaded and run locally. Cloud tags, network-exposed servers and third-party front-ends can all send data elsewhere.
"4-bit quantisation ruins a model."
For most tasks the loss is small, which is why 4-bit is the common default. But measure it on your task; some tasks are more sensitive.
"Bigger is always better locally."
A model that only fits by spilling onto the CPU can be so slow that a smaller model on the GPU serves you better.
"Open weights means I can use it however I like."
Each model has a licence. Read it before commercial use.

137.10Review

Key takeaways
  • Running locally gives privacy, offline use, fixed versions and no per-token bill, at the cost of capability, speed and maintenance.
  • You need weights (usually a quantised GGUF file), an engine to run them, and an interface such as a chat, web page or API.
  • Quantisation stores weights with fewer bits; Q4_K_M is a common default, and quality loss depends on the task.
  • Memory decides what you can run: model size, plus context, plus overhead. ollama ps shows whether you're on GPU or CPU.
  • Ollama is the easy route (run, pull, ls, ps, a local API on port 11434 with OpenAI- and Anthropic-compatible endpoints); llama.cpp gives finer control.
  • "Local" is only private if cloud tags, network exposure, front-ends and outputs are all handled too.
