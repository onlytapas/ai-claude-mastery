Almost every tool in this book (Claude Code via npm, Playwright, the Python SDKs, MCP servers) arrives through a package manager. A package manager is an app store for code: you name what you want, and it downloads the right version plus everything that version needs. On a Mac, Homebrew installs tools for the whole machine. Inside a project, npm (for JavaScript) and pip or uv (for Python) install libraries into that project only. If you understand where things get installed, which version you got, and how the project records it, most "it doesn't work on my machine" problems become easy to fix.

58.1What a package manager is

A package is a bundle of code someone has published so others can reuse it: a command-line tool, or a library you call from your own code. A package manager is the program that finds packages in an online catalogue (a registry), downloads them, puts them in the right place and keeps track of what you have.

Most packages rely on other packages. Those are its dependencies. Installing one package can quietly pull in dozens more. Working out a set of versions that all fit together is called dependency resolution, and it is the hardest part of the manager's job.

In everyday life

Think of a recipe box delivered to your door. You order "lasagne for four". The service works out that you need pasta sheets, tomatoes, cheese and a particular sauce, which itself needs garlic and basil. It sends the lot, labelled, in quantities that match. You never list the garlic yourself. A package manager does the same for software: you ask for one thing, and it works out and fetches everything that thing needs.

58.2What "installing" actually does

Installing feels like magic, but it is a few ordinary steps you could do by hand.

1 · ResolveWork out which versions of the package and its dependencies fit together
2 · DownloadFetch archives from the registry (and check their checksums)
3 · UnpackCopy files into a known folder: a Homebrew prefix, node_modules, or .venv
4 · LinkMake commands findable, by putting a link in a folder that is on your PATH
5 · RecordWrite down what was installed: package.json, a lock file, or the Homebrew database

Step 4 is why a fresh install sometimes says "command not found". The files are on disk, but the folder holding the command isn't on your PATH yet (Chapter 56). Opening a new terminal window, or running the line the installer printed, usually fixes it. which node or which python3 shows which copy your shell will actually run.

Under the hood: why one install brings 200 packages

Dependencies form a tree. If you install package A, and A needs B and C, and C needs D, you get four packages. The ones you didn't ask for directly are transitive dependencies. JavaScript packages tend to be small and numerous, so a tool like a test framework can pull in hundreds. npm stores them in a mostly flat node_modules folder and keeps a separate copy only when two packages need incompatible versions of the same thing. Python's pip installs exactly one version of each package per environment, so if two packages demand incompatible versions, pip reports a conflict instead. That difference is one reason Python projects lean so heavily on virtual environments: each project gets its own clean set.

58.3Homebrew: tools for the whole Mac

Homebrew is the most common way to install developer tools on macOS. It is free and also works on Linux. Its official install command, from brew.sh, is:

Terminal (macOS or Linux)
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

The script explains what it will do and pauses before changing anything. At the end it may print two or three "Next steps" lines that add Homebrew to your PATH. Run them: skipping that step is the most common reason brew is "not found" afterwards.

Homebrew keeps everything under one folder, its prefix: /opt/homebrew on Apple Silicon Macs, /usr/local on Intel Macs, and /home/linuxbrew/.linuxbrew on Linux. Each package lives in its own folder under Cellar, and its commands are linked into bin under the prefix.

Linux and Windows

On Ubuntu or Debian, the system package manager is apt (sudo apt install jq). On Windows, winget plays the same role, and much of this book's command-line work is easiest inside WSL (Windows Subsystem for Linux), where the Linux instructions apply. Claude Code itself can be installed with Homebrew (brew install --cask claude-code) or npm; Chapter 63 covers the options, and notes that Homebrew installs don't auto-update.

58.4Node.js and its versions

Node.js runs JavaScript outside a web browser. You need it for Playwright, many MCP servers, the npm install route for Claude Code, and front-end projects. Check whether you have it, and which version:

Terminal
node --version     # for example v26.x.x, or "command not found"

Switching versions with nvm

Different projects often need different Node versions: an old test suite pinned to Node 22, a new one on Node 26. A version manager lets you keep several and switch per project. The best known is nvm (Node Version Manager) for macOS, Linux and WSL. Install it with the command in the nvm README; at the time of writing that is:

Terminal
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.41.0/install.sh | bash
# open a new terminal window, then:
command -v nvm             # prints "nvm" if it worked
nvm install --lts          # install the newest LTS release
nvm install 22             # and an older one
nvm use 22                 # switch this terminal to Node 22
nvm alias default --lts node   # make the newest LTS the default for new terminals
echo "22" > .nvmrc         # record the project's version in the project folder
nvm use                    # reads .nvmrc and switches

nvm doesn't support native Windows. Its README points Windows users to WSL; separate projects such as nvm-windows exist but are not part of nvm. If you only ever need one version, installing Node with Homebrew (brew install node) or the official installer from nodejs.org is fine.

58.6Lock files: the cure for "works on my machine"

A range like ^1.11.23 means two people installing a week apart can get different versions. Usually that's harmless. Sometimes a "minor" release changes behaviour and one person's tests fail while another's pass. The lock file fixes this by recording the exact version that was actually installed, for every package in the tree. Commit it, and everyone (including CI) installs the same set.

Real-world example

A team's Playwright suite goes red in CI on Monday morning with "locator.click: Timeout exceeded", but passes on every laptop. Nobody changed the tests. The pipeline ran npm install, not npm ci, and the lock file had never been committed, so CI picked up a newer release of a dependency than the laptops had. The fix: commit package-lock.json, switch CI to npm ci, and upgrade on purpose in a separate pull request where a test failure is expected and investigated. (Illustrative scenario.)

"externally-managed-environment"

If you run pip install requests against a Homebrew or Linux system Python, pip may refuse with an externally-managed-environment error. That's deliberate (Python's PEP 668): the operating system or Homebrew manages that Python, and installing into it can break their tools. Don't override it with --break-system-packages. Create a virtual environment instead (next section). The error is protecting you.

58.8pip and virtual environments

A virtual environment is a folder, conventionally .venv, inside your project. It holds links to a Python interpreter plus that project's own installed packages. Project A can have one version of requests and project B another, and neither touches the system Python. Use one for every project. It costs nothing and prevents a whole class of problems.

In everyday life

A virtual environment is like a separate toolbox for each job. The plumber's box and the electrician's box can both contain a screwdriver of a different size, and neither tradesperson borrows the wrong one. The system Python is the shared workshop wall: you don't hang your own tools on it.

Terminal (macOS / Linux)
mkdir qa-py-lab && cd qa-py-lab
python3 -m venv .venv            # create the environment
source .venv/bin/activate        # switch this terminal into it; the prompt shows (.venv)
which python                     # now points inside .venv
python -m pip install requests   # installs into .venv only
python -m pip freeze > requirements.txt   # record exact versions
deactivate                       # leave the environment
Windows PowerShell
py -m venv .venv
.venv\Scripts\Activate.ps1       # if blocked, see troubleshooting in the lab
python -m pip install requests

Two habits pay off. First, write python -m pip rather than bare pip: it guarantees pip installs into the Python you're actually running. Second, add .venv/ to .gitignore. Commit requirements.txt instead; a colleague recreates your setup with python -m pip install -r requirements.txt in their own fresh environment.

Under the hood: what "activate" really changes

Activation is less magical than it sounds. The activate script puts .venv/bin at the front of your PATH and sets a VIRTUAL_ENV environment variable. So when you type python, the shell finds .venv/bin/python first. That Python looks for packages in .venv/lib/pythonX.Y/site-packages rather than the system location. You can skip activation entirely by calling the environment's Python directly: .venv/bin/python script.py. That is exactly what CI scripts and tools such as uv often do.

58.9uv: the all-in-one alternative

uv, from the company Astral, is a newer Python tool that does the jobs of pip, venv and a Python version manager in one fast program. Many recent projects and several AI SDK quick-starts show uv commands next to pip ones (for example, the Claude Agent SDK documents both pip install claude-agent-sdk and uv add claude-agent-sdk). You don't have to switch, but you should recognise it.

Terminal
# install (pick one; commands from the uv documentation)
curl -LsSf https://astral.sh/uv/install.sh | sh     # macOS / Linux
brew install uv                                     # Homebrew
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"   # Windows

# a project, uv style
uv init qa-tools        # creates a folder with pyproject.toml, .python-version and starter code
cd qa-tools
uv add requests         # adds to pyproject.toml, writes uv.lock, creates .venv
uv run check.py         # runs your script inside the project environment; no activation needed
uv sync                 # make .venv match uv.lock (after cloning, for example)

Opinion · this book's authors

For a beginner, learn pip and venv first: they come with Python, every tutorial uses them, and they show you what is really going on. Adopt uv when your team does, or when you start juggling several projects and Python versions. Either is a sound choice; mixing both in one project is the thing to avoid.

58.10Global versus local, and installing safely

Global (machine-wide)

Command-line tools you use everywhere: Git, jq, Node itself, Python itself, uv, Claude Code. Install these with Homebrew (or npm install -g for a few Node tools). One copy, available in every folder.

Local (per project)

Libraries your code imports, and project-specific tools such as Playwright or pytest. Install these into node_modules or .venv so each project records and controls its own versions.

A good rule: if it appears in your code's import or require, or a teammate needs the same version to reproduce your results, it's local.

Never use sudo with npm or pip

sudo npm install -g … and sudo pip install … run a stranger's install scripts as the all-powerful root user and leave files your normal account can't update. Anthropic's Claude Code install guide says explicitly not to use sudo with the npm route. If you get "EACCES: permission denied", fix the cause: use a Node version manager, Homebrew's Node, or a virtual environment.

Every package is code you run

Installing a package runs someone else's code on your machine, sometimes immediately (npm packages can declare install scripts). That is a real attack route, known as a supply-chain attack. A basic checklist for testers and AI users:

  • Check the name carefully. Attackers publish look-alikes (typosquatting), such as one letter off a popular package. AI assistants occasionally suggest package names that don't exist, and attackers have registered such names. Confirm a package on its registry page before installing.
  • Prefer well-used, maintained packages with a linked source repository.
  • Commit lock files and use npm ci in CI, so an upstream change can't slip in silently.
  • Run npm audit (or your company's scanner) and read what it reports rather than blindly forcing fixes.
  • Pin versions for anything that runs with access to secrets, such as MCP servers (Chapter 99).
Real-world example: Claude Code and installs

Claude Code will often want to run npm install or pip install while working. Under the default permission mode it asks first. Read the package name before approving, exactly as you would when a colleague asks. A team can pre-approve safe project commands, such as Bash(npm run *), in settings (Chapter 78), while still being asked about new installs.

Troubleshooting

  • "command not found: brew" right after installing: run the "Next steps" lines the installer printed, or open a new terminal.
  • "EACCES: permission denied" from npm: don't use sudo. Install Node through nvm or Homebrew so global packages live in a folder you own.
  • externally-managed-environment from pip: you're not in a virtual environment. Activate .venv first.
  • PowerShell refuses to run Activate.ps1: your execution policy blocks scripts. Ask IT, or run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned if your company policy allows it.
  • Company laptop blocks installs or the registry: ask IT for the approved route. Many companies run an internal registry mirror, which npm and pip can be pointed at. Alternatively, do the lab in a browser-based environment such as GitHub Codespaces.
  • Proxy or certificate errors (SELF_SIGNED_CERT_IN_CHAIN, SSL: CERTIFICATE_VERIFY_FAILED): a corporate proxy is inspecting traffic. Get the company's certificate setup from IT. Don't turn off certificate checking.
Common misunderstandings
"I installed it, so it should work everywhere."
Local packages exist only in that project's node_modules or .venv. Global commands also need their folder on your PATH.
"node_modules should be committed so others have the same code."
Commit the lock file instead. node_modules is rebuilt from it with npm ci.
"pip and python are always the same Python."
Not necessarily. python -m pip guarantees they match.
"sudo fixes permission errors."
It hides the cause and runs install scripts as root. Fix the install location instead.
"If an AI suggests a package, it exists and is safe."
Models can suggest packages that don't exist or are malicious look-alikes. Check the registry page first.

58.11Review

Key takeaways
  • A package manager resolves, downloads, unpacks, links and records packages and their dependencies.
  • Homebrew installs machine-wide tools on macOS and Linux; npm, pip and uv install project libraries locally.
  • Use Node.js LTS releases (22, 24 and 26 on 9 Nov 2026); nvm switches versions per project via .nvmrc.
  • npm: package.json declares, package-lock.json locks, node_modules holds; CI uses npm ci.
  • Python: one virtual environment per project, python -m pip, and a recorded requirements.txt or uv.lock.
  • Commit lock files, never use sudo for installs, and check every package name before installing it.
Check yourself

CI fails but every laptop passes, and nobody changed the tests. The pipeline runs npm install and package-lock.json isn't committed. What is the most likely cause?

Without a committed lock file, version ranges can resolve differently over time. Commit the lock file and use npm ci.

pip says externally-managed-environment. What should you do?

The error protects a Python managed by the OS or Homebrew. A virtual environment is the intended route.

package.json says "dayjs": "^1.11.23". Which version could npm install?

A caret allows newer minor and patch releases within the same major version, from 1.11.23 upwards.

Which belongs in Git?

Declarations and lock files are small and make installs reproducible; the installed folders are rebuilt from them.

What does npx @playwright/mcp@latest do if the package isn't installed?

That convenience is also a risk: you run whatever is latest at that moment. Pin versions for tools with access to secrets.
