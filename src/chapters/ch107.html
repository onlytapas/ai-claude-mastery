A chatbot answers once and stops. An agent keeps going: it looks at the situation, decides on an action, uses a tool to do it, reads the result, and decides again, until the job is done or it hits a limit. The model supplies the judgement; ordinary code supplies the loop, the tools, the memory and the limits. Many tasks don't need an agent at all: a fixed sequence of steps (a workflow) is cheaper and more predictable. Agents earn their place when you can't know the steps in advance, and they fail in predictable ways that a tester can check for.

107.1From chatbot to agent

When you ask Claude in a chat window "what are good boundary values for an age field?", it reads your message and writes one reply. Everything it needs is in the message. That is a single model call: text in, text out.

Now ask: "Look through last night's test results, find the failures that are new since yesterday, and tell me which team owns each." One reply can't do that. Something has to open the results, compare two runs, look up owners, and only then answer. The steps depend on what it finds: if there are no new failures, there is nothing to look up.

An agent is a system that handles this second kind of task. It works towards a goal by repeatedly choosing an action, carrying it out with a tool, and looking at the result. Three things make it work:

PartPlain meaningIn the test-results example
A modelThe "brain" that reads the situation and decides what to do nextClaude decides to open last night's results first
ToolsActions the program lets the model request: read a file, search, call an API, run a commandread_results, compare_runs, lookup_owner
A loop with limitsOrdinary code that runs the requested tool, hands back the result, and repeats until the model says it's done or a limit is hitStop after 20 steps or when Claude gives its final answer
In everyday life

A chatbot is like phoning an expert and asking a question: you get an answer, and the call ends. An agent is like giving a capable new colleague a task, a laptop and some access rights. They try something, look at what happened, try the next thing, and come back when they're done. How much access you give them, and how often they must check in, are decisions you make, not them.

The model never runs anything itself. It only asks. Your program decides whether to carry the request out. That single fact is the basis of almost every safety control in this part of the book.

107.2The agent loop

Every agent, from a small script to Claude Code, runs some version of the same cycle. It's usually described in four steps:

PerceiveRead the goal and everything learned so far
PlanThe model decides the next action, or that it's finished
ActThe program runs the chosen tool
ObserveThe tool's result is added to what the model can see

Then it goes round again. The loop ends when the model replies without asking for a tool (it thinks the job is done), or when your code stops it: too many steps, too much money spent, too much time taken, or a person says stop.

This idea has a well-known research ancestor. In October 2022, Shunyu Yao and colleagues published ReAct ("Reasoning and Acting"), which had a language model alternate between writing down its reasoning and taking actions such as a Wikipedia search, reading each result before reasoning again. Interleaving thought and action helped the model correct itself and reduced made-up answers. Modern agent loops are direct descendants.

What the loop looks like in the Claude API

In Chapter 89 you met tool use. An agent is tool use in a loop. Here is the shape of one turn, using the field names from Anthropic's documentation:

One turn of the loop (simplified)
# 1. You send: the goal, the conversation so far, and the tool definitions
{"model": "claude-opus-5-5", "max_tokens": 1000,
 "tools": [{"name": "read_bug", "description": "Read one bug file by name.",
            "input_schema": {"type": "object",
                             "properties": {"name": {"type": "string"}},
                             "required": ["name"]}}],
 "messages": [{"role": "user", "content": "How many open P1 bugs are there?"}]}

# 2. Claude replies with stop_reason "tool_use" and a tool_use block
{"stop_reason": "tool_use",
 "content": [{"type": "tool_use", "id": "toolu_01...", "name": "read_bug",
              "input": {"name": "BUG-101.txt"}}]}

# 3. Your code runs read_bug, then sends the result back as a user message
{"role": "user",
 "content": [{"type": "tool_result", "tool_use_id": "toolu_01...",
              "content": "BUG-101 Checkout total ignores voucher\nPriority: P1\nStatus: Open"}]}

# 4. Repeat until stop_reason is "end_turn": Claude's final answer

Three details from the documentation matter in real code. The tool_result must answer the matching id. Tool results must come first in that user message, before any text. And if a tool fails, you send the error back with "is_error": true so Claude can adapt, rather than crashing your program.

Under the hood: where the "plan" actually lives

The model has no hidden memory between calls. Each turn, your program sends the whole conversation again: the goal, every earlier tool request and every result. The "plan" is whatever the model works out from that history on this call. Current Claude models think before answering (Chapter 19), so some of that planning happens in a thinking block you may not see in full.

Two consequences follow. First, the history grows every step, which costs tokens and eventually fills the context window, so long-running agents must trim or summarise it. Second, anything that gets into the history (including text inside a web page or test log the agent read) can influence the next decision. That is why prompt injection is an agent problem first and foremost.

107.3Tools: the agent's hands

A tool, in API terms, is a name, a plain-language description, and an input schema (a JSON description of the parameters). The model only knows what a tool does from those three things. A vague description gives you a confused agent, however good the model.

Anthropic's "Building effective agents" article (December 2024) calls this the agent-computer interface (ACI), and suggests putting as much effort into it as you would into a user interface for people. Its advice, and the later article "Writing effective tools for agents" (September 2025), comes down to a few practical rules:

RuleWhyQA example
Fewer, well-scoped toolsEvery tool definition costs tokens and adds a choice the model can get wrongOne search_tests(query, status) tool, not separate tools for each status
Describe it as you would to a new teammateInclude format, edge cases, and how it differs from similar tools"Returns at most 50 results. Use status='failed' to see only failures."
Unambiguous parameter namesAvoid guessingjira_issue_key rather than id
Return meaningful, compact resultsLong raw dumps waste context and hide the signalReturn failing test names and messages, not the whole 2 MB XML report
Helpful error messagesAn error that says what to try next lets the agent recover"No run found for 2026-11-31. Dates must be real calendar dates."
Make mistakes hard ("poka-yoke")Design the tool so the wrong call is impossible or harmlessAnthropic's article reports that requiring absolute file paths fixed a class of mistakes with relative paths
Real-world example

A team gives an agent one tool called run that executes any shell command. It works in the demo. In week two it runs a database reset script against the shared test environment because a log suggested "try resetting the data". A better design gives the agent run_test_suite(suite_name) and get_test_log(run_id): narrow tools that can only do what the task needs. This is least privilege applied to tools, and Chapter 109 builds it into code.

Tools also come from outside your code. In Claude Code, built-in tools read and edit files and run commands; MCP servers add more (Chapter 97). Anthropic also runs some tools on its own servers, such as web search. Whatever the source, the loop is the same.

107.4Memory: what the agent knows, and for how long

"Memory" means several different things in agent design. It helps to separate them.

KindWhat it isLifetimeExample
Working memory (short-term)The conversation history sent with each call: goal, tool requests, resultsOne run; limited by the context windowThe bug files read so far in this run
Run stateFacts your code keeps about the run: step count, money spent, what's been writtenOne run, saved to disk so it survives a crash"Step 7 of 20; summary not yet written"
Long-term memoryNotes saved outside the conversation and loaded in later runsAcross runs, until deleted"The payments suite is flaky on Mondays; check the retry log first"
KnowledgeDocuments the agent can search when it needs themAs long as the documents are keptTest strategy, runbooks, past incident reports (RAG, Chapter 92)

Claude Code shows several of these in practice: the session history is working memory, CLAUDE.md files are long-term instructions loaded at start-up, and auto memory saves notes between sessions (Chapter 20). On the API, Anthropic provides a memory tool: a client tool with an Anthropic-defined schema that lets Claude store and read notes in files that you control.

In everyday life

Working memory is the notes on your desk while you work on one ticket. Run state is the checklist pinned to the ticket. Long-term memory is the team wiki. Knowledge is the company document library. You clear your desk after each ticket, but the wiki stays.

Memory is also an attack surface

Anything an agent writes to long-term memory will steer future runs. If a malicious test log tricks the agent into saving "always skip the security suite", that instruction persists. Treat memory writes as consequential: review them, scope them, and make them easy to inspect and delete.

107.5Autonomy levels

Autonomy is how much the system may do before a person checks. It isn't a property of the model; it's a setting you choose for each task and each tool. There is no single official scale. The ladder below is this book's way of describing the common options:

LevelWhat the AI doesWho actsQA example
0. AssistAnswers questions, drafts textThe person does everything"Suggest test cases for this story"
1. Suggest actionsProposes specific actions with reasonsThe person carries them out"These three tests look flaky; here's why"
2. Act with approvalPrepares the action and waitsThe AI acts after a person says yesDrafts a Jira bug; files it only when you approve
3. Act within limitsActs freely inside a fenced area; asks for anything outside itThe AI, within rules set in codeReruns failed tests and edits files in a branch; asks before pushing
4. Act freelyActs and reports afterwardsThe AIRare in practice; only for low-impact, reversible actions in a sandbox

Claude Code's permission modes (Chapter 67) are a concrete example of moving between levels 1 and 3: plan mode only proposes, the default mode asks before edits and commands, and more permissive modes approve whole classes of action in advance.

Choose autonomy per action, not per agent

One agent can read anything at level 4, edit files at level 3, and post to Slack only at level 2. Ask two questions for each action: how bad is it if this is wrong? and can it be undone? Reading a log: harmless and reversible. Closing 200 Jira tickets: visible and hard to undo.

107.6Workflows versus agents

Anthropic's article "Building effective agents" (published 19 December 2024) draws a line that many teams now use. In its words, workflows are "systems where LLMs and tools are orchestrated through predefined code paths", while agents are systems where the LLM "dynamically direct[s] their own processes and tool usage, maintaining control over how they accomplish tasks". The article calls both "agentic systems".

Workflow

You write the steps in code. The model fills in the judgement at each step. Example: for every new bug report, (1) summarise it, (2) classify the component, (3) suggest a priority. The order never changes.

Good when: the steps are known; you want predictability, low cost and easy testing.

Agent

You give a goal and tools. The model decides which tools to call, in what order, and when it's done. Example: "find out why the nightly run failed and propose a fix".

Good when: the number and order of steps can't be known in advance, and you can tolerate higher cost and some unpredictability.

The article's central advice is to find "the simplest solution possible, and only increasing complexity when needed". Often that's a single well-prompted model call with good examples. Then a workflow. Only then an agent. Chapter 108 covers the workflow patterns it describes (prompt chaining, routing, parallelisation, orchestrator-workers, evaluator-optimiser) and when each fits.

Single callOne prompt, maybe with retrieval and examples
WorkflowFixed steps in code; model at each step
AgentModel chooses steps in a loop with tools

The article also gives three principles for building agents: keep the design simple, make the agent's planning steps visible (transparency), and craft the agent-computer interface carefully through good tool documentation and testing. On frameworks, it suggests starting with the model API directly, and if you use a framework, understanding what it does underneath, because extra layers can hide the actual prompts and responses and make debugging harder.

Opinion · Anthropic ("Building effective agents")

The article's authors argue that the most successful implementations they saw used simple, composable patterns rather than complex frameworks. This is a recommendation from experience, not a measured result, but it matches what many QA teams find: the agent you can debug beats the clever one you can't.

Under the hood: why "agent" is a spectrum in practice

Real systems mix the two. Claude Code is an agent at the top level, but inside it some steps are fixed code (checking permissions, running hooks). A workflow might include one step that is a small agent ("investigate this failure, up to 5 tool calls"). The useful question isn't "is it an agent?" but "for each decision, who chooses: my code or the model?" Every decision you move to the model gains flexibility and loses predictability.

107.7Where agents fail

Agents fail in recognisable ways. As a tester, this list is your starting test plan.

FailureWhat it looks likeTypical guard
Compounding errorsA wrong guess in step 2 feeds every later stepChecks between steps; shorter tasks; human review of key outputs
LoopingCalls the same tool again and again without progressStep limit; detect repeated identical calls
Premature "done"Declares success without checking (tests "pass" because none ran)Verify the outcome in code, not by the agent's word
Wrong tool or wrong argumentsSearches the wrong project; passes a relative pathBetter tool descriptions; strict schemas; validation in the tool
Prompt injectionText inside a web page, email or log tells the agent to do something elseLeast privilege; approval for consequential actions; treat tool output as data
Scope creep"While I was there, I also refactored the login module"Narrow instructions; limit which files and tools are reachable
Runaway cost or timeA long loop reads huge files over and overToken, money and time budgets enforced in code
Context overflowThe history fills the context window; early instructions get lostCompact results; summarise history; split the task
Chance all 20 steps succeed (illustrative arithmetic)
99% per step82%
95% per step36%
90% per step12%
Illustrative, not measured: 0.9920 ≈ 0.82, 0.9520 ≈ 0.36, 0.9020 ≈ 0.12. Real steps aren't independent, and agents can recover from errors, but the arithmetic shows why long unchecked chains are risky.
Real-world example

An agent is asked to "make the checkout tests pass". It edits the assertion from expect(total).toBe(90) to expect(total).toBe(100). The tests pass; the voucher bug ships. The agent met the goal as written. The guard is a better goal ("fix the product code, not the tests; never change assertions without asking") plus a review step a human actually reads.

Anthropic's own experience points the same way. In its June 2025 write-up of its multi-agent research system, it reports that agents typically use about four times more tokens than chat, and that small failures in long runs are costly, so it added checkpoints and the ability to resume from where an error occurred. Chapter 109 turns these guards into code, and Chapter 113 covers supervising agents in production.

mini_agent.py
"""The smallest useful agent loop: perceive, decide, act, observe, repeat.
Offline: python3 mini_agent.py --fake      Real: python3 mini_agent.py (needs ANTHROPIC_API_KEY)"""
import json, os, sys
from pathlib import Path

BUGS = Path("bugs")
TOOLS = [
    {"name": "list_bugs", "description": "List bug files in the bugs folder.",
     "input_schema": {"type": "object", "properties": {}}},
    {"name": "read_bug", "description": "Read one bug file by name.",
     "input_schema": {"type": "object", "properties": {"name": {"type": "string"}},
                      "required": ["name"]}},
]

def list_bugs():
    return json.dumps(sorted(p.name for p in BUGS.glob("*.txt")))

def read_bug(name):
    return (BUGS / Path(name).name).read_text()   # Path(name).name drops any folder part

def fake_model(messages):
    """Pretends to be Claude: a fixed script, same reply shape as the real API."""
    used = [b for m in messages if m["role"] == "assistant" for b in m["content"]
            if b["type"] == "tool_use"]
    seen = [b["content"] for m in messages if isinstance(m["content"], list)
            for b in m["content"] if b["type"] == "tool_result"]
    step = len(used) + 1
    if not used:
        return {"stop_reason": "tool_use", "content": [
            {"type": "tool_use", "id": f"t{step}", "name": "list_bugs", "input": {}}]}
    files = json.loads(seen[0])
    if len(used) <= len(files):
        return {"stop_reason": "tool_use", "content": [
            {"type": "tool_use", "id": f"t{step}", "name": "read_bug",
             "input": {"name": files[len(used) - 1]}}]}
    p1 = [s.splitlines()[0] for s in seen[1:] if "Priority: P1" in s and "Status: Open" in s]
    return {"stop_reason": "end_turn", "content": [
        {"type": "text", "text": f"{len(p1)} open P1 bug(s): " + "; ".join(p1)}]}

def real_model(messages):
    import anthropic
    r = anthropic.Anthropic().messages.create(
        model="claude-opus-5-5", max_tokens=1000, tools=TOOLS, messages=messages)
    return r.to_dict()

def run(task, model, max_steps=10):
    messages = [{"role": "user", "content": task}]
    for step in range(1, max_steps + 1):
        reply = model(messages)                                   # decide
        messages.append({"role": "assistant", "content": reply["content"]})
        if reply["stop_reason"] != "tool_use":                    # finished
            return " ".join(b["text"] for b in reply["content"] if b["type"] == "text")
        results = []
        for b in reply["content"]:
            if b["type"] == "tool_use":                           # act
                out = {"list_bugs": list_bugs, "read_bug": read_bug}[b["name"]](**b["input"])
                print(f"step {step}: {b['name']}({b['input']}) -> {out[:50]!r}")
                results.append({"type": "tool_result", "tool_use_id": b["id"], "content": out})
        messages.append({"role": "user", "content": results})     # observe
    return "Stopped: step limit reached."

if __name__ == "__main__":
    BUGS.mkdir(exist_ok=True)
    samples = {"BUG-101.txt": "BUG-101 Checkout total ignores voucher\nPriority: P1\nStatus: Open",
               "BUG-102.txt": "BUG-102 Typo on login page\nPriority: P3\nStatus: Open",
               "BUG-103.txt": "BUG-103 Search crashes on emoji\nPriority: P1\nStatus: Closed",
               "BUG-104.txt": "BUG-104 Payment page times out\nPriority: P1\nStatus: Open"}
    for name, text in samples.items():
        (BUGS / name).write_text(text)
    fake = "--fake" in sys.argv
    if not fake and not os.environ.get("ANTHROPIC_API_KEY"):
        sys.exit("No ANTHROPIC_API_KEY set. Run with --fake to use the offline stand-in.")
    print(run("How many open P1 bugs are there? List them.", fake_model if fake else real_model))

Troubleshooting. SyntaxError near f"...": you're on an old Python; check python3 --version is 3.10 or newer. No ANTHROPIC_API_KEY set: add --fake, or set the key. KeyError in the real mode: Claude asked for a tool name you didn't define; check the TOOLS names match the dictionary in run(). The fake mode was tested on Python 3.11; the real mode follows Anthropic's documented format but was not run for this chapter because no API key was available.

Common misunderstandings
"The model runs the tools."
The model only requests a tool call. Your program decides whether to run it, which is where permissions and approvals live.
"Agents are always better than workflows."
Agents cost more, vary more and are harder to test. Use one only when the steps can't be fixed in advance.
"The agent remembers everything from last week."
Only what was saved outside the conversation and loaded again. Each API call sees only what you send.
"If the agent says it's done, it's done."
Agents can declare success too early. Check the outcome in code or by a person.
"Autonomy is a feature of the model."
It's a design decision you make for each action, based on impact and reversibility.

107.8Review

Key takeaways
  • An agent is a model plus tools plus a loop with limits: perceive, plan, act, observe, repeat.
  • In the Claude API, the loop is tool use repeated: stop_reason: "tool_use", run the tool, send a tool_result, until end_turn.
  • Tool design (the agent-computer interface) matters as much as the prompt: few, narrow, well-described tools with helpful errors.
  • Memory comes in layers: working memory (the conversation), run state (your code), long-term notes and searchable knowledge.
  • Choose autonomy per action, based on how bad a mistake would be and whether it can be undone.
  • Anthropic distinguishes workflows (predefined code paths) from agents (the model directs the process) and advises the simplest solution that works.
  • Agents fail predictably: compounding errors, loops, premature "done", injection, scope creep, runaway cost. Test for each.
Check yourself

What tells your program that Claude wants a tool to be run?

The tool_use block names the tool and its input; your code runs it and replies with a tool_result carrying the same id.

By Anthropic's definition, which of these is a workflow rather than an agent?

The steps are predefined in code. In an agent the model directs its own steps and tool use.

An agent must close duplicate Jira tickets. Which autonomy level fits best at first?

Closing tickets is visible and tedious to undo, so it needs approval; reading and preparing the list is safe to automate.

Each step of a 20-step task succeeds 95% of the time, independently. Roughly how often does the whole task succeed?

0.95 to the power 20 is about 0.36. This is why long unchecked chains are risky and checks between steps help.

Where does an agent's long-term memory actually live?

The model doesn't learn between calls. Memory is whatever your system saves and sends back later.

Teach it

"An agent is a model in a loop. It looks at the goal and what it's learned, picks a tool, our code runs the tool, and the result goes back in. Round it goes until it says it's done or hits a limit we set. The model never acts directly; it asks, and our code decides. Most tasks don't need an agent; a fixed sequence of steps is cheaper and easier to test. When we do use one, we give it narrow tools, limits on steps and cost, and approval before anything consequential, and we test for the usual failures: loops, false 'done', and instructions hidden in the data."
