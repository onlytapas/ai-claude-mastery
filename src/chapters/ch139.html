Running a model for one person on a laptop is easy. Serving it to thousands of people at once, quickly and cheaply, is an engineering discipline. The core problem is that GPU memory and memory bandwidth are scarce, and every conversation's KV cache competes for them. Modern serving engines such as vLLM solve this with smarter scheduling (continuous batching), smarter memory (PagedAttention and prefix caching) and smaller, faster models (quantisation, distillation and speculative decoding). Every optimisation is a trade-off between latency, cost and quality, and each one should be tested like any other change to production.

139.1From model file to service

A model on its own is just a file of numbers. To turn it into something like the Claude API, you need software around it that accepts requests, decides which ones to run together, manages memory, runs the maths on the GPU and streams answers back. That software is the serving stack.

API serverAccepts HTTP requests (often in the OpenAI or Anthropic format), checks them and queues them
SchedulerDecides, step by step, which requests run together on the GPU
Memory managerGives each request space for its KV cache and reclaims it when done
EngineRuns prefill and decode on the GPU with optimised code ("kernels")
StreamerSends each new token back to the right user as it's produced

The numbers that matter

MetricPlain meaningWhat drives it
Time to first token (TTFT)How long before the answer starts appearingQueueing, plus prefill of the prompt (long prompts take longer)
Time per output token (TPOT), or inter-token latencyHow fast the answer streams once startedDecode speed, which falls as more requests share each step
ThroughputTotal tokens or requests per second across all usersBatch size, memory available for KV cache, kernel efficiency
Tail latency (p95, p99)How slow the slowest 5% or 1% of requests areBursts, long prompts and long answers blocking others
GoodputThroughput counting only requests that met their latency targetThe balance of all the above
In everyday life

Think of a busy coffee shop. TTFT is how long until the barista starts your order. TPOT is how fast they work once they've started. Throughput is cups per hour for the whole shop. Tail latency is the unlucky customer stuck behind someone ordering twelve complicated drinks. A shop tuned only for cups per hour can still leave that customer furious, which is why serving teams watch p95 and p99, not just averages (percentiles).

139.3Batching, done properly

Chapter 25 explained why batching helps: in decode, the GPU reads all the weights for every step, so serving many requests in the same step shares that cost. The question is how you batch.

Static batching

Collect a group of requests, run them together until all have finished, then start the next group. A one-word answer sits waiting for a 2,000-word essay in the same batch. GPU slots go idle and new users wait in the queue.

Continuous batching

Re-decide the batch at every decode step. As soon as one request finishes, its slot goes to a waiting request. The GPU stays full, and short answers leave immediately. This is the default in modern engines; llama.cpp's server, for example, lists it as enabled by default.

In everyday life

Static batching is a lift that waits until every passenger has reached their floor before going back down for new people. Continuous batching is a paternoster or escalator: people step on and off at any moment, and it never runs empty while someone is waiting.

Under the hood: chunked prefill and disaggregation

Continuous batching creates a new problem. When a request with a very long prompt arrives, its prefill is a big burst of computation. If it runs in one go, every other user's next token is delayed: their streaming visibly stutters.

Chunked prefill (a documented vLLM feature) splits long prefills into pieces and mixes them with ongoing decode steps, smoothing out the stutter at a small cost to the new request's TTFT.

Prefill–decode disaggregation goes further: prefill and decode run on different groups of GPUs, each tuned for its phase (compute-heavy versus memory-bandwidth-heavy), and the KV cache is transferred between them. NVIDIA lists it as a key feature of TensorRT-LLM. It adds complexity and network traffic, so it pays off mainly at large scale.

139.4Memory: the KV cache is the real budget

Once the weights are loaded, the rest of the GPU's memory goes on KV caches, one per active request. The more requests whose caches fit, the bigger the batch and the higher the throughput. So much of serving optimisation is really KV cache optimisation.

The size per token is simple to work out:

The KV cache formula
bytes per token = 2 (key and value) × layers × KV heads × head size × bytes per number

For an illustrative 70B-class model with 80 layers, 8 KV heads of size 128 and 16-bit numbers, that's about 0.33 MB per token. A 32,000-token conversation needs over 10 GB of cache on its own. The lab calculates this for you.

Three techniques that changed serving

TechniqueThe problemThe fix
PagedAttention (Kwon et al., 2023)Older systems reserved one large, contiguous block per request, sized for the longest possible answer. Most of it sat unused, and gaps fragmented memoryStore the cache in small fixed-size pages allocated on demand, like an operating system's virtual memory. The paper reports "near-zero waste" and 2–4× higher throughput than the systems it compared at the same latency
Prefix cachingMany requests start with the same text: a long system prompt, a shared document, the same few-shot examples. Prefilling it every time wastes compute and memoryKeep the KV cache for a shared prefix and reuse it across requests. vLLM calls this Automatic Prefix Caching. It's the same idea behind the API feature prompt caching (Chapter 89)
KV cache quantisationThe cache itself is stored at 16 bitsStore it at 8 bits, roughly doubling how many tokens fit, with a small accuracy risk. vLLM documents "Quantized KV Cache" support

Model design matters too. Many modern models use fewer KV heads than query heads (grouped-query attention), which shrinks the cache several times compared with giving every attention head its own keys and values. That's why "8 KV heads" appears in the example above.

Real-world example

An internal test-generation service sends every request with the same 6,000-token system prompt describing the product, the house test style and the Jira conventions. Turning on prefix caching means that block is prefilled once and reused. TTFT drops noticeably for every user, and the GPU spends its time on the part of each request that's actually new. The same reasoning is why Anthropic's guidance puts stable content first and variable content last when you use prompt caching with Claude.

139.5Making the model cheaper to run

Quantisation for serving

Chapter 137 covered quantisation for laptops, where the goal is to fit at all. In data-centre serving, the goals are throughput and cost. Two broad families:

ApproachWhat's reducedHelps most withExamples supported by vLLM
Weight-onlyWeights stored at 4 or 8 bits; maths done at 16 bits after unpackingMemory-bound decode at small batch sizes; fitting larger modelsAWQ, GPTQ, GGUF, bitsandbytes
Weights and activationsBoth stored and multiplied in 8-bit (or lower) formats on hardware that supports itCompute-bound work: big batches and long prefillsFP8 and INT8 "W8A8" schemes through tools such as LLM Compressor
Quantisation is a model change

A quantised model is a slightly different model. Treat switching to it like a release: run your evaluation suite before and after (Chapter 125), and look especially at the tasks you care about most, such as structured output, code and numbers.

Distillation

Distillation trains a small "student" model to imitate a large "teacher" model, using the teacher's outputs (or its full probability distributions over next tokens) as training targets. The idea was popularised by Hinton, Vinyals and Dean's 2015 paper "Distilling the Knowledge in a Neural Network". The student is much cheaper to serve and often keeps a surprising share of the teacher's ability on the tasks it was distilled for. Many small open models are partly distilled from larger siblings. Note that model licences and API terms often restrict using one company's outputs to train a competing model, so check before distilling from someone else's model.

Speculative decoding

Plain idea: decode is slow because the big model produces one token per step. So let a small, fast "draft" model guess the next few tokens, then have the big model check all those guesses in a single step. Every guess the big model agrees with is accepted for free; at the first disagreement, the big model's own choice is used and drafting starts again.

DraftSmall model proposes "the user is not logged in"
VerifyBig model checks all six tokens in one parallel pass
AcceptFirst four match; the fifth is replaced by the big model's choice
RepeatFive tokens produced for roughly the cost of one big step plus drafting

Leviathan, Kalman and Matias (2022) showed this can be done "without any changes to the outputs": the final text follows exactly the distribution the big model alone would produce. They reported 2–3× speed-ups on T5-XXL. It works best when the text is predictable (code, boilerplate, structured output) and when the GPU has spare compute, which is typically at low batch sizes; under heavy load, the extra verification work competes with other requests. vLLM and TensorRT-LLM both list speculative decoding among their features.

Under the hood: why verification is nearly free

Remember from Chapter 25 that decode is memory-bound: the GPU spends most of each step waiting for weights to arrive, while its calculators sit partly idle. Checking six draft tokens in one forward pass reads the weights once, just like producing one token, and uses some of that idle compute. That's why the big model can "check five tokens for the price of one". The acceptance rule from the paper (accept a draft token with a probability based on how the two models' probabilities compare, otherwise resample) guarantees the output distribution is unchanged, so speculative decoding is a pure speed optimisation, not a quality trade-off.

Variants drop the separate draft model: some add extra prediction heads to the big model itself, others look up likely continuations from the prompt text. The principle (guess cheaply, verify in parallel) is the same.

Smarter routing

The cheapest optimisation is often not to use the big model at all. Model routing sends easy requests to a small model and hard ones to a large one. With Claude this means choosing between Haiku, Sonnet and Opus per task (Chapter 40); in self-hosting it may mean running two models behind one API.

139.6Trade-offs, and how to test an optimisation

Every lever moves at least one of three dials: latency, cost per token, and quality.

LeverLatencyCost per tokenQuality risk
Bigger batchesWorse per user (slower streaming)BetterNone
Continuous batchingBetter, especially TTFTBetterNone
Prefix cachingBetter TTFT for shared prefixesBetterNone
Weight quantisationUsually betterBetter (fewer or cheaper GPUs)Small, task-dependent: measure
KV cache quantisationNeutral to betterBetter (bigger batches)Small: measure on long contexts
Speculative decodingBetter at low loadNeutral to betterNone by design
Distillation or a smaller modelBetterMuch betterReal: needs full evaluation
Tensor parallelism across more GPUsBetter per userWorse (more GPUs per request)None

Testing an optimisation is ordinary QA work with two halves:

  1. Quality. Run the same evaluation set on the old and new configuration (Chapter 36, Chapter 125). Compare task scores, structured-output validity, and a sample of answers read by a person. For "lossless" changes like speculative decoding, a check that outputs match at temperature 0 is a good sanity test, though tiny numeric differences in GPU maths can still cause occasional divergence.
  2. Performance. Load test with realistic traffic: the real mix of prompt lengths, answer lengths and arrival bursts. Report TTFT and TPOT at p50, p95 and p99, plus throughput, at several load levels. A change that helps average latency at low load can hurt p99 at peak.
Opinion · common among inference engineers

A view often expressed by people who run inference services is that most of the cost savings come from unglamorous choices (the right model size, high GPU utilisation, prefix caching, and not over-provisioning for rare peaks) rather than from the latest exotic technique. That's a practitioner judgement, not a measured law, but it's a useful order in which to look.

# serve_calc.py - how KV cache memory and batching shape a model server. ILLUSTRATIVE numbers.
GPU_GB = 80                 # one H100 SXM: 80 GB of memory
BANDWIDTH_GBS = 3350        # ...and 3.35 TB/s of memory bandwidth
WEIGHTS_GB = 35             # e.g. a 70B-parameter model at 4 bits
OVERHEAD_GB = 5             # runtime, activations, fragmentation (illustrative)

# Shape of an illustrative 70B-class model with grouped-query attention
LAYERS, KV_HEADS, HEAD_DIM = 80, 8, 128

def kv_bytes_per_token(bytes_per_value):
    return 2 * LAYERS * KV_HEADS * HEAD_DIM * bytes_per_value   # 2 = one key + one value

free_gb = GPU_GB - WEIGHTS_GB - OVERHEAD_GB
print(f"Memory left for the KV cache: {free_gb} GB\n")
print(f"{'KV precision':<14}{'MB/token':>9}{'2K ctx':>9}{'32K ctx':>9}   (requests that fit)")
for label, b in [("16-bit", 2), ("8-bit", 1)]:
    per_tok = kv_bytes_per_token(b)
    fits = [int(free_gb * 1e9 // (per_tok * ctx)) for ctx in (2048, 32768)]
    print(f"{label:<14}{per_tok / 1e6:>9.2f}{fits[0]:>9}{fits[1]:>9}")

print("\nDecode speed vs batch size (memory-bound model of one decode step)")
print(f"{'batch':>5}{'ms/step':>9}{'tok/s per user':>16}{'tok/s total':>13}")
weights_ms = WEIGHTS_GB / BANDWIDTH_GBS * 1000      # read every weight once per step
for batch in (1, 8, 32, 64):
    step_ms = weights_ms + 0.25 * batch              # + illustrative per-request cost
    per_user = 1000 / step_ms
    print(f"{batch:>5}{step_ms:>9.1f}{per_user:>16.0f}{per_user * batch:>13.0f}")

# ttft.py - measure time to first token and streaming speed from a local Ollama model.
import json
import os
import time
import urllib.request

HOST = os.environ.get("OLLAMA_HOST_URL", "http://localhost:11434")
MODEL = os.environ.get("OLLAMA_MODEL", "qwen3.5:0.8b")
PROMPT = "List five negative test cases for a login form, one line each."

def run_once():
    body = {"model": MODEL, "stream": True, "options": {"temperature": 0},
            "messages": [{"role": "user", "content": PROMPT}]}
    req = urllib.request.Request(HOST + "/api/chat", data=json.dumps(body).encode("utf-8"),
                                 headers={"Content-Type": "application/json"})
    start = time.perf_counter()
    first = None
    with urllib.request.urlopen(req, timeout=300) as resp:
        for line in resp:                       # one JSON object per line
            chunk = json.loads(line)
            if first is None and chunk.get("message", {}).get("content"):
                first = time.perf_counter() - start
            if chunk.get("done"):
                total = time.perf_counter() - start
                tokens = chunk["eval_count"]
                return first, total, tokens

for i in range(3):                              # run 1 includes loading the model
    first, total, tokens = run_once()
    print(f"run {i + 1}: first token {first * 1000:7.0f} ms | total {total:5.1f} s | "
          f"{tokens} tokens | {tokens / (total - first):5.1f} tok/s after first token")

Troubleshooting
  • Connection refused from ttft.py: Ollama isn't running; start the app or ollama serve. The first script needs nothing running.
  • TypeError about NoneType in ttft.py: no text arrived before the reply finished (for example, a model that only produced "thinking"). Try another prompt or model, or add "think": false to the request body.
  • Run 1 isn't slower: the model was already loaded from earlier use. Run ollama stop qwen3.5:0.8b first to see a cold start.
  • All numbers seem slow: check ollama ps; a model on CPU will be much slower than these samples.
Common misunderstandings
"Faster serving always means lower quality."
Continuous batching, prefix caching and speculative decoding don't change the model's outputs by design. Quantisation and distillation do, and need evaluation.
"Throughput and latency improve together."
Bigger batches raise throughput and slow each user's stream. You tune for a target, not for both at once.
"The weights are the main memory cost of serving."
At scale, the KV caches of all active conversations often use as much memory as the weights or more, especially with long contexts.
"Average latency tells you how the service feels."
Users notice the slow tail. Measure p95 and p99 under realistic load.
"Speculative decoding helps in every situation."
It helps most when the GPU has spare compute and the text is predictable; under heavy load the gains shrink.

139.7Review

Key takeaways
  • A serving stack adds an API server, scheduler, memory manager, GPU engine and streamer around the model.
  • Measure TTFT, time per output token, throughput and tail latency (p95/p99), not just averages.
  • vLLM, SGLang and TensorRT-LLM are the main open-source data-centre engines; llama.cpp and Ollama suit smaller deployments.
  • Continuous batching keeps the GPU full; PagedAttention, prefix caching and KV quantisation stretch scarce memory.
  • Quantisation and distillation make models cheaper but change them; speculative decoding speeds decode without changing outputs.
  • Treat every optimisation as a release: evaluate quality and load-test performance before and after.
Check yourself

What does continuous batching change compared with static batching?

Static batching waits for the slowest request in the group; continuous batching never leaves a slot idle while someone is waiting.

What problem did PagedAttention address?

Allocating the cache in small pages on demand left near-zero waste, so more requests fit in each batch.

Why can speculative decoding speed things up without changing the output?

Leviathan et al. (2022) showed exact equivalence; the gain comes from using idle compute in memory-bound decode.

Your team plans to switch a production model to a 4-bit quantised version. What should QA insist on?

Quantisation changes the model slightly, and the impact is task-specific. Performance and quality both need checking.

Which metric best captures "the answer starts appearing quickly"?

TTFT covers queueing and prefill; time per output token covers how fast it streams afterwards.

Teach it

"Serving a model to many people is mostly a memory problem. Every conversation keeps a KV cache on the GPU, and the more caches fit, the more people you can serve at once. Engines like vLLM keep the GPU busy by letting requests join and leave the batch at every step, and store caches in small pages so nothing is wasted. To make serving cheaper you can quantise the model, distil it into a smaller one, or use speculative decoding, where a small model guesses and the big one checks. The first two change the model, so you test quality; the last doesn't. Always measure time to first token and the slowest requests, not just averages."
