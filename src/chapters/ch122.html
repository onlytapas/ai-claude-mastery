Testers spend a surprising share of their week on things that aren't testing: making test data, fixing broken environments, rerunning flaky tests and nursing old test code back to health. These jobs are repetitive, detailed and well described in text, which is exactly where AI shines. Claude can produce hundreds of realistic, varied test records in seconds, read a 5,000-line log to find the one line that matters, and sort fifty flaky failures into likely causes. You still decide what's right. But the grind shrinks, and the time comes back to real testing.

122.1Why test data is a bottleneck

Ask any QA team what slows them down and "we didn't have the right data" is near the top. Typical problems:

ProblemWhat it looks like
Too little varietyEvery test user is "John Smith, 30, London". Bugs with long names, accents or old dates go unseen.
Missing edge casesNobody tested an order with 0 items, 9,999 items, or a price of £0.00.
Copies of productionSomeone copied real customer records into a test database "just this once". Now it's a privacy risk.
Stale dataTests break because a coupon expired or a user was deleted by another tester.
Slow to createA tester spends an afternoon building 40 rows in a spreadsheet by hand.

AI can help with all five, as long as you stay in charge of what "good data" means.

122.2Generating synthetic data with Claude

Synthetic data is test data that is made up, not copied from real people, but realistic enough to behave like real data. Claude is good at this because it has seen how names, addresses, dates and product descriptions look in many languages and countries.

In everyday life

Think of a film set. The shop fronts look real, the newspapers on the stand have headlines, the fruit looks fresh. None of it is a real shop. That's synthetic data: convincing enough to test the scene, with no real person's life involved.

A good data prompt

Prompt
Create 40 customer records for testing a UK/EU online shop's signup form, as CSV with columns:
first_name, last_name, email, date_of_birth (YYYY-MM-DD), country, postcode, phone, marketing_opt_in

Mix:
- 25 ordinary, realistic records across UK, Ireland, France, Germany and Poland
- 15 edge cases, each labelled in an extra "case" column:
  names with accents (Zoë, Łukasz), apostrophes (O'Brien), hyphens, very long names (60+ chars),
  a single-character first name, an email with a plus sign, an age of exactly 18 today,
  someone born on 29 February, empty optional fields, leading/trailing spaces

Rules: all invented people; use example.com / example.org emails only; phone numbers
must be clearly fake. Don't use any real person's name and details together.

Notice what the prompt does: it fixes the format, mixes normal and edge cases, labels each edge case so you know why it's there, and sets privacy rules (reserved example.com domains can never deliver email to a real person).

Real-world example

A tester asks for "20 test users" and gets 20 neat, similar records. A second tester uses the prompt above and finds, in the first run, that the signup form rejects "O'Brien" and trims "Zoë" to "Zo". Same tool, same minutes spent. The difference is that the second prompt asked for the edge cases.

Edge-case checklist to ask for

Text

  • Accents and non-Latin scripts (é, ß, 漢字, العربية)
  • Emoji
  • Apostrophes, quotes, hyphens
  • Very long and very short values
  • Leading or trailing spaces
  • Characters that break HTML or SQL (<, >, ', ;)

Numbers and dates

  • 0, negative, maximum allowed, one over the maximum
  • Decimals and rounding (0.005)
  • 29 February, 31 December, time-zone edges
  • Ages exactly at a limit (17, 18)
  • Very old and future dates
  • Different formats (1/2/2026 means different dates in different countries)

122.3Privacy: never use real people

Hard rule

Never paste real customer data into an AI chat, and never copy production data into test environments without your organisation's approved masking process. Data-protection laws such as the EU's GDPR apply to test environments too, and leaked "test" data is still a leak. Check your company's AI and data policies (Chapter 132).

When you truly need production-like data (for example, to reproduce a bug that only happens with real data shapes), the safe options are:

  • Masking: replace sensitive values (names, emails, card numbers) with fake ones while keeping the structure. "maria.lopez@bank.example" becomes "user0482@example.com".
  • Anonymisation: remove or generalise anything that could identify a person, even in combination (postcode + birth date + gender can identify many people).
  • Synthetic look-alikes: describe the shape of the real data to Claude ("orders have 1–30 lines, 5% use two currencies, some addresses have no postcode") and let it generate fresh records with the same shape.

Claude can help write masking scripts, but have the approach reviewed by whoever owns data protection in your organisation. AI doesn't replace that sign-off.

122.4Fixtures, seed files and data builders with Claude Code

In the chat app you get data as text. In Claude Code, Claude can write it straight into your project as files your tests load. A test fixture is the fixed starting data (or setup) a test needs.

Prompt in Claude Code
Look at @db/schema.sql and @tests/checkout.spec.ts.
Create tests/fixtures/orders.json with 12 orders that cover: empty basket, one item,
100 items, mixed VAT rates, a 100% discount coupon, a cancelled order and a refunded order.
Every order must match the schema's columns and constraints. Then write
tests/fixtures/seed.sql that inserts the same data. Don't change the schema or the app.

Because Claude reads the real schema, the data respects the actual rules: column names, required fields, foreign keys. That's the big advantage over a chat window.

Builders: data as code

Fixed files get stale. Many teams prefer a small builder (or factory): a function that creates a valid record with sensible defaults, where each test overrides only what it cares about. Ask Claude to create one:

tests/builders/customer.ts — the kind of builder Claude can write
import { faker } from '@faker-js/faker';

// A valid customer by default; override only what a test needs.
export function buildCustomer(overrides = {}) {
  return {
    firstName: faker.person.firstName(),
    lastName: faker.person.lastName(),
    email: faker.internet.email({ provider: 'example.com' }),
    country: 'GB',
    marketingOptIn: false,
    ...overrides,
  };
}

// In a test: only the detail that matters is visible.
// const minor = buildCustomer({ dateOfBirth: '2010-05-01' });

Here @faker-js/faker is a widely used open-source library that produces fake names, emails and addresses. Claude writes and explains the builder; the library supplies endless variety at run time without anyone pasting data around.

Fixed data, generated data, or both?

Fixed fixtures make failures easy to reproduce: the same data every run. Random generated data finds surprises, but a failure may not happen again. A common middle path is to generate data with a fixed seed (a starting number for the random generator), so "random" data is the same on every run until you change the seed. Faker libraries support this. Ask Claude: "Make the builder use a fixed seed in CI and a random seed locally, and print the seed when a test fails." Then any surprise can be replayed.

122.5Fixing test environments with AI

"It works on my machine" costs QA teams hours. Environment problems are mostly about reading: logs, configuration files and error messages. Claude Code can read them far faster than a person, and it can run the diagnostic commands too (with your permission).

Symptom"The test environment won't start"
CollectClaude runs status and log commands, and reads config files
Narrow downFinds the first real error, not the noise after it
ProposeExplains the cause and suggests a fix
You decideApprove the change, or take it to the environment owner
Prompt in Claude Code
Our local test stack won't start. Run `docker compose ps` and `docker compose logs --tail=200`,
read docker-compose.yml and .env.example (NOT .env), and tell me:
1) which service fails first and the exact error line,
2) the most likely cause, 3) the smallest fix. Don't change any files yet.

Two good habits are built into that prompt. It asks for the first failure, because later errors are often just knock-on effects. And it keeps Claude away from the real .env file, which may hold secrets (Chapter 98). Pair that with a deny rule in your settings (Chapter 78).

Real-world example

A database container keeps restarting. Two hundred log lines scroll past. Claude points to line 37: "port 5432 is already in use". A forgotten local database is still running. The fix takes ten seconds once someone finds that line; the finding was the expensive part.

122.6Flaky tests: a triage method

A flaky test passes sometimes and fails sometimes, with no change to the code. Flaky tests are dangerous because teams learn to ignore red builds, and then real failures get ignored too.

The five usual causes

CauseWhat's happeningTypical clue in the logs
TimingThe test checks before the page or service is readyTimeouts; "element not found" that passes on retry
OrderThe test depends on another test running firstFails only when run alone, or only in a certain order
Shared stateTests change the same user, basket or recordFails only when tests run in parallel
EnvironmentNetwork, slow machine, time zone, browser versionFails on CI but not locally; at certain times of day
DataRandom or expiring data produces an unlucky caseFails with one particular value; fails after a date

Using Claude Code to triage

Prompt in Claude Code
tests/checkout.spec.ts › "applies coupon" failed 3 times in the last 20 CI runs.
1. Read the test and the page objects it uses.
2. Read the three failure logs in ci-logs/ and compare them with a passing run.
3. Run it 20 times locally: npx playwright test tests/checkout.spec.ts -g "applies coupon" --repeat-each=20
4. Classify the most likely cause (timing, order, shared state, environment, data),
   quote the evidence, and propose a fix. Do NOT add fixed waits (waitForTimeout).

Playwright's --repeat-each option runs the same test many times, a quick way to make an intermittent failure show itself. Its trace viewer (with trace: 'on-first-retry' in the configuration) records exactly what the browser did on the failing attempt, and Claude can read the trace's error and step list with you.

Watch out

The lazy "fix" for timing problems is adding a fixed wait ("sleep 5 seconds"). It makes tests slower and still flaky. Ask Claude for a proper fix instead: wait for a specific condition, such as Playwright's web-first assertions that retry until an element is visible. Put this rule in your CLAUDE.md so it applies to every session (Chapter 77).

A fair quarantine policy

Sometimes you can't fix a flaky test today. Quarantine means moving it out of the main pass/fail gate so it doesn't block releases, while it's still run and tracked. A sensible policy, which Claude can help you write up and automate:

  1. A test that fails then passes on retry is labelled flaky automatically.
  2. Flaky tests go into quarantine with an owner and a ticket.
  3. Quarantined tests still run and report, but don't fail the build.
  4. Anything still in quarantine after an agreed period (say two sprints) is fixed or deleted. A test nobody fixes isn't protecting anyone.

122.7Test maintenance and "self-healing" tests

When developers change a page, tests that find elements by their old names break. Fixing these locators one by one is tedious. Claude Code can do it in bulk: read the failing tests, look at the new page (through the code or the Playwright MCP server, Chapter 102), and propose updated locators.

Prompt in Claude Code
The login page was redesigned in this branch. 9 tests in tests/auth/ now fail to find elements.
For each failure: find the element in the new markup, propose a resilient locator
(prefer getByRole / getByLabel / data-testid over CSS classes), and show me the diff.
If an element was genuinely removed, flag it — that may be a real bug, not a locator change.

The last line matters. Some tools advertise self-healing tests that automatically swap broken locators at run time. That can save time, but it has a real risk: if a button genuinely disappeared, a tool that quietly "heals" the test to click something else hides a bug. The safer pattern is assisted repair: AI proposes, a person reviews the diff, and anything that looks like a missing feature is reported, not patched.

Opinion · industry claims

Vendors often quote large reductions in maintenance effort from self-healing features. Treat such figures as marketing until you've measured them on your own suite. Chapter 126 shows how to measure effort saved honestly.

122.8Slimming the suite: duplicates and smart regression

Big test suites grow slow and repetitive. Claude can help in two ways.

Finding duplicates and gaps. Ask Claude Code to read a folder of tests and produce a table: what each test checks, which ones overlap almost completely, and which requirements have no test at all. You decide what to merge or delete; Claude does the reading.

Choosing what to run. Running everything on every change is safe but slow. Claude can read the change and suggest which tests matter most:

Prompt in Claude Code
Run `git diff main...HEAD --stat` and read the changed files.
List the test files most likely to be affected, ranked, with one line of reasoning each.
Then list areas that changed but have NO tests. Don't run anything yet.

Use this to prioritise (run the risky tests first, get feedback sooner), not to skip the full suite before a release. A model's guess about impact can miss hidden connections, such as a shared configuration file.

Common misunderstandings
"It's only test data, so real customer records are fine."
Privacy law and company policy still apply. Use synthetic or properly masked data.
"Retrying flaky tests fixes them."
Retries hide the symptom. Use retries to detect flakiness, then fix the cause.
"Self-healing means no more maintenance."
It can hide real bugs. Prefer AI-proposed fixes that a person reviews.
"AI-generated data covers every edge case."
Only the ones you or it thought of. Keep your own edge-case checklist and ask for it explicitly.

122.9Review

Key takeaways
  • Claude generates realistic synthetic data in seconds; the value comes from asking for labelled edge cases.
  • Never put real personal data into prompts or test environments; use synthetic or approved masked data.
  • In Claude Code, data respects your real schema; builders with fixed seeds give variety and reproducibility.
  • For environment problems, have Claude find the first real error, and keep it away from secret files.
  • Triage flaky tests by cause (timing, order, shared state, environment, data), fix without fixed waits, and quarantine with an owner and a deadline.
  • Use AI to propose locator repairs and regression priorities, with a person reviewing the result.
Check yourself

Why should test emails use example.com?

example.com and example.org are reserved for documentation and testing.

A test fails only when the whole suite runs in parallel. What's the most likely cause?

Parallel tests changing the same data is the classic shared-state problem.

What's the best fix for a test that checks a page before it's ready?

Condition-based waits are faster and reliable; fixed waits and retries hide the problem.

What's the main risk of fully automatic "self-healing" tests?

A disappeared button may be a bug. Assisted repair with review is safer.

Why use a fixed random seed for generated test data in CI?

Fixed seeds give variety you can replay.
