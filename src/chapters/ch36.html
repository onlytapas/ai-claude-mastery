Before you start: Chapter 24 (evaluations and benchmarks), Chapter 33 (reading benchmarks critically) and Chapter 35 (choosing a model). For the lab you need Python 3.9 or newer (Chapter 58); Chapter 86 shows how to get a Claude API key. You can do most of the lab offline, with no key at all.

Public benchmarks tell you how models do on someone else's tasks. To choose a model for your team, you need to know how it does on yours. The method is ordinary testing: write down what "good" looks like, collect realistic examples with expected answers, run every model on exactly the same inputs several times, grade the answers the same way, and compare accuracy, made-up answers, speed and cost. Save the results, so that when a new model or version arrives you can rerun the same test and see what got better or worse. This chapter gives you the method and a complete harness you can run today.

36.1Why test models yourself

A vendor's launch post might show its new model beating rivals on a dozen benchmarks. None of those benchmarks is "label our Jira bugs using our severity rules" or "extract the build number from our CI logs". Benchmarks also suffer from contamination and saturation, and they're run with settings you won't use (Chapter 33). The only evidence that answers your question is a test on your tasks.

Testers already have the right instincts. A model comparison is a test campaign: you have a system under test (each model), test cases (your examples), a test oracle (the grading), and a report. The new parts are that the system is non-deterministic, so you repeat runs, and that some answers are free text, so grading needs more thought.

In everyday life

A restaurant choosing a new supplier doesn't just read the supplier's brochure. The chef orders samples, cooks the restaurant's own dishes with them several times, has the same tasters score them blind, and checks the price per plate. A month later, when the supplier changes its recipe, the chef cooks the same dishes again. That's this whole chapter.

Real-world example

A QA team uses a model to suggest severities for incoming bug reports. A new, cheaper model is released, and the team wants to switch. Rather than argue about benchmarks, they run 120 past bug reports, with severities agreed by the triage group, through both models three times each. The cheaper model matches on most cases, but it marks two data-loss bugs as "Minor". The team switches anyway, adding a rule that any report mentioning data loss goes to a person. The decision took an afternoon and was backed by evidence anyone could rerun.

36.2The framework in eight steps

1. DecisionWhat are we choosing, and what would change our mind?
2. TasksThe real jobs, with success criteria
3. DatasetRepresentative examples with expected answers
4. Fixed set-upIdentical prompts and settings for every model
5. GradeCode checks first, rubric or judge for free text
6. MeasureAccuracy, hallucination, latency, tokens, cost
7. RepeatSeveral runs per case for consistency
8. Record and regressWrite the decision; rerun when models change

Step 1, the decision. Write one sentence: "Should our bug-triage job move from Model A to Model B?" Add your pass criteria before you see results, for example "B must be within 3 points of A's accuracy, have no more made-up answers, and cost less." Deciding the bar first stops you moving it afterwards.

Step 2, the tasks. List the jobs the model will actually do and what "correct" means for each. "Summarise a bug" isn't testable; "give a one-word severity from Critical, Major, Minor, Trivial using our definitions" is.

Step 4, a fixed set-up. Every model gets the same system prompt, the same user prompt and the same output limit. Record the model ID, date and settings. If one model needs a different prompt to work well, test that too, but label it as a separate configuration. You're comparing model plus prompt, so say so.

Don't tune on your test set

If you keep rewriting the prompt until Model B passes your 50 examples, you've trained the prompt on the test, and the score will look better than real life. Keep a separate handful of examples for prompt tweaking, and use the main set only for scoring.

36.3Building a representative dataset

Your dataset is a list of test cases: an input and the answer you'd accept (a golden answer). It should look like the real traffic, including the awkward parts.

IngredientWhat it meansQA example
Typical casesThe everyday bulk of the workClear bug reports with an obvious severity
Hard casesOnes people argue aboutA cosmetic bug on the payment page: Minor or Major?
Edge casesUnusual formats and lengthsA report written in German; a 5,000-line stack trace
Trap casesThe answer is not in the input"Which build was tested?" when no build is mentioned. The right answer is UNKNOWN.
Past failuresCases where a model got it wrong beforeThe data-loss bug labelled "Minor" last month

Trap cases measure hallucination directly: any answer other than "UNKNOWN" is invented (Chapter 22). They're cheap to write and very revealing.

How many cases? Start with 20–50 to find obvious differences, and aim for 100 or more before a decision that matters. Small sets can only show big differences (see the deeper note in 36.7). Where from? Past tickets, test cases and logs, with the agreed answers. Privacy: remove or replace personal and customer data before any of it goes to an external API, and check your company's AI policy.

Getting golden answers people agree on

If two experienced testers would give different severities for the same bug, a model can't be "wrong" on that case in any useful sense. Before scoring models, have two people label a sample independently and compare. Where they disagree, either sharpen the definition ("Critical means no workaround and affects payment or data") or drop the case. The share of cases where people agree is a ceiling: don't expect a model to beat the agreement level of your own team.

36.4Grading: code checks, rubrics and LLM judges

Grading is the test oracle. Use the simplest grader that works for each task.

GraderHow it worksGood forWatch out for
Exact or label matchCode compares the answer to the expected labelClassification, yes/no, severitiesFormatting noise ("Critical." versus "critical"): normalise first
Structured checkParse the JSON and compare fieldsExtraction from bug reports and storiesModels wrapping JSON in code fences: strip them
Contains / regexRequired values must appearBoundary values, IDs, error codesPassing answers that also contain wrong extras
Rubric scored by a personA checklist of what a good answer includes, scored 1–5Explanations, summaries, test ideasSlow; scorers drift. Use two scorers on a sample
LLM judgeA model scores the answer against the rubricFree text at scaleJudges favour longer answers and their own family's style. Check against human scores

An LLM judge is itself a model that can be wrong. Three habits keep it honest. Give it a specific rubric, not "is this good?" Ask for a fixed output format ("SCORE: 4") that code can parse. And before trusting it, score 20 answers yourself and check that the judge agrees with you on most of them. If possible, use a judge from a different family, or at least a different model, from the ones being compared.

Reasoning quality

"Did it reason well?" is a rubric question. Write down what good reasoning looks like for the task (cites the evidence in the report, considers impact and workaround, doesn't invent facts) and score against that. Don't grade the model's hidden "thinking"; grade the answer it gives and the reasons it states.

36.5What to measure

MetricDefinition used in the harnessWhy it matters
AccuracyShare of all runs that passed their graderThe headline quality figure
Reasoning qualityRubric score from the judge (pass at 4 or 5 out of 5)Quality of free-text answers
Hallucination rateShare of trap-case runs where the model invented an answer instead of saying UNKNOWNMade-up facts in a bug report or test result are dangerous
Latency p50 / p95Median and 95th percentile seconds per requestp95 shows the slow cases users notice
TokensAverage input and output tokens reported by the APIDifferent tokenizers and thinking change these
CostTokens × list price, including the judge; also per 1,000 tasksScales your test to production volume
ConsistencyShare of cases where every repeat got the same pass/fail resultA model that is right two times out of three is a flaky test

36.6The harness

A test harness is the code that feeds test cases to the system under test, collects the results and reports them. This one is two files: a dataset (tasks.jsonl) and a script (compare.py). The script uses only the Python standard library, plus Anthropic's official anthropic package for Claude. It has three kinds of provider:

  • anthropic: any Claude model ID, for example anthropic:claude-sonnet-5-5.
  • other: any provider that offers an OpenAI-compatible "chat completions" endpoint. Mistral's model card, for example, lists /v1/chat/completions. Check your provider's documentation for the base URL and model ID.
  • mock: two pretend models, careful and hasty, plus a pretend judge. They need no key and no internet, so you can see how everything works before spending anything.

The script: compare.py

compare.py
#!/usr/bin/env python3
"""compare.py - run the same tasks against several models and compare them.

Usage examples:
  python3 compare.py --models mock:careful mock:hasty
  python3 compare.py --models anthropic:claude-sonnet-5-5 anthropic:claude-haiku-5-5
  python3 compare.py --models anthropic:claude-sonnet-5-5 --baseline results/run-OLD.csv

Model specs are provider:model-id. Providers: anthropic, other (any
OpenAI-compatible chat completions endpoint) and mock (offline, no key needed).
"""
import argparse
import csv
import json
import math
import os
import re
import statistics
import sys
import time
import urllib.request
from datetime import datetime

# USD per million tokens: (input, output). Copied from the vendors' pricing
# pages on 9 Nov 2026. Prices change: check them before you trust a cost figure.
PRICES = {
    "claude-opus-5-5": (4.00, 20.00),
    "claude-sonnet-5-5": (2.00, 10.00),
    "claude-haiku-5-5": (0.10, 0.50),  # prompts up to 100K tokens
}
# Add other providers' prices here, e.g. via env: OTHER_PRICE_IN, OTHER_PRICE_OUT.

SYSTEM = ("You are a careful QA assistant. Follow the requested output format "
          "exactly. If the input does not contain the information asked for, "
          "answer UNKNOWN. Never guess.")

MAX_TOKENS = int(os.environ.get("MAX_TOKENS", "4000"))


# ---------------------------------------------------------------- providers
_anthropic_client = None


def call_anthropic(model, prompt, case):
    global _anthropic_client
    import anthropic  # pip install anthropic
    if _anthropic_client is None:
        _anthropic_client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY
    start = time.perf_counter()
    resp = _anthropic_client.messages.create(
        model=model, max_tokens=MAX_TOKENS, system=SYSTEM,
        messages=[{"role": "user", "content": prompt}])
    secs = time.perf_counter() - start
    # Keep only the visible answer; skip any thinking blocks.
    text = "".join(b.text for b in resp.content if b.type == "text")
    return text, resp.usage.input_tokens, resp.usage.output_tokens, secs


def call_other(model, prompt, case):
    base = os.environ["OTHER_BASE_URL"].rstrip("/")
    key = os.environ["OTHER_API_KEY"]
    field = os.environ.get("OTHER_MAX_TOKENS_FIELD", "max_tokens")
    body = {"model": model, field: MAX_TOKENS,
            "messages": [{"role": "system", "content": SYSTEM},
                         {"role": "user", "content": prompt}]}
    req = urllib.request.Request(
        base + "/chat/completions", data=json.dumps(body).encode(),
        headers={"Authorization": "Bearer " + key,
                 "Content-Type": "application/json"})
    start = time.perf_counter()
    with urllib.request.urlopen(req, timeout=180) as r:
        data = json.load(r)
    secs = time.perf_counter() - start
    text = data["choices"][0]["message"].get("content") or ""
    usage = data.get("usage", {})
    return (text, usage.get("prompt_tokens", 0),
            usage.get("completion_tokens", 0), secs)


def call_mock(model, prompt, case):
    """Fake models so you can test the harness offline. Deterministic."""
    exp = case.get("expected")
    rep = case.get("_repeat", 0)
    if model == "judge":  # pretend judge: 5 for the reference answer, else 2
        return ("SCORE: 5" if case["_answer"] == case["expected"]
                else "SCORE: 2"), 200, 5, 0.40
    if model == "careful":
        text = json.dumps(exp) if isinstance(exp, dict) else (
            "\n".join(exp) if isinstance(exp, list) else exp)
        return text, len(prompt) // 4 + 40, 30, 1.20
    # "hasty": fast, mostly right, invents answers, wobbles on one case
    wrong = {"sev-02": "Minor", "trap-01": "4.2.17", "trap-02": "12",
             "explain-02": "It is a test."}
    if case["id"] == "kind-01" and rep == 1:
        return "BUGREPORT", len(prompt) // 4 + 40, 5, 0.30
    if case["id"] in wrong:
        return wrong[case["id"]], len(prompt) // 4 + 40, 8, 0.30
    if isinstance(exp, dict):
        return "```json\n" + json.dumps(exp) + "\n```", len(prompt) // 4, 25, 0.35
    if isinstance(exp, list):
        return "\n".join(exp), len(prompt) // 4 + 40, 10, 0.30
    return exp, len(prompt) // 4 + 40, 20, 0.30


PROVIDERS = {"anthropic": call_anthropic, "other": call_other, "mock": call_mock}


def call(spec, prompt, case):
    provider, _, model = spec.partition(":")
    if provider not in PROVIDERS or not model:
        sys.exit(f"Bad model spec '{spec}'. Use provider:model-id, "
                 f"provider one of {sorted(PROVIDERS)}")
    return PROVIDERS[provider](model, prompt, case)


def cost_usd(spec, tok_in, tok_out):
    provider, _, model = spec.partition(":")
    if provider == "mock":
        return 0.0
    if model in PRICES:
        p_in, p_out = PRICES[model]
    elif provider == "other" and "OTHER_PRICE_IN" in os.environ:
        p_in = float(os.environ["OTHER_PRICE_IN"])
        p_out = float(os.environ["OTHER_PRICE_OUT"])
    else:
        return float("nan")  # unknown price: shown as n/a
    return (tok_in * p_in + tok_out * p_out) / 1_000_000


# ---------------------------------------------------------------- graders
def first_word(text):
    words = re.findall(r"[A-Za-z0-9.]+", text)
    return words[0].strip(".").upper() if words else ""


def parse_json(text):
    text = re.sub(r"^```(json)?|```$", "", text.strip(), flags=re.M).strip()
    return json.loads(text)


def grade(case, answer, judge_spec):
    """Return (passed, hallucinated or None, note, judge_cost)."""
    kind, exp = case["type"], case["expected"]
    if kind == "label":
        got = first_word(answer)
        return got == exp.upper(), None, got, 0.0
    if kind == "unanswerable":
        said_unknown = "UNKNOWN" in answer.upper()
        return said_unknown, not said_unknown, answer.strip()[:40], 0.0
    if kind == "contains_all":
        missing = [s for s in exp if not re.search(rf"\b{re.escape(s)}\b", answer)]
        return not missing, None, "missing " + ",".join(missing) if missing else "all present", 0.0
    if kind == "json":
        try:
            got = parse_json(answer)
        except (ValueError, TypeError):
            return False, None, "not valid JSON", 0.0
        bad = [k for k, v in exp.items() if str(got.get(k)).lower() != str(v).lower()]
        invented = any(exp[k] == "UNKNOWN" and str(got.get(k)).upper() != "UNKNOWN"
                       for k in bad)
        return not bad, (True if invented else None), "wrong " + ",".join(bad) if bad else "ok", 0.0
    if kind == "rubric":
        judge_prompt = (
            "You are grading an answer. Use only this rubric.\n\n"
            f"<rubric>{case['rubric']}</rubric>\n<question>{case['prompt']}</question>\n"
            f"<answer>{answer}</answer>\n\nReply with one line: SCORE: <1-5>")
        judge_case = dict(case, _answer=answer)
        text, t_in, t_out, _ = call(judge_spec, judge_prompt, judge_case)
        m = re.search(r"SCORE:\s*([1-5])", text)
        score = int(m.group(1)) if m else 0
        return score >= 4, None, f"judge score {score}", cost_usd(judge_spec, t_in, t_out)
    raise ValueError(f"unknown task type {kind}")


# ---------------------------------------------------------------- helpers
def percentile(values, pct):
    """Nearest-rank percentile; fine for small samples."""
    if not values:
        return float("nan")
    ordered = sorted(values)
    rank = max(1, math.ceil(pct / 100 * len(ordered)))
    return ordered[rank - 1]


def fmt(x, spec="{:.2f}"):
    return "n/a" if isinstance(x, float) and math.isnan(x) else spec.format(x)


def load_cases(path):
    with open(path, encoding="utf-8") as f:
        return [json.loads(line) for line in f if line.strip()]


# ---------------------------------------------------------------- main
def run(args):
    cases = load_cases(args.tasks)
    rows = []
    for spec in args.models:
        for case in cases:
            for rep in range(args.repeats):
                c = dict(case, _repeat=rep)
                try:
                    answer, t_in, t_out, secs = call(spec, case["prompt"], c)
                    passed, halluc, note, judge_cost = grade(c, answer, args.judge)
                    error = ""
                except Exception as e:  # keep going; record the failure
                    answer, t_in, t_out, secs = "", 0, 0, float("nan")
                    passed, halluc, note, judge_cost = False, None, "", 0.0
                    error = f"{type(e).__name__}: {e}"[:200]
                rows.append({
                    "model": spec, "case": case["id"], "type": case["type"],
                    "repeat": rep, "passed": int(passed),
                    "hallucinated": "" if halluc is None else int(halluc),
                    "latency_s": round(secs, 3), "tokens_in": t_in,
                    "tokens_out": t_out, "cost_usd": cost_usd(spec, t_in, t_out),
                    "judge_cost_usd": judge_cost, "note": note, "error": error,
                    "answer": answer.replace("\n", " ")[:300]})
                print(f"{spec:32} {case['id']:11} rep {rep}  "
                      f"{'PASS' if passed else 'FAIL'}  {error or note}")
    return rows


def summarise(rows, models):
    print("\nSUMMARY (per model)")
    head = (f"{'model':32} {'acc%':>5} {'consist%':>8} {'halluc%':>7} "
            f"{'p50 s':>6} {'p95 s':>6} {'in tok':>7} {'out tok':>7} "
            f"{'total $':>8} {'$/1k tasks':>10} {'errors':>6}")
    print(head)
    print("-" * len(head))
    for spec in models:
        r = [x for x in rows if x["model"] == spec]
        ok = [x for x in r if not x["error"]]
        acc = 100 * sum(x["passed"] for x in r) / len(r)
        by_case = {}
        for x in r:
            by_case.setdefault(x["case"], set()).add(x["passed"])
        consist = 100 * sum(len(v) == 1 for v in by_case.values()) / len(by_case)
        traps = [x for x in r if x["hallucinated"] != ""]
        halluc = (100 * sum(x["hallucinated"] for x in traps) / len(traps)
                  if traps else float("nan"))
        lat = [x["latency_s"] for x in ok]
        total = sum(x["cost_usd"] + x["judge_cost_usd"] for x in r)
        print(f"{spec:32} {acc:5.0f} {consist:8.0f} {fmt(halluc, '{:.0f}'):>7} "
              f"{fmt(percentile(lat, 50)):>6} {fmt(percentile(lat, 95)):>6} "
              f"{statistics.mean(x['tokens_in'] for x in r):7.0f} "
              f"{statistics.mean(x['tokens_out'] for x in r):7.0f} "
              f"{fmt(total, '{:.4f}'):>8} {fmt(1000 * total / len(r), '{:.2f}'):>10} "
              f"{len(r) - len(ok):6d}")


def compare_baseline(rows, path):
    with open(path, newline="", encoding="utf-8") as f:
        old = list(csv.DictReader(f))

    def rates(rs):
        out = {}
        for x in rs:
            out.setdefault(x["case"], []).append(int(x["passed"]))
        return {k: sum(v) / len(v) for k, v in out.items()}

    before, now = rates(old), rates(rows)
    print(f"\nREGRESSION CHECK against {path}")
    worse = [(c, before[c], now[c]) for c in now if c in before and now[c] < before[c]]
    better = [(c, before[c], now[c]) for c in now if c in before and now[c] > before[c]]
    for c, b, n in worse:
        print(f"  WORSE   {c:11} pass rate {b:.0%} -> {n:.0%}")
    for c, b, n in better:
        print(f"  BETTER  {c:11} pass rate {b:.0%} -> {n:.0%}")
    if not worse and not better:
        print("  No case changed pass rate.")
    return len(worse)


def main():
    ap = argparse.ArgumentParser(description=__doc__,
                                 formatter_class=argparse.RawDescriptionHelpFormatter)
    ap.add_argument("--models", nargs="+", required=True)
    ap.add_argument("--tasks", default="tasks.jsonl")
    ap.add_argument("--repeats", type=int, default=3)
    ap.add_argument("--judge", help="model that grades rubric tasks "
                    "(default: mock:judge for mock runs, else anthropic:claude-opus-5-5)")
    ap.add_argument("--baseline", help="earlier results CSV to compare against")
    args = ap.parse_args()
    if args.judge is None:
        all_mock = all(m.startswith("mock:") for m in args.models)
        args.judge = "mock:judge" if all_mock else "anthropic:claude-opus-5-5"

    if any(m.startswith("anthropic:") for m in args.models + [args.judge]) \
            and not os.environ.get("ANTHROPIC_API_KEY"):
        sys.exit("Set ANTHROPIC_API_KEY first (see the setup steps).")
    if args.baseline and not os.path.exists(args.baseline):
        sys.exit(f"Baseline file not found: {args.baseline}")
    rows = run(args)
    os.makedirs("results", exist_ok=True)
    out = datetime.now().strftime("results/run-%Y%m%d-%H%M%S-%f.csv")
    with open(out, "w", newline="", encoding="utf-8") as f:
        w = csv.DictWriter(f, fieldnames=list(rows[0]))
        w.writeheader()
        w.writerows(rows)
    summarise(rows, args.models)
    print(f"\nRaw results: {out}")
    if args.baseline:
        sys.exit(1 if compare_baseline(rows, args.baseline) else 0)


if __name__ == "__main__":
    main()
How the script works, section by section

Providers. Each call_* function takes a model ID, a prompt and the test case, and returns the answer text, input tokens, output tokens and seconds taken. call_anthropic uses the Messages API through the official SDK; it keeps only the text blocks of the reply, because current Claude models may also return "thinking" blocks. call_other sends a plain HTTPS request to {OTHER_BASE_URL}/chat/completions with a Bearer token. call_mock returns scripted answers so the output is predictable.

Graders. grade() picks a grader by task type. Label tasks compare the first word. JSON tasks strip code fences, parse, and compare each expected field; if a field should be UNKNOWN but the model filled it in, that counts as a hallucination. Trap tasks pass only if the answer contains UNKNOWN. Rubric tasks send the question, rubric and answer to the judge model and parse "SCORE: n".

Runner. For every model, case and repeat, it calls the model, grades the answer and appends a row. Exceptions such as a network error are caught and recorded in the error column, so one failure doesn't stop the run.

Reporting. Every row goes to a timestamped CSV in results/, which you can open in a spreadsheet. The summary computes the metrics from 36.5. With --baseline, it compares the pass rate of each case with an earlier CSV and exits with code 1 if any case got worse, which is what a CI job needs (exit code).

Prices in the script

The PRICES table holds Anthropic's list prices on 9 November 2026: Opus 5.5 $4 / $20, Sonnet 5.5 $2 / $10 and Haiku 5.5 $0.10 / $0.50 per million tokens (Haiku's rate rises for prompts over 100K tokens, which these tests never reach). Check the pricing page and update the table before you rely on a cost figure. For an other: model, set OTHER_PRICE_IN and OTHER_PRICE_OUT; otherwise its cost shows as n/a.

How many cases do you need to trust a difference?

With 10 cases, one case is worth 10 percentage points, so "80% versus 90%" can be one unlucky example. A common rough guide for a pass rate measured on n independent cases is that the 95% margin of error is at most about 1 ÷ √n: about ±32 points for 10 cases, ±14 for 50 and ±10 for 100. Repeats help with consistency but don't replace more cases, because three runs of the same case aren't independent evidence about other cases. Practical rule: use small sets to find big differences quickly, and grow the set before a close call. When two models are within the margin, decide on cost, speed or risk instead.

36.8Regression testing when models change, and the decision record

Models change under you. Versions are retired (Anthropic's deprecations page lists Claude Sonnet 4.5 retiring on 30 November 2026), new ones arrive every few weeks, and a vendor can change behaviour behind an alias. Your saved results are the baseline. Rerun the same dataset whenever you change model, prompt or settings, and compare case by case. This is regression testing for AI.

Terminal
python3 compare.py --models mock:careful
mv "$(ls -t results/run-*.csv | head -1)" results/baseline.csv   # keep the newest run as the baseline
python3 compare.py --models mock:hasty --baseline results/baseline.csv
echo $?                                             # 1 means at least one case got worse
Expected output (end of the second run)
REGRESSION CHECK against results/baseline.csv
  WORSE   sev-02      pass rate 100% -> 0%
  WORSE   kind-01     pass rate 100% -> 67%
  WORSE   trap-01     pass rate 100% -> 0%
  WORSE   trap-02     pass rate 100% -> 0%
  WORSE   explain-02  pass rate 100% -> 0%

Because the script exits with 1 when any case gets worse, you can put it in a CI pipeline (Chapter 125). A failing pipeline then means "the new model or prompt broke something that used to work", with the exact cases named. Keep the dataset in version control alongside the prompts.

The decision record

A decision record is a short document that captures what was decided, why, and on what evidence, so someone can challenge it later or redo it when things change. Keep it next to the dataset.

decision-record.md (template)

Common misunderstandings
"One run per case is enough."
Models are non-deterministic. Repeats reveal flaky answers that a single run hides, as kind-01 showed.
"An LLM judge is objective."
It's another model with its own biases, such as preferring longer answers. Check it against human scores first.
"Higher accuracy wins."
Not if the difference is within the margin of error, or if the winner costs ten times more. Decide on pre-written criteria.
"We tested it, so it's settled."
Models, prices and versions change. Rerun the same dataset on every change and on a schedule.
"The public benchmark already answered this."
Benchmarks test other people's tasks with other settings. Use them for a shortlist, not the decision.

36.9Review

Key takeaways
  • Treat a model comparison as a test campaign: decision, tasks, dataset, fixed set-up, grading, metrics, repeats, record.
  • Write the pass criteria before you see results.
  • Include trap cases whose correct answer is UNKNOWN; they measure hallucination directly.
  • Grade with code wherever possible; use rubrics and an LLM judge for free text, checked against human scores.
  • Measure accuracy, hallucination rate, consistency, p50/p95 latency, tokens and cost per 1,000 tasks.
  • Small datasets only reveal big differences; grow the set before close calls.
  • Save results as a baseline and rerun on every model, prompt or setting change, ideally in CI.
Check yourself

Why write the pass criteria before running the comparison?

Deciding the bar first keeps the decision honest, as with any test plan.

A trap case asks for a build number that isn't in the report. The model answers "4.2.17". What does this measure?

The right answer was UNKNOWN; any specific value is invented.

Model A passes 9 of 10 cases and Model B passes 8 of 10. What's the soundest conclusion?

With 10 cases, one case is 10 points, well within the margin of error.

What is the best first grader for "reply with one word: Critical, Major, Minor or Trivial"?

Use the simplest grader that works; a label match is fast, free and repeatable.

Why does compare.py --baseline exit with code 1 when a case gets worse?

A non-zero exit code is how scripts tell CI that something failed.

Assignment

Build a dataset of at least 30 real, anonymised cases for one AI task your team runs, including at least five trap cases and five hard cases, with golden answers agreed by two people. Run it against two models with three repeats. Write a decision record with pass criteria set beforehand, the summary table, the cases where the models differed, and a review date. Commit the dataset, script and record to a repository so the comparison can be rerun.

Teach it

"Choosing a model is just testing. Decide what we're choosing and what 'good enough' means before we look. Collect real examples with agreed answers, including trick questions where the right answer is 'unknown', because those catch made-up answers. Give every model exactly the same prompts, run each case three times, grade with code where we can and with a rubric where we can't, and compare accuracy, invented answers, speed and cost per thousand tasks. Save the results, and when a new model comes out, rerun the same set and see what got worse."
