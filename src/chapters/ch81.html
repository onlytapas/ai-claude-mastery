A subagent is a helper that Claude hands a self-contained job to. It works in its own fresh context window, with its own instructions, its own tool list and, if you like, a cheaper or stronger model. When it finishes, only its summary comes back to your conversation, not the hundreds of lines it read along the way. You define your own subagents as small Markdown files in .claude/agents/, and Claude decides when to use them from a one-line description. Used well, subagents keep long sessions focused, enforce "read-only" roles, and let you reuse a good reviewer across every project.

81.1What a subagent is

Every Claude Code session has one main conversation. Everything Claude reads, every command it runs and every result it sees lands in that conversation's context window. That's fine for a quick change. It becomes a problem when a side task produces a flood of material you'll never look at again: a 4,000-line CI log, the output of a full test run, a search through fifty files.

A subagent solves this by doing the noisy part somewhere else. Claude writes a short task message (the "delegation prompt"), a subagent picks it up in a brand-new context window, works through it with its own tools, and returns one summary. Your main conversation receives the summary and nothing else.

You ask"Why did last night's regression run fail?"
Claude delegatesWrites a task message for the log-analyst subagent
Subagent worksReads the 4,000-line log in its own context window
Summary returns"3 failures, all timeouts on the payments API after 02:10"
You continueYour main context holds the summary, not the log
In everyday life

A test lead asks a colleague: "Go through last night's run and tell me what broke." The colleague spends an hour in the logs and comes back with three bullet points. The lead never has to read the logs, and their head stays clear for the release meeting. A subagent is that colleague. The written brief you give them matters, because they weren't in the meeting and know only what you tell them.

Each subagent has its own system prompt (the standing instructions that shape how a model behaves), its own tool access and its own permissions. The official documentation lists five benefits: keeping exploration out of your main context, enforcing constraints by limiting tools, reusing a configuration across projects, specialising behaviour with a focused prompt, and controlling cost by sending suitable tasks to a faster, cheaper model such as Haiku.

Subagents use your plan too

A subagent sends its own requests to the model, and those count towards the same usage limits as your main conversation. Delegating saves context, not necessarily tokens. Five subagents running in parallel can use more of your allowance than doing the work yourself.

Why the tool is called "Agent" (and sometimes "Task")

Claude starts a subagent by calling a tool. In version 2.1.63 that tool was renamed from Task to Agent. Old Task(...) references in settings and agent files still work as aliases, so you may meet both spellings in older team repositories. Permission rules, hook matchers and tool lists should use Agent for anything new.

81.3Where subagent files live

A custom subagent is a Markdown file. Where you put it decides who gets it. When two subagents share a name, the higher-priority location wins.

PriorityLocationWho gets itTypical use
1 (highest).claude/agents/ inside the managed settings directoryEveryone the organisation deploys it toCompany-mandated reviewers
2--agents '<json>' on the command lineThat one sessionQuick experiments, CI scripts
3.claude/agents/ in the projectEveryone who clones the repo (commit it)A team's QA reviewer for this codebase
4~/.claude/agents/You, in every projectYour personal helpers
5 (lowest)A plugin's agents/ folderWherever the plugin is enabledShared kits (Chapter 84)
  • Subfolders are fine. Both agent folders are scanned recursively, so .claude/agents/review/ works. The folder doesn't change the subagent's identity: only the name field does.
  • Nested projects. Claude Code walks up from your working directory to the repository root and reads every .claude/agents/ it finds; the one closest to you wins a name clash.
  • Hot reload. Edits to existing files are picked up within a few seconds. Restart only when you created the first agent in a brand-new agents folder, because a running session doesn't watch folders that didn't exist at start-up.
  • Plugin subagents are named with the plugin as a prefix, such as my-plugin:reviewer.

For a one-off session, you can define subagents inline as JSON. Each key is a name; prompt plays the role of the Markdown body:

Terminal (from the official docs)
claude --agents '{"code-reviewer": {"description": "Expert code reviewer.", "prompt": "You are a senior code reviewer.", "tools": ["Read", "Grep", "Glob", "Bash"], "model": "sonnet"}}'

With -p (non-interactive mode), --agents also accepts the path to a JSON file holding the same object (v2.1.281 or later).

81.4The file format

A subagent file has two parts. At the top, between two --- lines, is frontmatter: settings written in YAML, a simple "key: value" format. Below it is plain Markdown, which becomes the subagent's system prompt.

.claude/agents/code-reviewer.md (the documented example)
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.

Only name and description are required. The subagent receives this body plus basic environment details such as the working directory. It does not receive Claude Code's own long system prompt, so write the body as a complete brief.

Silent failures

Field names are camelCase and must match exactly: disallowedTools, not disallowed-tools (that hyphenated style belongs to skills). Claude Code ignores unknown fields without an error. It also silently skips a file with no name, a name but no description, a --- that isn't on the first line, or YAML that doesn't parse. Run claude plugin validate .claude/agents to catch parse errors before a session (v2.1.233+), and claude --debug to see why a file was skipped.

Plugin subagents are restricted

For security, subagents that come from a plugin ignore hooks, mcpServers and permissionMode. If you need those, copy the file into .claude/agents/ or ~/.claude/agents/.

81.5Tools and permissions

Limiting tools is the most useful thing a subagent definition does. A reviewer that can't edit files can't "helpfully" rewrite the code it was asked to review.

Allowlist with tools

Only these tools, nothing else. No MCP tools unless you list them.

tools: Read, Grep, Glob, Bash

Denylist with disallowedTools

Everything the subagent would inherit, minus these.

disallowedTools: Write, Edit
  • If both are set, disallowedTools is applied first; a tool in both is removed.
  • MCP servers: tools: mcp__github__* grants every tool from the github server; disallowedTools: mcp__github withholds them; disallowedTools: mcp__* withholds every MCP tool.
  • A trap: disallowedTools: Bash(git push *) removes the whole Bash tool, not just pushes. To keep Bash but block pushes, put Bash(git push *) in permissions.deny in settings, which applies to the main conversation and every subagent.
  • Background subagents get fewer tools. Subagents Claude starts from the main conversation run in the background by default, and a background subagent keeps only a fixed set of built-in tools (Read, Grep, Glob, Bash, Edit, Write, WebFetch, WebSearch and some others) plus every MCP tool. Interactive tools such as AskUserQuestion are never available to subagents.
  • Nesting. A subagent can start its own subagents, up to three layers below the main conversation by default (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH changes this; 1 turns nesting off). Leave Agent out of a reviewer's tools list to keep it from delegating.

Permission mode. If you don't set permissionMode, the subagent inherits the main conversation's mode. Even if you do, the main session often wins: when the main conversation is in bypassPermissions, acceptEdits or auto, the subagent runs in that mode; in plan mode it stays in plan mode. Your value applies only when the main session is in default or dontAsk. Background subagents send their permission prompts to your main session, naming the subagent that's asking.

81.6Choosing a model

The model field lets you match the model to the job. A log summariser rarely needs your most capable model; a security reviewer might.

1. Per callA model Claude passes when it starts the subagent (an alias only)
2. FrontmatterThe file's model field; inherit means "same as main"
3. EnvironmentCLAUDE_CODE_SUBAGENT_MODEL, if set
4. FallbackThe main conversation's model

That order applies from v2.1.251; before that, the environment variable came first. To force one model onto every subagent, set both CLAUDE_CODE_SUBAGENT_MODEL and CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1 (v2.1.257+). Run /tasks while a subagent is working to see which model and effort level it's actually on. Your organisation's availableModels allowlist still applies; a blocked choice is swapped for an allowed one with a warning.

Real-world example

A QA team runs its log-analyst on haiku with effort: low because it only reads and summarises, and its qa-reviewer on sonnet because judging whether an assertion is meaningful needs more reasoning. The main session stays on whatever model each person prefers.

81.7Calling a subagent

There are four ways, from gentlest to strongest:

HowWhat you doWhat's guaranteed
AutomaticNothing. Claude matches your request against each subagent's description. Phrases such as "use proactively" in the description encourage itNothing; Claude decides
By name"Use the qa-reviewer subagent to check tests/checkout/"Claude usually delegates
@-mentionType @ and pick it, e.g. @"qa-reviewer (agent)" check the new tests, or type @agent-qa-reviewerThat subagent runs for this task
Whole sessionclaude --agent qa-reviewer, or "agent": "qa-reviewer" in settingsThe main thread itself takes on its prompt, tools and model

With an @-mention, your full message still goes to Claude, which writes the subagent's task prompt. The mention controls which subagent runs, not the exact words it receives. With --agent, the subagent's prompt replaces Claude Code's default system prompt entirely, much as --system-prompt does, and the name shows as @qa-reviewer in the start-up header.

Foreground, background and forks

A foreground subagent blocks the conversation until it's done. A background subagent runs while you keep working, and its result arrives later as a notification. With nothing configured, subagents that Claude starts from the main conversation run in the background.

A fork is a special subagent that inherits the whole conversation so far instead of starting fresh, so you don't have to re-explain anything. Its own tool calls still stay out of your context. Start one yourself with /subtask:

In a Claude Code session
/subtask draft negative test cases for the coupon rules we just discussed

"Fork mode", on by default from v2.1.302, lets Claude start forks on its own; while it's on, Claude can't wait for a subagent in an interactive session. To let Claude wait for results, set CLAUDE_CODE_FORK_SUBAGENT to 0 in the env block of your settings and restart. To stop forks only, add "Agent(fork)" to permissions.deny.

81.8What a subagent sees (and doesn't)

This is where most disappointing subagents go wrong. A non-fork subagent starts with:

  • its own system prompt (your Markdown body) plus environment details;
  • the task message Claude writes when it delegates;
  • your CLAUDE.md files at every level (except Explore, Plan and subagents with omitClaudeMd);
  • a git status snapshot (except Explore and Plan);
  • the full text of any skills listed in its skills field.

It does not see your conversation history, the files Claude has already read, the skills you've already invoked, your output style or your auto memory. If something in the chat matters, it must be in the delegation prompt, so ask Claude to include it: "Delegate to the qa-reviewer and tell it we use data-qa attributes, not data-testid."

Persistent memory

The memory field gives a subagent its own notes folder that survives between sessions. The subagent's prompt then includes the first 200 lines or 25KB of that folder's MEMORY.md, and Read, Write and Edit are enabled so it can maintain its notes.

ScopeFolderWhen
user~/.claude/agent-memory/<agent-name>/Learnings useful in all projects
project.claude/agent-memory/<agent-name>/Project knowledge the team can share through git (the recommended default)
local.claude/agent-memory-local/<agent-name>/Project knowledge that stays off git

Subagent memory is part of auto memory: turn auto memory off (Chapter 77) and the field has no effect.

81.9When to delegate, and when not to

Use the main conversation when…Use a subagent when…Use a skill instead when…
You'll go back and forth refining the workThe task produces lots of output you won't need againYou want a reusable procedure that runs in your main conversation
Planning, coding and testing share a lot of contextYou want to enforce a tool restriction, such as read-onlyThe instructions matter more than the isolation
It's a quick, targeted change, or speed matters (a fresh subagent has to gather context first)The work is self-contained and can be summarisedYou want it on demand as /name (Chapter 80)

Three patterns from the documentation are worth knowing by name: isolate high-volume work ("use a subagent to run the suite and report only the failures"), parallel research (several subagents each investigate an independent area), and chaining (reviewer finds issues, then a second subagent fixes them). For a quick question about something already in the conversation, /btw is lighter than any subagent.

Opinion · this textbook's authors

Start with zero custom subagents. Add one only when you notice the same pattern twice: a side task flooding your context, or a role that should never have write access. Teams that create ten subagents on day one tend to end up with overlapping descriptions, and Claude then picks the wrong one. Anthropic's own guidance points the same way: keep descriptions short, because every custom subagent's description sits in context in every session.

81.10The /agents change

Older tutorials, videos and blog posts show /agents opening an interactive wizard with tabs for creating and editing subagents. That's out of date. On Claude Code v2.1.197 and earlier, /agents opened that interface. In current versions it only prints a reminder: ask Claude to create or manage subagents, or edit .claude/agents/ and ~/.claude/agents/ directly.

Don't confuse these three

/agents (in a session) is the reminder described above. claude agents (in your shell) opens agent view, which monitors and dispatches background sessions (Chapter 69), not subagents. /list-agents lists subagents, teammates and sessions Claude can message, and appears only when cross-session messaging is on. To see subagents running right now, use /tasks.

The easiest way to create a subagent today is to ask for one, then read what Claude wrote:

Prompt
Create a project subagent in .claude/agents/ called qa-reviewer that reviews
automated tests for weak assertions, fixed waits and missing negative cases.
Make it read-only and have it use Sonnet.

81.11Two QA subagents, built properly

1. The test reviewer

Read-only by design, so it can only report. The body is a complete brief, because the subagent won't see your conversation.

.claude/agents/qa-reviewer.md
---
name: qa-reviewer
description: Reviews automated test code (Playwright, pytest, API tests) for weak assertions, fixed waits, flaky patterns and missing negative cases. Use proactively after tests are written or changed.
tools: Read, Grep, Glob
model: sonnet
color: green
---

You are a senior QA engineer reviewing automated tests. You never edit files.

For each test file you are given (or every changed test file if none is named):
1. Check that each test asserts something meaningful about behaviour,
   not just that a page loaded or a call returned.
2. Flag fixed waits (waitForTimeout, time.sleep) and suggest a web-first
   assertion or explicit wait instead.
3. Flag brittle locators (CSS chains, nth-child, auto-generated ids).
4. List missing cases: invalid input, empty states, boundaries, permissions.
5. Note any test that could pass even if the feature were broken.

Reply with a table: file, line, problem, why it matters, suggested fix.
End with the three most important changes. If everything looks fine, say so
plainly rather than inventing problems.

2. The log analyst

Its job is to read huge files so your main conversation doesn't. It runs on a cheaper model at low effort and can't change anything.

.claude/agents/log-analyst.md
---
name: log-analyst
description: Reads CI, test-runner and application logs and returns a short failure summary. Use when the user asks why a run failed or shares a log file.
tools: Read, Grep, Glob
model: haiku
effort: low
color: cyan
---

You analyse log files for a QA team. Never paste large chunks of the log back.

1. Find every failure, error and exception. Use Grep before reading whole files.
2. Group failures that share a root cause (same error text, same endpoint,
   same time window).
3. For each group give: count, first occurrence (timestamp and line number),
   one representative error line, and your best guess at the cause, labelled
   as a guess.
4. Separate test-code problems (bad locator, wrong data) from product
   problems (5xx responses, crashes) and environment problems (timeouts,
   DNS, out of memory).

Finish with a one-line verdict: product bug, test bug, environment, or unclear.
Real-world example: using them together

"Use the log-analyst on artifacts/nightly.log, then have the qa-reviewer look at whichever test files the failures point to." Claude chains the two: the analyst's summary tells it which files matter, and the reviewer reads only those. Your main conversation ends up with two short reports instead of a log and a dozen test files.

Common misunderstandings
"The subagent knows what we've been discussing."
A normal subagent starts fresh and sees only its own prompt, CLAUDE.md and Claude's delegation message. Only a fork inherits the conversation.
"Subagents save money."
They save main-conversation context. They spend their own tokens, which count towards the same limits. A cheaper model can lower cost; parallel subagents can raise it.
"/agents is where I manage subagents."
Not any more. It prints a reminder; edit the files or ask Claude. claude agents is something else entirely (background sessions).
"disallowedTools: Bash(rm *) blocks only rm."
A specifier there removes the whole Bash tool. Use a deny rule in settings for command-level blocking.
"If I misspell a field, Claude Code will tell me."
Unknown fields are ignored silently. Validate files and check the debug log.

81.12Review

Key takeaways
  • A subagent does a self-contained job in its own context window and returns only a summary, keeping your main conversation focused.
  • Built-ins include Explore and Plan (read-only, no CLAUDE.md) and general-purpose; disable any with Agent(name) in permissions.deny.
  • Custom subagents are Markdown files with YAML frontmatter in .claude/agents/ (team) or ~/.claude/agents/ (personal); only name and description are required, and the body is the system prompt.
  • tools and disallowedTools restrict capability; model and effort match cost to the job; memory gives persistent notes.
  • Claude delegates from the description; an @-mention guarantees a specific subagent; --agent runs the whole session as one.
  • /agents no longer opens an editor (since after v2.1.197): ask Claude or edit the files, and validate them with claude plugin validate .claude/agents.
Check yourself

What comes back to your main conversation when a normal subagent finishes?

The point of a subagent is that the noisy work stays in its own context window and only the result returns.

Which two frontmatter fields are required in a subagent file?

Everything else is optional. A file without a description is skipped with only a debug-log message.

You want a reviewer subagent that can read files and run Bash but never edit. Which is simplest?

An allowlist gives exactly those tools and nothing else, so Edit and Write are unavailable.

A colleague says "type /agents to open the subagent editor". On Claude Code 2.1.319, what happens?

The interactive interface existed only up to v2.1.197. Agent view is claude agents in the shell.

Your log-analyst gives poor answers because it doesn't know which test environment failed, which you mentioned earlier in the chat. Why?

Ask Claude to include the detail in the delegation, put it in the subagent's body, or use a fork, which inherits the conversation.

Assignment

Pick one recurring, noisy task in your team's work: reading CI logs, scanning a test report, or checking a pull request's tests. Write a project subagent for it with a precise description, the smallest tool list that works, and a model chosen on purpose. Validate it with claude plugin validate .claude/agents, use it on three real cases, and note each time whether Claude delegated automatically. Revise the description until it does. Commit it with a short note in your team's CLAUDE.md saying it exists and when to use it.

Teach it

"A subagent is a helper Claude hands a job to. It works in its own separate memory, with its own instructions and tools, and only its summary comes back, so a 4,000-line log never clutters our main session. You create one as a small Markdown file in .claude/agents: a name, a description of when to use it, which tools it may use and which model. Make reviewers read-only, put cheap jobs on Haiku, and remember it doesn't see our chat, so the brief has to be complete. And /agents no longer opens an editor: just ask Claude to write the file."
