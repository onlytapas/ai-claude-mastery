Before you start: Chapter 14 (tokens). Chapter 19 helps for the part about thinking tokens.

A language model has no memory of its own between requests. Everything it "knows" about your conversation is the text sent to it each time, and that text has to fit in its context window, measured in tokens. Current Claude models can hold 1 million tokens, which is a lot, but quality drops as the window fills, a problem Anthropic calls context rot. Every "memory" feature, from Claude's app memory to CLAUDE.md, works by putting the right text back into the window. Good results come from curating what goes in, not from filling it up.

20.1The model forgets everything, every time

This surprises most people: when you send your tenth message in a chat, the model does not "remember" the first nine. The app sends the whole conversation so far to the model again, together with your new message. The model reads it all from the start, writes a reply, and then forgets it. Next time, the app sends everything again, now including that reply.

Turn 1 sentinstructions + message 1
Turn 2 sentinstructions + message 1 + reply 1 + message 2
Turn 3 sentinstructions + messages 1–2 + replies 1–2 + message 3
…untilthe total reaches the context window limit

Anthropic's documentation describes the context window as "all the text a language model can reference when generating a response, including the response itself", and as the model's "working memory". It is completely separate from what the model learned in training (Chapter 17).

In everyday life

Imagine a brilliant contractor with no long-term memory who visits each morning. Before they start, you hand them a folder: the brief, yesterday's notes, the latest emails. They read the whole folder, do excellent work, and leave. Tomorrow they remember nothing, so the folder is everything. The context window is the size of that folder. A bigger folder holds more, but a folder stuffed with irrelevant paper makes it harder to find what matters.

20.2What fills the window

Your visible messages are only part of it. Anthropic's documentation says that everything in the request counts: the system prompt, every message (including tool results, images and documents), tool definitions, and the output Claude generates, including its thinking.

20.4Context rot: why more isn't automatically better

Anthropic's documentation is direct about this: "more context isn't automatically better. As token count grows, accuracy and recall degrade, a phenomenon known as context rot. This makes curating what's in context just as important as how much space is available."

Several effects combine:

  • Dilution. Attention (Chapter 16) has to spread across more tokens. One key sentence among 500,000 tokens of logs competes with everything else.
  • Distraction. Old, wrong or irrelevant material can pull answers off course. An abandoned approach from an hour ago is still in the window, and the model may keep using it.
  • Position effects. Researchers have found that models use information at the start and end of a long input more reliably than information in the middle.
Under the hood: "lost in the middle"

In 2023, Nelson Liu and colleagues at Stanford published "Lost in the Middle: How Language Models Use Long Contexts", which gave the lost in the middle effect its name. They gave models a question plus many documents, only one of which held the answer, and moved that document around. Accuracy was highest when the answer was near the beginning or the end, and dropped noticeably when it was in the middle: a U-shaped curve. The models they tested were 2023 models, and newer ones handle long inputs much better, but the general lesson has held: position and clutter matter.

A popular test for this is the "needle in a haystack": hide one fact in a long text and ask for it. Modern models usually pass simple versions. Harder versions, which need several hidden facts combined or reasoning about them, still show drops as length grows. That is why the lab in 20.8 hides three facts, not one.

Anthropic's prompting guidance also suggests putting long documents before your question, and its vision guide says the same about images. Your instructions then sit at the end, close to where the model starts writing.

What happens when it's full

On the API, Anthropic documents two cases. If the input alone exceeds the window, the request fails with a "prompt is too long" error. If the input fits but the reply runs into the limit while being written, generation stops with the stop reason model_context_window_exceeded. Chat apps handle this for you: Anthropic notes that interfaces such as claude.ai "can also manage the context window on a rolling 'first in, first out' basis", and Claude Code compacts automatically (20.5). Either way, older detail is lost, so don't rely on something said long ago.

20.5Compaction and clearing

When a session grows long, there are three ways to make room. All three throw something away, so it pays to know which you're using.

TechniqueWhat it doesWhere (Verified 9 Nov 2026)

In everyday life

Compaction is like a colleague handing over a ticket with a summary comment: "Tried A and B, both failed; root cause is likely the cache; next step is C." You lose the detail of every attempt but keep what matters. If the summary misses something important, it's gone, which is why /compact lets you say what to keep: /compact keep the failing test names and the exact error messages.

Real-world example: choosing between them

You've spent 90 minutes in Claude Code fixing a flaky Playwright test and it's now fixed. Next you want to write API tests for a different service. Use /clear: nothing from the flaky-test hunt helps, and it would only distract. If instead you're halfway through the same investigation and the session is getting slow, use /compact with instructions about what to preserve.

20.6"Memory" is text put back into the window

If the model forgets everything, how do Claude's memory features work? They all do the same basic thing: store notes outside the model and insert the relevant ones into the context window at the start of a conversation or when needed. This is a form of context engineering. Nothing about the model itself changes.

Two consequences follow. First, memory costs context: a 5,000-line CLAUDE.md is read at the start of every session and competes with your actual task. Keep memory files short and specific; Chapter 77 shows how. Second, memory is only as good as what's written: if a saved note is wrong or outdated, Claude will confidently use it. Review memory like you'd review test data.

Under the hood: memory versus training

It's natural to assume that when Claude "remembers" your preference, it has learned it. It hasn't. The model's weights, the billions of numbers set in training (Chapter 11), don't change when you chat. Changing them is fine-tuning, a separate and much heavier process (Chapter 18).

Memory systems are retrieval: they decide which stored text is relevant and add it to the prompt. That's the same idea as RAG (Chapter 23), applied to your own notes. It also explains why memory can be inspected, edited and deleted, and why turning memory off immediately changes behaviour: the notes simply aren't sent any more.

On the API, nothing is remembered unless your code sends it. If you build an application, your code owns the conversation history, and you decide what to keep, summarise or drop. Anthropic also offers a memory tool for agents that store notes in files your application controls; Chapter 88 covers designing this.

20.7Prompt caching, briefly

Because the whole conversation is sent again every turn, the same long beginning (system prompt, tools, documents) is processed over and over. Prompt caching lets the API store that processed beginning for a short time and reuse it. Anthropic's default cache lifetime is 5 minutes, with a 1-hour option. Cached reads are much cheaper: for example $0.20 instead of $4 per million input tokens on Opus 5.5 (verified 9 Nov 2026).

One point people often miss: cached tokens still take up the context window. Anthropic puts it plainly: caching "changes what you pay for those tokens, not whether they count." Caching fixes cost, not context rot. Chapter 90 covers caching properly.

Opinion · Anthropic's engineering team

In its article "Effective context engineering for AI agents", Anthropic's engineering team argues that context should be treated as a finite resource with diminishing returns, and that the goal is the smallest set of high-signal tokens that gets the job done. Not every practitioner agrees on how aggressively to trim; some prefer giving models more material and letting them search it. Both views agree that what's in the window matters more than its size.

  2. Open Claude Code in that folder with claude. Run /context and note the "messages" figure.a coloured grid; messages near zero; the system prompt, tools and any memory files already using some space.
  3. Ask: "Read haystack.log in full and list every NOTE line, with its line number. Do not use grep or any search command." Then run /context again.probably all three notes; messages usage jumps by tens of thousands of tokens. (If you use claude.ai instead, upload the file and ask the same question.)
  4. Run /clear, then ask: "Find every NOTE line in haystack.log." Run /context.Claude uses a search command, gets all three in seconds, and uses a tiny fraction of the context. This is the main lesson: search, don't stuff.
  5. Run /compact keep only the three NOTE facts after step 3 (repeat it if you cleared), then ask "What was the code freeze date?""14 March", answered from the summary.
  6. Ask: "Remember that our staging environment resets every Friday at 18:00." Then run /memory.Claude saves it to auto memory; /memory lists your memory files and the auto-memory folder.
  7. Exit, start a new session with claude, and ask "When does staging reset?""Friday at 18:00", because the note was put back into the new session's context.
make_haystack.py (Python 3, standard library only)
"""Write a long, boring test log with three facts hidden in it."""
import random

random.seed(7)  # same file every time
SUITES = ["checkout", "login", "search", "profile", "payments", "cart"]
FACTS = {
    0.05: "NOTE: staging environment resets every Friday at 18:00",
    0.50: "NOTE: release 4.2 code freeze moved to 14 March",
    0.95: "NOTE: flaky test cart_spec:88 owned by team Falcon",
}
TOTAL = 4000

lines = []
for i in range(TOTAL):
    for position, fact in FACTS.items():
        if i == int(TOTAL * position):
            lines.append(f"[{i:05d}] {fact}")
    suite = random.choice(SUITES)
    ms = random.randint(40, 900)
    lines.append(f"[{i:05d}] PASS {suite}_spec:{random.randint(1, 200)} ({ms} ms)")

with open("haystack.log", "w", encoding="utf-8") as f:
    f.write("\n".join(lines) + "\n")
print(f"Wrote haystack.log with {len(lines)} lines "
      f"(about {sum(len(l) for l in lines) // 1000} KB).")
Troubleshooting

Claude used grep in step 3 anyway: that's sensible behaviour; repeat the instruction or accept it and compare with step 4. Step 7 doesn't recall the fact: check /memory shows auto memory on, or that you're in the same folder (auto memory is per project). If your organisation turned it off, add the line to CLAUDE.md via /memory instead. No Claude Code access: do steps 1, 3 and 4 in claude.ai by uploading the file, and use a Project's instructions for steps 6–7.

Common misunderstandings
"Claude remembers our earlier conversation because it learned from it."
The model never changes. Apps resend the history and memory features insert saved notes.
"With 1M tokens I can paste everything."
You can, but quality degrades as context grows (context rot), and you pay for every token. Curate.
"Compaction is lossless."
It's a summary. Detail is dropped. Tell /compact what to keep.
"Prompt caching gives me more room."
Cached tokens still count toward the window. Caching lowers cost and speeds up processing.
"A longer CLAUDE.md makes Claude smarter about our project."
Only if it's relevant. It is loaded every session and competes with the task. Short and specific wins.
"Incognito means nothing is sent to the model."
The conversation is still sent to the model to be answered; incognito chats just aren't saved to history or memory.

20.9Review

Key takeaways
  • The model is stateless: every turn, the whole relevant conversation is sent again and must fit in the context window.
  • The window holds system prompt, tools, memory files, history, tool results, images, thinking and the new reply.
  • Current Claude models: 1M-token window, 128K-token maximum reply (verified 9 Nov 2026).
  • Context rot: accuracy and recall degrade as context grows, and the middle of long inputs is used less reliably.
  • Compaction summarises, clearing starts fresh, context editing removes by rule. All drop something.
  • Memory features (apps memory, Projects, CLAUDE.md, auto memory) are text inserted into the window, not learning.
  • Caching saves money but not space. Search rather than stuff; one task per session.

Teach it

"Claude doesn't remember our conversation. Every time we send a message, the whole conversation gets sent again, and it has to fit in a fixed space called the context window. Claude's window is huge, a million tokens, but the fuller it gets, the worse it gets at finding the important bit. So we keep it clean: one task per session, let Claude search logs instead of pasting them, and clear or compact when it gets long. Memory features like CLAUDE.md just paste our notes back in at the start, so keep them short and correct."
