"Claude" is a word people use for several different things. The model is the trained brain that turns text into text. A harness is the software wrapped around it that gives it tools, memory and a loop to keep working. An app (claude.ai, the desktop and mobile apps, Claude Code) is a harness with a screen for people. The API is the door programs use to reach the model directly, and the Agent SDK lets you build your own harness. MCP is a standard plug that connects any of these to outside tools. Knowing which piece you are using tells you what it can do, what it costs, and where your data goes.

41.1Why the word "Claude" causes confusion

Listen to a team talk about AI for ten minutes and you will hear sentences like these:

  • "Claude can't read our Jira." (It can, if someone connects it. That is a connector question, not a model question.)
  • "Claude Code is a different model from claude.ai." (Usually it is the same model family with a different harness around it.)
  • "We can't use Claude, it isn't approved." (Perhaps the consumer app isn't, but the company's AWS account may already offer Claude through Bedrock.)
  • "Claude remembered our project." (Memory is a feature of the app, not something the model learned.)

Each sentence mixes up different layers. This chapter gives you a clear map so you can say precisely which piece you mean. That precision matters for support questions, for security reviews and for budgets.

In everyday life

Think of a car. The engine provides the power (the model). The car around it, with steering, brakes, dashboard and fuel tank, makes the engine useful (the harness and app). You can buy a finished car (claude.ai or Claude Code), or buy just the engine and build your own vehicle (the API and Agent SDK). Accessories such as a tow bar or roof rack plug into standard fittings (MCP). And you can buy the same engine from the manufacturer's showroom or from a dealer you already have an account with (Anthropic directly, or a cloud platform). Same engine, different packaging, different paperwork.

41.2The pieces, one by one

The model

A model is the trained neural network: Fable 5.1, Opus 5.5, Sonnet 5.5 or Haiku 5.5 (Chapter 40). On its own a model does exactly one thing. It receives text (and images or documents) and produces text. It cannot open a file, browse a website or run a test. It does not remember yesterday's conversation. Everything else people associate with "Claude" is built around it.

A model can, however, ask for an action. Through tool use it writes a structured request such as "please run npx playwright test login.spec.ts". Some other piece of software must decide whether to do it, do it, and send back the result.

The harness

That other software is the harness. An agentic harness runs the agent loop: send the task to the model, receive a tool request, run the tool (after checking permissions), feed the result back, and repeat until the job is done. The harness also manages the context window, decides which instructions to load (such as CLAUDE.md), and enforces the safety rules your organisation set.

Why this matters

Two products using the same model can behave very differently because their harnesses differ. Claude Code's harness can edit files and run shell commands on your machine; the claude.ai chat harness cannot touch your laptop's files at all. When something works in one and not the other, the harness is usually the reason.

The apps

An app is a harness plus a user interface built for people. Anthropic's apps include:

  • Claude apps on the web (claude.ai), desktop (macOS, Windows; Linux in beta) and mobile (iOS, Android): chat, Projects, Artifacts, Research, memory, connectors and more (Part VI, starting at Chapter 43).
  • Claude Code: an agentic coding tool that works in your terminal, in VS Code, Cursor and JetBrains, in the desktop app, on the web at claude.ai/code and in GitHub Actions (Part VIII, starting at Chapter 63).
  • Claude Cowork, Claude in Chrome, Claude for Excel, PowerPoint and Word and Claude Tag (Claude in Slack): Claude placed inside the places people already work (Chapter 51).

You sign in to apps with a Claude account, and they are paid for by a subscription plan (Chapter 42). Claude Code is the exception that can use either a subscription or an API key.

The API and the Console

The Claude API is how programs talk to the model directly. Your code sends a request to the Messages endpoint (POST /v1/messages) with a model name, a maximum reply length and the conversation, and receives the model's reply. There is no chat window, no memory and no file access unless you build them. You pay per token. Chapter 86 walks you through your first call.

Developers manage API keys, billing and usage in the Claude Console at platform.claude.com (it moved there from console.anthropic.com in 2025). The Console groups keys and spending limits into workspaces, for example one for the QA team's CI jobs and one for an internal chatbot.

The API also offers ready-made server tools that run on Anthropic's side, such as web search, web fetch and code execution, and a hosted agent service called Managed Agents (in beta since 8 April 2026) for teams that want Anthropic to run the agent loop and sandbox for them.

The Agent SDK

The Claude Agent SDK is a software library (an SDK) for Python (claude-agent-sdk) and TypeScript (@anthropic-ai/claude-agent-sdk). Anthropic describes it as giving developers "the same tools, agent loop, and context management that power Claude Code". In car terms, it is the chassis, steering and brakes from a finished car, ready for you to build your own vehicle. It was called the Claude Code SDK until 29 September 2025. Chapter 110 builds agents with it.

MCP and connectors

The Model Context Protocol (MCP) is an open standard, announced by Anthropic on 25 November 2024 and donated in December 2025 to the Agentic AI Foundation under the Linux Foundation. It defines a common way for an AI application to talk to outside systems through MCP servers: one for Jira, one for a browser, one for a database. In the Claude apps these appear as connectors; in Claude Code you add them with claude mcp add. MCP is not part of the model. It is a plug standard that harnesses use. Part XI (Chapter 97 onward) covers it fully.

Cloud platforms

The same Claude models are also sold through the big cloud providers: Amazon Bedrock, Google Cloud (Vertex AI, which Claude Code's docs now call "Google Cloud's Agent Platform") and Microsoft Foundry. Anthropic also lists "Claude Platform on AWS" and "Claude Models on Google Cloud (Anthropic managed)". Model IDs are similar (for example anthropic.claude-opus-5-5 on Bedrock), but the partner sets the price, handles billing and signs the contract. Companies often choose this route because their cloud account, security reviews and spending commitments already exist.

Real-world example: one task, three routes

A team wants Claude to draft test cases from new Jira stories.

  • Route A, the app: a tester connects the Jira connector in claude.ai, opens a Project with the team's test-case template, and asks Claude to draft cases for PROJ-412. No code, uses the tester's plan.
  • Route B, Claude Code: a QA engineer runs Claude Code in the test repository with a Jira MCP server, and asks it to draft the cases and write the Playwright specs. Uses the engineer's plan or the team's API key.
  • Route C, your own tool: a developer writes a small Python service with the Agent SDK that runs whenever a story moves to "Ready for QA" and posts draft cases as a Jira comment. Pays per token through the API or Bedrock.

Same model family in all three. Different harness, different cost model, different data rules.

Opinion · a common recommendation from practitioners

Many experienced teams suggest climbing the stack from the top: prove the idea in the app, automate it with Claude Code, and only write code against the API or SDK when the workflow has to run unattended or at scale. The argument is that each step down costs more engineering effort, so you should know the idea works first. Teams with strong developers sometimes skip straight to the API; neither path is "correct".

Every route sends your prompt, and anything attached to it, to wherever the model runs. What happens next depends on which door you used and which agreement covers it. The most common data mistake

A tester pastes a production customer record into a personal Free or Pro account "just to check a bug". That data is now under consumer terms, outside the company's contract, possibly with training switched on. The model is the same as in the company's Team plan; the agreement is not. Use your organisation's approved route, and mask real personal data (Chapter 132).

Under the hood: what actually travels in a Claude Code request

When Claude Code asks the model for its next step, the request contains the system instructions, your CLAUDE.md files, the conversation so far, and the results of any tools that ran: file contents Claude read, command output, test logs, MCP responses. So if Claude Code reads your .env file, its contents go to the model provider. That is why teams add deny rules such as Read(./.env) to their settings (Chapter 78), and why an organisation can enforce such rules for everyone through managed settings (Chapter 42). Which provider receives the request depends on the credential Claude Code is using: a subscription login and an Anthropic API key both go to Anthropic; setting CLAUDE_CODE_USE_BEDROCK, CLAUDE_CODE_USE_VERTEX or CLAUDE_CODE_USE_FOUNDRY sends requests through that cloud instead.

Common misunderstandings
"Claude Code uses a special coding model."
Claude Code uses the same Claude models as everything else (Opus 5.5 by default on most plans). What's special is the harness: tools, permissions and the agent loop.
"The model remembers my previous chats."
The model has no memory between requests. Memory, Projects and CLAUDE.md are app features that put saved text back into the context.
"MCP is something the model does."
The model only asks for a tool. The harness connects to the MCP server, runs the call and returns the result.
"Claude on Bedrock is a different, weaker Claude."
It is the same model family sold through a different door, with different pricing, contracts and sometimes a lag before the newest model appears.
"If the model is the same, the data rules are the same."
Data rules follow the agreement (consumer, commercial, cloud partner, MCP server owner), not the model.

41.6Review

Key takeaways
  • The model turns input into output; it cannot act or remember on its own.
  • A harness runs the agent loop, executes tools, enforces permissions and manages context. Apps are harnesses with a screen; Claude Code is the most capable one for software work.
  • The API is the programmatic door, paid per token; the Agent SDK lets you build your own harness with Claude Code's loop; Managed Agents hosts one for you.
  • MCP is an open plug standard used by harnesses to reach outside systems. Connectors are MCP inside the apps.
  • Cloud platforms sell the same models under your cloud contract. Data rules follow the route and agreement, so pick the approved route for company data.
Check yourself

Claude Code runs npx playwright test on your laptop. Which piece actually executes the command?

The model only requests the command. Claude Code checks permissions, runs it locally and returns the output to the model.

What does the Claude Agent SDK give a developer?

Anthropic describes it as "the same tools, agent loop, and context management that power Claude Code", for Python and TypeScript.

Your company already pays for AWS and wants Claude under that contract. Which route fits?

Bedrock offers Claude models through AWS, with AWS pricing and contracts. Pro is a consumer plan; a connector is a plug for tools, not a way to buy model access.

By default, are API inputs and outputs used to train Anthropic's models?

Anthropic's privacy centre says commercial products, including the API, are not used for training by default. Submitted feedback is the main exception.

A tester says "Claude remembered our coding conventions from last week". What is the most accurate explanation?

Models don't learn from individual chats. Apps re-insert saved information into each request.
