A project is a folder for related chats that comes with its own reference material and its own standing instructions. Everything you put in the project's knowledge, such as your test strategy, glossary and Jira conventions, is available in every chat you start inside it, and the instructions shape how Claude answers there. You set the context up once instead of re-pasting it into every chat. On Team and Enterprise plans you can share a project, so a whole QA team works from the same material and the same rules. A project doesn't make Claude learn permanently; it just gives it the same well-chosen starting context every time.

47.1The problem projects solve

Imagine you use Claude every day to write test cases for one product. Each new chat starts blank. So each time you paste the product overview, explain your test-case template, remind Claude that you use Gherkin, and mention that the payments module is out of scope. That is slow, and it drifts: today's paste is slightly different from yesterday's, so the output varies.

Anthropic describes projects as "self-contained workspaces with their own chat histories and knowledge bases". You put the stable context in once, and every chat in the project starts with it.

In everyday life

A project is like the onboarding pack and desk you give a new contractor. The binder on the desk holds the reference documents (knowledge). The note taped to the monitor says how you like things done (instructions). Every morning they sit at the same desk, so you don't explain it all again. But they don't remember yesterday's conversations unless they're written down in the binder.

Projects are available on every plan. Free accounts can create up to five; the help centre doesn't state a cap for paid plans. At the time of writing (UI liable to change):

The help centre says the project's name and description are for people, not for Claude. If something matters to the answers, put it in the instructions or the knowledge.

On Team and Enterprise you also choose visibility when you create it: keep it private, or share it with your broader organisation. Enterprise organisations can require tags on projects. 47.3Project knowledge

Project knowledge is the set of documents, text files and code you add to the project. Claude uses it in every chat in that project. Files follow the project limits from Chapter 46: up to 30 MB each, with text extracted (multimodal PDFs are the exception, so their charts and images can be read).

What makes good knowledge for a QA team

Put inWhyLeave out
Test strategy and definition of doneClaude can check work against your actual rulesOld strategies that contradict the current one
Product overview and domain glossaryFewer wrong assumptions about features and termsMarketing copy with no testable detail
Test-case and bug-report templates, with one good example eachConsistent output format across the teamTen examples of varying quality
API specification (for example an OpenAPI file)Accurate API test ideas and payloadsSecrets, tokens, real customer data
Known risks, out-of-scope list, environments tableClaude stops suggesting tests you can't runAnything you'd not show every project member
Knowledge goes stale

Claude can't tell that last quarter's environments table is out of date. Put a "last updated" date at the top of each knowledge file, keep one owner per file, and delete superseded versions instead of adding new ones next to them. Conflicting files give inconsistent answers.

Under the hood: what happens when knowledge gets big

When the knowledge is small, it is simply placed in Claude's context window at the start of each chat, alongside the instructions. Claude can see all of it at once.

On paid plans (Pro, Max, Ultra, Team, Enterprise), when the knowledge approaches the context limit, Claude automatically switches to RAG, retrieval-augmented generation. Instead of reading everything, it searches the knowledge for the passages most relevant to your question and reads those. The help centre says this expands capacity "by up to 10x" while aiming to keep response quality. You'll learn how retrieval works in Chapter 23.

The trade-off: with retrieval, Claude sees the parts it found, not the whole. A question like "list every requirement across all specs" may miss items that the search didn't surface. For exhaustive checks on big document sets, attach the specific files to the chat, or split the work.

On the Free plan there is no retrieval mode, so the whole knowledge base must fit in the context window.

47.4Project instructions

Project instructions are standing guidance that applies to every chat in the project. They work much like a system prompt: who Claude should act as, what format to use, what to avoid. Everything in Chapter 44 and Chapter 45 applies, with one difference: instructions are read for every question, so they should be about how to work, not about one task.

Example project instructions: QA for a checkout product
You are a senior QA engineer on the "ShopFast" checkout team.

Context
- Product, environments and scope are in the project knowledge.
  Prefer it over general knowledge. If the knowledge doesn't cover
  something, say so instead of assuming.
- Payments provider internals are out of scope (see out-of-scope.md).

When writing test cases
- Use the template in test-case-template.md.
- Write scenarios in Gherkin (Given/When/Then).
- Cover positive, negative and boundary cases; label each.
- Link each case to its Jira story key if one is given.

When writing bug reports
- Use bug-template.md. Severity uses the scale in test-strategy.md.
- Only state facts I gave you or that are visible in attachments.

Always
- British English. Be concise. Use tables for lists of cases.
- End with "Open questions" if anything was ambiguous.

Good instructions

Short, stable rules. Point to files by name. Say what to do when the knowledge is silent. Describe format once. Under a page.

Weak instructions

A specific task ("write tests for story SHOP-412"), which belongs in a chat. Long copies of documents already in knowledge. Vague style words ("be thorough and amazing"). Rules that contradict the files.

Real-world example

A team's project instructions said "always produce 20 test cases". Test case quality fell for small stories, because Claude padded the list. They changed it to "produce as many cases as the risk warrants, usually 5 to 15, and explain any gaps", and reviews got faster. Instructions are rules for every chat, so a number that suits one story hurts another.

47.5What is shared between chats, and memory

This is a common surprise. Chats inside one project do not automatically see each other. The help centre says context isn't shared across project chats unless it is in the project knowledge. If a chat produced a useful result, such as an agreed list of risk areas, save it as a file in the knowledge so later chats can use it.

Memory adds a layer on top. Each project has its own memory, separate from your other projects. Claude uses it alongside your non-project (account) memory, but never another project's memory. To keep a project completely separate, turn off "Use account memory" in the project's Memory settings. To skip memory for a single chat, turn off "Memory" in the "+" menu before your first message. Memory is covered fully in Chapter 50.

47.6Sharing projects on Team and Enterprise

Sharing a project is a Team and Enterprise feature. Shared projects are how a QA team gets the same context and the same rules, instead of five slightly different personal copies.

To share, open the project and click "Share project" next to its name, add colleagues by name or email (several at once), choose a role and click "Share". You can also make a project visible to the whole organisation. A "Shared with you" tab on the Projects page lists projects others have shared with you.

RoleWhat they can doTypical QA use
Can viewSee the project's contents, knowledge and instructions, and chat in it; cannot change itTesters, developers and analysts who use the project
Can editChange instructions and knowledge, manage members and their settings (and add tags on Enterprise)The QA lead and one or two maintainers
Labels vary between help articles

The current "create and manage projects" article calls the read-only role "Can view"; an older sharing article called it "Can use". The meaning is the same. Check what your app shows.

Each member's chats in a shared project are their own. Sharing the project shares the knowledge and instructions, not everyone's conversations. Chats are shared separately, as snapshots (Chapter 51).

Admin controls

  • Owners can turn off project sharing for the organisation. Turning off "Share projects" also turns off public (organisation-wide) projects; existing shares stay in place.
  • Owners or Primary Owners can turn off organisation-wide visibility separately.
  • Enterprise organisations can require tags on projects.
  • If an artifact was made inside a project, people you share it with also need access to the project (Chapter 48).
Sharing the knowledge shares the files

Everyone with access can see every knowledge file. Before sharing org-wide, re-read the knowledge list as if you were the newest person in the company. Remove anything with personal data, credentials or confidential customer names.

Opinion · this textbook's authors

For teams, the most useful pattern is one shared "source of truth" project per product, with few editors and many viewers, plus personal projects for experiments. Editing rights for everyone tends to produce duplicated and conflicting knowledge within weeks.

Troubleshooting. Claude ignores the template: check the file name in your instructions matches the uploaded file exactly. Answers invent policy: strengthen the "if the knowledge doesn't cover something, say so" line. No "Share project" button: sharing is Team and Enterprise only, or your owner has turned it off. "New Project" missing on Free: you may already have five projects; archive or delete one.

Common misunderstandings
"Claude learns from my project and gets permanently better at my product."
The model doesn't change. Each chat is given the instructions and knowledge (and any project memory) as context. Remove a file and Claude no longer knows what was in it.
"All chats in a project can see each other."
They can't, unless information is saved in the knowledge or picked up by project memory.
"Putting the project's purpose in its description guides Claude."
Claude can't see the name or description. Use the instructions.
"Sharing a project shares my chats in it."
It shares knowledge and instructions. Each person's chats stay their own.
"More knowledge is always better."
Outdated or conflicting files make answers worse, and on large projects retrieval may surface the wrong one. Curate.

47.8Review

Key takeaways
  • A project bundles chats with shared knowledge and standing instructions, so you set context up once.
  • Projects are on all plans; Free accounts can create up to five. Retrieval for large knowledge (up to about 10 times more) is on paid plans.
  • Instructions should be short, stable rules about how to work; tasks belong in chats.
  • Chats in a project don't share context with each other; each project has its own memory, separate from other projects.
  • Team and Enterprise can share projects with "Can view" or "Can edit" roles; owners control whether sharing is allowed.
  • Curate knowledge: date it, give it an owner, delete superseded files, and never include secrets or real customer data.

Assignment

Design your team's real QA project on paper first: list five knowledge files (with an owner and update frequency for each), write instructions under 300 words, and decide who gets "Can edit". Then build it (with masked content if needed), run three real tasks through it (test cases, a bug report, a release-notes review), and note one change to the instructions after each. Present the result to your team in ten minutes.

Teach it

"A Claude project is a workspace with a binder and a rule sheet. The binder is the knowledge: our strategy, templates and specs. The rule sheet is the instructions: how to write test cases, which format, what's out of scope. Every chat in the project starts with both, so we stop re-pasting context. Chats don't see each other, so save anything worth keeping into the knowledge. On Team plans we can share the project so everyone gets the same answers, and only a few people should be editors."
