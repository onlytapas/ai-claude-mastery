A model can only learn what is in its data. If the data is wrong, incomplete, duplicated or one-sided, the model will be too, and no amount of clever engineering fully fixes that. Most of the work in real AI projects is not building models but collecting, labelling, cleaning and checking data. That makes data quality a testing problem, and QA engineers already have the right instincts for it. For large language models, the data is a huge slice of written human output, which raises real and unresolved questions about copyright and consent.

13.1What a dataset is

A dataset is a collection of examples a model learns from. Each example (or "record", or "row") has features, the information the model gets as input, and often a label, the right answer we want it to learn to produce.

TaskOne exampleFeatures (input)Label (answer)
Route bug reportsA Jira bugTitle, description, stack traceComponent: UI, API or Data
Predict flaky testsOne CI test runTest name, duration, retries, machine, time of dayFlaky or not
Spot defects in screenshotsA page screenshotThe pixels"Layout broken" or "OK"
Train a language modelA web page or bookThe text so farThe next token (the text labels itself)

The last row matters. Language models are trained mostly by self-supervised learning (Chapter 10): the "label" for each position is simply the next piece of the same text. That's why they can learn from trillions of tokens without anyone labelling them by hand. Human labelling still matters a lot for the later stages (Chapter 18).

In everyday life

A dataset is like a recipe book a trainee chef learns from. If half the recipes have typos in the quantities, the chef learns wrong quantities. If every recipe is Italian, the chef can't cook Thai food, however talented. If the same lasagne recipe appears forty times, the chef thinks lasagne is far more important than it is. The chef is only as good as the book.

"Garbage in, garbage out"

This old computing phrase is the single most useful sentence about AI data. A model trained on poor data doesn't announce that it's poor; it gives confident, polished, wrong answers.

13.2Labelling: where the "right answers" come from

Labelling (or "annotation") means people attach the correct answer to each example. It sounds simple. It isn't.

  • It's expensive and slow. Someone has to read every bug report or look at every image.
  • Experts disagree. Is "Checkout button greyed out after API timeout" a UI bug or an API bug? Two senior testers can honestly differ.
  • Guidelines drift. Labellers on week one and week ten interpret the rules differently.
  • Labels can be quietly wrong. Tired, rushed or under-trained labellers make mistakes that nobody checks.
Real-world example: ImageNet

ImageNet, led by Fei-Fei Li and published in 2009, grew to over 14 million images labelled with thousands of categories. The labelling was done largely by crowd workers through Amazon Mechanical Turk. It made the 2012 deep-learning breakthrough possible (Chapter 5). Later studies found label errors in it and in other famous benchmark datasets: Northcutt and colleagues (2021) estimated an average of at least 3.3% errors in the test sets of ten widely used datasets. Even celebrated datasets are imperfect.

Good labelling practice looks a lot like good test design:

PracticeWhyQA equivalent
Written labelling guidelines with examples and edge casesEveryone labels the same wayClear acceptance criteria
Two people label the same sample and you measure agreementShows how clear the task really isPeer review of test cases
A gold set of examples with known answers, mixed inCatches careless labellersKnown-good regression checks
An "unsure" option and an escalation routeStops people guessingRaising a question instead of assuming
Measuring agreement between labellers

The simplest measure is percentage agreement: of 200 bugs labelled by two people, how many got the same label? But if 90% of bugs are UI, two people who both always say "UI" would agree 81% of the time by pure chance. Statistics such as Cohen's kappa correct for chance agreement: 1 means perfect, 0 means no better than chance. If labellers can't agree well, a model trained on their labels can't be expected to beat that level either, and your "accuracy" target should reflect it.

13.3Cleaning: the unglamorous majority of the work

Raw data is almost always messy. Data cleaning means finding and fixing problems before training. Practitioners often say cleaning and preparing data takes most of a project's time; treat any exact percentage you hear as anecdote, but the pattern is real.

ProblemExample in a bug-report datasetTypical fix
Missing valuesComponent field left blankRemove, or send back for labelling
Inconsistent formats"UI", "ui", "Front-end", "FE"Map to one agreed spelling
DuplicatesThe same bug raised by three peopleKeep one copy
Outliers and impossible valuesTest duration of −5 seconds, or 900 hoursInvestigate; fix or remove
Wrong labelsA database bug labelled "UI"Review a sample; relabel
Stale dataBugs from a product you retired in 2021Filter by date or relevance
Sensitive dataCustomer emails and card numbers pasted into bug descriptionsRemove or mask before use (data masking)
Cleaning can introduce bias too

"Drop every row with a missing field" sounds safe. But if one team never fills in the component field, you've just deleted that team's bugs from the dataset, and the model will be worse at exactly their kind of bug. Every cleaning rule is a decision about what the model will and won't see. Write those decisions down.

13.4Splits: training, validation and test

Chapter 12 showed why a model must be checked on data it never trained on. In practice you split the cleaned dataset into three parts, before any training starts:

Training setAbout 70–80%. The model adjusts its weights on this.
Validation setAbout 10–15%. Checked during development to compare models, tune settings and stop early.
Test setAbout 10–15%. Locked away. Used once, at the end, for an honest score.

The percentages are common rules of thumb, not laws. With huge datasets, 1% can be plenty for validation.

In everyday life

The training set is the homework. The validation set is the mock exams you use to decide how to revise. The test set is the real exam, which nobody may peek at. If the teacher hands out the real exam paper as homework, a perfect score means nothing.

Data leakage: the silent killer of honest scores

Data leakage is when information from the validation or test set sneaks into training. The model looks brilliant in testing and disappoints in real use. Common causes:

  • Duplicates across splits. The same bug, raised twice, ends up in both training and test. The model just recognises it.
  • Time travel. Randomly splitting CI runs from the last year means the model trains on March and is tested on February. In real use it must predict the future, so split by date: train on older, test on newer.
  • Features that give the answer away. A "resolved by" field that is always the API team for API bugs. The model learns the field, not the bug.
  • Group overlap. Ten screenshots of the same page in both training and test. Split by page, not by screenshot.
Real-world example

A team reports that their test-failure classifier is 96% accurate (illustrative). A QA lead asks one question: "How did you split the data?" The answer is "randomly, by row". Many failures are the same test failing on several retries, so near-identical rows sat on both sides of the split. Re-split by test name and by date, accuracy drops to 78%. The model didn't get worse; the measurement got honest.

Language models and benchmark contamination

The same problem exists at enormous scale. If the questions and answers of a public benchmark are posted on the web, they can end up in a model's training data, and its score on that benchmark overstates its real ability. This is called contamination. It's one reason to test models on your own, private examples (Chapter 24).

13.5Bias in data

In everyday speech "bias" means prejudice. In data it means something broader: the data is systematically unrepresentative of the world the model will be used in. A model faithfully learns whatever patterns are there, including unfair or outdated ones.

Kind of biasWhat happensQA example
Sampling biasSome groups or situations are under-representedA screenshot-checker trained only on Chrome desktop misses Safari mobile layout bugs
Historical biasThe data faithfully records a past that was itself unfair or differentA triage model learns that bugs from a certain region were "low priority", because they always were, not because they should be
Label biasLabellers' own assumptions shape the answersOne reviewer marks every accessibility bug as "minor"
Measurement biasThe way data is collected distorts it"Bugs found" only counts bugs that customers bothered to report
Survivorship biasYou only see what made it through some filterTraining on merged pull requests only, never the rejected ones
Real-world examples

Hiring. Reuters reported in 2018 that Amazon had scrapped an experimental CV-screening tool after finding it penalised CVs containing the word "women's". It had learned from ten years of past hiring, which was mostly men.

Face analysis. Joy Buolamwini and Timnit Gebru's 2018 "Gender Shades" study found that commercial gender-classification systems were far less accurate for darker-skinned women than for lighter-skinned men, largely because of who was in the training and benchmark data.

Opinion · fairness researchers vs. some engineers

Many fairness researchers, including the Gender Shades authors, argue that bias must be actively measured and corrected because "neutral" data reflects an unequal world. Some engineers and commentators argue that models should reflect the data as it is and that adjusting it introduces the designers' own values. There's no purely technical answer: choosing what a model should learn is a human decision. What both sides accept is that you can't fix a bias you never measured.

13.6Data quality is a QA problem

Data deserves the same discipline as code. Data engineers commonly describe quality along a set of dimensions, and each one turns naturally into test cases.

DimensionQuestionA test you could automate
CompletenessIs anything missing?No empty labels; every row has a title
ValidityDo values follow the rules?Component is one of UI, API, Data; durations are positive
ConsistencyDoes the same thing look the same everywhere?No "ui" vs "UI"; dates in one format
UniquenessAre there duplicates?No repeated titles or IDs
AccuracyIs it actually right?A human re-checks a random 5% sample of labels
TimelinessIs it current enough?Nothing older than the current product version
RepresentativenessDoes it match real use?Class counts and browser mix compared with production

Two documentation habits from the research community are worth copying. "Datasheets for Datasets" (Gebru and colleagues, 2018) proposes that every dataset ship with a short document: why it was made, who collected it, how it was labelled, what's missing and what it shouldn't be used for. "Model Cards" (Mitchell and colleagues, 2019) do the same for models. AI companies publish system cards for their models in this spirit.

Real-world example

Before a team trains a defect-routing model on 20,000 Jira issues, a QA engineer writes a data test suite: 12 checks covering the dimensions above, run in CI on every data refresh. On the first run it finds 1,400 duplicates, 600 unlabelled issues and a component called "Misc" holding 18% of the data (illustrative). Fixing those does more for the model than any change to the model itself.

13.7Synthetic data

Synthetic data is data generated by a program or a model rather than collected from the real world. You've probably used it already: fake customer records for a test environment are synthetic data.

Good for

  • Privacy: test or train without real customer data
  • Rare cases: generate more examples of unusual bugs or edge cases
  • Balancing: top up under-represented classes
  • Scale: thousands of varied test inputs quickly

Risky because

  • It inherits the blind spots of whatever generated it
  • It can be too clean and regular compared with messy reality
  • Models trained heavily on their own output can degrade over generations, an effect researchers call model collapse (Shumailov et al., Nature, 2024)
  • Always validate against real data

AI labs now use synthetic data heavily, particularly in post-training: for example, having a model generate practice problems, or critique and rewrite answers (Chapter 18). Recent Claude system cards list synthetic data generated by other models as one ingredient of the training mix.

Real-world example

A tester asks Claude: "Generate 50 realistic but fake UK customer records for a checkout test, including edge cases: very long names, apostrophes, non-Latin characters, postcodes with and without spaces." That's synthetic test data. The same tester then checks the output: are all 50 actually different? Do the postcodes follow the real format? Is anything accidentally a real person? Validate synthetic data like any other input.

13.8How language-model training data is gathered

At a high level, the text used to pre-train large language models comes from a few kinds of source:

SourceWhat it is
Public web crawlsPrograms called crawlers visit and save publicly reachable web pages. Common Crawl, a non-profit founded in 2007, publishes a huge free archive used by many labs and researchers. Labs also run their own crawlers.
Books, papers and codeDigitised books, scientific articles, public code repositories
Licensed dataData paid for under agreements with publishers and other owners
Human-written dataDemonstrations, ratings and comparisons from paid contractors, used mostly in post-training
User dataConversations from users who have allowed it, under each company's policy
Synthetic dataText generated by models, as in 13.7

Raw web text is mostly unusable, so it goes through heavy filtering: removing duplicates, spam, boilerplate, low-quality and harmful pages, and personal information; identifying languages; and mixing sources in chosen proportions. For example, the GPT-3 paper (Brown et al., 2020) reported that filtered Common Crawl made up 60% of its training mix by weight, alongside curated web text, books and Wikipedia. Chapter 17 covers data mixtures and scale.

Verified 9 Nov 2026 · Anthropic

Recent Claude system cards describe the training data as a proprietary mix of publicly available information from the internet, public and private datasets, and synthetic data generated by other models (the exact wording varies between cards). Anthropic's privacy centre says its crawler honours website owners' robots.txt "do not crawl" instructions and does not try to bypass CAPTCHAs. On user data: consumer users (Free, Pro, Max) choose in their settings whether their chats and coding sessions may be used to improve Claude, and Incognito chats are excluded; for commercial products such as Claude for Work and the API, Anthropic says it does not use inputs or outputs for training by default.

At work

Before pasting test data, logs or customer information into any AI tool, check which plan your company uses and what its data policy says. "Is this used for training?" and "Who can see it?" are separate questions. Chapter 98 covers safe handling of secrets and data.

13.9The copyright and consent debate

Training on large parts of the written internet raises questions that courts, lawmakers and the public are still working out. This section describes the debate; it is not legal advice, and positions differ by country.

Arguments made by many creators and publishers

  • Their work was copied without permission or payment
  • Models can compete with the very people whose work trained them
  • Opt-out tools came after much of the data had already been collected
  • People who posted online years ago never imagined this use

Arguments made by many AI developers

  • Training learns patterns rather than storing copies, similar to how people learn by reading
  • In the US, this can be "fair use" because the use is transformative
  • Requiring permission for every web page would make training impractical
  • They respect opt-out signals such as robots.txt and license some data
  1. Dec 2023The New York Times sues OpenAI and Microsoft over the use of its articles in training. The case is one of many brought by authors, artists, news organisations and music publishers against AI companies.
  2. Jun 2025Bartz v. Anthropic ruling. US District Judge William Alsup found that training Claude on lawfully acquired books was fair use, but that downloading and keeping pirated copies of books was not protected.
  3. Sep 2025Settlement. Anthropic agreed to a $1.5 billion settlement with the authors' class, reported as about $3,000 per book for roughly 465,000–500,000 works, and to destroy the pirated datasets. It received preliminary court approval in September 2025; press reports say final approval followed in 2026.
Opinion · differing views

Some legal commentators read the Bartz ruling as a signal that training itself may be lawful in the US when the data is lawfully obtained. Others stress that it was one district-court decision, that other cases may decide differently, and that laws in the EU, UK and elsewhere differ. Creators' groups argue for consent and payment regardless of the legal answer. Treat any confident claim about "the law on AI training" with care: it is still being decided.

# check_data.py - basic data-quality checks on a labelled dataset
import csv
import random
import sys
from collections import Counter

path = sys.argv[1] if len(sys.argv) > 1 else "bugs.csv"
with open(path, newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))
print(f"Loaded {len(rows)} rows from {path}\n")

# 1. Missing labels
missing = [r["id"] for r in rows if not r["component"].strip()]
print("Missing labels:", missing or "none")

# 2. Inconsistent label spelling (same label, different case or spaces)
raw = Counter(r["component"] for r in rows if r["component"].strip())
by_norm = {}
for label in raw:
    by_norm.setdefault(label.strip().lower(), []).append(label)
clashes = {k: v for k, v in by_norm.items() if len(v) > 1}
print("Inconsistent spellings:", clashes or "none")

# 3. Exact duplicate texts
seen = {}
dupes = []
for r in rows:
    key = r["title"].strip().lower()
    if key in seen:
        dupes.append((seen[key], r["id"]))
    else:
        seen[key] = r["id"]
print("Duplicate titles (first id, repeat id):", dupes or "none")

# 4. Clean: drop missing labels and duplicates, normalise labels
CANON = {"ui": "UI", "api": "API", "data": "Data"}
clean, keys = [], set()
for r in rows:
    key = r["title"].strip().lower()
    label = r["component"].strip()
    if not label or key in keys:
        continue
    keys.add(key)
    clean.append({"title": r["title"], "component": CANON.get(label.lower(), label)})
print(f"\nAfter cleaning: {len(clean)} rows")

# 5. Class balance
counts = Counter(r["component"] for r in clean)
for label, n in counts.most_common():
    print(f"  {label:5s} {n:2d}  {'#' * n}")

# 6. Split into train / validation / test (70 / 15 / 15) with a fixed seed
random.seed(42)
random.shuffle(clean)
n = len(clean)
a, b = int(n * 0.7), int(n * 0.85)
train, valid, test = clean[:a], clean[a:b], clean[b:]
print(f"\nSplit: train={len(train)}  validation={len(valid)}  test={len(test)}")

# 7. Leakage check: no title may appear in more than one split
def leaks(train, others):
    seen = {r["title"].lower() for r in train}
    return [r["title"] for r in others if r["title"].lower() in seen]

print("Leakage between splits:", leaks(train, valid + test) or "none")

# 8. For comparison: what if we had split the RAW rows, before removing duplicates?
raw_rows = list(rows)
random.seed(0)
random.shuffle(raw_rows)
print("Raw split leaks:", leaks(raw_rows[:11], raw_rows[11:]) or "none")

Troubleshooting

KeyError: 'component': the CSV header was changed or saved with extra spaces; the first line must be exactly id,title,component. Strange first column name such as '﻿id': your editor saved the CSV with a byte-order mark; save as plain UTF-8, or change the encoding in the script to utf-8-sig. Different split numbers or leak result: the shuffle depends on the random seed and Python's random module; the counts of missing, inconsistent and duplicate rows must still match. No company data? The provided CSV is all you need; never paste real customer data into a lab.

Common misunderstandings
"More data always beats better data."
More helps, but duplicated, mislabelled or one-sided data can make a model worse. Much recent progress in language models came from better filtering, not just more text.
"The model is biased, so the engineers must have been biased."
Often the data simply reflects past patterns. That's an explanation, not an excuse: it still needs measuring and fixing.
"A high test score proves the model works."
Only if the test set was truly separate. Leakage and contamination produce high scores that collapse in real use.
"Synthetic data is free of problems because it's not real."
It carries the blind spots of whatever generated it, and needs validating against reality.
"The copyright question has been settled."
Individual rulings and settlements exist, but the overall legal picture is still developing and differs between countries.

13.11Review

Key takeaways
  • A dataset is examples with features and, often, labels. A model can only learn what's in it.
  • Labelling is costly and subjective; guidelines, double-labelling and gold sets keep it honest.
  • Cleaning fixes missing values, inconsistent formats, duplicates, wrong labels and sensitive data, and every cleaning rule is a decision.
  • Split into training, validation and test sets before training; split by time or group when that matches real use.
  • Data leakage and benchmark contamination make scores look better than reality.
  • Bias in data comes from sampling, history, labels and measurement; measure it before you trust a model.
  • Data quality has testable dimensions, so treat datasets like code: write checks and run them in CI.
  • Language models train mostly on filtered web text plus books, code, licensed, human-written and synthetic data. Copyright and consent are live, unresolved debates.
Check yourself

A flaky-test model is trained and tested on a random split of last year's CI runs. What is the main risk?

In real use the model must predict the future. Split by date so the test set comes after the training set.

Which dataset problem is a script least able to detect on its own?

Duplicates and blanks are mechanical. Judging whether a bug really belongs to "Data" or "API" needs human or model review.

A screenshot-checker trained only on Chrome desktop images misses Safari mobile layout bugs. What kind of bias is this?

Some situations the model will meet were under-represented, or absent, in the data it learned from.

What is the test set for?

The validation set is used for tuning; the test set stays locked away until the end.

According to Anthropic's privacy centre, is data from the Claude API used to train models by default?

Anthropic says it does not use commercial-product inputs or outputs for training by default. Consumer users choose in their settings.

Teach it

"An AI model is only as good as its data. Real data is messy: missing values, duplicates, inconsistent labels and labels people disagree on. Cleaning it is most of the work. We split data into training, validation and test sets so we can check the model on things it never saw, and we watch for leakage, where the same examples sneak into both sides and make scores look better than they are. Data can also be biased, under-representing some groups or repeating old unfairness. As testers, we're good at this: treat a dataset like code and write tests for it. And for big language models, the data is much of the public web, which is why copyright and consent are still being argued in court."
