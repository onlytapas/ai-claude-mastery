A multi-agent system is several agents, each with its own context window, instructions and tools, working on one job. Usually a lead agent breaks the job up, hands pieces to other agents, and combines what comes back. Done well, this keeps each agent's context clean and focused, lets independent work run at the same time, and lets you give each worker only the tools it needs. Done badly, it multiplies cost, loses information at every handoff, and produces agents that contradict each other. The skill is knowing which jobs split cleanly, and designing exactly what crosses the boundary between agents.

111.1From one agent to several

In Chapter 108 you met orchestrator–workers as a workflow pattern: one model call splits a task, other calls do the parts. A multi-agent system takes the same idea further: each worker is a full agent with its own loop, so it can read files, run tools and decide its own steps before reporting back.

In everyday life

A test lead preparing a release doesn't personally run every check. They ask one tester to run regression on payments, another to do exploratory testing on the new search, and a third to check accessibility. Each tester works with their own notes and tools, and comes back with a short report. The lead never sees every click; they see three summaries, decide what matters, and write the release recommendation. That is a multi-agent system made of people, and it has the same failure modes: vague briefs, overlapping work, and reports that leave out the one detail that mattered.

111.2Why split the work at all?

Anthropic's Agent SDK documentation lists four benefits of subagents. They are a good checklist for any multi-agent design:

BenefitWhat it meansQA example
Context isolationThe worker's file reads and tool results stay in its own context; only its final message returnsA worker reads 40 failure logs; the lead receives one page of findings, not 40 logs
ParallelisationIndependent parts run at the same time, so the job takes as long as the slowest partSecurity, performance and test-coverage reviews of one pull request at once
Specialised instructionsEach worker has a focused system promptAn accessibility reviewer primed with WCAG checks (Chapter 123)
Tool restrictionsEach worker gets only the tools it needsThe log analyst can read but never edit or run commands

Context isolation matters more than it first appears. Every turn, an agent re-reads its whole conversation, and quality drops as the window fills with old tool output (context rot, Chapter 20). A worker that reads twelve logs and returns a summary keeps that clutter out of the lead's window.

  • A lead agent on Claude Opus 4 with Claude Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2%" on Anthropic's internal research evaluation.
  • On the BrowseComp benchmark, three factors explained 95% of the variance in performance, and "token usage by itself explains 80% of the variance". In other words, much of the gain came from spending more tokens, spread across parallel context windows.
  • The same article says multi-agent systems fit poorly where "all agents [must] share the same context" or there are many dependencies between agents, and notes that "most coding tasks involve fewer truly parallelizable tasks than research".
Opinion · two published views

Anthropic's engineers argue multi-agent designs pay off for broad, parallel work such as research, where the extra tokens buy better answers. Walden Yan of Cognition (makers of the Devin coding agent) argued the opposite for many tasks in "Don't Build Multi-Agents" (12 June 2025), with two principles: "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results". He concluded that running multiple agents in collaboration "only results in fragile systems". The two views mostly agree on the facts: split work that is genuinely independent, and keep work that depends on shared decisions in one context.

111.4Handoffs and shared state

The boundary between agents is where most multi-agent systems fail. In Claude Code and the Agent SDK, a (non-fork) subagent's context "starts fresh": it gets its own system prompt, the project's CLAUDE.md if settings are loaded, its tool definitions, and the prompt string the lead writes when it calls the Agent tool. It does not get the lead's conversation history, tool results or system prompt. Coming back, only the subagent's final message returns to the lead.

Real-world example: a weak and a strong brief

Weak: "Look into the checkout failures." The worker doesn't know which run, which files, what "look into" means, or what to send back, so it explores widely and returns a long essay.

Strong: "Read the JUnit files in results/ from build 1842 (checkout.xml and payment.xml only). For each failing test, give: test name, error message, whether the same test failed in results/previous/ (yes/no), and a one-line likely cause. Do not edit files. Reply as a Markdown table, at most 30 lines." Anthropic's article makes the same point: each worker needs "an objective, an output format", guidance on tools and sources, and clear task boundaries, or agents duplicate work.

What crosses the boundary

  • Going out: everything the worker needs and can't find for itself: paths, build numbers, decisions already made, what not to do.
  • Coming back: a fixed format with evidence (file and line, log excerpt) so the lead can check claims rather than trust them. If you need the full detail, have the worker write it to a file and return the path.

Shared state without collisions

  • Give each agent its own files. Claude Code's agent-team guidance is blunt: "Two teammates editing the same file leads to overwrites."
  • Read-only workers, one writer. Let many agents analyse, and only the lead (or a human) change things.
  • Make writes idempotent (idempotency, Chapter 109). Two workers that both "create a Jira bug for the login failure" must not create two bugs.
  • Isolate code changes in worktrees (Chapter 69), so parallel edits land on separate branches and meet in review.
Under the hood: the "telephone game" and how to measure it

Every handoff compresses information. A worker that read 50,000 tokens of logs and returned 300 tokens has thrown away more than 99% of what it saw; that is the point, but it means the lead cannot notice a pattern the worker didn't report. Errors also compound: if each of three stages keeps the important detail 90% of the time, all three together keep it only about 73% of the time (0.9 × 0.9 × 0.9; illustrative). Two practical defences: make reports structured so missing fields are obvious, and keep the full worker transcripts so you can audit them. Claude Code stores subagent transcripts in separate files, the SDK marks every message produced inside a subagent with parent_tool_use_id, and a SubagentStop hook receives agent_transcript_path, so you can trace any claim back to the tool output it came from.

111.5Cost, and how to cap it

Each agent carries its own system prompt and tool definitions, re-reads its own conversation each turn, and spends a few turns getting its bearings. More agents means more of all three. Anthropic's agent-team page says token costs "scale linearly" with the number of teammates. Parallel agents finish sooner, but you pay for every one.

The lab's small script makes this concrete. It is a model with made-up numbers, not a measurement, but its shape is real: splitting long work cuts each agent's peak context sharply; total tokens fall a little at first (shorter conversations are cheaper to re-read), then rise as each extra agent adds fixed overhead. When each piece of work is small, a single agent wins outright.

Hard limits in the Agent SDK

Claude decides how many subagents to start, and subagents can start their own. The SDK documentation gives three caps (for Python SDK 0.2.127+ and TypeScript SDK 0.3.219+):

Newer models delegate more

The SDK docs note that Claude Opus 5 "delegates to subagents more readily than earlier models", so these limits matter most there. With the claude_code system prompt preset, Claude Code adds a line telling Opus 5 not to call the Agent tool unless asked; with your own system prompt, add a delegation instruction yourself, and set the limits anyway.

111.6When not to use several agents

Use one agent when…Consider several when…
Steps depend on each other (write the fixture, then the test that uses it)Parts are genuinely independent (review five separate services)
Everyone needs the same context (one tricky bug in one module)Each part needs lots of reading the others don't need
The work edits the same filesEach worker can own its own files, or only reads
The job is small; setup would outweigh the workThe job is broad: many sources, many hypotheses
You can't yet evaluate the single-agent versionYou have a baseline and evidence the split improves it
Start with one

Build the single-agent version first, measure it (Chapter 125), and split only the part that is failing for a reason a split would fix: an overflowing context, or slow work that could run in parallel. A multi-agent design you can't compare to a baseline is a guess with a bigger bill.

111.7Multi-agent work in Claude Code and the Agent SDK

Subagents (Claude Code)

A subagent is a Markdown file in .claude/agents/ (project) or ~/.claude/agents/ (personal). The frontmatter names it and limits it; the body is its system prompt. Only name and description are required; other fields include tools, disallowedTools, model, permissionMode, maxTurns, background and isolation: worktree. Built-in subagents include Explore (fast, read-only search), Plan and general-purpose. Claude picks a subagent from its description, or you name it: "Use the failure-analyst agent to…". Files are picked up within seconds; /agents now only prints a reminder of where they live.

Subagents (Agent SDK)

In code, pass AgentDefinition objects in the agents option and allow the Agent tool:

Two specialist subagents (Python, Agent SDK)
from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Glob", "Agent"],
    agents={
        "failure-analyst": AgentDefinition(
            description="Analyses failing tests in JUnit XML. Use for test-result triage.",
            prompt="You analyse test failures. Report test, error, likely cause. Never edit files.",
            tools=["Read", "Grep", "Glob"],      # read-only
            model="haiku",
        ),
        "flake-checker": AgentDefinition(
            description="Checks whether a failing test also failed in earlier runs.",
            prompt="Compare results/ with results/previous/. Reply with a yes/no table.",
            tools=["Read", "Glob"],
        ),
    },
    max_budget_usd=1.0,
)
# async for message in query(prompt="Triage results/ using both agents", options=options): ...

To see delegation in the stream, look for ToolUseBlocks named "Agent" (older versions said "Task", so match both); messages produced inside a subagent carry parent_tool_use_id. By default a spawned subagent runs in the background and its report arrives in a later turn; Claude waits when its next step needs the result, or when you say "run it and wait".

Background sessions (Claude Code)

These are separate whole sessions, not subagents: claude --bg "task" starts one and prints its id, claude agents opens agent view to watch and attach, and /background sends the current session there (Chapter 69). They're a research preview, run on your machine, and use your quota like any session. The /batch skill uses this idea at scale: it plans a large change, splits it into 5–30 units and runs each in its own git worktree with a background subagent.

Agent teams (Claude Code, experimental)

Agent teams are off by default; you turn them on with CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 in your environment or in the env block of settings.json. One session is the lead; teammates are separate Claude Code sessions sharing a task list (pending, in progress, completed, with dependencies) and a mailbox for direct messages. You can talk to any teammate yourself.

SubagentsAgent teams
ContextOwn window; results return to the callerOwn window; fully independent
CommunicationReport back to the callerTeammates message each other directly
CoordinationThe main agent manages all workShared task list and messages
Token costLower: summaries return to the main contextHigher: each teammate is a separate Claude instance
Best forFocused tasks where only the result mattersWork that needs discussion and challenge

The docs suggest starting with 3–5 teammates and with research or review tasks that don't write code. Known limitations include no session resumption for in-process teammates, task status that can lag, one team per session, no nested teams, and no teammates in non-interactive (-p) or Agent SDK sessions.

Permissions travel with the work

Subagents inherit acceptEdits, auto and bypassPermissions from the main session (Claude Code never applies a bypassPermissions value that a subagent definition sets for itself, but a bypassing parent passes bypass down). New teammates start in the lead's mode. And a message from another agent is never your consent: Claude Code tells the receiving agent that the message came from another Claude session, and a teammate can't approve a permission prompt on your behalf. Treat agent-to-agent messages as untrusted input, as you would a web page (Chapter 131).

111.9Lab: measure the trade-off, then delegate

Part A runs anywhere with Python 3. Part B needs Claude Code (Chapter 64). It reuses the sample results from the Chapter 110 lab; if you skipped it, the step below creates similar files.

context_budget.py (complete; Python 3 standard library only)
"""Compare one agent with an orchestrator plus workers (illustrative numbers only).

Every agent re-reads its whole conversation on every turn, so input tokens add up.
Change the numbers at the top and run again: python3 context_budget.py
"""
LOGS = 12             # failure logs to analyse
LOG_TOKENS = 6_000    # tokens per log
OVERHEAD = 8_000      # system prompt + tool definitions that every agent carries
BRIEF = 400           # the task text, or the lead's brief to one worker
SUMMARY = 300         # tokens in one worker's report back to the lead
SETUP_TURNS = 3       # turns a fresh worker spends getting its bearings
SETUP_TOKENS = 4_500  # tokens those turns add (listing files, reading the README...)


def agent_run(logs: int, setup_turns: int = 0) -> tuple[int, int]:
    """One agent: optional setup turns, then one log per turn, then an answer.
    Returns (peak context, total input tokens over all turns)."""
    context = OVERHEAD + BRIEF
    sizes = [context]
    for _ in range(setup_turns):
        context += SETUP_TOKENS // max(setup_turns, 1)
        sizes.append(context)
    for _ in range(logs):
        context += LOG_TOKENS
        sizes.append(context)
    return max(sizes), sum(sizes)


def team(workers: int) -> tuple[int, int, int]:
    """Lead plans, workers split the logs, lead merges the reports."""
    share = -(-LOGS // workers)                         # ceiling division
    worker_peak, worker_total = agent_run(share, SETUP_TURNS)
    lead_turns = [OVERHEAD + BRIEF, OVERHEAD + BRIEF + workers * SUMMARY]
    peak = max(worker_peak, *lead_turns)
    total = workers * worker_total + sum(lead_turns)
    return peak, total, workers + 1


if __name__ == "__main__":
    print(f"{LOGS} logs x {LOG_TOKENS:,} tokens; {OVERHEAD:,} overhead per agent (illustrative)\n")
    print(f"{'Design':<20}{'Agents':>7}{'Peak context':>14}{'Total input':>14}")
    peak, total = agent_run(LOGS)
    print(f"{'Single agent':<20}{1:>7}{peak:>14,}{total:>14,}")
    for w in (2, 3, 4, 6, 12):
        peak, total, agents = team(w)
        print(f"{'Lead + ' + str(w) + ' workers':<20}{agents:>7}{peak:>14,}{total:>14,}")

Troubleshooting

Claude doesn't use the subagent: name it explicitly ("use the failure-analyst agent"), and make the description say when to use it. Agent not found: check the YAML frontmatter (three dashes above and below, name spelled exactly) and that the file is in .claude/agents/ of the folder where you started claude; restart if the folder is new. haiku not available on your plan or provider: delete the model line so it inherits the main model. No Claude Code access: Part A plus the SDK example in 110.7 (with an API key) cover the same ideas.

Common misunderstandings
"More agents means better results."
Gains come from spending more tokens on genuinely parallel work. For dependent or small tasks, extra agents add cost and failure points.
"Subagents can see what the main conversation saw."
A non-fork subagent starts fresh. Only the brief you write crosses over, so include paths, ids and decisions.
"Running in parallel makes it cheaper."
It makes it faster. You still pay for every agent's tokens, and each carries its own overhead.
"A teammate said the user approved it, so it's fine."
Messages between agents are not user consent. Claude Code labels them as coming from another Claude session.
"Agent teams are the upgraded version of subagents."
They are a different, experimental tool for work that needs discussion, at a higher token cost. Subagents remain the default for focused delegation.

111.10Review

Key takeaways
  • A multi-agent system splits one job across agents with separate contexts: usually a lead plus workers who report back.
  • The benefits are context isolation, parallelism, specialised prompts and restricted tools. Anthropic reported a 90.2% gain on its internal research evaluation, at roughly 15 times the tokens of a chat.
  • Handoffs are where systems fail: write briefs with an objective, scope, boundaries and output format; return structured reports with evidence.
  • Share state carefully: one owner per file, read-only workers, idempotent writes, worktrees for parallel code changes.
  • Cap depth, concurrency and budget. Start with one agent, measure, and split only what a split would fix.
  • In Claude Code: subagent files in .claude/agents/, background sessions with claude --bg, and experimental agent teams. In the SDK: AgentDefinition in agents, with Agent allowed.
Check yourself

What does a (non-fork) subagent receive from the lead agent?

The brief is the only content passed from parent to subagent, so it must contain the paths, ids and decisions the worker needs.

According to Anthropic's research-system article, what explained most of the performance variance on BrowseComp?

The article says token usage alone explained 80% of the variance; tool-call count and model choice were the other two factors.

Three agents will each update the same test-plan.md. What is the safest design?

Concurrent edits to one file cause overwrites. One owner per file avoids conflicts.

How do you turn on Claude Code agent teams?

Agent teams are experimental and disabled by default; the environment variable enables them.

In the lab model with short (800-token) logs, why does every multi-agent design cost more in total than one agent?

Overhead per agent dominates when each piece of work is small: a single agent is cheaper and simpler.

Assignment

Pick one recurring QA job that might split well, such as a release-readiness check across several services, or reviewing a large pull request. Write a one-page design: the lead's job, each worker's brief (objective, inputs, boundaries, tools, output format), what state is shared and who owns it, and the caps you'd set. Then argue the opposite case: what would go wrong with one agent, and what would go wrong with your split? Finish with how you would measure which design is better (Chapter 125).

Teach it

"A multi-agent system is a lead agent handing pieces of a job to worker agents, each with its own memory and tools, and combining their reports. It helps when the pieces are independent and each needs a lot of reading, because the lead's context stays clean and the work runs in parallel. It costs more: Anthropic measured about fifteen times the tokens of a chat. The weak point is the handoff: the worker only knows what the brief says, and the lead only knows what the report says. So write tight briefs, ask for structured reports with evidence, give each file one owner, and cap the number of agents and the budget. And try it with one agent first."
