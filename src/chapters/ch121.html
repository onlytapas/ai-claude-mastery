Claude Code can write, run and fix automated tests inside your real repository. That turns days of automation work into hours, but only if you work in a disciplined way. Give it your standards in CLAUDE.md, make it plan before it codes, make it run every test it writes, prove each test can fail, and never let it "fix" a failing test by weakening the check. With that discipline, one tester can maintain far more automation than before. Without it, you get a large, green, useless test suite.

121.1The working rhythm

1 · ExploreClaude reads the app, the existing tests and your CLAUDE.md
2 · PlanPlan mode: Claude proposes tests; you correct the plan
3 · ImplementClaude writes tests, page objects and fixtures
4 · RunClaude runs the tests and fixes its own mistakes
5 · ProveBreak the feature on purpose: the test must go red
6 · ReviewYou read the diff, then commit

Steps 5 and 6 are what separate a professional from someone who just generated code. Every chapter section below supports this loop.

In everyday life

Think of an apprentice electrician. They're fast and know the theory. You still agree the plan before they start, you watch them test each circuit, and you flip the breaker yourself to check the safety cut-out actually works. "It looks wired" isn't the same as "it works".

121.2Setting up a Playwright project

Playwright is Microsoft's open-source browser testing framework. Create a fresh project (or use your team's existing one):

Terminal
mkdir shop-tests && cd shop-tests
git init
npm init playwright@latest     # choose TypeScript, a "tests" folder, and install browsers
npx playwright test            # runs the example tests that come with the template
npx playwright show-report     # opens the HTML report in your browser
CommandWhat it does
npm init playwright@latestCreates the project: a config file, example tests and the browser downloads
npx playwright testRuns all tests, headless (no visible browser window) by default
npx playwright test --headedRuns with the browser visible, which is useful to watch what happens
npx playwright test --uiOpens Playwright's interactive UI mode to step through tests
npx playwright codegen <url>Records your clicks and writes test code, a handy starting point
npx playwright show-reportShows the last run's HTML report, with traces for failures

Then start Claude Code in that folder with claude.

121.3A CLAUDE.md for a test repository

CLAUDE.md is the briefing Claude reads at the start of every session (Chapter 77). For automation, it's where your standards live, so every test Claude writes follows them without you repeating yourself.

CLAUDE.md
# Shop tests — Playwright + TypeScript

## Commands
- Run all: `npx playwright test`
- One file: `npx playwright test tests/checkout.spec.ts`
- Repeat to check flakiness: `npx playwright test tests/checkout.spec.ts --repeat-each=10`
- Report: `npx playwright show-report`

## Standards
- Page objects live in `pages/`, one class per page. Tests never contain raw selectors.
- Locators, in order of preference: getByRole, getByLabel, getByTestId. Never CSS classes or XPath.
- Use web-first assertions (`await expect(locator).toHaveText(...)`). Never `waitForTimeout`.
- Test data comes from `fixtures/` or is created through the API in a fixture. Never hard-code real emails.
- Test names: "should  when ".

## The red-test rule
If a test fails, decide whether the APP or the TEST is wrong and tell me before changing either.
Never weaken, skip or delete an assertion to make a test pass without my approval.

## Don't
- Don't edit anything outside `tests/`, `pages/` and `fixtures/`.

121.4Plan mode first

Press Shift+Tab until the mode indicator shows plan mode, or start Claude Code with claude --permission-mode plan. In plan mode Claude reads and investigates but changes nothing (Chapter 67). Remember that interactive sessions now start in auto mode by default, where a safety classifier approves most actions for you. That's convenient, but for new automation work, planning first is still the professional habit.

Prompt in plan mode
Read CLAUDE.md, the pages/ folder and tests/ to learn our patterns.
Then plan Playwright tests for the discount-code story in @docs/stories/PAY-412.md.
Use the test design in @docs/test-design/PAY-412.md (boundaries and decision table).
For each test: name, steps, assertion, data needed, and which page object methods.
List any new page object methods you'd add. Don't write code yet.

Read the plan as a reviewer. Common corrections: "use the existing CheckoutPage, don't create a new one", "the £500.01 case is unconfirmed, so leave it out", "create the test user through the API, not the UI". Approve once it's right.

121.5Page objects, fixtures and locators

A page object keeps all the knowledge about one page (its locators and actions) in one class. When the UI changes, you fix one file, not fifty tests.

pages/CheckoutPage.ts
import { type Page, type Locator, expect } from '@playwright/test';

export class CheckoutPage {
  readonly page: Page;
  readonly codeInput: Locator;
  readonly applyButton: Locator;
  readonly discountLine: Locator;
  readonly total: Locator;
  readonly codeError: Locator;

  constructor(page: Page) {
    this.page = page;
    this.codeInput = page.getByLabel('Discount code');
    this.applyButton = page.getByRole('button', { name: 'Apply' });
    this.discountLine = page.getByTestId('discount-line');
    this.total = page.getByTestId('order-total');
    this.codeError = page.getByTestId('code-error');
  }

  async goto() {
    await this.page.goto('/checkout');
  }

  async applyCode(code: string) {
    await this.codeInput.fill(code);
    await this.applyButton.click();
  }
}

A fixture is reusable setup a test asks for by name. Here, every test that asks for checkout gets a ready page object:

fixtures/test.ts
import { test as base } from '@playwright/test';
import { CheckoutPage } from '../pages/CheckoutPage';

type Fixtures = { checkout: CheckoutPage };

export const test = base.extend<Fixtures>({
  checkout: async ({ page }, use) => {
    const checkout = new CheckoutPage(page);
    await checkout.goto();
    await use(checkout);
  },
});
export { expect } from '@playwright/test';
tests/discount.spec.ts
import { test, expect } from '../fixtures/test';

test('should apply 10% when the basket is exactly at the £20.00 minimum', async ({ checkout }) => {
  // Arrange: basket set to £20.00 (in a real suite, through an API fixture)
  await checkout.applyCode('SAVE10');
  await expect(checkout.discountLine).toHaveText('-£2.00');
  await expect(checkout.total).toHaveText('£18.00');
});

test('should reject the code when the basket is £19.99', async ({ checkout }) => {
  await checkout.applyCode('SAVE10');
  await expect(checkout.codeError).toHaveText('Spend £20 or more to use this code');
});
LocatorExampleWhy
getByRolegetByRole('button', { name: 'Apply' })Matches how users and screen readers see the page; resilient and accessibility-friendly
getByLabelgetByLabel('Discount code')Finds form fields by their visible label
getByTestIdgetByTestId('order-total')Stable hooks (data-testid) agreed with developers
CSS / XPath.btn-primary > spanBreaks when styling changes; avoid

An assertion such as await expect(locator).toHaveText(...) is "web-first": Playwright keeps retrying until the text appears or a timeout passes. That's why you never need waitForTimeout.

121.6Run it, then prove it can fail

Prompt after implementation
Run npx playwright test tests/discount.spec.ts.
If anything fails, apply the red-test rule from CLAUDE.md:
tell me whether the app or the test is wrong, with evidence from the trace, before changing anything.

When everything is green, prove the tests can go red. This step is the one most teams skip, and it's the one that matters most.

Prompt: mutation check
Temporarily change the expected discount in the first test from -£2.00 to -£3.00
and run it. Confirm it fails with a clear message. Then revert the change and
show me git diff to prove the file is back to the original.

Better still, ask a developer to break the feature itself in a local branch (for example, apply the discount after tax). If your tests stay green, they aren't testing what you think.

Why "green" is not evidence

A test passes when its assertion holds. If the assertion is too weak (checking that the total is visible instead of correct), checks the wrong element, or never runs because of an early return, the test passes whatever the app does. AI-written tests are especially prone to this because the model is trying to produce code that runs successfully. Deliberately breaking the system and seeing the right test fail is a lightweight form of mutation testing: it measures whether your tests can detect a change. Dedicated mutation-testing tools automate this for unit tests; for UI tests, a few deliberate breaks per feature is a practical substitute.

121.7API tests

Many checks are faster and more reliable through the API than through the browser. Playwright includes an HTTP client as the request fixture.

tests/api/discount.api.spec.ts
import { test, expect } from '@playwright/test';

test('should return 400 for an unknown discount code', async ({ request }) => {
  const response = await request.post('/api/basket/apply-code', {
    data: { code: 'NOT-A-REAL-CODE' },
  });
  expect(response.status()).toBe(400);
  const body = await response.json();
  expect(body.error).toBe('CODE_NOT_FOUND');
});

A good prompt: "Read @openapi.yaml and write negative API tests for POST /api/basket/apply-code: missing fields, wrong types, empty strings, very long strings, unauthenticated requests and rate limits. Use only status codes and error codes that appear in the spec." The last sentence stops Claude inventing error codes. For APIs, HTTP and status codes see Chapter 85.

121.8Flaky tests and the red-test rule

A flaky test passes sometimes and fails sometimes with no code change. Claude is very good at diagnosing flakiness, provided you stop it from "fixing" the symptom.

Prompt: investigate flakiness
tests/discount.spec.ts fails about 1 run in 10 in CI.
1. Run it with --repeat-each=20 and report how many runs fail.
2. Open the traces for the failures and explain the root cause with evidence.
3. Propose a fix. Allowed: better locators, web-first assertions, proper
   waiting for network responses, isolated test data.
   Not allowed: waitForTimeout, retries as the fix, weaker assertions.
Show me the proposal before editing.
Common causeTypical fix
Asserting before the app has updatedWeb-first assertion on the final state
Tests sharing one user or basketCreate fresh data per test in a fixture (Chapter 122)
Ambiguous locator matching two elementsRole and name, or a unique data-testid
Animations or toasts covering a buttonWait for the element to be stable or the toast to disappear
A genuine race condition in the appThat's a bug: report it, don't hide it
The red-test rule

An agent asked to "make the tests pass" may succeed by changing toHaveText('£18.00') to toBeVisible(), adding test.skip, or bumping retries until it passes by luck. Each of these turns a failing test into a lie. Your CLAUDE.md rule, plus reviewing every diff, is the defence. A red test that reveals a real bug is the most valuable output of your whole suite.

121.9Reviewing the diff

Before you commit, read the change yourself: !git diff inside Claude Code, or the diff view in VS Code. Look for:

  • Changes outside tests/, pages/ and fixtures/
  • Assertions removed, loosened or skipped
  • Raw selectors in tests instead of page objects
  • Hard-coded waits, emails or passwords
  • Copy-pasted tests that should be one parameterised test

Then ask Claude to commit with a clear message, or commit yourself. Chapter 71 covers Git workflows with Claude Code.

121.10Skills, subagents and hooks for QA

Three Claude Code features turn good habits into automatic ones (Chapters 80–82).

A test-reviewer subagent

A subagent works in its own fresh context and reports back. A reviewer that has only read access can't "helpfully" change anything.

.claude/agents/test-reviewer.md
---
name: test-reviewer
description: Reviews Playwright tests for weak assertions, flakiness risks and
  standards violations. Use after tests are written or changed.
tools: Read, Glob, Grep
model: sonnet
---
You are a strict QA automation reviewer. For each changed test file, report:
- assertions that could never fail, or that check visibility instead of values
- waitForTimeout, retries used as a fix, or test.skip without a reason
- raw selectors in tests instead of page objects
- shared state or hard-coded data between tests
- missing negative and boundary cases compared with the test design
Return a table: file, line, issue, suggested fix. Do not edit files.

Use it with a prompt such as "Use the test-reviewer subagent on the files changed in this branch." The /agents command no longer opens a setup wizard; you create agents by writing the file or asking Claude to create it.

A lint and format hook

A hook runs every time, whatever the model decides. This one formats every file Claude edits:

.claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }
        ]
      }
    ]
  }
}

The hook receives details of the edit as JSON on standard input; jq extracts the file path and passes it to Prettier. It needs jq and Prettier installed. You could equally run ESLint or npx tsc --noEmit.

A skill for your test template

A skill such as /new-e2e-test can hold the steps for adding a test the team's way: page object first, fixture, test, run, mutation check. Chapter 80 shows how to write one.

121.11Headless in CI

Claude Code can run without the interactive screen in print mode (claude -p). In print mode it starts in the standard (Manual) permission mode, so you must explicitly allow the tools it may use.

Triage failures and write a summary
claude -p "Read test-results/ and the Playwright report. Group failures by likely root cause, mark which look flaky, and write a short Markdown summary." \
  --allowedTools "Read,Grep,Glob" \
  --output-format text > triage.md
.github/workflows/e2e.yml (excerpt)
name: e2e
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test
      - name: Triage failures with Claude
        if: failure()
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          npm install -g @anthropic-ai/claude-code
          claude -p "Summarise the Playwright failures in test-results/ by root cause" \
            --allowedTools "Read,Grep,Glob" > triage.md
          cat triage.md >> "$GITHUB_STEP_SUMMARY"

The API key comes from a GitHub Actions secret, never from the file (Chapter 98). For interactive use in pull requests, Anthropic's official action anthropics/claude-code-action@v1 lets reviewers write @claude in a comment; run /install-github-app in Claude Code to set it up.

Playwright's own AI agents

Playwright itself ships test agents (planner, generator and healer) that can be set up for Claude Code with npx playwright init-agents --loop=claude (Chapter 102). They automate plan → write → repair. The same rules apply: review every generated or "healed" change, and watch for weakened assertions.

Common misunderstandings
"All green means done."
Green only means the assertions held. Prove each important test can fail.
"Retries fix flaky tests."
Retries hide flakiness. Find the root cause; use retries only as a temporary safety net with a tracked ticket.
"Auto mode means I don't need to review."
Auto mode decides which actions are safe to run without asking. It doesn't judge whether your tests are good. Reviewing the diff is still your job.
"Let Claude write 300 tests overnight."
Every test is code someone must maintain. Automate what your risk analysis (Chapter 120) says matters.
"The # key adds a memory."
That shortcut was removed. Edit CLAUDE.md directly or use /memory.

121.12Review

Key takeaways
  • Work in a loop: explore, plan, implement, run, prove it can fail, review the diff.
  • CLAUDE.md carries your automation standards and the red-test rule into every session.
  • Page objects, fixtures and role/label/test-id locators keep AI-written tests maintainable.
  • Prove tests can fail by breaking things on purpose. Green alone is not evidence.
  • Diagnose flakiness from traces. Never let "fixes" weaken assertions, add sleeps or rely on retries.
  • A read-only reviewer subagent, a formatting hook and a headless CI triage step make good habits automatic.
Check yourself

Claude reports it "fixed" a failing test by changing toHaveText('£18.00') to toBeVisible(). What's the right response?

The test no longer checks the total. That's the red-test rule.

Which locator does this chapter recommend first?

Role-based locators match how users and assistive technology see the page and survive styling changes.

Why make a test fail on purpose after it passes?

A test that can't fail gives false confidence.

In claude -p print mode, how do you let Claude read test results without prompts?

Print mode starts in the standard (Manual) mode, so tools must be allowed explicitly.

Why give the test-reviewer subagent only Read, Glob and Grep tools?

Least privilege applies to agents too.
