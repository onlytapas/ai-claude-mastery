MCP is a set of rules for a conversation between an AI application and a tool. The AI application (the host, such as Claude Code) runs a small connector (a client) for each tool it talks to. The tool side (the server) says what it can do, and the client asks it to do things. Every message is a short piece of structured text in a format called JSON-RPC. Once you can read those messages, MCP stops being magic: you can see exactly what Claude asked Jira or Playwright to do, what came back, and where it went wrong.

99.1Three roles: host, client and server

The official specification describes every MCP setup with three roles:

RolePlain meaningExample
HostThe AI application you use. It holds the conversation, talks to the model and decides what the model may do.Claude Code, the Claude desktop app, claude.ai
ClientA connector inside the host. There's one client per server, and each keeps its own line of communication.The part of Claude Code that talks to your Jira server
ServerA program that offers capabilities for a particular system.The Atlassian server for Jira, the Playwright server for a browser
Host: Claude CodeHolds the chat, talks to the Claude model, enforces your permissions
Client 1 → Jira serverReads stories, creates bugs
Client 2 → Playwright serverOpens a browser, clicks, takes screenshots
Client 3 → Database serverRuns read-only queries
In everyday life

Think of a hotel concierge desk (the host). Behind the desk are several phones, each with a direct line to one service: the restaurant, the taxi company, the theatre box office. Each phone line is a client, and each service is a server. The guest (you) talks only to the concierge. The concierge decides which service to call, makes the call, and passes the answer back. Crucially, the concierge also refuses requests the guest isn't allowed to make. In Claude Code, that's your permission settings.

The model itself (Claude) never talks to a server directly. It asks the host to call a tool, and the host does the calling. That's why the host is where permissions, approvals and logging live.

99.2What a server can offer: tools, resources and prompts

A server can offer three kinds of thing. The difference between them is who decides when they're used:

FeatureWhat it isWho decides when it's usedQA example
ToolsActions the AI can run, like functionsThe model ("model-controlled"), with the host asking you for approvalcreate_issue in Jira; browser_click in Playwright
ResourcesData the server can provide, each with an address (URI)The application ("application-driven"): the host lets you pick themA Jira issue, a test report file, a database table description
PromptsReady-made message templates for a workflowThe user ("user-controlled"): you choose oneA "review this pull request" template from a GitHub server

In Claude Code you'll meet all three. Tools are what Claude calls on its own. Resources appear when you type @ (for example @github:issue://123). Prompts appear as slash commands such as /mcp__github__pr_review 456. Chapter 100 shows each in practice.

Real-world example

You ask Claude Code: "Check whether bug SHOP-812 is reproducible on staging." Claude might use the Jira server's tool to read SHOP-812, then the Playwright server's tools to open staging and follow the steps, then the Jira tool again to add a comment with screenshots. If you'd typed @ and attached the issue yourself, the issue would have arrived as a resource instead.

99.3The language they speak: JSON-RPC

Every MCP message is written in JSON-RPC 2.0, a long-established, simple format for "please run this procedure" messages. It's plain text in JSON, the same curly-bracket format used by most web APIs (Chapter 85). There are three message types:

TypePlain meaningMust have
Request"Please do this, and tell me the result."An id, a method (what to do) and usually params (details)
Response"Here's the result" or "Here's what went wrong."The same id as the request, plus either result or error
Notification"For your information…" No reply expected.A method, and no id

The id is how answers are matched to questions. If Claude Code sends three requests at once, the server's replies may come back in any order; the ids say which is which.

In everyday life

It's like ordering at a busy café with numbered tickets. You order (request) and get ticket 42. Your coffee comes out with "42" on it (response with the same id). The barista shouting "we're out of oat milk!" to everyone is a notification: nobody is expected to answer.

99.4A real conversation, message by message

Here's what a client and server actually say to each other. These examples follow the current specification (2026-07-28). The tool is the specification's own weather example; a Jira or Playwright server works exactly the same way, just with different tool names. The grey // comments are explanations added for this book. Real JSON messages contain no comments.

Step 1: "What can you do?" (tools/list)

Client → server: request
{
  "jsonrpc": "2.0",
  "id": 1,                                   // ticket number for matching the reply
  "method": "tools/list",                    // what we want
  "params": {
    "_meta": {                               // required on every request since 2026-07-28
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" }
    }
  }
}
Server → client: response
{
  "jsonrpc": "2.0",
  "id": 1,                                   // same ticket number
  "result": {
    "resultType": "complete",                // a finished answer (see 92.6)
    "tools": [
      {
        "name": "get_weather",               // what the AI will call
        "title": "Weather Information Provider",
        "description": "Get current weather information for a location",
        "inputSchema": {                     // JSON Schema: what arguments are allowed
          "type": "object",
          "properties": {
            "location": { "type": "string", "description": "City name or zip code" }
          },
          "required": ["location"]
        }
      }
    ],
    "ttlMs": 300000,                         // the client may cache this list for 5 minutes
    "cacheScope": "public"
  }
}

The description and inputSchema matter enormously: they're what the model reads to decide whether and how to use the tool. A vague description is the most common reason an AI "won't use" a server's tool, or uses it wrongly. This is a testable quality of any MCP server.

Step 2: "Please do it" (tools/call)

Client → server: request (the _meta block is shortened here; it's required in practice)
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "New York" },  // must match the inputSchema
    "_meta": { "io.modelcontextprotocol/protocolVersion": "2026-07-28",
               "io.modelcontextprotocol/clientCapabilities": {} }
  }
}
Server → client: response
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "content": [
      { "type": "text",
        "text": "Current weather in New York:\nTemperature: 72°F\nConditions: Partly cloudy" }
    ],
    "isError": false                         // the tool itself succeeded
  }
}

Two different kinds of failure

The specification separates errors in a way every tester should know:

Protocol error

The request itself was wrong: unknown tool, malformed message. It comes back as a JSON-RPC error with a code, for example -32602 "Unknown tool: invalid_tool_name". The model can rarely fix these itself.

Tool execution error

The request was fine but the job failed: the API was down, a date was in the past, a Jira project didn't exist. It comes back as a normal result with "isError": true and a message. The model is meant to read it and try again differently.

Real-world example: a QA view

When you test an MCP server your team built, check both kinds. Does an unknown tool produce a proper protocol error? Does a bad argument produce a clear isError message the model can act on, such as "Project key SHOPP not found; did you mean SHOP?", rather than a stack trace?

99.5Versions: from handshake to stateless

MCP is versioned by date. The current version is 2026-07-28. The previous one, 2025-11-25, is still widely used, and you'll meet both.

Legacy versions (2025-11-25 and earlier)Modern version (2026-07-28)
Starting a conversationAn initialize handshake: client and server exchange versions and capabilities once, then the client sends notifications/initializedNo handshake. Every request carries its own version and capabilities in _meta
Learning about a serverFrom the initialize replyOptional server/discover request, which every server must support
Sessions over HTTPAn Mcp-Session-Id header tied requests togetherRemoved. Any request can go to any server instance
Server asking the user somethingThe server sent its own requests to the clientThe server replies "input required"; the client asks the user and retries (92.6)

Why the change? Remote MCP servers now run at large scale behind load balancers, like any web service. If every request carries everything needed to process it, any copy of the server can answer it, and nothing breaks when a connection drops. The specification calls this being stateless.

A version mismatch doesn't have to be fatal. If a server doesn't support the requested version, it replies with an UnsupportedProtocolVersion error (code -32022) listing the versions it does support, and the client retries with one of those. Clients and servers can also be "dual-era", speaking both styles.

How Claude Code handles both versions

Claude Code has two MCP client "runtimes". The v1 runtime is built on version 1 of the official MCP TypeScript SDK. The v2 runtime uses SDK 2.0, which adds the 2026-07-28 revision. On v2, Claude Code asks each server whether it supports the newer revision and uses it with those that do; other servers are spoken to the older way. Which runtime you get depends on your version and settings (recent versions use v2 by default in most sessions). You can choose explicitly with the MCP_SDK_GENERATION environment variable (v1 or v2), and MCP_PROTOCOL_NEGOTIATION (auto or legacy) controls whether it asks servers about the newer revision. You rarely need these. They're useful when diagnosing an older server that misbehaves.

99.6When a server needs more from you

Sometimes a server can't finish without more information, for example "which Jira project?" or "please sign in to this second system". The current specification handles this with a pattern called multi round-trip requests:

1 · Client askstools/call create_bug
2 · Server replies "input required"resultType: "input_required" plus what it needs
3 · Host asks youA form or a link appears in Claude Code
4 · Client retriesThe same call, now including your answers
5 · Server completesresultType: "complete"

The main kind of "what it needs" is elicitation, which has two modes:

  • Form mode: a small structured form, such as choosing a project or confirming a severity. The specification forbids using form mode to ask for passwords, API keys, access tokens or payment details.
  • URL mode: send you to a web page for anything sensitive, such as signing in, so the secret never passes through the AI application.

Two older client features, sampling (a server asking the host's model to generate text) and roots (the host telling a server which folders it may use), still work but are deprecated in 2026-07-28, along with server logging. New servers shouldn't rely on them. The specification guarantees deprecated features at least twelve months' notice before removal.

99.7How messages travel: transports

A transport is the delivery method for those JSON-RPC messages. The meaning of the messages is identical on every transport. There are two standard ones:

stdio (local)Streamable HTTP (remote)
How it worksThe host starts the server as a program on your computer and writes messages to its input, reading replies from its output, one message per lineThe server runs somewhere else (a company or vendor server) at one web address, such as https://mcp.example.com/mcp. Each message is an HTTP POST
Typical useTools that need your machine: a local browser (Playwright), local files, a database on your laptopCloud services: Jira, Confluence, GitHub, Sentry, Notion
Sign-inCredentials come from environment variables you set when adding the serverUsually OAuth 2.1 sign-in in the browser, or a fixed header such as an API key
In Claude Codeclaude mcp add name -- command argsclaude mcp add --transport http name URL

A third option, the older HTTP+SSE transport (URLs often ending in /sse), has been deprecated since 2025 in favour of Streamable HTTP. You'll still see it in some setup instructions. Claude Code still accepts --transport sse, and recent versions fall back to SSE automatically when an HTTP server needs it.

Two stdio rules that cause real bugs
  • A stdio server must write only MCP messages to its standard output. If a developer adds a debugging print or console.log that writes to standard output, it corrupts the message stream and the host disconnects. Logs belong on standard error (stderr).
  • Messages are one per line and must not contain raw line breaks. Line breaks inside text are escaped as \n, as in the weather example above.

For Streamable HTTP, the specification requires servers to validate the Origin header (to stop malicious web pages reaching a local server) and recommends that local servers listen only on 127.0.0.1, not on all network interfaces. These are worth checking in a security test (Chapter 105).

99.8Signing in: authorization in brief

For remote servers, the specification uses OAuth 2.1, the same standard behind "Sign in with Google". Chapter 98 explains OAuth step by step; here's the shape of it as MCP uses it:

1 · TryThe client calls the server without a token
2 · "401 Unauthorized"The server replies with where to find its sign-in details
3 · DiscoverThe client reads the server's metadata and finds its authorization server
4 · You sign inA browser opens; you approve the access requested
5 · TokenThe client receives an access token and sends it as Authorization: Bearer … on each request
  • Servers should ask only for the scopes (permissions) they need, such as "read issues" rather than "administer everything".
  • Tokens must be issued for that specific server. A server must reject tokens meant for something else.
  • stdio servers don't use this flow; they read credentials from the environment.
  • Claude Code runs the browser sign-in for you when you open /mcp, or from the shell with claude mcp login <name>. It stores tokens securely and refreshes them automatically. Non-interactive claude -p runs can't complete a browser sign-in, so sign in interactively first.

99.9One tool call, start to finish, in Claude Code

Now put it all together. You type: "Find open P1 bugs in Jira project SHOP and summarise them."

1 · Tool listAt startup Claude Code learned each server's tools (or their names, with tool search)
2 · Model decidesClaude replies with a tool_use request for a Jira search tool and arguments
3 · Permission checkClaude Code checks your rules for mcp__jira__… and asks you if needed
4 · tools/callThe Jira client sends the JSON-RPC request
5 · Server worksThe server calls Jira's own API with your token
6 · ResultContent (or isError) returns; large output is limited or saved to a file
7 · Back to ClaudeThe result joins the context; Claude writes the summary or calls another tool

How MCP tools are named in Claude Code

Inside Claude Code, every MCP tool gets a name with double underscores: mcp__<server>__<tool>. That's the name you use in permission rules:

Permission rules for MCP tools (in a settings file)
{
  "permissions": {
    "allow": [
      "mcp__jira__search_issues",          // one specific tool, no prompt
      "mcp__playwright__*"                  // every tool from the playwright server
    ],
    "deny": [
      "mcp__jira__delete_issue"             // never, even if asked
    ]
  }
}
  • Server names with dots or spaces become underscores in rule names.
  • claude.ai connectors appear as mcp__claude_ai_<server>__<tool>; plugin servers as mcp__plugin_<plugin>_<server>__….
  • The tool names in these examples (search_issues, delete_issue) are illustrations. Run /mcp to see the real names a server offers.

Limits that protect your context

A single tool result can be huge, such as a database dump or a long log. Claude Code warns when an MCP tool's output exceeds 10,000 tokens and, by default, limits it at 25,000 tokens (adjustable with the MAX_MCP_OUTPUT_TOKENS environment variable). An over-limit result is saved to a file, and Claude is told where it is, so it can read just the part it needs. With many servers connected, tool search loads only tool names at the start and fetches full definitions when Claude needs them, so adding servers costs little context.

In everyday life

It's like a manager with a team of specialists. The manager (Claude) doesn't need every specialist's full manual on the desk all day, just a list of who does what. When a job comes up, the manager pulls that one manual. And if a specialist hands back a 500-page report, it goes in a filing cabinet with a note on the desk saying where it is.

Common misunderstandings
"Claude connects to the server directly."
The model only requests a tool call. The host (Claude Code) makes the call, after checking your permissions.
"MCP is a product or a server."
It's a protocol: rules for messages. Servers, clients and hosts are built by many different companies.
"If the server says a tool is read-only, it's safe."
Tool descriptions and annotations come from the server and should be treated as untrusted unless you trust the server. Your permission rules are the real safeguard.
"Every MCP server needs OAuth."
Local stdio servers use environment variables, and some remote servers use a fixed API key header. OAuth is the standard for remote servers acting on your behalf.
"SSE and Streamable HTTP are the same."
SSE is the older, deprecated transport. Use Streamable HTTP (--transport http) unless a server's documentation says otherwise.

99.10Review

Key takeaways
  • Host (the AI app), client (one per server, inside the host), server (offers capabilities for a system).
  • Tools are model-controlled actions, resources are application-driven data, prompts are user-chosen templates.
  • All messages are JSON-RPC 2.0: requests and responses matched by id, plus notifications with no reply.
  • Version 2026-07-28 made MCP stateless: no initialize handshake, per-request _meta, server/discover, and "input required" replies for elicitation. Older 2025-11-25 servers still work through version negotiation.
  • stdio for local programs, Streamable HTTP for remote services; HTTP+SSE is deprecated. Remote sign-in uses OAuth 2.1.
  • Tool execution errors (isError: true) are for the model to fix; protocol errors mean the request itself was wrong.
  • In Claude Code, MCP tools are named mcp__server__tool, and that's how you allow or deny them.
Check yourself

In Claude Code connected to Jira and Playwright, how many MCP clients are there?

Each server gets its own client inside the host application.

A message has a method but no id. What is it?

Notifications are one-way and must not include an id.

Jira is down, and the server returns a result with "isError": true and the message "Jira API timed out". What kind of error is this?

The request was valid; the job failed. That's reported inside a normal result.

What did MCP version 2026-07-28 remove?

Every request now carries its version and capabilities in _meta.

Which permission rule allows every tool from a server named playwright?

MCP tools are named mcp__server__tool.

Assignment

Pick one MCP server your team uses or plans to use. Using the Inspector or /mcp, document its tools in a table: tool name, what its description says, its required arguments, and whether it reads or changes data. Then mark each tool allow, ask or deny for your team, and write the matching permission rules. That table is a real deliverable for any team adopting MCP.

Teach it

"MCP is a message format between an AI app and a tool. The app is the host; it runs one client per server. Servers offer tools (actions the model chooses), resources (data you attach) and prompts (templates you pick). Messages are JSON-RPC: requests and replies matched by an id. Local servers run as programs on your machine over stdio; remote ones are web addresses using HTTP and OAuth sign-in. In Claude Code every tool is called mcp__server__tool, and that's what you allow or deny."
