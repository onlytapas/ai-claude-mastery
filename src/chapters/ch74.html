Inside a Claude Code session, anything you type that starts with / is a slash command: a shortcut that tells Claude Code to do something specific, such as switch model, clear the conversation, review your code or connect a tool. Some commands are built into the program. Others are skills, packaged instructions that Claude follows using its normal tools. You, your team, plugins and MCP servers can add more. This chapter lists every documented command, explains each in plain words, and shows when a professional tester would reach for it.

Version and accuracy

Everything here was checked on 9 November 2026 against Claude Code 2.1.319: the official commands page at code.claude.com and the installed program's own help. Claude Code changes almost every week. Your list may contain commands this chapter doesn't (from your company, plugins or a newer version) or miss some it does (because of your plan, platform or settings). Type / in your own session: that list is always the truth.

74.1How slash commands work

Six rules cover almost everything:

  1. Only at the start of a message. /compact works; please /compact is just text. Anything after the command name becomes its arguments: /compact keep the test failures passes "keep the test failures" to /compact.
  2. Angle and square brackets in this chapter. <path> means you must give a value; [name] means it's optional. You don't type the brackets.
  3. Typing / opens a menu. Keep typing to filter it, use the arrow keys to choose, and press Enter. /help shows help and the available commands.
  4. Commands wait their turn. If you send one while Claude is still working, it's queued until the turn ends. A few, including /status, /tasks and /usage, run immediately.
  5. Not everyone sees every command. Some depend on your platform, plan or provider (for example, subscription-only or macOS-only commands). A few, such as /heapdump, /setup-bedrock and /setup-vertex, are hidden from the menu and run only if you type the full name.
  6. Many commands have aliases, other names that do the same thing. /reset and /new both do what /clear does. The tables list aliases next to each command.
In everyday life

Slash commands are like the buttons on a TV remote. You can always ask someone in the room "turn it up a bit" (a normal prompt), but the volume button does exactly one thing, instantly and reliably. Prompts are flexible; commands are precise.

Examples of the syntax
/help                               # no arguments
/model sonnet                       # one argument
/compact keep the failing test names and stack traces   # free-text argument
/code-review high --fix             # an argument plus a flag
/config theme=dark                  # key=value argument

74.2Four kinds of command

Everything in the / menu looks the same, but there are different kinds underneath. The difference matters when something behaves unexpectedly, and when you want to add your own.

74.5The commands that need more explanation

Most commands are self-explanatory once you've run them. These deserve a closer look. Open whichever you need.

/code-review: reviewing changes for bugs

Syntax: /code-review [low|medium|high|xhigh|max|ultra] [--fix] [--comment] [--max-findings n|all|default] [pr#|branch|path] · Kind: bundled skill · Alias: /review

  • What it does: reviews your current changes (or a PR number, branch or path you name) for correctness bugs and reports findings.
  • Level controls how hard it looks: lower levels report a few high-confidence findings; higher levels look wider and may include less certain ones. ultra runs a deep review in the cloud (the same thing as /ultrareview).
  • --fix applies the fixes to your files after the review. --comment posts findings as comments on the pull request. --max-findings caps how many are reported.
  • Limits: it's a skill, so results vary between runs, and higher levels use more of your allowance. max is the most expensive level.
  • Related: /security-review (security only), /simplify (tidiness, not bugs), /diff.

QA use: before testing a developer's PR, run /code-review high 482 and then ask "Given these findings and the diff, what should I test manually?" You start testing with a list of the riskiest areas.

/context, /compact and /autocompact: managing the context window

The context window is everything Claude can see at once (Chapter 20). As it fills, answers get slower and less focused.

  • /context [all] shows a coloured grid of what's using space (system instructions, CLAUDE.md, tool output, conversation) plus suggestions. Check it first when answers start to drift.
  • /compact [instructions] replaces the conversation so far with a summary, freeing space while keeping the gist. Your instructions steer what's kept: /compact keep the failing test names, the stack trace and the fix we agreed.
  • /autocompact [auto|<tokens>] sets when Claude compacts automatically, e.g. /autocompact 500k. It's saved to your user settings.

Compact or clear? Use /compact to keep going on the same task. Use /clear when you start an unrelated task, since old context only distracts.

/rewind: checkpoints and undo

Syntax: /rewind · Aliases: /checkpoint, /undo · also Esc Esc on an empty prompt

Every prompt that starts a turn creates a checkpoint of Claude's file edits. /rewind lets you pick a point and choose: restore code and conversation, restore conversation only, restore code only, summarise from here, summarise up to here, or never mind.

  • Limits: files changed only by shell (Bash) commands aren't tracked; most subagent edits aren't restored; edits made outside Claude Code aren't tracked. Snapshots are kept for the 100 most recent checkpoints and cleaned up after about 30 days.
  • Checkpoints are not a replacement for git. Commit work you care about.

QA use: Claude rewrote three page objects in a direction you don't like. Rewind code and conversation to before that prompt and give clearer instructions, rather than arguing it back step by step.

/model and /effort: choosing the brain and how hard it thinks
  • /model [model] accepts aliases such as fable, best, opus, sonnet, haiku, opusplan (Opus in plan mode, Sonnet for doing) or a full model name like claude-opus-5-5. It saves your choice as the default for new sessions. In the picker, press s to switch for this session only, and use ← → to adjust effort.
  • /effort [level|auto|status|ultracode [on|off]] sets how much Claude thinks before acting: low, medium, high, xhigh, max. The current Opus, Sonnet and Haiku 5.5 models default to medium. max lasts for the current session only. auto clears your saved level; status shows it.
  • Related: /status shows the current model; /fast toggles fast mode; /advisor adds a second model as an adviser.

QA use: a flaky timing issue has resisted two attempts. Try /effort high or switch to a more capable model for that one investigation, then switch back. Chapter 68 covers model and effort choices in depth.

  • /permissions (alias /allowed-tools) manages allow, ask and deny rules (Chapter 78) and lets you review what auto mode has denied.
  • /config [key=value ...] (alias /settings) opens the Settings screen or sets keys directly. /config --help lists the keys you can set.
  • /update-config [request] is a skill: describe the change in plain words ("always allow npx playwright test", "deny reading .env") and Claude edits settings.json for you. Review the change before accepting.

/mcp: managing connected tools

Syntax: /mcp, /mcp reconnect <server> or /mcp reconnect all, /mcp enable [<server>|all], /mcp disable [<server>|all]

Shows every connected MCP server and its status, lets you sign in (OAuth) to servers like Atlassian or GitHub, lists each server's tools, and reconnects, enables or disables servers. Servers are added with the terminal command claude mcp add, not from inside a session: that's covered in Chapter 83, and the whole of Part XII (Chapters 97–106) goes deeper.

/init and /memory: teaching Claude about your project
  • /init scans the project and writes a starter CLAUDE.md: build and test commands, structure, conventions. Setting the environment variable CLAUDE_CODE_NEW_INIT=1 gives an interactive flow instead.
  • /memory opens your CLAUDE.md files for editing and turns auto memory on or off.

QA use: run /init in a test repository, then trim the result and add your rules ("use data-testid selectors", "never weaken a failing assertion without asking"). Chapter 77 shows how.

/plan and /goal: thinking first, and working until done
  • /plan [description] enters plan mode: Claude investigates and proposes a plan but makes no changes until you approve. You can also reach it with Shift+Tab (Chapter 67).
  • /goal [condition|clear] sets a goal; Claude keeps working across turns until the condition is met. Example: /goal all tests in tests/checkout pass. Use /goal clear to remove it. Give it a condition that can actually be checked.

  • /doctor (alias /checkup) checks installation, settings, extensions and CLAUDE.md, and offers fixes that Claude applies after you confirm. /doctor prompt-audit [path] audits prompt files. Outside a session, the terminal command claude doctor gives a lighter read-only check (Chapter 75).

  • /status shows version, model, account and connectivity: the first thing to check when helping a colleague whose setup behaves differently.

Common misunderstandings
"Slash commands work anywhere in a message."
Only at the very start. Text before the slash turns the whole thing into an ordinary prompt.
"/compact and /clear do the same thing."
/compact keeps a summary and continues the same conversation; /clear starts fresh (the old one stays resumable).
"/rewind is my backup."
It doesn't track changes made by shell commands, most subagent edits, or edits outside Claude Code. Use git for anything important.
"/model only changes this session."
It saves your choice as the default for new sessions. Press s in the picker for this session only.
"If a command is in a tutorial, it exists."
/vim, /pr-comments, /ultraplan and the # shortcut have all been removed. Check /help.
"Skills behave exactly like built-in commands."
Skills are instructions Claude follows with its tools, so results can vary and may ask for permission. Built-in commands behave identically every time.

Key takeaways
  • Slash commands only work at the start of a message; text after the name is the argument.
  • There are built-in commands, bundled skills, one workflow (/deep-research), and commands added by you, plugins and MCP servers.
  • Custom commands come from .claude/skills/ (preferred) or .claude/commands/; plugin skills appear as /plugin:skill; MCP prompts as /server:prompt (MCP).
  • The everyday core: /clear, /plan, /context, /compact, /rewind, /code-review, /diff, /model, /resume, /mcp.
  • Several commands were removed or renamed; your own / menu and /help are always the source of truth.
