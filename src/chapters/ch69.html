Most people use Claude Code one task at a time: ask, wait, review, repeat. But much of the waiting is Claude running tests or reading code, and you could hand it three independent jobs at once. The danger is that three helpers editing the same folder will trip over each other. Claude Code solves this with git worktrees, separate copies of your project that share one history, and with background sessions, which keep working while you do something else. This chapter shows how to run work in parallel safely, how to keep an eye on it, and how to bring the results back together.

69.1Why run work in parallel?

Think about a typical morning for a QA engineer. The nightly run has three unrelated failures: a broken locator on the login page, a timeout in the checkout test, and a test that started failing after a date change. Each fix needs Claude to read code, change something and run the tests, which can take several minutes. Done one after another, you spend most of the morning waiting.

Run in parallel, each fix gets its own Claude session. You check in on each one when it needs a decision, review each result, and merge the good ones.

Good for parallel workBetter done one at a time
Independent bug fixes in different filesTasks that depend on each other's results
Investigating several flaky testsTwo changes to the same file or the same page object
Writing tests for separate featuresWork you need to watch closely, step by step
A long-running investigation while you do other workAnything you can't review properly afterwards
In everyday life

A kitchen with three cooks is faster than one cook, but only if each has their own chopping board. If all three chop on the same board, ingredients get mixed up and someone gets cut. In Claude Code, the worktree is the separate chopping board. You, as head chef, still taste every dish before it goes out.

Cost to remember

Every session uses your plan's allowance (or API credit) independently. Five parallel sessions use roughly five times as much as one. Start with two or three, and only for tasks that are genuinely independent.

69.2Git worktrees, from zero

Normally a git project has one folder on your computer, the checkout, and you can have one branch open in it at a time. A branch is a separate line of work (Chapter 61). If you switch branches, the files in the folder change to match.

A git worktree is an extra folder linked to the same project. Each worktree has its own files and its own branch, but they all share one history and one connection to the remote repository. So you can have the main branch open in one folder and three fix branches open in three other folders, all at the same time.

One repositoryShared history, shared remote (GitHub)
Main checkoutYour normal folder, on main
Worktree AIts own folder and branch: fix the login locator
Worktree BIts own folder and branch: fix the checkout timeout
ResultChanges stay separate until you merge them

You can create worktrees yourself with git's own command, git worktree add, but Claude Code can create and clean them up for you.

69.3Starting Claude in a worktree: --worktree

Pass --worktree (short form -w) with a name:

Terminal
cd ~/projects/shop-tests
claude --worktree fix-login-locator

Claude Code creates a new folder at .claude/worktrees/fix-login-locator/ inside your repository, on a new branch called worktree-fix-login-locator, and starts the session there. Open a second terminal and run the same command with a different name to start a second, fully separate session. If you leave out the name, Claude Code makes one up (something like bright-running-fox).

CommandWhat it does
claude -w fix-login-locatorNew worktree and branch with that name; session starts inside it
claude -wSame, with a generated name
claude -w '#123'Branch from pull request 123 (a PR or merge-request URL also works)
claude --worktree fix-login-locator --resumeGo back to a worktree session you kept earlier
claude -w fix-login-locator --tmuxOpen the worktree session in a tmux session (uses iTerm2 panes where available)

Things to know

  • Trust first. If you've never run Claude in that repository, run plain claude there once and accept the trust prompt, or --worktree will stop with an error.
  • Fresh copy, fresh setup. A worktree starts as a clean checkout, so it has no node_modules and none of your git-ignored files such as .env. Ask Claude to install dependencies (for example npm ci) before running tests.
  • Keep the folder out of git. The documentation recommends adding .claude/worktrees/ to your .gitignore, so the worktree folders don't show up as untracked files.
  • Must be a git repository. Otherwise you'll see "Can only use --worktree in a git repository".

Cleaning up

When you exit a worktree session, Claude Code checks for work you'd lose. A clean, unnamed worktree is removed automatically, along with its branch. If the worktree has changes or new commits, Claude asks whether to keep or remove it. Keeping it leaves the folder and branch, and Claude prints the exact command to resume later.

Copying .env files into new worktrees, and what worktrees share

Tests often need a git-ignored .env file with a base URL or a test account. To copy such files into every new worktree automatically, add a file called .worktreeinclude to the project root. It uses .gitignore syntax, and only files that match a pattern and are git-ignored are copied:

.worktreeinclude
.env
.env.test

Copying secrets into more folders means more places they live on disk, so include only what tests really need (Chapter 98 covers handling secrets).

Worktrees aren't completely isolated. According to the documentation they share:

  • the repository's .git directory (so git commit works inside a worktree);
  • plugins installed at project scope;
  • permission approvals: "Yes, and don't ask again" in a worktree is saved to the main checkout's .claude/settings.local.json and applies everywhere in that repository;
  • untracked project skills, agents and commands, if the worktree has no .claude/skills of its own.

You can choose which branch worktrees start from with the worktree.baseRef setting; by default they branch from the repository's default branch, not from whatever you have checked out.

69.4Background sessions and agent view

Worktrees separate the files. Background sessions separate the attention: a session keeps working without a terminal window open, and you check on it when it needs you.

Research preview

Agent view and background sessions are marked as a research preview in the documentation (verified for Claude Code 2.1.319). Commands and keys may change. Check claude agents --help on your version.

Starting one from the shell

Terminal
claude --bg --name "flaky-checkout" "investigate why the checkout test times out in the nightly run"

The prompt comes after the options, as normal text. Claude Code prints a short ID and the commands to manage it, for example:

Output (shape from the documentation)
backgrounded · 7c5dcf5d · flaky-checkout
  claude agents             list sessions
  claude attach 7c5dcf5d    open in this terminal
  claude logs 7c5dcf5d      show recent output
  claude stop 7c5dcf5d      stop this session

Note: --bg can't be combined with -p (print mode). Print mode answers once and exits, so there's nothing to come back to.

The commands

CommandWhat it does
claude --bg "task" (or --background)Starts a session in the background and returns immediately
claude agentsOpens agent view: one screen listing all background sessions and their state
claude agents --jsonPrints the active sessions as JSON for scripts (add --all to include finished ones)
claude attach <id or name>Opens a background session in this terminal as a full conversation
claude logs <id or name>Prints the session's recent output
claude stop <id> (alias kill)Stops the session; the conversation is kept, and you can attach to it again
claude rm <id>Deletes a background session, and its worktree when that's safe
claude respawn <id> or --allRestarts sessions so they run the current Claude Code version (useful after an update)
claude --bg --exec 'npx playwright test'Runs a plain shell command as a background job

Inside agent view

Run claude agents. Type a prompt and press Enter to dispatch a new session; every prompt you enter there starts a new session, not a follow-up. Select a row with the arrow keys, press Space to peek (see the latest output or the question it's waiting on, and reply), and press Enter or → to attach. Press ← on an empty prompt to detach and go back to the list. Press ? to see all shortcuts.

Row stateMeaning
WorkingClaude is running tools or writing
Needs inputWaiting for you: a question, a permission decision or another prompt
IdleNothing to do; ready for your next prompt
Completed / FailedThe task finished successfully, or ended with an error
StoppedYou stopped it, or its process ended

Moving a session you already have open

Inside a normal session, type /background (alias /bg), or press ← on an empty prompt, to send it to the background. /fork copies the conversation into a new background session while you keep working in this one. If you're attached to a background session, /stop stops it, and /exit only detaches.

Real-world example: how edits stay separate

When a session dispatched with --bg or from agent view is about to edit files in a git repository, Claude first moves it into its own worktree under .claude/worktrees/. So three background fixes don't overwrite each other. When it has changed code, Claude is told to preserve the work: it commits, pushes the branch if there's a remote, and may open a draft pull request. It never pushes to main or master, never force-pushes and never merges. If your CLAUDE.md says you handle git yourself, it leaves git to you.

Know the limits
  • Background sessions run on your machine. They survive closing the terminal and sleep, but stop if the computer shuts down.
  • A session you moved to the background with ← or /background keeps editing the folder it was already in. It isn't moved into a worktree.
  • Outside a git repository there's no isolation, so don't send parallel sessions to edit the same files.

Don't confuse these with background tasks inside one session: pressing Ctrl+B while a long Bash command runs sends just that command to the background, and /tasks lists those commands and subagents.

69.6Cloud sessions and Remote Control

These two sound similar but are opposites. In a cloud session the work runs on Anthropic's computers. With Remote Control, the work runs on your computer and you just steer it from somewhere else.

Cloud sessions

  • Run on Anthropic-managed cloud machines, started from claude.ai/code, the Claude mobile app, the Desktop app, or the terminal.
  • claude --cloud "task" starts one. It clones your GitHub repository at your current branch, so push your changes first.
  • claude --teleport or /teleport pulls a cloud session down into your terminal. From the terminal this is one-way: you can't push a running local session up to the cloud.
  • /web-setup connects GitHub using your local gh sign-in.

Remote Control

  • Lets you continue a local session from claude.ai/code or the Claude iOS or Android app. Commands still run on your machine.
  • Start with claude --remote-control (or --rc), or type /remote-control (/rc) inside a session. claude remote-control runs a server with no local session.
  • Needs a Claude subscription (not an API key). On Team and Enterprise, an Owner must turn it on.
Real-world example

You start a long regression investigation on your work laptop before a meeting, with Remote Control on. During a break you open the Claude app on your phone, see that the session is asking whether it may run the full suite, and approve it. The tests run on your laptop, with your local environment and test data, not in the cloud.

Plan availability, organisation settings and supported providers affect both features. For example, Remote Control isn't available through Bedrock, Google Cloud's Agent Platform or Microsoft Foundry. Check with your admin if an option is missing.

69.7Repeating work: /loop and /schedule

Some QA work is just checking: has the deploy finished? Is the nightly run green yet? Claude Code has three ways to repeat a prompt.

Needs your computer onYesYesNo

/loop 5m check whether the staging deploy has finished and tell me when it's done

/loop tasks belong to the session. Cloud tasks use auto mode for permissions by default and get MCP connectors configured per task.

69.8Safe habits for parallel work

  1. One task per worktree. Never point two sessions at the same folder. Name each worktree after its task.
  2. Keep tasks independent. If two fixes touch the same page object, do them in sequence.
  3. Give each task a clear finish line. "Make checkout.spec.ts pass three runs in a row without weakening assertions" is better than "fix checkout".
  4. Review before merge. Each worktree produces a branch. Read each diff and run the suite yourself (Chapter 71 covers pull requests).
  5. Merge one at a time. After the first merge, the other branches may need updating from main.
  6. Clean up. Remove finished worktrees and sessions (claude rm) so old copies don't pile up.
  7. Watch the cost. Parallel sessions multiply usage. Check /usage.
Three fixes in parallel45 min · any git repository with tests
  1. In your test repository, run claude once and accept the trust prompt. Add .claude/worktrees/ to .gitignore and commit it.a clean git status after the commit.
  2. Pick three small, independent problems (or create them: break three different tests in three different files on purpose, and commit that as your starting point).
  3. Dispatch them as background sessions:

  4. Run claude agents. Watch the three rows. Peek (Space) at one that needs input and answer it.rows moving between Working, Needs input and Completed.

Common misunderstandings
"Parallel sessions are free speed."
Each uses your allowance separately, and each result still needs your review. Parallel work saves waiting time, not review time.
"A worktree is a copy of the whole repository."
It's a separate folder and branch, but it shares the one .git history and remote. Commits made there are in the same repository.
"Background sessions run in the cloud."
No. --bg sessions run on your machine. --cloud sessions run in the cloud.
"Remote Control runs my session on Anthropic's servers."
It runs on your computer; your phone or browser is just the remote.
"A new worktree has everything my tests need."
It's a fresh checkout: no installed packages and no git-ignored files. Install dependencies, and use .worktreeinclude for needed config.

69.9Review

Key takeaways
  • Parallel work helps when tasks are independent and you can review every result.
  • A git worktree is an extra folder with its own branch, sharing one history. claude -w name creates one under .claude/worktrees/ and starts Claude in it.
  • claude --bg starts a background session on your machine; claude agents shows them all; attach, logs, stop, rm and respawn manage them (research preview).
  • Background sessions move into their own worktree before editing, commit their work, and never push to main or merge.
  • Cloud sessions run on Anthropic's machines; Remote Control steers a session that runs on yours.
  • /loop repeats a prompt in an open session; /schedule creates cloud tasks that run without your computer.
Check yourself

What problem do git worktrees solve for parallel Claude sessions?

Separate folders and branches keep parallel edits apart until you merge them.

Where does a session started with claude --bg run?

Background sessions are local. Use --cloud for the cloud.

You want a check to run every morning even when your laptop is closed. Which option fits?

/loop and --bg need your machine running; cloud scheduled tasks don't.

What will a background session that has changed code never do on its own?

It commits and may push its own branch or open a draft PR, but never pushes to main, force-pushes or merges.

With Remote Control on, where do the commands actually run?

Your phone or browser only steers the session.

Assignment

Write a one-page "parallel work policy" for your team. Include: which kinds of tasks may run in parallel, the naming rule for worktrees and background sessions, the maximum number of parallel sessions per person, the review and merge steps, and a cleanup routine. Try it for a week with two or three real tasks, then adjust the policy based on what went wrong.

Teach it

"Claude Code can work on several things at once. A git worktree gives each task its own folder and branch, so edits don't clash. claude --bg starts a task in the background on your machine, and claude agents shows all of them so you can step in when one needs you. Cloud sessions run on Anthropic's machines; Remote Control lets you steer your local session from your phone. Keep tasks independent, and review every branch before you merge."
