Functional tests ask "does it work?". Non-functional tests ask "does it look right, is it fast enough, can everyone use it, and is it safe?". These checks need specialist tools, and the tools have a learning curve. Claude flattens that curve. It writes the scripts, explains the results in plain words, and points out what the numbers or screenshots mean. The specialist tools still do the measuring, and some things, such as how a screen-reader user actually experiences your site, still need people.

123.2Visual testing with Playwright

Visual regression testing compares a new screenshot of a page with an approved one (the baseline) and fails if they differ. Playwright Test has this built in.

tests/visual.spec.ts
import { test, expect } from '@playwright/test';

test('login page looks right', async ({ page }) => {
  await page.goto('https://demo.playwright.dev/todomvc');
  await expect(page).toHaveScreenshot();      // compare with the saved baseline
});

The first time it runs, there's no baseline yet, so Playwright saves one and reports that it wrote it. You check that image and commit it. From then on every run compares against it. When a change is intended, you update the baselines on purpose:

Terminal
npx playwright test --update-snapshots
The big catch

Playwright's documentation warns that rendering varies with the operating system, browser version, settings, hardware and headless mode. A baseline made on a Mac won't match a Linux CI machine. Generate and compare screenshots in the same environment, usually the CI container.

Reducing false alarms

Pages often contain things that change every run: dates, adverts, animations, avatars. Playwright's screenshot assertion has options for this, such as hiding parts of the page with mask, turning off animations, and allowing a small number of differing pixels with maxDiffPixels. Ask Claude Code: "Make the visual test ignore the clock and the user avatar, and explain each option you used." Check the options it uses against the Playwright docs page linked in the sources.

Claude as a second pair of eyes

Claude can read images. Paste a screenshot into Claude Code (or let it take one with Playwright MCP) and ask a question a pixel comparison can't answer:

Prompt
Here are the checkout page at desktop width and at 390px phone width.
Look for layout problems a user would notice: overlapping or cut-off text,
buttons off-screen, unreadable contrast, misaligned prices. List each with its location.

Pixel comparison is good at

  • Catching any change at all, however small
  • Being exactly repeatable
  • Running on every commit

Claude reviewing images is good at

  • Judging whether a change looks wrong to a person
  • Explaining the problem in words
  • Pages without a baseline yet

Use both: pixel comparison as the automatic gate, Claude to triage differences and review new pages. Claude can miss small details and occasionally describes things that aren't there, so confirm anything it reports before filing a bug.

123.3Performance testing with k6

Load testing means sending many requests at once to see how a system behaves under pressure. k6 is a popular open-source load-testing tool from Grafana Labs. You write tests in JavaScript and run them from the terminal. Claude is very good at writing k6 scripts, which makes performance testing far more approachable for testers who aren't performance specialists.

In everyday life

A restaurant that serves one customer perfectly might collapse when 200 arrive at once. Load testing is a rehearsal dinner with a crowd: you find out where the kitchen jams before the real opening night.

checkout-load.js — a simple k6 test
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 20,               // 20 virtual users at the same time
  duration: '1m',       // for one minute
  thresholds: {
    http_req_failed: ['rate<0.01'],     // fewer than 1% of requests may fail
    http_req_duration: ['p(95)<500'],  // 95% of requests under 500 ms
  },
};

export default function () {
  const res = http.get('https://quickpizza.grafana.com');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);              // each virtual user pauses 1 second, like a real person
}
Terminal
k6 run checkout-load.js

The thresholds turn a performance test into a pass/fail check: if fewer than 95% of requests finish within 500 milliseconds, or more than 1% fail, k6 marks the whole test as failed. That means you can run it in CI like any other test. The example uses quickpizza.grafana.com, a demo site Grafana provides for k6 practice. Only load-test systems you own or have permission to test.

Reading the results: why "p95" matters more than the average

k6 reports response times as averages and as percentiles. p95 is the time within which 95% of requests finished; the slowest 5% took longer. Averages hide pain: if 90 requests take 100 ms and 10 take 5 seconds, the average is about 0.6 seconds, which sounds fine, while one user in ten waits five seconds. Percentiles show that tail. This is why thresholds are usually set on p95 or p99.

Paste the k6 summary into Claude and ask: "Explain these results for a non-specialist, compare p95 with last week's run (attached), and list what to investigate first." It turns a wall of numbers into a short, prioritised story. But the investigation itself (database queries, server metrics, profiling) needs the system's owners and monitoring tools.

Real-world example

A tester who has never written a load test asks Claude Code: "Read our OpenAPI file and write a k6 test for the search and add-to-basket endpoints. Ramp up to 50 users over 2 minutes, hold for 5, ramp down. Fail if p95 is over 800 ms. Explain every line." Within minutes they have a working script and understand it. The team's performance engineer reviews the realistic-load assumptions; the tester owns running it.

Claude can also convert or explain scripts for other tools your organisation already uses, such as Apache JMeter. The principle is the same: Claude writes and explains, the load tool measures, people decide what "fast enough" means.

123.4Accessibility basics

Accessibility means people with disabilities can use your product: people who are blind and use a screen reader, who can't use a mouse, who are colour-blind, deaf, or have cognitive or motor impairments. It's a legal requirement in many countries and simply good quality.

The standard most organisations follow is WCAG (Web Content Accessibility Guidelines) from the W3C. The current version, WCAG 2.2, became a W3C Recommendation in October 2023. It's organised around four principles:

PrinciplePlain meaningExample check
PerceivablePeople can see or hear the content in some formImages have text alternatives; enough colour contrast
OperablePeople can use every controlEverything works with a keyboard alone; focus is visible
UnderstandableContent and behaviour make senseForm errors explain how to fix them
RobustIt works with assistive technologyButtons are real buttons, with names a screen reader can announce

Success criteria come in three levels: A (minimum), AA (the usual legal and corporate target) and AAA (highest).

123.5Automating accessibility checks with axe-core

axe-core is a widely used open-source accessibility testing engine. The @axe-core/playwright package lets you run it inside Playwright tests, and Playwright's documentation has a guide for it.

Terminal
npm install --save-dev @axe-core/playwright
tests/a11y.spec.ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('home page has no detectable WCAG A/AA violations', async ({ page }) => {
  await page.goto('https://demo.playwright.dev/todomvc');
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'])  // only WCAG A and AA rules
    .analyze();
  expect(results.violations).toEqual([]);   // fail if anything was found
});

When a test fails, the violations list is long and technical. This is where Claude earns its place:

Prompt in Claude Code
Run tests/a11y.spec.ts. For each violation: explain in plain English who is affected
and how, which WCAG success criterion it relates to, the exact element, and the smallest fix.
Write it as a bug report a developer can act on. Group duplicates.

Claude reading the accessibility tree

The Playwright MCP server shows Claude the page's accessibility tree: the structure a screen reader uses (Chapter 102). That lets Claude spot problems a rule engine may not, such as a button announced only as "button" with no name, or headings that skip levels, and explain how the page would sound to a screen-reader user.

123.6What automation can't check

Important

Playwright's own guide says plainly that automated testing cannot detect all types of WCAG violations. A clean axe report means "no detectable problems", not "accessible".

Automation and AI can help with

  • Missing labels and alternative text
  • Colour contrast
  • Invalid structure and roles
  • Explaining issues and drafting fixes
  • Suggesting manual test steps

Still needs people

  • Real screen-reader testing (VoiceOver, NVDA, JAWS)
  • Keyboard-only journeys end to end
  • Whether alt text is actually meaningful
  • Cognitive load and clarity of language
  • Testing with disabled users, the gold standard

A good use of Claude here: "Write a 20-minute manual screen-reader test script for the checkout, step by step, with what a tester should hear at each step." It makes manual testing faster to plan, without pretending to replace it.

123.7Security testing basics for QA

Security testing is a specialist field, and serious testing (penetration tests, security code review) belongs to security professionals and only with authorisation. But QA engineers can catch many problems early with negative tests, and Claude is good at brainstorming abuse cases:

Prompt
For the "change email address" feature described in @docs/stories/ACC-77.md, list abuse cases
a QA engineer should test (authorisation, input handling, rate limits, session handling),
each as a test idea with expected behaviour. Only suggest tests appropriate for our own
staging environment. Mark which ones need the security team.

Typical QA-level checks include: can user A see or change user B's data by editing an ID in the URL; do forms reject script and SQL-like input safely; do sessions expire; are errors free of internal details. Common misunderstandings
"A passing axe scan means the site is accessible."
It means no automatically detectable problems. Manual and real-user testing are still needed.
"The average response time tells me if it's fast."
Look at p95 and p99: averages hide the slow experiences that users complain about.
"Claude can load-test the site by itself."
Claude writes and explains the scripts; a tool like k6 generates the load and measures.
"Screenshot baselines work everywhere."
Rendering differs between machines. Create and compare baselines in the same environment.

123.8Review

Key takeaways
  • Playwright's toHaveScreenshot() compares against baselines; keep them in one consistent environment and update them deliberately.
  • Claude complements pixel comparison by judging whether a page looks wrong and explaining why.
  • k6 scripts with thresholds turn performance into pass/fail checks; Claude writes and explains them; percentiles matter more than averages.
  • WCAG 2.2 (A, AA, AAA) is the accessibility standard; axe-core automates part of it, Claude explains results, and people must test the rest.
  • QA can catch basic security problems with negative tests and abuse cases; deeper testing belongs to security specialists.
Check yourself

The first run writes the baseline; check it and commit it.

In k6, what does the threshold http_req_duration: ['p(95)<500'] mean?

p(95) is the 95th percentile of response times.

Automated tools catch only part of WCAG.

Each does what it's good at.
