A sandbox is a fence the operating system puts around the shell commands Claude runs. Inside the fence, commands can write only to your project folder and a temp folder, and can reach only the internet hosts you've approved. Because the operating system enforces the fence while each command runs, it holds even if Claude, or a malicious file Claude read, tries something unexpected. That is why Claude Code can safely run sandboxed commands without asking you each time. But the fence surrounds only shell commands: Claude's own file tools, hooks and local MCP servers sit outside it.

79.1Why a sandbox?

Permission prompts protect you, but they wear you down. After the fortieth "Allow npm test?" most people click Yes without reading, which is no protection at all. Permission rules (Chapter 78) help, but they match command text: a deny on Bash(curl *) doesn't stop /usr/bin/curl, and an allowed npm test might run a test script that does far more than its name suggests.

The sandbox takes a different approach. Instead of judging the command before it runs, it limits what any command can reach while it runs. A test script that tries to write to your home folder or post data to an unknown server simply fails.

In everyday life

A laboratory glovebox. A chemist can do anything they like with what's inside the box, quickly and without filling in a form for each step, because the box itself stops anything escaping. The safety comes from the box, not from checking each movement of their hands. But the glovebox only contains what's inside it: the chemist's coffee cup on the bench is not protected by it.

Anthropic built the sandbox on its open-source @anthropic-ai/sandbox-runtime package. On macOS it uses Apple's built-in Seatbelt framework; on Linux and WSL2 it uses bubblewrap (an unprivileged isolation tool) plus socat (a network relay).

79.2What it restricts by default

The sandbox is off by default. Once on, every shell command Claude runs (Bash, PowerShell and Monitor commands), and every process those commands start, lives inside these limits:

AccessDefault inside the sandboxChange it with
WritesOnly the working directory, a per-user temp directory, and directories you added (--add-dir, /add-dir, permissions.additionalDirectories). Protected paths stay write-denied.sandbox.filesystem.allowWrite, denyWrite
ReadsMost of the machine, including credential files such as ~/.ssh and ~/.aws/credentialssandbox.filesystem.denyRead, allowRead, sandbox.credentials
NetworkNo direct route out. Traffic goes through a local proxy that checks each host against your allowed domains, which start empty.sandbox.network.allowedDomains, deniedDomains
Environment variablesInherited from Claude Code, including any secrets in itsandbox.credentials
Read the "Reads" row twice

The default sandbox stops commands writing almost anywhere and sending almost anywhere, but it lets them read most files, including SSH keys. The network limit is what stops a stolen key leaving your machine. If you widen the network list, protect credentials explicitly (79.5).

Under the hood: how the network fence works

On Linux and WSL2 a sandboxed command runs in its own network namespace with no connection to your network. On macOS, Seatbelt blocks every connection except the one to the sandbox proxy. Claude Code runs that proxy on your machine, outside the sandbox, and points commands at it with HTTP_PROXY, HTTPS_PROXY and related variables. The proxy checks the hostname of each connection against your allowed and denied domains.

Consequences: tools that honour proxy variables (curl, npm, git over HTTPS) work once their host is allowed. Tools that ignore them, such as plain ssh and most database drivers, can't connect even to an allowed host. Anything that isn't TCP (UDP, HTTP/3 over QUIC, ping) can't leave at all. The proxy also refuses an allowed hostname that resolves only to a local address such as 127.0.0.1 or the 169.254.169.254 cloud metadata endpoint, which blocks a classic trick for stealing cloud credentials.

By default the proxy decides from the hostname and does not inspect encrypted (TLS) traffic.

79.3What runs outside the sandbox

This is the part most people get wrong. The sandbox wraps shell commands only. These run outside it:

Outside the sandboxWhat governs it instead
Claude's built-in file and web tools: Read, Edit, Write, WebFetch, WebSearchPermission rules. A denyRead entry doesn't stop the Read tool; allowedDomains doesn't limit WebFetch.
Command hooksRuns with your full access. Review hook scripts (Chapter 82).
Local MCP serversRun with your full access. A local Playwright or database MCP server is not fenced (Chapter 105).
Plugin monitors, LSP servers, mods, your status line command, apiKeyHelperYour full access
Commands you type yourself at the ! promptUnsandboxed in most sessions
Commands matching sandbox.excludedCommandsThe normal permission flow
Unsandboxed retries that you (or a mode) approveThe normal permission flow (79.4)

Subagents run in the same process as your session and share its sandbox, so their Bash commands are sandboxed too. To put everything behind one boundary, run the whole Claude Code process inside a container, a virtual machine, a dev container or the sandbox runtime itself (79.8).

79.4Turning it on and proving it works

Step 1: dependencies (Linux and WSL2 only)

Terminal (Ubuntu or Debian)
sudo apt-get install bubblewrap socat
Terminal (Fedora)
sudo dnf install bubblewrap socat

macOS needs nothing extra. On WSL, the sandbox needs WSL2, not WSL1 (wsl -l -v in PowerShell tells you which).

Step 2: run /sandbox

Inside a session, /sandbox opens a panel with tabs:

  • Mode: auto-allow or regular permissions (below).
  • Overrides: whether failed commands may fall back to running unsandboxed. It shows the allowUnsandboxedCommands setting as "Strict sandbox mode".
  • Config: the resolved settings, including protected paths under "Denied within allowed".
  • Dependencies (Linux): appears when something is missing. If it's the only tab, the sandbox can't start yet.

Choosing a mode saves sandbox.enabled to .claude/settings.local.json, for this project. To sandbox every project, put it in your user file:

~/.claude/settings.json
{ "sandbox": { "enabled": true } }

Or try it for one session without saving anything:

Terminal
claude --settings '{"sandbox": {"enabled": true, "allowUnsandboxedCommands": false}}'
Silent fallback

If the platform doesn't support the sandbox or a dependency is missing, Claude Code by default runs commands unsandboxed. If you rely on the sandbox, set "failIfUnavailable": true inside the sandbox block so Claude Code refuses to start instead.

Step 3: prove it

Ask Claude to run these. (Don't type them yourself after !: your own commands usually run outside the sandbox.)

Ask Claude to runExpected result inside the sandbox
touch ~/sandbox-probeFails: Operation not permitted on macOS, Read-only file system on Linux and WSL2
curl --noproxy '*' https://example.comFails: Could not resolve host, because there is no route around the proxy

If Claude offers to retry outside the sandbox, say no. If touch succeeded, delete ~/sandbox-probe and run /sandbox to check it's really on.

The two sandbox modes

Auto-allow (default)

A command that runs inside the sandbox is approved automatically, with no prompt, because the fence contains it. Commands that run outside it (excluded or retried) go through normal permissions.

Regular permissions

Every Bash command still goes through the normal permission flow, even though it's sandboxed. More control, more prompts.

Even in auto-allow, some things still stop: commands matching a Bash deny rule, content-scoped ask rules such as Bash(git push *), rm or rmdir aimed at critical paths, and Monitor commands. Commands where a leading variable assignment could change what runs, such as FOO=bar npm test, also go through normal permissions (but still run sandboxed).

Auto-allow works even in Manual mode

With auto-allow on, sandboxed Bash commands that modify files inside the fence run without prompting even in Manual mode, where the Edit tool would still prompt. The fence, not you, is the safeguard for those commands. Plan mode is the exception: auto-allow doesn't widen approvals there.

The escape hatch

When a command fails inside the sandbox, Claude may retry it with a dangerouslyDisableSandbox flag. That retry runs unsandboxed. Who approves it depends on your mode: in Manual and acceptEdits you see a prompt titled "Bash command (unsandboxed)"; in auto mode the classifier judges it; in dontAsk it's denied; in bypassPermissions it just runs. A matching allow rule such as Bash(curl *) also approves the unsandboxed retry, so be careful with broad allows. To remove the hatch entirely, set "allowUnsandboxedCommands": false (strict sandbox mode).

79.5Configuring the fence

All sandbox settings live under the sandbox key. Filesystem lists from different settings files merge, and edits apply to the next command without a restart.

Different path style from permission rules

Sandbox paths use ordinary conventions: /tmp/build is absolute and ~/.kube is in your home folder. Permission rules use //path for absolute and /path for project-relative. Same idea, different spelling: easy to get wrong.

Files

Let a tool write outside the project
{
  "sandbox": {
    "enabled": true,
    "filesystem": { "allowWrite": ["~/.kube", "/tmp/build"] }
  }
}
.claude/settings.json: block reading the home folder except this project
{
  "sandbox": {
    "enabled": true,
    "filesystem": { "denyRead": ["~/"], "allowRead": ["."] }
  }
}

When read rules overlap, the narrower path wins. In a project file, . means the project root; in your user file it would mean ~/.claude, so that example belongs in the project file.

Credentials

Hide credential files and secret variables from sandboxed commands
{
  "sandbox": {
    "enabled": true,
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" },
        { "name": "NPM_TOKEN", "mode": "deny" }
      ]
    }
  }
}

Denied files can't be read inside the sandbox, and denied variables are unset before each sandboxed command. Deny entries from all settings files merge, and no file can remove one another file added.

Network

Pre-approve the hosts your tests need
{
  "sandbox": {
    "enabled": true,
    "network": {
      "allowedDomains": ["registry.npmjs.org", "api.test.example.com"],
      "deniedDomains": ["prod.example.com"]
    }
  }
}

The first time a command needs a host that isn't listed, Claude Code prompts in Manual or acceptEdits mode. "Yes" allows it for this session; "Yes, and don't ask again" saves a WebFetch(domain:…) allow rule to your local settings, and the sandbox honours those rules too. Domains in WebFetch(domain:…) allow rules are also pre-allowed for the sandbox.

The test host above is illustrative. When the sandbox blocks a connection, Claude Code names the denied host in the command's result, so run your suite once and read which hosts your tools actually need.

Excluding a command

~/.claude/settings.json
{
  "sandbox": {
    "enabled": true,
    "excludedCommands": ["docker compose *"]
  }
}

Excluded commands run with no filesystem or network limits, through the normal permission flow. Every part of a chained command must match, and matching is on the command text. Prefer allowWrite or allowedDomains when a tool just needs one more folder or host: those keep it fenced.

Exclusions can be turned into an escape

The documentation warns that if you exclude a tool that acts on a file in your working directory, as docker compose does with its compose file, Claude can write that file and then run it outside the sandbox. Keep exclusion patterns narrow.

79.6Protected paths

Even inside the folders where sandboxed commands may write, some files stay write-denied, because changing them could let a command give itself more power. They include:

  • In your working directory and the folders above it: the .claude settings files; .claude/skills, .claude/agents, .claude/commands and .claude/hooks; .mcp.json.
  • In your working directory: shell startup files such as .bashrc and .zshrc, .gitconfig, .vscode and .idea, and hooks and config inside .git.
  • Most of ~/.claude, plus ~/.claude.json and the credential store.

Without this, a sandboxed script could add a hook or an MCP server to your settings, and that hook would run outside the sandbox next time. An allowWrite entry doesn't remove the protection.

79.7How the sandbox fits with permissions and modes

Three layers, each answering a different question:

LayerQuestion it answersCoversEnforced by
Permission rulesMay this tool call happen?Every toolClaude Code, before the call, from the command text
Permission modeWho approves calls no rule decides?Every toolClaude Code (you, a classifier, or nobody)
SandboxWhat can a running shell command reach?Shell commands and their child processesThe operating system, while it runs

/sandbox is not a permission mode, and the sandbox's auto-allow is not the same as auto mode. Auto-allow approves Bash commands because the fence contains them; auto mode uses a classifier to review actions. They work independently and combine well.

With auto mode

In auto mode with the sandbox on, Claude names the extra hosts a command needs on the command itself (for example registry.npmjs.org), and the classifier reviews the hosts together with the command. An approved list opens those hosts for that one command only; nothing is added to your settings. A host that no approved command listed is refused without a prompt. deniedDomains still block, and strict allowlist settings switch per-command lists off.

ModeA sandboxed command reaches an unlisted host
Manual, acceptEdits (and plan, usually)You get a prompt
AutoRefused unless the command listed the host and the classifier approved
dontAskRefused
bypassPermissionsAllowed, unless a strict allowlist setting is on
Real-world example: a QA pairing

A test lead wanted Claude to iterate on a flaky API suite unattended for an hour. She used auto mode for fewer interruptions, the sandbox in auto-allow so test runs didn't need approval, allowedDomains limited to the package registry and the staging API host, deniedDomains for production, and a deny rule on Edit of the expected-results folder. The classifier judged intent, the fence limited reach, and the deny rule protected the oracle. No single layer would have been enough.

79.8Test suites, organisations and limits

Common QA snags (from the documented troubleshooting)

SymptomDocumented fix
Tests can't reach your dev server on localhostmacOS: set sandbox.network.allowLocalBinding to true (this exposes every localhost port to sandboxed commands). Linux/WSL2: a sandboxed command's localhost is private, so run that command via excludedCommands, or have the test command start the server itself.
jest hangs or failswatchman is incompatible: run jest --no-watchman.
Chromium says No usable sandbox! on LinuxStart the browser with --no-sandbox, exclude the test command, or set allowNestedUserNamespaces in your user file (which the docs warn turns off a security boundary).
docker commands failDocker is incompatible; exclude the specific commands you need, e.g. docker compose *.
A host-not-allowed errorApprove the host or add it to allowedDomains.
gh or other Go-based CLIs fail TLS checks on macOSExclude that tool, e.g. gh *, accepting that it runs with your full access.

For organisations

Administrators can require the sandbox through managed settings:

managed-settings.json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false
  }
}

With the retry disabled in managed settings (or with --settings), the sandbox becomes "admin-required" and Claude Code ignores repository settings that would loosen it, including excludedCommands in project files. Because the sandbox doesn't run on native Windows, failIfUnavailable makes Claude Code exit there, so Windows users need WSL2 or a container.

Documented limits

  • Broad domains leak. The proxy decides from the hostname without inspecting TLS, so allowing something as broad as github.com can open paths for data exfiltration, including "domain fronting" tricks.
  • Unix sockets. Allowing a socket such as /var/run/docker.sock effectively grants access to the host.
  • Over-broad writes. Allowing writes to folders on your PATH or to shell startup files can lead to code running outside the fence later.
  • Weaker modes. enableWeakerNestedSandbox (for Docker without privileged namespaces) and allowNestedUserNamespaces considerably weaken isolation.
  • Both halves matter. Without network isolation a compromised command could send out your SSH keys; without filesystem isolation it could plant a backdoor. Check that a widening on one side doesn't undo the other.
Opinion · the author, following Anthropic's documentation

Use the sandbox on every developer machine where Claude runs tests, and pair it with deny rules for file tools. For truly unattended or risky work (untrusted repositories, long autonomous runs, bypassPermissions), go one level up and run the whole of Claude Code in a container or VM, because hooks and local MCP servers sit outside the built-in sandbox.

Common misunderstandings
"With the sandbox on, Claude can't touch anything outside my project."
Only shell commands are fenced. Claude's Read, Edit and Write tools, hooks and local MCP servers are not; permission rules govern the file tools.
"The sandbox stops commands reading my SSH keys."
Not by default: reads are allowed almost everywhere. Add credentials or denyRead entries.
"If the sandbox can't start, Claude Code won't run commands."
By default it falls back to running them unsandboxed. Set failIfUnavailable if you depend on it.
"Sandbox auto-allow and auto mode are the same thing."
Auto-allow trusts the fence; auto mode uses a classifier. They're independent and can be combined.
"Allowing github.com is harmless."
The docs warn that broad domains can be used to exfiltrate data. Allow the narrowest hosts you can.

79.9Review

Key takeaways
  • The sandbox is an operating-system fence around shell commands and their child processes: Seatbelt on macOS, bubblewrap and socat on Linux and WSL2, nothing on native Windows.
  • Off by default. Turn it on with /sandbox or "sandbox": {"enabled": true}; set failIfUnavailable if you rely on it.
  • Defaults: writes only to the project, temp and added folders; reads almost everywhere; network only via a proxy to allowed domains (initially none).
  • File and web tools, hooks, local MCP servers and your own ! commands run outside it.
  • Widen with allowWrite and allowedDomains before reaching for excludedCommands; protect secrets with credentials; turn off the unsandboxed retry with allowUnsandboxedCommands: false.
  • Rules, modes and sandbox are complementary layers; for full isolation, run Claude Code in a container or VM.
Check yourself

With the sandbox enabled, which of these runs inside it?

The sandbox wraps shell commands and their children. MCP servers, hooks and the built-in file tools run outside it.

By default, can a sandboxed command read ~/.ssh/id_ed25519?

The default read policy is broad; the network limit is what stops the key leaving. Protect credentials explicitly.

Your test tool needs to write to /tmp/build. What's the preferred fix?

allowWrite keeps the tool fenced and widens only one path; exclusion removes all limits.

What does "allowUnsandboxedCommands": false do?

It makes Claude Code ignore the dangerouslyDisableSandbox retry; commands stay sandboxed unless they match excludedCommands.

On Linux, your sandboxed test command can't reach a dev server you started on localhost. Why?

On Linux and WSL2 the command runs in its own network namespace. Exclude that command, or have it start the server itself.
