Claude Code reads its behaviour from a few plain JSON files called settings files: one for you on this machine, one shared by your team in the repository, one private to you in that repository, and optionally one pushed by your company. When files disagree, a fixed order decides who wins, except that lists of rules are combined. The most important thing these files hold is permission rules: lists of what Claude may do without asking, what it must always ask about, and what it may never do. Those rules are enforced by Claude Code itself, not by Claude's good intentions, so they are the right place to put your team's safety limits.

78.1Where settings live

A setting is one named choice, such as which model to use or which commands need approval. Settings are stored as keys in JSON files. There are four places Claude Code looks:

ScopeFileWho it affectsCommit to git?
User~/.claude/settings.jsonYou, in every project on this machineNo (it's in your home folder)
Shared project.claude/settings.jsonEveryone who works in the repositoryYes: this is the team's file
Project local.claude/settings.local.jsonYou, in this repository onlyNo: keep it out of git
Managedmanaged-settings.json (or MDM / server-managed)Everyone your organisation deploys it toNot yours to edit

The managed file sits in a system folder: /Library/Application Support/ClaudeCode/managed-settings.json on macOS, /etc/claude-code/managed-settings.json on Linux and WSL, and C:\Program Files\ClaudeCode\managed-settings.json on Windows. Administrators can also deliver managed settings from the claude.ai admin console or through device-management tools.

In everyday life

Think of an office. Company policy (managed) applies to everyone and can't be overruled. The team's shared handbook (project) sits in the team folder. Your sticky notes on your own monitor (local) only affect you at that desk. Your personal habits (user) travel with you to every desk. When your sticky note and the team handbook disagree on something small, your sticky note wins at your desk; when company policy speaks, everyone follows it.

A few facts that save confusion:

  • Nothing is created at install. Claude Code writes ~/.claude/settings.json the first time you change certain /config options, and .claude/settings.local.json the first time you answer "Yes, and don't ask again" on a permission prompt.
  • The local file is kept out of git for you. When Claude Code first writes it in a git repository, it adds **/.claude/settings.local.json to your global git excludes file. If you create it by hand, add it to .gitignore yourself. In a git repository the local file lives at the repository root.
  • ~/.claude.json is a different file. Claude Code writes it itself: your account, MCP servers at local and user scope, trust decisions. You don't normally edit it.
  • Strict JSON only. No comments, no trailing commas. A // comment makes the file a "Settings Error" at the next start.
  • Autocomplete helps. Add "$schema": "https://json.schemastore.org/claude-code-settings.json" as the first key and editors such as VS Code will suggest keys and flag mistakes.

78.2Who wins: precedence and merging

When the same key appears in more than one place, the highest level wins (settings precedence):

1. ManagedCompany policy. Nothing overrides it, not even --settings
2. Command line--settings <file-or-json>, for one session
3. Project local.claude/settings.local.json
4. Shared project.claude/settings.json
5. User~/.claude/settings.json

Two rules change how that plays out in practice:

  1. Lists merge instead of overriding. If permissions.allow appears in your user file and the team file, Claude Code combines both lists. Each file adds rules; none erases another's. (A few model-list keys such as fallbackModel follow their own rules.)
  2. A deny anywhere is final. If a tool is denied at any level, no other level can allow it. A deny in your personal user file beats an allow in the team file, and a managed deny beats --allowedTools on the command line.

Environment variables are not a level in this stack. Each variable that pairs with a key has its own rule; for example, an exported ANTHROPIC_MODEL beats the model key, and the --model flag beats both.

Trying a setting for one session

Terminal
claude --settings '{"model": "claude-opus-5-5"}'          # inline JSON, this session only
claude --settings ./ci-settings.json                      # or a file
claude --setting-sources user,project                     # load only these sources (skips local)

Checking what actually loaded

  • /status inside a session shows a Setting sources line listing each file that loaded, such as "User settings" or "Project local settings". It tells you which files were read, not which file supplied each key.
  • claude doctor from your terminal lists entries Claude Code rejected, such as a malformed permission rule.
  • Most edits reload live, including permissions and hooks. A few keys, such as model and effortLevel, are read only at session start.
Under the hood: what happens with a broken file

If a user, project or local file has invalid JSON or a value the schema rejects, an interactive session opens with a Settings Error dialog: fix it with Claude's help, exit, or continue without that file. If only individual entries are wrong, such as one malformed rule or an unknown hook event, you get a Settings Warning and Claude Code skips just those entries.

In print mode (claude -p) there is no dialog: broken files or values are silently skipped. That matters in CI, where a typo in a deny rule could quietly remove a safety limit. After a -p run that seems to ignore a setting, run claude doctor to see what was dropped.

78.4Permission rules: allow, ask, deny

Every time Claude wants to use a tool (run a shell command, edit a file, fetch a web page, call an MCP tool), Claude Code checks your rules first. There are three lists:

allow

Run without asking me. Use for safe, repetitive things: running the test suite, linting, reading logs.

ask

Always ask me, even in modes that normally wouldn't. Use for risky things you still sometimes want: git push, running arbitrary scripts.

deny

Never. Use for things that must not happen: reading .env, deleting folders, hitting production.

no match

The current permission mode decides (Chapter 67). In Manual mode that means a prompt.

1. deny?If any deny rule matches: blocked
2. ask?If any ask rule matches: prompt
3. allow?If any allow rule matches: runs
4. modeOtherwise the permission mode decides

The order is fixed: deny, then ask, then allow. The first match wins and specificity does not matter. So a broad deny Bash(aws *) blocks aws s3 ls even if you also wrote a precise allow Bash(aws s3 ls). You cannot carve an exception out of a deny with an allow.

Rules are enforced; instructions are not

Writing "never read .env files" in CLAUDE.md shapes what Claude tries to do. It doesn't stop anything. Permission rules are checked by Claude Code before the tool runs, whatever the model decides. Put real limits in rules (or hooks, Chapter 82, or the sandbox, Chapter 79), and use CLAUDE.md for guidance.

Two kinds of deny behave differently. A bare tool name such as "Bash" removes the tool from Claude's view entirely: Claude never even sees it. A scoped deny such as Bash(rm *) leaves the tool available and blocks only matching calls.

.claude/settings.json: the shape of a permissions block
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)"]
  }
}

How Bash rules really match

  • Compound commands are split. Claude Code understands &&, ||, ;, |, |&, & and newlines. For npm test && rm -rf build to run without a prompt, every part must be allowed. Deny and ask rules fire if any part matches, even inside $(…) or a loop.
  • Some wrappers are stripped first. timeout, time, nice, nohup, stdbuf, command, builtin and noglob are removed before matching, so Bash(npm test *) also covers timeout 30 npm test. Runners such as npx, docker exec or devbox run are not stripped, so Bash(npx *) allows anything npx can launch.
  • Read-only commands need no rule. A built-in set including ls, cat, head, tail, grep, find, wc, diff and read-only forms of git runs without a prompt in every mode, with some exceptions (for example find with -delete or -exec).
  • Redirects are checked as file writes. npm test > out.txt checks out.txt against your Edit rules and working directories.
A Bash deny is not a security wall

Rules match the command text. A deny on Bash(git push *) stops git push origin main but not git -C . push origin main; a deny on Bash(curl *) doesn't stop /usr/bin/curl … or sh -c 'curl …'. Deny rules catch the way Claude normally writes a command. When a limit must hold no matter how the command is spelled, add the sandbox (which the operating system enforces) or a PreToolUse hook.

How file paths anchor

Read and Edit rules use gitignore-style patterns. The tricky part is the leading slash:

PatternMeans
//pathAbsolute, from the filesystem root
~/pathFrom your home folder
/pathRelative to the settings file's anchor: the project folder for project and local files, but ~/.claude/ for your user file
path or ./pathRelative to the current directory; a bare file name such as .env matches at any depth

So Read(/secrets/**) in your user settings protects ~/.claude/secrets, not a secrets folder in your project. To protect something in every project from your user file, write Read(**/.env) or use // or ~/.

Under the hood: parameter rules and tool-name globs

Parameter matching. Deny and ask rules can match a top-level input field of a built-in tool with Tool(param:value): Agent(isolation:worktree), Bash(run_in_background:true). You can't use it on a tool's main content field (command for Bash, file_path for Read): Bash(command:rm *) would be easy to bypass with a compound command, so Claude Code ignores it and warns at startup. Allow rules never use parameter matching, because one safe field doesn't make the whole call safe.

Tool-name globs. Deny and ask rules accept "*" (every tool) or "mcp__*" (every MCP tool). Allow rules accept a glob only after a literal server prefix: mcp__github__get_* works; mcp__* as an allow is skipped. MCP rules with parentheses are skipped in settings files; use --disallowedTools for MCP parameter matching.

Typos. A deny or ask rule naming a tool that doesn't exist produces a startup warning, which catches mistakes like writing a display label instead of the canonical name.

78.6Modes, prompts and trust

Rules work together with the permission mode (Chapter 67). As a reminder: default (shown as Manual; manual is an accepted alias), acceptEdits, plan, auto, dontAsk and bypassPermissions. Set the starting mode with permissions.defaultMode, or --permission-mode for one session.

Two surprises worth knowing

From v2.1.283, new interactive terminal and VS Code sessions start in auto mode when it is available; claude -p and the Agent SDK start in default. And defaultMode values auto and bypassPermissions do not take effect from project or local files: put them in your user file. That stops a repository you clone from switching your safety level.

Deny rules apply in every mode, including bypass. Explicit ask rules still prompt in every mode too.

What "Yes, and don't ask again" saves

Prompt typeSaved where, for how long
Bash commandAn allow rule in .claude/settings.local.json at the repository root: permanent, per repository
WebFetch domainSame file: permanent, per repository and domain
File editNot saved to a file: lasts until the session ends

Approving a compound command such as git status && npm test saves a separate rule for each part that needed approval, here npm test. Review that local file now and then: it quietly accumulates.

Workspace trust

Workspace trust works like this: the first time you open Claude Code in a folder, it asks whether you trust it. permissions.allow rules and additionalDirectories in a project's shared .claude/settings.json only take effect after you accept that dialog, and the dialog lists what the folder would grant. A cloned repository can't silently pre-approve Bash(*) for you. Deny and ask rules, which only restrict, are not held back this way.

Real-world example

A tester found she was clicking "Yes" thirty times a day for npx playwright test … and git diff. She ran /fewer-permission-prompts, which proposed allow rules for the read-only commands she used most. She then added one deliberate rule herself, Bash(npx playwright test *), rather than the far broader Bash(npx *), and committed the result so her whole squad benefited. The skill handles the safe read-only bulk; you decide anything that can change state.

78.8A layered setup for a QA repository

Here is a complete, realistic setup for a Playwright and API test repository. Each layer has a clear job.

.claude/settings.json (committed: the team's rules)
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npx playwright test *)",
      "Bash(npx playwright show-report)",
      "Bash(npm run lint)",
      "Bash(npm run test:api *)",
      "Bash(git diff *)",
      "Bash(git log *)",
      "mcp__playwright__browser_snapshot",
      "mcp__playwright__browser_navigate",
      "WebFetch(domain:playwright.dev)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(npm install *)",
      "mcp__playwright__browser_evaluate"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./auth/**)",
      "Edit(/tests/fixtures/golden/**)",
      "Bash(rm -rf *)",
      "WebFetch(domain:prod.example.com)"
    ]
  }
}
LineWhy
git diff *, git log *Read-only git commands often run without a rule anyway; listing them makes the intent explicit for reviewers.
npx playwright test *Lets Claude run and re-run tests freely, the most common action. Narrow on purpose: not npx *.
ask on git push, npm installBoth change things outside your folder (the remote, the dependency tree). A human should glance first.
deny Read(./auth/**)Saved Playwright login state (storage-state files) contains session cookies.
deny Edit(/tests/fixtures/golden/**)Golden files are the expected answers. An AI that "fixes" a failing test by editing the expected output is hiding a bug.
deny WebFetch(domain:prod.example.com)Keep exploration on test environments. (For shell commands such as curl, pair this with the sandbox's network list in Chapter 79.)
.claude/settings.local.json (yours only, not committed)
{
  "permissions": {
    "allow": ["Bash(./scripts/seed-my-local-db.sh)"]
  },
  "env": { "BASE_URL": "http://localhost:3000" }
}
~/.claude/settings.json (you, every project)
{
  "permissions": {
    "defaultMode": "acceptEdits",
    "deny": ["Read(~/.ssh/**)", "Read(~/.aws/**)", "Read(**/.env)"]
  }
}

Because lists merge, a session in this repository has the team's rules, your local extras and your personal denies all at once. Because deny wins everywhere, your personal Read(**/.env) protects you even in a repository whose team file forgot it.

Opinion · the author, drawing on Anthropic's documented guidance

Start strict and loosen with evidence. A team file with a short, deliberate allow list and a firm deny list is easier to review than one built from hundreds of "don't ask again" clicks. Treat changes to .claude/settings.json like code: they go through pull-request review, because an allow rule is a grant of power to an automated agent.

Common misunderstandings
"A more specific allow rule overrides a general deny."
No. Deny is checked first and the first match wins. Specificity is ignored.
"Settings in my project file replace my user settings."
Single values are overridden by the higher level, but lists such as permissions.allow are combined across files.
"Bash(git *) is a sensible way to allow git log."
It allows every git command, including push and reset --hard. Put the * after the subcommand: Bash(git log *).
"Read(/secrets/**) in my user file protects my project's secrets folder."
In the user file, a single leading slash anchors at ~/.claude/. Use **/secrets/**, // or ~/.
"Denying Bash(curl *) means Claude can't reach the internet from the shell."
Rules match command text; /usr/bin/curl or python3 -c … get through. Use the sandbox for an enforced network limit.
"Putting rules in CLAUDE.md is enough."
CLAUDE.md is guidance to the model. Only rules, hooks, modes and the sandbox are enforced.

78.9Review

Key takeaways
  • Four settings files: user (~/.claude/settings.json), shared project (.claude/settings.json), project local (.claude/settings.local.json) and managed. Precedence: managed, command line, local, project, user.
  • Lists merge across files; a deny at any level can't be overridden.
  • Rules are checked deny, then ask, then allow; first match wins; otherwise the permission mode decides.
  • Bash rules match command text: put * after the subcommand, mind the space, and remember a deny is not a wall.
  • File rules use gitignore patterns; // is absolute, ~/ is home, and a single / depends on which file the rule is in.
  • Check with /status, /permissions and claude doctor; write with /permissions, /update-config and /fewer-permission-prompts.
Check yourself

The team file allows Bash(aws s3 ls). Your user file denies Bash(aws *). Claude tries aws s3 ls. What happens?

Deny is evaluated before allow and specificity doesn't matter, so the broad deny blocks it.

Which file should hold rules your whole team should share?

The shared project file is the one meant for version control; the local file is personal and kept out of git.

You want Claude to run any git log command without asking, and nothing else in git. Which rule?

Everything before the first * limits the rule, so the subcommand must come before the wildcard.

What does "Yes, and don't ask again" do for a Bash command?

Bash and WebFetch approvals are saved to the local file; file-edit approvals last only for the session.

A cloned repository's .claude/settings.json sets "defaultMode": "bypassPermissions". What happens?

Those two modes must come from your user settings (or the command line or managed settings), so a repository can't lower your guard.

Assignment

Write a proposed .claude/settings.json for one of your team's real test repositories. Include at least five allow rules for safe, frequent commands, two ask rules and four deny rules (secrets, saved login state, golden or baseline files, production hosts). For every rule, write one sentence of justification in the pull-request description. Then run /fewer-permission-prompts on a week of your own sessions and compare its suggestions with yours.

Teach it

"Claude Code reads settings from four JSON files: mine for every project, the team's in the repo, my private one in the repo, and the company's. The higher one wins on single values, but rule lists are added together. Permission rules come in three lists. Deny is checked first, then ask, then allow, and the first match wins, so you can't punch a hole in a deny. Bash rules match the command text, so put the star after the subcommand, like git log *. And CLAUDE.md is advice; rules are the enforced part."
