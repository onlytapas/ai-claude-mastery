Most command-line tools do one small job well: find lines, count lines, sort lines. The power comes from joining them. Every command reads text in through one channel and writes results out through another, with a third channel kept for error messages. The pipe | feeds one command's output straight into the next, and redirection (>) sends it into a file. Every command also finishes with a number, its exit code, that says whether it succeeded, and that number is what scripts and CI pipelines use to decide what happens next.

55.2grep: find lines that match

grep reads text line by line and prints only the lines that contain a pattern. The name comes from an old editor command, "globally search for a regular expression and print". Its basic shape is:

Syntax
grep [OPTIONS] PATTERN [FILE...]   # square brackets mean "optional"
Terminal (in ~/qa-practice)
grep ERROR logs/app.log
Output
2026-11-09 09:02:40 ERROR Payment service timeout for order 1042
2026-11-09 09:04:18 ERROR Database connection refused
2026-11-09 09:07:10 ERROR Payment service timeout for order 1043

Three of the ten lines matched. Notice what's missing: line 7 says error in lower case. By default grep is case-sensitive, so ERROR and error are different patterns. That's exactly the kind of detail that makes a tester miss a bug in a log, so learn the options.

OptionMeaningExample and what it prints
-iIgnore casegrep -i error logs/app.log prints 4 lines, including the lower-case one
-cCount matching lines instead of printing themgrep -c ERROR logs/app.log prints 3
-nShow line numbersgrep -n WARN logs/app.log prints 3:2026-11-09 09:01:12 WARN … and 8:…
-vInvert: print lines that do not matchgrep -v INFO logs/app.log hides the routine lines, leaving warnings and errors
-wMatch whole words onlygrep -w error matches "error" but not "errors" or "ERROR"
-rSearch every file in a folder, recursivelygrep -r ERROR logs prefixes each line with its file name
-lList only the names of files that contain a matchgrep -l ERROR logs/* prints logs/api.log and logs/app.log
-oPrint only the matching part, not the whole lineSee the pattern examples below
-EExtended patterns, so | means "or"grep -E "ERROR|WARN" logs/app.log
-A 1, -B 1, -C 1Also show 1 line After, Before, or around each matchContext for a stack trace or the request that caused an error
-qQuiet: print nothing, just set the exit codeUsed in scripts (section 55.7)

Options can be combined: grep -in error is the same as grep -i -n error. Here is -r on the whole folder:

Terminal

logs/app.log:2026-11-09 09:07:10 ERROR Payment service timeout for order 1043

Each line now starts with file name: so you know where it came from. That's how you'd search a folder of CI logs for one failing test name.

Patterns: a first taste of regular expressions

The pattern doesn't have to be a plain word. grep understands regular expressions (regex for short), a mini-language for describing text. You only need a few pieces to start:

PieceMeansExample
.Any single characterc.t matches cat, cut, c9t
*The previous thing, zero or more times[0-9]* means "any run of digits"
[0-9], [a-z]One character from a rangeHTTP [45][0-9][0-9] matches 4xx and 5xx codes

A|B (with -E)A or B-E "ERROR|FATAL"
Terminal
grep -o "order [0-9]*" logs/app.log

order 1042
order 1043

-o printed only the part that matched, which pulls the order numbers out of the messages. Always put the pattern in double quotes when it contains spaces or special characters, or the shell will split or change it before grep sees it.

In everyday life

grep is the "Find" box in your browser, but it works on a thousand files at once and gives you every hit as a list you can count, sort or save. -v is like crossing out every line you already know is fine, so the interesting ones are left.

55.3find: locate files by name, type, size or age

grep looks inside files. find looks for the files themselves. It walks down through a folder and every folder inside it, testing each item against the conditions you give.

Syntax
find [WHERE TO START] [CONDITIONS] [ACTION]
Terminal
find . -name "*.log"
Output
./logs/api.log
./logs/app.log

Read it as: start in . (the current folder), and print anything whose name matches *.log. The * is a wildcard meaning "any characters". The quotes matter: without them the shell tries to expand *.log itself before find runs. In zsh, the macOS default shell, an unquoted pattern that matches nothing in the current folder stops the command with zsh: no matches found: *.log.

ConditionMeaningExample
-name "PATTERN"Name matches (case-sensitive)find . -name "*.csv"
-iname "PATTERN"Name matches, ignoring casefind . -iname "APP*" finds app.log
-type f / -type dOnly files / only directories (folders)find . -type d prints ., ./logs, ./reports
-mtime -1Modified less than 1 day ago (+7 means more than 7 days ago)Today's test reports
-size +10MBigger than 10 megabytes (k for kilobytes)Hunting giant log files filling a disk
-exec CMD {} +Run a command on everything found; {} stands for the file namesSee below

Several conditions together must all be true. find . -type f -name "*.log" -mtime -1 means "files, ending in .log, changed in the last day". Combining find with grep answers "which of today's logs mention ERROR?":

Terminal
find . -name "*.log" -exec grep -l ERROR {} +
Output
./logs/api.log
./logs/app.log
find can delete

find also has a -delete action, and people combine it with -exec rm. There is no bin and no undo. Always run the same find command without the delete part first, read the list, and only then add the action.

SystemNotes
macOS / LinuxBoth have find with these options. macOS also has mdfind, which searches the Spotlight index and is much faster across the whole disk.
Windows PowerShellGet-ChildItem -Recurse -Filter *.log (short form gci -r -fi *.log).

55.4wc, sort, uniq and cut: count and summarise

These four small tools turn a pile of lines into an answer.

wc: word count

Terminal
wc logs/app.log
wc -l logs/*.log
Output
      10      79     570 logs/app.log
       4 logs/api.log
      10 logs/app.log
      14 total

With no options wc prints three numbers: lines (10), words (79) and bytes (570), then the file name. -l asks for lines only, which is what you want 90% of the time; -w gives words and -c bytes. Given several files it adds a total line. The spaces in front of the numbers are just padding.

cut: pick out columns

cut -d, -f2 means "split each line at the delimiter , and keep field 2". On the results file that gives the status column:

Terminal
cut -d, -f2 reports/results.csv
Output
status
PASS
PASS
FAIL
PASS
FAIL
PASS
SKIP

The first line is the header. tail -n +2 ("start from line 2") skips it, which you'll see in a moment.

sort and uniq

sort puts lines in order. uniq removes adjacent duplicate lines, so it is almost always used after sort. With -c it counts how many times each line appeared.

CommandDoes
sortAlphabetical order
sort -nNumeric order (so 95 comes before 812, not after it)
sort -rReverse the order; -rn means biggest number first
sort -t, -k3 -nSplit on commas (-t,) and sort by column 3 (-k3), numerically
sort -uSort and drop duplicates in one step
uniq -cCollapse repeated lines and put a count in front

On their own they're mildly useful. Joined together with pipes they become a reporting tool, and that's the next section.

55.5Standard input, output and error

Every program that runs in a terminal is started with three text channels already connected. They're called streams, and each has a number:

NumberNameShort nameNormally connected to
0Standard inputstdinYour keyboard
1Standard outputstdoutYour terminal screen: the normal results
2Standard errorstderrAlso your terminal screen: error and warning messages

Because stdout and stderr both appear on the same screen, they look like one thing. They're not, and you can prove it. Ask ls to list one folder that exists and one file that doesn't:

Terminal
ls logs missing.txt
Output
ls: missing.txt: No such file or directory
logs:
api.log
app.log

The first line went to stderr; the listing went to stdout. Once you start redirecting (next section) you'll see them separate.

In everyday life

Think of a test runner as a worker at a desk with an in-tray (stdin), an out-tray for finished work (stdout) and a separate red tray for problems (stderr). Normally both trays are emptied onto the same table in front of you, your screen. Redirection lets you send the out-tray to one place and the red tray to another, so a report file doesn't fill up with error chatter, and errors don't get lost inside a report.

Under the hood: file descriptors

Inside the operating system, a running program refers to every open file, pipe or terminal by a small whole number called a file descriptor. Unix-like systems (macOS and Linux) agree that 0, 1 and 2 are always stdin, stdout and stderr. That's why redirection uses numbers: 2> literally means "point file descriptor 2 somewhere else before starting the program". The program itself doesn't know or care; it just writes to descriptor 1 or 2 as usual. This is why the same tool can write to a screen, a file or another program without any change to its code.

55.6Pipes and redirection

The pipe: |

A pipe, the vertical bar | (Shift + backslash on most keyboards), connects the stdout of the command on its left to the stdin of the command on its right. Neither command needs to know about the other.

Terminal
grep ERROR logs/app.log | wc -l
Output
       3

grep found the error lines and, instead of printing them, handed them to wc -l, which counted them. When wc reads from a pipe there's no file name, so it prints only the number. Now the one-liner that summarises a test run:

Terminal
tail -n +2 reports/results.csv | cut -d, -f2 | sort | uniq -c | sort -rn
Output
   4 PASS
   2 FAIL
   1 SKIP
tail -n +2drop the header row
cut -d, -f2keep only the status column
sortgroup identical statuses together
uniq -ccount each group
sort -rnbiggest count first

Build pipelines one stage at a time. Run the first command, look at the output, add | next-command, look again. If the final result is wrong, delete stages from the right until you find where it went wrong. A few more QA questions answered this way:

Terminal
tail -n +2 reports/results.csv | sort -t, -k3 -rn | head -3   # three slowest tests
grep -o "ERROR [A-Za-z ]*" logs/app.log | sort | uniq -c | sort -rn   # most common error types
grep -h -o "/api/[a-z]*" logs/*.log | sort | uniq -c | sort -rn   # most mentioned endpoints
Output
checkout_card,FAIL,3021
checkout_paypal,PASS,2210
login_valid,PASS,812
   2 ERROR Payment service timeout for order
   1 ERROR Database connection refused
   3 /api/orders
   1 /api/users
   1 /api/login
   1 /api/checkout

(-h stops grep printing file names when it searches several files.) The middle one is the tester's favourite: it turns a long log into "two payment timeouts and one database failure", which is the first line of a good bug report.

Redirection: >, >>, 2> and <

Redirection connects a stream to a file instead of the screen.

SymbolMeaningExample
> fileSend stdout to a file, replacing whatever was in itgrep ERROR logs/app.log > errors.txt
>> fileSend stdout to a file, adding to the endgrep ERROR logs/api.log >> errors.txt
2> fileSend stderr (stream 2) to a filels logs missing.txt 2> ls-errors.txt
> file 2>&1Send stdout to the file, then send stderr to the same place as stdoutCapture everything a test run prints
2> /dev/nullThrow stderr away. /dev/null is a special file that discards whatever is written to itHide expected noise
< fileFeed a file into stdinwc -l < logs/app.log prints just 10, with no file name
| tee fileShow the output and save a copygrep ERROR logs/app.log | tee errs.txt | wc -l
Terminal
grep ERROR logs/app.log > errors.txt       # prints nothing: the output went into the file
grep ERROR logs/api.log >> errors.txt      # add the API errors on the end
wc -l errors.txt
ls logs missing.txt 2> ls-errors.txt     # the listing shows; the error is saved
cat ls-errors.txt
Output
       5 errors.txt
logs:
api.log
app.log
ls: missing.txt: No such file or directory

3 lines from the first grep plus 2 appended gives 5. In the second pair, the error was diverted to a file while the normal listing still appeared on screen: proof that the two streams are separate.

> empties the file first

The shell opens the target file and empties it before the command starts. sort results.csv > results.csv therefore destroys your data: by the time sort reads the file, it's already empty. Write to a new file, check it, then rename it. And use >> whenever you mean "add to".

Order matters in 2>&1

cmd > all.txt 2>&1 puts both streams in the file. cmd 2>&1 > all.txt does not: it points stderr at the screen (where stdout was at that moment) and only then moves stdout. Read redirections left to right. In zsh and Bash, &> all.txt is a shorter way to write the first form.

SystemNotes
macOS / LinuxIdentical. On Linux GNU wc pads numbers differently, which doesn't matter.
Windows PowerShell|, >, >>, 2> and 2>&1 all exist, but PowerShell pipes pass objects. Equivalents: Measure-Object -Line for wc -l, Sort-Object, Group-Object for sort | uniq -c, Tee-Object, and $null in place of /dev/null.

55.7Exit codes and chaining commands

Every command, when it finishes, hands the shell a number called its exit code (also called exit status or return code). The rule is simple: 0 means success; anything from 1 to 255 means something went wrong. The shell keeps the last command's exit code in a special variable, $?, which you can print with echo.

Terminal
grep ERROR logs/app.log > /dev/null
echo $?
grep FATAL logs/app.log
echo $?
grep FATAL nofile.log
echo $?
Output
0
1
grep: nofile.log: No such file or directory
2

grep documents three outcomes: 0 found a match, 1 found no match, 2 an error such as a missing file. Read $? immediately: the very next command, even echo, replaces it. Other tools have their own meanings above 0, listed in their man page under "EXIT STATUS". For example, ls with a missing file returns 1 on macOS and 2 on Linux.

Real-world example: why CI cares

When a CI pipeline (Jenkins, GitHub Actions, GitLab CI) runs npx playwright test or pytest, it doesn't read the words on screen. It looks only at the exit code. Zero turns the step green; anything else turns it red and stops the pipeline. If a wrapper script swallows the test runner's exit code, a failing suite shows as green. This is one of the most common causes of "the build passed but the tests were failing" (Chapter 57 shows how to pass exit codes on correctly).

&&, || and ;

OperatorMeaningExample
A && BRun B only if A succeeded (exit code 0)mkdir -p out && cd out
A || BRun B only if A failed (non-zero)grep -q ERROR app.log || echo "Clean log"
A ; BRun A, then B, whatever happenedecho one; false; echo two prints both lines
Terminal
grep -q FATAL logs/app.log && echo "Found fatal" || echo "No fatal errors"
Output
No fatal errors

grep -q printed nothing and returned 1 (no match), so the && part was skipped and the || part ran. Two built-in commands make experiments easy: true does nothing and returns 0; false does nothing and returns 1.

Under the hood: what a pipeline's exit code is

A pipeline such as grep FATAL logs/app.log | wc -l has several commands but only one $?. By default it's the exit code of the last command. Here grep failed (1) but wc succeeded, so $? is 0 and the failure is hidden. Bash and zsh have an option, set -o pipefail, that makes the pipeline fail if any stage fails. We tested both: without it the status was 0; with it, 1. Scripts often turn it on (Chapter 57).

SystemNotes
macOS / LinuxIdentical in zsh and Bash.
Windows PowerShellThe last program's exit code is in $LASTEXITCODE. $? exists but is just True or False. && and || work in PowerShell 7 and later, not in the older Windows PowerShell 5.1; ; works in both.
Triage a log and a test run from the terminal35 min · macOS, Linux or WSL

  2. Count error lines both ways: grep -c ERROR logs/app.log and grep -ci error logs/app.log.3, then 4. Write down why they differ.
  3. Show only warnings and errors, with line numbers: grep -n -v INFO logs/app.log.6 lines, starting 3:, 4:, 6:, 7:, 8:, 9:.
  4. Find every log in the folder tree: find . -type f -name "*.log"../logs/api.log and ./logs/app.log (the order can differ).

  6. List only the failing tests: grep ",FAIL," reports/results.csv | cut -d, -f1.checkout_card and search_empty.

Troubleshooting. zsh: no matches found: put the pattern in quotes. No such file or directory: you're not in ~/qa-practice; run pwd. Counts of 0 for things you can see: check upper and lower case, or add -i. The terminal seems stuck after a command: you probably left out the file name, so the tool is waiting for keyboard input on stdin; press Ctrl+C.

Common misunderstandings
"grep found nothing, so the log is clean."
Maybe the case or wording differs. Search with -i, and check the exit code: 1 means no match, 2 means grep couldn't read the file at all.
"> and >> are interchangeable."
> replaces the file's contents; >> adds to the end. Mixing them up silently loses earlier results.
"uniq removes all duplicates."
Only neighbouring ones. Sort first, or use sort -u.
"Error messages are part of a command's output."
They travel on a separate stream, stderr. > file captures only stdout; add 2>&1 to capture both.
"Exit code 1 always means a crash."
It means whatever that tool documents. For grep, 1 simply means "no match", which may be good news.

55.8Review

Key takeaways
  • grep finds lines inside files (-i, -c, -n, -v, -r, -l, -o, -E, -q); find finds files by name, type, size or age.
  • wc -l counts lines; cut picks columns; sort orders; uniq -c counts repeated neighbouring lines.
  • Every program has stdin (0), stdout (1) and stderr (2). Results and errors travel separately.
  • | joins commands; > overwrites a file, >> appends, 2> redirects errors, 2>&1 merges them.
  • Exit code 0 means success. $? shows the last one; && runs on success, || on failure, ; always. CI decides pass or fail from exit codes alone.
Check yourself

Which command counts the lines in app.log that contain "error" in any mix of upper and lower case?

-c counts matching lines and -i ignores case. -v would show the lines that don't match.

You run npx playwright test > run.txt but the error messages still appear on screen and not in the file. Why?

Use > run.txt 2>&1 to capture both streams.

Why does sort | uniq -c usually need the sort?

Sorting puts identical lines together so uniq can count them as one group.

grep -q FATAL app.log returns exit code 1. What does that mean?

For grep, 0 is a match, 1 is no match and 2 is an error such as a missing file.

In run-tests && deploy, when does deploy run?

&& runs the next command only on success, which is why it's the simplest release gate.

Teach it

"Terminal tools each do one small thing: grep finds lines, find finds files, wc counts, sort sorts, uniq counts repeats. The pipe symbol feeds one tool's output into the next, so grep ERROR app.log | wc -l counts errors. Greater-than saves output to a file; two greater-thans add to it. Errors travel on a separate stream, so you capture them with 2>. And every command ends with an exit code, zero for success, which is all CI looks at to turn a build red or green."
