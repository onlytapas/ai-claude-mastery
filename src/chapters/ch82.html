A hook is a small program or check that Claude Code itself runs at a fixed moment: before a tool runs, after a file is edited, when Claude finishes a reply, when a session starts. Instructions in CLAUDE.md are requests that Claude usually follows; a hook happens every time, because the harness runs it, not the model. A hook receives a JSON description of what's happening, and it answers through its exit code or a JSON reply: carry on, block this, or here's extra context. That makes hooks the right tool for rules that must never be skipped, such as "always check test data after an edit" or "never touch application code during a QA session".

82.1What a hook is, and why it's different

Suppose your CLAUDE.md says "Run the linter after every edit." Most of the time Claude will. But it's an instruction to a model, and a long session, a compacted context or a tricky task can make it slip. A hook removes the "most of the time". You register a command against an event, and Claude Code runs it whenever that event happens.

In everyday life

A note on the office door saying "please close the door" is an instruction: people usually comply. A door closer, the spring on the hinge, closes it every time, whoever walked through and however busy they were. CLAUDE.md is the note. A hook is the door closer.

Instruction (CLAUDE.md, skill, output style)

Claude reads it and decides how to apply it. Flexible, can use judgment, can be forgotten or misapplied. Costs context tokens.

Hook

Claude Code runs it at a lifecycle event. Deterministic, can't be talked out of it, and can block actions. Command hooks cost no context unless they return text for Claude.

The official docs draw the same line: use CLAUDE.md for what Claude should know, and a hook for "something that has to happen every time without exception, such as formatting after each edit or blocking a command".

82.2Where hooks live and the shape of a hook

Hooks are written in JSON settings files, plus a few other places:

LocationScopeShared?
~/.claude/settings.jsonAll your projectsNo
.claude/settings.jsonOne projectYes, commit it
.claude/settings.local.jsonOne project, just youNo
Managed policy settingsOrganisation-wideYes, admin-controlled
Plugin hooks/hooks.jsonWhile the plugin is enabledYes (Chapter 84)
Skill frontmatterRest of the session once the skill is invokedYes
Subagent frontmatterWhile that subagent runsYes

Hooks from different levels merge: your user hooks don't replace the project's. Hooks in settings files also fire inside subagents. Every hook has the same three levels of nesting:

1. EventWhen: PostToolUse
2. Matcher groupFilter: "matcher": "Edit|Write"
3. Handler(s)What runs: a command, URL, MCP tool, prompt or agent
.claude/settings.json: the documented shape
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "/path/to/lint-check.sh" }
        ]
      }
    ]
  }
}

Each event name is a key inside the single hooks object. To add a second event, add a sibling key; don't paste a second "hooks" object. Settings files are strict JSON: no comments, no trailing commas.

  • /hooks opens a read-only browser of every configured hook, labelled with where it came from. Edit the files to change them; the file watcher normally picks up edits without a restart.
  • "disableAllHooks": true turns hooks off without deleting them. It can't switch off managed hooks unless it's set in managed settings. For one run, claude --settings '{"disableAllHooks": true}'.

How the events fit together in one session

The docs describe three rhythms. Per session: SessionStart and SessionEnd. Per turn: UserPromptSubmit, then finally Stop (or StopFailure). Per tool call, inside the agent loop: PreToolUse, possibly PermissionRequest, then PostToolUse or PostToolUseFailure, with PostToolBatch after a group of parallel calls. Subagent and task events sit inside that loop; Elicitation sits inside an MCP tool call. The rest (Notification, ConfigChange, FileChanged and so on) fire on their own whenever their trigger happens.

82.4Matchers and the if filter

A matcher decides which occurrences of an event trigger the hook. How it's read depends on the characters in it:

MatcherRead asExample
"*", "" or left outMatch everythingEvery Notification
Only letters, digits, _, -, spaces, , and |Exact names; | or , separates alternativesEdit|Write matches exactly those two tools
Any other characterA JavaScript regular expression, matching anywhere in the valuemcp__playwright__.*; ^Notebook

Matchers are case-sensitive. A regex is unanchored, so Edit.* also matches NotebookEdit; write ^Edit$ for a whole-word match. What the matcher is compared with depends on the event: the tool name for tool events, startup/resume/clear/compact/fork for SessionStart, manual/auto for PreCompact, the notification type (such as permission_prompt or idle_prompt) for Notification, the agent type for SubagentStart/SubagentStop. Some events, including UserPromptSubmit and Stop, ignore matchers and always fire.

For tool events you can filter further with a per-handler if, written in permission-rule syntax (Chapter 78): "if": "Bash(git *)" runs only for git commands, "if": "Edit(*.ts)" only for TypeScript files. It holds exactly one rule, and it's best-effort: when Claude Code can't tell what a Bash command runs, the hook runs anyway. Use real permission rules, not if, for hard allow and deny.

82.5The five handler types

TypeWhat runsDefault timeoutGood for
commandA shell command or program; the event JSON arrives on stdin600 sAlmost everything: checks, formatters, guards
httpThe event JSON is POSTed to a URL; the response body is the reply600 sA central policy or audit service
mcp_toolCalls a tool on a configured MCP server600 sReusing a scanner you already expose over MCP
promptSends the event to a Claude model for a single yes/no judgment30 sFuzzy checks: "are all tasks really complete?"
agentSpawns a subagent that can read files before deciding (experimental)60 sChecks that need to look at the code

Not every event accepts every type. Tool, prompt and stop events accept all five (except PermissionRequest, which has no agent); most others accept only command, http and mcp_tool; SessionStart and Setup accept only command and mcp_tool. Common fields on every handler: type, if, timeout (seconds), statusMessage (spinner text) and once (skill hooks only).

Command hooks: exec form and shell form

Without args, command is passed to a shell, so pipes and && work. With args, Claude Code runs the program directly with no shell, which avoids quoting problems with paths. The docs recommend exec form whenever you use a path placeholder such as ${CLAUDE_PROJECT_DIR} (the project root) or ${CLAUDE_PLUGIN_ROOT}:

Exec form
{ "type": "command", "command": "python3",
  "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/protect_src.py"] }

Other command fields: async: true runs it in the background (it can then no longer block anything), shell picks bash or powershell, and onFailure: "block" (v2.1.295+) makes a crash or timeout block the action instead of letting it through.

A prompt hook

From the docs: ask a model whether Claude should really stop
{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "prompt", "prompt": "Evaluate if Claude should stop: $ARGUMENTS. Check if all tasks are complete." } ] }
    ]
  }
}

$ARGUMENTS is replaced with the event JSON. The model answers {"ok": true} or {"ok": false, "reason": "…"}; on Stop, a false answer feeds the reason back to Claude as its next instruction and the turn continues.

82.6Input: what a hook receives

A command hook reads one JSON object from standard input. Every event includes common fields such as session_id, transcript_path, cwd, permission_mode and hook_event_name; inside a subagent you also get agent_id and agent_type. Tool events add tool_name, tool_input and tool_use_id.

What a PreToolUse hook on Bash receives (from the docs, abbreviated)
{
  "session_id": "abc123",
  "cwd": "/home/user/my-project",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": {
    "command": "npm test",
    "description": "Run test suite",
    "timeout": 120000,
    "run_in_background": false
  },
  "tool_use_id": "toolu_01ABC123..."
}

tool_input depends on the tool. For Write it holds file_path and content; for Edit, file_path, old_string, new_string and replace_all. File paths are absolute. That's why the examples below read tool_input.file_path.

82.7Exit codes and blocking

The simplest way for a hook to answer is its exit code:

Exit codeMeaningWhat happens
0SuccessThe action goes ahead, unless JSON on stdout says otherwise. Plain stdout is added to Claude's context only on UserPromptSubmit, UserPromptExpansion, SessionStart and PostModelSwitch
2Blocking errorOn events that can block, the action stops and your stderr becomes the reason Claude sees. On PostToolUse the tool already ran, so stderr is just shown to Claude
Anything elseNon-blocking errorThe action goes ahead; you see a "hook error" notice
Exit 1 does not block

In ordinary Unix scripts, 1 means failure. In a Claude Code hook, exit 1 is a non-blocking error and the action still happens. A policy hook must use exit 2 (or JSON, below). Likewise, a hook that can't start (wrong path, missing interpreter) or times out lets the action through, unless you set "onFailure": "block".

When a PreToolUse hook blocks, Claude receives a message like this as the tool's error, and adjusts its plan:

Real output from the lab hook (verified on 2.1.319)
PreToolUse:Edit hook error: [python3 ${CLAUDE_PROJECT_DIR}/.claude/hooks/protect_src.py]: Blocked: src/app.js is application code. QA sessions may only change tests/, docs/ and test data.

82.8JSON output: finer control

Instead of exiting 2, a hook can exit 0 and print exactly one JSON object on stdout. Pick one approach per hook. Universal fields work on every event:

FieldEffect
continuefalse stops Claude entirely after the hook
stopReasonMessage shown when continue is false
systemMessageA warning shown to you
terminalSequenceA desktop notification, title or bell, emitted for you
suppressOutputAccepted but now has no effect

Events decide in different ways. Many (UserPromptSubmit, PostToolUse, Stop, SubagentStop, PreCompact, ConfigChange and others) use a top-level "decision": "block" with a "reason". PreToolUse uses hookSpecificOutput:

PreToolUse decision (from the docs)
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Database writes are not allowed"
  }
}
  • permissionDecision is allow (skip the prompt), deny, ask (prompt the user) or defer (non-interactive runs only). With several hooks, deny beats defer beats ask beats allow.
  • An allow from a hook never overrides a deny rule in settings. A deny from a hook blocks even in bypassPermissions mode.
  • updatedInput rewrites the tool's arguments before it runs (replace the whole object). The old top-level approve/block values for PreToolUse are deprecated.
  • additionalContext inside hookSpecificOutput adds a note to Claude's context. Write it as plain facts ("The test environment is staging"); text dressed up as system commands can trigger Claude's prompt injection defences.
  • Strings over 10,000 characters are saved to a file and replaced by a short preview.
Why "nothing but JSON" on stdout matters

Claude Code treats stdout as JSON only if the whole output is one object, starting with { and ending with }. If your shell profile echoes a greeting, or your script prints a debug line first, the output becomes plain text and your decision is silently ignored. Build JSON with a proper encoder (json.dumps in Python, jq -n in shell) rather than gluing strings, so quotes and backslashes are escaped correctly.

82.9Four working examples

1. Check files right after Claude edits them

A QA repository is full of JSON fixtures and Python tests. One stray comma breaks a whole suite. This PostToolUse hook checks the file Claude just wrote and, if it's broken, exits 2 so Claude sees the error and fixes it immediately.

.claude/hooks/check_after_edit.py
#!/usr/bin/env python3
"""PostToolUse hook: check a JSON or Python file right after Claude edits it."""
import json
import py_compile
import sys

data = json.load(sys.stdin)
path = data.get("tool_input", {}).get("file_path", "")

try:
    if path.endswith(".json"):
        with open(path, encoding="utf-8") as f:
            json.load(f)
    elif path.endswith(".py"):
        py_compile.compile(path, doraise=True)
except (ValueError, py_compile.PyCompileError) as err:
    print(f"{path} is broken after your edit: {err}", file=sys.stderr)
    sys.exit(2)

sys.exit(0)

For a JavaScript project, the docs' own one-liner runs Prettier on each edited file (it needs jq and Node.js): "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write". Swap in npx eslint for linting.

2. Block edits to src/

During a QA session you may want Claude to write tests but never "fix" application code to make them pass. This PreToolUse guard blocks any Edit or Write under src/.

.claude/hooks/protect_src.py
#!/usr/bin/env python3
"""PreToolUse hook: stop Claude editing application code under src/."""
import json
import os
import sys

data = json.load(sys.stdin)
file_path = data.get("tool_input", {}).get("file_path", "")
project = os.environ.get("CLAUDE_PROJECT_DIR") or data.get("cwd", ".")

if file_path:
    rel = os.path.relpath(os.path.abspath(os.path.join(project, file_path)), project)
    rel = rel.replace("\\", "/")
    if rel == "src" or rel.startswith("src/"):
        print(f"Blocked: {rel} is application code. QA sessions may only "
              "change tests/, docs/ and test data.", file=sys.stderr)
        sys.exit(2)

sys.exit(0)

Register both scripts in the project's settings, in exec form:

.claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "python3",
            "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/protect_src.py"] }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "python3",
            "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/check_after_edit.py"] }
        ]
      }
    ]
  }
}
A hook is not the only lock

This guard covers the Edit and Write tools. Claude could still change a file through Bash (for example sed -i). For a hard boundary, combine it with permission deny rules such as "Edit(/src/**)" (Chapter 78) and the sandbox (Chapter 79). Hooks are excellent guard rails, not a complete security wall.

3. Get a desktop notification when Claude needs you

~/.claude/settings.json (macOS; from the docs)
{
  "hooks": {
    "Notification": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude Code needs your attention\" with title \"Claude Code\"'"
          }
        ]
      }
    ]
  }
}

On Linux the docs use notify-send 'Claude Code' 'Claude Code needs your attention'. On macOS, if nothing appears, allow notifications for Script Editor in System Settings > Notifications.

4. Inject context at session start

Plain stdout from a SessionStart hook is added to Claude's context. Use it for facts that change: the current branch, the target environment, open defects. (For facts that never change, CLAUDE.md is simpler.)

.claude/settings.json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume|compact",
        "hooks": [
          {
            "type": "command",
            "command": "echo \"Current branch: $(git branch --show-current). Test environment: staging.\""
          }
        ]
      }
    ]
  }
}

The compact value re-injects the facts after compaction, which can otherwise summarise them away.

82.10Security

Hooks run as you

The docs put it bluntly: command hooks "execute shell commands with your full user permissions. They can modify, delete, or access any files your user account can access." Hooks are also outside the sandbox (Chapter 79).

  • Workspace trust. In an interactive session, Claude Code holds back hooks from settings files until you accept the workspace trust dialog for the folder. But claude -p and SDK runs never show that dialog and treat the folder as trusted, so a cloned repository's .claude/settings.json hooks will run. Before scripting -p over a repo you didn't write, review its .claude/ folder, use --bare, or pass --settings '{"disableAllHooks": true}'.
  • Review hooks like code. A pull request that adds or changes a hook is a pull request that can run any command on every teammate's machine.
  • Documented best practices: validate and sanitise input; always quote shell variables ("$VAR"); reject paths containing ..; use absolute paths or ${CLAUDE_PROJECT_DIR}; skip sensitive files such as .env, .git/ and keys.
  • Organisation controls. Admins can set allowManagedHooksOnly in managed settings so only managed (and force-enabled plugin) hooks run.

82.11Testing and debugging hooks

  1. Test the script on its own by piping sample JSON into it and checking the exit code: echo '{"tool_input":{"file_path":"src/app.js"}}' | python3 .claude/hooks/protect_src.py; echo $?.
  2. Check it's registered: /hooks should list it under the right event.
  3. Read the debug log: start claude --debug, then read ~/.claude/debug/<session-id>.txt for lines such as Hooks: PostToolUse:Write […] finished with status 0 (31ms).
  4. Common causes: matcher case wrong (edit instead of Edit); script not executable (chmod +x) in shell form; invalid settings JSON; something printed before your JSON; a Stop hook that blocks forever (check stop_hook_active in its input and exit 0 if it's true).

Troubleshooting. Hook never runs: check /hooks, the matcher's case, and that you accepted workspace trust. "No such file or directory" in a hook error: the script path is wrong; use ${CLAUDE_PROJECT_DIR} with args. Block doesn't happen: the script exits 1 instead of 2, or prints JSON with extra text around it. python3 not found on Windows: use python or the full path to the interpreter.

Common misunderstandings
"Putting a rule in CLAUDE.md is the same as a hook."
CLAUDE.md is advice to the model. A hook is run by Claude Code every time, whatever the model thinks.
"Exit 1 blocks the action."
Only exit 2 (or a JSON deny/block) blocks. Exit 1 is a non-blocking error and the action proceeds.
"A PostToolUse hook can undo an edit."
The tool already ran. Exit 2 shows your message to Claude so it can correct course; to prevent an edit, use PreToolUse.
"A hook's allow overrides my deny rules."
It doesn't. Deny rules in settings still apply, and a hook's deny holds even in bypass mode.
"Hooks only run when I'm watching."
In -p and SDK runs the folder is treated as trusted, so committed hooks run unattended. Review them before automating over unfamiliar repos.

82.12Review

Key takeaways
  • Hooks are run by Claude Code at lifecycle events, so they happen every time; use them for rules that must not depend on the model remembering.
  • Shape: event → matcher group → handlers, in settings files, plugin hooks/hooks.json, or skill and subagent frontmatter; /hooks shows them read-only.
  • There are 33 events in 2.1.319; the workhorses are PreToolUse, PostToolUse, SessionStart, UserPromptSubmit, Stop and Notification.
  • Five handler types: command, http, mcp_tool, prompt, agent (experimental).
  • Exit 0 = proceed, exit 2 = block with stderr as the reason, anything else = non-blocking error. JSON output gives finer control, such as permissionDecision on PreToolUse.
  • Hooks run with your permissions and outside the sandbox; review them like code, and be careful with -p over untrusted repositories.
Check yourself

Your PreToolUse guard script prints a reason and exits with code 1. What happens to the tool call?

Only exit code 2 (or a JSON deny) blocks. Policy hooks must use exit 2.

Which matcher matches only the Edit and Write tools exactly?

Letters and | only means exact names. Edit.* is a regex that also matches NotebookEdit, and matchers are case-sensitive.

Where does a command hook find the details of the event, such as the file Claude is about to edit?

Command hooks read JSON from stdin; HTTP hooks receive the same JSON as the POST body.

You want Claude to automatically see the current git branch whenever a session starts or resumes. Which event fits best?

Plain stdout from a SessionStart hook is added to Claude's context; its matcher can cover startup, resume and compact.

Why is running claude -p over a freshly cloned, unfamiliar repository a hook risk?

Review the repo's .claude folder first, or use --bare or disableAllHooks for that run.

Assignment

Find one rule your team keeps reminding Claude (or each other) about: "don't touch generated files", "keep fixtures valid JSON", "always run the API smoke test before saying done". Decide which event enforces it, write the hook, test it by piping sample JSON, register it in .claude/settings.json, and prove it blocks or reports the bad case in a real session. Write a short pull request description explaining what the hook runs, why, and how to disable it, so a reviewer can assess it safely.

Teach it

"A hook is a check that Claude Code runs itself, at a fixed moment, every time: before a tool runs, after an edit, when a session starts. It gets a JSON description of what's happening on stdin. If it exits 0, things carry on; if it exits 2, the action is blocked and its error message goes to Claude; any other exit code is just a warning. That's how we make rules that can't be forgotten, like 'never edit src/ in a QA session' or 'check fixtures after every edit'. Hooks run with our own permissions, so we review them like code."
