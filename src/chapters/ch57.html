A shell script is a plain text file containing the commands you would otherwise type, one after another. Saving them in a file means you can run the same steps again with one command, share them with your team and run them in CI. Scripts add a few programming ideas on top of what you already know: variables to hold values, arguments to accept input, if to decide, loops to repeat and functions to name a group of steps. The single most important habit is to finish with the right exit code, because that's how CI knows whether your script passed or failed.

57.1Your first script

A shell script is a text file of shell commands. By convention its name ends in .sh, although the shell doesn't care about the extension. Make a folder for this chapter and create a file:

Terminal
mkdir -p ~/qa-scripts && cd ~/qa-scripts
nano hello.sh

Type this in, then press Ctrl+O, Enter to save and Ctrl+X to exit:

hello.sh
#!/usr/bin/env bash
# hello.sh - my first script
echo "Hello from a script"
echo "Today is $(date +%A)"
echo "You are in: $(pwd)"
LineMeaning
#!/usr/bin/env bashThe shebang: which program should run this file (explained below)
# hello.sh - …A comment. Anything after # is ignored by the shell; it's for humans
echo "…"Print a line
$(date +%A)Command substitution: run date +%A (the weekday name) and put its output here

There are two ways to run it:

Terminal
bash hello.sh          # way 1: ask bash to read the file
chmod +x hello.sh      # way 2: make it executable once...
./hello.sh             # ...then run it like any program
Output
Hello from a script
Today is Monday
You are in: /Users/alex/qa-scripts

The ./ means "the file in this folder". You need it because the current folder isn't on PATH (Chapter 56). Without chmod +x, ./hello.sh fails with permission denied and exit code 126.

The shebang

The shebang is the two characters #! followed by the path of an interpreter, on the very first line. When you run ./hello.sh, the operating system reads that line and starts that program to run the rest of the file.

ShebangMeans
#!/usr/bin/env bashFind bash on the PATH and use it. Portable across macOS and Linux; the style used in this chapter
#!/bin/bashUse Bash at exactly that location
#!/bin/shUse the basic POSIX shell: fewer features, runs almost anywhere
#!/usr/bin/env python3The same idea works for Python scripts (Chapter 59)
Why Bash and not zsh?

You type commands in zsh on a Mac, but CI servers and Docker images nearly always have Bash, so team scripts are usually written for Bash. macOS still includes Bash, but an old one: bash --version on our test Mac prints GNU bash, version 3.2.57. Every script in this chapter was tested with that version, so it also runs on the newer Bash found on Linux.

In everyday life

A script is a written test procedure. Instead of a tester following "step 1, step 2, step 3" by hand each time, you write the steps down once in a form the computer can follow exactly. The shebang is the line at the top saying which language the procedure is written in.

57.2Variables and quoting

Syntax
name="Priya"                 # set: no spaces around =
echo "Hello, $name"          # use: $ in front
echo "Report: ${name}_report.txt"   # braces mark where the name ends
today=$(date +%Y-%m-%d)      # store a command's output
total=$((3 + 4))             # arithmetic: whole numbers only

Variables in a script work exactly like the shell variables in Chapter 56, and a script can read any environment variable that was exported to it, such as $HOME or $BASE_URL.

Quote your variables

Rule of thumb: always write "$variable" in double quotes. Without quotes the shell splits the value at spaces, which breaks file names like Login tests.log.

QuotesWhat happens insideExample
Double "…"$variables and $(commands) are expanded; spaces are keptecho "Env: $TEST_ENV" prints Env: staging
Single '…'Nothing is expanded: exactly what you typedecho 'Env: $TEST_ENV' prints Env: $TEST_ENV
NoneExpanded, then split at spaces and wildcards expandedAvoid for variables
Unquoted variables delete the wrong files

If dir="old reports", then rm -r $dir becomes rm -r old reports: two separate folders, old and reports. rm -r "$dir" removes the one folder you meant. This is the most common serious scripting bug.

57.3Arguments: input to your script

Words you type after the script name are its arguments. Inside the script they arrive as numbered variables.

VariableHolds
$0The script's own name, as it was called
$1, $2, …First, second, … argument
$#How many arguments there are
"$@"All the arguments, each kept separate (use this to pass them on)
${2:-staging}Argument 2, or staging if it's missing or empty
greet.sh
#!/usr/bin/env bash
# greet.sh - variables and arguments
name="$1"
env_name="${2:-staging}"
echo "Script name: $0"
echo "Number of arguments: $#"
echo "Hello, $name. Testing against: $env_name"
Terminal

./greet.sh Priya
./greet.sh Priya production
./greet.sh "Priya Shah" uat
./greet.sh Priya Shah uat
Output

Hello, Priya. Testing against: staging
Script name: ./greet.sh
Number of arguments: 2
Hello, Priya. Testing against: production
Script name: ./greet.sh

Compare the last two runs. With quotes, "Priya Shah" is one argument. Without them it's two, so Shah became the environment name. The person running your script has to quote, too.

57.4Making decisions with if

Syntax
if CONDITION; then
  commands
elif OTHER_CONDITION; then
  commands
else
  commands
fi                          # "if" backwards closes the block

The key idea: the condition is just a command, and if looks at its exit code. 0 counts as true; anything else as false. So if grep -q ERROR app.log; then works directly. Most often the command is [ … ], the test command, which compares things. The spaces inside the brackets are required.

TestTrue when
[ -f "$file" ]The file exists (and is a regular file)
[ -d "$dir" ]The directory exists
[ -z "$x" ] / [ -n "$x" ]The text is empty / not empty
[ "$a" = "$b" ] / !=Two pieces of text are equal / different
[ "$n" -eq 0 ]Numbers: -eq equal, -ne not equal, -gt greater, -ge greater or equal, -lt less, -le less or equal
[ ! -f "$file" ]! reverses any test: "file does not exist"

Note that numbers use letters (-gt) and text uses symbols (=). Mixing them up is a common beginner bug. Here is a script that fails when a log contains errors, a realistic CI check:

check-log.sh
#!/usr/bin/env bash
# check-log.sh - fail if a log file contains ERROR lines
log_file="$1"

if [ -z "$log_file" ]; then
  echo "Usage: $0 LOG_FILE" >&2
  exit 2
fi

if [ ! -f "$log_file" ]; then
  echo "No such file: $log_file" >&2
  exit 2
fi

error_count=$(grep -c "ERROR" "$log_file")

if [ "$error_count" -eq 0 ]; then
  echo "OK: no errors in $log_file"
  exit 0
else
  echo "FAIL: $error_count error(s) in $log_file"
  exit 1
fi

>&2 sends a message to stderr, the right place for usage and error messages (Chapter 55). exit N stops the script immediately with exit code N. We use 0 for pass, 1 for "the check found a problem" and 2 for "the script was used wrongly", following grep's convention.

Terminal
chmod +x check-log.sh
./check-log.sh; echo "exit=$?"
./check-log.sh nope.log; echo "exit=$?"
./check-log.sh ~/qa-practice/logs/app.log; echo "exit=$?"
echo "INFO ok" > clean.log
./check-log.sh clean.log; echo "exit=$?"
Output
Usage: ./check-log.sh LOG_FILE
exit=2
No such file: nope.log
exit=2
FAIL: 3 error(s) in /Users/alex/qa-practice/logs/app.log
exit=1
OK: no errors in clean.log
exit=0

57.5Repeating work with loops

loops.sh
#!/usr/bin/env bash
# loops.sh - for and while loops
for browser in chromium firefox webkit; do
  echo "Would run tests in $browser"
done

for file in tests/*.sh; do
  echo "Found test file: $file"
done

count=1
while [ "$count" -le 3 ]; do
  echo "Attempt $count"
  count=$((count + 1))
done
LoopHow it works
for x in a b c; do … doneRuns the body once per word, with $x set to each in turn
for file in tests/*.sh; doThe shell expands the wildcard to a list of matching file names, sorted alphabetically
while CONDITION; do … doneRepeats as long as the condition command returns 0. Something inside must eventually make it false, or it loops forever (Ctrl+C stops it)

To try it you need a tests folder. Create three pretend tests, each a tiny script that passes (exit 0) or fails (exit 1):

Terminal (paste as one block)
mkdir -p tests
printf '#!/usr/bin/env bash\necho "login page loads"\nexit 0\n' > tests/test_login.sh
printf '#!/usr/bin/env bash\necho "search returns results"\nexit 0\n' > tests/test_search.sh
printf '#!/usr/bin/env bash\necho "expected total 42.00 but got 40.00" >&2\nexit 1\n' > tests/test_checkout.sh
chmod +x loops.sh
./loops.sh
Output

Would run tests in firefox
Would run tests in webkit

Found test file: tests/test_login.sh
Found test file: tests/test_search.sh

Attempt 3
Real-world example: waiting for a server

A while loop is how CI scripts wait for an app to start before testing it. This tries a health URL up to 30 times, a second apart, using curl -sf from Chapter 56 as the condition:

tries=0
until curl -sf "$BASE_URL/health" > /dev/null; do
  tries=$((tries + 1))
  if [ "$tries" -ge 30 ]; then
    echo "Server did not start" >&2
    exit 1
  fi
  sleep 1
done

until is the opposite of while: it repeats until the condition succeeds. The /health path is illustrative; use your app's real health or home page.

57.6Functions, and a QA runner

A function gives a name to a group of commands so you can reuse it. Inside a function, $1, $2 are the function's own arguments, and local keeps a variable private to it.

Syntax
log() {
  echo "[$(date +%H:%M:%S)] $1"
}

log "Starting tests"     # call it like a command: prints [14:43:36] Starting tests

Now put everything together. This script runs every test file in a folder, saves each test's output to its own log, prints progress, writes a summary report and exits 1 if anything failed, so CI marks the build red.

run-qa.sh
#!/usr/bin/env bash
# run-qa.sh - run every test in a folder and write a summary report
# Usage: ./run-qa.sh [TEST_DIR] [REPORT_FILE]

test_dir="${1:-tests}"
report="${2:-qa-report.txt}"
passed=0
failed=0
failed_names=""

log() {
  echo "[$(date +%H:%M:%S)] $1"
}

run_test() {
  local test_file="$1"
  local name
  name=$(basename "$test_file" .sh)
  if bash "$test_file" > "logs/$name.log" 2>&1; then
    log "PASS  $name"
    passed=$((passed + 1))
  else
    log "FAIL  $name (see logs/$name.log)"
    failed=$((failed + 1))
    failed_names="$failed_names $name"
  fi
}

if [ ! -d "$test_dir" ]; then
  echo "Test folder not found: $test_dir" >&2
  exit 2
fi

mkdir -p logs
log "Running tests in $test_dir"

for test_file in "$test_dir"/*.sh; do
  run_test "$test_file"
done

total=$((passed + failed))
{
  echo "QA report - $(date '+%Y-%m-%d %H:%M')"
  echo "Total:  $total"
  echo "Passed: $passed"
  echo "Failed: $failed"
  if [ "$failed" -gt 0 ]; then
    echo "Failed tests:$failed_names"
  fi
} > "$report"

log "Report written to $report"
cat "$report"

if [ "$failed" -gt 0 ]; then
  exit 1
fi
exit 0
PartWhat it does
"${1:-tests}"Test folder from argument 1, defaulting to tests
basename "$test_file" .shTurns tests/test_login.sh into test_login
if bash "$test_file" > … 2>&1; thenRuns the test, captures both its streams in a log file, and branches on its exit code
{ … } > "$report"Groups several echos and redirects them into the report file together
Final exit 1 / exit 0Passes the overall result to whoever ran the script: you, &&, or CI
Terminal
chmod +x run-qa.sh
./run-qa.sh; echo "exit=$?"
Output
[14:43:36] Running tests in tests
[14:43:36] FAIL  test_checkout (see logs/test_checkout.log)
[14:43:36] PASS  test_login
[14:43:36] PASS  test_search
[14:43:36] Report written to qa-report.txt
QA report - 2026-11-09 14:43
Total:  3
Passed: 2
Failed: 1
Failed tests: test_checkout
exit=1

cat logs/test_checkout.log shows expected total 42.00 but got 40.00: the failure detail is kept, not lost in the scroll. And because the exit code is honest, the script works as a gate:

Terminal

Using a real test runner

The pretend tests stand in for your real suite. Real runners already return 0 for all-passed and non-zero for failures, so the same pattern applies: run them inside if, or save $? straight away.

Example: wrap Playwright or pytest
npx playwright test > logs/playwright.log 2>&1
status=$?                        # save it before any other command replaces it
echo "Playwright finished with exit code $status"
exit "$status"                   # hand the real result to CI

Swap the first line for python3 -m pytest > logs/pytest.log 2>&1 on a Python project. For a richer report, have the runner write JUnit XML (Playwright's --reporter=junit, pytest's --junitxml=results.xml), which CI tools can display; Chapter 59 shows how to read it with Python.

57.7Exit codes, safety settings and checking your script

Without an exit command, a script's exit code is that of the last command it ran. That's a trap: if the last line is echo "Done", the script returns 0 even though the tests before it failed. Always end with an explicit exit based on what happened.

Strict mode: set -euo pipefail

Many team scripts start with one line after the shebang:

set -euo pipefail
PartEffect
-eStop the script as soon as a command fails (non-zero), except in conditions such as if, && and ||
-uTreat use of an unset variable as an error (catches typos like $BASE_ULR)
-o pipefailA pipeline fails if any stage fails, not just the last (Chapter 55)
Under the hood: the surprises in strict mode

-e stops on any non-zero exit code, including ones that aren't errors. We tested this: with set -e, the line n=$(grep -c FATAL app.log) ends the whole script with exit code 1, because grep returns 1 when it finds nothing, even though a count of 0 is exactly what you hoped for. Write n=$(grep -c FATAL app.log || true) to allow it. Likewise -u stops at the first unset variable with a message such as UNDEFINED_VAR: unbound variable; give optional variables defaults with ${VAR:-default}. In our runner, a failing test is checked inside if, so -e wouldn't stop it. Strict mode is a good default, but understand it before adding it to an existing script.

Check before you run

ToolWhat it does
bash -n script.shReads the script and reports syntax errors (a missing fi or done) without running anything. Silent and exit code 0 means none were found
bash -x script.shRuns it, printing each command (with variables filled in) before it runs, prefixed with +. The best way to see where a script goes wrong
ShellCheckA free checker that warns about unquoted variables and dozens of other common bugs. Install with brew install shellcheck (macOS) or sudo apt install shellcheck (Ubuntu), then run shellcheck run-qa.sh. It also runs online at shellcheck.net

But a script runs with your permissions and can delete files, so read every line you didn't write, run bash -n and ShellCheck, and try it on practice data first. Troubleshooting. bad interpreter: the shebang has a typo, or the file was saved with Windows line endings (fix with your editor's "LF" setting). command not found for your script: use ./ in front. [: missing ]: a space is missing inside the brackets. integer expression expected: you used -eq on something that isn't a number, often an empty variable.

Common misunderstandings
"name = "Priya" sets a variable."
The spaces make the shell run a command called name. Write name="Priya".
"A script that prints FAIL has failed."
CI ignores the words. Only the exit code counts, so end with exit 1 when something failed.
"Quotes around variables are optional."
They're optional only until a value contains a space. Quote every "$variable".
"if [ $a = $b ] and if [ $a -eq $b ] are the same."
= compares text; -eq compares numbers. "07" = "7" is false; 07 -eq 7 is true.
"set -e makes scripts safe."
It helps, but it also stops on harmless non-zero codes (like grep finding nothing) and is skipped inside conditions. Understand it, and still check exit codes deliberately.

57.8Review

Key takeaways
  • A script is a text file of commands. Start it with a shebang (#!/usr/bin/env bash), make it executable with chmod +x, and run it with ./name.sh.
  • name="value" with no spaces; use as "$name", always quoted. $(cmd) captures output, $((…)) does arithmetic.
  • Arguments arrive as $1, $2; $# counts them; ${1:-default} fills gaps.
  • if branches on a command's exit code; [ … ] tests files, text and numbers. for loops over lists or files; while/until repeat on a condition.
  • Functions name reusable steps. End every script with an explicit, honest exit: 0 for success, non-zero for failure.
  • Check with bash -n, debug with bash -x, lint with ShellCheck; read every line of any script you didn't write.
Check yourself

What does the first line #!/usr/bin/env bash do?

That's the shebang. Execute permission still has to be given separately with chmod +x.

You run ./report.sh "Sprint 42" uat. What is $#?

The quotes keep "Sprint 42" as one argument, so there are two: $1 is Sprint 42, $2 is uat.

Your script runs the tests and its last line is echo "Done". The tests fail. What exit code does CI see?

Without an explicit exit, a script returns the last command's code. Save the test runner's $? and exit with it.

Which condition is true when the variable count holds a number greater than zero?

Numbers use -gt, -eq and friends. Inside [ ], > is treated as redirection to a file called 0.

Which command shows each line of a script as it runs, with variables filled in?

-x traces execution; -n only checks syntax without running anything.

Assignment

Write smoke.sh for one of your team's test environments. It should take the base URL as argument 1 (with a sensible default), check three pages or API endpoints with curl -s -o /dev/null -w "%{http_code}" in a loop, print PASS or FAIL for each with a function, write a short report file with the date, and exit 1 if any check failed. Run it through bash -n and ShellCheck, then add it to a pipeline step or share it in a pull request.

Teach it

"A shell script is just the commands you'd type, saved in a file. The first line, the shebang, says which shell runs it; chmod +x makes it runnable; dot-slash runs it. Inside, dollar-one and dollar-two are the arguments, if checks a command's exit code, for repeats over a list, and functions name a group of steps. The rule that matters most: end with exit 0 if everything passed and exit 1 if anything failed, because that number is all CI looks at."
