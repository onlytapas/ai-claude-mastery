About twenty short commands cover most of what you'll do in a terminal: find out where you are, look at what's there, move around, make and organise files, read them, and get help. They all follow one pattern: the command's name, then options that change how it behaves, then arguments that say what to work on. Learn the pattern once and every new command, including the ones Claude Code proposes, becomes readable. The one command to treat with real care is rm, because it deletes immediately with no Bin to rescue you.

54.1The shape of every command

Here is a typical command, taken apart:

Anatomy
ls  -l  -a  ~/Documents
│   └──┬──┘ └────┬────┘
│      │         └── argument: what to work on
│      └── options: how to do it
└── command name: which program to run
PartWhat it isExamples
Command nameAlways first. The program (or shell built-in) to run.ls, cp, git, claude
Options (also called flags or switches)Change how the command behaves. Start with a dash.-l, -a, --version
Option valuesSome options need a value straight after them.head -n 5: the option -n takes the value 5
Arguments (also called operands)Say what to work on: usually file or folder names.notes.txt, ~/Documents

Rules of thumb that hold for nearly every command in this chapter:

  • Spaces separate the parts. That's why names with spaces need quotes (Chapter 53).
  • Short options are one dash and one letter (-l). They can usually be combined: ls -la is the same as ls -l -a.
  • Long options are two dashes and a word (--version). They're easier to read but can't be combined. Many Mac commands support few or no long options (54.10).
  • Options normally come before arguments. ls -l reports, not ls reports -l. (Linux tools often accept either order; Mac tools often don't.)
  • Everything is case-sensitive. -a and -A are different options; LS is not a command.
  • Square brackets in help text mean "optional". ls [file ...] means you may give zero or more file names. Don't type the brackets.
In everyday life

A command is like an order at a coffee shop: "Latte (the command), large, oat milk (the options), for Sam (the argument)". The barista knows what a latte is; the options adjust it; the argument says who it's for. Give the parts in the wrong place or misspell the drink and you get a puzzled reply, which in a terminal is an error message.

54.2Where am I and what's here: pwd and ls

pwd (print working directory) has no options you need. It prints the absolute path of the folder you're in. In this chapter's examples, alex stands for your user name, and all output is real, captured on a Mac while writing.

Terminal
pwd

Real-world example

Before starting Claude Code on a test project, a tester types cd ~/projects/shop-tests, checks with pwd and ls that package.json and tests/ are there, and only then types claude. Two seconds of checking means Claude starts in the right project, with the right CLAUDE.md and settings (Chapter 65).

54.4Making things: mkdir and touch

mkdir (make directory) creates one or more folders. Each argument is a folder to create.

Terminal
mkdir reports logs              # two arguments, two folders
mkdir sprint-42/day-1           # parent sprint-42 doesn't exist yet...
mkdir: sprint-42: No such file or directory
mkdir -p sprint-42/day-1        # -p: create any missing parents too
ls sprint-42
day-1

The error says mkdir couldn't find sprint-42 to put day-1 inside. -p ("parents") creates the whole chain, and also doesn't complain if the folder already exists, which makes it safe in scripts.

touch creates an empty file if the name doesn't exist. If it does exist, it only updates the file's "last modified" time and leaves the content alone.

Terminal
touch notes.txt
ls -l notes.txt
-rw-r--r--@ 1 alex  staff  0 Nov  9 14:48 notes.txt

Size 0: the file exists but is empty. To put a line of text into it quickly:

Terminal
echo "Login test passed" > notes.txt     # > sends echo's output into the file
ls -l notes.txt
-rw-r--r--@ 1 alex  staff  18 Nov  9 14:48 notes.txt
> replaces the whole file

> ("redirect") overwrites the file's existing content without asking. >> adds to the end instead. Both are covered properly in Chapter 55; for now, use > only on files you've just created.

54.5Copying, moving and renaming: cp and mv

Both take the same shape: source first, destination last.

Syntax
cp  [options]  source  destination
cp  [options]  source1 source2 ...  destination-folder
mv  [options]  source  destination

cp: copy

Terminal
cp notes.txt notes-backup.txt          # copy a file to a new name
cp -i notes.txt notes-backup.txt       # -i: ask before overwriting
overwrite notes-backup.txt? (y/n [n]) n
not overwritten
cp logs reports                        # try to copy a folder...
cp: logs is a directory (not copied).
cp -r logs logs-copy                   # -r: copy a folder and everything in it
  • If the destination is an existing folder, the copy goes inside it with the same name. If it's a new name, the copy gets that name.
  • If the destination is an existing file, cp overwrites it silently. -i (interactive) makes it ask first; the [n] in the question means pressing Enter alone answers "no".
  • Folders need -r or -R ("recursive": go into every folder inside). On a Mac, man cp documents -R; -r also works in practice and is what you'll see in most Linux documentation.

mv: move and rename

There's no separate rename command. Renaming is moving a file to a new name in the same folder.

Terminal
mv notes-backup.txt reports/           # move into a folder (trailing / makes the intent clear)
ls reports
notes-backup.txt
mv logs-copy old-logs                  # rename a folder (no -r needed for mv)
mv -i reports/notes-backup.txt notes.txt
overwrite notes.txt? (y/n [n]) n
not overwritten

Like cp, mv silently replaces an existing file at the destination unless you add -i. Unlike cp, it moves folders without needing -r.

Habit worth forming

Use -i with cp, mv and rm until you're confident. It costs one keystroke and prevents the most common accidental overwrite.

54.6Deleting: rm and rmdir, with care

rm (remove) deletes files. There is no Bin. The file doesn't go to the Trash or Recycle Bin, and there is no undo. Recovering it, if possible at all, means backups (Time Machine, Git, a cloud copy).

Terminal
rm -i notes.txt          # -i: ask first
remove notes.txt? n
rmdir old-logs           # rmdir only removes EMPTY folders
rmdir: old-logs: Directory not empty
rm -r old-logs           # -r: remove a folder and everything in it
CommandWhat it deletesAsks first?Risk
rm file.txtOne fileNo (unless the file is write-protected)Medium
rm -i file.txtOne fileYesLow
rmdir folderAn empty folder onlyNo; refuses if not emptyVery low
rm -r folderA folder and everything inside itNo (may ask for protected files)High
rm -rf folderSame, and -f ("force") suppresses all questions and errorsNeverVery high
Read every rm before pressing Enter

Before running or approving any rm, especially rm -rf, check three things: what path it names, where you are (pwd), and whether there's a stray space. rm -rf ./build deletes a build folder; rm -rf . /build (one extra space) would delete the current folder's contents. Never run rm -rf on /, ~ or a path you didn't type yourself. If a command uses a pattern such as rm *.log, run ls *.log first to see exactly what it matches (patterns are covered in Chapter 55). When Claude Code asks permission for an rm, apply the same three checks (Chapter 78).

A safer delete on recent Macs

macOS 15 and later include a trash command (its manual page says it "first appeared in macOS 15.0"). trash notes.txt moves the file to the Trash, where you can still recover it. On many Linux desktops, gio trash notes.txt does the same. On Windows PowerShell, Remove-Item (alias rm) deletes permanently, like rm.

In everyday life

Deleting in Finder is putting paper in the recycling bin by your desk: you can fish it out until it's emptied. rm is feeding it through a shredder. Both are useful, but you check what's in your hand before you shred.

54.7Reading files: cat, less, head and tail

The practice log used below has 40 lines, written in a common log format: date, time, level (INFO, WARN, ERROR) and message. The content is illustrative, generated for this lab; the commands and output are real.

cat: print the whole file

Terminal
cat notes.txt
Login test passed
cat -n notes.txt          # -n: number the lines
     1	Login test passed

cat (from "concatenate", because given several files it prints them one after another) is perfect for short files. For a 50,000-line log it floods your screen; use less, head or tail instead. cat on a folder gives cat: reports: Is a directory.

head and tail: the beginning and the end

Terminal
head -n 3 logs/app.log         # first 3 lines (default is 10)
2026-11-09 10:00:00 INFO  GET /api/orders 200 in 195ms
2026-11-09 10:00:17 INFO  GET /api/orders 200 in 285ms
2026-11-09 10:00:34 INFO  GET /api/orders 200 in 74ms
tail -n 3 logs/app.log         # last 3 lines (default is 10)
2026-11-09 10:10:29 INFO  GET /api/orders 200 in 267ms
2026-11-09 10:10:46 INFO  GET /api/orders 200 in 168ms
2026-11-09 10:11:03 INFO  GET /api/orders 200 in 209ms

-n 3 is an option with a value: "n lines = 3". Without it you get 10 lines. The newest entries in a log are at the end, which makes tail the tester's favourite.

tail -f: watch a log live

Terminal
tail -f logs/app.log           # -f: follow; keep printing new lines as they arrive

-f ("follow") prints the last lines and then waits, showing every new line the application writes. Run a test in another window and watch the server react in real time. It never finishes on its own: press Ctrl+C to stop watching (the log itself is unaffected).

Real-world example

A checkout test fails intermittently. The tester opens two terminal tabs: one runs tail -f on the test environment's server log, the other runs the failing test. At the moment of failure the log shows POST /api/checkout 500 Internal Server Error. They copy the surrounding lines with timestamps straight into the Jira bug, which turns "sometimes fails" into an actionable report for the developer.

less: read a long file page by page

less logs/app.log opens the file in a full-screen viewer. Nothing is printed into your terminal history and the file can't be changed from here. The keys:

KeyAction
Space / bNext page / back a page
↓ / ↑One line down / up
g / GJump to the start / end
/ERROR then EnterSearch forward for "ERROR"; n for the next match, N for the previous
qQuit and return to your prompt

The same keys work inside man pages (54.10), because man uses less to display them. If you're ever "stuck" in a screen of text with a : at the bottom, press q.

Windows PowerShell

cat is an alias for Get-Content. For the first or last lines: Get-Content logs\app.log -TotalCount 3 and Get-Content logs\app.log -Tail 3; add -Wait to follow like tail -f. In WSL or Git Bash, the Unix commands above work as shown.

54.8Opening and editing: open and nano

open (macOS)

open does from the terminal what double-clicking does in Finder.

Terminal (macOS)
open .                              # open the current folder in Finder
open notes.txt                      # open with the default app (often TextEdit)
open -a "Visual Studio Code" .      # -a: choose the application
open https://playwright.dev         # open a web address in your browser

On Linux the equivalent is usually xdg-open (for example xdg-open .). On Windows, start . (Command Prompt) or Invoke-Item . / explorer . (PowerShell) opens the folder in File Explorer; in WSL, explorer.exe . does the same.

nano: a simple editor inside the terminal

Sometimes you need to change a file without leaving the terminal, for example on a remote server or when a guide says "edit ~/.zshrc". nano is the friendliest terminal editor:

Terminal

The file opens full-screen. Type normally and move with the arrow keys; the mouse mostly won't work. The bottom two lines list the shortcuts, where ^ means the Control key:

On a Mac, nano is actually pico

On the Mac used for this chapter (macOS 26), /usr/bin/nano is a shortcut to pico, an older editor nano was modelled on; its title bar says UW PICO 5.09. The keys above work the same. Linux distributions ship GNU nano with the same basic keys. 54.9Tidying and remembering: clear and history

clear wipes the screen so you can start fresh. It doesn't undo anything or delete history; scroll up and the old output may still be there. Ctrl+L does the same; on macOS Terminal, Cmd+K also clears the scrollback.

history lists the commands you've typed, numbered. Real output from a short zsh session:

Terminal (zsh)
history
    1  pwd
    2  ls
    3  cat notes.txt
    4  head -n 3 logs/app.log
  • In zsh, plain history shows only the most recent 16 commands; history 1 shows everything from command 1. In bash, history shows the whole list.
  • !4 reruns command number 4. ↑ walks back one at a time.
  • Ctrl+R then a few letters searches your history: type Ctrl+R, then tail, and the last tail command appears; press Enter to run it or Ctrl+C to cancel. This is the biggest time-saver in the chapter.
History is saved to disk

Your history is written to a file in your home folder (for zsh on a Mac, usually ~/.zsh_history). If you ever type a password or API key directly into a command, it's now stored there in plain text. Put secrets in environment variables or a secrets manager instead (Chapter 98), and never paste your history into a chat or ticket without reading it.

In PowerShell, Get-History (alias history) lists the current session, clear is an alias for Clear-Host, and Ctrl+R also searches.

Real-world example

You can also ask Claude to explain an unfamiliar command, and then confirm the key parts in man: the manual on your own machine describes the version you actually have.

Common misunderstandings
"rm sends files to the Bin."
It deletes permanently. Use -i, use trash on recent Macs, and keep work in Git or backed-up folders.
"cp and mv warn me before overwriting."
By default they replace the destination silently. Add -i to be asked.
"clear undoes what I did."
It only tidies the screen. Files you changed stay changed.
"If --help fails, the command is broken."
Many macOS commands simply don't support long options. Read the usage: line they print, or use man.
"I need to memorise every option."
Nobody does. Learn the pattern (command, options, arguments) and look up the rest in man, --help or by asking Claude, then verify.

54.12Review

Key takeaways
  • Every command is name, options, arguments. Short options combine (-la); some take values (-n 5); brackets in help mean optional.
  • pwd, ls and cd tell you where you are, what's there and let you move. ls -l shows type, permissions, owner, size, date and name.
  • mkdir -p, touch, cp (-r for folders), mv (move and rename) organise files; source comes first, destination last.
  • rm is permanent. Use -i, check pwd and the path, preview patterns with ls, and treat rm -rf with great care.
  • cat for short files, head/tail for ends, tail -f for live logs, less for long files (q to quit).
  • man and --help teach you any command; on a Mac many basic commands only support man and a usage line.
Check yourself

In head -n 20 logs/app.log, what is 20?

-n takes a value straight after it. logs/app.log is the argument.

You run cp reports archive and get "reports is a directory (not copied)". What do you add?

Copying a folder and its contents needs the recursive option.

Which command renames draft.md to test-plan.md?

Renaming is moving to a new name. cp would leave the original behind.

Claude Code asks to run rm -rf test-results. Which statement is true?

-r is recursive and -f suppresses questions. Check the path and your working directory before approving.

You want to watch a server log while a test runs. Which command?

tail -f keeps printing new lines as they're written; stop it with Ctrl+C.

Teach it

"Every terminal command has the same shape: the command, then options with dashes that change how it works, then what to work on. pwd says where you are, ls lists what's there, cd moves you. mkdir makes folders, cp copies, mv moves or renames, and rm deletes for good, so add -i and read it twice. cat prints a file, head and tail show the start and end, tail -f follows a live log, and less pages through big files; q gets you out. When you don't know an option, man shows the manual."
