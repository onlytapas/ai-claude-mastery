A tester's day touches many systems: the code in GitHub, the test pipeline, the database behind the app, the error tracker, the issue tracker, the design files. Each one can be connected to Claude through its own MCP server. Once connected, you can ask one question, such as "why did last night's checkout tests fail, and is it the same bug as last week?", and Claude can gather the answer from all of them. The skill is to connect only what you need, with the smallest permissions that work, and to pick servers you can trust.

103.1The QA tool chain, connected

Think about where the evidence lives when a test fails:

GitHubWhat changed in the code, and the CI run that failed
DatabaseWhether the app saved the right data
Error trackerWhether production users hit the same error
Issue trackerWhether this bug is already reported
ClaudePulls it together into one answer, with links

Without MCP you'd open five browser tabs and copy text between them. With an MCP server for each system, Claude can look things up itself, inside the same conversation. Chapter 101 covered Jira and Confluence and Chapter 102 covered Playwright. This chapter covers the rest of a typical QA toolbox.

In everyday life

Imagine a detective who can phone the bank, the phone company and the CCTV office directly, instead of waiting for someone to bring printouts. Each MCP server is one of those phone lines. The detective still decides what to ask, and every call is logged, but the investigation is much faster.

103.2GitHub's official MCP server

GitHub publishes its own MCP server, maintained by GitHub itself at github/github-mcp-server. (An older GitHub server in the MCP reference collection has been archived; use the official one.) It comes in two forms:

FormHow it runsAddress or commandBest for
RemoteGitHub hosts it; Claude connects over the internet (HTTP)https://api.githubcopilot.com/mcp/Most people: nothing to install
LocalRuns on your computer in Docker or as a downloaded programghcr.io/github/github-mcp-server (Docker image)GitHub Enterprise Server, or teams that want everything on their own machines

Toolsets: switch on only what you need

The server has a lot of tools, grouped into toolsets. If you don't choose, you get the default set: context, repos, issues, pull_requests and users. Other toolsets include actions (CI workflows and their logs), code_security, dependabot, labels, notifications and projects.

Fewer tools is better for two reasons. Claude picks the right tool more reliably from a short list, and every tool description takes up space in Claude's context window.

Read-only mode

For a tester, read access is usually all you need: read the pull request, read the CI log, read the issue. GitHub offers a read-only switch that removes every tool able to change something. On the remote server you add /readonly to the end of the address (for example https://api.githubcopilot.com/mcp/readonly) or send the header X-MCP-Readonly: true. On the local server you use the --read-only flag or GITHUB_READ_ONLY=1.

Two layers of protection

Read-only mode limits which tools the server offers. Your personal access token limits what GitHub allows. Use both: a read-only server and a token that only has read permissions on the repositories you test. If one layer is misconfigured, the other still protects you.

103.3Connecting GitHub in Claude Code, step by step

The method GitHub documents for Claude Code is the remote server plus a personal access token (PAT). OAuth sign-in support varies between AI tools, and GitHub notes that each tool has to register its own app for it, so the token route is the one that works everywhere.

Step 1: create a fine-grained token

  1. On GitHub, open Settings → Developer settings → Personal access tokens → Fine-grained tokens, then Generate new token.
  2. Give it a clear name ("Claude Code – read-only QA") and a short expiry, such as 30 or 90 days.
  3. Under Repository access, choose Only select repositories and pick the ones you test.
  4. Under permissions, grant read-only access to what you need: typically Contents, Pull requests, Issues and Actions. Leave everything else as "No access".
  5. Copy the token. GitHub shows it only once.

Step 2: keep the token out of your files

Store it in an environment variable rather than typing it into a command that lands in your shell history or a shared file (Chapter 98 explains why).

In your terminal (macOS or Linux)
read -s GITHUB_PAT        # paste the token, press Enter; nothing is shown on screen
export GITHUB_PAT          # make it available to programs started from this terminal
  • read -s GITHUB_PAT waits for you to type or paste a value and stores it in a variable called GITHUB_PAT. The -s means "silent": the token isn't shown or saved in your history.
  • export makes the variable visible to the next command.

Step 3: add the server

Run in your terminal, not inside a Claude session
claude mcp add --transport http github \
  https://api.githubcopilot.com/mcp/readonly \
  --header "Authorization: Bearer $GITHUB_PAT"
PartMeaning
claude mcp addAdd an MCP server to Claude Code
--transport httpIt's a remote server reached over the web
githubThe name you'll see in /mcp; tools will be called mcp__github__…
…/mcp/readonlyThe read-only version of the default toolsets
--header "Authorization: Bearer $GITHUB_PAT"Sends your token with every request. The shell replaces $GITHUB_PAT with the real value. See Chapter 98 for what "Bearer" means.

The default scope is local: just you, just this project. Add --scope user to use it in every project.

Where the token ends up

Claude Code saves this configuration, including the header value, in its own settings file on your computer (~/.claude.json). That's fine for a personal, local-scope server. Never put a real token into a shared .mcp.json file that gets committed to git. For shared setups, the file can refer to an environment variable instead, such as "Authorization": "Bearer ${GITHUB_PAT}", so each person supplies their own.

Step 4: check it

claude mcp list          # lists every server and whether it connects
claude mcp get github    # details and health of this one server

Inside a session, /mcp shows the same information and lets you browse the tools.

Choosing toolsets on the remote server

Each toolset also has its own address: https://api.githubcopilot.com/mcp/x/actions gives just the Actions tools, and …/mcp/x/actions/readonly gives just the read-only ones. To mix several, send the X-MCP-Toolsets header with a comma-separated list. claude mcp add accepts --header more than once:

claude mcp add --transport http github https://api.githubcopilot.com/mcp/ \
  --header "Authorization: Bearer $GITHUB_PAT" \
  --header "X-MCP-Toolsets: repos,pull_requests,actions" \
  --header "X-MCP-Readonly: true"

GitHub notes that unknown toolset names in this header are silently ignored, so if a tool you expect is missing, check the spelling. X-MCP-Tools lists individual tools instead; an unknown tool name there stops the server from starting. Read-only mode always wins: write tools are left out even if you ask for them by name.

Real-world example

A tester starts the day with: "Summarise every failed workflow run on main since yesterday 6 pm. For each, give the failing test, the first error line and the PR that was merged just before it." Claude lists the runs, reads each failed job's log, matches them to recent merges, and produces a short table with links. The tester checks two of them by hand, then files bugs for the real failures. Twenty minutes of tab-switching becomes two.

GitHub server or the gh command?

If the gh command-line tool is installed and signed in, Claude Code can often do the same things by running gh commands in the terminal, with no MCP server at all. The MCP server is most useful in places with no terminal (claude.ai, Claude Desktop), when you want strict read-only toolsets, or when your team has standardised on it. Both are fine; don't set up both and forget one.

103.5Databases: checking test data safely

Testers query databases all the time. Did the order save with the right total? Which test accounts are locked? How many rows did the migration change? Letting Claude run those queries saves time, but a database is where mistakes become expensive. A single wrong DELETE can wipe test data that took a week to build.

Which server?

The first-generation PostgreSQL and SQLite servers in the official MCP reference collection are now archived, meaning no longer maintained. Don't use them. Two maintained options:

ServerMaintained byDatabasesNotes
DBHub (@bytebase/dbhub)BytebasePostgreSQL, MySQL, MariaDB, SQL Server, Oracle, SQLiteUsed as the example in Anthropic's Claude Code MCP documentation. Two tools by default (execute_sql, search_objects), so it uses little context. Supports read-only mode and row limits.
MCP Toolbox for DatabasesGoogle (open source)Many, including PostgreSQL, MySQL and cloud databasesReady-made tools plus a framework for defining your own safe, structured queries.

The golden rules

  1. Use a test or staging database, not production, unless your organisation has explicitly approved read-only production access.
  2. Connect with a read-only database user. Ask your database administrator for one. This is the strongest protection, because the database itself refuses changes, whatever the AI tries.
  3. Turn on the server's read-only mode and row limits as a second layer.
  4. Watch out for personal data. Anything a query returns is sent to the model. Prefer anonymised test data.
In everyday life

A read-only database user is like giving a visitor a museum ticket instead of the curator's keys. They can look at everything on display, but they can't move, take or break anything, however persuasive they are at the front desk.

Connecting DBHub

From Anthropic's Claude Code documentation
claude mcp add --transport stdio db -- npx -y @bytebase/dbhub \
  --dsn "postgresql://readonly:pass@staging.db.example.com:5432/shop"
  • --transport stdio: DBHub runs as a small program on your computer, started by Claude Code (Chapter 99 explains stdio).
  • db: the name for this server.
  • --: everything after this is the command that starts the server.
  • npx -y @bytebase/dbhub: download (if needed) and run DBHub. npx comes with Node.js (Chapter 58); -y skips the "install this package?" question.
  • --dsn "postgresql://readonly:pass@…/shop": the connection string: database type, user name, password, address, port and database name. Here the user is called readonly.
The password is in the command

The connection string contains a password, and Claude Code stores the command in its config file. Use a password that belongs to the read-only test user only, and never commit it to a shared file. For team setups, put the connection details in DBHub's own configuration file and keep that file out of git.

DBHub's read-only mode and row limits

DBHub's guardrails are set in a TOML configuration file (TOML is a simple settings-file format). Read-only mode makes DBHub check each statement against an allow-list of read-only commands such as SELECT and SHOW, and also uses the database's own read-only mode. max_rows caps how many rows a SELECT returns.

dbhub.toml (keep this file out of git if it contains a password)
[[sources]]
id = "staging"
dsn = "postgres://readonly:pass@staging.db.example.com:5432/shop"

[[tools]]
name = "execute_sql"
source = "staging"
readonly = true
max_rows = 200

Start DBHub with --config dbhub.toml instead of --dsn. When a result is cut off at the limit, DBHub marks it "truncated": true, so Claude can tell a capped result from a table that really has exactly 200 rows.

Already connected in claude.ai?

Connectors you've set up in claude.ai (for example Slack or Atlassian) can also appear in Claude Code when you're signed in with the same account. Chapter 100 explains how. Check /mcp before adding a second copy of the same service.

103.7How to judge any MCP server

Thousands of MCP servers exist, and anyone can publish one. The official MCP Registry (registry.modelcontextprotocol.io) lists published servers, but being listed is not the same as being safe. Before you connect a server, ask these questions:

QuestionGood signWarning sign
Who publishes it?The company behind the service (GitHub, Sentry, Atlassian), or a well-known organisationAn unknown individual, or a name that imitates a real company
Is it maintained?Recent releases, open issues being answeredNo updates for a year, or marked archived
What access does it ask for?Only what its job needs; read-only optionsFull account access for a read-only job
Can you see the code?Open source, or a clear security pageA closed program with no information
Where does your data go?Documented; runs locally or on the vendor's own serviceSends data to a third party you've never heard of
Does your company allow it?On your organisation's approved listNot reviewed by security
Why it matters

A local MCP server is a program running on your computer with your permissions. A remote one sees whatever data you send it. Treat installing an MCP server like installing a browser extension that can read your work accounts. Chapter 105 covers the security side in depth.

103.8Keeping it lean

Every connected server costs something, even when idle: its tool names (and sometimes descriptions) use context, and each one is another thing that can break. Claude Code reduces the context cost with tool search, which is on by default: at the start of a session only tool names and server instructions are loaded, and full definitions are fetched when needed. Good habits still help:

  • Connect servers at local scope for the project that needs them, not user scope for everything.
  • Use toolsets and read-only modes to trim what a server offers.
  • Remove servers you no longer use: claude mcp remove <name>.
  • Ask for targeted results ("the first error in the failed job"), not whole logs. Claude Code warns when one tool result exceeds 10,000 tokens and, by default, limits a result to 25,000 tokens (the MAX_MCP_OUTPUT_TOKENS environment variable changes that limit).

Common misunderstandings
"Read-only mode on the server is enough."
It's one layer. Also use a token or database user that can only read. Then even a misconfigured server can't change anything.
"Any server in the registry is safe."
The registry lists servers; it doesn't vouch for them. Check who publishes and maintains each one.
"The old reference Postgres server is the standard choice."
It's archived. Use a maintained server such as DBHub or MCP Toolbox for Databases.
"More servers make Claude smarter."
More servers make Claude's choices harder and use context. Connect what the task needs.
"It's fine to paste my token into the command."
It ends up in your shell history and possibly in shared files. Use an environment variable, and short-lived, narrowly scoped tokens.

103.9Review

Key takeaways
  • Use GitHub's official server (github/github-mcp-server): remote at https://api.githubcopilot.com/mcp/, or local in Docker.
  • Limit it with toolsets and read-only mode (/readonly, X-MCP-Readonly or --read-only), and use a fine-grained, read-only, short-lived token.
  • For databases, use a maintained server (DBHub, MCP Toolbox), a test database and a read-only database user. The old reference servers are archived.
  • Official servers exist for Sentry, Linear, BrowserStack, Slack, Figma and more; remote ones usually sign in with OAuth.
  • Judge every server by publisher, maintenance, permissions, code visibility, data flow and company approval.
  • Keep connections lean: local scope, trimmed toolsets, targeted questions.
Check yourself

How do you make GitHub's remote MCP server offer only read tools?

Read-only mode removes write tools. Pair it with a read-only token.

Which toolset do you need for Claude to read CI job logs?

The actions toolset covers GitHub Actions workflows, runs, jobs and logs. It isn't in the default set.

What is the strongest protection against Claude changing data in a database?

The database itself refuses changes, whatever any tool or prompt tries.

The reference PostgreSQL MCP server in the official servers repository is…

Use a maintained alternative such as DBHub or MCP Toolbox for Databases.

A server in the MCP Registry asks for full admin access to your company's GitHub organisation just to read issues. What should you do?

Being listed isn't an endorsement. Over-broad permissions are a major warning sign.

Assignment

Map your own QA tool chain. List every system you check when a test fails (code, CI, database, error tracker, issue tracker, chat, design). For each, find out whether an official MCP server exists, how it signs in, and whether it has a read-only option. Pick the two that would save you the most time, write down the exact claude mcp add commands with least-privilege credentials, and get your security team's approval before connecting them.

Teach it

"Each tool we use, such as GitHub, the database or Sentry, can have its own MCP server, so Claude can gather evidence from all of them in one conversation. GitHub's official server can run read-only with just the toolsets we need, and we pair that with a read-only token. For databases we use a maintained server, a test database and a read-only user. Before connecting any server, we check who publishes it, what access it wants and whether our company allows it."
