60.3Sending data: query parameters and JSON bodies

Two ways to send information, matching the parts of a request from Chapter 85:

  • Query parameters (the ?key=value part of the URL): pass a dictionary as params=. The library handles encoding spaces and special characters. requests.get(url, params={"userId": 1, "completed": "false"}, timeout=10).
  • A JSON body (for POST, PUT and PATCH): pass a dictionary as json=. The library converts it to JSON text and sets Content-Type: application/json for you.

60.5Errors and timeouts

Things go wrong in two different ways, and your code must handle both:

The server answered, with an error

You get a response with a 4xx or 5xx status. raise_for_status() turns it into requests.HTTPError (httpx: httpx.HTTPStatusError). The body often explains what was wrong: read response.text.

No usable answer at all

DNS failure, connection refused, TLS problems, or no reply in time. These raise exceptions directly: requests.ConnectionError and requests.Timeout (httpx: subclasses of httpx.TransportError, such as ConnectError and ReadTimeout).

A timeout is how long you're willing to wait. With requests, always pass timeout=: its default is to wait indefinitely, so one hung server can freeze a CI job until the job's own limit kills it, with no useful error. A single number applies to connecting and to each wait for data. For AI calls, which can legitimately take a minute or more for long answers, set a generous read timeout rather than none.

SituationRetry?Why
Connection error, timeoutYes, a few timesOften a brief network or server blip
429 Too Many RequestsYes, after waiting (respect Retry-After)You hit a rate limit; it resets
500, 502, 503, 504Yes, with backoffServer-side or gateway problems, often temporary. (The Claude API also uses 529 for "overloaded".)
400, 401, 403, 404, 422NoYour request is wrong or unauthorised; sending it again gives the same answer

60.6Retries with exponential backoff

If a server is struggling, retrying instantly makes things worse. Exponential backoff means waiting longer after each failure: 0.5 seconds, then 1, then 2, then 4. Adding a little random jitter stops a crowd of clients from retrying in lockstep. If the server sends a Retry-After header, use its number instead. And stop after a few attempts: an endless retry loop is just a slower hang.

In everyday life

You ring a busy GP surgery at 8 a.m. and get the engaged tone. Redialling every second just keeps the line jammed for everyone. Sensible people wait a minute, then two, then five. If the recorded message says "call back after 10 o'clock", you do exactly that. And after a few tries you stop and book online instead.

retry_demo.py
# retry_demo.py - timeouts, error handling and retries with exponential backoff
import random
import time

import requests

RETRY_STATUSES = {429, 500, 502, 503, 504}


def get_with_retry(url, max_attempts=4, base_delay=0.5, timeout=5):
    """GET a URL, retrying network errors and retryable status codes."""
    for attempt in range(1, max_attempts + 1):
        # Exponential backoff: 0.5s, 1s, 2s, 4s... plus a little random "jitter"
        wait = base_delay * 2 ** (attempt - 1) + random.uniform(0, 0.1)
        try:
            response = requests.get(url, timeout=timeout)
        except (requests.ConnectionError, requests.Timeout) as err:
            reason = type(err).__name__
        else:
            if response.status_code not in RETRY_STATUSES:
                response.raise_for_status()   # 4xx such as 404 or 401: retrying won't help
                return response
            reason = f"HTTP {response.status_code}"
            retry_after = response.headers.get("Retry-After", "")
            if retry_after.isdigit():         # the server told us how long to wait
                wait = float(retry_after)

        if attempt == max_attempts:
            raise RuntimeError(f"Gave up on {url} after {attempt} attempts ({reason})")
        print(f"  attempt {attempt} failed ({reason}); waiting {wait:.1f}s")
        time.sleep(wait)


if __name__ == "__main__":
    print("1. A healthy endpoint")
    r = get_with_retry("https://httpbin.org/status/200")
    print("  ->", r.status_code)

    print("2. An endpoint that always returns 503")
    try:
        get_with_retry("https://httpbin.org/status/503", max_attempts=3)
    except RuntimeError as err:
        print("  ->", err)

    print("3. A slow endpoint with a 1-second timeout")
    try:
        get_with_retry("https://httpbin.org/delay/3", max_attempts=2, timeout=1)
    except RuntimeError as err:
        print("  ->", err)

    print("4. A 404, which is not retried")
    try:
        get_with_retry("https://httpbin.org/status/404")
    except requests.HTTPError as err:
        print("  ->", err)
Expected output (takes about 10 seconds; wait times vary slightly because of jitter)
1. A healthy endpoint
  -> 200
2. An endpoint that always returns 503
  attempt 1 failed (HTTP 503); waiting 0.5s
  attempt 2 failed (HTTP 503); waiting 1.0s
  -> Gave up on https://httpbin.org/status/503 after 3 attempts (HTTP 503)
3. A slow endpoint with a 1-second timeout
  attempt 1 failed (ReadTimeout); waiting 0.5s
  -> Gave up on https://httpbin.org/delay/3 after 2 attempts (ReadTimeout)
4. A 404, which is not retried
  -> 404 Client Error: Not Found for url: https://httpbin.org/status/404

The try / except / else shape is worth learning: except handles "no answer", else runs only when an answer arrived, and there we decide whether the status is worth retrying. A 404 goes straight to raise_for_status() and fails on the first attempt, as it should.

Under the hood: retries, idempotency and library helpers

Retrying is only safe when sending a request twice has the same effect as sending it once. That property is called idempotency. GET, PUT and DELETE are meant to be idempotent; POST usually isn't. If a "create order" POST times out, the server may have created the order before the reply was lost, and a blind retry creates a second one. Well-designed APIs accept an idempotency key header so retries are safe; otherwise, check whether the first attempt succeeded before retrying a POST. Retrying an AI request is generally safe in this sense (nothing is created), but each retry may cost tokens.

You don't always have to write retries by hand. requests can use urllib3's Retry class through an HTTPAdapter; httpx transports accept a retries setting for connection failures only; and the Anthropic SDKs retry certain errors twice by default, configurable with max_retries (Chapter 86). Writing it once yourself, as here, is how you learn what those settings mean.

60.7Pagination: getting every page

APIs rarely return thousands of records at once. They split long lists into pages, and the client asks for one page at a time. This is pagination. You'll meet three styles:

StyleLooks likeHow you know you're done

Cursor and link styles are the most robust, because records added while you're paging don't shift everything along. JSONPlaceholder supports _page and _limit and sends a standard Link header, which requests parses for you into response.links:

paginate.py
# paginate.py - follow "next" links until there are no more pages
import requests

url = "https://jsonplaceholder.typicode.com/todos?_page=1&_limit=50"
all_todos = []
pages = 0

while url:
    response = requests.get(url, timeout=10)
    response.raise_for_status()
    all_todos.extend(response.json())
    pages += 1
    url = response.links.get("next", {}).get("url")   # None on the last page

print(f"Fetched {len(all_todos)} todos in {pages} pages")
print("Server says total is", response.headers.get("X-Total-Count"))
Expected output
Fetched 200 todos in 4 pages
Server says total is 200
Always add a brake

A buggy API that always returns a "next" link would keep a while url: loop running forever. In production code, add a maximum page count and stop with an error if you reach it. A tester's instinct helps here: ask what happens if the server misbehaves.

60.8Async: many slow calls at once

A normal (synchronous) script sends a request and does nothing until the answer arrives. For one call that's fine. For a hundred, the waiting adds up. AI calls make this acute: a model response can take several seconds to a minute, so evaluating 200 prompts one at a time can take an hour while your computer sits idle.

Async code lets one program start many requests and wait for all of them together. In Python you write async def for a function that can pause, and await at each point where it waits on the network. asyncio.run() starts the whole thing, and asyncio.gather() runs several tasks at the same time and returns their results in the original order.

In everyday life

Synchronous code is a waiter who takes one table's order, walks to the kitchen, waits for the food, serves it, and only then greets the next table. Async code is a normal waiter: take an order, pass it to the kitchen, take the next order while the first is cooking, and serve each dish when it's ready. The kitchen isn't faster; the waiting simply overlaps.

async_compare.py
# async_compare.py - the same 10 requests, one after another vs at the same time
import asyncio
import time

import httpx

URLS = [f"https://jsonplaceholder.typicode.com/posts/{n}" for n in range(1, 11)]


def fetch_all_sync():
    with httpx.Client(timeout=10) as client:
        return [client.get(url).json() for url in URLS]


async def fetch_one(client, limit, url):
    async with limit:                       # at most 5 requests in flight at once
        response = await client.get(url)
        response.raise_for_status()
        return response.json()


async def fetch_all_async():
    limit = asyncio.Semaphore(5)
    async with httpx.AsyncClient(timeout=10) as client:
        tasks = [fetch_one(client, limit, url) for url in URLS]
        return await asyncio.gather(*tasks)   # results come back in the same order


start = time.perf_counter()
posts = fetch_all_sync()
print(f"sync : {len(posts)} posts in {time.perf_counter() - start:.2f}s")

start = time.perf_counter()
posts = asyncio.run(fetch_all_async())
print(f"async: {len(posts)} posts in {time.perf_counter() - start:.2f}s")
print("First title:", posts[0]["title"][:40])
Example output (your timings will differ)
sync : 10 posts in 2.17s
async: 10 posts in 3.10s
First title: sunt aut facere repellat provident occae

Same ten requests, roughly three times faster, because the waits overlap. The Semaphore(5) is the important line for AI work: it caps how many requests are in flight at once. Without a cap, 500 concurrent calls will hit the provider's rate limit and come back as 429s. Size the cap to your rate limit (Chapter 90), and keep retries with backoff for the 429s you still get.

Async in the Claude SDK

Anthropic's Python SDK offers an async client, AsyncAnthropic, used with await client.messages.create(...) in exactly this pattern. For large offline jobs where you don't need answers immediately, the Message Batches API is often cheaper than many concurrent calls (Chapter 90).

Under the hood: what the event loop actually does

Async Python isn't multi-threaded. A single event loop runs one piece of code at a time. When a task reaches await on a network read, it hands control back to the loop, which runs another task that's ready. When data arrives on the first task's connection, the loop resumes it. This makes async ideal for I/O-bound work (waiting on networks, disks or APIs) and useless for CPU-bound work (heavy calculation), which never pauses to let others run. Two practical consequences: calling a blocking function such as time.sleep() or requests.get() inside async code freezes every task (use await asyncio.sleep() and httpx's AsyncClient), and a forgotten await gives you a "coroutine" object instead of a result, with a RuntimeWarning: coroutine … was never awaited.

Copy-pasting retry loops into every script doesn't scale. The professional move is a small client class that wraps all the habits above once: base URL and token from environment variables, timeouts, retries with backoff, error handling and pagination. Your scripts then contain only the business logic. The project has three files: the client, a report script that uses it, and offline tests.

api_client.py
"""api_client.py - a small, reusable client for a JSON REST API.

Configuration comes from environment variables, never from the code:
  API_BASE_URL  (default: https://jsonplaceholder.typicode.com)
  API_TOKEN     (optional; sent as "Authorization: Bearer ..." when set)
"""
import os
import random
import time

import httpx

RETRY_STATUSES = {429, 500, 502, 503, 504}


class ApiError(Exception):
    """Raised when the API cannot give us a usable answer."""


class ApiClient:
    def __init__(self, base_url=None, token=None, timeout=10.0, max_attempts=4,
                 base_delay=0.5, transport=None):
        base_url = base_url or os.environ.get("API_BASE_URL", "https://jsonplaceholder.typicode.com")
        token = token or os.environ.get("API_TOKEN")
        headers = {"Accept": "application/json", "User-Agent": "qa-api-client/1.0"}
        if token:
            headers["Authorization"] = f"Bearer {token}"
        self.max_attempts = max_attempts
        self.base_delay = base_delay
        # transport lets tests swap the network for a fake (see test_api_client.py)
        self.http = httpx.Client(base_url=base_url, headers=headers,
                                 timeout=timeout, transport=transport)

    def close(self):
        self.http.close()

    def __enter__(self):
        return self

    def __exit__(self, *exc):
        self.close()

    def request(self, method, path, **kwargs):
        """Send one request, retrying network errors and 429/5xx with backoff."""
        for attempt in range(1, self.max_attempts + 1):
            wait = self.base_delay * 2 ** (attempt - 1) + random.uniform(0, 0.1)
            try:
                response = self.http.request(method, path, **kwargs)
            except httpx.TransportError as err:          # DNS, refused, timeouts
                reason = f"{type(err).__name__}"
            else:
                if response.status_code not in RETRY_STATUSES:
                    if response.is_error:
                        raise ApiError(f"{method} {path} -> {response.status_code}: {response.text[:200]}")
                    return response
                reason = f"HTTP {response.status_code}"
                retry_after = response.headers.get("Retry-After", "")
                if retry_after.isdigit():
                    wait = float(retry_after)
            if attempt == self.max_attempts:
                raise ApiError(f"{method} {path} failed after {attempt} attempts ({reason})")
            time.sleep(wait)

    def get_json(self, path, **params):
        return self.request("GET", path, params=params).json()

    def get_all(self, path, page_size=50):
        """Collect every item from a paged list endpoint (json-server style _page/_limit)."""
        items, page = [], 1
        while True:
            response = self.request("GET", path, params={"_page": page, "_limit": page_size})
            batch = response.json()
            items.extend(batch)
            if "next" not in response.links or not batch:
                return items
            page += 1

The __enter__ and __exit__ methods let you write with ApiClient() as client:, which closes connections automatically. The transport parameter exists purely for testing, as you'll see below.

todo_report.py
"""todo_report.py - use ApiClient to build a small completion report.

Run:  python todo_report.py            (report for all users)
      python todo_report.py --min 50   (flag users below 50% complete)
"""
import argparse
import json
import sys

from api_client import ApiClient, ApiError


def build_report(client, min_percent):
    users = {u["id"]: u["name"] for u in client.get_json("/users")}
    todos = client.get_all("/todos")

    rows = []
    for user_id, name in sorted(users.items()):
        mine = [t for t in todos if t["userId"] == user_id]
        done = sum(1 for t in mine if t["completed"])
        percent = round(100 * done / len(mine)) if mine else 0
        rows.append({"user": name, "done": done, "total": len(mine),
                     "percent": percent, "flag": percent < min_percent})
    return {"todos": len(todos), "users": len(users), "rows": rows}


def main():
    parser = argparse.ArgumentParser(description="Todo completion report")
    parser.add_argument("--min", type=int, default=50, help="flag users below this percent")
    args = parser.parse_args()

    try:
        with ApiClient() as client:
            report = build_report(client, args.min)
    except ApiError as err:
        print(f"API problem: {err}", file=sys.stderr)
        return 2

    print(f"{report['todos']} todos across {report['users']} users")
    for row in report["rows"]:
        marker = "  <-- below target" if row["flag"] else ""
        print(f"  {row['user']:26} {row['done']:2}/{row['total']} ({row['percent']}%){marker}")

    with open("report.json", "w", encoding="utf-8") as f:
        json.dump(report, f, indent=2)
    print("Wrote report.json")
    return 1 if any(r["flag"] for r in report["rows"]) else 0


if __name__ == "__main__":
    sys.exit(main())

Testing the client without a network

Tests that call a real public API are slow and fail when that API is down. httpx's MockTransport replaces the network with a Python function that plays the server, so you can test exactly the hard cases: a 503 followed by success, a 404, the auth header, multi-page results.

test_api_client.py
"""test_api_client.py - offline tests: a fake transport plays the server."""
import httpx
import pytest

from api_client import ApiClient, ApiError


def make_client(handler, **kwargs):
    return ApiClient(base_url="https://api.test", transport=httpx.MockTransport(handler),
                     base_delay=0, **kwargs)


def test_retries_503_then_succeeds():
    calls = []

    def handler(request):
        calls.append(request)
        if len(calls) < 3:
            return httpx.Response(503)
        return httpx.Response(200, json={"ok": True})

    with make_client(handler) as client:
        assert client.get_json("/health") == {"ok": True}
    assert len(calls) == 3


def test_404_is_not_retried():
    calls = []

    def handler(request):
        calls.append(request)
        return httpx.Response(404, json={"error": "not found"})

    with make_client(handler) as client, pytest.raises(ApiError, match="404"):
        client.get_json("/missing")
    assert len(calls) == 1


def test_token_sent_as_bearer_header():
    def handler(request):
        assert request.headers["Authorization"] == "Bearer secret-for-tests"
        return httpx.Response(200, json=[])

        assert client.get_json("/users") == []


def test_get_all_follows_pages():
    data = list(range(5))

    def handler(request):
        page = int(request.url.params["_page"])
        limit = int(request.url.params["_limit"])
        chunk = data[(page - 1) * limit: page * limit]
        headers = {}
        if page * limit < len(data):
            headers["Link"] = f'<https://api.test/items?_page={page + 1}>; rel="next"'
        return httpx.Response(200, json=chunk, headers=headers)

    with make_client(handler) as client:
        assert client.get_all("/items", page_size=2) == [0, 1, 2, 3, 4]

Troubleshooting

  • ModuleNotFoundError: No module named 'httpx': the virtual environment isn't active in this terminal. Run source .venv/bin/activate; the prompt should show (.venv).
  • ModuleNotFoundError: No module named 'api_client': run the scripts from the folder that contains api_client.py.
  • ConnectError or SSL: CERTIFICATE_VERIFY_FAILED on a company network: a proxy is intercepting traffic. Ask IT for the proxy settings and certificate bundle; httpx and requests read the HTTPS_PROXY environment variable. Never "fix" it with verify=False in real code.
  • httpbin.org is slow or returns 502/503 unexpectedly: it's a free shared service. Rerun later; for the retry demo, the behaviour you see is exactly what the code is for.
  • JSONDecodeError: the body wasn't JSON, often an HTML error page from a proxy or gateway. Print response.status_code and response.text[:200].
  • Windows PowerShell: set variables with $env:API_BASE_URL = "https://no-such-host.invalid", and read exit codes with $LASTEXITCODE.

60.10Debugging API code

When an API call misbehaves, find out what was actually sent and what actually came back, rather than what you think your code sent.

TechniqueHow
Print the real requestprint(response.request.method, response.request.url); headers via response.request.headers (mask tokens)
Print the raw bodyprint(response.status_code, response.text[:500]) before calling .json()
Turn on library loggingimport logging; logging.basicConfig(level=logging.INFO) makes httpx log every request and status; level=logging.DEBUG makes requests (through urllib3) log connections
Reproduce with curlIf curl (Chapter 85) works and Python doesn't, compare headers and body. If both fail, it's not your code
Check the environmentecho $API_BASE_URL; a missing or stale variable explains many 401s and 404s
Ask Claude wellPaste the code, the full traceback, the status code and the first lines of the response body (with secrets removed)
Real-world example

A tester's script that creates Jira test issues starts failing with KeyError: 'id'. The traceback points at response.json()["id"]. Printing the status and body shows 400 and {"errors": {"priority": "Field 'priority' cannot be set..."}}: an admin had removed the priority field from the create screen. The bug was never in the Python. A raise_for_status() call after the POST, printing the body, would have put the real error on the first line of the output. (Illustrative scenario.)

Common misunderstandings
"If the request didn't raise an error, it worked."
4xx and 5xx responses don't raise by themselves. Call raise_for_status() or check the status code.
"Timeouts are optional."
With requests, no timeout means a hung server can stall your script indefinitely. Always set one.
"Retry everything until it works."
Retry only temporary failures (network errors, 429, 5xx), with backoff and a limit. A 401 or 404 won't change on the next attempt.
"Async makes each request faster."
Each request takes as long as before. Async overlaps the waiting, so many requests finish sooner in total.
"It's fine to paste the token in for a quick test."
Quick tests get committed and shared. Use an environment variable from the start.

60.11Review

Key takeaways
  • requests is the simple classic; httpx has the same feel plus async support, a 5-second default timeout and a mock transport for tests.
  • Use params= for query strings and json= for JSON bodies; read results with .json() after checking the status.
  • Tokens come from environment variables and never appear in code or logs.
  • Always set timeouts; retry only network errors, 429 and 5xx, with exponential backoff, jitter, Retry-After and a maximum.
  • Follow pages until there's no next link or cursor, with a safety brake.
  • Async (async/await, asyncio.gather, a Semaphore) overlaps slow calls such as AI requests, within your rate limit.
  • Wrap these habits once in a client class, and test it offline with fake responses.
Check yourself

Your script calls requests.get(url) with no other arguments, and the server never replies. What happens?

Always pass timeout= to requests. httpx is different: it defaults to 5 seconds.

Which response should your code retry?

503 is usually temporary. 401 and 404 will give the same answer however many times you ask.

Where should an API token live?

Code and URLs get committed, logged and shared. Environment variables keep secrets out of both.

Why does async_compare.py use asyncio.Semaphore(5)?

Without a cap, a large batch fires every request at once and triggers 429s. gather works without it.

What lets test_api_client.py test retries without any network?

The client accepts a transport, so tests can inject a fake server that returns 503, 404 or paged data on demand.

Teach it

"Calling an API from Python is three lines; doing it properly is a handful of habits. Always set a timeout. Check the status code before trusting the body. Read tokens from environment variables, never from code. Retry only temporary failures, such as network errors, 429s and 5xx, waiting longer each time, and give up after a few tries. Follow 'next' links until there aren't any. When you have many slow calls, like AI requests, run them concurrently with async but cap how many at once. Put all of that in one small client class and test it with fake responses, so your scripts only contain the actual question you're asking."
