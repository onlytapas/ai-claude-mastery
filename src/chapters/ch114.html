Software moves through a lifecycle: someone decides what to build, it's designed, written, reviewed, tested, released and then run in production. AI can help at every stage, but the help looks different at each one: spotting gaps in a user story, comparing design options, writing code, reviewing changes, generating tests, drafting release notes and reading incident logs. The biggest gains come when a team uses AI across the whole flow, not just for typing code faster. The biggest risks come from trusting output nobody checked. Measure the whole delivery system, not lines of code.

114.1The lifecycle in one picture

The software development lifecycle (SDLC) is the path every change takes from idea to running software. Teams draw it differently (Scrum sprints, Kanban flow, continuous delivery), but the same stages appear in all of them:

PlanWhat and why: stories, acceptance criteria
DesignHow: architecture, APIs, data
CodeBuild it
ReviewCheck the change
TestProve it works
ReleaseShip it safely
OperateRun it, learn, feed back into Plan
In everyday life

Building a house has the same shape: the client brief, the architect's drawings, construction, the site inspection, the final survey, handing over the keys, then living in it and calling the plumber. A powerful new tool, such as a machine that lays bricks ten times faster, helps one stage. If the drawings are wrong or nobody inspects the work, faster bricklaying just produces the wrong house sooner.

That analogy is the main lesson of this chapter. Speeding up coding alone moves the bottleneck to review and testing. Teams that gain the most use AI at every stage, and especially on the stages that were already slow.

114.2Plan: better stories before any code exists

Problems found in a user story cost minutes to fix. The same problems found in production cost days. That makes planning the cheapest place to use AI, and it's where testers can have a big effect (shift-left testing).

Prompt: story refinement (paste the story, or fetch it with the Jira MCP server from Chapter 101)
Here is a user story for the checkout team:
<story>
As a shopper I can apply a coupon at checkout so that I pay less.
</story>
1. List every question a developer or tester would need answered before starting.
2. Propose acceptance criteria in Given/When/Then form.
3. Suggest how to split it if it's too big for one sprint.
Mark anything you're assuming rather than reading from the story.

Typical questions back: Can two coupons be combined? Do coupons expire? Are they case-sensitive? Is there a minimum spend? What happens to the discount if an item is returned? Each one is a future bug avoided.

Real-world example

A tester began running every story through a refinement prompt the day before backlog refinement, and bringing the top five questions to the meeting. The product owner first found it annoying, then started running the prompt herself before writing stories. The team agreed that the "questions found in refinement" count was a better early measure of quality than anything they'd tracked before.

114.3Design: options, trade-offs and decision records

Design is where a team decides how to build something: which components change, how data is stored, what an API looks like. AI is useful here as a fast, well-read sparring partner. It isn't the decision-maker, because it doesn't carry the consequences.

  • Generate options. "Give me three ways to store coupon usage, with pros, cons and what each makes harder to test."
  • Draft a decision record. A short document capturing the context, the options, the decision and its consequences, so future readers know why.
  • Draft contracts. An OpenAPI description of a new endpoint, which testers can review and use for contract tests before the code exists.
  • Think about failure. "What could go wrong with this design under load, with bad input, or if the payment service is down?"

In Claude Code, plan mode fits this stage: Claude reads the codebase and proposes a plan, but can't edit files until you approve it (Chapter 67). Use /plan or Shift+Tab to enter it.

Plausible is not proven

An AI design proposal can sound authoritative and still ignore a constraint it was never told about: a legacy system, a regulation, a team's skills. Feed it the constraints explicitly, and have a person who owns the system sign the decision.

114.4Code: from autocomplete to agents

AI coding help has moved through three styles, and teams now use all three:

StyleWhat it looks likeGood for
Inline suggestionsThe editor suggests the next lines as you typeSmall, local code where you already know what you want
Chat about codeYou paste code and ask questionsExplaining, small fixes, learning
Agentic codingA tool like Claude Code reads the repository, edits many files, runs commands and testsWhole tasks: a feature, a migration, a set of tests

Agentic coding shifts the developer's work towards three activities: giving clear direction (a good task description and a project CLAUDE.md, Chapter 77), keeping changes small enough to review, and checking the result. The same habits that make a human team effective, such as small pull requests, clear conventions and fast tests, make an AI-assisted team effective.

Tests are the agent's eyes

An agent can only check its own work against something. A fast, reliable test suite lets Claude Code run the tests after each change and fix what it broke. A slow or flaky suite leaves it guessing. Investment in test automation pays back twice once AI writes code.

114.5Review: the new bottleneck

When code is written faster, more code waits for review. Reviewers can't simply read faster, so teams add AI as a first pass:

ToolWhat it doesWhere it's covered
/code-review (alias /review)Reviews your current changes, a PR, branch or path for correctness bugs, at an effort level from low to max; ultra runs a deep review in the cloudChapter 71 (syntax); Chapter 115 (how to use findings)
claude ultrareviewThe same cloud multi-agent review from the shell or a scriptChapter 71

Claude GitHub ActionRuns Claude on pull requests when someone writes @claude, or on every PR with a fixed promptChapter 71

AI review is a first pass, not a replacement. It's strong at spotting bugs in the lines that changed; humans are better at asking whether the change is the right change at all. Chapter 115 covers how to review AI-written code.

114.6Test: the part this book knows best

Testing is covered throughout Part XV (Chapters 118–128): test design, automation with Playwright (Chapter 121), exploratory testing, accessibility, evals and ROI. From a lifecycle view, three points stand out:

  • Testing moves earlier. Acceptance criteria and test ideas can exist before code, because AI drafts them from the story.
  • More code means more to test. If developers deliver more changes, regression risk grows. Automated suites and risk-based selection matter more, not less.
  • Testers check the AI too. AI-written tests can assert the wrong thing. "Prove it can fail" (Chapter 121) becomes a routine step.

114.7Release: readiness, notes and automation

Release work is mostly gathering and summarising information, which suits AI well. Common uses:

  • Release notes from merged pull requests and Jira tickets, in language customers understand.
  • Release-readiness summaries: open bugs by severity, test results, known risks, untested areas. The go/no-go decision stays with people.
  • Checks in the pipeline using Claude Code non-interactively. claude -p runs one task and prints the result; with --permission-mode dontAsk, anything not pre-approved is denied rather than waiting for a person who isn't there.
Terminal: draft release notes from the git history (read-only tools only)
git log --oneline v4.1.0..HEAD > changes.txt
claude -p "Read changes.txt and draft customer-facing release notes grouped as
New, Improved and Fixed. Leave out internal refactors. Flag any change that
sounds risky for a tester to check." \
  --permission-mode dontAsk --allowedTools "Read" > release-notes-draft.md
Drafts, not decisions

Treat AI release notes and readiness summaries as drafts for a named person to check. A confident summary that omits a known critical bug is worse than no summary.

114.8Operate: logs, incidents and learning

Once software is live, the work is keeping it healthy. AI helps operations staff (often called SRE, site reliability engineering, or DevOps) to:

  • Read logs and traces quickly during an incident: "Group these errors by cause and show when each started."
  • Draft incident timelines and postmortems from chat messages and alerts (Chapter 115 covers root-cause analysis).
  • Write and update runbooks, the step-by-step guides for handling known problems.
  • Watch for change. In Claude Code, /loop re-runs a prompt on an interval while the session is open, for example /loop 5m check if the deploy finished; /schedule creates cloud scheduled tasks.

What operations learns feeds back into planning: a recurring incident becomes a story, and its postmortem becomes test cases. This loop is where QA, development and operations meet.

Production is different

Giving an AI agent write access to production systems is a high-risk decision. Start with read-only access to logs and dashboards, and apply the supervision design in Chapter 113 before allowing any action.

114.9How roles change

No role disappears in this picture, but the balance of each role's work shifts from producing to directing and checking.

RoleLess time onMore time on
DeveloperTyping routine code, looking up syntaxSpecifying tasks, reviewing AI changes, architecture, keeping changes small
Tester / QA engineerWriting boilerplate test code, test data, repetitive regressionRisk analysis, early story review, exploratory testing, checking AI output, evals
Product owner / BAFirst drafts of stories and documentsClarifying intent, acceptance criteria, saying what not to build
Operations / SRESearching logs by hand, writing first drafts of postmortemsIncident judgement, supervising agents, reliability design
Engineering managerStatus chasingSetting AI policy, measuring outcomes honestly, coaching review skills
Opinion · widely argued by engineering leaders

Many engineering leaders argue that the most valuable skill in an AI-assisted team becomes judgement: knowing what good looks like, and noticing when output is plausible but wrong. Testers have practised exactly that for years. On this view, QA experience becomes more valuable, not less. It's a view, not a measured result, and it depends on testers moving towards risk and review work (Chapter 118).

114.11Measuring whether AI is helping

The tempting measures are the wrong ones: lines of code written by AI, number of suggestions accepted, prompts per day. They measure activity, not results, and they're easy to inflate (Goodhart's law, Chapter 126). Measure the delivery system instead.

The DORA research programme (now part of Google Cloud) has studied software delivery performance for over a decade. Its current guide lists five software delivery metrics:

GroupMetricDefinition (from DORA)
ThroughputChange lead timeTime from committing a change to it being deployed to production
Deployment frequencyHow often deployments happen
Failed deployment recovery timeHow long it takes to recover from a failed deployment that needs immediate intervention
InstabilityChange fail rateShare of deployments that need immediate intervention, such as a rollback or hotfix
Deployment rework rateShare of deployments that are unplanned and result from a production incident

If AI really helps, throughput should improve without instability getting worse. Pair the DORA metrics with a few lifecycle-specific ones: review time per PR, questions found in refinement, escaped defects, and the QA measures in Chapter 126.

Research example: feelings are not measurements

In July 2025 the research group METR published a randomised study of 16 experienced open-source developers working on 246 real issues in their own large repositories. With AI tools allowed, they took 19% longer on average. Before the study they expected a 24% speed-up, and afterwards they still believed AI had sped them up by about 20%. METR has since said those results are out of date and published a follow-up study in February 2026 covering late-2025 tools. The lasting lesson isn't "AI is slow" or "AI is fast"; it's that people's impression of their own speed can be wrong in either direction, so measure.

Start with a baseline

Record your current numbers before rolling AI out across the lifecycle. Without a "before", no "after" means anything (Chapter 126).

One story through the whole lifecycle40 min · Claude Code + git + Python 3, a practice folder

Setup. Create a tiny practice project:

Terminal
mkdir lifecycle-lab && cd lifecycle-lab && git init
pricing.py
"""Basket pricing for the practice shop."""

COUPONS = {"SAVE10": 10, "SAVE25": 25}  # percent off


def basket_total(prices, coupon=None):
    """Return the basket total in pence after an optional coupon."""
    total = sum(prices)
    if coupon:
        percent = COUPONS.get(coupon.upper())
        if percent is None:
            raise ValueError(f"Unknown coupon: {coupon}")
        total = total - total * percent // 100
    return total
test_pricing.py
import unittest
from pricing import basket_total


class BasketTotalTests(unittest.TestCase):
    def test_no_coupon(self):
        self.assertEqual(basket_total([1000, 500]), 1500)

    def test_save10(self):
        self.assertEqual(basket_total([1000, 500], "SAVE10"), 1350)

    def test_unknown_coupon(self):
        with self.assertRaises(ValueError):
            basket_total([1000], "BOGUS")


if __name__ == "__main__":
    unittest.main()

Common misunderstandings
"AI in software development means AI writing code."
Coding is one stage of seven. Planning, review, testing and operations often gain as much or more.
"If developers are faster, the team is faster."
Only if review, testing and release keep up. Otherwise the queue just moves.
"Percentage of code written by AI is a good success metric."
It measures activity. Use delivery and quality measures such as the DORA metrics and escaped defects.
"We felt more productive, so it worked."
Feelings and measurements can disagree, as METR's 2025 study showed. Compare against a baseline.

114.12Review

Key takeaways
  • The lifecycle has seven stages: plan, design, code, review, test, release, operate. AI helps at each in a different way.
  • Planning is the cheapest place to use AI: find ambiguity and draft acceptance criteria before code exists.
  • Design with AI as a sparring partner; people choose and own decisions, recorded in decision records.
  • Faster coding makes review and testing the bottleneck; use /code-review, /security-review and strong automated tests.
  • Release and operations work (notes, readiness summaries, logs, postmortems) suits AI drafting with human sign-off.
  • Roles shift from producing to directing and checking; testers' judgement becomes central.
  • Measure delivery with the five DORA metrics and quality measures, against a baseline, not with AI activity counts.
Check yourself

A team doubles coding speed with AI but sees no change in delivery speed. What's the most likely reason?

Speeding up one stage only helps if the stages after it can keep up.

Which is the cheapest stage at which to catch an ambiguous requirement?

Fixing a sentence in a story costs minutes; fixing behaviour in production costs far more.

Which of these is one of DORA's software delivery metrics?

DORA measures delivery outcomes: lead time, deployment frequency, recovery time, change fail rate and rework rate.

In a CI job with nobody watching, which permission mode makes Claude Code deny anything not pre-approved?

dontAsk fails closed: actions that would need a prompt are denied. Bypass skips checks entirely.

What was the main lesson of METR's July 2025 developer study?

Developers believed they were about 20% faster while measured times were 19% longer. METR says the results are now out of date; the lesson is to measure.

Assignment

Draw your team's real lifecycle as a flow (it may have more or fewer stages than seven). For each stage, write: where AI is used today, one new use worth trying, the main risk and its control, and who owns sign-off. Then choose two DORA metrics and one QA metric, find your current values (your baseline), and agree with your manager how you'll track them for the next three months.

Teach it

"Every change goes through plan, design, code, review, test, release and operate. AI can help at each step: spotting gaps in stories, comparing designs, writing code, first-pass reviews, tests, release notes and reading logs. If you only speed up coding, the work just piles up at review and testing. So use it across the whole flow, keep people deciding at each step, and measure delivery, not how much code the AI wrote."
