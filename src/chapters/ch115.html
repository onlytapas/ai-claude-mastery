Debugging is detective work: reproduce the problem, collect evidence, form a guess about the cause, test the guess, and only then fix. Claude Code is an excellent assistant detective. It reads stack traces, logs and code fast, proposes hypotheses and runs experiments. But it is just as capable as a human of fixing a symptom and calling it solved. Root-cause analysis asks "why did this really happen, and why didn't we catch it?", and a good write-up turns one bug into lasting improvements. Code review, by people and by AI, is how you stop the next one; AI-written code needs that review as much as any other code.

115.1Debugging is a method, not a guess

Under pressure, people (and AI models) jump to a fix: "it's probably the cache, let's clear it". Sometimes that works, and nobody learns why. A method is slower for the first five minutes and much faster overall.

1. ReproduceMake it fail on demand, ideally with one command
2. ObserveCollect evidence: error, stack trace, logs, what changed
3. HypothesiseList possible causes; rank by evidence
4. ExperimentTest one hypothesis at a time
5. FixSmallest change that addresses the cause
6. VerifyReproduction now passes; add a regression test
In everyday life

A good doctor doesn't prescribe antibiotics because you said "I feel unwell". They ask questions, examine you, maybe order a test, and treat the cause. A painkiller (a symptom fix) can make you feel better while the infection continues. Software bugs are the same: a retry that hides a timeout is a painkiller.

The most valuable step is the first. A minimal reproduction, the smallest set of steps or code that still shows the bug, makes every later step easier, for you and for Claude. Testers are often the best people in the team at producing one.

115.2Debugging with Claude Code

Claude Code can do every step of the method: run the failing command, read the code, search history, add temporary logging, run experiments and propose a fix. Your job is to keep it on the method rather than letting it leap to a fix.

Not that kind of debug

Claude Code has a /debug skill and a --debug flag. They turn on debug logging for Claude Code itself, for when the tool misbehaves (an MCP server not starting, a hook not firing). They're not for debugging your application.

Real-world example

A tester reported that the order-history page showed the wrong order count for some users. Asked to investigate without fixing, Claude reproduced it with a seeded test user, then proposed three hypotheses: a timezone boundary, pagination, and cancelled orders being counted. Its experiment (create an order at 23:30 UTC) confirmed the timezone one. The developer's first instinct had been pagination. Thirty minutes of method saved a day of guessing.

Watch for "fixes" that remove the evidence

An AI under instruction to "make the test pass" may loosen the assertion, add a broad try/except, increase a timeout or skip the test. Each makes the symptom vanish and leaves the bug. Say explicitly: "Don't change tests or timeouts to make this pass; find the cause."

115.3Evidence: stack traces, logs and traces

Three kinds of evidence answer different questions:

EvidenceAnswersTips
Stack traceWhere in the code did it fail, and through which calls?Read from the line that names your own code; the top or bottom depends on the language (Python puts the failing line last)
LogsWhat was the system doing before and after?Filter by time window and request; compare with a time it worked
Distributed traceWhich service in a chain was slow or failed?Follow one request across services; find the longest or failing span

In systems with many services, a correlation ID (a request ID passed from service to service and written in every log line) lets you pull together everything that happened to one request. If your logs lack one, that's a finding for the RCA.

Summarise before you send

Pasting a 50,000-line log into a conversation wastes tokens and buries the signal (Chapter 20). Summarise first with a small script, or ask Claude to write one and run it, so it reads the summary rather than the raw file. Save this as error_summary.py:

error_summary.py
#!/usr/bin/env python3
"""Group ERROR lines in a log by error type: count, first and last time, sample request."""
import re, sys
from collections import OrderedDict

LINE = re.compile(r"^(\S+)\s+(\w+)\s+req=(\S+)\s+(\S+)\s+(\S+)\s+(.*)$")

groups = OrderedDict()
for raw in open(sys.argv[1] if len(sys.argv) > 1 else "app.log", encoding="utf-8"):
    m = LINE.match(raw.strip())
    if not m or m.group(2) != "ERROR":
        continue
    time, _, req, method, path, message = m.groups()
    error_type = message.split(":")[0]
    key = (error_type, method, path)
    g = groups.setdefault(key, {"count": 0, "first": time, "last": time, "req": req})
    g["count"] += 1
    g["last"] = time

for (error_type, method, path), g in sorted(groups.items(), key=lambda kv: -kv[1]["count"]):
    print(f"{g['count']:>3}  {error_type:<16}{method} {path}")
    print(f"     first {g['first']}  last {g['last']}  e.g. req={g['req']}")

Production logs can contain names, emails, addresses and tokens. Use approved tools only, redact before sharing, and follow your data rules (Chapter 132).

115.4Finding the guilty commit: automated bisect

Chapter 71 showed manual git bisect: git picks a commit halfway between a good and a bad one, you test it and say good or bad, and it narrows down. When a command can detect the bug, git can do all the testing itself with git bisect run:

Terminal
git bisect start HEAD v1.0               # bad commit first, then a known good one
git bisect run python3 check_shipping.py # git runs it at each step
git bisect reset                          # go back to where you started

The command's exit code tells git the answer:

Exit codeMeaning to git bisect
0This commit is good
125Can't test this commit (for example, it doesn't build): skip it
1 to 127, except 125This commit is bad
Anything else (above 127)Stop the bisect: something went wrong

A good check script is quick, tests only the bug in question, and exits 125 when it can't run. Claude is good at writing these: "Write a script that exits 0 if the SAVE25 bug is absent, 1 if present, and 125 if the project doesn't build. Then run git bisect between v4.1.0 and HEAD with it." Watch the first step or two to confirm the script really detects the bug: a script that always fails points at the wrong commit with complete confidence.

Under the hood: why bisect is so fast

Each test halves the number of suspect commits. With n commits you need about log2(n) tests: 10 for about 1,000 commits, 20 for about a million. Linear checking (one commit at a time) would need up to n. The catch is that bisect assumes the bug appeared once and stayed. If it came and went (for example, a flaky test, flaky tests being common in UI suites), bisect can blame an innocent commit. Make the check deterministic, or run it several times inside the script and fail only if it fails consistently.

115.5Root-cause analysis: past the symptom

Root-cause analysis (RCA) asks why a problem really happened, so that the fix prevents the whole class of problem rather than one instance. A useful distinction:

LevelExample (the shipping bug from the lab)
SymptomCustomers with light parcels were charged £3.00 instead of £4.50
Direct causemath.ceil was replaced with round, so 0.2 kg rounded to 0
Contributing factorsThe commit was labelled "tidy" and had no review; no test covered parcels under 0.5 kg; the business rule "per started kg" lived only in a comment
Root causes (systemic)No required review for small changes; no boundary-value tests for pricing rules; requirements not captured as tests

Five whys

The five whys technique keeps asking "why?" until you reach something you can change in the process, not just the code. Five is a rule of thumb, not a law.

Five whys (illustrative)
Why were light parcels undercharged? -> shipping_cost(0.2) returned 300.
Why?  -> round() replaced math.ceil() in a "tidy" commit.
Why wasn't it caught in review? -> Small commits could merge without review.
Why didn't tests catch it?      -> No test below 1 kg; boundaries weren't in the test design.
Why not?  -> The "per started kg" rule was never written as an acceptance criterion.

Notice the answer is rarely one thing. Real incidents usually have several contributing causes, which is why some teams prefer a causal diagram (a "fishbone" listing causes under headings such as code, tests, process, people, environment) over a single chain.

Where Claude helps, and where it doesn't

  • Helps: building a timeline from commits, tickets, chat exports and alerts; asking the next "why"; suggesting contributing factors you missed; drafting the write-up.
  • Doesn't replace: talking to the people involved, and the team's judgement about which actions are worth their cost.
Opinion · from the site reliability engineering community

Many reliability practitioners argue that "root cause" in the singular is misleading for complex systems, because incidents come from several factors combining, and that the search for one cause tends to end at "human error". They prefer the phrase "contributing factors". This chapter uses RCA because it's the common term, but the advice is the same: look for several causes, and look at the system.

115.6Writing an RCA people act on

An RCA document that nobody reads fixes nothing. Keep it short, factual and blameless: it describes what the system allowed to happen, not who to blame. People share more honestly when they won't be punished, and the honest details are where the learning is.

RCA template
Title:     Light parcels undercharged for shipping (INC-2041)
Severity:  (your scale)     Status: actions in progress
Summary:   Two or three sentences a manager can read in 20 seconds.
Impact:    Who was affected, how many, for how long, cost if known.
Timeline:  UTC times: introduced, deployed, detected, mitigated, resolved.
Detection: How we found out. How we SHOULD have found out.
Causes:    Direct cause; contributing factors (code, tests, process, tooling).
What went well: Things to keep.
Actions:   Each one: owner, due date, ticket link. Prefer prevention and
           detection over "be more careful".
           e.g. add boundary tests for all pricing rules (QA, 2 weeks, QA-881)
Evidence:  Links to commits, logs, dashboards, the bisect output.
Prompt: draft the RCA from evidence
Using the bisect output, the diff of the bad commit, the Jira ticket and
the Slack export in incident/ , draft an RCA using the template in
docs/rca-template.md. Blameless language. Mark every statement you
inferred rather than read from the evidence with [check]. Propose
actions, but don't assign owners; we'll do that in the review.

The [check] marker is the important part: it separates evidence from Claude's inference, so the review meeting checks exactly the right sentences.

115.7Using AI code review well

The best bug is the one that never merges. Chapter 71 introduced the tools and their syntax: /code-review (alias /review) with effort levels from low to max, ultra for a deep multi-agent review in the cloud, --fix and --comment; and claude ultrareview from the shell. Here the question is how to use them well.

Choosing the right review

SituationChoiceWhy
Checking your own work before committing/code-review at low or mediumFew, high-confidence findings; quick
A risky PR (payments, auth, data migration)/code-review high or ultraMore findings, including uncertain ones worth a look
A big change before release, from a script or CIclaude ultrareview <PR>Deep cloud review; prints findings unless you add --post. Free runs are limited, then it uses usage credits
Security-sensitive changes/security-reviewFocused on vulnerabilities in your branch's diff
Code works but is messy/simplifyReuse, simplification and efficiency; it doesn't hunt bugs

Triage every finding

A review finding is a hypothesis, not a verdict. Sort each one:

DecisionWhenWhat to do
AcceptYou can see the bug, or write a test that shows itWrite the failing test first, then fix
QuestionPlausible but unclearAsk Claude for a concrete input that triggers it; if it can't give one, downgrade
RejectWrong, or based on a misunderstanding of requirementsNote why; if the misunderstanding is common, add the rule to CLAUDE.md
Careful with --fix

--fix applies the findings to your working tree. That's convenient, but it can apply a wrong finding too. Use it on a clean branch, read the diff, and run the tests afterwards. For anything you'd struggle to review, prefer accepting findings one by one.

Real-world example

A high-effort review of a refund PR produced seven findings. Triage took ten minutes: two accepted (a missing currency check, and an off-by-one in a date range, each proven with a new test), three questioned (two downgraded when no failing input could be found), and two rejected because they assumed refunds could exceed the order total, which the business rules forbid. The team added that rule to CLAUDE.md, and later reviews stopped raising it.

115.8Reviewing AI-written code

AI-written code tends to look clean, well named and confident. That makes it easy to approve and sometimes hard to doubt. It fails in some characteristic ways that are worth checking deliberately:

CheckWhat to look for
Does it do what was asked, and only that?Extra "improvements" in unrelated files; scope creep hides risk
Do the APIs and packages exist?Invented functions, options or package names (hallucinations); a package name that doesn't exist could later be registered by an attacker
Were tests weakened?Loosened assertions, skipped tests, raised timeouts, deleted cases (Chapter 71, 71.3)
Are errors handled or hidden?Broad try/except or empty catch blocks that swallow failures
Edge casesEmpty input, zero, boundaries, time zones, rounding, concurrency: as in the shipping bug
SecurityString-built SQL, unescaped output, secrets in code, over-wide permissions
Fits the codebase?Duplicates an existing helper; ignores team conventions
Can you explain it?If you couldn't explain the change to a colleague, you're not ready to approve it
Same standard, different blind spots

Hold AI-written code to exactly the same standard as human code: same review, same tests, same approval. What changes is where you look hardest. People make typos and forget things; AI makes confident, plausible mistakes and over-reaches. A tester's habit of asking "how could this be wrong?" is the right instinct for both.

Setup. Save this script as make_bisect_lab.sh in an empty folder and run bash make_bisect_lab.sh. It builds a practice repository with twelve commits, one of which quietly breaks the shipping calculation.

make_bisect_lab.sh
#!/usr/bin/env bash
# Creates a practice repo with 12 commits; one of them quietly breaks rounding.
set -e
mkdir bisect-lab && cd bisect-lab
git init -q
git config user.email "lab@example.com"
git config user.name "Lab"
cat > shipping.py <<'PY'
def shipping_cost(weight_kg):
    """Return shipping cost in pence: 300 base + 150 per started kg."""
    import math
    return 300 + 150 * math.ceil(weight_kg)
PY
cat > check_shipping.py <<'PY'
from shipping import shipping_cost
assert shipping_cost(0.2) == 450, shipping_cost(0.2)
assert shipping_cost(1.0) == 450, shipping_cost(1.0)
assert shipping_cost(1.1) == 600, shipping_cost(1.1)
print("shipping OK")
PY
git add . && git commit -qm "Add shipping cost" && git tag v1.0
for i in $(seq 1 11); do
  echo "# note $i" >> NOTES.md
  if [ "$i" -eq 7 ]; then
    sed -i.bak 's/math.ceil(weight_kg)/round(weight_kg)/' shipping.py && rm shipping.py.bak
    git add . && git commit -qm "Tidy shipping calculation"
  else
    git add . && git commit -qm "Update notes $i"
  fi
done
echo "Created bisect-lab with $(git rev-list --count HEAD) commits"

Troubleshooting. mkdir: bisect-lab: File exists: delete the old folder or run the script elsewhere. Common misunderstandings
"The test passes now, so it's fixed."
Check how it passes. A loosened assertion or a longer timeout hides the bug. Verify against the original reproduction and the requirement.
"Root cause means finding who made the mistake."
It means finding what in the system allowed the mistake through. Blameless write-ups get honest details and better fixes.
"An AI review found nothing, so the code is fine."
It found nothing it was confident about. It can't judge whether the change matches intent; a human still approves.
"/debug will help me debug my app."
/debug troubleshoots Claude Code itself using its debug log. For your app, use the method in this chapter.
"Bisect can't help without a test."
Any command that exits 0 for good and non-zero for bad will do: a curl check, a grep on output, a short script Claude writes.

115.9Review

Key takeaways
  • Debug by method: reproduce, observe, hypothesise, experiment, fix, verify. A minimal reproduction is the most valuable step.
  • Give Claude evidence and say "don't change code yet"; plan mode, ! shell mode and /rewind support careful investigation.
  • Summarise large logs before sharing; use stack traces for "where", logs for "what", traces and correlation IDs for "which service".
  • git bisect run <command> finds the first bad commit automatically: exit 0 good, 125 skip, other codes up to 127 bad.
  • RCA separates symptom, direct cause, contributing factors and systemic causes; write it blameless, with owned and dated actions.
  • Triage every /code-review or ultrareview finding as accept (prove with a test), question or reject; use --fix carefully.
  • Review AI-written code to the same standard, looking hardest at scope creep, invented APIs, weakened tests, swallowed errors and edge cases.
Check yourself

Claude proposes increasing a test's timeout from 5 to 30 seconds to fix an intermittent failure. What's the best response?

Raising a timeout treats the symptom. Find the cause, then decide whether the timeout was really wrong.

During git bisect run, your check script exits with code 125. What does git do?

125 means "can't test this one", for example because it doesn't build.

Which of these is a contributing factor rather than the direct cause of the shipping bug?

The code change is the direct cause, undercharging is the symptom, and the missing test is a contributing factor that let it through.

A review finding says a function "may fail on some inputs", but Claude can't give a concrete failing input. What should you do?

Findings are hypotheses. Accept those you can demonstrate; downgrade those you can't.

What is /debug in Claude Code for?

It's for problems with Claude Code (hooks, MCP servers, start-up), not for your application's bugs.

Assignment

Take a real bug your team fixed in the last three months. Using its ticket, commits and any chat history, write a blameless RCA with the template in 114.6: timeline, direct cause, at least three contributing factors, and actions with owners and dates. Use Claude to draft it with [check] markers, then verify every marked sentence yourself. Finally, write the regression test that would have caught the bug, and prove it fails on the old code (bisect or checkout can help).

Teach it

"Debugging is detective work: make the bug happen on demand, collect evidence, guess the cause, test the guess, then fix and add a test. Claude is a great assistant detective if you give it the evidence and tell it not to change code until it's found the cause. git bisect run can find the commit that broke things automatically. Then ask why it got through, not who did it, and write that down with real actions. AI code review helps, but treat each finding as a hypothesis, and review AI-written code just as hard as anyone else's."
