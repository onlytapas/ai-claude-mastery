Skills, subagents, hooks and MCP servers all work on their own. A plugin is simply a folder that packages several of them, with a small manifest file giving the package a name and version, so a whole team can install the same setup in one step and receive updates. Plugins are listed in marketplaces: catalogues, usually git repositories, that you add once. The claude plugin command validates, installs, enables, inspects and even evaluates them. The harder skill is choosing the right building block in the first place, so the chapter ends with a decision table you can keep beside you.

84.1What a plugin is, and when you need one

Imagine your QA team has built up a good setup: a bug-report skill, a read-only test reviewer subagent, a hook that protects application code, and a Playwright MCP server. Today each person copies those files by hand, and copies drift. A plugin turns the set into one installable, versioned unit.

In everyday life

A new starter can be told "install Chrome, then these six extensions, then change these settings", or they can be handed the company laptop image that has it all. A plugin is the laptop image for Claude Code: same contents as doing it by hand, but packaged, named, versioned and easy to update.

The official guidance is practical. Keep things standalone (in .claude/ or ~/.claude/) while they serve one project or only you. Make a plugin when you want to share the setup with teammates, use it in several repositories, or publish versioned releases. A good trigger, from Anthropic's "build your setup over time" table: a second repository needs the same setup.

An enabled plugin is always on

Every skill and agent a plugin adds that Claude can invoke on its own puts its name and description into Claude's context on every turn, even when unused, and its MCP servers and hooks run in every session where it's enabled. Whatever a plugin runs, it runs as you. Install few plugins, from sources you trust, and disable ones you don't use.

84.3The manifest: plugin.json

The manifest names and describes the plugin. Only name is required; without a manifest, a plugin loaded with --plugin-dir is named after its folder.

qa-kit/.claude-plugin/plugin.json
{
  "name": "qa-kit",
  "description": "Shared QA setup: bug-report skill, test reviewer subagent and a protect-src hook",
  "version": "0.1.0",
  "author": { "name": "QA Team" },
  "license": "MIT"
}
FieldWhat it's for
nameRequired. Identifies the plugin and becomes the prefix on its skills and agents. No spaces
descriptionWhat users see in /plugin
versionOptional. When set, users stay on that version until you change it
authorAn object; name required inside it, email and url optional
OthersdisplayName, homepage, repository, license, keywords, defaultEnabled, dependencies, custom component paths (skills, commands, agents, hooks, mcpServers, lspServers, outputStyles) and userConfig for options users fill in

Inside hooks and MCP definitions, refer to bundled files with ${CLAUDE_PLUGIN_ROOT}, because you don't know where the plugin will be installed:

qa-kit/hooks/hooks.json
{
  "description": "Block edits under src/ while the kit is enabled",
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "python3",
            "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/protect_src.py"]
          }
        ]
      }
    ]
  }
}

84.4Marketplaces

A marketplace is a catalogue, not a shop: a git repository or folder containing .claude-plugin/marketplace.json, which lists plugins and where to fetch each one. You add a marketplace once, then install plugins from it by name@marketplace.

qa-tools/.claude-plugin/marketplace.json
{
  "name": "qa-tools",
  "description": "Claude Code plugins maintained by the QA team",
  "owner": { "name": "QA Team" },
  "plugins": [
    {
      "name": "qa-kit",
      "source": "./plugins/qa-kit",
      "description": "Bug-report skill, test reviewer subagent and protect-src hook"
    }
  ]
}

Required: name, owner (with a name), and plugins, each entry with name and source. Sources can be a relative path (as above), github, url, git-subdir, npm, archive or command. A top-level description is optional, but claude plugin validate warns when it's missing.

  • The official marketplace (claude-plugins-official) is added automatically the first time you start an interactive terminal session, unless your organisation blocks it. Browse it in the Discover tab of /plugin.
  • Three tiers: official names, community names (such as claude-community) and everything else, "third-party", which includes your own team's marketplace. Claude Code accepts official and community names only from github.com/anthropics/ repositories.
  • A plugin marketplace is not the same thing as Claude Marketplace, the website at claude.com/marketplace.

Sharing with a team through project settings

To make the team marketplace and plugin appear for everyone who opens the repository, commit both keys to .claude/settings.json:

.claude/settings.json (illustrative organisation and repository names)
{
  "extraKnownMarketplaces": {
    "qa-tools": {
      "source": { "source": "github", "repo": "your-org/qa-tools" }
    }
  },
  "enabledPlugins": {
    "qa-kit@qa-tools": true
  }
}

Two details trip teams up. First, Claude Code honours a repository's extraKnownMarketplaces only after you accept the workspace trust dialog. Second, enabling a plugin in project settings doesn't install it for everyone: each person still installs it on their own machine. To opt out of a project-enabled plugin personally, set it to false in .claude/settings.local.json (user settings can't override project settings).

84.5The claude plugin commands

Run these in your shell, outside a session (claude plugins is an alias). Inside a session, /plugin opens a panel with Discover, Installed and Marketplaces tabs, and /reload-plugins applies changes without restarting.

CommandWhat it does
Build and check
claude plugin validate <path>Checks a plugin or marketplace manifest, or the skills, agents and commands in a folder. --strict fails on warnings (use in CI); --json for scripts. Exit 0 passed, 1 failed, 2 validator error
claude plugin init|new <name>Scaffolds a plugin at ~/.claude/skills/<name>/, which loads next session as <name>@skills-dir. --with skills hooks adds starter files
claude --plugin-dir ./qa-kitLoads a plugin from a folder (or .zip) for one session, without installing it
claude plugin details <name>Shows the component inventory and projected token cost. The plugin must be loaded (installed, or via --plugin-dir in the same command)
claude plugin eval [target]Runs the plugin's eval cases and scores them, by default also without the plugin for comparison (v2.1.269+). claude plugin eval init helps you write the cases
claude plugin tag [path]Creates a {name}--v{version} git tag, checking plugin.json and the marketplace entry agree
Install and manage
claude plugin install|i <plugin>Installs from your marketplaces; --scope user|project|local (default user)
claude plugin enable <plugin> / disableTurns an installed plugin on or off without uninstalling
claude plugin uninstall|remove <plugin>Removes it
claude plugin update <plugin>Updates to the latest version (restart required)
claude plugin listLists installed plugins
claude plugin configure <plugin>Shows or sets a plugin's user options
claude plugin prune|autoremoveRemoves auto-installed dependencies no longer needed

claude plugin marketplace add <source>Adds a marketplace from owner/repo, a git URL, a hosted marketplace.json or a local path; --scope picks the settings file

Install scopes mirror settings files: user (you, every project, ~/.claude/settings.json), project (everyone in the repo, .claude/settings.json) and local (you, this repo, .claude/settings.local.json).

Terminal: a typical team flow (marketplace name from the example above)
claude plugin marketplace add your-org/qa-tools --scope project
claude plugin install qa-kit@qa-tools --scope project
claude plugin disable qa-kit@qa-tools     # turn it off for a while
claude plugin enable qa-kit@qa-tools
Plugin evals in a nutshell

claude plugin eval treats your plugin like any AI feature that needs testing (Chapter 125). Each case is a prompt plus graders, stored under evals/ as case.yaml, or prompt.md with graders/*.md. Claude Code runs each case several times (3 by default) in an isolated session with only your plugin loaded, and usually again without it, so the report shows whether the plugin actually helps. --threshold sets the pass mark, --max-cost-usd caps spend, and the exit code (0 pass, 1 fail, 2 partial run) lets CI gate a release. The help text is explicit that evals run on your machine as you: only evaluate plugins you trust, and a passing suite is not a security review.

84.7Output styles and the status line

Output styles

An output style sets Claude's role, tone and response format for a whole session. Besides Default there are four built-ins:

StyleWhat changes
ProactiveStarts work straight away and makes reasonable assumptions instead of asking about routine decisions (permission prompts are unchanged)
ConciseLeads with the result; no preamble, narration or recap
ExplanatoryAdds short "Insight" blocks explaining the choices behind the code
LearningExplains, and leaves small pieces of code for you to write

Switch with /output-style concise (the command ignores case) or /config > Output style; both save to .claude/settings.local.json. In a settings file, write "outputStyle": "Explanatory": there the value is case-sensitive, and a wrong case silently gives you Default. A custom style is a Markdown file in ~/.claude/output-styles/ or .claude/output-styles/:

.claude/output-styles/qa-reporter.md
---
name: QA reporter
description: Answers in the team's defect-report format
keep-coding-instructions: true
---
When you report a problem, use the headings Summary, Steps to reproduce,
Expected, Actual and Severity. Keep each section to three lines or fewer.

keep-coding-instructions: true keeps Claude Code's built-in software engineering instructions; leave it out only if Claude won't be coding. Styles are instructions, not guarantees, and they don't change how normal subagents respond (forks excepted).

The status line

The status line is a line under the prompt that you control. The fastest route is /statusline followed by a description ("show the model, folder and context used"); Claude writes the script and updates settings. By hand, a script receives session JSON on stdin and prints one line:

~/.claude/statusline.sh (from the docs; needs jq)
#!/bin/bash
input=$(cat)
MODEL=$(echo "$input" | jq -r '.model.display_name')
DIR=$(echo "$input" | jq -r '.workspace.current_dir')
PCT=$(echo "$input" | jq -r '.context_window.used_percentage // 0' | cut -d. -f1)
echo "[$MODEL] ${DIR##*/} | ${PCT}% context"
~/.claude/settings.json
{ "statusLine": { "type": "command", "command": "~/.claude/statusline.sh", "padding": 2 } }

Make it executable with chmod +x ~/.claude/statusline.sh. Like hooks, the status line command runs outside the sandbox, so review any script a colleague shares.

84.9Choosing the right tool

Part X has given you eight ways to shape Claude Code. They overlap just enough to confuse. Ask one question first: does this need to be guaranteed, or is it guidance? Guarantees belong in settings (permissions) or hooks. Guidance belongs in CLAUDE.md, skills, output styles or subagent prompts.

Real-world example: one rule, three wrong homes

"Never commit secrets in test data." As a CLAUDE.md line it's a reminder Claude may forget. As a skill it only applies when invoked. As a subagent it's a reviewer you must remember to call. The right home is a permission deny rule for reading .env files plus a PreToolUse hook that scans new fixture files for key patterns, packaged in the team plugin so every repository gets it.

Opinion · Anthropic's documentation

Anthropic's "build your setup over time" advice is to add features in response to real triggers rather than up front: a convention Claude gets wrong twice goes in CLAUDE.md; the same prompt typed repeatedly becomes a skill; a side task that floods the conversation becomes a subagent; something that must happen every time becomes a hook; a second repository needing the same setup becomes a plugin. This textbook agrees: a small setup you understand beats a large one nobody can debug.

Common misunderstandings
"A plugin can do things the parts can't."
A plugin packages skills, subagents, hooks, MCP servers and styles. Its value is distribution and versioning, not new powers.
"Enabling a plugin in .claude/settings.json installs it for the team."
It declares it. Each person still installs it, and the marketplace entry only registers after the trust dialog.
"A plugin that isn't being used costs nothing."
Descriptions of its model-invocable skills and agents sit in context every turn, and its hooks and MCP servers run every session. Check with claude plugin details.
"Validation passing means a plugin is safe."
It means the files are well-formed. A plugin runs as you; review what it does, especially hooks and MCP servers.
"An output style forces Claude's behaviour."
It's an instruction, like CLAUDE.md. Use a hook for anything that must happen.

84.10Review

Key takeaways
  • A plugin is a folder that packages skills, agents, hooks, MCP servers and more, with .claude-plugin/plugin.json (only name required) as its manifest.
  • Marketplaces are catalogues listed in .claude-plugin/marketplace.json; install with plugin@marketplace at user, project or local scope.
  • Key commands: validate (with --strict in CI), install, enable/disable, details (inventory and token cost), eval (scored test cases); test locally with --plugin-dir.
  • Output styles change voice and format; the status line is a script that prints one line from session JSON. Both are personal settings.
  • Choose by asking: must it be guaranteed (permissions, hooks), is it an outside system (MCP), is it noisy (subagent), is it a procedure (skill), or a fact (CLAUDE.md)? Package for reuse as a plugin.
Check yourself

Which file must go inside a plugin's .claude-plugin/ folder?

Components saved inside .claude-plugin/ don't load. They go at the plugin root, in skills/, agents/, hooks/ and so on.

You want CI to fail if a plugin has unrecognised fields or missing metadata. Which command fits?

--strict treats warnings as errors and exits 1, which a pipeline can act on.

Your team must never let Claude edit generated API clients under src/gen/. Which is the right primary tool?

"Never" needs enforcement. CLAUDE.md and output styles are instructions the model may not follow.

What does claude plugin details show that's useful before rolling a plugin out?

The inventory and token estimate tell you what the plugin adds to every session.

In .claude/settings.json, you set "outputStyle": "concise". What happens?

The settings value must be Concise. Only the /output-style command ignores case.

Assignment

Audit your team's Claude Code setup using the decision table in 84.9. List every rule, prompt and helper people currently share by copy and paste, and write next to each the tool it belongs in and why. Move at least one "must never" rule from CLAUDE.md into a permission rule or hook. Then package the shareable pieces as a plugin, validate it with --strict, check its cost with claude plugin details, and write a one-page README covering what it contains, what it runs on people's machines, and how to disable it.

Teach it

"A plugin is a package for our Claude Code setup: skills, subagents, hooks and MCP servers in one folder with a plugin.json that names it. We publish it in a marketplace, which is just a git repo with a catalogue file, and everyone installs it with one command. Before adding anything, ask: must it always happen? Then it's a permission or a hook. Is it an outside system? MCP. Is it noisy? A subagent. Is it a procedure? A skill. Is it a fact? CLAUDE.md. And remember an enabled plugin runs as you and costs context every session, so keep it small and review it."
