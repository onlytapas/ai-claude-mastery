Claude Code is a loop. You give it a goal. It packs everything relevant into a message and sends it to a Claude model. The model either answers or asks to use a tool, such as reading a file or running a command. Claude Code checks whether that action is allowed, runs it on your computer, and sends the result back. The model decides the next step. This repeats until the job is done. Understanding this loop explains almost everything Claude Code does, including its mistakes.

66.1Two parts: the model and the harness

Anthropic's documentation describes Claude Code as two components working together:

The model

A Claude model (for example Opus 5.5) running on Anthropic's servers. It reads, reasons and decides. On its own it can only produce text.

The harness

Claude Code itself, running on your computer. It provides the tools, manages what the model sees (the context), enforces permissions, and runs the actions. Anthropic calls this layer the agentic harness.

In everyday life

Think of a remote expert guiding a technician over the phone. The expert (the model) can't touch anything; they reason and give instructions. The technician (the harness) is on site with the tools, follows the house safety rules, does the work and reports back what they see. Neither could fix the problem alone.

The documentation describes the loop in three overlapping phases: gather context, take action, verify results. A question about your code may only need the first phase. Fixing a failing test usually cycles through all three several times.

1 · YouType a request and press Enter
2 · Build contextHarness gathers instructions, CLAUDE.md, memory, tool list, conversation

6 · Result backOutput added to the context; back to step 3

The loop ends when the model replies with text and no tool request: that's the final answer you see. You can break into the loop at any time with Esc, or queue a correction by typing while it works.

Anthropic's data-usage documentation says Claude Code runs locally and sends data over the network to talk to the model: your prompts and the model's outputs, encrypted in transit (TLS 1.2 or later). In practice the "prompt" sent each turn includes everything in the context: instructions, the conversation, and the contents of any file Claude read or command output it saw. What isn't sent: files Claude never read. It doesn't upload your whole disk or repository.

Data and training

Under commercial terms (Team and Enterprise plans, the API and cloud platforms), Anthropic's documentation states that it does not train models on code or prompts sent to Claude Code unless the customer opts in. Consumer plans have their own settings. Usage telemetry, which can be switched off, never includes your code, prompts or file paths. Check your organisation's agreement for retention details (Chapter 125).

So, practically

Anything Claude reads is sent to the model. That's why you keep secrets out of reach with deny rules, for example Read(./.env) (Chapter 78), rather than hoping Claude won't open them.

Real-world example

Your team's CLAUDE.md says "Select elements by data-testid only". You never mention it in your prompt, yet Claude follows it, because CLAUDE.md is in the context every turn. Run /context at any time to see what's using space.

66.5Step 3: the model decides

The model reads the whole context and produces a reply. On current models it may think first (extended thinking is always on for Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable; the effort level controls how much, Chapter 68). The reply is one of two things:

  • Text: an explanation, a question for you, or the final answer.
  • A tool request: "I want to use the Bash tool with the command npx playwright test checkout", often with some text explaining why. A reply can contain several tool requests at once, for example reading three files in parallel.
What a tool request and its result look like

Under the hood, Claude Code talks to the model through Anthropic's Messages API (Chapter 86). A tool request arrives as a tool_use block, and the harness answers with a tool_result block that refers back to it by ID. Simplified:

Model → harness: a tool request (simplified)
{
  "type": "tool_use",
  "id": "toolu_01A...",            // ticket number for this request
  "name": "Bash",                   // which tool
  "input": { "command": "npx playwright test checkout", "description": "Run the checkout tests" }
}
Harness → model: the result (simplified)
{
  "type": "tool_result",
  "tool_use_id": "toolu_01A...",    // matches the request
  "content": "1 failed: checkout.spec.ts:42 expected 90, received 100 ..."
}

The model never runs anything itself. It only ever writes requests like the first block. Everything that touches your computer happens in the harness, which is why the harness can enforce permissions. MCP tools (Chapter 99) travel the same way; their names look like mcp__playwright__browser_navigate.

66.6Step 4: the permission check

Every tool request passes a gate before it runs. The order matters, and it's the same idea a tester applies to access control: the most restrictive rule wins.

PreToolUse hooksYour scripts run first. A hook that blocks (exit code 2) stops the call outright.
RulesChecked in order: deny, then ask, then allow. First match wins.
ModeIf no rule matched, the permission mode decides: prompt you, allow, or send to the classifier.
OutcomeRun, ask you, or block (and tell the model why)
  • Hooks (Chapter 82) run before the permission prompt. A hook can block a call, but it can't override your deny or ask rules: a matching deny still blocks even if the hook said "allow".
  • Rules (Chapter 78) are evaluated deny → ask → allow. A broad deny like Bash(git push *) beats a narrower allow. A deny written at any settings level beats an allow at any other level.
  • Read-only actions such as reading files inside the working folder, and a built-in list of read-only shell commands, don't need approval in any mode.
  • The mode decides the rest. In Manual mode you're asked before edits and most commands. In Accept edits, file edits go through. In Plan mode, edits wait for an approved plan.

What the auto-mode classifier does

In Auto mode, a second model (the classifier) reviews actions instead of you. According to Anthropic's documentation, each action goes through a fixed order, and the first matching step wins:

  1. Your allow, ask and deny rules resolve first (with safety exceptions: for example, no allow rule can approve deleting critical paths such as your home folder).
  2. Read-only actions and file edits inside your working folder are approved automatically, except writes to protected paths such as settings files.
  3. Everything else goes to the classifier, which blocks actions that go beyond your request, target infrastructure it doesn't recognise, or appear to be driven by hostile content Claude read.
  4. If it blocks, Claude is told why and can try a different approach.

When you enter Auto mode, broad allow rules that would permit arbitrary code (for example Bash(*)) are switched off for the session; narrow ones like Bash(npm test) stay. Explicit ask rules still prompt you.

In everyday life

The permission check is building security. Your own sign-in rules (hooks) come first, then the official access list (deny, ask, allow), then the duty policy (the mode). In Auto mode, a security officer (the classifier) reviews visitors the list doesn't cover, and turns away anyone acting suspiciously.

You type: "The checkout test is failing on CI. Find out why and fix it, but tell me first if the app is wrong rather than the test." Here's an illustrative trace of how the loop might go in Manual mode. Real sessions vary.

66.9Context grows, then compacts

Every tool result is added to the context, so a long session fills up. Near the limit, Claude Code compacts automatically: it replaces the conversation with a summary that keeps your requests and key code, but early detailed instructions can be lost. That's why permanent rules belong in CLAUDE.md, which is reloaded, not in an early chat message.

Fresh sessionInstructions, CLAUDE.md, tool list
WorkingEach file read and command output adds tokens
Near the limitAutomatic compaction: conversation becomes a summary
ContinuesSummary + CLAUDE.md + new work
  • /context shows what's using space.
  • /compact focus on the checkout failure compacts now, keeping what you name.
  • /clear starts fresh when the next task is unrelated.
  • Subagents work in their own context; only their summary comes back, which keeps your main context lean.

If one file or output is so large that the context refills right after each summary, Claude Code stops auto-compacting after a few attempts and shows a "thrashing" error. The fix is to read the file in parts, use a subagent, or /clear.

66.10Checkpoints: the undo button, and its limits

Before Claude edits a file, the harness saves a snapshot. Every prompt that starts a turn creates a checkpoint, and you can go back with Esc Esc or /rewind, choosing to restore the code, the conversation, or both (Chapter 67).

What checkpoints can't undo
  • Files changed by shell commands (for example a script that rewrites files) aren't tracked.
  • Most subagent edits, and edits you or other programs make outside Claude, aren't tracked.
  • Anything outside your computer (a database change, an API call, a Jira ticket created through MCP, a deployment) can't be checkpointed. Permissions are your protection there.
  • Checkpoints are not a replacement for git. Commit good states.

Common misunderstandings
"Claude Code uploads my whole repository."
It sends what's in the context: your messages, instructions, and the files and outputs Claude actually read. Unread files stay on your machine.
"The model runs the commands."
The model only requests actions. The harness on your computer checks permissions and runs them.
"A hook that says allow overrides my deny rules."
No. Deny and ask rules are still enforced after hooks. A hook can block, but it can't unlock a denied action.
"Auto mode means no safety checks."
It means a classifier checks instead of you. Rules still apply, and some actions always prompt. (That's different from bypass mode, which skips checks and belongs only in isolated sandboxes.)
"Rewind can undo anything."
It only restores file edits Claude made through its edit tools. External effects (databases, tickets, deployments) can't be undone.

66.11Review

Key takeaways
  • Claude Code = a model that decides + a harness that holds the tools, manages context and enforces permissions.
  • The loop: build context → model replies → permission check → run locally → result back → repeat, until a text-only reply.
  • The harness runs on your computer; the model runs at Anthropic. Whatever Claude reads is sent to the model, encrypted.
  • Context includes system instructions, tools, CLAUDE.md, auto memory, skill descriptions, git state, the conversation and reminders.
  • Permission order: hooks, then rules (deny → ask → allow), then the mode; in Auto mode, a classifier reviews what's left.
  • Exact tool names (Read, Edit, Write, Bash, WebFetch, Agent, Skill, Task…) are what you use in rules and hooks.
  • Compaction summarises long sessions; checkpoints undo Claude's file edits only.
