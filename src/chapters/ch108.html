Most useful AI systems aren't one big clever agent. They're a few simple patterns joined together: do steps in order (chaining), send each input to the right handler (routing), do several things at once (parallelisation), let one model hand out work (orchestrator-workers), and let one step check another (evaluator-optimiser). Agents add two more habits: plan first, then act, and look back at mistakes before trying again. Each pattern buys something specific (accuracy, speed, flexibility) and costs something specific (latency, tokens, complexity). Pick the simplest one that solves the problem.

108.1The building block and the menu

Anthropic's article "Building effective agents" (December 2024) starts from one building block, which it calls the augmented LLM: "an LLM enhanced with augmentations such as retrieval, tools, and memory". Every pattern in this chapter is a way of connecting several calls to that block, with ordinary code in between.

A design pattern is a named, reusable solution to a problem that keeps coming up. You already know some from testing: the Page Object pattern in UI automation, Arrange-Act-Assert in unit tests. Agent design patterns play the same role: a shared vocabulary so a team can say "let's add an evaluator step" and everyone knows what that means.

108.2Prompt chaining

Split a task into fixed steps. Each step is its own model call that takes the previous step's output. Between steps, your code can run a gate: a programmatic check that stops the chain if the intermediate result looks wrong.

Call 1Rewrite the bug as numbered reproduction steps
Gate (code)Does it start with "1."? If not, stop
Call 2Write three test case titles from the steps
OutputTest titles for review

When to use it: the task splits cleanly into steps you know in advance, and each step is easier for the model than the whole. Anthropic's article describes the trade as accepting more latency for higher accuracy. Its examples: write marketing copy, then translate it; outline a document, check the outline against criteria, then write it.

Real-world example

A QA team turns Jira stories into test cases in three calls: (1) extract the acceptance criteria as a numbered list, (2) gate: code checks there is at least one criterion and none is longer than 300 characters, (3) generate test cases per criterion in a fixed JSON shape (Chapter 89, structured outputs). When step 1 fails on a badly written story, the gate stops it, and the story goes back to the product owner instead of producing nonsense tests.

In everyday life

An assembly line with inspection points. Each station does one job well, and an inspector between stations pulls faulty parts off the line before more work is wasted on them.

108.3Routing

A first step classifies the input. Your code then sends it to a handler built for that kind of input: a different prompt, different tools, a different model, or a person.

Classifyui, api or performance?
Route (code)Look up the handler; unknown goes to a default
HandlerSpecialised prompt, tools or team

When to use it: inputs fall into distinct categories that are better handled separately, and the classification can be done reliably. Anthropic's example is customer service: general questions, refund requests and technical support each go to a different process. It also notes that routing can send easy questions to smaller, cheaper models and hard ones to more capable models, which is model routing (Chapter 40).

Test the router like a classifier

A router is a classifier, so test it like one: build a labelled set of 50–100 real inputs, measure how often it picks the right branch, and look closely at the mistakes (Chapter 125). Always have a safe default branch for "none of the above". A silent misroute is worse than an honest "I'm not sure".

108.4Parallelisation: sectioning and voting

Run several model calls at the same time and combine the results in code. Anthropic's article describes two forms:

Sectioning

Split a task into independent parts and run them side by side. Example: review a pull request for security, accessibility and test coverage as three separate calls, each with a focused prompt. The article's example is guardrails: one call handles the user's request while another screens it for inappropriate content.

Voting

Run the same task several times and compare. Example: ask three times "is BUG-131 a duplicate of BUG-88?" and take the majority. The article's example is reviewing code for vulnerabilities with several prompts that each flag problems.

When to use it: sectioning when parts are truly independent and you want speed, or when each concern deserves full attention. Voting when you want more confidence than one answer gives, and when disagreement itself is useful information ("the three votes split: send to a human").

Under the hood: why votes differ, and what voting can't fix

A model's output is sampled (Chapter 16), so the same prompt can give different answers. Voting turns that variation into a signal: unanimous answers are more trustworthy than split ones. But voting can't fix a systematic error. If the prompt is missing the context needed to spot the duplicate, all three votes can be confidently wrong together. Voting also multiplies cost by the number of votes. Use it where a wrong answer is expensive, not everywhere.

108.5Orchestrator-workers

One model call, the orchestrator, looks at the task and decides what subtasks are needed. It hands each to a worker call, then combines what comes back. The article names the key difference from parallelisation as flexibility: the "subtasks aren't pre-defined, but determined by the orchestrator based on the specific input".

Orchestrator"This failure touches login, cart and payments"
WorkersOne investigation per area, often in parallel
OrchestratorCombines findings into one report

When to use it: you can't predict the subtasks in advance. The article's examples: coding changes that touch an unknown number of files, and research that gathers information from several sources.

Real-world example: Anthropic's Research feature

Anthropic described its own Research system (June 2025) as an orchestrator-worker design: a lead agent plans the research and starts subagents that search in parallel. It reported that a version with a Claude Opus 4 lead and Claude Sonnet 4 subagents outperformed a single Claude Opus 4 agent by 90.2% on its internal research evaluation, and that multi-agent systems used about 15 times more tokens than chat. Both figures are Anthropic's own measurements on its own task. The lesson for your team: the pattern can help on broad tasks, but check the gain is worth the cost on your task. Chapter 111 covers multi-agent systems in depth.

108.6Evaluator-optimiser

One call produces an answer. A second call (or code) evaluates it against clear criteria and gives specific feedback. The producer tries again using the feedback. The loop ends when the evaluator approves or a round limit is reached.

GenerateDraft three test titles
EvaluateAll start with "Verify" and mention the voucher? If not, say what's wrong
ReviseDraft again with the feedback
StopOn "OK", or after 3 rounds: hand to a human

When to use it: the article gives two signs: you have clear evaluation criteria, and iterating measurably improves the result. Its examples are literary translation and complex searches that need several rounds.

Prefer code checks where you can

If a criterion can be checked by code (valid JSON, every title starts with "Verify", the test file compiles, the test actually fails on the old build), check it with code. It's free, fast and never wrong about the rule. Use a model as the evaluator (LLM-as-judge) only for qualities code can't measure, such as clarity, and test the judge itself (Chapter 125).

Always cap the rounds

Without a round limit, a strict evaluator and a stubborn generator can loop forever, spending money each time. The article lists stopping conditions "such as a maximum number of iterations" as a standard control. When the cap is hit, the honest output is "couldn't satisfy the criteria; needs a person", not the last failed draft presented as finished.

108.7Agent patterns: plan-and-execute and reflection

The five patterns above are mostly workflows: your code holds the structure. Two further patterns are common inside agents, where the model holds it. They are not among the patterns named in Anthropic's article, so treat them as widely used practice rather than official guidance.

Plan-and-execute

The agent first writes a complete plan as a list of steps. Then it carries the steps out, one at a time, checking results as it goes and re-planning only if something unexpected happens. Writing the plan down first makes the agent's intentions visible before it acts, which supports the transparency principle in Chapter 107, and gives a person a natural moment to approve or edit the plan.

Claude Code's plan mode (Chapter 67) is a human-supervised version: Claude explores and proposes a plan, you review it, and only then does it edit files.

Reflection

After an attempt fails (a test still fails, an evaluator rejects the output), the model is asked to explain why in words and write down a lesson, then retry with that lesson in view. In March 2023, Noah Shinn and colleagues published Reflexion, in which language agents improve across attempts by writing out lessons from feedback and keeping them in memory, without retraining the model.

Under the hood: why reflection needs a real signal

Reflection works best when the feedback comes from the world, not from the model's own opinion: a test result, a compiler error, a measured value. A model asked "was your answer good?" with no new evidence will often just agree with itself. So pair reflection with a real check: run the test, call the API, compare with the expected output. Then the "lesson" is grounded in something observed.

108.8Choosing and combining patterns

Start with the simplest thing that could work, then add a pattern only when you can name the problem it solves.

If your problem is…Try…Cost you add
One big prompt gives patchy results on a multi-part taskPrompt chaining with gatesMore calls in sequence (latency)
Different kinds of input need different handlingRouting, with a safe defaultOne extra (cheap) call per input
Independent checks take too long one after anotherParallel sectioningSame tokens, less waiting; more concurrent requests (rate limits, Chapter 90)
You need more confidence in a yes/no decisionParallel votingTokens × number of votes
You can't know the subtasks until you see the inputOrchestrator-workersMuch higher token use; harder to debug
Output must meet clear criteria and often doesn't first timeEvaluator-optimiser with a round capUp to rounds × 2 calls
The agent dives in and wastes stepsPlan-and-execute, with plan reviewOne planning call; a human checkpoint
The agent repeats the same mistake on retryReflection grounded in a real failure signalOne extra call per failed attempt

Patterns compose. A realistic QA pipeline might route each nightly failure (product bug, test bug, environment), run a chain for product bugs (summarise, find similar, draft a Jira ticket), use voting for the "is it a duplicate?" decision, and finish with an evaluator that checks the draft has steps, expected and actual results. Only the investigation step for unknown failures needs a true agent.

Opinion · Anthropic ("Building effective agents")

The article argues that success comes from building the right system for your needs rather than the most sophisticated one, and that you should add complexity only when it demonstrably improves outcomes. In testing terms: every pattern you add is more behaviour to verify. Measure before and after (Chapter 125).

patterns.py
"""Four workflow patterns on one bug report.
Offline: python3 patterns.py --fake      Real: python3 patterns.py (needs ANTHROPIC_API_KEY)"""
import os, sys
from collections import Counter
from concurrent.futures import ThreadPoolExecutor

PROMPTS = {
    "classify": "Classify this bug report as exactly one word: ui, api or performance.\n\n{x}",
    "steps":    "Rewrite this bug report as numbered reproduction steps only.\n\n{x}",
    "tests":    "Write three test case titles, one per line, each starting 'Verify', for:\n\n{x}",
    "dupe":     "Is this a duplicate of 'BUG-88 Voucher not applied at checkout'? Answer yes or no.\n\n{x}",
    "review":   "Review these test titles. Reply OK if all three start with 'Verify' and mention "
                "the voucher; otherwise give one line of feedback.\n\n{x}",
}

def fake_llm(task, x):
    """Canned answers so the patterns run without an API key."""
    if task == "classify":
        return "api" if "500" in x else "ui"
    if task == "steps":
        return "1. Add item (100.00)\n2. Apply voucher SAVE10\n3. Check total"
    if task == "tests":
        if "Feedback" in x:
            return ("Verify SAVE10 voucher reduces total by 10%\nVerify expired voucher is rejected\n"
                    "Verify voucher total is recalculated after removing an item")
        return "Check discount\nVerify SAVE10 voucher reduces total\nTest expired codes"
    if task == "dupe":
        fake_llm.n = getattr(fake_llm, "n", 0) + 1
        return "no" if fake_llm.n % 3 == 0 else "yes"     # vary, like real sampling
    if task == "review":
        lines = x.strip().splitlines()[-3:]
        ok = all(l.startswith("Verify") and "voucher" in l.lower() for l in lines)
        return "OK" if ok else "Every title must start with 'Verify' and mention the voucher."

def real_llm(task, x):
    import anthropic
    r = anthropic.Anthropic().messages.create(model="claude-opus-5-5", max_tokens=500,
        messages=[{"role": "user", "content": PROMPTS[task].format(x=x)}])
    return "".join(b.text for b in r.content if b.type == "text").strip()

llm = fake_llm if "--fake" in sys.argv else real_llm

BUG = ("BUG-131: Applying voucher SAVE10 at checkout shows total 100.00 instead of 90.00. "
       "No error shown. API returns 200.")

def routing(bug):
    category = llm("classify", bug).lower()
    handlers = {"ui": "front-end squad", "api": "platform squad", "performance": "perf team"}
    return category, handlers.get(category, "triage lead")       # safe default route

def chaining(bug):
    steps = llm("steps", bug)
    if not steps.lstrip().startswith("1."):                       # gate: check before continuing
        raise ValueError("step 1 output failed the gate")
    return llm("tests", steps)

def voting(bug, n=3):
    with ThreadPoolExecutor(max_workers=n) as pool:
        votes = list(pool.map(lambda _: llm("dupe", bug).lower(), range(n)))
    return Counter(votes).most_common(1)[0][0], votes

def evaluator_optimiser(bug, max_rounds=3):
    draft = llm("tests", bug)
    for round_no in range(1, max_rounds + 1):
        verdict = llm("review", draft)
        print(f"  round {round_no}: {verdict}")
        if verdict.strip().upper().startswith("OK"):
            return draft
        draft = llm("tests", f"{bug}\n\nPrevious attempt:\n{draft}\n\nFeedback: {verdict}")
    return draft + "\n(stopped after max rounds: needs a human)"

if __name__ == "__main__":
    if llm is real_llm and not os.environ.get("ANTHROPIC_API_KEY"):
        sys.exit("No ANTHROPIC_API_KEY set. Run with --fake to use the offline stand-in.")
    print("ROUTING:", routing(BUG))
    print("CHAINING:\n" + chaining(BUG))
    print("VOTING:", voting(BUG))
    print("EVALUATOR-OPTIMISER:")
    print(evaluator_optimiser(BUG))

Troubleshooting. ModuleNotFoundError: anthropic in real mode: run pip install anthropic in the same environment, or use --fake. Votes come out in a different order each run: expected, because the three calls run in parallel threads. Real-mode answers don't match the fake's: expected; the fake is rule-based. If the real router returns a word outside ui, api, performance, the safe default sends it to triage lead. The fake mode was tested on Python 3.11; the real mode follows Anthropic's documented request format but was not run for this chapter because no API key was available.

Common misunderstandings
"More agents and more patterns mean better results."
Each pattern adds cost, latency and behaviour to test. Add one only when you can name the problem it solves, and measure the improvement.
"Parallelisation and orchestrator-workers are the same."
In parallelisation your code fixes the subtasks in advance. In orchestrator-workers the model decides them from the input.
"Voting fixes hallucinations."
It reduces random errors. If every call lacks the same information, all votes can be wrong together.
"An evaluator loop will always converge."
It may not. Cap the rounds and escalate to a person when the cap is reached.
"Reflection means the model learns."
The model's weights don't change. The lesson is text kept in the conversation or memory and sent with the next attempt.

108.9Review

Key takeaways
  • Every pattern connects calls to the same building block: a model augmented with retrieval, tools and memory.
  • Prompt chaining: fixed steps with gates between them; trades latency for accuracy.
  • Routing: classify, then send to a specialised handler; test the router as a classifier and keep a safe default.
  • Parallelisation: sectioning for independent parts, voting for confidence; voting multiplies cost.
  • Orchestrator-workers: the model chooses subtasks at run time; flexible, expensive and harder to debug.
  • Evaluator-optimiser: produce, judge, revise; prefer code checks and always cap the rounds.
  • Plan-and-execute and reflection are common agent habits; ground reflection in real failure signals.

Teach it

"There are a handful of standard ways to wire AI calls together. Chaining does steps in order with checks in between. Routing sorts inputs and sends each to the right handler. Parallelisation runs several calls at once, either splitting the work or voting on the same question. Orchestrator-workers lets one model hand out jobs it decides on the fly. Evaluator-optimiser has one step check another and send it back with feedback, with a cap on rounds. Each adds cost and things to test, so we start simple and add a pattern only when we can name the problem it fixes."
