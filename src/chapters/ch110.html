The Claude Agent SDK is Claude Code packaged as a library. Instead of typing into a terminal, your Python or TypeScript program calls one function, query(), and gets back a stream of messages while Claude plans, calls tools, reads results and decides when it is finished. You don't write the agent loop yourself; you decide what the agent may touch. You give it tools (built-in ones such as Read and Bash, your own functions, or MCP servers), you set the rules for which actions run without asking, and you attach hooks: small pieces of your own code that run before or after each action and can block it. Get those three things right and you have an agent you can put into a pipeline.

110.1What the Agent SDK is, and what it isn't

In Chapter 86 you called the Claude API directly: you sent a message, you got a message back. If you wanted Claude to use a tool, you had to describe the tool, notice when Claude asked for it, run it yourself, send the result back and repeat. That repeat-until-done cycle is the agent loop from Chapter 107, and writing it well (with retries, context management, permissions and logging) is real work.

The Claude Agent SDK gives you that loop ready-made. Anthropic's documentation describes it as giving you "the same tools, agent loop, and context management that power Claude Code, programmable in Python and TypeScript". It was called the Claude Code SDK until 29 September 2025, when it was renamed.

In everyday life

The Client SDK is like buying a very good drill: powerful, but you hold it and decide every hole. The Agent SDK is like hiring a contractor who arrives with a full toolbox, plans the job and works through it, while you set the house rules: which rooms they may enter, what needs your sign-off, and a camera that records every tool they pick up.

Anthropic's own comparison puts the four options side by side:

You want toUseWhat you get
Embed Claude Code's agent in your own Python or TypeScript application, in a process you operateAgent SDKA library that runs the Claude Code binary, with built-in tools, permissions, sessions and hooks
Work interactively, or run one-off tasks from a terminalClaude Code CLI (Chapter 63)The terminal interface; claude -p for scripted runs
Call the Claude API directly from your own codeClient SDK (the anthropic package)Direct API access; you write the tool loop yourself, or use its beta tool runner
Have Anthropic host the agentManaged Agents (beta)A hosted harness with sessions in an Anthropic-managed cloud sandbox or your own sandbox
Real-world example

A QA team wants a nightly job that reads the Playwright results, groups the failures, and drafts a triage note for the morning stand-up. The Client SDK would need a hand-written loop and hand-written file tools. claude -p would work but is awkward to test and extend. The Agent SDK fits: a Python script in the repository, unit-testable custom tools, a hook that stops the agent writing anywhere except the report folder, and a hard budget cap. That is exactly what you build in the lab.

Understanding, using, building

Earlier chapters were about using Claude Code. This chapter is about building: you write and own the program, so you also own its safety settings, its costs and its failures.

110.3The query loop

Everything starts with query(). You pass a prompt and an options object; it returns an async iterator (async, Chapter 58), a stream you read with async for. Each item is a message describing one step.

Your codecalls query(prompt, options)
SDKstarts the bundled Claude Code process
Claudethinks, then asks for a tool
Claude Codechecks permissions and hooks, runs the tool
Resultgoes back to Claude; repeat until done
ResultMessagefinal answer, cost, turns

This is the quickstart example from the official docs, unchanged apart from the comments:

agent.py (Python)
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, AssistantMessage, ResultMessage


async def main():
    async for message in query(
        prompt="Review utils.py for bugs that would cause crashes. Fix any issues you find.",
        options=ClaudeAgentOptions(
            allowed_tools=["Read", "Edit", "Glob"],  # run these without asking
            permission_mode="acceptEdits",           # auto-approve file edits
        ),
    ):
        if isinstance(message, AssistantMessage):
            for block in message.content:
                if hasattr(block, "text"):
                    print(block.text)                # Claude's reasoning
                elif hasattr(block, "name"):
                    print(f"Tool: {block.name}")     # a tool call
        elif isinstance(message, ResultMessage):
            print(f"Done: {message.subtype}")


asyncio.run(main())
agent.ts (TypeScript, run with npx tsx agent.ts)
import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const message of query({
  prompt: "Review utils.py for bugs that would cause crashes. Fix any issues you find.",
  options: { allowedTools: ["Read", "Edit", "Glob"], permissionMode: "acceptEdits" }
})) {
  if (message.type === "assistant" && message.message?.content) {
    for (const block of message.message.content) {
      if ("text" in block) console.log(block.text);
      else if ("name" in block) console.log(`Tool: ${block.name}`);
    }
  } else if (message.type === "result") {
    console.log(`Done: ${message.subtype}`);
  }
}

Errors arrive twice

A single-shot query() yields the error result and then raises an exception. Wrap the loop in try/except so your script reports the failure cleanly instead of crashing with a traceback; the docs' own examples do this.

query() or ClaudeSDKClient?

query() starts a fresh session for each call: ideal for one job, such as a CI step. ClaudeSDKClient keeps one session open so you can send follow-up prompts, interrupt (interrupt()), switch permission mode mid-run (set_permission_mode()) or change model (set_model()). Use it with async with ClaudeSDKClient(options=...) as client:, then await client.query("...") and read client.receive_response(). To continue a query() session later, keep the session_id from the result and pass resume=session_id in the next call's options.

Under the hood: what the SDK is actually doing

The SDK is a thin layer. It starts the Claude Code binary as a child process and talks to it over standard input and output with a stream of JSON messages (the same idea as claude -p --output-format stream-json, Chapter 75). Claude Code does the real work: building the system prompt, calling the API, running tools, compacting the context when it fills, applying permission rules. When Claude Code needs a decision from your program, such as "may I run this tool?" or "here is a PreToolUse event", it sends a control request over the same channel and your callback answers it.

Two consequences follow. First, the SDK version and the bundled Claude Code version move together; the Python package records which CLI it bundles (2.1.319 for 0.2.179). Second, behaviour you know from Claude Code (settings files, CLAUDE.md, skills, auto-compaction) applies here too unless you turn it off. By default the SDK loads user, project and local settings just like the CLI; setting_sources=[] (TypeScript settingSources: []) gives you an isolated agent that ignores whatever happens to be in ~/.claude on the machine it runs on.

110.4Tools: built-in, custom and MCP

The agent can only act through tools. You decide which ones exist and which ones run without asking. The docs separate two layers, and confusing them is the most common SDK mistake:

OptionLayerEffect
tools=["Read", "Grep"]AvailabilityOnly these built-in tools are in Claude's context. MCP tools are unaffected. tools=[] removes all built-ins.
allowed_tools=[...]PermissionListed tools run without a permission prompt. Unlisted tools still exist; calls to them go through the permission flow.
disallowed_tools=["Bash"]BothA bare name removes the tool from context. A scoped rule such as "Bash(rm *)" keeps the tool but denies matching calls.

The built-in tools are Claude Code's: Read, Write, Edit, Glob, Grep, Bash, WebFetch, WebSearch, Agent (subagents, Chapter 111) and others listed in the tools reference. A useful starting set from the quickstart: Read, Glob, Grep for read-only analysis; add Edit to modify code; add Bash for full automation.

Your own tools

A custom tool is an ordinary Python async function wrapped with the @tool decorator (name, description, input schema), then placed in an in-process MCP server made by create_sdk_mcp_server. "In-process" means the server lives inside your Python program; no separate process starts. Claude sees the tool as mcp__{server key}__{tool name}, and that full name is what goes in allowed_tools.

A custom tool (Python)
from typing import Any
from claude_agent_sdk import tool, create_sdk_mcp_server, ToolAnnotations

@tool("count_flaky", "Count how often a test failed in the last N runs",
      {"test_name": str, "runs": int},
      annotations=ToolAnnotations(readOnlyHint=True))
async def count_flaky(args: dict[str, Any]) -> dict[str, Any]:
    failures = 3   # illustrative: look this up in your CI history instead
    return {"content": [{"type": "text",
                         "text": f"{args['test_name']} failed {failures} of {args['runs']} runs"}]}

ci_server = create_sdk_mcp_server(name="ci", version="1.0.0", tools=[count_flaky])
# options: mcp_servers={"ci": ci_server}, allowed_tools=["mcp__ci__count_flaky"]
  • Return shape: a dict with content (a list of blocks such as {"type": "text", ...} or images) and optionally "is_error": True.
  • Errors don't stop the loop. An uncaught exception becomes an error result carrying the raw message. Catching it and returning is_error with a helpful message lets Claude retry sensibly.
  • Annotations are hints, not enforcement. readOnlyHint=True lets Claude run the tool in parallel with other read-only tools; it does not stop your handler writing to disk.
  • Tool search is on by default. Claude first sees a compact list of SDK MCP tool names and loads a full schema when it needs one, which saves context when you have many tools.
  • Python limitation: the @tool decorator forwards only content and is_error, so structuredContent needs a standalone MCP server.

External MCP servers

Any MCP server you met in Part XII works here. Pass it in mcp_servers as a stdio command or a URL:

Connecting the Playwright MCP server (Chapter 102)
options = ClaudeAgentOptions(
    mcp_servers={
        "playwright": {"command": "npx", "args": ["@playwright/mcp@latest", "--headless", "--isolated"]},

    },

strict_mcp_config=True makes the agent use only the servers you pass, ignoring any .mcp.json or user configuration on the machine. For a CI agent that is usually what you want.

110.5Permissions: who decides whether a tool runs

When Claude asks for a tool, Claude Code checks the call in a fixed order. Each step can decide, or pass it on:

1. Hookscan deny; an "allow" doesn't skip deny or ask rules
2. Deny rulesdisallowed_tools and settings; deny wins, even in bypass mode
3. Ask rulesfrom settings; go to your callback
4. Permission modee.g. acceptEdits approves file edits
5. Allow rulesallowed_tools and settings
6. can_use_toolyour callback decides; skipped in dontAsk
ModeBehaviourGood for
defaultNo automatic approvals; anything needing approval that no allow rule covers goes to can_use_tool (or is denied if you have none). New SDK apps start here.Apps with a human approver
dontAskAnything that would prompt is denied instead. Only pre-approved tools and calls that need no approval run.Headless jobs and CI: a hard "no" by default
acceptEditsAuto-approves file edits and simple filesystem commands (mkdir, rm, mv...) inside the working directoriesTrusted edits in a throwaway folder

Two traps from the docs

allowed_tools does not limit bypassPermissions. With allowed_tools=["Read"] and bypass mode, Bash, Write and Edit are still approved. Use disallowed_tools to block. Auto-approved calls never reach can_use_tool. If a tool is in allowed_tools, or the mode approves it, your callback's checks are silently skipped. For a check that must see every call, use a PreToolUse hook.

Asking a human with can_use_tool

The callback receives the tool name, its input and a context object, and returns an allow or deny result. A deny message goes back to Claude so it can adjust.

An approval callback (Python)
from claude_agent_sdk import PermissionResultAllow, PermissionResultDeny

async def ask_human(tool_name, tool_input, context):
    print(f"\nClaude wants to run {tool_name}: {tool_input}")
    if input("Allow? [y/N] ").strip().lower() == "y":
        return PermissionResultAllow()
    return PermissionResultDeny(message="The tester declined this action.")

# options: permission_mode="default", can_use_tool=ask_human,
#          allowed_tools=["Read", "Glob"]   (so only the risky calls reach the human)

This is the approval gate from Chapter 109, built into the framework. A blocking input() is fine for a terminal tool; a web app would show a dialog and wait.

110.6Hooks: your code at every step

A hook is a callback that runs when an event fires (Chapter 82 covers hooks in Claude Code itself). In the SDK it is an async function with three arguments: the event data (tool name, tool input, session id and so on), the tool-use id, and a context object reserved for future use in Python. Return {} to let things proceed, or a decision.

Event (Python SDK)FiresQA use
PreToolUseBefore a tool runs; can deny, allow or change the inputBlock writes outside the report folder; block git push
PostToolUse / PostToolUseFailureAfter a tool returns or failsAudit log; attach extra context
UserPromptSubmitWhen a prompt is submittedAdd today's build number to every prompt
StopWhen the agent stopsSave state, send a summary
SubagentStart / SubagentStopSubagent lifecycleTrack parallel work (Chapter 111)
PreCompact, PermissionRequest, NotificationBefore compaction; on a permission decision; status messagesArchive transcripts; custom approvals; Slack alerts

The TypeScript SDK has many more events (such as SessionStart, SessionEnd, PostToolBatch, TaskCompleted). In Python, SessionStart and SessionEnd exist only as shell hooks in settings files.

A PreToolUse hook that protects .env files (from the docs)
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

async def protect_env_files(input_data, tool_use_id, context):
    file_path = input_data["tool_input"].get("file_path", "")
    if file_path.split("/")[-1].lower() == ".env":
        return {"hookSpecificOutput": {
            "hookEventName": input_data["hook_event_name"],
            "permissionDecision": "deny",
            "permissionDecisionReason": "Cannot modify .env files",
        }}
    return {}

options = ClaudeAgentOptions(
    hooks={"PreToolUse": [HookMatcher(matcher="Write|Edit", hooks=[protect_env_files])]}
)
  • Matchers match tool names only ("Write|Edit", "^mcp__"), not file paths. Check paths inside the hook.
  • Several matching hooks run in parallel, and the most restrictive decision wins: deny beats defer, ask and allow.
  • A crashing guard lets the call through on most events. Set on_failure="block" on the HookMatcher (Python SDK 0.2.177+) so a failing safety hook blocks instead.
  • Hooks don't cover other routes. A Write|Edit hook won't see a file written by Bash. Remove Bash, or use the sandbox, if that matters.
Opinion · this textbook's authors

Treat the permission rules as the lock and hooks as the alarm. Use tools, disallowed_tools and dontAsk to make dangerous actions impossible; use hooks to log everything and to catch the cases rules can't express, such as "writes only under out/". Relying on a prompt that says "please don't delete anything" is neither.

Testing an agent

The model is non-deterministic, but most of your code isn't. Keep parsing, path checks and formatting in plain functions, test them without the model (the lab's --selftest does exactly this), and evaluate the agent's end result separately (Chapter 125).

110.8Lab: a QA triage agent

The agent reads JUnit XML results (the format most test runners, including Playwright, pytest and Maven, can produce), uses a custom tool to parse them exactly, and writes out/triage.md. The design choices are deliberate:

ChoiceWhy
A custom summarise_junit toolCounting tests is a job for code, not a language model. The tool returns exact numbers; Claude does the judgement.
tools=["Read", "Glob", "Write"]No Bash, no Edit, no web: Claude can't see tools it doesn't need
permission_mode="dontAsk"Unattended: anything not pre-approved is refused, never left waiting for a prompt
PreToolUse hook guard_writesWrites are allowed only under out/, so test results can't be "fixed"

qa_agent.py (complete, tested with claude-agent-sdk 0.2.179 and Python 3.11)
"""QA triage agent: reads JUnit XML results and writes a triage summary.

Usage:
  python qa_agent.py --samples    # create two example result files
  python qa_agent.py --selftest   # test the tool and hooks (no API key needed)
  python qa_agent.py              # run the agent (needs ANTHROPIC_API_KEY)
"""
import asyncio
import json
import sys
import time
import xml.etree.ElementTree as ET
from pathlib import Path
from typing import Any

from claude_agent_sdk import (
    AssistantMessage,
    ClaudeAgentOptions,
    HookMatcher,
    ResultMessage,
    TextBlock,
    ToolAnnotations,
    ToolUseBlock,
    create_sdk_mcp_server,
    query,
    tool,
)

PROJECT = Path(__file__).resolve().parent
RESULTS = PROJECT / "results"
OUT = PROJECT / "out"
AUDIT = PROJECT / "audit.jsonl"

SYSTEM = """You are a QA triage assistant.
1. List the JUnit XML files in results/ with Glob.
2. Call summarise_junit once for each file. Do not guess numbers.
3. Write out/triage.md with: a totals table (file, tests, failures, errors, skipped),
   then each failing test with its message and a one-line likely cause,
   then a 'Suggested next steps' list.
Only write inside out/. Never change test results."""


TOTAL_KEY = {"failure": "failures", "error": "errors", "skipped": "skipped"}


def summarise_junit(path: Path) -> dict[str, Any]:
    """Parse a JUnit XML file into totals and a list of failing tests."""
    root = ET.parse(path).getroot()
    suites = [root] if root.tag == "testsuite" else root.findall("testsuite")
    totals = {"tests": 0, "failures": 0, "errors": 0, "skipped": 0}
    failing = []
    for suite in suites:
        for case in suite.findall("testcase"):
            totals["tests"] += 1
            for kind in ("failure", "error", "skipped"):
                node = case.find(kind)
                if node is None:
                    continue
                totals[TOTAL_KEY[kind]] += 1
                if kind != "skipped":
                    failing.append({
                        "test": f"{case.get('classname')}.{case.get('name')}",
                        "kind": kind,
                        "message": (node.get("message") or "").strip()[:300],
                    })
    return {"file": path.name, **totals, "failing": failing}


@tool(
    "summarise_junit",
    "Parse one JUnit XML file from the results/ folder. Returns JSON with totals and failing tests.",
    {"filename": str},
    annotations=ToolAnnotations(readOnlyHint=True),
)
async def summarise_junit_tool(args: dict[str, Any]) -> dict[str, Any]:
    name = Path(args["filename"]).name          # ignore any folders Claude adds
    path = RESULTS / name
    if not path.is_file():
        return {"content": [{"type": "text", "text": f"No file called {name} in results/"}],
                "is_error": True}
    try:
        data = summarise_junit(path)
    except ET.ParseError as exc:
        return {"content": [{"type": "text", "text": f"{name} is not valid XML: {exc}"}],
                "is_error": True}
    return {"content": [{"type": "text", "text": json.dumps(data, indent=2)}]}


qa_server = create_sdk_mcp_server(name="qa", version="1.0.0", tools=[summarise_junit_tool])


async def guard_writes(input_data, tool_use_id, context):
    """PreToolUse hook: block any Write or Edit outside out/."""
    raw = input_data["tool_input"].get("file_path", "")
    target = (PROJECT / raw).resolve()       # relative paths resolve against the project
    if OUT.resolve() not in target.parents:
        return {"hookSpecificOutput": {
            "hookEventName": input_data["hook_event_name"],
            "permissionDecision": "deny",
            "permissionDecisionReason": f"Writes are only allowed inside out/, not {raw}",
        }}
    return {}


async def audit_log(input_data, tool_use_id, context):
    """PostToolUse hook: append one JSON line per tool call."""
    entry = {"time": time.strftime("%Y-%m-%dT%H:%M:%S"),
             "tool": input_data["tool_name"],
             "input": input_data["tool_input"]}
    with AUDIT.open("a", encoding="utf-8") as f:
        f.write(json.dumps(entry) + "\n")
    return {}


def make_options() -> ClaudeAgentOptions:
    return ClaudeAgentOptions(
        cwd=str(PROJECT),
        system_prompt=SYSTEM,
        tools=["Read", "Glob", "Write"],                  # the only built-ins Claude sees
        mcp_servers={"qa": qa_server},
        allowed_tools=["Read", "Glob", "Write", "mcp__qa__summarise_junit"],
        permission_mode="dontAsk",                        # anything else is denied, not asked
        hooks={
            "PreToolUse": [HookMatcher(matcher="Write|Edit", hooks=[guard_writes])],
            "PostToolUse": [HookMatcher(hooks=[audit_log])],
        },
        setting_sources=[],                               # ignore personal settings and CLAUDE.md
        max_turns=15,
        max_budget_usd=0.50,
    )


async def run_agent() -> None:
    OUT.mkdir(exist_ok=True)
    try:
        async for message in query(prompt="Triage the latest test results.", options=make_options()):
            if isinstance(message, AssistantMessage):
                for block in message.content:
                    if isinstance(block, TextBlock):
                        print(block.text)
                    elif isinstance(block, ToolUseBlock):
                        print(f"  -> {block.name} {json.dumps(block.input)[:80]}")
            elif isinstance(message, ResultMessage):
                cost = message.total_cost_usd or 0
                print(f"\nResult: {message.subtype} | error: {message.is_error} | turns: {message.num_turns} | cost: ${cost:.4f}")
    except Exception as exc:                              # query() raises after an error result
        print(f"Run ended with an error: {exc}")

async def selftest() -> None:
    result = await summarise_junit_tool.handler({"filename": "checkout.xml"})
    data = json.loads(result["content"][0]["text"])
    assert (data["tests"], data["failures"], data["errors"], data["skipped"]) == (4, 1, 1, 1), data
    print("tool: checkout.xml ->", {k: data[k] for k in ("tests", "failures", "errors", "skipped")})
    missing = await summarise_junit_tool.handler({"filename": "../secrets.xml"})
    assert missing.get("is_error"), missing
    print("tool: path outside results/ -> error result")
    base = {"hook_event_name": "PreToolUse", "tool_name": "Write"}
    ok = await guard_writes({**base, "tool_input": {"file_path": "out/triage.md"}}, None, None)
    bad = await guard_writes({**base, "tool_input": {"file_path": "results/checkout.xml"}}, None, None)
    assert ok == {} and bad["hookSpecificOutput"]["permissionDecision"] == "deny"
    print("hook: out/triage.md allowed; results/checkout.xml denied")

if __name__ == "__main__":
    if "--samples" in sys.argv:

Troubleshooting

Not logged in · Please run /login then "Run ended with an error": no credentials reached the agent. Set ANTHROPIC_API_KEY in the same shell; the SDK doesn't read .env. (This is exactly what the script printed when this chapter was tested without a key.) ModuleNotFoundError: claude_agent_sdk: the virtual environment isn't active. CLI not found: you got the source package without a bundled binary; install Claude Code natively. error_max_turns or error_max_budget_usd: raise the limit slightly, or tighten the prompt. Claude never calls your tool: check the name in allowed_tools is mcp__qa__summarise_junit, matching the server key "qa".

No API key at work? Steps 1 to 5 still teach the important parts: the tool, the hook and the test. Step 6 can be run later by someone with a key, or with the Bedrock, Google Cloud or Foundry variables from 109.2 if your company uses those.

Common misunderstandings
"The Agent SDK is just the API with a nicer wrapper."
It runs the whole Claude Code agent: built-in tools, permission system, hooks, sessions, compaction. The Client SDK is the thin wrapper.
"allowed_tools is the list of tools Claude can use."
It is the list that runs without asking. Availability is controlled by tools and bare-name disallowed_tools.
"My can_use_tool check protects every call."
Calls approved earlier (allow rules, acceptEdits, bypass) never reach it. Use a PreToolUse hook for checks that must always run.
"I can let customers log in with their Claude subscription."
Not without Anthropic's approval. Products built on the SDK use API keys or a cloud provider.
"The agent ignores my settings files, so it's isolated."
By default it loads user, project and local settings like the CLI. Pass setting_sources=[] for isolation.

Key takeaways
  • The Agent SDK (claude-agent-sdk for Python, @anthropic-ai/claude-agent-sdk for TypeScript) runs Claude Code's agent loop inside your program. It bundles the Claude Code binary.
  • query() streams SystemMessage, AssistantMessage, UserMessage and finally a ResultMessage with the outcome, turns and cost. ClaudeSDKClient keeps a session open for follow-ups.
  • tools controls what exists; allowed_tools controls what runs without asking; deny rules win in every mode.
  • Custom tools are @tool functions in an in-process MCP server, named mcp__server__tool. External MCP servers plug into mcp_servers.
  • Permission order: hooks, deny rules, ask rules, mode, allow rules, can_use_tool. Use dontAsk for unattended jobs.
  • Hooks run your code before and after actions: block, log, or change inputs. Set on_failure="block" on safety hooks.
  • Authenticate with an API key or a cloud provider; set max_turns and max_budget_usd; test the deterministic parts without the model.
Check yourself

You set allowed_tools=["Read"] and permission_mode="bypassPermissions". Can Claude still run Bash?

allowed_tools pre-approves; it doesn't restrict. In bypass mode unlisted tools are approved too, apart from the few actions no mode auto-approves.

You defined a tool parse_report in a server you passed as mcp_servers={"qa": server}. What goes in allowed_tools?

MCP tools are named mcp__{server key}__{tool name}, using the key you gave the server in mcp_servers.

Which setting makes an unattended CI agent refuse anything not pre-approved, rather than wait for a prompt?

dontAsk turns every would-be prompt into a denial, so nothing hangs waiting for a human.

Your security check lives in can_use_tool, but Write is also in allowed_tools. What happens to Write calls?

Auto-approved calls skip can_use_tool. Put checks that must always run in a PreToolUse hook.

You keep ANTHROPIC_API_KEY in a .env file and get "Not logged in". Why?

The docs state the SDK doesn't load .env automatically.

Teach it

"The Agent SDK is Claude Code as a library. You call query() with a prompt and options, and you get a stream of messages while Claude reads files, calls tools and decides when it's done. Our job is the guard rails: tools decides what exists, allowed_tools what runs without asking, dontAsk refuses everything else, and hooks let our own code block or log every action. Exact work like counting test results goes into custom tools we can unit-test; Claude does the judgement. And we always cap turns and budget."
