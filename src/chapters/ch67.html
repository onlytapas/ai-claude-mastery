Claude Code can read files, change files and run commands on your computer. A permission mode decides how much of that it may do without asking you first. Choosing the right mode is like choosing how closely to supervise a new colleague: sometimes you check every step, sometimes you only want a plan first, and sometimes you let them get on with it while an automatic checker watches. And if something goes wrong anyway, checkpoints let you rewind Claude's file edits, much like an "undo" button, though one with important limits.

67.1Why permission modes exist

Every time Claude wants to do something beyond reading (edit a file, run npm test, delete a folder), Claude Code checks whether it's allowed. The answer comes from three things, in this order:

Deny rulesThings that are never allowed, in any mode (Chapter 78)
Allow and ask rulesYour saved "always allow" or "always ask" choices
Permission modeThe general level of freedom for everything else
ResultRun it, ask you, or refuse

The mode is the "default setting" for everything not covered by a specific rule. It's the main dial you'll turn day to day.

In everyday life

Think of a new tester joining your team. On day one, you review every bug they file before it goes to developers. After a month, you let them file bugs directly but still review anything marked "critical". After a year, you trust them with most things, and a team lead spot-checks the risky ones. Permission modes are the same idea: different levels of trust for different situations.

67.2The six modes

Each mode has a config value (what you type in settings or flags) and a label (what you see on screen).

Config valueLabel on screenWhat runs without askingBest for
default (alias manual)ManualReading files only. Everything else asks you first.Learning; sensitive repositories; reviewing every action
acceptEditsAccept editsReading, editing files and common file commands such as mkdir, touch, mv, cpIterating on code you'll review as a diff
planPlanReading (plus commands the auto-mode checker approves, where auto mode is available). File edits are blocked until you approve a plan.Exploring and planning before any change
autoAutoEverything, with a background classifier reviewing actions before they runLong tasks with fewer interruptions
dontAskDon't askReading in the working folders and pre-approved tools only. Anything that would normally ask is refused instead.Locked-down scripts and CI jobs
bypassPermissionsBypass permissionsEverything, with no checksIsolated, throwaway containers or virtual machines only

The status bar at the bottom of the screen always shows the current mode, for example ⏸ manual mode on, ⏵⏵ accept edits on, ⏸ plan mode on, ⏵⏵ auto mode on, ⏵⏵ don't ask on or ⏵⏵ bypass permissions on.

Some things always ask or always stop

Deny rules block in every mode, including bypass. Explicit "ask" rules, and dangerous operations such as deleting critical paths with rm, still prompt you in every mode. Modes loosen the everyday checks; they don't switch off your safety net.

67.3Which mode you start in, and why it's now "auto"

Older guides (including the first version of this book) said Claude Code starts by asking before everything. That changed. Since version 2.1.283, new interactive sessions in the terminal and in VS Code start in auto mode, if auto mode is available to you. Print mode (claude -p) and the Claude Agent SDK still start in default (Manual).

The starting mode is decided in this order:

  1. The --permission-mode flag, if you used one.
  2. permissions.defaultMode in your settings.
  3. The built-in default: auto for interactive sessions, default for claude -p.

If auto mode isn't available (for example, the model doesn't support it, or your organisation has turned it off), the session starts in Manual instead.

Terminal: choosing the starting mode
claude --permission-mode plan          # start in plan mode
claude --permission-mode manual        # start in Manual (same as "default")
claude --permission-mode acceptEdits   # start accepting edits
~/.claude/settings.json: always start in Manual
{
  "permissions": {
    "defaultMode": "default"
  }
}
Where you set it matters

auto and bypassPermissions do not take effect from project or local settings files. To make one of them your default, put it in your user settings (~/.claude/settings.json). This stops a repository you clone from quietly switching your safety level. An organisation can also remove auto mode entirely with the disableAutoMode setting.

67.4Switching modes with Shift+Tab

During a session, press Shift+Tab to move to the next mode. The cycle goes:

Manualdefault
Accept editsacceptEdits
Planplan
Bypassonly if enabled at start
Autolast, when available
  • From auto, the next press goes back to Manual.
  • bypassPermissions only appears in the cycle if you started with --permission-mode bypassPermissions, --dangerously-skip-permissions, --allow-dangerously-skip-permissions, or defaultMode: "bypassPermissions" in user, --settings or managed settings.
  • dontAsk never appears in the cycle. You can only choose it with --permission-mode dontAsk.
  • /plan jumps straight into plan mode, and can take a task: /plan add tests for the coupon rules.

In other surfaces the same modes appear differently: a mode indicator in VS Code, a selector in the desktop app, and a drop-down on claude.ai/code. Cloud sessions offer only Accept edits, Plan and Auto.

67.5Auto mode: how the checker works

In auto mode, Claude doesn't stop to ask you about routine actions. Instead, a separate automatic checker (Anthropic's documentation calls it a background classifier) reviews each action before it runs, and refuses ones it judges risky. You get far fewer interruptions on long tasks, without switching off safety completely.

Claude wants to acte.g. run npx playwright test
Rules firstDeny and ask rules still apply
Classifier reviewAn automatic check judges whether the action looks safe for this task
Run or refuseSafe-looking actions run; risky ones are denied

You can inspect and tune it:

CommandWhat it does
/permissionsManage allow / ask / deny rules, and review actions auto mode denied
/auto-mode-setupDrafts autoMode.environment entries describing your project, and saves them to user settings after you review them
claude auto-mode configPrints the auto-mode configuration currently in effect, as JSON
claude auto-mode defaultsPrints the built-in classifier rules
claude auto-mode critiqueGets AI feedback on your custom auto-mode rules
claude auto-mode resetRemoves the autoMode section from your user settings

In Manual or Accept edits mode, a Bash permission prompt may offer "Yes, and switch to auto mode": a quick way to hand over once you're comfortable with where a task is going.

Limits of auto mode

The classifier is an automated judgement, not a guarantee. It can't know your company's unwritten rules (for example, "never touch the shared staging database"). Write those down as deny rules (Chapter 78), keep secrets out of reach, and still review the diff at the end. For high-stakes repositories, Manual or plan mode is the safer choice.

The old flag that no longer exists

Early versions had a flag called --enable-auto-mode. It was removed in version 2.1.111. The correct way today is --permission-mode auto, or simply nothing at all, since auto is the interactive default. If you find the old flag in a team script or wiki page, update it.

67.6Plan mode in depth

Plan mode is the single most valuable habit for serious work. In plan mode Claude can read and investigate, but it cannot edit files until you approve its plan.

1 · ExploreClaude reads code, tests and docs
2 · PlanIt proposes a step-by-step plan
3 · You reviewCorrect mistakes, add constraints
4 · ApproveChoose how to proceed (for example, with auto or accept edits)
5 · ExecuteClaude carries out the approved plan

When to use plan mode

  • Any change touching more than one or two files.
  • Unfamiliar code or a repository you don't own.
  • Anything where a wrong first step is expensive (database migrations, shared test data, CI configuration).
  • When you're not sure what you want yet. Asking for a plan is a cheap way to think.
Real-world example: a QA plan

You type: "/plan Add Playwright tests for the expired-coupon rules in docs/CHK-412.md. Follow the conventions in CLAUDE.md." Claude reads the story, the existing tests and page objects, then proposes: three test cases, a new fixture for an expired coupon, no changes to src/. You notice it missed "two coupons can't stack", add it, and approve. The tests it then writes match what you actually needed, first time.

The opusplan alias

The model alias opusplan uses Opus in plan mode and Sonnet for execution: a stronger model for thinking, a faster one for doing. Chapter 68 covers models and aliases.

67.7Reading a permission prompt

When Claude needs permission, it shows exactly what it wants to do, for example the full command. You typically choose between allowing it once, allowing it and not being asked again for that kind of action (which saves a rule), or refusing, optionally telling Claude what to do instead.

The prompt showsAsk yourself
A command, e.g. npx playwright test checkoutDo I know what this does? Does it only touch test files and a test environment?
A delete, e.g. rm -rf test-results/Is that folder safe to lose? Is the path exactly right?
A push or deploy, e.g. git pushHave I reviewed the diff? Is this the right branch?
A network call, e.g. curl to an unknown addressWhy is it contacting that site? Could data be leaving my machine?

"Don't ask again" is a good choice for safe, repetitive commands such as running your test suite or linter. It's a poor choice for anything destructive, anything that sends data elsewhere, or anything you don't fully understand. Saved rules can be reviewed and removed later with /permissions. Chapter 78 explains the rule syntax in full.

In everyday life

A permission prompt is a test step with an expected result. A tester would never click "pass" without checking the outcome. Treat "Allow" the same way: read, understand, then approve.

67.8Checkpoints and rewind

Every prompt you send that starts a turn creates a checkpoint of the files Claude edits. If something goes wrong, you can go back.

  • Open the rewind menu with /rewind (aliases /checkpoint and /undo), or press Esc Esc on an empty prompt.
  • Pick the point you want to return to, then choose an action:
ActionWhat happens
Restore code and conversationFiles and the conversation both go back to that point
Restore conversationThe conversation goes back; files stay as they are now
Restore codeFiles go back; the conversation stays
Summarize from here / Summarize up to hereCondense part of the conversation to save context (Chapter 68)
Never mindClose the menu without changing anything

Snapshots are kept for the 100 most recent checkpoints, survive resuming a session, and are cleaned up after about 30 days (controlled by the cleanupPeriodDays setting).

What rewind can't undo
  • Files changed by shell commands are not tracked. If Claude ran a script that rewrote files, or rm deleted something, rewind won't bring it back.
  • Most edits made by subagents aren't restored.
  • Edits made outside Claude Code (by you, your editor or another tool) aren't tracked.
  • Symlinks and hard links are skipped.
  • Anything that left your machine, such as a pushed commit, a Jira comment, an email or a database write through MCP, can't be "rewound" at all.

Checkpoints are a convenience, not a replacement for Git. Commit good states often (Chapter 61).

Why shell commands escape checkpoints

Claude Code takes a snapshot when its own file tools (Edit and Write) change a file, because it knows exactly which file is about to change. A shell command is a black box: npm run generate might touch hundreds of files, a database, or the network. Claude Code can't know in advance what to snapshot, so it doesn't try. This is one more reason to read Bash permission prompts carefully: they're the actions you can't easily undo.

67.9Worktrees: a safe separate copy

When you want Claude to try something risky or work on two things at once, a Git worktree gives it a separate working copy of your repository on its own branch:

Terminal
claude --worktree coupon-tests      # or: claude -w coupon-tests

This creates .claude/worktrees/coupon-tests/ on a branch called worktree-coupon-tests. Your main folder stays untouched. Chapter 69 covers worktrees and parallel work in detail.

Common misunderstandings
"Claude Code always asks before doing anything."
Not any more. Interactive sessions start in auto mode since version 2.1.283, where a classifier reviews actions instead of asking you.
"Auto mode and bypass mode are the same."
Auto mode still checks each action and refuses risky ones. Bypass mode checks nothing and belongs only in isolated containers.
"Rewind undoes everything Claude did."
It restores files changed by Claude's own edit tools. Shell-command changes, external edits and anything sent elsewhere aren't covered.
"Plan mode is slower, so skip it."
A two-minute plan review usually saves far more time than undoing a wrong change.
"Setting auto in the project's settings file will turn it on for everyone."
auto and bypassPermissions are ignored in project and local settings files; they only work from user settings or the command line.

67.11Review

Key takeaways
  • Six modes: default (Manual), acceptEdits, plan, auto, dontAsk and bypassPermissions.
  • Interactive sessions start in auto since v2.1.283; claude -p starts in default.
  • Shift+Tab cycles Manual → Accept edits → Plan → (Bypass) → Auto; dontAsk is never in the cycle.
  • Deny rules work in every mode; auto mode adds a classifier, bypass removes all checks.
  • Plan first for anything significant: explore, plan, review, approve, execute.
  • /rewind or Esc Esc restores Claude's own file edits, but not shell-command changes. Use Git as well.
