Shipping an AI feature is the start, not the end. Unlike ordinary code, an AI feature can get worse without anyone changing a line: users ask new kinds of questions, documents change, or the model you depend on is retired. LLMOps is the set of habits that keeps such features healthy: log every call with its prompt version, model, tokens, cost and outcome; keep prompts in version control; let an evaluation gate in CI block changes that lower quality; watch quality and cost signals in production; plan model migrations before retirement dates; and have a runbook ready for when something goes wrong. None of it needs expensive tools to start. This chapter builds a working version in about 270 lines of Python.

95.1Why AI features need their own operations

LLMOps (large language model operations) applies the ideas of DevOps (automation, monitoring, fast and safe change) to features built on language models. The ideas are familiar to any tester; what changes is what can go wrong.

Same input, same output?Yes, so a passing test stays passingNot guaranteed; answers vary in wording and sometimes in substance

95.2Logging and tracing AI calls

Every call to the model should leave one structured record. "Structured" means fields with names, as JSON, so you can filter and count, rather than free-text log lines.

Log thisWhy
Timestamp, feature name, a trace IDTo find the call and connect it to the user action that caused it
Prompt name and version (or a hash of the prompt text)To know exactly which instructions produced an answer
Requested model and the model in the responseTo confirm what actually ran

Latency in millisecondsUsers notice slow answers before wrong ones

What never to log

API keys or any part of an Authorization header. Personal data such as customer names, emails and account numbers, unless your privacy team has approved where logs go and how long they're kept. Full prompts and answers are very useful for debugging, but they often contain exactly that data. A common pattern is: metadata for every call, full content for a small sample, kept in a restricted store with short retention (Chapter 132).

A shared vocabulary: the OpenTelemetry GenAI conventions

OpenTelemetry (OTel) is an open standard, run by the Cloud Native Computing Foundation, for collecting traces, metrics and logs from software. A trace follows one request through a system; each step inside it is a span, with a start time, a duration and named attributes. OTel's GenAI semantic conventions define standard attribute names for AI calls, so any OTel-compatible tool can understand them. They are still marked Development (not yet stable), so names can change. Verified 9 Nov 2026

AttributeMeaningExample
gen_ai.operation.nameKind of operation (required)chat
gen_ai.provider.nameWho provides the model (required); the Anthropic page says it must be anthropicanthropic
gen_ai.request.model / gen_ai.response.modelModel asked for / model that answeredclaude-haiku-5-5
gen_ai.request.max_tokensThe output cap50
gen_ai.usage.input_tokens / gen_ai.usage.output_tokensTokens used77 / 3
gen_ai.response.finish_reasonsWhy generation stopped (a list)["end_turn"]
gen_ai.response.idThe response's IDmsg_...
gen_ai.prompt.name / gen_ai.prompt.versionNamed prompt template and its version, when you use onetriage / 2

The conventions recommend the span name {operation} {model}, for example chat claude-haiku-5-5.

Under the hood: tracing built into Anthropic's SDKs

Anthropic's documentation describes OpenTelemetry support in two halves, currently in beta. SDK tracing: the official SDKs (Python, TypeScript and others) emit spans from your own process, sent by your application's OpenTelemetry exporter, once you register a tracer provider (for Python, install opentelemetry-sdk). API tracing: an organisation admin adds a destination (an OTLP/HTTP endpoint) in the Claude Console or through the Admin API, and Anthropic's servers send spans for API requests there, with no code change. Both default to metadata only (IDs, timing, status, token counts); exporting full prompts and responses is a separate content mode you switch on deliberately. Because the feature is in beta and its option names may change, follow the current docs page (sources) rather than copying settings from memory. Both halves need a backend that receives OTLP, such as the open-source Jaeger or a commercial observability service your company already uses.

tracing.py
"""Wrap every Claude call: time it, count tokens and cost, log one JSON line.
Attribute names follow the OpenTelemetry GenAI semantic conventions (gen_ai.*)."""
import hashlib
import json
import os
import time
import uuid
from datetime import datetime, timezone
from pathlib import Path

LOG_FILE = os.environ.get("LLM_LOG", "llm_calls.jsonl")
# USD per million tokens (input, output). Verified 9 Nov 2026; check the pricing page.
PRICES = {"claude-opus-5-5": (4.0, 20.0), "claude-sonnet-5-5": (2.0, 10.0),
          "claude-haiku-5-5": (0.10, 0.50), "claude-fable-5-1": (10.0, 50.0)}


def load_prompt(name):
    """Prompts live in files named <name>-v<N>.txt so every change is a new version."""
    text = Path("prompts", f"{name}.txt").read_text(encoding="utf-8")
    return text, hashlib.sha256(text.encode()).hexdigest()[:12]


def cost_usd(model, tokens_in, tokens_out):
    p_in, p_out = PRICES.get(model, (0.0, 0.0))
    return round((tokens_in * p_in + tokens_out * p_out) / 1_000_000, 6)


class FakeClient:
    """Stands in for anthropic.Anthropic() when there is no API key (--fake)."""
    class _Usage:
        def __init__(self, i, o):
            self.input_tokens, self.output_tokens = i, o

    class _Block:
        type = "text"

        def __init__(self, text):
            self.text = text

    class _Msg:
        def __init__(self, model, text, i, o):
            self.id, self.model, self.stop_reason = "msg_fake_" + uuid.uuid4().hex[:8], model, "end_turn"
            self.content, self.usage, self._request_id = [FakeClient._Block(text)], FakeClient._Usage(i, o), "req_fake"

    def __init__(self):
        self.messages = self

    def create(self, model, max_tokens, system, messages):
        text = messages[-1]["content"].lower()
        label = "environment" if "timeout" in text or "502" in text else (
            "flaky" if "retry" in text else "product-bug")
        time.sleep(0.05)
        return FakeClient._Msg(model, label, 60 + len(text) // 4, 3)


def traced_call(client, *, feature, prompt_name, user_text, model, max_tokens=1000):
    system, prompt_hash = load_prompt(prompt_name)
    record = {
        "timestamp": datetime.now(timezone.utc).isoformat(timespec="seconds"),
        "trace_id": uuid.uuid4().hex,
        "feature": feature,
        "prompt.name": prompt_name,
        "prompt.sha256": prompt_hash,
        "gen_ai.operation.name": "chat",
        "gen_ai.provider.name": "anthropic",
        "gen_ai.request.model": model,
        "gen_ai.request.max_tokens": max_tokens,
    }
    start = time.perf_counter()
    try:
        msg = client.messages.create(model=model, max_tokens=max_tokens, system=system,
                                     messages=[{"role": "user", "content": user_text}])
        text = "".join(b.text for b in msg.content if b.type == "text")
        record.update({
            "status": "ok",
            "gen_ai.response.id": msg.id,
            "gen_ai.response.model": msg.model,
            "gen_ai.response.finish_reasons": [msg.stop_reason],
            "gen_ai.usage.input_tokens": msg.usage.input_tokens,
            "gen_ai.usage.output_tokens": msg.usage.output_tokens,
            "request_id": getattr(msg, "_request_id", None),
            "cost_usd": cost_usd(model, msg.usage.input_tokens, msg.usage.output_tokens),
            "output_preview": text[:80],      # keep previews short; never log secrets or personal data
        })
        return text
    except Exception as e:                    # log the failure, then let the caller handle it
        record.update({"status": "error", "error.type": type(e).__name__})
        raise
    finally:
        record["latency_ms"] = round((time.perf_counter() - start) * 1000)
        with open(LOG_FILE, "a", encoding="utf-8") as f:
            f.write(json.dumps(record) + "\n")

Three design choices worth copying. The record is written in a finally block, so failed calls are logged too, with their error type, before the error continues to the caller. The prompt is loaded from a file and its SHA-256 hash is logged, so even an unnoticed one-word edit shows up as a new hash. And the output preview is cut to 80 characters, enough to eyeball, too short to hold much sensitive data.

import sys
from collections import Counter, defaultdict

    sys.exit("No calls logged yet.")


def pct(values, q):
    values = sorted(values)
    return values[min(len(values) - 1, int(q * len(values)))]


by_feature = defaultdict(list)
for r in rows:
    by_feature[r["feature"]].append(r)

print(f"{len(rows)} calls in {path}\n")

    cost = sum(r.get("cost_usd", 0) for r in rs)

for model in {r["gen_ai.request.model"] for r in rows}:

95.4Versioning prompts and models

A prompt is code. It changes behaviour, so it needs the same care: version control, review and a record of what was live when.

  • Prompts live in files in git, not pasted inside functions or edited in a web console. A pull request that changes a prompt gets reviewed like any other change.
  • Every prompt has a name and version (triage-v2), and every call logs it, plus a hash of the exact text. When someone reports a bad answer, you know which prompt produced it.
  • Pin the model ID. From the 4.6 generation onwards, Claude model IDs such as claude-opus-5-5 are pinned snapshots with no date suffix: the model behind that ID doesn't silently change. Put the ID in configuration, not scattered through code, so a migration is a one-line change that goes through the gate.
  • Pin the API version and SDK version. The anthropic-version header (currently 2026-10-21) and your SDK version both change behaviour; the 2026-10-21 version, for example, removed temperature (Chapter 86). Upgrade them on purpose, not by accident.
  • Keep a short change log: date, what changed (prompt, model, retrieval, documents), eval score before and after, who approved.
Versioning the data too

For RAG features (Chapter 93), the document index is part of the behaviour. Log which index build answered a question (a build date or ID), and re-run the eval after re-indexing, just as after a prompt change.

95.5Evaluation gates in CI

An eval gate is a CI step that runs your evaluation and fails the build if scores drop below the last approved baseline by more than an agreed margin. It's the AI version of "no merge with failing tests". The baseline is a small JSON file in git, updated only when a reviewer approves a new level.

eval_triage.py
"""Usage: python eval_triage.py --out candidate.json [--fake] [--model M] [--prompt triage-v2]
Runs the labelled failures through the triage prompt and writes scores for gate.py."""
import argparse
import json
import tracing

LABELS = {"product-bug", "test-bug", "environment", "flaky"}

p = argparse.ArgumentParser()
p.add_argument("--out", required=True)
p.add_argument("--fake", action="store_true")
p.add_argument("--model", default="claude-haiku-5-5")
p.add_argument("--prompt", default="triage-v2")
args = p.parse_args()

if args.fake:
    client = tracing.FakeClient()
else:
    import anthropic
    client = anthropic.Anthropic()

cases = json.load(open("eval/triage_cases.json", encoding="utf-8"))
correct = valid = flaky_total = flaky_found = 0
for c in cases:
    label = tracing.traced_call(client, feature="eval-triage", prompt_name=args.prompt,
                                user_text=c["failure"], model=args.model, max_tokens=50).strip()
    correct += label == c["label"]
    valid += label in LABELS
    if c["label"] == "flaky":
        flaky_total += 1
        flaky_found += label == "flaky"
    print(f"{'ok  ' if label == c['label'] else 'MISS'} expected {c['label']:<12} got {label}")

scores = {"label_accuracy": round(correct / len(cases), 2),
          "valid_label_rate": round(valid / len(cases), 2),
          "flaky_recall": round(flaky_found / flaky_total, 2)}
with open(args.out, "w", encoding="utf-8") as f:
    json.dump({"label": f"{args.prompt} on {args.model}", "scores": scores}, f, indent=1)
print(scores, "->", args.out)
gate.py
"""Usage: python gate.py baseline.json candidate.json [--max-drop 0.02]
CI eval gate: fail the build if the candidate's eval score drops too far."""
import argparse
import json
import sys

p = argparse.ArgumentParser()
p.add_argument("baseline")
p.add_argument("candidate")
p.add_argument("--max-drop", type=float, default=0.02, help="allowed drop, e.g. 0.02 = 2 points")
args = p.parse_args()

base = json.load(open(args.baseline))
cand = json.load(open(args.candidate))
failed = False
for metric, old in base["scores"].items():
    new = cand["scores"].get(metric)
    if new is None:
        print(f"FAIL {metric}: missing from candidate")
        failed = True
        continue
    drop = old - new
    status = "FAIL" if drop > args.max_drop else "ok  "
    failed |= drop > args.max_drop
    print(f"{status} {metric:<22} {old:.2f} -> {new:.2f}")
print(f"\n{base['label']} -> {cand['label']}: {'BLOCKED' if failed else 'PASSED'}")
sys.exit(1 if failed else 0)

The CI workflow

This GitHub Actions workflow runs on every pull request. The offline job costs nothing: unit tests, then the eval harness with the fake client, which catches code changes that break the evaluation itself. The live-eval job calls Claude, so it runs only when a reviewer adds the label run-live-eval, typically on pull requests that touch prompts or the model ID. Its baseline, baseline-live.json, is the scores file from the first live run your team approved; commit it before enabling the job.

      - run: python gate.py baseline-live.json candidate.json

        with:
          name: eval-results

            candidate.json

CI secrets and cost

Store the key as an encrypted repository secret, never in the workflow file (Chapter 98). Use a separate API key and workspace for CI with its own spend limit, so a loop in a pull request can't use the production budget. GitHub doesn't pass repository secrets to workflows triggered from forks, which is a sensible default to keep.

Opinion · this textbook's authors

A gate with a 2-point margin on 8 cases is a teaching example: one case is 12.5 points. Real gates need enough cases that one unlucky answer doesn't block a good change (often 50 to a few hundred per feature), and some teams run each case more than once because answers vary. Decide the margin with the product owner, not alone.

95.6Monitoring quality drift and cost

Quality drift means the feature's real-world quality changes over time even though its code doesn't. Typical causes: users start asking about a new product area; the documents behind a RAG feature go stale; a new team writes stories in a different style; or you migrated models and some behaviour shifted. You can't catch drift with pre-release evals alone, because the inputs are what changed.

95.7Handling model deprecations

Anthropic retires older models on a published schedule. Its documentation defines four states: Active (fully supported and recommended), Legacy (no longer receives updates and might be deprecated in future), Deprecated (still works but not recommended; a replacement and a retirement date are given) and Retired (no longer available; requests fail). For publicly released models, Anthropic gives customers with active deployments at least 60 days' notice before retirement, by email and in the documentation. Verified 9 Nov 2026

Real-world example: why "just change the ID" fails

A team moving from an older model to Claude Opus 5.5 changes one line and deploys. The calls fail with 400 errors: their code sent temperature, which API version 2026-10-21 rejects, and it forced a tool call with tool_choice, which Opus 5.5 rejects. Their eval gate would have caught both in CI. Also, Opus 5.5's default effort is medium, so set effort explicitly and re-measure cost and quality rather than assuming they carry over.

The script in 95.3 includes a RETIRING table so the daily report warns when logged traffic still uses a retiring model. Keep it updated from the deprecations page.

95.8Incident management for AI features

An incident is anything that harms users or the business and needs a coordinated response. AI features add new kinds:

Incident typeExampleFirst move
Provider outage or overloadMany 529 overloaded_error or 500 responsesCheck status.claude.com; switch the feature to its fallback (hide the button, queue requests, show "try later")
Rate or spend limit429 errors, or the monthly cap reachedReduce traffic (pause batch jobs); request a limit increase; review what caused the spike
Quality regressionWrong answers reported after a prompt changeRoll back to the previous prompt version; add the failing cases to the eval
Harmful or embarrassing outputAn answer with confidential data, or offensive content, shown to a customerKill switch; preserve logs; involve security, legal or communications as your process requires
Prompt injection exploitedA document or ticket makes the feature leak data or take an unintended actionKill switch; remove the content; review tool permissions (Chapter 131)
Cost runawayA retry loop or a huge input multiplies spendKill switch or lower spend limit; fix the loop; add a per-request token cap
Retired modelAll calls fail with errors after a retirement dateSwitch to the replacement already tested (95.7); this one should never happen

Two controls make every incident above easier. A kill switch: a feature flag that turns the AI feature off (or to a non-AI fallback) in seconds without a deploy. And a graceful fallback: what users see when the AI part is off, such as the plain search results without a generated answer, or a message that the assistant is unavailable.

Learn from it

After every AI incident, add the triggering input to the eval set. That turns each incident into a permanent regression test (regression testing), and over time the eval set fills with exactly the cases that matter.

A runbook is a short, practical document that tells whoever is on call what to do, step by step, without needing to know the system's history. Write it before you need it. Here is a template for one AI feature; copy it into your wiki or repository and fill in every bracket.

Common misunderstandings
"If nobody changes the code, the AI feature can't get worse."
Inputs, documents and user behaviour change. Monitor quality in production, not just before release.
"Log everything, including full prompts, forever."
Prompts often contain personal or confidential data. Log metadata always, content only in samples, with access control and retention limits.
"Our model ID never changes, so we never need to migrate."
Pinned IDs don't change behaviour, but they are retired. Track the deprecations page and test the replacement early.
"An eval gate replaces human review."
It catches measured regressions. Sampled human review catches what your metrics don't measure.
"We need an observability platform before we start."
A JSON-lines log and a 40-line report give you most of the value on day one. Adopt OpenTelemetry tooling as you grow.

95.10Review

Key takeaways
  • AI features fail quietly and change without code changes, so they need logging, evals and monitoring designed for that.
  • Log one structured record per call: feature, prompt version and hash, model, tokens, cost, latency, stop reason, status, request ID. Never log keys; treat content as sensitive.
  • The OpenTelemetry GenAI conventions (gen_ai.*) give standard names; they're still in Development, and Anthropic's SDK and API tracing are in beta.
  • Prompts are code: in git, versioned, reviewed. Pin model, API version and SDK version.
  • An eval gate in CI compares each metric with an approved baseline and blocks regressions; run paid live evals only when needed.
  • Anthropic gives at least 60 days' notice before retiring a public model; find usage with the Console's Usage export and migrate through the gate.
  • Have a kill switch, a fallback and a runbook before the first incident; turn every incident into an eval case.
Check yourself

Why does the logger record a hash of the prompt text as well as its name?

Names depend on people remembering to bump them. The hash changes with every byte of the text.

Which OpenTelemetry GenAI attribute holds the number of tokens the model produced?

gen_ai.request.max_tokens is the cap you asked for; gen_ai.usage.output_tokens is what was actually used.

The gate reports label_accuracy 0.88 → 0.75 and the other metrics unchanged. What happens in CI?

The gate checks each metric separately, so a large drop in one can't hide behind the others.

How much notice does Anthropic commit to before retiring a publicly released model?

Per Anthropic's model deprecations page: at least 60 days' notice, by email and in the documentation.

Customers report confidential data appearing in your AI assistant's answers. What is the first action?

Stop the harm first, keep the evidence, then investigate. Fixes come after containment.
