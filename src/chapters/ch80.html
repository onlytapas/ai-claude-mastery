A skill is a folder containing a SKILL.md file: a short header saying what the skill is for, followed by instructions in plain Markdown. Claude Code always knows each skill's name and description, but only loads the full instructions when the skill is used, either because you typed /skill-name or because Claude decided your request matched the description. A skill can also carry reference files and scripts. Skills are how you turn "the instructions I keep pasting" into a reusable, shareable team tool, and they replaced the older custom slash commands, which still work.

80.1What a skill is, and when to write one

Anthropic's guidance is direct: create a skill when you keep pasting the same instructions, checklist or multi-step procedure into chat, or when a section of CLAUDE.md has grown into a procedure rather than a fact. The key difference from CLAUDE.md is when it costs you. CLAUDE.md loads into every session in full. A skill's body loads only when it's used, so a long checklist costs almost nothing until you need it.

In everyday life

A kitchen. CLAUDE.md is the notice on the wall that every cook reads at the start of every shift ("allergens are labelled in red"). Skills are the recipe cards in the drawer: the head chef knows the title of every card, but only pulls out "Hollandaise" when someone orders eggs Benedict. You can also hand a cook a card directly: "make this one now".

You want…UseChapter
Facts and conventions that apply to every taskCLAUDE.md77
A reusable procedure or body of knowledge, loaded on demandSkillthis one
A separate worker with its own context and tool limitsSubagent81
Something that must happen every time, guaranteedHook82
A connection to an outside system (Jira, a browser, a database)MCP server83

Claude Code skills follow the Agent Skills open standard (agentskills.io), so a skill that sticks to the standard's fields also works in other tools that support it. Claude Code adds extras on top, such as invocation control, running in a subagent and live context injection.

80.2Your first skill in five minutes

A skill is a folder with one required file. The folder name becomes the command:

Terminal
mkdir -p ~/.claude/skills/summarize-changes
~/.claude/skills/summarize-changes/SKILL.md (from Anthropic's documentation)
---
description: Summarizes uncommitted changes and flags anything risky. Use when the user asks what changed, wants a commit message, or asks to review their diff.
---

## Current changes

!`git diff HEAD`

## Instructions

Summarize the changes above in two or three bullet points, then list any risks you notice such as missing error handling, hardcoded values, or tests that need updating. If the diff is empty, say there are no uncommitted changes.

Two parts: frontmatter (YAML settings between two --- lines, which must be the very first line of the file) and the body (Markdown instructions). The line !`git diff HEAD` is dynamic context injection: Claude Code runs that command and pastes its output in before Claude reads the skill, so Claude works from your real diff.

Test it in any git project with an uncommitted change, either by asking "What did I change?" (Claude matches the description and loads the skill) or by typing /summarize-changes. No restart is needed: Claude Code watches skill folders and picks up new and edited skills during the session. If you created a new top-level skills folder mid-session, run /reload-skills once.

80.3Where skills live and how they're named

  • Name clashes: enterprise beats personal, which beats project. A skill beats a same-named file in .claude/commands/.
  • Command name: the frontmatter name if set, otherwise the folder name. .claude/skills/deploy-staging/SKILL.md gives /deploy-staging.
  • Reserved names: don't call a skill folder synced or anthropic-skills; Claude Code uses those for skills synced from your claude.ai account.
  • Seeing them: /skills lists every skill (press t to sort by token cost). /skill-doctor reports what each skill costs in context and how often it's used.

80.4The frontmatter, field by field

Every field is optional; description is the one Anthropic recommends always setting. Field names must match exactly, hyphens included: Claude Code silently ignores fields it doesn't recognise, so a typo fails quietly.

Portability

If you plan to upload a skill to claude.ai or use it through the API, stick to the six standard fields: name, description, license, compatibility, metadata and allowed-tools. Those paths reject other fields with an "Unexpected key(s)" error, and dynamic context injection only works in Claude Code.

80.5How invocation works

FrontmatterYou can invokeClaude can invokeWhat sits in context
(default)YesYesDescription always; full skill when invoked
disable-model-invocation: trueYesNoNothing until you invoke it
user-invocable: falseNoYesDescription always; full skill when invoked
Session startNames and descriptions of all skills enter the listing
TriggerYou type /name, or your request matches a description
RenderArguments substituted; !`…` commands run and their output is pasted in
LoadThe rendered skill enters the conversation as one message and stays there

Some details that matter in practice:

  • Position matters. /deploy staging at the start of your message runs the skill. "go ahead and /deploy to staging" mid-sentence only permits Claude to run it.
  • Stacking. At the terminal prompt, /write-tests /fix-issue 123 loads both skills, each receiving 123.
  • It isn't re-read. Claude Code doesn't re-read SKILL.md on later turns, so write standing instructions ("run the tests after every edit") rather than one-off steps.
  • Compaction. When a long conversation is summarised, Claude Code re-attaches the first 5,000 tokens of each recently invoked skill, within a combined 25,000-token budget. Put the most important instructions at the top.
  • Too many skills. The listing has a budget (1% of the context window by default). With many skills, descriptions of the least-used ones get dropped, and Claude stops matching them.

Controlling skills from settings

Skills are invoked through a tool called Skill, so permission rules (Chapter 78) apply: Skill(deploy *) in deny blocks the deploy skill; a bare Skill deny switches all skills off. The skillOverrides setting changes visibility without editing the skill, which is handy for skills committed by someone else:

.claude/settings.local.json
{
  "skillOverrides": {
    "legacy-context": "name-only",
    "deploy": "off"
  }
}

The four values are "on", "name-only", "user-invocable-only" and "off". In /skills, Space cycles them and Esc saves to .claude/settings.local.json. Plugin skills aren't affected.

Review skills in repositories you clone

A project skill's allowed-tools is applied even in a folder you haven't trusted, including in -p runs. A skill can grant itself broad tool access, so read the allowed-tools lines of a repository's skills before running Claude Code there.

80.6Arguments, supporting files and scripts

Arguments

PlaceholderBecomes

$ARGUMENTS[0] or $0The first argument (0-based). Quote multi-word values: /skill "hello world" second.
$nameA named argument declared in arguments.
${CLAUDE_SKILL_DIR}The skill's own folder: use it to point at bundled scripts.
${CLAUDE_PROJECT_DIR}The project root.
${CLAUDE_SESSION_ID}, ${CLAUDE_EFFORT}The session ID and current effort level.

Supporting files

A skill folder
my-skill/
├── SKILL.md        # required: overview and navigation
├── reference.md    # loaded only when SKILL.md points Claude to it
├── examples.md
└── scripts/
    └── helper.py   # executed, not loaded into context

Keep SKILL.md under 500 lines and link to the other files ("for field rules, see reference.md"). Claude opens them only when needed, so detail costs nothing until used. Scripts are even cheaper: Claude runs them and sees only their output.

Live context and its permission rule

A line starting with !`command` (or a fenced block opened with ```! for several commands) runs before Claude sees the skill. Two rules to remember: if the command fails, the whole invocation is aborted; and outside auto mode, the command must be allowed by your rules (read-only commands are) or listed in allowed-tools, otherwise the invocation aborts with a permission-check error rather than prompting. Administrators can switch injection off with "disableSkillShellExecution": true.

80.7Custom commands: .claude/commands/

Before skills, Claude Code had custom slash commands: single Markdown files in .claude/commands/ (project) or ~/.claude/commands/ (personal). They have now been merged into skills. In the documentation's words, a file at .claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both create /deploy and work the same way.

Command file

One Markdown file. Accepts the same frontmatter except name and paths. Subfolders become namespaces: .claude/commands/frontend/component.md is /frontend:component. Still fully supported.

Skill folder

A folder, so it can hold reference files and scripts. Can be loaded automatically by Claude. Preferred for new work.

To migrate a command, make a folder named after it, move the file in as SKILL.md, and add a good description.

80.8Three QA skills, end to end

All three go in a project's .claude/skills/ so the team shares them through git.

Skill 1: /bug-report, a task you trigger

It writes a consistent bug report from your rough notes. It has side effects on your team's process, so only you can invoke it. It pulls the current branch and working-tree status in automatically.

.claude/skills/bug-report/SKILL.md
---
name: bug-report
description: Turn rough tester notes into a complete bug report in the team format.
argument-hint: [rough notes about the bug]
disable-model-invocation: true
allowed-tools: Bash(git branch --show-current) Bash(git status --short)
---

## Context
Branch: !`git branch --show-current`
Working tree:
!`git status --short`

## Task
Write a bug report from these notes: $ARGUMENTS

Use the exact structure in [template.md](template.md). Rules:
- Steps to reproduce are numbered, start from a clean state, and contain one action each.
- Expected and Actual are separate and factual. No guesses about the cause in Actual.
- If the notes don't say the environment, browser or test data, list them under "Questions for the reporter" instead of inventing them.
- Suggest a severity (Blocker, Critical, Major, Minor, Trivial) with a one-line reason.
- Save the report to bug-reports/ with a short kebab-case file name, then show it.
.claude/skills/bug-report/template.md
# [Short title: what is wrong, where]

**Severity (suggested):** … — reason
**Environment:** app version, environment, browser/device, test account
**Branch:** …

## Steps to reproduce
1. …

## Expected result
…

## Actual result
…

## Evidence
Screenshots, logs, console errors, request IDs.

## Questions for the reporter
- …

Use it: /bug-report discount code SAVE10 gives 0 off on checkout in staging chrome, worked yesterday.

Skill 2: test-case-designer, knowledge Claude applies on its own

This one Claude should load whenever someone asks for test cases, so the description carries the trigger words. The detailed technique guide sits in a supporting file.

.claude/skills/test-case-designer/SKILL.md
---
name: test-case-designer
description: Designs test cases from a user story, Jira ticket or acceptance criteria using the team's conventions. Use when the user asks for test cases, test scenarios, a test plan for a story, or edge cases.
when_to_use: Trigger phrases include write test cases for, what should we test, edge cases for this story, and turn these acceptance criteria into tests.
---

When designing test cases:
1. Restate the requirement in one sentence and list any ambiguities first. Do not invent answers to them.
2. Apply the techniques in [techniques.md](techniques.md): equivalence partitions, boundary values, state transitions and negative cases.
3. Output a Markdown table with columns: ID, Title, Preconditions, Steps, Expected result, Priority (P1-P3), Technique.
4. IDs use the story key if given (e.g. SHOP-142-TC01), otherwise TC01, TC02.
5. Every acceptance criterion must be covered by at least one P1 case. End with a coverage line: criterion to case IDs.
6. Mark any case that needs test data the team doesn't have as "DATA NEEDED".
.claude/skills/test-case-designer/techniques.md
# Test design techniques (team guide)

## Equivalence partitions
Split each input into groups the system should treat the same. One case per group.
Example: quantity 1-10 valid; 0 and negative invalid; 11+ invalid; non-numeric invalid.

## Boundary values
Test at, just below and just above each edge: 0, 1, 10, 11.

## State transitions
For anything with a status (order, account, ticket), list allowed and forbidden moves.
Test at least one forbidden move.

## Negative and abuse cases
Empty, very long, special characters, wrong type, duplicate submit, expired session,
missing permissions.

Use it: just ask "What should we test for SHOP-142: users can apply one discount code per order?" and watch for Claude loading test-case-designer.

Skill 3: /junit-summary, a skill with a bundled script

Reading a big JUnit XML file is a waste of tokens. A small script does the counting; Claude only sees the summary and then does what it's good at: explaining likely causes and next steps. allowed-tools pre-approves exactly that script, using ${CLAUDE_SKILL_DIR} so the path is right wherever the skill is installed.

.claude/skills/junit-summary/SKILL.md
---
name: junit-summary
description: Summarise a JUnit XML test report and triage the failures. Use when the user shares or mentions a JUnit, Playwright or pytest XML report, or asks why the test run failed.
argument-hint: [path/to/report.xml]
allowed-tools: Bash(python3 ${CLAUDE_SKILL_DIR}/scripts/summarise_junit.py *)
---

1. Run `python3 ${CLAUDE_SKILL_DIR}/scripts/summarise_junit.py $ARGUMENTS`.
   If no path was given, look for *.xml under test-results/ or reports/ and ask which one.
2. Do not open the XML file itself unless the summary is not enough.
3. Report: the totals line, then a table of failures with columns Test, Error, Likely category
   (product bug, test bug, environment, flaky/timing, data), Next step.
4. Call out the slowest tests if any take more than 3 seconds.
5. Never mark a failure as flaky without evidence such as a timeout or a pass on retry.
.claude/skills/junit-summary/scripts/summarise_junit.py
#!/usr/bin/env python3
"""Summarise a JUnit XML report: totals, failures and slowest tests."""
import sys
import xml.etree.ElementTree as ET


def main() -> int:
    if len(sys.argv) != 2:
        print("usage: summarise_junit.py <report.xml>")
        return 2
    try:
        root = ET.parse(sys.argv[1]).getroot()
    except (OSError, ET.ParseError) as err:
        print(f"Could not read report: {err}")
        return 2

    cases = list(root.iter("testcase"))
    failed, skipped, timings = [], 0, []
    for case in cases:
        name = f'{case.get("classname", "")}::{case.get("name", "")}'
        timings.append((float(case.get("time", 0) or 0), name))
        problem = case.find("failure")
        if problem is None:
            problem = case.find("error")
        if problem is not None:
            message = (problem.get("message") or problem.text or "").strip()
            failed.append((name, message.splitlines()[0][:160] if message else ""))
        elif case.find("skipped") is not None:
            skipped += 1

    passed = len(cases) - len(failed) - skipped
    print(f"TOTAL {len(cases)} | PASSED {passed} | FAILED {len(failed)} | SKIPPED {skipped}")
    for name, message in failed:
        print(f"FAIL {name} -- {message}")
    print("SLOWEST:")
    for seconds, name in sorted(timings, reverse=True)[:3]:
        print(f"  {seconds:.2f}s {name}")
    return 0


if __name__ == "__main__":
    sys.exit(main())

Under the hood: why scripts beat instructions for counting

Language models are good at judgement and poor at exact bookkeeping over thousands of lines. If Claude reads a 5 MB XML report, it spends a large share of its context window on angle brackets and may still miscount. A script is deterministic, fast and essentially free in tokens: only its few lines of output enter the conversation. The pattern generalises: let code do what code does reliably (parsing, counting, validating) and let Claude do what needs reading and reasoning (categorising failures, suggesting next steps). The script uses only Python's standard library, and returns exit code 2 with a clear message if the file is missing or malformed.

80.9Testing a skill: does it trigger, and does it help?

Seeing a skill run tells you Claude found it, not that it did what you meant. Anthropic's documented method checks two things separately: does Claude invoke it on the prompts it should (and not on others), and is the output better than without it?

Collect5–10 realistic prompts, plus a few that should not trigger it
WithRun each in a fresh session with the skill on
WithoutRun again with it set to "off" in skillOverrides
CompareTrigger rate, output quality, tokens and time

Fresh sessions matter: leftover context from writing the skill hides gaps in the written instructions.

Automating it with skill-creator

Anthropic's skill-creator plugin runs that loop for you inside Claude Code. Install it at the Claude Code prompt:

Claude Code prompt
/plugin install skill-creator@claude-plugins-official

If the marketplace isn't found, add it first with /plugin marketplace add anthropics/claude-plugins-official. Then ask, for example, "evaluate my junit-summary skill with skill-creator". It stores test cases in evals/evals.json inside the skill folder, runs each case in a clean subagent, grades assertions into grading.json, compares with-skill and without-skill results in benchmark.json, can A/B two versions of the skill, proposes description edits when the skill triggers on the wrong requests, and opens an HTML review page. Skill-creator can also help you write a new skill from a conversation. For skills shipped in a plugin, claude plugin eval is the CI-friendly alternative (Chapter 84).

Common misunderstandings
"Skills load into every session, like CLAUDE.md."
Only the name and description do. The body loads when the skill is invoked.
"Custom commands are deprecated and will stop working."
They've been merged into skills and still work; skills are simply preferred for new work.
"allowed-tools restricts the skill to those tools."
It pre-approves them for one turn. Other tools stay available under your normal permissions; use disallowed-tools to remove tools.
"If the skill ran once, it works."
Test triggering and output quality separately, in fresh sessions, against a no-skill baseline.
"A long, detailed SKILL.md is best."
Once loaded, every line costs tokens on every turn. Keep the body short and move detail into supporting files and scripts.

80.10Review

Key takeaways
  • A skill is a folder with SKILL.md: YAML frontmatter plus Markdown instructions. Personal skills go in ~/.claude/skills/, team skills in .claude/skills/.
  • Descriptions are always in context; bodies load on demand. Write descriptions with the words people actually use.
  • disable-model-invocation: true = only you; user-invocable: false = only Claude.
  • $ARGUMENTS, $0 and ${CLAUDE_SKILL_DIR} make skills reusable; supporting files and scripts keep them cheap.
  • .claude/commands/ files still work and behave like skills; prefer skills for new work.
  • Prove value with a with/without comparison; skill-creator automates it.
Check yourself

Which part of a skill is in Claude's context in every session, before anyone uses it?

Only the listing is always present. The body loads on invocation, and supporting files only when Claude opens them.

You write a /deploy-staging skill. Claude must never run it on its own. Which field?

user-invocable: false does the opposite: it hides the skill from you and leaves it to Claude.

What happens to .claude/commands/smoke.md?

Custom commands were merged into skills and keep working; skills add folders for supporting files and automatic loading.

Your skill lists allowed-tools: Bash(npm test *). What does that do?

It's a temporary pre-approval for the invoking turn; it neither restricts other tools nor writes to settings.

Why does the junit-summary skill use a Python script instead of asking Claude to read the XML?

Deterministic work goes in code; reasoning about causes stays with Claude.

Assignment

Pick the instruction you paste into Claude most often at work, such as your regression checklist, your API test conventions or your release-readiness questions. Turn it into a project skill with a strong description, at least one supporting file and, if any part is mechanical, a script. Write five prompts that should trigger it and three that shouldn't. Run the with/without comparison (by hand or with skill-creator) and share the results with your team alongside a pull request adding the skill.
