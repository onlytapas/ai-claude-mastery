127.1From tool user to toolmaker

Most people use AI one conversation at a time. They type a good prompt, get a good result, and next week they type it again. Everyone on the team writes their own slightly different version, and the quality depends on who wrote it.

A toolmaker notices the repetition and captures it once. The prompt becomes a skill anyone can call. The review checklist becomes a subagent. The "don't forget to run the test" reminder becomes a hook that never forgets. That's how one person's good habit becomes the whole team's standard.

In everyday life

A carpenter who cuts the same shape fifty times doesn't measure fifty times. They build a jig: a simple guide that makes every cut identical, so even an apprentice gets it right. The tools in this chapter are jigs for QA work. They make good practice the easy, default path.

Real-world example

A test lead notices that bug reports from five testers come in five different formats, and developers keep asking for the build number. Writing one /bug-report skill takes half an hour with Claude Code's help. From then on, every report has the same sections, and the skill asks for the build number instead of guessing it.

127.3Tool 1: a team skills pack

A skill is a folder containing a SKILL.md file: a short block of settings (the "frontmatter", between --- lines) followed by plain instructions. Put project skills in .claude/skills/<name>/SKILL.md and commit them; everyone who clones the repository gets them. You run a skill by typing /name, and Claude can also load it on its own when your request matches its description.

.claude/skills/bug-report/SKILL.md
---
name: bug-report
description: Write a bug report in the team's Jira format. Use when the user describes a defect, a failing test or broken behaviour, or asks for a bug report.
argument-hint: "[short description of the problem]"
---

Write a bug report for: $ARGUMENTS

Use exactly these sections:
1. **Title**: [Area] what is wrong, in under 12 words
2. **Environment**: build, browser, OS, test account
3. **Steps to reproduce**: numbered, one action per step
4. **Expected result** and **Actual result**
5. **Severity** (S1–S4) with a one-line reason
6. **Evidence**: screenshots, log lines or test output provided

Ask for any missing environment details before finishing. Never guess a build number.
  • description is what Claude reads to decide when the skill applies, so it says both what it does and when to use it, in the words people actually type.
  • argument-hint is the grey hint shown after /bug-report in the menu.
  • $ARGUMENTS is replaced by whatever you type after the command.
.claude/skills/test-plan/SKILL.md
---
name: test-plan
description: Draft a test plan for a feature or user story, with risks, scope and test cases. Use when the user asks for a test plan or test cases for a story.
argument-hint: "[story key or feature name]"
---

Create a test plan for $ARGUMENTS.

1. List ambiguous or missing acceptance criteria as questions first.
2. Rank the main risks (likelihood and impact).
3. Write test cases as a table: ID, Title, Preconditions, Steps, Expected, Priority (P1–P3).
   Cover positive, negative, boundary, accessibility and error-handling cases.
4. Mark which cases should be automated, and why.

The third skill uses a powerful feature: a line written as !`command` runs that shell command before Claude sees the skill, and pastes its output in. So the skill arrives already knowing what changed.

.claude/skills/risk-review/SKILL.md
---
name: risk-review
description: Review the current branch's changes for test risk and suggest what to test. Use before testing a pull request or deciding regression scope.
disable-model-invocation: true
---

## Changed files on this branch
!`git diff --stat origin/main...HEAD`

Using the changes above:
1. Group the changed files by product area.
2. For each area, say what could break and how likely it is.
3. List the existing test suites that cover these areas, and the gaps.
4. Recommend a regression scope: must-run, should-run and safe-to-skip.
  • disable-model-invocation: true means only a person can run it. Use this for skills that you want to run deliberately, not whenever Claude thinks they fit.
  • If your main branch isn't called main, change origin/main to match.

How to test it

  1. Start a new session and type /. The three skills should be in the list. /skills also lists them.
  2. Run /bug-report checkout total ignores coupon and check every section is present and it asks for the build.
  3. Describe a bug in plain words without the command. Claude should pick the skill up from its description. If it doesn't, improve the description.
  4. Try an awkward case: a vague one-line complaint, a bug with no steps. Good skills ask questions; bad ones invent details.

How to share it

Commit the .claude/skills/ folder. Personal variations go in ~/.claude/skills/ instead, which only you see.

127.4Tool 2: a test-reviewer subagent

A subagent is a helper Claude can hand a job to. It starts with a fresh, empty context, follows its own instructions, can be limited to certain tools, and reports back only its result. That makes it ideal for an independent review: it isn't influenced by the conversation that produced the code.

.claude/agents/test-reviewer.md
---
name: test-reviewer
description: Reviews test code for flakiness, weak assertions and missing cases. Use after tests are written or changed.
tools: Read, Glob, Grep
model: sonnet
---

You are a strict QA reviewer. For each test file you are given, report:
- hard-coded waits or timing assumptions (for example waitForTimeout)
- assertions that can never fail, or that check too little
- missing negative, boundary and error cases
- shared state or order dependence between tests
- selectors that are likely to break (CSS classes instead of test ids or roles)

Return a table with columns: file, line, issue, suggested fix. Do not edit files.
  • Only name and description are required. The text below the frontmatter becomes the subagent's own instructions.
  • tools: Read, Glob, Grep makes it read-only: it can look but can't change anything. A reviewer shouldn't edit what it reviews.
  • model: sonnet picks the model; you can also use opus, haiku, fable or inherit (use the session's model).

Use it by asking: "Use the test-reviewer subagent on tests/checkout.spec.ts." In current versions, /agents only prints a reminder; you create and edit subagents by writing these files (or asking Claude to). Files are picked up within seconds.

How to test it

Write a deliberately bad test: a waitForTimeout(3000), an assertion like expect(true).toBe(true), and a CSS-class selector. A good reviewer flags all three. If it misses one, tighten its instructions. This is "testing the tester", and it's a habit worth keeping.

127.5Tool 3: a hook that checks every test edit

Skills and subagents are instructions Claude chooses to follow. A hook is different: Claude Code itself runs it at a set moment, every time. Use a hook for anything that must never be skipped.

This hook runs after Claude edits or writes a file. If the file is a Playwright spec, it lints it and runs just that test. If either fails, Claude is told immediately and can fix it.

.claude/hooks/check-test-file.sh
#!/bin/bash
# Runs after Claude edits or writes a file.
# If the file is a Playwright spec, lint it and run just that spec.
input=$(cat)
file=$(echo "$input" | jq -r '.tool_input.file_path // empty')

case "$file" in
  *.spec.ts|*.spec.js) ;;      # carry on for test files
  *) exit 0 ;;                 # ignore every other file
esac

cd "$CLAUDE_PROJECT_DIR" || exit 0

if ! out=$(npx eslint "$file" 2>&1); then
  echo "ESLint found problems in $file:" >&2
  echo "$out" >&2
  exit 2
fi

if ! out=$(npx playwright test "$file" --reporter=line 2>&1); then
  echo "The test in $file failed:" >&2
  echo "$out" | tail -n 40 >&2
  exit 2
fi
exit 0
LineWhat it does
input=$(cat)Claude Code sends details of the action as JSON on the script's input. This reads all of it.
jq -r '.tool_input.file_path // empty'Pulls out the path of the file that was edited (or nothing, if there isn't one).
case … esacOnly continues for files ending .spec.ts or .spec.js.
$CLAUDE_PROJECT_DIRThe project's root folder, provided by Claude Code.
exit 2 with a message on >&2Exit code 2 plus text on the error stream. After an edit, this shows the message to Claude so it can react. Exit 0 means "all fine".

Make it executable with chmod +x .claude/hooks/check-test-file.sh, then register it in .claude/settings.json:

.claude/settings.json (the hooks section)
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-test-file.sh", "timeout": 300 }
        ]
      }
    ]
  }
}
  • PostToolUse means "after a tool has run". "matcher": "Edit|Write" limits it to file edits and new files.
  • timeout is in seconds. Running a browser test takes a while, so we allow up to five minutes.
  • You can view the hooks Claude Code has loaded with /hooks.

How to test it, without Claude

Because a hook is just a script reading JSON, you can test it yourself by sending it fake input:

Terminal
echo '{"tool_input":{"file_path":"src/app.ts"}}' | CLAUDE_PROJECT_DIR="$PWD" .claude/hooks/check-test-file.sh; echo "exit=$?"
# exit=0: not a test file, so it does nothing

echo '{"tool_input":{"file_path":"tests/checkout.spec.ts"}}' | CLAUDE_PROJECT_DIR="$PWD" .claude/hooks/check-test-file.sh; echo "exit=$?"
# exit=0 if the spec passes; exit=2 and an error message if it fails
Careful

A hook runs real commands, automatically, with your permissions. Read any hook before adding it, especially one from someone else, and keep hooks fast: a slow hook after every edit makes everyone's sessions slow.

127.7Tool 5: a nightly failure summary in CI

Claude Code can run without a person watching, using print mode (claude -p). It answers once and exits, which is perfect for scripts and CI pipelines. This GitHub Actions workflow runs the test suite every night and, if anything fails, asks Claude to summarise the failures into the job's summary page.

.github/workflows/nightly.yml
name: Nightly tests with AI summary
on:
  schedule:
    - cron: "0 2 * * *"          # every day at 02:00 UTC
  workflow_dispatch:              # also allow manual runs

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npx playwright install --with-deps

      - name: Run tests
        id: tests
        continue-on-error: true
        run: npx playwright test --reporter=junit
        env:
          PLAYWRIGHT_JUNIT_OUTPUT_NAME: test-results/results.xml

      - name: Summarise failures with Claude
        if: steps.tests.outcome == 'failure'
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          curl -fsSL https://claude.ai/install.sh | bash
          ~/.local/bin/claude -p "Read test-results/results.xml. Group the failures by likely root cause. For each group give the tests, the error, whether it looks like a product bug, a test bug or flakiness, and a suggested next step. Use Markdown." \
            --bare \
            --allowedTools "Read,Grep,Glob" \
            --permission-prompts none \
            --max-budget-usd 1 \
            --output-format json | jq -r '.result' >> "$GITHUB_STEP_SUMMARY"

      - name: Fail the job if tests failed
        if: steps.tests.outcome == 'failure'
        run: exit 1
PartWhy it's there
continue-on-error: true and id: testsLets the workflow carry on to the summary step after a test failure, while remembering the result
curl … install.sh | bashThe official native installer; it puts claude in ~/.local/bin
-p "…"Print mode: one prompt, one answer, then exit
--bareSkips loading hooks, skills, plugins, MCP servers and CLAUDE.md, so CI runs are predictable. It signs in only with ANTHROPIC_API_KEY.
--allowedTools "Read,Grep,Glob"Read-only: the summary job can look at files but not change anything
--permission-prompts noneNobody is there to answer questions, so anything that would ask permission is denied automatically
--max-budget-usd 1A spending cap for this run, in US dollars
--output-format json then jq -r '.result'Gets a structured answer and pulls out just the text
$GITHUB_STEP_SUMMARYA file GitHub shows on the run's summary page
Final step exit 1Keeps the job red when tests failed, so nobody mistakes a summary for a pass

Store the key as a repository secret named ANTHROPIC_API_KEY (Chapter 98 explains keys and secrets). Never write it into the file. Anthropic also publishes an official GitHub Action, anthropics/claude-code-action@v1, which is the better choice when you want people to mention @claude in pull requests (Chapter 71).

How to test it

Trigger it manually with "Run workflow" (that's what workflow_dispatch allows) after deliberately breaking one test on a branch. Check the summary page shows a sensible grouping and that the job still ends red.

127.8Tool 6: a test dashboard

Managers and developers want to see the state of testing without opening reports. Two simple routes:

Route A: a script that builds a page

Claude Code writes a small script that turns JUnit reports into a one-page HTML dashboard. It runs anywhere, including at the end of the CI job above, and needs no server.

Route B: a Claude Artifact

Paste or upload a summary in the Claude app and ask for an interactive dashboard Artifact (Chapter 48). Quick to create and easy to share, but you refresh it by hand.

Here's Route A. It uses only Python's standard library, so there's nothing to install.

tools/make_dashboard.py
#!/usr/bin/env python3
"""Turn JUnit XML test reports into a one-page HTML dashboard.

Usage: python3 tools/make_dashboard.py [reports-folder] [output-file]
"""
import glob
import html
import sys
import xml.etree.ElementTree as ET
from datetime import datetime

folder = sys.argv[1] if len(sys.argv) > 1 else "test-results"
output = sys.argv[2] if len(sys.argv) > 2 else "dashboard.html"

suites, failures = [], []
for path in sorted(glob.glob(f"{folder}/**/*.xml", recursive=True)):
    root = ET.parse(path).getroot()
    found = [root] if root.tag == "testsuite" else root.findall("testsuite")
    for s in found:
        total = int(s.get("tests", 0))
        failed = int(s.get("failures", 0)) + int(s.get("errors", 0))
        skipped = int(s.get("skipped", 0))
        suites.append((s.get("name", path), total, total - failed - skipped, failed, skipped))
        for case in s.findall("testcase"):
            problem = case.find("failure")
            if problem is None:
                problem = case.find("error")
            if problem is not None:
                message = (problem.get("message") or "").strip()[:200]
                failures.append((case.get("classname", ""), case.get("name", ""), message))

total = sum(s[1] for s in suites)
passed = sum(s[2] for s in suites)
failed = sum(s[3] for s in suites)
rate = f"{passed / total * 100:.1f}%" if total else "n/a"

def cells(values):
    return "".join(f"<td>{html.escape(str(v))}</td>" for v in values)

suite_rows = "".join(f"<tr>{cells(s)}</tr>" for s in suites)
failure_rows = "".join(f"<tr>{cells(f)}</tr>" for f in failures) or "<tr><td colspan='3'>No failures</td></tr>"

page = f"""<!doctype html><html><head><meta charset="utf-8"><title>Test dashboard</title>
<style>body{{font-family:system-ui,sans-serif;margin:2rem;color:#1d2a22}}
table{{border-collapse:collapse;margin:1rem 0}}td,th{{border:1px solid #ccc;padding:.4rem .7rem;text-align:left}}
.big{{font-size:2rem;font-weight:700}}</style></head><body>
<h1>Test dashboard</h1><p>Generated {datetime.now():%Y-%m-%d %H:%M} from {html.escape(folder)}</p>
<p class="big">{passed} of {total} passed ({rate}) · {failed} failed</p>
<h2>Suites</h2><table><tr><th>Suite</th><th>Tests</th><th>Passed</th><th>Failed</th><th>Skipped</th></tr>{suite_rows}</table>
<h2>Failures</h2><table><tr><th>File</th><th>Test</th><th>Message</th></tr>{failure_rows}</table>
</body></html>"""

with open(output, "w", encoding="utf-8") as f:
    f.write(page)
print(f"Wrote {output}: {passed}/{total} passed, {failed} failed")
  • It finds every .xml report under the folder, reads each test suite's totals, and collects each failing test's message.
  • html.escape makes sure an error message containing < or quotes can't break the page.
  • Run it with python3 tools/make_dashboard.py test-results dashboard.html. It prints a one-line summary such as Wrote dashboard.html: 3/5 passed, 1 failed.

To publish it automatically, add a CI step that runs the script and uploads dashboard.html as a build artifact, or ask Claude Code to extend it with trends over time once you have several nights of reports.

Why ask Claude to write the script instead of asking it for the dashboard each time?

Asking Claude to read reports and describe them every day costs tokens, varies slightly each time, and depends on a person remembering to ask. A script Claude wrote once runs in a fraction of a second, gives exactly the same kind of output every time, costs nothing to run, and can be reviewed like any other code. A good rule: use AI to build deterministic tools for repeatable jobs; use AI directly for judgement, like grouping failures by likely cause in the CI summary.

127.9Tool 7: package it all as a team plugin

Committing files to one repository shares them with that repository's users. A plugin shares them across every repository, installed in one step. It's a folder with a manifest and the same kinds of files you've already written.

Plugin folder layout
qa-toolkit/
├── .claude-plugin/
│   └── plugin.json            # the manifest (only this file goes in .claude-plugin/)
├── README.md                  # what it does and how to use it
├── skills/
│   ├── bug-report/SKILL.md
│   ├── test-plan/SKILL.md
│   └── risk-review/SKILL.md
├── agents/
│   └── test-reviewer.md
├── hooks/
│   └── hooks.json             # same shape as the "hooks" part of settings.json
└── scripts/
    └── check-test-file.sh
qa-toolkit/.claude-plugin/plugin.json
{
  "name": "qa-toolkit",
  "description": "Our QA team's skills, test reviewer, test-file hook and results server",
  "version": "1.0.0",
  "author": { "name": "QA Team" },
  "license": "MIT"
}
qa-toolkit/hooks/hooks.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"${CLAUDE_PLUGIN_ROOT}/scripts/check-test-file.sh\"",
            "timeout": 300
          }
        ]
      }
    ]
  }
}
  • ${CLAUDE_PLUGIN_ROOT} means "wherever this plugin is installed". Wrap it in quotes so a folder name with a space can't break the command; Claude Code's validator warns if you forget.
  • Inside a plugin, skills are called with the plugin's name in front: /qa-toolkit:bug-report.
  • Plugin subagents ignore some settings (such as their own hooks and MCP servers), so keep the reviewer simple.
  • An MCP server can be included with a .mcp.json file in the plugin folder.

How to test it

Terminal
claude plugin validate ./qa-toolkit       # checks the manifest, hooks and layout
claude --plugin-dir ./qa-toolkit          # loads it for this session only

The validator prints ✔ Validation passed when the plugin is correct, plus advice. Some advice (an icon, an install line in the README) only matters if you publish to Anthropic's public plugin directory; an internal team plugin doesn't need it. With --plugin-dir, type /qa-toolkit:bug-report to try it without installing anything.

How to share it

Put the plugin in a Git repository that also contains a marketplace file, .claude-plugin/marketplace.json, listing your plugins (Chapter 84 shows the format). Then teammates run:

Terminal
claude plugin marketplace add your-org/qa-plugins
claude plugin install qa-toolkit@qa-plugins --scope project

The part after @ is the marketplace's name from its marketplace.json. --scope project records the plugin in the project's shared settings so everyone on that project gets it; user scope would install it just for you. Inside a session, /plugin lets people browse and manage plugins, and /reload-plugins loads new ones without restarting.

127.11Owning and maintaining your tools

The moment other people rely on a tool, it becomes a small product. Treat it that way:

  • Give every tool an owner and write their name in the README.
  • Keep tools in version control and change them through pull requests, so changes are reviewed.
  • Bump the version in plugin.json when you change behaviour, and note what changed.
  • Keep test examples: a few bug descriptions for the skills, a bad test file for the reviewer, a sample report for the dashboard. Re-run them after changes. Chapter 125 shows how to turn these into proper evals.
  • Re-check after Claude Code updates. Features change; the version this book was checked against is 2.1.319.
  • Ask for feedback. A skill nobody uses is a sign the description, the output or the problem is wrong.
  • Retire tools that are no longer needed. Fewer, better tools beat a cluttered menu.

Common misunderstandings
"I need to be a developer to build tools."
Claude Code writes most of the code. You bring what matters most: knowing which problems are worth solving and what "good" looks like.
"A skill will always be followed exactly."
Skills are instructions, followed very reliably but not guaranteed. If something must always happen, use a hook or a script.
"Hooks are a good place for slow, heavy checks."
Hooks run often. Keep them fast and focused; put full-suite runs in CI.
"Once it works, it's done."
Tools need owners, versions and re-testing, especially as Claude Code and your test stack change.
"The CI summary replaces looking at failures."
It's a head start. A person still decides whether each failure is a product bug, a test bug or noise.

127.12Review

Key takeaways
  • Building tools turns one person's good practice into the team's default, and saves time on every future task.
  • Skills capture how to do a task; subagents give independent reviews; hooks enforce what must always happen; MCP servers connect live data; claude -p works unattended; scripts give identical results every time; plugins share everything.
  • Test every tool with real and awkward examples before others depend on it, including "testing the tester".
  • Share project tools by committing .claude/ files; share across projects with a plugin and a marketplace.
  • Owned, versioned, reviewed and regularly re-tested tools stay useful; unowned tools quietly rot.
Check yourself
