Sometimes the tool your team needs doesn't have an MCP server: your own test-report format, an internal test-data service, a home-grown release checklist. Building a server for it is smaller than it sounds. With the official Python SDK, each tool is an ordinary Python function with a short description. In this chapter you'll build a server called qa-results that lets Claude read JUnit test reports, list failing tests and explain why they failed. The code was tested against the current SDK while this chapter was written.

104.1Should you build one?

Building a server is the right choice in some situations and overkill in others.

SituationBest option
The service already has an official MCP serverUse it (Chapter 103)
You only need Claude Code to do it, on your machine, and a terminal command already does the jobLet Claude run the command, or write a skill that explains how (Chapter 80)
You want the same ability in claude.ai, Claude Desktop, other AI tools, or for the whole teamBuild an MCP server
You need strict control over what the AI can do (only these three read-only actions)Build an MCP server: it offers exactly the tools you define, nothing more
You need to wrap an internal API that needs secret credentialsBuild an MCP server: the server holds the credentials, and Claude never sees them
In everyday life

An MCP server is like a hotel reception desk. Guests (AI assistants) can't wander into the back office. They ask at the desk, and the desk offers a fixed menu of services: book a taxi, store luggage, call a doctor. You decide what's on the menu. That's why a well-designed server is safer than giving the AI direct access to everything.

104.2What we'll build

Most test frameworks (Playwright, Jest, pytest, JUnit, Cypress and others) can write their results as a JUnit XML file. Our server will read those files and offer Claude:

NameKindWhat it does
list_reportsToolLists the report files in the reports folder
list_failing_testsToolLists every failed or errored test in one report, with a short message
get_failure_detailsToolShows the full error and stack trace for one test
reports://summaryResourceA pass/fail summary of every report, which you can attach to a conversation

Remember from Chapter 99: tools are actions the model decides to call; resources are data that the application or you attach. Everything here only reads, so the server can never change or delete anything.

104.3Set up the project

The official Python SDK is the package called mcp (version 2.3.0 when this was written). It needs Python 3.11 or newer.

In a terminal
mkdir qa-results && cd qa-results     # make a project folder and go into it
python3 -m venv .venv                   # create a private Python environment in .venv
source .venv/bin/activate               # switch to it (Windows: .venv\Scripts\activate)
pip install "mcp[cli]"                  # install the SDK plus its "mcp" command-line tool
mkdir test-results                      # the folder our server will read from

A virtual environment (.venv) keeps this project's packages separate from everything else on your computer (Chapter 58). The [cli] part adds the mcp command, used later for testing. If your team uses the uv tool instead, the equivalent is uv add "mcp[cli]".

Now save a sample report as test-results/junit.xml, so there's something to read:

test-results/junit.xml
<?xml version="1.0" encoding="UTF-8"?>
<testsuites>
  <testsuite name="checkout" tests="3" failures="1" errors="1">
    <testcase classname="checkout.spec.ts" name="applies a valid coupon" time="1.2"/>
    <testcase classname="checkout.spec.ts" name="rejects an expired coupon" time="0.9">
      <failure message="expect(received).toHaveText(expected)">Expected: "Coupon expired"
Received: "Invalid code"
    at checkout.spec.ts:42:31</failure>
    </testcase>
    <testcase classname="checkout.spec.ts" name="shows the order total" time="30.0">
      <error message="Timeout 30000ms exceeded">waiting for getByTestId('order-total')</error>
    </testcase>
  </testsuite>
</testsuites>

In JUnit XML, each <testcase> is one test. A <failure> inside it means an assertion failed; an <error> means something crashed or timed out. A test with neither passed.

104.4The server, part by part

Create server.py. We'll build it in five parts; together they form one complete, working file of about 90 lines.

Part 1: imports and settings

"""qa-results: an MCP server that lets Claude read JUnit test reports."""
import os
from pathlib import Path
import xml.etree.ElementTree as ET
from typing import Annotated

from pydantic import Field

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations

PROJECT = Path(os.environ.get("CLAUDE_PROJECT_DIR", "."))  # Claude Code sets this to your project folder
REPORTS = Path(os.environ.get("REPORTS_DIR", PROJECT / "test-results")).resolve()
MAX_CHARS = 4000  # keep tool output small: it all goes into Claude's context

mcp = MCPServer(
    "qa-results",
    instructions="Read JUnit XML test reports: list failing tests and show why they failed.",
)
  • The first line, in triple quotes, is a description of the file. Python ignores it when running.
  • import os, Path and ET are built into Python: environment variables, file paths and an XML reader.
  • Annotated and Field let us attach a description to each tool input (Part 3). pydantic is installed automatically with the SDK.
  • The three mcp imports bring in the server class, the error type for tools, and "annotations" (labels such as "this tool only reads").
  • PROJECT: when Claude Code starts a local server, it sets the environment variable CLAUDE_PROJECT_DIR to your project folder. If it isn't set, we use the current folder (".").
  • REPORTS is the one folder our server may read. Someone can override it with a REPORTS_DIR environment variable. .resolve() turns it into a full, exact path, which matters for the safety check in Part 2.
  • MAX_CHARS caps how much text one tool returns. Everything a tool returns goes into Claude's context window, so a 5 MB stack trace would be expensive and unhelpful.
  • MCPServer("qa-results", instructions=…) creates the server. The name appears in Claude Code's /mcp list. The instructions tell Claude what the server is for, which helps it find these tools when it searches.
Older tutorials say FastMCP

Version 1 of the Python SDK called this class FastMCP (imported from mcp.server.fastmcp). Version 2 renamed it to MCPServer, imported from mcp.server. If you copy code from an older blog post and it fails to import, this is usually why. The SDK has a migration guide.

Part 2: helper functions (not visible to Claude)

ReportName = Annotated[str, Field(description='Report file name from list_reports, e.g. "junit.xml"')]


def open_report(report: str) -> ET.Element:
    """Parse one report file, refusing anything outside the reports folder."""
    path = (REPORTS / report).resolve()
    if not path.is_relative_to(REPORTS):
        raise ToolError("Report must be inside the reports folder.")
    if path.suffix != ".xml" or not path.is_file():
        raise ToolError(f"No report called {report!r}. Use list_reports to see the names.")
    return ET.parse(path).getroot()


def failures(root: ET.Element):
    """Yield (testcase, problem) for every failed or errored test."""
    for case in root.iter("testcase"):
        problem = case.find("failure")
        if problem is None:
            problem = case.find("error")
        if problem is not None:
            yield case, problem
  • ReportName is a reusable description of the "report" input: a piece of text (str) with a helpful explanation. Both tools that take a report name use it.
  • open_report builds the full path to the file. REPORTS / report joins the folder and the name, and .resolve() works out the real location, expanding things like .. ("go up one folder").
  • is_relative_to(REPORTS) checks that the final location is still inside the reports folder. This is the path traversal defence: without it, a request for ../../.ssh/id_rsa could read your private SSH key.
  • The second check makes sure it's an existing .xml file. The error message tells Claude how to fix its mistake ("Use list_reports"). Section 97.6 explains why that matters.
  • ET.parse(path).getroot() reads the XML and returns its top element.
  • failures walks through every <testcase>. If it contains a <failure> or an <error>, it hands back that test and the problem. yield returns results one at a time, like a conveyor belt.

Part 3: the tools

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def list_reports() -> list[str]:
    """List the JUnit XML report files available to read."""
    return sorted(p.name for p in REPORTS.glob("*.xml"))


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def list_failing_tests(report: ReportName) -> list[dict]:
    """List every failed or errored test in a JUnit XML report."""
    return [
        {
            "test": case.get("name"),
            "class": case.get("classname"),
            "kind": problem.tag,
            "message": (problem.get("message") or "")[:200],
        }
        for case, problem in failures(open_report(report))
    ]


@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def get_failure_details(
    report: ReportName,
    test: Annotated[str, Field(description="Test name exactly as list_failing_tests shows it")],
) -> str:
    """Show the full error message and stack trace for one failing test."""
    for case, problem in failures(open_report(report)):
        if case.get("name") == test:
            text = f"{problem.get('message', '')}\n\n{problem.text or ''}".strip()
            return text[:MAX_CHARS]
    raise ToolError(f"No failing test named {test!r} in {report}.")
  • @mcp.tool(…) is a decorator: a label on the line above a function that says "offer this function to AI clients as a tool". That single line is the whole registration.
  • ToolAnnotations(readOnlyHint=True) tells clients the tool changes nothing. Claude Code uses this hint, for example to run read-only calls side by side.
  • The function name becomes the tool name. The docstring (the line in triple quotes) becomes the tool description that Claude reads to decide when to use it.
  • The type hints (report: ReportName, -> list[str]) become the input and output schema. You don't write any JSON Schema by hand: the SDK generates it.
  • list_reports finds every .xml file in the folder and returns their names, sorted.
  • list_failing_tests returns one small record per failure. The message is cut to 200 characters so the list stays short; the details come from the next tool. This "summary first, details on request" design keeps Claude's context tidy.
  • get_failure_details finds the named test and returns its message plus the full text inside the failure element (usually the stack trace), capped at MAX_CHARS. If no test matches, it raises a ToolError.

Part 4: the resource

@mcp.resource("reports://summary")
def summary() -> str:
    """Pass/fail totals for every report in the folder."""
    lines = []
    for name in list_reports():
        root = open_report(name)
        total = len(list(root.iter("testcase")))
        failed = len(list(failures(root)))
        lines.append(f"{name}: {total} tests, {failed} failing")
    return "\n".join(lines) or "No reports found."
  • @mcp.resource("reports://summary") publishes this function's result as a resource with that address (a URI). The reports:// part is a name we chose; it doesn't need to be a web address.
  • It counts tests and failures in every report and returns one line per file, such as junit.xml: 3 tests, 2 failing.

Part 5: start the server

if __name__ == "__main__":
    mcp.run()  # stdio: Claude Code starts this script and talks to it over stdin/stdout
  • This runs only when the file is started directly (python server.py), not when another file imports it (as our tests will).
  • mcp.run() starts the server using the stdio transport by default: messages arrive on standard input and replies go out on standard output (Chapter 99). The SDK can also serve over HTTP, which you'd use for a server shared over a network.
Never print() in a stdio server

In a stdio server, standard output is the conversation with Claude Code. A stray print("debug") injects garbage into that conversation and can break the connection. Send debugging messages to standard error instead, or use Python's logging module, which writes to standard error by default.

104.5Names, descriptions and inputs Claude can use

Claude never sees your code. It sees only each tool's name, description and input schema. Here is what the SDK generates for get_failure_details:

What Claude receives (simplified)
{
  "name": "get_failure_details",
  "description": "Show the full error message and stack trace for one failing test.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "report": { "type": "string", "description": "Report file name from list_reports, e.g. \"junit.xml\"" },
      "test":   { "type": "string", "description": "Test name exactly as list_failing_tests shows it" }
    },
    "required": ["report", "test"]
  },
  "annotations": { "readOnlyHint": true }
}

That's all Claude has to go on, so treat it like documentation for a new colleague:

DoAvoid
Verb-first names that say what happens: list_failing_testsVague names: process, handle_data, tool1
Descriptions that say what the tool does and when to use it, with the key words firstEmpty or one-word descriptions
Describe every input, with an example valueInputs like s: str with no explanation
Point to the tool that provides a value ("from list_reports")Making Claude guess file names
A few focused toolsOne giant tool with ten modes, or fifty near-identical tools

Claude Code cuts very long descriptions (server instructions and up-front tool descriptions at 4,096 characters), and its tool search reads the start of each description, so put the important words first.

Real-world example

A team's first version of a similar server had one tool, query(q: str), described as "Query results". Claude kept passing full English sentences, guessing file names, and asking the user what to do. Splitting it into three clearly named tools with described inputs fixed it the same day: Claude started chaining them correctly without being told.

104.6Errors that help Claude recover

Things go wrong: Claude asks for a report that doesn't exist, or misspells a test name. How the tool reports that decides what happens next.

What the tool doesWhat Claude seesUse when
raise ToolError("…")A result marked as an error, with your message. Claude reads it and usually tries again correctly.Almost always: bad input, nothing found, not allowed
Some other exception (a bug)Only that the call failed. Your log gets the details.Never on purpose; it means your code needs fixing
return "Error: …"A normal, successful result that happens to say "Error"Don't. Clients treat it as success, so the error flag is missing

The best error messages say what was wrong and how to fix it: "No report called 'nightly.xml'. Use list_reports to see the names." When we tested this server, a wrong name produced exactly that message with the error flag set, ready for Claude to correct itself.

104.7Test it before Claude does

You're a tester: don't make Claude your first test. There are two good ways to check a server on its own.

Automated tests with the SDK's client

The SDK includes a Client that can connect straight to your server object in memory, with no separate process and no network. That makes ordinary automated tests possible:

test_server.py (run with: pip install pytest, then python -m pytest)
import pytest
from mcp import Client
from server import mcp


@pytest.mark.anyio
async def test_lists_failing_tests():
    async with Client(mcp) as client:
        result = await client.call_tool("list_failing_tests", {"report": "junit.xml"})
        names = [t["test"] for t in result.structured_content["result"]]
        assert names == ["rejects an expired coupon", "shows the order total"]


@pytest.mark.anyio
async def test_refuses_files_outside_the_folder():
    async with Client(mcp) as client:
        result = await client.call_tool("list_failing_tests", {"report": "../secrets.xml"})
        assert result.is_error
  • from server import mcp imports your server object (this is why Part 5 checks __name__: importing doesn't start it).
  • @pytest.mark.anyio lets pytest run async test functions. async and await are Python's way of waiting for things like messages without freezing.
  • Client(mcp) connects to the server in memory; call_tool calls a tool exactly as Claude would.
  • The first test checks the right failures come back. The second is a security test: it proves the path traversal defence works. Both passed against SDK 2.3.0.

Clicking around in the MCP Inspector

The MCP Inspector is the official visual tool for trying a server: it lists the tools, builds a form for each input and shows the raw messages.

mcp dev server.py                                    # the SDK's shortcut; needs the uv tool and Node.js
npx @modelcontextprotocol/inspector python server.py   # or run the Inspector directly (needs a recent Node.js)

Open the address it prints in your browser, choose a tool, fill in the form and run it. Check the descriptions read well, the inputs are clear, and the errors make sense. The Inspector also has a command-line mode (--cli) for scripted checks in CI.

104.8Connect it to Claude Code

Claude Code starts a stdio server itself, so you give it the exact command that runs your file. Use the Python inside your virtual environment, so the mcp package is found.

From the qa-results folder
claude mcp add --transport stdio qa-results \
  --env REPORTS_DIR="$PWD/test-results" \
  -- "$PWD/.venv/bin/python" "$PWD/server.py"
  • qa-results is the server's name in Claude Code; its tools become mcp__qa-results__list_reports and so on.
  • --env REPORTS_DIR=… sets the reports folder for the server. $PWD is the shell's name for "the folder I'm in", so the paths become complete.
  • Options go before the name; the command that starts the server goes after --.
  • On Windows the Python path is .venv\Scripts\python.exe.

Then check it and use it:

claude mcp get qa-results     # should report the server as connected
claude                        # start a session
Inside the session
/mcp                                         # see qa-results and its three tools
Which tests failed in the latest report, and why? Group them by likely cause.
Compare with @qa-results:reports://summary   # attach the resource with @

The first time Claude calls each tool, Claude Code asks your permission. To allow this server's tools without prompts, add the rule mcp__qa-results__* to your allow list (Chapter 78).

104.9Security checklist for your own server

RiskWhat could happenWhat our server does
Path traversalA crafted file name reads files outside the folderResolves the path and checks it's inside REPORTS; tested
Doing too muchA tool deletes or changes things it shouldn'tOnly read-only tools exist; nothing can write
Huge outputsOne call floods Claude's contextMessages cut to 200 characters; details capped at 4,000
Leaking secretsTokens or passwords appear in results and go to the modelReads only test reports. If you wrap an API, keep its key in the server's environment and never return it
Untrusted filesA malicious XML file attacks the parserReports come from your own CI. For files from outside, use a hardened parser such as the defusedxml package
Prompt injectionText inside a report says "ignore your instructions and…"Can't be fully prevented by the server; Claude Code's permission prompts and your review are the safeguard (Chapter 105)
In everyday life

Your server is a shop counter, not an open warehouse. Decide exactly what's sold over the counter (tools), check every order slip (input validation), never hand over the safe combination (secrets), and keep parcels to a size that fits through the hatch (output limits).

104.10Share it with your team

To give everyone on a project the same server, commit the server code to the repository (for example under tools/qa-results/) and add a project-scope entry to .mcp.json at the repository root:

.mcp.json
{
  "mcpServers": {
    "qa-results": {
      "command": "${CLAUDE_PROJECT_DIR:-.}/tools/qa-results/.venv/bin/python",
      "args": ["${CLAUDE_PROJECT_DIR:-.}/tools/qa-results/server.py"],
      "env": { "REPORTS_DIR": "${CLAUDE_PROJECT_DIR:-.}/test-results" }
    }
  }
}
  • An entry with a command and no type is a stdio server.
  • ${CLAUDE_PROJECT_DIR:-.} means "the project folder, or the current folder if that isn't set". Claude Code's documentation says .mcp.json entries need the :-. default here, because the variable is set for the server, not for Claude Code itself.
  • Each teammate creates the virtual environment once (python3 -m venv tools/qa-results/.venv, then installs mcp into it). Add .venv to .gitignore.
  • The first time someone opens the project, Claude Code asks them to approve the project's servers. That approval step is deliberate: a repository can't silently start programs on your machine.

You can also run claude mcp add --scope project …, which writes the .mcp.json entry for you. For wider sharing, MCP servers can be published to package registries and the MCP Registry, or bundled into a Claude Code plugin (Chapter 84).

104.11The same idea in TypeScript

If your team works in JavaScript or TypeScript, the official TypeScript SDK works the same way. Its current version (v2) is published as @modelcontextprotocol/server; the older v1 package @modelcontextprotocol/sdk appears in many existing tutorials. Input schemas are written with a schema library such as Zod. This version of two tools was tested against @modelcontextprotocol/server 2.4.0:

server.ts (install: npm install @modelcontextprotocol/server zod)
import { readdir } from 'node:fs/promises';
import path from 'node:path';
import { McpServer } from '@modelcontextprotocol/server';
import * as z from 'zod/v4';
import { StdioServerTransport } from '@modelcontextprotocol/server/stdio';

const project = process.env.CLAUDE_PROJECT_DIR ?? '.';
const reports = path.resolve(process.env.REPORTS_DIR ?? path.join(project, 'test-results'));

const server = new McpServer({ name: 'qa-results', version: '1.0.0' });

server.registerTool(
    'list_reports',
    {
        description: 'List the JUnit XML report files available to read.',
        annotations: { readOnlyHint: true }
    },
    async () => {
        const names = (await readdir(reports)).filter(n => n.endsWith('.xml')).sort();
        return { content: [{ type: 'text', text: names.join('\n') || 'No reports found.' }] };
    }
);

server.registerTool(
    'report_exists',
    {
        description: 'Check whether a report file is in the reports folder.',
        inputSchema: z.object({ report: z.string().describe('Report file name, e.g. "junit.xml"') }),
        annotations: { readOnlyHint: true }
    },
    async ({ report }) => {
        const names = await readdir(reports);
        return { content: [{ type: 'text', text: names.includes(report) ? 'yes' : 'no' }] };
    }
);

async function main() {
    await server.connect(new StdioServerTransport());
}

main();
  • registerTool(name, settings, handler) is the TypeScript version of @mcp.tool(): you give the name and description explicitly instead of taking them from a function.
  • z.object({ report: z.string().describe(…) }) defines the input. The SDK converts it to JSON Schema for clients.
  • The handler returns a list of content items; here, one piece of text.
  • server.connect(new StdioServerTransport()) starts listening on stdio, like mcp.run() in Python.
  • To run TypeScript directly during development you can use npx tsx server.ts; for sharing, compile it to JavaScript first.
What actually travels between Claude Code and your server

When Claude decides to call list_failing_tests, Claude Code writes one line of JSON to your server's standard input. It's a JSON-RPC request (Chapter 99): roughly {"jsonrpc":"2.0","id":7,"method":"tools/call","params":{"name":"list_failing_tests","arguments":{"report":"junit.xml"}}}. The SDK reads it, checks the arguments against the schema generated from your type hints, calls your Python function, and writes the reply to standard output: a result with content (text for the model) and, because the function returns structured data, structuredContent holding the same list as JSON. If your function raises ToolError, the reply instead has "isError": true and your message. You never write this plumbing; that's the point of the SDK.

Common misunderstandings
"Building an MCP server is a big engineering project."
A useful server can be under 100 lines. The SDK handles the protocol; you write ordinary functions.
"Claude reads my code to understand the tools."
It sees only names, descriptions and input schemas. Write those as carefully as the code.
"Returning an error message as text is fine."
Without the error flag it looks like success. Raise ToolError so the client knows the call failed.
"print() is a harmless way to debug."
In a stdio server it corrupts the conversation with Claude Code. Log to standard error.
"Code from any MCP tutorial will work."
The SDKs changed between versions (FastMCP became MCPServer; the TypeScript package was split). Check which version a tutorial uses.

104.12Review

Key takeaways
  • Build your own server when no official one exists and you need the ability in several AI tools, for a team, or with tight control and hidden credentials.
  • With the Python SDK (mcp, class MCPServer), a tool is a decorated function: its name, docstring and type hints become what Claude sees.
  • Good names, descriptions and described inputs matter more than clever code.
  • Raise ToolError with a message that explains how to fix the problem.
  • Test with the SDK's in-memory Client and the MCP Inspector before connecting to Claude.
  • Connect with claude mcp add --transport stdio name -- command; share via a project .mcp.json using ${CLAUDE_PROJECT_DIR:-.}.
  • Defend against path traversal, oversized output and leaked secrets; prefer read-only tools.
Check yourself

In the Python SDK, where does Claude get a tool's description from?

The SDK takes the name from the function, the description from its docstring and the input schema from its type hints.

A tool can't find the file Claude asked for. What should it do?

ToolError sets the error flag and gives Claude a message it can act on.

Why does our server check that the resolved path is inside the reports folder?

That's path traversal, a classic security hole. The second test in 97.7 proves the defence works.

Why must a stdio MCP server avoid print()?

Log to standard error instead.

In a shared .mcp.json, how should a stdio server refer to the project folder?

The variable is set for the server, so .mcp.json entries need the :-. default. A hard-coded path won't work on a teammate's computer.

Teach it

"An MCP server is a menu of tools we choose to offer the AI. With the Python SDK, each tool is a normal function with a clear name, a one-line description and typed inputs; the SDK turns that into what Claude sees. We raise ToolError with helpful messages, block anything outside the folder we allow, keep outputs small, and test it with the SDK's client before Claude ever touches it. Then one command connects it to Claude Code, and a .mcp.json file shares it with the team."
