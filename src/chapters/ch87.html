The Claude API doesn't remember anything between calls. A "conversation" is simply a list of messages, alternating user and assistant, that your program keeps and sends again with every request, together with a system prompt that sets the rules. Each reply ends with a stop reason that tells your code what to do next. Streaming lets you show the answer as it's written, using server-sent events. Put these three ideas together and you can build a working chat program in about 70 lines of Python.

87.1The API has no memory

When you chat on claude.ai, it feels as if Claude remembers what you said a minute ago. Underneath, the app is doing something simple: every time you press Enter, it sends the whole conversation so far to the model. The Messages API works the same way, and it leaves that job to you. Anthropic's documentation says it directly: the Messages API is stateless, so "you always send the full conversational history to the API". Verified 9 Nov 2026

In everyday life

Imagine a brilliant consultant with no memory at all. Every time you phone, you read out the full transcript of all your earlier calls, then ask your new question. They answer perfectly, because the transcript is all they need. But each call gets longer, and you pay by the minute. That is exactly how a multi-turn API conversation works, and exactly why long chats get expensive.

Here is a three-turn conversation as the API sees it. The third message is the new question; the first two are history your program kept.

A multi-turn request body
{
  "model": "claude-opus-5-5",
  "max_tokens": 1000,
  "system": "You are a senior QA engineer. Reply concisely.",
  "messages": [
    {"role": "user",      "content": "Give boundary values for an age field accepting 18 to 65."},
    {"role": "assistant", "content": "17, 18, 65 and 66. Also try 0, -1 and a non-number."},
    {"role": "user",      "content": "Turn those into a table with expected results."}
  ]
}

Three things follow from this design:

  • You own the history. If your program forgets to append Claude's reply, the next turn won't know what Claude said. If you save the list to a file or database, you can resume a conversation days later.
  • You can edit the history. Earlier turns don't have to be real. The docs note that you can include "synthetic" assistant messages, which is useful in tests: you can start a conversation from any state you want to check.
  • Every turn re-sends everything. Input tokens grow with each turn, so turn 20 costs far more than turn 1. Section 87.8 covers what to do about it.
Message threads (beta)

Anthropic's docs also describe message threads, a beta feature where the API keeps the conversation so that later requests send only the new messages. A thread expires 5 minutes after its last request. This chapter uses the standard stateless pattern, which works everywhere and is what every SDK example assumes. Check the current docs before relying on a beta.

Content: a string or a list of blocks

A message's content can be a plain string, as above, or a list of content blocks, such as a text block and an image block in the same user message. Claude's replies always come back as a list of blocks (Chapter 86), and on current models that list can include thinking blocks before the text. The safest habit is to append Claude's reply to your history exactly as it came back, the whole content list, rather than copying out just the text. Chapter 89 shows why this matters for tool use, where the API requires the thinking blocks to be returned unchanged.

87.2System prompts: the standing brief

The system field holds instructions that apply to the whole conversation: who Claude is in this application, the rules it follows, the format you want, and any background it needs. It is not part of the messages list; it's a separate top-level field.

Put it in systemPut it in a user message
The role ("You are a QA analyst for the payments team")The actual task or question for this turn
Rules that never change ("Never invent test data that looks like real card numbers")The user story, log file or document to work on
Output format ("Each test case has a title, steps and expected result")Anything the end user typed
Product background every turn needsContent from outside sources (and treat it as data: Chapter 88)

Anthropic's prompting guide says that setting a role in the system prompt "focuses Claude's behavior and tone for your use case", and that even a single sentence makes a difference. It also recommends explaining why a rule exists, because Claude generalises from the explanation. "Keep answers under 200 words because they're shown in a narrow side panel" works better than "Be brief".

Real-world example: one app, two system prompts

A team builds an internal "test helper" chat. For testers, the system prompt says: "You help manual testers. Use plain language. Output test cases as numbered lists." For the automation squad, a second deployment says: "You help automation engineers using Playwright with TypeScript. Output runnable code using getByRole locators." Same model, same code, different behaviour, controlled entirely by the system prompt. Both prompts live in version control, so a change to either one is reviewed like a code change (Chapter 88).

Two newer rules worth knowing

  • Mid-conversation system messages. On current models (including Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5), you can add a message with "role": "system" after a user turn to give a new instruction partway through. It has the same authority as the top-level field. It can't be the first entry in messages: instructions that apply from the start still go in system. Verified 9 Nov 2026
  • No more prefill. Older tutorials end the message list with a partial assistant message, such as {"role": "assistant", "content": "{"}, to force Claude to continue in a set format. Prefilling the last assistant turn is not supported on Claude 4.6 and later models: those requests return a 400 error. Use structured outputs (Chapter 89) or clear instructions instead.
The system prompt is not a secret vault

Don't put API keys, passwords or confidential data in a system prompt. Determined users can sometimes coax a model into revealing its instructions, and the prompt is sent (and possibly logged) with every request. Keep secrets in your code's environment, and give the model only what it needs (Chapter 88 covers least privilege).

87.3Stop reasons in a chat application

Every successful reply has a stop_reason field explaining why Claude stopped writing. Chapter 86 listed them all. In a chat program, each one calls for a different reaction. Anthropic's guide stresses one point that surprises people: stop reasons are not errors. They arrive in a normal HTTP 200 response; real errors are 4xx and 5xx status codes.

stop_reasonWhat your chat program should do
end_turnShow the reply and append it to the history. The normal case.
max_tokensShow the reply but warn the user it was cut off. Consider raising max_tokens.
stop_sequenceOnly happens if you set stop_sequences. Check which one in the stop_sequence field.
refusalClaude declined. stop_details names the policy category. Show a polite message; don't keep retrying the same text.
model_context_window_exceededThe conversation filled the context window. Treat the reply as truncated, then shorten the history (87.8).
tool_use, pause_turnOnly when you use tools (Chapter 89).
Real-world example: testing an AI chat feature

When you test any chat feature built on the API, add one test case per stop reason. Can you make it hit max_tokens (ask for a very long answer with a small cap)? Does the UI say the answer was cut off, or does it silently end mid-sentence? What happens after a refusal: is the refused message kept in the history, poisoning every later turn? These are cheap tests that catch real bugs.

87.4Why stream?

Without streaming, your program sends a request and waits, showing nothing, until Claude has written the entire answer. For a long answer, with thinking first, that can take many seconds. Streaming sends the answer in small pieces as it's generated, so the user sees words appear almost at once, the way claude.ai does.

Without streaming

  • One request, one complete JSON response
  • Simple code
  • The user stares at a spinner
  • Very long requests risk HTTP timeouts

With streaming

  • One request, many small events
  • A little more code (the SDK hides most of it)
  • The first words appear quickly
  • Long generations stay alive; the docs note the SDKs require streaming for large max_tokens values to avoid timeouts

Streaming doesn't make Claude finish faster overall, and it doesn't cost more: you pay for the same tokens either way. It improves time to first token, the delay before anything appears, which is what users feel.

87.5How streaming works: server-sent events

To stream, add "stream": true to the request body. The response is no longer one JSON object. It's a series of server-sent events (SSE): a simple web standard where the server keeps the connection open and writes short text messages, one after another. Each event has a name line and a data line holding JSON, followed by a blank line. Verified 9 Nov 2026

Terminal: watch a raw stream (-N stops curl buffering the output)
curl https://api.anthropic.com/v1/messages -N \
  -H "content-type: application/json" \
  -H "Authorization: Bearer $ANTHROPIC_API_KEY" \
  -H "anthropic-version: 2026-10-21" \
  -d '{
    "model": "claude-opus-5-5",
    "max_tokens": 1000,
    "stream": true,
    "messages": [{"role": "user", "content": "Give four boundary values for an age field accepting 18 to 65."}]
  }'

Every stream follows the same order, documented by Anthropic:

message_startA Message object with empty content and starting usage
Content blocksFor each block: content_block_start, one or more content_block_delta, content_block_stop
message_deltaTop-level changes: the stop_reason and the output token count
message_stopThe end

Reading the events

EventWhat it carriesWhat your code does
message_startMessage ID, model, input token count; stop_reason is null hereNote the input tokens
content_block_startThe block's index and type (text, thinking, tool_use)Start a new block
content_block_deltaA small piece: text_delta for text, thinking_delta and signature_delta for thinking, input_json_delta for tool inputsAppend the piece to the block at that index (print text pieces)
content_block_stopThe block is completeFor tool inputs, parse the collected JSON now
message_deltaThe stop_reason and usageRead the stop reason; output token counts here are cumulative, not increments
message_stopNothing moreFinish
pingNothing; keeps the connection aliveIgnore
errorAn error mid-stream, for example overloaded_error (which would be HTTP 529 without streaming)Stop, and retry or report
Expect the unexpected

Anthropic's versioning policy allows it to add new event types at any time, and the streaming guide says your code "should handle unknown event types gracefully". In practice: ignore any event you don't recognise instead of crashing. That's also a good negative test for any stream parser your team writes.

Under the hood: parsing SSE yourself

You'll rarely need to parse SSE by hand, because the SDKs do it. But writing a tiny parser once makes the format concrete, and it's useful for testing: you can save a stream to a file and replay it. The rules are simple. A line starting event: names the event. A line starting data: carries the payload. A blank line ends the event. This script rebuilds the reply from a saved stream and ignores pings and unknown events.

parse_sse.py (standard library only; tested offline)
"""parse_sse.py: rebuild Claude's reply from a saved raw SSE stream."""
import json
import sys


def events(lines):
    """Yield (event_name, data_dict) pairs from SSE lines."""
    name, data = None, []
    for raw in lines:
        line = raw.rstrip("\n")
        if line.startswith("event:"):
            name = line[len("event:"):].strip()
        elif line.startswith("data:"):
            data.append(line[len("data:"):].strip())
        elif line == "" and data:           # a blank line ends one event
            yield name, json.loads("".join(data))
            name, data = None, []
    if data:
        yield name, json.loads("".join(data))


def main(path):
    text, stop_reason, usage = [], None, {}
    with open(path, encoding="utf-8") as f:
        for name, data in events(f):
            if name == "message_start":
                usage.update(data["message"]["usage"])
            elif name == "content_block_delta" and data["delta"]["type"] == "text_delta":
                text.append(data["delta"]["text"])
            elif name == "message_delta":
                stop_reason = data["delta"].get("stop_reason")
                usage.update(data.get("usage", {}))
            elif name == "error":
                print("Stream error:", data["error"]["type"])
                return
            # ping and unknown event types are ignored on purpose
    print("Text:", "".join(text))
    print("Stop reason:", stop_reason)
    print("Usage:", usage)


if __name__ == "__main__":
    main(sys.argv[1] if len(sys.argv) > 1 else "stream.txt")
Terminal
python3 parse_sse.py stream.txt
Text: Test 17, 18, 65 and 66.
Stop reason: end_turn
Usage: {'input_tokens': 25, 'output_tokens': 15}

Note how usage is merged: the input count comes from message_start, and the output count from the last message_delta, which is a running total.

87.6Streaming with the SDKs

The official SDKs give you a higher-level helper that collects the events for you. In Python, client.messages.stream(...) is used as a context manager (with ... as stream:), and stream.text_stream gives you just the text pieces as they arrive. When the stream ends, stream.get_final_message() returns the complete Message object, identical to what a non-streaming call would have returned, with content blocks, stop reason and usage. Verified 9 Nov 2026

Python: stream_once.py
import anthropic

client = anthropic.Anthropic()

with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=1000,
    system="You are a senior QA engineer. Reply concisely.",
    messages=[{"role": "user", "content": "Write three test ideas for a password reset link."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)    # show each piece immediately
    final = stream.get_final_message()

print("\nStop reason:", final.stop_reason)
print("Tokens:", final.usage.input_tokens, "in,", final.usage.output_tokens, "out")
TypeScript: stream-once.ts (ES module)
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const stream = client.messages
  .stream({
    model: "claude-opus-5-5",
    max_tokens: 1000,
    messages: [{ role: "user", content: "Write three test ideas for a password reset link." }]
  })
  .on("text", (text) => process.stdout.write(text));

const final = await stream.finalMessage();
console.log("\nStop reason:", final.stop_reason);
When you don't need the pieces

If you only want the finished answer but your max_tokens is large, you can still use the stream helper and just call stream.get_final_message() without printing anything. The docs recommend this for long generations, because the SDK uses streaming internally to avoid HTTP timeouts and hands you the normal Message at the end.

When a stream breaks

Networks fail. If a stream stops partway, the docs describe a capture-and-resume approach: keep the text you received, then send a new request. On Claude 4.6 and later models, because prefill isn't allowed, you do this with a user message that contains the partial answer and asks Claude to continue from where it left off. Tool-use and thinking blocks can't be partially recovered; you can resume only from the most recent text. For most chat apps, the simpler choice is to show "Connection lost, retry?" and resend the turn.

87.7Build it: a command-line chat in Python

Time to put the pieces together. This program keeps a history list, streams each reply, handles errors and stop reasons, and prints the token count after every turn so you can watch the conversation grow.

Terminal: setup (macOS/Linux; on Windows activate with .venv\Scripts\activate)
mkdir qa-chat && cd qa-chat
python3 -m venv .venv && source .venv/bin/activate
pip install anthropic
export ANTHROPIC_API_KEY="paste-your-key-here"   # Chapter 86
chat.py (complete)
"""chat.py: a small streaming chat CLI for Claude (QA assistant)."""
import anthropic

MODEL = "claude-opus-5-5"
MAX_TOKENS = 4000
SYSTEM = (
    "You are a QA assistant for a software testing team. "
    "Answer concisely. When asked for test cases, use a numbered list "
    "where each item has a title, steps and an expected result."
)


def ask(client, history):
    """Stream one reply for the conversation so far. Returns the final Message."""
    with client.messages.stream(
        model=MODEL,
        max_tokens=MAX_TOKENS,
        system=SYSTEM,
        messages=history,
    ) as stream:
        for text in stream.text_stream:
            print(text, end="", flush=True)
        return stream.get_final_message()


def main():
    client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY
    history = []                            # the whole conversation lives here
    print("QA chat. Commands: /reset clears the history, /quit exits.")
    while True:
        try:
            user_text = input("\nYou: ").strip()
        except (EOFError, KeyboardInterrupt):
            print()
            break
        if not user_text:
            continue
        if user_text == "/quit":
            break
        if user_text == "/reset":
            history.clear()
            print("(history cleared)")
            continue

        history.append({"role": "user", "content": user_text})
        print("Claude: ", end="", flush=True)
        try:
            reply = ask(client, history)
        except anthropic.APIError as err:
            history.pop()                   # forget the turn that failed
            print(f"\n[error] {err}")
            continue

        print()
        if reply.stop_reason == "refusal":
            history.pop()                   # don't keep a refused turn
            print("[declined] Claude declined this request.")
            continue
        history.append({"role": "assistant", "content": reply.content})
        if reply.stop_reason == "max_tokens":
            print("[warning] reply was cut off at max_tokens")
        print(f"[turns: {len(history)} | tokens in: {reply.usage.input_tokens}"
              f" | out: {reply.usage.output_tokens}]")


if __name__ == "__main__":
    main()

How it works, line by line

  • history is the conversation. Each user turn is appended before the call; each reply is appended after it, using the full reply.content list.
  • ask() streams the reply and returns the final Message, so the rest of the code can check stop_reason and usage as if it were a normal call.
  • On an API error (a 429 or 529, say, after the SDK's own automatic retries), the user turn is removed again with history.pop(). Without this, the history would end with two user messages in a row on the next attempt, which is a classic bug.
  • On a refusal, the refused turn is dropped, so it doesn't affect later turns.
  • /reset clears the history: the cheapest way to start fresh.
Example session (illustrative; Claude's wording and token counts will differ)
QA chat. Commands: /reset clears the history, /quit exits.

You: Give boundary values for an age field that accepts 18 to 65.
Claude: 17 (reject), 18 (accept), 65 (accept), 66 (reject). Also try 0, -1, 18.5 and an empty field.
[turns: 2 | tokens in: 61 | out: 154]

Claude: Scenario Outline: Age validation ...
[turns: 4 | tokens in: 239 | out: 402]

Look at "tokens in". It rises every turn, because each request carries the whole history. The output count includes Claude's thinking, which is billed as output even though text_stream doesn't print it.

87.8Managing a growing conversation

Current Claude models have a 1-million-token context window, so a chat rarely runs out of room. Cost and quality usually become problems first. Every turn re-bills the whole history as input, and Anthropic's docs note that "as token count grows, accuracy and recall degrade", a problem called context rot (Chapter 20).

StrategyHowTrade-off
ResetStart a new conversation for a new taskLoses everything; often the right call
Sliding windowSend only the last N turns (always cut in user/assistant pairs)Simple; Claude forgets early details
SummariseAsk Claude to summarise older turns, then replace them with the summaryKeeps the gist; costs an extra call; details can be lost
Server-side compactionAn API feature (beta) that summarises earlier parts on the server so the conversation can continue past the limitLess code; beta, so check the current docs
Prompt cachingMark the stable start of the conversation so repeated input is billed at a much lower rateCuts cost, not context size (Chapter 90)

Choosing what stays in the window, and in what order, is the heart of context engineering, the subject of Chapter 88.

Common misunderstandings
"Claude remembers my earlier API calls."
It doesn't. The conversation exists only in the list your program sends each time.
"Streaming is cheaper or makes Claude faster."
You pay for the same tokens. Streaming only shows the answer sooner.
"I can append just the reply text to the history."
That works for plain chat but breaks tool use. Append the whole content list as returned.
"A refusal or max_tokens is an error, so it'll raise an exception."
Both arrive as normal 200 responses. Your code must check stop_reason.
"I can force JSON by prefilling an opening brace."
Not on Claude 4.6 and later: prefill returns a 400. Use structured outputs (Chapter 89).

87.9Review

Key takeaways
  • The Messages API is stateless: your program keeps the conversation and sends all of it every turn.
  • The system field holds the role, rules and format; current models also accept mid-conversation system messages. Prefill no longer works on Claude 4.6 and later.
  • Check stop_reason on every reply: stop reasons are normal 200 responses, not errors.
  • Streaming uses server-sent events in a fixed order: message_start, content blocks (start, deltas, stop), message_delta, message_stop, with pings and possible error events. Ignore unknown events.
  • In Python, client.messages.stream() with text_stream and get_final_message() gives you live text and the complete message.
  • Long conversations cost more and can lose quality; reset, trim, summarise or compact.
Check yourself

Your chat app forgets what the user said two turns ago. What's the most likely cause?

The API is stateless. If the earlier turns aren't in the messages list, Claude never sees them.

In a stream, where do you find the stop reason?

stop_reason is null in message_start and arrives in message_delta, along with cumulative output usage.

Your stream parser crashes when it meets an event type it has never seen. What should it do instead?

Anthropic may add new event types within an API version, and the docs say to handle unknown events gracefully.

You want Claude's answer to always start with "{" so it's JSON. On Opus 5.5, what's the right approach?

Prefill returns a 400 on Claude 4.6 and later, and temperature is rejected on API version 2026-10-21. Structured outputs guarantee JSON (Chapter 89).

Why does turn 20 of a conversation cost more than turn 1, even if both questions are short?

Input tokens include every earlier message. That's why trimming, summarising and caching matter.
