Claude Code is easy to start and easy to misuse. The good habits are simple: start it inside the project you want it to work on, slow it down while you're learning so you see every action, read each permission prompt like a test step, and stop it the moment it heads the wrong way. This chapter walks you through a full first session in a throwaway practice project, so you can make mistakes where they don't matter.

65.1Start in the right folder

Claude Code works on whatever folder you start it in. That folder becomes its working directory: it can read files there (and in sub-folders) freely, and it asks before touching anything outside it. So the first rule is simple: open your terminal, go to the project, then start Claude.

Terminal
cd ~/projects/shop-app      # go to the project folder first
claude                      # then start Claude Code
In everyday life

Starting Claude Code is like letting a contractor into one room of your house. You open the door of the room you want worked on. If you start it in your home folder, you've effectively opened every room at once, which is rarely what you want.

The workspace trust prompt

The first time you start Claude Code in a folder, it asks whether you trust that folder. This matters because a project can contain its own Claude Code settings, hooks and MCP servers (Chapters 78, 82 and 83), and those can run commands. Only say yes for projects you know: your team's repositories, or folders you created yourself. For a repository you've just downloaded from a stranger, read its .claude/ folder and .mcp.json first.

Good to know

If you start Claude Code directly in your home folder, the trust answer is kept only for that session and the prompt comes back every time. Anthropic's documentation recommends starting from a project folder instead, where trust is remembered per folder. Non-interactive runs (claude -p, Chapter 75) skip the trust prompt entirely, so only use them in folders you trust.

65.3Choose a learning-friendly mode

Since version 2.1.283, a new interactive session normally starts in Auto mode. In Auto mode, a background safety checker (a classifier) reviews Claude's actions and blocks risky ones, so you get very few prompts. That's convenient for experienced users, but while you're learning you want to see each action.

So for your first sessions, press Shift+Tab once. From Auto, the first press goes to Manual, and the indicator shows ⏸ manual mode on. In Manual mode, Claude can read files without asking, but asks before editing files or running commands. You'll see exactly what it wants to do, and you'll learn far faster.

Mode (as shown)Asks you before…Use it when
ManualFile edits and shell commandsLearning; sensitive work
Accept editsMost shell commands (edits and simple file commands like mkdir run freely)You trust the direction and will review the diff
PlanIt doesn't edit at all until you approve a planBefore any bigger change
AutoRarely; a classifier checks actions insteadRoutine work once you're confident

Chapter 67 covers all six modes, including two you'll rarely use in a normal session.

65.4The three input symbols and the keys that matter

Most of the time you just type. Three symbols at the start of what you type change what happens:

TypeWhat happensExample
@Mention a file or folder. Autocomplete helps you pick it, and Claude reads it.Explain @tests/login.spec.ts
! at the startShell mode: runs the command yourself, adds its output to the conversation, and Claude responds to it.! npm test
/ at the startRuns a command or skill, such as /help or /clear./context
Changed in newer versions

Older tutorials say that starting a message with # saves a memory. That shortcut was removed in version 2.0.70. To save something permanently, ask Claude to add it to your CLAUDE.md, or use /memory (Chapter 77).

The keys worth learning on day one

EscStops Claude mid-task. Work so far is kept; give it a new direction. Also declines a permission prompt.
Esc EscOn an empty prompt: opens the rewind menu to go back to an earlier point (Chapter 67). With text typed: clears your draft.

Ctrl+CInterrupts a running operation. With nothing running, the first press clears your input and a second press exits.

You can also type while Claude is working. Your message is queued and Claude reads it at the next safe point, so you can correct course without stopping it.

65.5Answering permission prompts

When Claude wants to do something that needs approval, it shows a box with a title (for example "Bash command"), a short description, the exact command or file, and "Do you want to proceed?". The options look like this:

OptionEffect
YesAllow this one action.
Yes, and don't ask again for …Allow it and remember. For a shell command, the rule is saved to .claude/settings.local.json in that repository and applies in future sessions there. For file edits, it lasts until the session ends.
Yes, and switch to auto modeApprove and change mode (not shown on every prompt).
NoRefuse. Press Tab to add a note telling Claude what to do instead.

A good habit is to read every prompt like a test step, using three questions:

  1. What exactly will run? Read the whole command. If you don't understand it, choose No and ask "What does that command do?"
  2. What can it change? Reading is harmless. Deleting (rm), pushing (git push), installing, or calling external services deserve a second look.
  3. Do I want this every time? Only choose "don't ask again" for safe, repeatable commands like npm test or git status.
Real-world example

Claude asks to run rm -rf node_modules && npm install. That deletes a folder of downloaded packages and downloads them again. It's usually harmless and a common fix, but it takes time and needs the internet. A sensible answer is "Yes" once, not "don't ask again", because you don't want unattended deletes.

65.6Ending and coming back

To…Do this
Leave Claude CodeType /exit, or press Ctrl+D twice
Continue the most recent conversation in this folderclaude -c (same as claude --continue)
Pick an older conversation from a listclaude -r (same as claude --resume), or /resume inside a session
Give a session a memorable name/rename checkout-tests, or start with claude -n checkout-tests
Start a fresh conversation without leaving/clear

Conversations are saved on your computer (under ~/.claude/projects/, kept for 30 days by default), which is how resuming works. A new session always starts with an empty conversation: Claude doesn't remember yesterday's chat unless you resume it or the information is in CLAUDE.md or auto memory (Chapter 77).

65.7How to ask well in Claude Code

Prompting in Claude Code is the same skill as in the chat app (Chapter 44), with three additions:

  • Delegate, don't dictate. Describe the goal and the context ("The discount is wrong for orders over 100; the code is in src/pricing"). You don't need to list which files to open; Claude finds them.
  • Give it a way to check itself. "Make the tests in test/discount.test.js pass" beats "fix the discount", because success is measurable.
  • Say what's out of bounds. "Only change the test files" or "Don't install new packages."
In everyday life

Brief Claude Code as you'd brief a capable new colleague on their first day: explain the goal and the rules of the house, then let them get on with it, and check their work before it ships.

What happens when you press Enter

Your message goes, together with instructions, your CLAUDE.md files and the conversation so far, to a Claude model running on Anthropic's servers. The model replies either with text or with a request to use a tool (read a file, run a command). Claude Code runs that tool on your computer, after checking permissions, and sends the result back. This repeats until the task is done. Chapter 66 follows one task through this loop in detail.

65.8A guided first session (45 minutes)

This session uses a tiny practice project you create yourself, so nothing important is at risk. You need Node.js (Chapter 58); the project uses Node's built-in test runner, so there's nothing to install.

Your first Claude Code session45 min · terminal
  1. Create an empty practice folder and start Claude in it: 
    mkdir ~/claude-practice
cd ~/claude-practice
git init
claude
    a workspace trust question for the new folder (answer yes; you just created it), then the prompt box.
  2. Press Shift+Tab until the indicator says ⏸ manual mode on.the mode indicator changes. From Auto, one press is usually enough.
  3. Ask: "Create a tiny Node.js project: src/discount.js with a function applyDiscount(price, percent), and test/discount.test.js using Node's built-in test runner (node --test). Include tests for 0%, 50%, 100% and a negative percent. Don't install any packages."a short plan, then permission prompts to create each file, each showing the file contents. Approve them with "Yes".
  4. Run the tests yourself with shell mode: ! node --testthe test results printed in the conversation, and Claude commenting on them. If any test fails, that's fine: you'll fix it next.
  5. Ask: "What does applyDiscount do with a negative percent? Is that sensible for a shop?"an explanation, probably pointing out that a negative discount would raise the price. This is Claude helping you think like a tester.
  6. Ask: "Make applyDiscount throw an error for percents below 0 or above 100, update the tests, and run them."a diff for each file (removed and added lines), then a prompt to run node --test. Read each diff before approving.
  7. Halfway through, press Esc once, then type "Actually, use a RangeError with a clear message."Claude stops, then continues with your correction.
  8. Mention a file: "Explain @test/discount.test.js line by line for a beginner."a plain explanation of each test.
  9. Ask: "Commit these changes with a clear message."a prompt to run git add and git commit. Read the message before approving.
  10. Press Esc Esc on an empty prompt, look at the rewind menu, then choose "Never mind".a list of earlier points in the conversation you could go back to.
  11. Type /exit. Then run claude -c.the same conversation back, ready to continue.
Common misunderstandings
"I'll start Claude Code from my home folder so it can see everything."
That gives it access to far more than it needs, and the trust prompt reappears every time. Start in the project folder.
"Auto mode means it never makes mistakes."
Auto mode reduces prompts; it doesn't check whether the code is right. You still review diffs and test results.
"Pressing Esc throws away all the work."
Esc stops the current step and keeps what's been done. Rewind (Esc Esc) is how you go back.
"Typing # saves a note to memory."
Not any more: that shortcut was removed. Ask Claude to update CLAUDE.md, or use /memory.
"Claude will remember this tomorrow."
Only if you resume the conversation, or the information is in CLAUDE.md or auto memory.

65.9Review

Key takeaways
  • Always cd into the project first; only trust folders you know.
  • Learn in Manual mode (Shift+Tab from Auto) so you see every edit and command.
  • @ mentions a file, ! runs a shell command, / runs a command or skill. The old # memory shortcut is gone.
  • Esc stops, Esc Esc rewinds, Ctrl+C interrupts or exits.
  • Read each permission prompt like a test step; choose "don't ask again" only for safe, repeatable commands.
  • /exit to leave; claude -c to continue; claude -r to pick an older conversation.
Check yourself

You want Claude Code to work on your test repository. What should you do first?

The folder you start in becomes Claude's working directory.

A new session shows ⏵⏵ auto mode on. You're learning and want to approve each edit and command. What do you do?

From Auto, the first Shift+Tab press goes to Manual (shown as "⏸ manual mode on").

What does typing ! npm test do?

The ! prefix is shell mode.

Claude is halfway through a change you realise is wrong. Best move?

Esc stops it and keeps the work so far; you can redirect immediately.

Which command picks up yesterday's conversation from a list?

-r (resume) opens the picker. -c continues only the most recent conversation; -p runs one non-interactive request.

Assignment

Repeat the guided session on a real but low-risk repository from your team, such as a test-automation repo, in Manual mode. Ask Claude to explain the project's structure and how to run its tests, then run them with !. Write down every permission prompt you saw and whether you'd approve it permanently. Share the list with a colleague and agree on which commands are safe to allow for the team (you'll turn that list into rules in Chapter 78).

Teach it

"Go into the project folder, then type claude. Trust only folders you know. While learning, press Shift+Tab to Manual so it asks before every edit and command. @ points at a file, ! runs a command, / runs a Claude command. Esc stops it, Esc Esc rewinds. Read every permission prompt like a test step. /exit to leave, claude -c to come back."
