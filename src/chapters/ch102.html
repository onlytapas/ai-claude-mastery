Playwright is a popular, free tool from Microsoft for automating web browsers, widely used for end-to-end testing. Microsoft also publishes a Playwright MCP server that lets Claude drive a real browser itself: open pages, click, type, read what's on screen and check the console. Instead of looking at pictures of the page, it reads the page's structure, the same information screen readers use. For a tester, that means Claude can explore an application with you, report what it finds, and then write proper, repeatable Playwright tests from what it learned.

102.1Three ways AI can work with a browser

People mix these up, so it's worth being precise.

ApproachHow it worksStrengthsWeaknesses
Playwright MCPClaude calls browser tools (navigate, click, type, snapshot) one step at a time, liveGreat for exploring, reproducing bugs and checking a fix; adapts as it goesSlow and uses many tokens; results vary run to run; not a regression suite
Playwright testsClaude (or you) writes test files in code; npx playwright test runs themFast, repeatable, cheap to run thousands of times, works in CISomeone has to write and maintain them
Computer useThe model looks at screenshots and moves a mouse and keyboard (Chapter 112)Works with any app, including desktop softwareSlowest; relies on reading pixels; more error-prone
In everyday life

Playwright MCP is like a colleague exploring the app while describing what they see: brilliant for finding things out. Playwright tests are the written checklist that a machine runs every night, the same way every time. Good teams use the first to discover and the second to protect. The workflow in this chapter moves from one to the other.

102.2How Playwright MCP "sees" a page

A web page has a hidden structure behind the visuals: headings, buttons, text boxes, links and checkboxes, each with a name. Browsers keep this as the accessibility tree so screen readers can describe pages to blind users. Playwright MCP sends Claude a text snapshot of that tree. Each element gets a short reference (like e8) that Claude uses when it wants to click or type.

A simplified idea of what a snapshot contains (TodoMVC page)
- heading "todos"
- textbox "What needs to be done?"      [ref=e8]
- list:
  - listitem:
    - checkbox "Toggle Todo"             [ref=e15]
    - text "Buy milk"
- text "1 item left"
- link "All"  - link "Active"  - link "Completed"

The real format has more detail, but the idea is the same: structured text, not pixels. This has real advantages:

  • No vision model needed. Any capable language model can read it.
  • Precise actions. "Click ref e15" is unambiguous; "click the small box on the left" isn't.
  • A built-in accessibility check. If a button has no accessible name, Claude literally can't tell what it is, and neither can a screen-reader user. That's a bug worth reporting (Chapter 123).

Screenshots are still available when you want them (for example, to attach to a bug report or check layout), through a screenshot tool, and an optional "vision" mode exists for pages that need coordinate-based clicking.

102.3Install it in Claude Code

The server runs on your own computer. Claude Code starts it with npx, which downloads and runs the latest published version of the package @playwright/mcp.

Terminal
claude mcp add playwright -- npx @playwright/mcp@latest
PartMeaning
claude mcp add playwrightRegister a server nicknamed playwright. Permission rules will call its tools mcp__playwright__….
--"Everything after this is the command that starts the server." Claude Code's own options go before it.
npx @playwright/mcp@latestDownload (if needed) and run the newest Playwright MCP release. No --transport is needed: local servers use stdio by default, talking to Claude Code through text streams (Chapter 99).

Playwright's own README shows the shorter claude mcp add playwright npx @playwright/mcp@latest. The version with -- is the form Claude Code's documentation recommends, and it's the safer habit once you start adding options.

Check it:

Terminal
claude mcp list

You should see playwright with a connected status. Inside a session, /mcp shows its tools. The first time it opens a browser, Playwright may need to download one; there's a tool for installing the browser if it's missing, and Claude will usually handle it.

Pinning a version

@latest always fetches the newest release, which is convenient for learning. For a team setup, pin a specific version (@playwright/mcp@ followed by the version number you've tested, which npm view @playwright/mcp version shows) so everyone gets the same behaviour and an update can't surprise you mid-sprint.

102.4Your first exploratory session

Start claude and try:

Prompt
Use the Playwright browser to open https://demo.playwright.dev/todomvc.
Describe what the page does and list the main controls you can see.

By default the browser opens headed, in a visible window, so you can watch Claude work. That's ideal while learning. Behind the scenes Claude calls tools like these:

ToolWhat it does
browser_navigateGo to a URL
browser_snapshotRead the page's accessibility snapshot
browser_click, browser_type, browser_press_keyInteract with an element by its reference
browser_fill_form, browser_select_option, browser_file_uploadFill several fields, choose from dropdowns, upload files
browser_wait_forWait for text to appear or disappear, or for a time
browser_take_screenshotSave an image of the page or an element
browser_console_messagesRead JavaScript errors and warnings: gold for bug reports
browser_network_requestsList the network calls the page made, such as failed API requests
browser_tabs, browser_navigate_back, browser_closeManage tabs, go back, close the browser
browser_evaluate, browser_run_code_unsafeRun JavaScript or Playwright code in the page: powerful, so keep these behind approval

Extra groups (network mocking, cookies and storage, PDF, vision and others) are switched on with the --caps option.

Exploratory prompts that work well

Prompts
Explore the to-do app like a curious first-time user. Try at least 10 different actions,
including unusual ones (empty input, very long text, emoji, double-clicking).
After each, note what happened. Then list anything that looks like a bug.

Check the browser console after each action and tell me about any errors.

Find every interactive control on this page that has no accessible name.

102.5Options that matter for testers

Options go after the package name, following the --. For example, to run headless in Firefox:

Terminal
claude mcp remove playwright
claude mcp add playwright -- npx @playwright/mcp@latest --headless --browser firefox
OptionWhat it doesWhen a tester uses it
--headlessRun without a visible window (headed is the default)Background runs; servers with no screen
--browser <name>chrome, firefox, webkit or msedgeCross-browser checks; WebKit is close to Safari
--device "iPhone 15" or --mobileEmulate a phoneMobile layouts. Mobile pages are often lighter, which also saves tokens
--viewport-size 1280x720Set the window sizeResponsive-design checks
--isolatedKeep the browser profile in memory only; nothing persistsClean sessions, like a new user every time
--storage-state <file>Start an isolated session with saved cookies and local storageStart already logged in as a test user
--test-id-attribute <name>Which attribute counts as a test ID (default data-testid)Match your team's convention, e.g. data-qa
--codegen <lang>Language for the Playwright code shown alongside actions (default TypeScript)Python or Java teams
--secrets <file>A dotenv file of secret values to hide from tool outputStops test passwords showing up in what Claude reads (a convenience, not a security guarantee)
--caps <list>Enable extra tool groups such as vision or pdfNetwork mocking, storage, coordinate clicks
--save-sessionSave the session into the output directoryKeep a record of an exploratory session
--config <file>Read all settings from a JSON fileTeam-wide, version-controlled setup

A configuration file keeps long option lists tidy:

playwright-mcp.json
{
  "browser": {
    "browserName": "chromium",
    "isolated": true,
    "launchOptions": { "headless": true },
    "contextOptions": { "viewport": { "width": 1280, "height": 720 } }
  },
  "testIdAttribute": "data-testid"
}
Terminal
claude mcp add playwright -- npx @playwright/mcp@latest --config playwright-mcp.json

102.6From exploration to a real test

Exploration finds things. Tests keep them fixed. Here is the hand-off.

1. Set up Playwright Test (once per project)

Terminal
npm init playwright@latest

This asks a few questions (language, test folder, whether to add a GitHub Actions workflow, whether to install browsers) and creates playwright.config.ts, a tests/ folder and an example test. Accept the defaults if unsure.

2. Ask Claude to write the test from what it just did

Prompt
You just added three to-dos, completed one and checked the counter.
Write that as a Playwright test in tests/todo-counter.spec.ts.
Use role-based locators (getByRole, getByPlaceholder) and web-first assertions (await expect(...)).
No fixed waits (no waitForTimeout). Then run it with npx playwright test.

You'll get something like this:

tests/todo-counter.spec.ts
import { test, expect } from '@playwright/test';

test('counter shows items left after completing one', async ({ page }) => {
  await page.goto('https://demo.playwright.dev/todomvc');
  const input = page.getByPlaceholder('What needs to be done?');

  for (const item of ['Buy milk', 'Write tests', 'Book dentist']) {
    await input.fill(item);
    await input.press('Enter');
  }

  await page.getByRole('listitem').filter({ hasText: 'Buy milk' })
            .getByRole('checkbox', { name: 'Toggle Todo' }).check();

  await expect(page.getByTestId('todo-count')).toHaveText('2 items left');
});
LinePlain English
test('…', async ({ page }) => {Define a test with a name; Playwright hands it a fresh browser page
page.getByPlaceholder(…)A locator: find the input by its placeholder text, as a user would
.fill(), .press('Enter')Type text, then press Enter
.filter({ hasText })…check()Find the list item containing "Buy milk" and tick its checkbox
await expect(…).toHaveText(…)A web-first assertion: Playwright keeps checking until it's true or times out, so no fixed sleeps are needed

3. Run it and read the result

Terminal
npx playwright test tests/todo-counter.spec.ts

The output says how many tests ran, with how many workers (parallel browsers), and ends with a line such as 3 passed (one per browser project in the default config). If something fails, Playwright prints the failing line and the difference between expected and actual. Open the visual report with:

npx playwright show-report
Real-world tip: prove the test can fail

A test that always passes is worthless. Change the expected text to '3 items left' and run it again: it must fail. Then change it back. Make this a habit with every AI-written test (Chapter 121).

102.7Logged-in sessions and test accounts

Most real applications need a login. There are three approaches:

ApproachHowWatch out
Persistent profile (default)The MCP browser keeps its own profile per project, so a login you complete stays for the next sessionOnly one browser can use a profile at a time; run extra clients with --isolated
Isolated + storage state--isolated --storage-state=auth.json starts every session already signed inauth.json contains session cookies: keep it out of git
Browser extension--extension connects to your own running Chrome or Edge, with its loginsClaude then acts with your real sessions; avoid this for production accounts
Test accounts only

Use dedicated test accounts on test environments. Never let an AI-driven browser loose in production with a real customer or admin account. Keep passwords out of prompts: use a storage-state file, or the --secrets option so values are masked in what Claude reads.

102.8Playwright's own test agents

Since version 1.56, Playwright itself ships three AI "test agents" that work with Claude Code and other tools. They're defined as instructions plus MCP tools, generated into your project:

Terminal (in a Playwright project)
npx playwright init-agents --loop=claude
PlannerExplores the app and writes a Markdown test plan in specs/
GeneratorTurns the plan into Playwright test files in tests/, checking locators live
HealerRuns failing tests, inspects the page and patches locators, waits or data until they pass

The planner uses a seed test that sets up the environment (logins, fixtures) and copies its style. Regenerate the agent definitions whenever you update Playwright.

A tester's caution about "healing"

Playwright documents that when the healer believes functionality is broken, it may mark the test as skipped rather than make it pass. Either way, a self-healing test can hide a real bug: a changed button label might be a deliberate redesign, or a regression. Review every healed change in a pull request, exactly as you would a colleague's.

102.9In CI, and how much it costs

  • Run tests in CI, not exploration. Your pipeline should run npx playwright test: fast, cheap and repeatable. Use MCP-driven sessions for investigation, triage and writing tests, not as the nightly regression suite.
  • Headless on servers. CI machines have no screen; use --headless if you do run the MCP server there. Microsoft publishes a Docker image (mcr.microsoft.com/playwright/mcp) that currently supports headless Chromium only.
  • Tokens add up. Every snapshot is text that fills Claude's context window. Big pages mean big snapshots. Keep sessions focused on one flow, and start fresh between flows (Chapter 68).
  • Consider the Playwright CLI. Playwright's README notes that coding agents may get the same job done with fewer tokens through the Playwright CLI combined with skills, while MCP remains better for long exploratory sessions that need continuous browser state.

102.10Safety

The Playwright MCP README is blunt: Playwright MCP is not a security boundary. Options like --allowed-origins help keep Claude on the right sites but don't stop a determined attack. So:

  1. Be careful with untrusted websites. A page can contain hidden text written to manipulate an AI (prompt injection, Chapter 131). Point the browser at your own test environments.
  2. Keep powerful tools behind approval. Allow the read-only tools you use constantly and make the code-running ones ask:
    .claude/settings.json
    {
  "permissions": {
    "allow": ["mcp__playwright__browser_snapshot", "mcp__playwright__browser_navigate"],
    "ask":   ["mcp__playwright__browser_evaluate", "mcp__playwright__browser_run_code_unsafe"]
  }
}
  3. Never use real customer data or production admin accounts.
  4. Pin versions for team use, and only install the official @playwright/mcp package. Look-alike package names are a known supply-chain trick (Chapter 105).

Common misunderstandings
"Playwright MCP replaces my test suite."
It's for exploring and writing tests. Repeatable regression testing should run as real Playwright tests.
"Claude is looking at screenshots."
By default it reads the accessibility snapshot, structured text. Screenshots are an extra tool.
"A test written by AI is correct if it passes."
It might assert the wrong thing, or nothing important. Read it, and prove it can fail.
"Self-healing tests mean no more maintenance."
Healing changes tests. Every change needs review, because a "heal" can hide a real regression.
"--allowed-origins makes it safe to browse anywhere."
It isn't a security boundary. Keep the browser on trusted test environments.

102.11Review

Key takeaways
  • Playwright MCP lets Claude drive a real browser step by step; Playwright tests are the repeatable, cheap way to keep checks running; computer use is the slow, general fallback.
  • It reads the page's accessibility tree as text snapshots with element references, not pixels.
  • Install with claude mcp add playwright -- npx @playwright/mcp@latest; options such as --headless, --browser, --isolated, --storage-state and --config go after the package name.
  • The core workflow: explore with MCP → have Claude write a Playwright test with role-based locators and web-first assertions → run npx playwright test → prove it can fail.
  • Playwright's planner, generator and healer agents (npx playwright init-agents --loop=claude) automate plan → test → repair; review every healed change.
  • It's not a security boundary: use test accounts on test environments, keep code-running tools behind approval, pin versions.
Check yourself

How does the Playwright MCP server mainly show a page to Claude?

Structured snapshots make actions precise and work without a vision model.

In claude mcp add playwright -- npx @playwright/mcp@latest --headless, what does -- do?

Everything after --, including --headless, is passed to the server.

What should your CI pipeline run every night?

Tests are fast, cheap and repeatable; MCP sessions are for discovery.

The healer agent changes a locator so a failing test passes. What should you do?

Healing can hide bugs. Treat it like any code change.

You need every MCP session to start logged in as a test user, with nothing left behind. Which options fit?

Isolated keeps nothing on disk; storage state loads the test user's cookies at the start.

Assignment

Pick one real user journey in your team's test environment (for example: log in, search, add to basket). Run a 20-minute exploratory session with Playwright MCP and record every observation. Then have Claude write the journey as a Playwright test following your team's conventions, prove it can fail, and open a pull request. In the description, list what the exploration found that you hadn't thought to test.

Teach it

"Playwright MCP gives Claude a real browser. It reads the page's structure, the same information screen readers use, then clicks and types like a user. Use it to explore, reproduce bugs and check fixes. Then ask Claude to turn what it did into a proper Playwright test, run it with npx playwright test, and prove it can fail. Keep it on test environments with test accounts, because it isn't a security boundary."
