Choosing a model is a trade-off between quality, speed, cost and control. Most jobs don't need the most capable model, and paying for it can turn a cheap nightly job into an expensive one. Start from the hard limits (where data may go, what the budget is, how fast the answer must arrive), shortlist two or three models that fit, and then test them on your real work. This chapter walks through twelve common scenarios so you can see that reasoning applied. The shortlists are starting points to test, not verdicts.

35.1Five questions before you pick

Most bad model choices come from starting with "which model is best?" Start with these questions instead, in this order. The early ones rule models out; the later ones rank what's left.

1. Where may the data go?Vendor API, your cloud contract, or only your own servers
2. How fast must it answer?A person waiting, or a job that runs overnight
3. How many times will it run?Ten a day or a million
4. How hard is the thinking?Sorting into labels, or reasoning across a codebase
5. What does a mistake cost?A mislabelled ticket, or a missed contract clause
In everyday life

Hiring for a job works the same way. You wouldn't hire a senior architect to sort the post, and you wouldn't ask a new starter to sign off the building's fire safety. First you check the hard rules (right to work, security clearance), then the hours and the budget, and only then do you compare skills. And before anyone's hired for good, there's a trial period.

The answers map onto three broad tiers, which every big family offers in some form (Chapter 31):

35.2A quick cost estimate

Before any scenario, learn this sum. It takes two minutes and stops most budget surprises.

The cost formula
cost per run = (input tokens  × input price  ÷ 1,000,000)
             + (output tokens × output price ÷ 1,000,000)

daily cost   = cost per run × runs per day

A rough rule for English is that one token is about three-quarters of a word, but tokenizers differ between families (Chapter 34), so measure real prompts when the number matters. Remember that "thinking" tokens from reasoning models are billed as output.

Worked example (illustrative numbers)

A support team triages 50,000 tickets a day. Each prompt is about 800 tokens (instructions plus the ticket) and each answer about 20 tokens (a label and a priority). That's 40 million input tokens and 1 million output tokens a day.

On Claude Haiku 5.5 ($0.10 / $0.50): 40 × $0.10 + 1 × $0.50 = $4.50 a day.
On Claude Opus 5.5 ($4 / $20): 40 × $4 + 1 × $20 = $180 a day.
Using the Batch API (50% off at Anthropic) halves either figure, if the answers can wait.

The token counts are illustrative; the prices are Anthropic's list prices on 9 November 2026. If Haiku labels the tickets well enough, the difference is about $64,000 a year.

35.3Scenarios 1–4: volume, length, code and control

Scenario 1 · Bulk ticket triage

Situation. 50,000 support tickets a day must be labelled (bug, question, feature request), given a component and sent to the right queue. Constraints: very high volume, simple decisions, a wrong label costs a few minutes of a person's time.

Shortlist to test: Claude Haiku 5.5, GPT-6 Luna, Gemini 3.8 Flash. Why: the task is classification, which fast models handle well, and volume makes price dominant. Use structured output (JSON with a fixed list of labels) and batch processing if same-day is fast enough. Trade-off: small models struggle more with vague or angry tickets. Send tickets the model marks "unsure" to a person or a bigger model (scenario 12).

Scenario 2 · Long contract or specification review

Situation. Legal and QA want every requirement in a 300-page supplier contract checked against the system specification. Constraints: long documents, low volume, a missed clause is expensive.

Shortlist: Claude Opus 5.5, GPT-6 Astra, Gemini 4 Argon. Why: all accept about a million tokens, so both documents fit in one request, and the work needs careful reasoning. Volume is tiny, so the price of the top tier hardly matters. Trade-off: a model can skim the middle of a very long input (Chapter 20). Ask for a quote and page reference for every finding, then spot-check them. For hundreds of contracts, switch to RAG or per-section prompts.

Scenario 3 · A coding agent in your test repository

Situation. A QA team wants an agent that writes and fixes Playwright tests across a large repository, runs them and opens pull requests. Constraints: long, multi-step sessions; mistakes are caught by review and CI.

Shortlist: Claude Opus 5.5 in Claude Code (Chapter 121), GPT-6 Astra or Sol in Codex, Gemini in Antigravity. Why: agentic coding rewards the most capable models, and the agent tool around the model matters as much as the model. Anthropic positions Opus 5.5 for "long-running agentic coding". Trade-off: cost per session can be high. Try Sonnet 5.5 for routine edits, and keep Fable 5.1 for problems where Opus 5.5 at higher effort still fails.

Scenario 4 · Data must stay on-premises

Situation. A bank's QA team wants AI help with production incident logs, but policy says the data can't leave company servers. Constraints: no external API calls at all.

Shortlist: open-weight models you can host: Mistral Large 4, DeepSeek V4 (MIT licence), Qwen3.8-27B (Apache 2.0), Meta's Muse Glimmer 30B (Apache 2.0), OpenAI's gpt-oss. Why: the hard rule removes every API-only model before quality is considered. Trade-off: you now run the hardware and the updates. The largest models (Mistral Large 4 is about 1T parameters) need serious GPU servers; a 27B–30B model runs on far less but is weaker. Check each licence with legal (Chapter 32).

A middle path

"Can't use a public API" doesn't always mean "must self-host". Some companies are allowed to use models through their existing cloud contract and region. Claude is available on Amazon Bedrock, Google Cloud and Microsoft Foundry. Ask your security team which rule actually applies before you buy GPUs.

35.4Scenarios 5–8: speed, budget, images and data

Scenario 5 · A low-latency help chat

Situation. An in-app help widget answers testers' questions about the test environment. Constraints: a person is waiting; the first words should appear in under a second or two.

Shortlist: Claude Haiku 5.5 (Anthropic lists it as the fastest Claude), GPT-6.1 Terra, Gemini 3.8 Flash. Why: what users feel is time to first token, and fast models with streaming give the best experience. Large reasoning models think before they answer, which feels slow in chat. Trade-off: harder questions get weaker answers. Ground the bot in your own documentation so it doesn't need to "know" things.

Scenario 6 · A cost-capped CI job

Situation. Every pull request triggers an AI review of changed test files, with a hard budget of $300 a month. Constraints: about 2,000 pull requests a month (illustrative), each sending 20,000 tokens and getting 1,500 back.

Estimate: 40M input and 3M output tokens a month. Sonnet 5.5 ($2 / $10): $80 + $30 = $110. Opus 5.5 ($4 / $20): $160 + $60 = $220. Both fit; Opus leaves little room for growth. Shortlist: Claude Sonnet 5.5 or GPT-6.1 Sol, with prompt caching for the fixed review instructions. Trade-off: set a maximum output length and a token cap in the job, and alert when spending passes 80% of budget (Chapter 90).

Scenario 7 · Vision on screenshots

Situation. Testers attach screenshots to bug reports. The team wants the model to describe the visual defect and suggest a title and severity. Constraints: image input; medium volume.

Shortlist: Claude Sonnet 5.5, GPT-6.1 Sol, Gemini 4 Argon or 3.8 Flash. Why: all these families accept images. For screen recordings, Gemini 4 Argon documents video input directly; with others, extract key frames first. Trade-off: models can miss small details such as a one-pixel misalignment, and they guess what a screen "should" look like. Pair this with real visual regression tooling (Chapter 123) rather than replacing it.

Scenario 8 · Generating test data

Situation. The team needs 5,000 realistic but fake customer records with edge cases (long names, accented characters, unusual addresses). Constraints: no real personal data; output must match a schema.

Shortlist: Claude Sonnet 5.5 or Haiku 5.5, GPT-6.1 Terra, using structured outputs against a JSON Schema. Why: generating synthetic data is creative but not deep reasoning, and the schema catches format errors. Trade-off: models repeat themselves at scale. Ask for edge cases explicitly, generate in batches with different seeds or instructions, and check for duplicates with code (Chapter 122).

35.5Scenarios 9–12: regulation, logs, everyday work and routing

Scenario 9 · Regulated data and data residency

Situation. A European healthcare client requires that patient-adjacent data is processed in a named region under a signed agreement. Constraints: legal, not technical.

Approach: the decision belongs to your legal and security teams, not to the benchmark tables. Options include a cloud platform contract in the required region (Claude on Bedrock, Google Cloud or Foundry; Gemini on Google Cloud; GPT on Azure), Anthropic's Enterprise options, or a European open-weight model such as Mistral Large 4 self-hosted. Regions and certifications change, so get the current list from the provider in writing. Trade-off: the newest model is sometimes available on the vendor's own API before every cloud region.

Scenario 10 · Analysing huge CI logs for flaky tests

Situation. A nightly run produces 600,000 tokens of logs, and the team wants a summary of which failures look flaky and which look real. Constraints: long input, runs every night.

Shortlist: pre-filter first, then Claude Sonnet 5.5 or Opus 5.5, GPT-6.1 Sol. Why: it fits a 1M window, but price tiers bite: Haiku 5.5 rises from $0.10 to $0.50 per million input tokens above 100K tokens, and Grok 4.7 doubles above 200K. A grep step that keeps only failing tests and their stack traces might cut the input by 95% (illustrative), making every option cheap. Trade-off: filtering can remove the clue. Keep the filter simple and log what it dropped (Chapter 122).

Scenario 11 · Everyday knowledge work in the app

Situation. A test manager wants help drafting release notes, summarising meetings and turning requirements into test ideas. Constraints: no code; low volume; uses the Claude app, not the API.

Approach: this is a plan and settings choice more than a model choice. In the Claude apps, the model picker and plan decide what's available (Chapter 43, Chapter 42). The default model is fine for drafting; switch to a more capable one for hard analysis. Trade-off: usage limits depend on the model and the length of chats, so very long conversations with the biggest model use up allowance fastest.

Scenario 12 · Routing: use two models together

Situation. Scenarios 1 and 5 both had a cheap model that's good enough most of the time. Approach: model routing. A cheap model handles every request first and reports its confidence or flags "unsure"; only those cases go to a more capable model. Another form escalates on failure: if the generated test doesn't compile, retry with the bigger model.

RequestTicket, question or task
Fast modelAnswers most cases cheaply
CheckConfident? Valid JSON? Tests pass?
EscalateOnly failures go to the capable model

Trade-off: more moving parts to build, monitor and test. The "unsure" signal itself must be tested: a small model that's confidently wrong never escalates.

Why a model's "confidence" is a weak signal on its own

Asking a model "how sure are you, 1 to 10?" gives a number, but that number is generated text, not a measured probability. Models can be confidently wrong, especially on questions where the input lacks the answer (Chapter 22). Stronger escalation signals are ones code can check: did the output parse as valid JSON, is the label in the allowed list, does the test compile and run, do two cheap attempts agree? Use self-reported confidence only alongside such checks, and measure how often escalation catches real errors.

Opinion · this textbook's authors

Teams more often overspend by defaulting to the biggest model than lose quality by choosing a smaller one, because nobody measures whether the smaller one would have been enough. Our suggestion: for any job that runs more than a few hundred times a day, test at least one model a tier below your first choice. That's advice from experience, not a measured rule.

Write and pressure-test a scenario card for your team30 min · Claude app (any plan) or any chat assistant
  1. Pick one real, repeated AI task in your team, for example "label incoming Jira bugs by component".One sentence describing the task.
  2. Answer the five questions from 35.1 in writing: where data may go, speed needed, runs per day, difficulty, cost of a mistake.Five short answers. At least one of them rules some models out.
  3. Estimate the tokens per run: paste one typical input into a word counter and divide words by 0.75. Do the cost sum from 35.2 for one fast and one capable model from Chapter 34.Two daily cost figures, often 10–40 times apart.
  4. Collect five real, anonymised examples with the answer you'd accept. In the Claude app, run all five with a fast model, then with a more capable one, using the same prompt.A small table: example, expected answer, fast model right or wrong, capable model right or wrong.
  5. Write your shortlist of two with one sentence of reasoning each, and one risk to watch.A one-page scenario card, ready to be tested properly with the harness in Chapter 36.

Troubleshooting. If you can't paste real data into a public tool, rewrite the examples with fake names and numbers first. If both models get all five right, your examples are too easy: add the awkward cases that cause arguments in your team.

Common misunderstandings
"Always use the best model; quality is worth it."
For high-volume, simple jobs the most capable model can cost 40 times more for no measurable gain.
"Always use the cheapest model; AI is AI."
Cheap models make more mistakes on hard reasoning and long inputs. Match the tier to the task.
"Five examples proved Model A is better."
Five examples are a sanity check, not evidence. Use a proper dataset and repeat runs (Chapter 36).
"We can't use AI because data can't leave the building."
Open-weight models can run in-house, and cloud contracts may already be approved. Ask which rule actually applies.
"Once chosen, the model is settled."
Prices, versions and retirements change every few months. Put a review date in the decision record.

35.7Review

Key takeaways
  • Ask five questions in order: data location, speed, volume, difficulty, cost of a mistake.
  • Hard limits (data residency, budget) rule models out before quality is considered.
  • Do the cost sum before committing: tokens × price × runs. Batch and caching discounts can halve it or more.
  • Fast models suit classification, extraction and chat; the most capable suit long agentic coding and high-stakes analysis.
  • Routing (cheap first, escalate on code-checked failures) often beats any single model.
  • Write a decision record with evidence and a review date.
Check yourself

What should you settle first when choosing a model?

Hard rules like data residency remove options before any quality comparison matters.

A job sends 40M input and 1M output tokens a day. At $0.10 / $0.50 per million, what does it cost per day?

40 × $0.10 = $4.00, plus 1 × $0.50 = $0.50.

Which is the strongest signal for escalating a request to a bigger model?

Code-checked failures are reliable; self-reported confidence is just generated text.

A nightly job sends 600K tokens of logs. Why might pre-filtering matter beyond the obvious saving?

Haiku 5.5 and Grok 4.7 both have higher rates for long prompts.

Your policy forbids sending data to any external service. Which is a valid shortlist?

Only open-weight models can run entirely on your own servers.

Assignment

Take the scenario card from the lab and turn it into a one-page proposal for your manager: the task, the five answers, the cost estimates for two models, the five-example results, your recommended shortlist and the risks. End with the question you need answered before testing properly (often a data-handling question for security).

Teach it

"Don't ask which model is best. Ask five things: where can the data go, how fast does it need to answer, how often will it run, how hard is the thinking, and what does a mistake cost. The first answers knock models out. Then do the sum: tokens times price times runs per day. A fast model can be forty times cheaper and good enough for labelling tickets, while contract review or a coding agent deserves the top tier. If it's mixed, run the cheap model first and escalate when a check fails. Then test properly and write the decision down."
